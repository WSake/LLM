## 0. 为什么需要"横向对比"：刀与工具的关系

上一章（07）回答"想把状态摊开，有多少种切法"——七把刀：DP/ZeRO/FSDP/TP/PP/SP/EP，每把切什么、省什么、付什么通信，都量化过了。本章换一个我们每天都在问的问题：**真到要训的时候，我该装哪个框架？**

答案不是"DeepSpeed 比 FSDP 好"——框架不发明切法，07 那七把刀就是全部切法。框架做的是三件事：

1. **打包**：把几把刀焊成一把顺手工具（DeepSpeed 默认背"ZeRO 三档 + offload"，Megatron 默认背"TP/PP/SP"，FSDP 背"ZeRO-3 语义按层物化"）。
2. **装配**：把模型、数据、训练循环、日志串成可跑的脚本（Transformers 是生态中枢，LLaMA-Factory 是 1-8 卡微调台，TRL/verl 是 RL 引擎）。
3. **取舍**：每个框架对"你能训多大、跑到什么档位"做了不同的默认。

知识地图 §17.3.8 把这件事的决策分成**三类选择**：模型库 → 预训练引擎 → RL 引擎。一个实用的心智：

> **先选族（你要做什么），再选族内的引擎（它帮你背哪些刀），最后用一张"最大可装表"兜底（装不装得下）。**

> 一句话（为什么有本篇）：**07 章说的是"有哪些刀"，本篇说的是"谁把刀打包成你用着顺手的工具"——选型不是比谁最好，是比"谁的默认组合正好装得下你这个模型、你这个卡数、你这个任务"。**

## 1. 一站全景：三类选择一张表

§4.8 原话是"同层比较，不评'谁最好'"。把它的表按"族"分列，先记住三族的分工（`framework_demo.py` A 段逐行打印这张画像）：

| 族 | 代表 | 帮你背哪几把刀 | 什么时候用它 |
|---|---|---|---|
| **模型库 / 接口** | Transformers · PEFT · Accelerate | 加载/分词/训练循环；PEFT 背 LoRA/QLoRA；Accelerate 背 DDP | 你要自己写训练逻辑，或只做单卡/小卡微调 |
| **预训练引擎** | DeepSpeed · FSDP · Megatron-LM/Core | ZeRO-1/2/3+offload+PP；ZeRO-3 按层物化；TP/PP/SP 3D | 全参训不动、要摊显存/提吞吐，或从头预训练 |
| **RL 引擎** | TRL · verl | 在引擎之上再叠 SFT/DPO/PPO/GRPO；verl 面向大规模 GRPO/RLVR | 对齐与推理模型 RL，成本在采样和双驻留 |
| 微调平台（横跨） | LLaMA-Factory · Axolotl · Unsloth | 把模型库 + PEFT + 部分引擎的常用组合再打包成一键/配置化 | 快、可复现，1-8 卡微调 |

一个框架通常跨族（TRL 内部就吃 Transformers + PEFT/FSDP），但**选型的第一决定是"族"**：你要做的是微调、预训练还是 RL，决定了你大概率停在哪一层。

> 一句话（全景）：**十二个框架不是十二种切法，而是同一套切法的四种打包方式（接口/引擎/RL 引擎/微调平台）——先问你是哪类任务，等于先走到正确的货架前。**

## 2. 怎么构造：四张可重算的选型表

真实对拍框架需要真实多卡集群，本篇不做——把"选型"做成一份能重算、能自检的决策账（`framework_demo.py`，全部确定性、无随机，三遍运行逐位一致）：

- **A 画像矩阵（账算）**：§4.8 表画像化，每框架一行：族 / 形态 / 承载的切法 / 一句话定位。
- **B 组装账（账算）**：同一份 06 章的 78.2 GiB，被 DDP / ZeRO-3 / FSDP / Megatron TP8×PP2 四种组装，逐卡数（2/4/8/16）填每卡三件套；70B 按同口径 ×10 外推。**看"框架换的是包装，账不变"。**
- **C 最大可装表 + 决策引擎（账算 + 断言自校）**：每卡 40 GiB 桌面、该组装每卡三件套 ≤ 40 GiB → 反解最大可装参数量 N；再把 §4.8 选型建议编码成确定性规则引擎，跑 4 个典型场景，所有关键数字用 `assert` 校准。
- **D 任务适配矩阵（账算）**：§4.8 五条选型建议的量表化 + LoRA/全参双路径收束。

> 一句话（构造选择）：**这章不发明新数字——所有账沿用 06/07 的 78.2 GiB 与切法，本章的产出是"把同一本账装进不同工具的格子"以及"装不装得下"的决策表；断言保证每张表与 06/07 的口径自洽。**

## 3. 先选族，再看框架帮你常备哪几刀（A/B 段）

A 段画像决定"族"，B 段组装账回答"同一份账，不同框架装出来每卡几 GiB"：

```text
[B] 组装账输出节选（每卡三件套 GiB）
    DDP（÷1，batch 切法）        78.2    78.2    78.2    78.2 │ ✗ 永远放不下
    DeepSpeed ZeRO-3（÷P）    39.1    19.6     9.8     4.9 │ ✓ 2 卡刚够、8 卡余量 4 倍
    FSDP（同 ZeRO-3 按层物化）     39.1    19.6     9.8     4.9 │ ✓ 稳态同 ZeRO-3
    Megatron TP8×PP2（÷16）       —       —       —     4.9 │ 16 卡组装
```

三个读数：

1. **框架不改变"省什么"，只改变"把哪几刀切到你手边"**：DDP 用哪个框架包着，在任何卡数下每卡都是 78.2 GiB（它切 batch，不切账本）；ZeRO-3/FSDP 在 2/4/8/16 卡是 39.1/19.6/9.8/4.9（÷P）；Megatron ÷16 只对 16 卡组装开放。**你以为在"选显存方案"，其实方案是 07 的切法定的，框架只是备好了哪几把。**
2. **40 GiB 桌面是一道现实门槛**：7B 全参 2 卡 FSDP = 39.1 GiB 刚够（07 章实践作业"FSDP 放两张卡"）、8 卡余量 4 倍；70B（×10 外推 782 GiB）则 8 张 80 GiB 卡也放不下（97.8 > 80）、16 卡 48.9 勉强、32 卡 24.4 有余。这就是为什么例 2 的 70B 决策要先问装不装得下。
3. **从组装看定位**：DeepSpeed/FSDP 是"分片数据并行"引擎（唯一背着 ZeRO-3 语义的），Megatron 是"层内+层段"引擎（TP/PP/SP，侵入模型结构）——**07 的七把刀，框架各有常备**；想要 TP/PP/SP，你就得走进 Megatron 那一格。

> 一句话（A/B）：**先选族定货架，再看族内引擎把哪几把刀常备在身上；账本数字 07 已给，本章只是把它们按组装方式重新排进表格——读表首要认清"省什么由切法决定，不由框架名决定"。**

## 4. 最大可装表：装不装得下是第一闸门（C 段）

`framework_demo.py` C 段把"选型"拉成一张可反查的表：**每卡 40 GiB 桌面，该组装能端住的最大 N**（三件套口径，不含激活/通信缓冲，是乐观上限）：

```text
[C] 最大可装表输出节选（参数上限 B）
    组装                    2 卡      4 卡      8 卡     16 卡
    DDP                 3.6B    3.6B    3.6B    3.6B
    ZeRO-1              5.4B    7.2B    8.6B    9.5B
    ZeRO-2              6.1B    9.5B   13.2B   16.4B
    ZeRO-3 / FSDP       7.2B   14.3B   28.6B   57.3B
    Megatron TP8×PP2      —      —      —   57.3B
```

三个读数：

1. **DDP 封顶 3.6B，卡数无关**：40 GiB 桌、三件套 12 B/参数，单卡全参最多 3.6B——切 batch 救不了"装不下"；要装 7B 以上，比 DDP 更高的任何档位都来自"分片"。ZeRO-1 到 ZeRO-3 档位间能差出一倍（8 卡：8.6 → 13.2 → 28.6B），因为优化器 52.2 GiB 是账本 2/3 的大头。
2. **÷P 档每翻倍卡数、上限翻倍**：ZeRO-3/FSDP 在 2/4/8/16 卡 = 7.2/14.3/28.6/57.3B。40 GiB 桌要端 70B 全参，ZeRO-3 一路推到 16 卡也只有 57.3B——不够，只剩 Megatron ÷16 这档（同为 57.3）或继续加卡。**这张表的第一用途就是"先做减法"：先划掉装不下的组装，剩下的才值得比较吞吐与工程。**
3. **诚实边界**：表只算权重/梯度/优化器三件套，不含激活——长序列/大 batch 时激活账（02-10）会直接压回桌面下方；TP 还有每层 4 次 all-reduce 的带宽账（07 D 段）。所以这张表是"上限"而非"额定"，写方案用它排高位，落地方案还要再叠激活与通信。

> 一句话（C 表）：**选型第一问不是"哪个框架顺手"，是"哪个组装装得下"——一张最大可装表把 78.2 GiB 和卡数对账，先划掉装不下的，再在剩下里讲吞吐与生态。**

## 5. 决策引擎：四个场景怎么走（C2 段）

C 段把 §4.8 的选型建议变成确定性规则，跑 4 个典型场景：

```text
[C2] 决策引擎输出节选
    Qwen2.5-7B · 2×40 GiB · SFT          → LLaMA-Factory（LoRA 路径）：LoRA ≈13.0 GiB 级单卡即可；FSDP 全参 39.1 GiB 刚够
    Llama-70B · 8×80 GiB · 全参 SFT      → DeepSpeed ZeRO-3/FSDP：每卡 97.8 GiB（✗）→ 需 ≥10 卡、对齐节点 @16 卡 48.9 GiB；或 PEFT 降档
    1B 从头预训练 · 8×40 GiB             → Megatron-Core/DeepSpeed：1B ≈11.2 GiB 单卡已装；ZeRO-1@8 ≈4.7 GiB/卡即够
    Qwen3-8B RLVR（GRPO）· 64×80 GiB     → verl：三件套摊到 1.4 GiB/卡；真成本在采样与双驻留
```

三个读数：

1. **小模型两路都通，按优先级挑**：7B 上 LoRA 单卡 13.0 GiB 级、全参 FSDP 两卡 39.1 刚够——两条路都装得下，于是才轮到比较"要速度（LoRA）还是要完整更新（全参）"。**装不装得下先筛掉一半，剩下的才轮到"偏好"。**
2. **同一张表挡掉了"硬塞 70B"**：8×80 GiB 装 70B 全参 = 97.8 GiB/卡 ✗；最小需 ≥10 卡、按 8 卡节点对齐取 16（48.9 ✓），或者降档 PEFT。**大模型的选型第一课就是：先读最大可装表，别让"想训练的雄心"撞上"装不下的显存"。**
3. **不同任务的成本中心根本不在同一本账**：1B 预训练三件套 11.2 GiB 单卡就装得下——预训练的真账在吞吐，ZeRO-1 摊开优化器（每参 4+8/8 = 5 B → ≈4.7 GiB/卡）就够，TP/PP 留给更大模型；8B RLVR 三件套 @64 卡摊到 1.4 GiB——RL 的真成本在采样生成与策略/参考双驻留（05 章 GRPO 的账），不在这套三件套。**先确定成本中心，再选族，然后才是引擎。**

> 一句话（决策引擎）：**四例各按"族 → 装不装得下 → 成本中心"三步走完：小模型比偏好、大模型先做减法、预训练看吞吐、RL 看采样与双驻留——每个例子的关键数字都被 assert 锁死，输入同样的场景永远得到同样的推荐。**

## 6. 任务矩阵与双路径收束（D 段）

D 段把 §4.8 的五条选型建议表量化，并把 06/07 两本账收束成"LoRA/全参双路径"：

| 场景 | 推荐栈 | 依据 |
|---|---|---|
| 个人 / 单卡微调 | Transformers + PEFT + Unsloth | 生态最顺；LoRA 13 GiB 级单卡可跑 |
| 中小团队 1-8 卡微调 | LLaMA-Factory / Axolotl | 一键/配置化、可复现 |
| 预训练 / 大集群 | Megatron-Core / DeepSpeed | TP/PP/ZeRO 万卡级、吞吐账 |
| RL / 推理模型 | verl / TRL | GRPO/RLVR 大规模 |
| 国产算力（NPU） | MindSpore / PaddleNLP | 生态绑定算力 |

三个读数：

1. **"谁最好"没有，只有"谁这一格最顺手"**：§4.8 原话是"同层比较，不评谁最好"。单卡 LoRA → Transformers+PEFT 生态最快；1-8 卡上表即用 → LLaMA-Factory；十万卡预训练 → Megatron；RL → verl。**选型表是"场景→解答"的映射，不是排行榜。**
2. **LoRA/全参双路径是两本账的收束**：路径① PEFT（06 的减负）——LoRA 7B ≈ 权重 13.0 + 可训练子集约 0.02 ≈ 13.0 GiB 级、QLoRA NF4 主权重 ≈3 GiB 级（账算）；路径② 全参 + 并行（07 的摊匀）——7B + ZeRO-3@8 = 9.8 GiB、FSDP 同语义按层物化。**两条路在 7B·2×40 相交：LoRA 单卡走、FSDP 全参两卡走。**
3. **生产常搭档 LoRA + FSDP 的原因落回 07 的账**：LoRA 把每卡要同步的梯度压到通信近乎白送（07 B 段：ring all-reduce 61.2 → reduce-scatter 30.6 ms 那一级再往下），FSDP 让基座权重也能进 40 GiB 桌——**06 的减负与 07 的摊匀不是二选一，是同一个方案的两半。**

> 一句话（D 段）：**选型最终落在"场景 × 装得下"的交点上；LoRA 与 FSDP 在 7B 场景两路同通、在 70B 场景只能二选一——读这张矩阵比记框架名有用，它把"你该用啥"翻译成一格。**

## 7. 常见坑

**① 拿框架名当"显存方案"。**
DDP 用任何框架包着，每卡都是 78.2 GiB（B 段）。省不省由 07 的切法决定，不由框架名决定——先问"我切到哪一档"，再问"哪个框架帮我切"。

**② 只算三件套就下单。**
C 表是乐观上限，不含激活与通信缓冲。长序列/大 batch 一上，激活账会把 7B 从"9.8 GiB 稳坐"拉回桌面边缘——落地方案把 02-10 的激活账叠回去。

**③ 小模型照抄大模型组装。**
1B 预训练三件套 11.2 GiB，单卡就装得下；为了"先进"上 Megatron TP8×PP2，吞吐账反而难看（07 D 段 TP 通信敏感）。**组装跟着"成本中心"走，不跟着"最高档位"走。**

**④ 全参装不进就往"硬塞"。**
70B 全参 8×80 GiB = 97.8 GiB ✗，硬塞只会 OOM/UFO。正确做法是最大可装表先做减法（@16 卡 48.9）或降档 PEFT——**选型的第一个动作永远是查表，不是调参。**

**⑤ RL 用微调框架硬跑。**
GRPO/RLVR 的成本中心在采样与策略/参考双驻留（05 章 GRPO 账），不在三件套——三件套 @64 卡只有 1.4 GiB/卡反而是陷阱。**RL 选 verl/TRL 这类 RL 引擎，微调选微调平台，别拿"能不能训"当"该不该用"。**

**⑥ 过度绑定"谁最好"。**
§4.8 原话"同层比较，不评谁最好"。对着场景表选，别把某一个框架当信仰——换卡数、换任务、换成本中心，"正确格"就变了。
