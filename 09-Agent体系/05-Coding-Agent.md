## 0. 为什么第 5 课是「Coding Agent」？

04 把行动推理范式讲全了：ReAct 的 T→A→O 骨架、Reflexion 的执行器外验、Self-Refine 的无执行器内验、ToT/LATS 的树搜索。但 04 的账全是"模拟任务"——排序函数、文案打分，那台"执行器"是我们手工喂的真实性。**本篇是把这些范式丢进一个它们最能吃的真金白银领域：代码。**

§9.11 开宗明义：**为什么是 Agent 的最佳落地？因为代码任务是"可验证的"——测试/编译器就是执行器真值，自动评测与强化学习燃料都齐了。** 这句话把 04 的账全部升级：

- **04 账 A 的 A==O 不变式**：在代码域里，O 不再是"我们编的观察"，而是**编译报错 / 测试输出**——客观、可复现、逐行可读。Reflexion 的"反思"第一次有了不靠感觉的反馈源。
- **04 账 B 的执行器外验**：有测试真值 → 走 Reflexion（看报错改代码）；04 里的排序函数 1/3→3/3，本篇直接继承并加上"Edit→Run→Observe"的回路计时。
- **03 账 D 的"代码即计划"**：Coding Agent 的补丁 = 一份可增删改的执行计划，测试就是它的验收。**计划节点那套"验证回路"从词面规则验证器升级成真编译/真测试。**

所以本篇不是"又一个 Agent 系统"课，而是**把 01–04 攒的四件技能（Loop · 护栏 · 计划 · 行动推理）组装成 09 章第一个能交付的形态**：能改代码、跑测试、修 bug 的 Agent（§17.7.7）。§9.11 的趋势一句话收束：**先做"能过测试的函数"，再做"能改仓库的 Agent"**——这就是本篇的叙事主线：账 A·C 在"函数"层，账 B·D 在"仓库与提交"层。

## 1. 先把问题拆开：代码任务凭什么最值钱

不是所有任务都适合当 Agent 试验田。§9.11 说代码是**最好**的试验田，拆开是四条独有性质：

| 性质 | 代码任务的独有面 | 对 Agent 意味着什么 | 卡住的其他领域 |
|---|---|---|---|
| **可验证** | 测试/编译器给出客观对错 | Observation 有执行器真值，Reflexion 有反馈源（账 A） | 文案、对话全靠"看起来像"→ Self-Refine 内验 |
| **可回放** | 每次运行结果确定 | 多分支并行、回退、复现都便宜（账 C·D） | 物理/人交互不可重放 |
| **模块化** | 符号/文件/行是天然切片 | 仓库导航有抓手：索引问相关、grep 管精确（账 B） | 长文档无符号边界 |
| **有终结条件** | 测试通过 = 明确验收 | 评测有可验证终结条件，不用 LLM-judge（§9.12，账 D） | 开放任务终止判据模糊 |

一句话：**"可验证"让 Observation 从"模型说"变成"环境说"，RL 燃料才齐——这正是 §9.11 立项的理由。** 本篇四账全部围绕这条性质展开：

1. **会改函数吗？** —— 测试回路的闭环速度：看报错 vs 盲改（账 A）。
2. **能找到要改的地方吗？** —— 仓库导航的成本分摊：全读 / 索引 / grep（账 B）。
3. **会同时试多个修法吗？** —— 多分支并行：3 步 vs 6 步（账 C）。
4. **敢合入吗？** —— 评测闸 + 安全分诊：过全套测试才接受、高危动作人工确认（账 D）。

## 3. 实验 A · 测试回路账：Action=Edit，看报错才收敛

同一个"排序函数比较方向反了"的 bug（v0：期望 `[3,4,5]` 实得 `[5,4,3]`，测试 1/3），两套修法：

```
① 看报错（Reflexion 式 = 04 账 B 的代码域实例）：
   v0 测试 1/3 失败 → 报错读入『test2 期望[3,4,5] 实得[5,4,3]』→ 判定：比较方向反
   v1 反转比较方向 → 测试 3/3 通过（终局）          —— 尝试 2 次 · 跑测试 2 次 · 测试输出 1/3 → 3/3

② 盲改（只看通过数，报错内容不用）：
   v0 1/3 → 盲改『加 try/except』1/3 → 盲改『改用 sorted() 重建』2/3 → 盲改『反转比较方向』3/3
                                                    —— 尝试 4 次 · 跑测试 4 次 · 测试输出 1/3 → 1/3 → 2/3 → 3/3
```

| 修法 | 尝试 | 跑测试 | 测试路径 | 收敛判据 |
|---|---:|---:|---|---|
| 看报错（Reflexion） | **2** | 2 | 1/3 → **3/3** | 每条修改后必有一次测试观察 |
| 盲改（只看通过数） | **4** | 4 | 1/3 → 1/3 → 2/3 → 3/3 | 同样收敛，但多烧 2 次尝试 |

三个直接结论：

1. **两条路都收敛 3/3，但代价不同**：看报错 **2** 次尝试，盲改 **4** 次——差的那 2 次就是"没看报错内容"交的学费。**测试/编译输出是代码域的执行器真值（04 账 A 的 A==O 不变式在此兑现）：Observation 是收敛的唯一注释。**
2. **Reflexion 不是玄学，就是"跑→读→改→再跑"**：04 账 B 的排序函数在"反思写记忆"层；本篇把它落进"测试回路"——**Action=Edit、Observation=测试输出、Reflexion=看报错改代码**，一行测试日志锁死闭环。
3. **每条修改后必有一次观察**（断言 3/3）：没有这次观察，下一轮 Edit 就是盲改。这正是 §9.12 "可验证终结条件"的微观版本——**每一轮都有终结判据，不是最后才验收。**

> 探针断言：refl 尝试 2 < blind 4 · 双方终局 3/3 · 每条修改后必有测试观察，全部锁定。
> 挂靠：04 账 B Reflexion 外验（v0 1/3→反思→3/3，本篇直接继承并升级成 Edit→Run→Observe 回路）；06-05 工具错误回喂自愈 3/3（测试失败=工具的报错消息，回喂→修正，同一机制）。

## 4. 实验 B · 仓库导航账：索引问『哪个相关』，grep 管『哪一行』

任务从"改函数"升到"改仓库"：要在 18 个文件的迷你仓库里，找到**排序函数 + 它依赖的常量**两处才能动刀（§9.11 核心技术第 1 项"仓库索引 RAG over codebase"）。三种找法，报读 token 与命中目标：

| 策略 | 读 token | 命中 | 说明 |
|---|---:|---:|---|
| 全仓直读（长上下文暴力） | **100%** | 2/2 | 保底：一定命中，但给全部 18 文件买单 |
| 仓库索引 top-6（语义检索） | **26%** | **1/2** | 漏 1 目标：依赖常量语义近 ≠ 词面命中 |
| 仓库索引 top-8（加宽召回） | **44%** | 2/2 | 2/2 命中，仍读 44% 陪跑 |
| 符号/grep 切片（词面精确） | **6%** | 2/2 | 已知符号名直接定位，最省 |

三个直接结论：

1. **成本三档差 16 倍，命中可以一样**：全读 100%·命中 2/2，符号切片 6%·命中 2/2——**对已知符号名，"grep 到行"就是最省的入口**。长上下文暴力不是能力，是钱包（08-06 的 k 成本线 154.4/307.9/614.1 字符同一本账）。
2. **检索漏项由词面兜底，互为备份**：索引 top-6 语义近却漏了依赖常量（1/2）——**语义检索回答"哪个文件相关"，词面 grep 回答"哪一行精确"**，两者是分工不是替代（§9.11 "仓库索引"的真实姿态）。top-8 靠加宽召回补回 2/2，代价是 44% 陪跑。
3. **这就是 §14.4 的"代码问答→改仓库"路线**：先 RAG over repo 让 Agent 知道代码在哪，再 Edit 工具精确落刀——本篇账 B 量的是"知道在哪"这一半花了多少钱。

> 探针断言：命中全 2/2（除 top-6 漏 1）· 成本 100 > 44 > 6 · 检索/词面互补，全部锁定。
> 挂靠：08-10 Agentic RAG 的检索决策账（judge 省 25.4% 上下文——Agent 决定**要不要查**，本篇决定**查到哪一层**）；08-02/08-06 的分块与压缩（token 切片是仓库导航的同款剂量）。

## 5. 实验 C · 并行多分支账：算力换墙钟

一个 bug 两个候选假设：A「改比较方向」、B「改测试期望」。每假设 = 写测试 1 步 + 实现 1 步 + 跑 1 步 = 3 步。顺序跑（A 失败再 B）vs 并行跑（A‖B 同时）：

| 打法 | 写+实现+跑 | 墙钟步数 | 测试运行 | 结果 |
|---|---:|---:|---:|---|
| 顺序 | A 3 步失败 → B 3 步通过 | **6** | 2 | 取 B |
| 并行 | A、B 同时 3 步 | **3** | 2 | 取通过分支 |

两个直接结论：

1. **墙钟省 50%（6→3 步），测试运行次数不变（2 次）**——并行不增加验证开销，只翻倍算力。**这是"算力换墙钟"：评估成本（测试次数）锁死，探索宽度翻倍。** 多分支是 04 账 C ToT 在代码域的形态：**测试真值 = 价值函数**，哪条分支过测试取哪条。
2. **顺序打法的浪费不在测试，在等待**：B 明明先被验证也对，但必须等 A 跑完 3 步才知道。§9.11 把"并行探索多分支"列为核心技术，正是因为**代码测试廉价可回放**，多开几个 worker 跑测试几乎零边际成本。

> 探针断言：并行 3 < 顺序 6 · 测试次数同 2，全部锁定。
> 挂靠：04 账 C ToT/LATS 树搜索（贪心 12 < ToT 21 < 穷举 120 eval；本篇是 2-分支特例：2 eval 次不变、墙钟因并行减半）；前后呼应账 A——并行分支的每条也都要"有观察"，先跑先看。

## 6. 实验 D · 评测闸与安全台账：可验证终结条件 + 最小权限

§9.12 的"好的 Agent 评测 = **固定环境 + 可验证的终结条件 + 成本指标**"落到提交前那一刻：**3 份候选补丁，过全套测试才接受，否则回退不落盘**：

| 补丁 | 测试结果 | 裁决 | 落盘 |
|---|---|---:|---|
| p1 | 0/3 | 回退 | ✗ |
| p2 | **3/3** | **接受** | ✓ |
| p3 | 2/3 | 回退 | ✗ |

**接受 1/3 · 回退 2/3**——终结条件不是"模型说修好了"，是"3/3 全绿"（§9.12 原话：不要用"看起来像"的 LLM-judge 替代环境真实验证）。成本指标 = 测试运行次数 / 步数（账 A 已量：看报错 2 次 vs 盲改 4 次——评测闸的每一轮都不是免费的）。

测试过了还不够，§9.13 的**基线护栏**接着上线——操作风险分诊（7 个操作，高风险的必须人工确认）：

| 操作 | 层级 | 决策 |
|---|---|---|
| read file / grep 符号 | 只读 | 自动 |
| edit 测试文件 / edit 源码文件 | 改动 | 自动 |
| **改生产配置** / **删除分支·rm** / **发布·push 生产** | **高风险** | **人工确认** |

**高风险 3/7 全拦截**。§9.13 基线护栏原文："最小权限 + 沙箱执行 + **人工确认高风险动作** + 输入输出内容过滤 + 审计日志 + **可回滚**"——账 D 量化的是其中两条：**高风险动作人工确认（3/7）** + 可回滚就是 p1/p3 的"回退不落盘"（2/3）。这正是 §9.14 趋势① **Agent 系统化：评测 + 护栏 + 人工审批进生产**。

> 探针断言：补丁接受 1/3 · 危险操作 3/7 拦截，全部锁定。
> 挂靠：09-02 账 B 人工确认分诊 1/1（本篇是它放大成 7 操作台账）；06-05 工具调用自愈 3/3（评测闸与函数校验同一把尺：Schema 兜形状、测试兜行为）；SWE-bench Verified 2025 事实标准 = 要素事实（固定环境 + 可验证终结 + 成本指标的工业级实例）。

## 7. 这篇 Coding Agent 怎么用（一页带走 + 掌握度检验）

一页带走（四条硬记忆 + 一条主线）：

```
④ 一条主线：先做"能过测试的函数"，再做"能改仓库的 Agent"（§9.11 趋势）——账 A·C 是函数层，账 B·D 是仓库·提交层
① 测试回路（账 A）：Action=Edit · Observation=测试/编译输出 · Reflexion=看报错改代码 —— 看报错 2 次 vs 盲改 4 次，Observation 是收敛的唯一注释
② 仓库导航（账 B）：索引问"哪个相关"（top-6 只 26% 但漏依赖）、grep 管"哪一行"（6% 最精确），检索与词面互为兜底 —— 全仓直读 100% 是最贵的保底
③ 并行多分支（账 C）：测试廉价可回放 → 并行 = 算力换墙钟，3 步 vs 6 步，测试次数不变（多分支 = 04 账 C ToT 的代码域形态）
④ 评测闸 + 护栏（账 D）：过全套测试才接受（1/3 接受 2/3 回退）· 高风险操作 3/7 人工确认 = 最小权限（§9.12 固定环境 + 可验证终结条件 + 成本）
```

**掌握度检验**：不看资料，回答四个问题——(a) 一个"排序方向反了"的 bug，拿到测试输出『期望[3,4,5] 实得[5,4,3]』，下一步你会改什么？（不动手工，直接说改哪行、改完干嘛）(b) 一个 50 文件的仓库要你改 A 函数，你手头有符号名、有 embedding 索引、有全仓上下文 1M，你按什么顺序找、每步看多少 token？(c) 同一 bug 你有两个候选修法，为什么不串行跑而并行跑？并行省了什么、花了什么？(d) 一个补丁 2/3 测试过了，你敢合入吗？为什么？哪些操作必须等人？（答案：(a) 改比较方向，改完立刻重跑测试（账 A：每改必观察）；(b) 符号名→grep 切片 6%·2/2 起步，搜不到再用索引 top-8 兜底——索引问相关、grep 管精确（账 B）；(c) 并行省墙钟 3 步 vs 6 步，测试次数不变；花的是算力（账 C）；(d) 不敢，2/3 不过全套测试自动回退；改生产配置/删分支/发布这类高风险操作必须人工确认（账 D：3/7 拦截）。**答不全 = 回看账 A 的 blind 与账 D 的 3/7。**）

## 8. 常见坑（Coding Agent 的 6 个）

1. **把"模型说改好了"当验收**：LLM 输出自然语言"改好了" ≠ 测试通过。一测就红——**验收只认测试输出，不认"看起来像"（§9.12 原话）**。看账 A refl 与 blind 的差别：差在有没有"读"真值，不是差在提示词。
2. **全仓直读当默认导航**：拿长上下文把 18 个文件全塞进去。找到是找到了，但为保底付了 100% token——**8-RAG 同款剂量账：先字幕切片 6%，检索兜底 44%**（账 B）。
3. **看测试只数过几个、不读报错内容**：看过 pass/fail 数就当观察了。v0 1/3 失败，数数不知道错哪，读『期望[3,4,5] 实得[5,4,3]』才知道方向反了——**Observation 的价值在内容，不只是状态**（账 A blind 的教训）。
4. **检索漏了就以为检索没用**：索引 top-6 漏依赖常量，就下结论"仓库索引没用"。这是把"问哪个相关"的工具拿来干"哪一行精确"的活——**漏项交给 grep 兜底，分工不是缺陷**（账 B）。
5. **串行跑多个候选修法**：修法 A 跑了 3 步失败才跑 B。测试廉价可回放，**并行省一半墙钟、测试次数不涨**——只有不可回放或资源受限才被迫串行（账 C）。
6. **测试过了就直接合入**：p2 3/3 接受没问题，但"3/3"不等于"可以上生产"——**改配置 / 删分支 / 发布这类高风险动作，测试全绿也得人工确认（§9.13 最小权限）**，且失败补丁要能回退（账 D：回退 2/3）。
