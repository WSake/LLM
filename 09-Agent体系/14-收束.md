## 0. 为什么第 14 课（收官篇）是「Agent 框架生态」？

09 章从 01 的「Agent 定义与演进谱系」一路走到 10 的「浏览器 Agent」——你学过了**个体**（五要素公式、六状态机主循环、计划/推理/自纠错三件雕琢脑子的事）、**动作**（代码/浏览器/电脑三个让手脚落地的形态）、**治理**（评测台、六护栏、人工审批）、**网络**（多智能体的拓扑与信任）。每一个新任务来了，脑子里都有一张局部的地图：

- 修 bug → 想到 05 Coding Agent 的测试回路；
- 抓网页 → 想到 10 浏览器 Agent 的 DOM；
- 老系统报表 → 想到 09 Computer Use 的确认框 + 回滚；
- 多部门调研 → 想到 08 多智能体的星型拓扑 + 协调税；
- 单步问答 → 想到 06-05 工具调用 + schema 校验。

**但知识点还是散在十篇里的。** 收官篇做一件事：**把它们串成一张图上线**。§9.14 给的就是这张图的骨架——**生态分四层**（协议→运行时→平台→应用）像一张"世界地图"，**五大趋势**（系统化/长时/多模态/端侧/推理融合）像五条主力航线，而 01-10 的知识点就是这条航线上一个接一个的**站**。本篇四账把这张图"铺开 → 走一遍 → 标航线 → 检验落地"：

- **账 A 铺开**：12 个生态代表（你已经在 07 章和 09 章见过的一大半）各就各位落进四层，验证"分层"不是"排名"——每层管一段，LangGraph 和 Dify 不竞争；
- **账 B 走一遍**：同一 3 个真实 Agent 应用沿四层叠起来——原来真实产品永远是"协议连工具 + 运行时画循环 + 平台托管发布 + 应用定形态"四件事一起做；
- **账 C 标航线**：五条趋势 × 每条≥1 个已交付锚点——你要的不是"2026 新知识"（那不现实），是把已经学过的数字归档到趋势名下（复习链）；
- **账 D 检验落地**：5 个全新任务，每行都答出"动作落哪层 + 怎么验证 + 什么护栏 + 什么终结 + 单还是多"——五项全部命中 01-10 的已交付篇 = 09 章毕业，拿到那张"任务→方案"的坐标纸。

**和 09 章开篇（01 的定义课）是什么关系？** 01 答"Agent 是什么、有什么类型"，收官答"Agent 从书里到生产，工程上分哪些层、一线有什么可用件、趋势往哪走"——**开篇给概念全景，收官给工程全景图**。对走路线 B（应用/工程）的你尤其值：这张图就是 07 章框架层（真引擎）与 09 章 Agent 层（真问题）之间那座桥的桥头堡。

**首先把『四层』的单位说清——这不是产品排名，是"管的问题不同"。** 新手最常见的误会是把 LangGraph 和 Dify 放一起比"谁更好"——它们根本不打架：

1. **协议层（MCP/A2A）管"怎么连"**：MCP 把工具/数据源暴露成任意 Agent 可调的标准接口（07-11 你实测过：把工具包成 MCP server，任何 Agent 会调 MCP 就能用）；A2A 管"Agent 与 Agent 之间"的消息。这一层的产品不出"智能"，出"插头标准化"——**没有协议层，十个厂家的 Agent 各说各话，工具互不相识**。
2. **运行时层（LangGraph/Agents SDK/ADK/Pydantic AI）管"循环怎么跑"**：单 Agent 的主循环、工具编排、状态（checkpoint）在这层实现。07-02 你真实跑过 LangGraph 1.0.10：显式图状态机、中断恢复补 2 步不重跑。**这一层是"Agent 的骨架和保险丝"**。
3. **平台层（Dify/Coze/Agent 云）管"怎么托管发布"**：低代码编排 + 部署运维 + 日志可观测 + 发到渠道（IM/网页）。07-04 你实测过 Dify 的工作流托管。**这一层把"能跑的 Agent"变成"可运营的产品"**，绝大多数业务用户接触的是它。
4. **应用层（浏览器/电脑/代码）管"任务形态"**：Agent 的动作落在一个具体的世界里——浏览器（10-10 DOM 结构）、桌面 GUI（09-09 视觉语义）、代码仓库（05 测试回路）。**应用层不是框架，是"手往哪放"**：§9.14 原文给出的三形态正好就是 09 章最后三篇的动作层。

**再看『五大趋势』——它们是"105 章十篇知识"的收件箱。** 2026 年如果你只看新闻，'Agent 生态'是一团雾；但你已经有 01-10 篇打底，就能把每条趋势**归档到具体篇目和数字**上（账 C 逐一做）。§9.14 的第五句尤其狠——**"thinking 模式就是 Agent 的第一步思考"**：推理模型预先把"想清楚再动手"内置进模型，Agent 框架的 Thought 层被模型吸收，框架只剩 行动/观察/反思（04 的 2025 融合账）——**这就是趋势⑤的本体**。

## 3. 实验 A · 生态分层账：协议→运行时→平台→应用，每层管一段

把 §9.14 第一行"分层："展开——12 个**你在 07 章和 09 章都见过面的代表**，各落进四层之一。判定标准不是"谁大牌"，是**"它在解决 Agent 的哪个问题"**：

| 代表 | 层 | 它在这一层解决什么 |
|---|---|---|
| MCP | 协议 | 把工具/数据源暴露成 Agent 可调的标准接口 |
| A2A | 协议 | 跨 Agent 协作的消息协议（跨厂商） |
| LangGraph | 运行时 | 显式图状态机：节点+边+checkpoint（07-02 真引擎） |
| Agents SDK | 运行时 | 轻量 Agent 运行时：handoff/工具/追踪 |
| ADK | 运行时 | Agent Development Kit：编排 Agent |
| Pydantic AI | 运行时 | 类型安全 Agent：schema 即边界 |
| Dify | 平台 | 低代码托管：工作流+发布+可观测（07-04 实装） |
| Coze | 平台 | 托管：插件+发布到 IM/网页 |
| Agent 云 | 平台 | 厂商托管：部署/运维/弹性 |
| 浏览器 Agent | 应用 | 任务形态①浏览器（10-10 DOM+视觉落地） |
| Computer Use | 应用 | 任务形态②电脑（09-09 视觉 GUI 落地） |
| Coding Agent | 应用 | 任务形态③代码（05 测试回路落地） |

**归类 12/12 断言全过 · 每层代表 ≥2 家（协议 2 / 运行时 4 / 平台 3 / 应用 3）。** 三个读数：

**第一个，分层判据是"它解决问题的性质"，不是"它多拽"。** 同一个框架（比如 LangGraph）为什么是运行时不是平台？——因为它的职责是**把 Agent 的循环画清楚**（节点、边、状态、checkpoint），它不帮你发布到微信群、不帮你做账号体系。Dify 恰好反过来：它也编排工作流，但**它的出厂职责是把流程托管 + 发布 + 可观测**。**判层三问**：它主要解决『怎么连』→ 协议；『循环/状态怎么画』→ 运行时；『怎么托管运营』→ 平台；『手往哪放』→ 应用。混淆的根源通常是"平台都内置了运行时、运行时也带托管"——但**看它存在的"首因"，不看附赠**。

**第二个，"每层 ≥2 家"保护你不做单选题。** 协议层 2 家（MCP 连工具、A2A 连 Agent）、运行时 4 家（图式 LangGraph / 轻量 Agents SDK / 编排 ADK / 类型安全 Pydantic AI）、平台 3 家（开源 Dify / 闭源 Coze / 云厂商托管）。**这正好和 07-00 框架分类学的结论呼应**：不是"选一个全家桶"，而是"每层选一个顺手的、把四层组装"。你手里其实已经有了——07 章真引擎实测过 LangGraph 和 Dify，07-11 实测过 MCP，本篇只是把它们挪到正确的那一层。

**第三个，应用层是唯一"不是框架"的层——它是任务形态。** 浏览器/电脑/代码不是"框架"，是"Agent 的手落到哪个世界"：§9.14 原文的三形态，**逐一对应 09 章最后三篇的动作层**（10-10 DOM、09-09 GUI、05 测试回路）。这对工程人是个强提示：**好消息是应用层你已经全学过了**（09 章 05/09/10 三篇就是这三形态的完整拆解），本篇不用再学新东西。

**账 A 的总结论（断言 12/12 全过）**：

> **生态分四层、每层管一段：协议（MCP/A2A）管『怎么连』、运行时（LangGraph/Agents SDK/ADK/Pydantic AI）管『循环怎么跑』、平台（Dify/Coze/Agent 云）管『怎么托管运营』、应用（浏览器/电脑/代码）管『手往哪放』。12 个代表 12/12 落对层、每层 ≥2 家；分层不是『谁更好』是『每层管一段』——判层三问（怎么连→协议；循环→运行时；托管→平台；形态→应用），混淆时就问它存在的『首因』。**

## 4. 实验 B · 四层装配账：真实产品是四层叠起来，不是四选一

账 A 把层分清了，账 B 立刻把层"叠回去"——**同一 3 个真实 Agent 应用 × 四层**，每格选一个代表性实现，看真实产品到底长什么样：

| 应用 | 协议层（连什么） | 运行时（循环怎么跑） | 平台（怎么托管） | 应用（任务形态） |
|---|---|---|---|---|
| 客服机器人 | MCP（接订单/库存工具） | LangGraph（客服状态图·重试·checkpoint） | Coze（托管+IM 渠道发布） | 对话应用（交互形态） |
| 网页调研 Agent | MCP（浏览器抓取·页面解析） | Agents SDK（轻量循环+工具编排） | Agent 云（弹性部署+定时调度） | 浏览器（10-10 DOM+视觉） |
| 代码修 bug Agent | A2A（与编辑器/CI 协作） | Pydantic AI（类型安全工具调用） | Dify（工作流托管+日志回看） | 代码（05 测试回路） |

**3×4 = 12 格无空层断言全过。** 三个读数：

**第一个，四层是四个不同的问题，一次配齐、缺一层都跑不成。** 客服机器人：没有 MCP 连订单库存，它读不到数据（断协议层）；没有 LangGraph 画状态图，会话状态乱、重试无门（断运行时）；没有 Coze 托管发布，它只活在开发机里、进不了微信群（断平台）；没有对话交互，技能无处释放（断应用）。**真实产品的每一层都由不同人 / 不同件负责，职责边界就是账 A 的判层三问。**

**第二个，天选的组合是"在你已实测的件里挑"，不是从零选型。** 06-25 你测过客服机器人跑 LangGraph（带记忆重试·中断恢复补 2 步），07-04 测过 Dify 工作流，07-11 测过 MCP 协议——**账 B 的三个装配都是把已实测组件放回坐标**。对新学习者这句话最有用：**07 章（框架真引擎）+ 09 章（问题与动作）之间不需要"再学一遍框架"，需要的是"把已知件放对位"**——本篇就是在做这个放对位。

**第三个，"应用层"常常是"你已经决定好的"——先定动作，再倒推上面三层。** 页面调研任务的动作层是浏览器，于是协议连浏览器抓取（MCP）、运行时选轻量循环（Agents SDK）、平台选云托管（可定时）；代码任务的动作层是代码仓库，于是协议连 CI/编辑器（A2A）、运行时选类型安全（Pydantic AI）、平台选工作流托管（Dify）。**选型的顺序其实就是 §9.14 分层的倒序：任务形态 → 平台 → 运行时 → 协议**——这正好把账 A 的"世界地图"翻成"装配清单"。

**账 B 的总结论（断言 12/12 无空层）**：

> **真实产品是四层叠起来，不是四选一：同一 3 个应用 × 四层 12 格无空层——客服 MCP+LangGraph+Coze+对话、调研 MCP+Agents SDK+Agent 云+浏览器、修 bug A2A+Pydantic AI+Dify+代码。装配顺序是分层的倒序：先定任务形态（应用）→ 托管（平台）→ 循环（运行时）→ 连接（协议）；每一层都是 07/09 章已实测过的件，本篇只做放位。**

## 8. 常见坑（收束篇的 7 个）

1. **量框架比"谁更好"，而不是判"各管哪一段"**（账 A 的靶子）：LangGraph vs Dify 放一起打架。**修法**：判层三问（怎么连→协议 / 循环→运行时 / 托管→平台 / 形态→应用），看"首因"不看附赠——平台常内置运行时，但它的出厂职责是托管。
2. **以为用过其中一个 = 拥有整个生态的"位置"**（账 A 的第二个靶子）：会在 LangGraph 里写节点=拿到运行时层的能力，不等于你会 Dify 托管。**修法**：四层是四种行为，逐层补齐——07 章已实测 3 件（LangGraph/Dify/MCP），其余按要素事实补认知。
3. **选型从"抄个热门框架"开始，而不是从任务倒推**（账 B 的靶子）：任务形态都没定就选 LangGraph 全家桶。**修法**：装配顺序=先应用（手往哪放）→平台→运行时→协议；页面调研先定浏览器（10），再倒推 MCP/Agents SDK/Agent 云。
4. **把五大趋势当"学习清单"重新学一遍**（账 C 的靶子）：看到趋势①每个词都陌生（评测台、护栏、审批）——其实都是 06/07/05 已交付篇。**修法**：每条趋势先翻到 09 章对应篇目（账 C 的锚点列就是索引），用复习链代替"学新"，真正的新知识只有 04 的融合账和 §10.8 一眼带。
5. **决策时跳过"动作层"直接想框架**（账 D 的靶子）：「这个任务用什么 Agent？→ 用 LangGraph！」。**修法**：第一问永远是"手往哪放"——修 bug 落代码 05、抓价落浏览器 10、老系统落 GUI 09、多部门落多 Agent 08、单步落工具 06-05；框架层是装配清单的末尾不是起点。
6. **把『多 Agent』当"更高级"全自动选**（账 D 的靶子）：单步查询也上多 Agent（6 calls/12 msgs 质量 1.00 = 纯开销）。**修法**：单 vs 多是拓扑选择不是规模词——单步用单 Agent，流水线型任务（写好审好改）才值得链式多 Agent，且先算协调税（上下文 10→78）摆得平吗。
7. **收官就放羊——忘记 09 章"接口谱系"最优序**（整个 09 章收束的靶子）：新任务第一反应上浏览器 Agent 抓网页（最慢、墙最多）。**修法**：有 API 走 API（06-05）→ 有 MCP 走 MCP（07-11）→ 最后才上下浏览器（10）、GUI（09）——收官再背一遍这条序，10 的实际 4 轮 vs API 1 次就是证据。
