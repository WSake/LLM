## 0. 为什么第 8 课是「Multi-Agent」？

07 讲完安全，把"安全事件>0 不上生产"的红线踩死。本篇回到 09 章的主线——"怎么更会干活"——但换一个规模维度：**01 到 07 全部默认『一个 Agent 内一个 loop』，本篇第一次把一个 Agent 拆成『N 个 Agent 怎么协作』。** 这是 09 章承上启下的关键一课：单 Agent 的每一课（Loop/计划/推理/编码/评测/安全）都是多 Agent 的积木，Multi-Agent 是把这些积木组织成网络的那一课。

§9.8 的定位很诚实：🟢 掌握取舍。它不要求你亲手搭一套多 Agent 系统（真引擎的搭法在 07 章 08-CrewAI / 10-Agents SDK / 07-AG2 / 02-LangGraph 已经教过），它要求你**知道什么时候该上多、什么时候别上、上了选哪种拓扑、每种拓扑要付什么税**。这和 07 章实现层的分工正好互补：07 教"怎么搭"，本篇教"该不该搭"。

为什么必须专门讲，而不是引用一遍 §6.9 就完事？因为 **§9.8 的『为什么』和『代价』是两个方向相反的力，只有把它们都量化，取舍才成立**：多角色的收益（写手/审校/执行真能提高质量吗？）与多 Agent 的税（token 爆炸、错误传导、协调复杂会吃掉多少收益？）在本篇四个账里逐项称重。决策原则『先单 Agent，再上多』也因此不再是口号，而是一张看得见盈亏的权衡表。

## 1. 先把问题拆开：多 Agent 是什么、四拓扑、决策原则

§9.8 一句话定义：**多 Agent = 多个自主 loop（02 章六状态机）× 一个协同结构。** 每个 Agent 都是一颗会自己思考/行动/观察的节点，协同结构决定它们之间怎么传递信息。协同结构有四种常见形态：

| 拓扑 | 形态 | 一句话 | 实现层（要素事实） |
|---|---|---|---|
| **星型**（supervisor 分配） | 一个中枢节点分派任务、汇总结果 | 部门经理模式 | LangGraph（显式图）/ Agents SDK（handoff） |
| **环型/链式**（流水线） | 上一段的输出是下一段的输入 | 工厂产线 | CrewAI（角色化任务链） |
| **网状**（自由对话） | Agent 互相广播、自由讨论 | 开会 | AutoGen / AG2（group chat） |
| **层级**（子 Agent 再分） | supervisor 下面还有 manager | 组织架构 | LangGraph（子图嵌套） |

**两条决策原则**（§9.8 原文，本篇就围绕它们展开）：

1. **先单 Agent，再上多。** 先把 02 章的六状态机 loop 跑稳，能单 Agent 干的绝不拆——多一个节点就是多一份调用、多一轮上下文、多一条出错链路（账 A 就量这份"多"的代价）。
2. **一个清晰的 loop 胜过三个混乱的 Agent。** 节点的堆叠不自动带来质量——三个没有明确分工的 Agent 互相干扰，质量可能比一个专注的 loop 更差（账 A 场景 1 把这个数字钉死，账 B 说明多角色回报的天花板）。

**实现层的分工**（本篇不 import 任何框架，它们是**要素事实**）：星型/层级 → LangGraph 显式图、Agents SDK（`handoff()` 自动工具）；网状 → AG2 / AutoGen 的 group chat（`AgentReply.ask()` 事件流回灌）；链式多角色 → CrewAI（`role/goal/backstory` 角色配方，sequential 任务接力）；跨厂商 → A2A 协议（2025）。想亲手跑这些引擎的读数，去看 07 章对应篇；本篇给选型的坐标系。

## 3. 实验 A · 拓扑×场景账：先单 Agent，再上多

把 §9.8 的两条决策原则放到三种典型任务上，五种拓扑各跑一遍，得到调用数（成本）、墙钟轮数（时延）、协调消息数（协调开销）、质量分（作者预置仿真）：

**场景 1 · 单步查询**（单角色 · 1 步就能干完）：

| 拓扑 | 调用 | 墙钟轮 | 协调消息 | 质量 |
|---|---|---|---|---|
| **单Agent** | **1** | 1 | 0 | 1.00 |
| 星型supervisor | 3 | 3 | 3 | 1.00 |
| 链式2节点 | 2 | 2 | 1 | 1.00 |
| **网状3Agent** | **6** | 2 | **12** | 1.00 |
| 层级(m+worker) | 2 | 2 | 2 | 1.00 |

比一比第 1 行和第 4 行：**质量都是 1.00**——一个查天气的任务，五个拓扑都能答对。但成本从 1 调用、0 条协调消息，涨到 6 调用、12 条消息。**这就是『一个清晰的 loop 胜过三个混乱的 Agent』的数字版：简单任务上多 Agent 帮不了质量半分，只烧 6× 的调用和 12 条协调消息。** 决策原则①（先单 Agent，再上多）在场景 1 上没有任何反例。

**场景 2 · 写→审→发**（多角色 · 3 段串行）：

| 拓扑 | 调用 | 墙钟轮 | 协调消息 | 质量 |
|---|---|---|---|---|
| 单Agent | 3 | 3 | 0 | **0.60** |
| 星型supervisor | 5 | 4 | 6 | 0.87 |
| **链式3角色** | **3** | 3 | 2 | **0.87** |
| 网状3Agent | 6 | 2 | 12 | 0.87 |
| 层级(审管+星下) | 6 | 4 | 8 | 0.87 |

这一场景多 Agent 才真的赚了：**同样 3 次调用的链式（0.87）比单 Agent 一把梭（0.60）质量高出 0.27——多角色分工（写手→审校→发布）换来了真质量**（账 B 会解释这 0.27 是哪来的）。但注意第二行和第三行：**星型 5 调用、4 轮，质量却和链式 3 调用、3 轮完全一样。** supervisor 的分配/汇总这一圈绕路，没有多换来任何质量——因为瓶颈在审校，不在调度。**多 Agent 是拓扑选择：该多角色的时候多，但 supervisor 不是加了就一定值。**

**场景 3 · 三主题调研**（可并行 · 3 个独立主题 + 1 汇总）：

| 拓扑 | 调用 | 墙钟轮 | 协调消息 | 质量 |
|---|---|---|---|---|
| 单Agent | 4 | 4 | 0 | 0.90 |
| **星型supervisor** | 5 | **3** | 7 | **0.95** |
| 链式3角色 | 4 | 4 | 3 | 0.90 |
| 网状3Agent | 6 | 2 | 12 | 0.90 |
| 层级(2管+3wk) | 7 | 4 | 8 | 0.95 |

这一场景星型是赢家：**三个主题并行分给三个 worker，墙钟从单 Agent 的 4 轮压到 3 轮**（并行省时延），supervisor 汇总时再带一次检查，质量 0.90→0.95。但代价买得很清楚：**调用 4→5（+1 是协调税），协调消息 0→7。** 再看最底下：层级 7 调用最贵、质量却不比星型高——**每叠一层 manager 就多一级编排税，收益不跟着涨。**

**账 A 的总结论（8/8 断言全过）**：

> **先单 Agent，再上多；上多 = 按任务结构选拓扑，不是堆节点。** 单步任务 → 单 Agent（多 Agent = 6× 纯开销）；多角色串行 → 链式（supervisor 绕路不增质）；可并行子任务 → 星型（用 +1 调用换 1 轮墙钟 + 汇总检查）；全广播的网状和深层级在普通任务上是最贵的选择，留给真正需要自由讨论的场景（§9.14 长时任务/多 Agent 协同）。

## 4. 实验 B · 多角色协作账：外部审校 > 自检，瓶颈封顶

场景 2 的质量差 0.27 是怎么来的？账 B 把"多角色分工"拆成一次具体的协作：写一篇文章，写作环节带出 3 个缺陷（事实错误 / 内容重复 / 漏要点），看四种配置各抓到几个：

| 配置 | 调用 | 抓缺陷 | 抓率 |
|---|---|---|---|
| 单Agent 一把梭 | 1 | — | 0/3 (0.00) |
| 单Agent + 自检 | 2 | {1} | 1/3 (0.33) |
| **链式 写手→审校** | 2 | **{1, 2}** | **2/3 (0.67)** |
| 星型 写手+审校+supervisor | 3 | {1, 2} | 2/3 (0.67) |

三条读数——**第一条，外部审校 > 自检，而且差在同样的预算上**：单 Agent + 自检和链式写手→审校都是 2 次调用，前者只抓 1/3（事实错误，词面自查能看见的），后者抓 2/3（事实错误 + 内容重复，审校=一把外部真值尺）。这正是 04 章的分界在多 Agent 里的显形：**Self-Refine 是"No 执行器内自检"（没有真值，只能自己批判自己，漏信息），Reflexion/外部验证是"有执行器外验"（审校 Agent 就是那个执行器）。** 把第 2 次调用花在"请外部审校"上，比花在"再问自己一遍"上，多抓 1 个缺陷。

**第二条，瓶颈封顶质量**：再加一个 supervisor（3 次调用），抓的仍是 {1, 2}——第 3 个缺陷（漏要点）审校没看见，supervisor 复查也没看见。**瓶颈在审校 Agent 的能力，不在节点数。** 这就是"加人前先问瓶颈是谁"：审校是瓶颈，就该换更强的审校 / 给审校加目标清单，而不是再叠一个 supervisor（账 A 场景 2 里 supervisor 绕路不增质就是同一现象的另一个面）。

**第三条，增量递减**：抓缺陷 0 → 1 → 2 → 2，调用 1 → 2 → 2 → 3。每多 1 次调用换来的增量是 +1 → +1 → **+0**。多 Agent 的分工红利是一条递减曲线——**第一刀（从无检查到有一次检查）最值，之后边际递减，到瓶颈处归零。**

## 5. 实验 C · 协调的税三张脸：token 爆炸 × 错误传导 × 共享写入

§9.8 把多 Agent 的代价一口气列了三样：token 爆炸、错误传导、协调复杂。账 C 把它们逐一称重。

**C1 · token 爆炸：上下文回灌段模型**。每个 Agent 每轮调用的上下文 = 任务 + 它收到的所有上游输出（段模型：任务 10 段 · 每节点输出 4 段 · 分派/汇报 2 段）：

| 结构 | 各次调用的上下文(段) | 总段数 | 末节点 |
|---|---|---|---|
| 单Agent | [10] | 10 | 10 |
| 链式 3 节点 | [10, 14, 18] | 42 | 18 |
| 星型 1sup+2worker | [10, 12, 12, 18] | 52 | 18 |
| **网状 3Agent·2轮** | [26, 26, 26] | **78** | **26** |

**单 Agent 10 段，网状 78 = 7.8×**；链式 4.2×、星型 5.2×。而且看末节点：链式最后一个节点要吞 18 段、网状每个节点吞 26 段——**广播拓扑里每条消息都进所有节点上下文，越到后面每个节点越是"看全部"**。这就是 token 爆炸的机制，也是 06 章六指标里 token 成本的来源：**多 Agent 的成本线 = 节点 × 轮次 × 平均上下文，每加一个节点/一轮，所有人都得多读一遍历史。**

**C2 · 错误传导：一个错值（2+3=6）在结构里传多远**：

| 结构 | 被污染环节 | 传导距离 | 阻断位置 |
|---|---|---|---|
| 链式 3 角色 | 3/3 | 3 | 无（只有末端总检，后置，总检≠不出错） |
| **星型 worker→汇总** | **1/3** | **1** | **supervisor 汇报检查点（复核算术 100%）** |
| 网状 3 Agent 讨论 | 3/3 | 2 | 外部用户最终发现（共识性错误） |

链式里 node1 算错 2+3=6，下游先 recycle node2、node3 各自相信上游，**1 处错 → 3 个环节被污染**（错误沿链路传染）；网状里错值被广播、全体"一致同意"一个错误答案——**共识性错误比链式更隐蔽，因为没人站在对立面**。星型呢？worker 汇报给 supervisor 时，supervisor 复核一把就把错值拦在源头（1/3 被污染）。**协调结构直接决定错误传导距离：检查点（汇报即检查点）是唯一把传导压回 1 的手段**——这和 07 的审计/回滚同源：拦得住，才兜得住（账 D 的审计就是跨 Agent 版的它）。

**C3 · 协调复杂的一格：并行共享写入**。2 个 worker 并行调研 A/B 两个主题，都要写 `final_report.txt`：**无锁并行 = last-write-wins，先写完那份被后写覆盖，丢 1 份调研结果**；分片/各自命名（各写各片再合并）才 0 丢失——而"合并"又是一段新的协调逻辑。§9.8 那句"协调复杂"在这里变成具体的事故：**并行省的是墙钟（账 A 场景 3），但从"谁先写、谁覆盖"到"谁负责最后汇拢"，每一样都是新的协调债。** 真多 Agent 系统把这一格升级成共识/汇合协议（05 章的并行多分支，或 07 章 LangGraph 的状态读写）。

## 6. 实验 D · 信任与监督账：07 六护栏放进多 Agent 网络

07 的六护栏（最小权限 + 沙箱 + 人工确认 + 输入输出过滤 = 拦得住 · 审计 + 回滚 = 兜得住）在单 Agent 上成立，一旦拆成网络，每个威胁都乘上一个**"网络因子"**：注入打进的不再是 1 个大脑而是 N 个大脑（共识放大）、外泄会经共享日志/汇总扩散给 N 个节点（账 C2 刚演示过结构里信息怎么流）。账 D 把 13 个跨 Agent 事件跑过三档治理配置：

| 配置 | 漏网事件 | 按类型拆解 |
|---|---|---|
| 无治理(互信直连) | 13/13 | 供应链3 · 外泄3 · 注入4 · 越权3 |
| 隔离治理(隔离+沙箱) | 9/13 | 供应链2 · 外泄3 · 注入4 |
| **全配(+监督+审批+消息标注)** | **2/13** | 供应链1 · 注入1 |

**无治理 13/13 = 对话即信任**：Agent 之间直连互信，任何一条注入消息全网执行，这就是网络上裸奔的默认值。**隔离治理 9/13**：权限隔离把"跨 Agent 越权"整类锁死（越权 3 条全拦——worker 调他人的删除工具、冒充 supervisor、越界读共享库都没了），但注入 4 / 外泄 3 / 供应链 2 还在——**因为网络版的最小权限只堵『动手』，不堵『读进毒』：消息和文档还在传**。**全配只剩 2**：supervisor 上下文覆盖（账 C1 里 supervisor 吞的上下文最全，恰恰也最容易被覆盖）和伪装合法 Agent 投毒共享工具（伪装到人工审批都难发现）。关键是这两条被 **审计 13/13 全留痕 + 回滚 2/2 恢复**兜住了 → **残留影响 0**。

**上生产判定**（红线沿用 06 账 D 的"安全事件>0 不上生产"）：

| 配置 | 残留影响 | 是否上生产 |
|---|---|---|
| 无治理(互信直连) | 13 起 | ❌ |
| 隔离治理(隔离+沙箱) | 9 起 | ❌ |
| **全配(+监督+审批+消息标注)** | **0 起** | **✅** |

**与 07 对照，网络版六护栏多了三样东西**：① **权限隔离 = 每 Agent 单独的最小 scope**（07 最小权限从"一个 token 一把钥匙"升级成"每个 Agent 一把各自的钥匙"——worker 被注入只能碰自己的活，07 账 C 的"越权 5/5→0/5"在网络里变成"跨 Agent 越权 3/3 全拦"）；② **supervisor = 天然审批座 + 检查点**（07 里人工确认高风险动作要在系统外配，网络里 supervisor 就是 05 章高危 3/7 人工拦截的天然落点，账 C2 的汇报即检查点也是它）；③ **消息标注为数据 = 每个 hop 都要贴的"这是数据"**（07 账 B 最便宜的那一档缓解——工具结果标注为数据——在网络里每跳消息都标，注入 4 条被压到 2）。审计/回滚从单 Agent 变成跨 Agent 的全局台账。

## 7. 这篇 Multi-Agent 怎么用（一页带走 + 掌握度检验）

**一页带走：**

- **先单 Agent，再上多**（§9.8 决策原则）：简单任务上网状 = 6 调用/12 消息换质量 1.00（=单 Agent 1 调用），**多 Agent 是拓扑选择，不是加人游戏**。
- **四拓扑按任务结构选**：单步→单 Agent；多角色串行→链式（星型 supervisor 绕路不增质）；可并行子任务→星型（+1 调用换 1 轮墙钟 + 汇总检查）；网状/深层级最贵，留给真需要自由讨论的场景。
- **分工红利是递减曲线**（账 B）：外部审校（外部真值尺）> 自检（内自检），同 2 调用 2/3 vs 1/3；**瓶颈封顶质量**——加 supervisor 仍 2/3，加人前先问瓶颈是谁。
- **协调的税三张脸**（账 C）：token 爆炸（上下文回灌单 10<链 42<星 52<网 78 = 7.8×）· 错误传导（链/网 3/3 被污染 vs 星型检查点 1/3）· 共享写入丢数据（无锁 last-write-wins 丢 1 份）。
- **07 六护栏的网络版**（账 D）：权限隔离（每 Agent 一把钥匙）+ supervisor 审批座 + 消息标注为数据，漏网 13→9→2；审计 13/13、回滚 2/2 → **残留 0 才上生产**（06 红线）。

**掌握度检验（自问自答）：**
1. §9.8 四拓扑各长什么样？各适配哪种任务结构？（答案：星型=中枢分配/汇总（parallel 子任务）、链式=流水线（多角色串行）、网状=自由对话（讨论）、层级=子 Agent 再分（组织架构）。）
2. 为什么说"一个清晰的 loop 胜过三个混乱的 Agent"？账 A 哪个数字支撑它？（答案：场景 1 单步查询——网状 6 调用/12 协调消息，质量 1.00 与单 Agent 1 调用完全一样；简单任务多 Agent 是纯开销。）
3. 账 B 为什么"外部审校 > 自检"？（答案：同样 2 次调用，审校（外部真值尺）抓 2/3、自检（无真值内自检，04 章 Self-Refine）只抓 1/3——把第 2 次调用花在外部验证上更值。）
4. 协调的税三张脸，各自最狠的数字？（答案：token 爆炸网状 78/单 10 = 7.8×；错误传导链式/网状 3/3 被污染 vs 星型检查点 1/3；共享写入无锁丢 1 份。）
5. 07 六护栏放进网络，多了哪三样？（答案：每 Agent 单独 scope 的权限隔离（跨 Agent 越权 3/3 全拦）、supervisor 审批座（高危拦截天然落点）、每个 hop 的消息标注为数据；审计/回滚跨 Agent 兜底→残留 0 才上生产。）

## 8. 常见坑（Multi-Agent 的 7 个）

1. **简单任务也上多 Agent**（账 A 场景 1 的靶子）：单步查询上五个拓扑质量全 1.00，网状烧 6 调用/12 消息。**修法**：先单 Agent，loop 跑稳再拆；§9.8 决策原则① 当闸门。
2. **用"角色数"当"节点数"堆人**（账 B 的靶子）：加 supervisor 仍 2/3 封顶——瓶颈在审校能力，不在节点数。**修法**：加人前先问瓶颈是谁；瓶颈在审校就换更强的审校，叠 supervisor 只是绕路（账 A 场景 2）。
3. **默认网状最好**（账 A/C1 的靶子）：网状协调消息 12、上下文 7.8×，质量却不见得高。**修法**：按任务结构选拓扑，全广播留给真需要讨论的场景；多数任务星型/链式是更省的选择。
4. **上下文每轮全量回灌、不设预算**（账 C1 的靶子）：链式末节点吞 18 段、网状吞 26 段，节点一多 token 就爆炸。**修法**：显式画"谁看什么、多大"的上下文图；超预算就压缩/裁剪（挂 06-03 / 08-06 的压缩账）。
5. **以为并行免费**（账 C3 的靶子）：无锁并行 last-write-wins 丢 1 份调研结果。**修法**：共享状态分片/命名/锁，合并是新的协调步骤；并行省的是墙钟，协调复杂度得有人付账。
6. **忽略错误传导**（账 C2 的靶子）：链式 1 处错 → 3 个环节被污染，网状变成"共识性错误"更难发现。**修法**：把检查点装到汇合处——supervisor 汇报即检查点（复核算术这类可验证的），别只留末端总检。
7. **网络里没有信任边界**（账 D 的靶子）：无治理 13/13 = 对话即信任，任何注入消息全网执行。**修法**：权限隔离（每 Agent 单独 scope）+ 消息标注为数据 + supervisor 人工审批高风险接入，审计回滚兜底——只有全配残留 0 才上生产（06 红线）。

## 9. 诚实边界（AAA 自我审查）

- **要素事实 vs 本机实测**：四拓扑定义、决策原则、§9.8『为什么/代价』、实现层清单（LangGraph / AutoGen·AG2 / CrewAI / Agents SDK / A2A 2025）= **按知识地图 §9.8 与公开资料整理的要素事实（写作环境无外网，未在线复核）**；不是本机跑真实多 Agent 框架的结果。**请在引用时保留"要素事实"前缀**。
- **仿真 vs 真实运行**：账 A 的调用/轮数/消息/质量分、账 B 的缺陷表与审校抓错率、账 C 的段模型与错值传导、账 D 的 13 个事件表与拦截判定 = **作者按 §9.8 预置的确定性数据表**（`multi_agent_demo.py` 内固定常量），不是真实 CrewAI/AG2/LangGraph 在多 Agent 任务上的器跑结果。真实系统的调用次数/延迟/token 因框架、模型、并发而异，本机的数字是教学拓扑上的确定性刻度；但"网状最贵、链式传导最远、检查点最短、隔离只堵动手不堵读进毒"这些方向性结论与 §9.8 一致。
- **统计 = 本机确定性计算**：四账全部计数/累加/覆盖矩阵/残留判定为纯 stdlib 逻辑运算，stdout 三个独立进程 md5 恒一 `0cbc2856…`，墙钟 ≈0.000–0.001 s 仅进 stderr——不依赖任何随机种子、网络或第三方库。
- **边界不自留坑**：本篇没有把"真实多 Agent 系统的性能"冒充成本机测量；没有把多 Agent 说成"永远该上"（账 A 演示简单任务 6× 纯开销）；没有把六护栏的网络版说成"装了就安全"（账 D 全配仍漏 2，靠审计回滚兜底——07 的『护栏是纵深不是保险柜』在网络里同样成立）。
