## 0. 为什么第 9 课是「Computer Use」？

08 讲完多智能体，把"怎么把 N 个 Agent 组织成网络"画完了。本篇回到**单个 Agent 的动作层**，问一个从 02 章到 08 章一直默认跳过的前提：**Agent 的『action』到底落在哪？** 02 章之前，Agent 的动作全是**工具调用**（06-05 的 Function Calling / 07-11 的 MCP），先决假设是**这世界有 API**。但真实老系统不是这样的——**旧版计费系统只有一个桌面 GUI、运营后台内网网页没有接口文档、第三方 SaaS 连 API 键都不给你**。这就是 §9.9 存在的理由，也是 09 章把它排在 Coding Agent 前、作为"2025 关键词"的原因：

> **Agent 直接操作操作系统 GUI（点击/输入/截图），无需 API。**

本篇的定位（🟢 了解）比 Coding Agent（🔴 必有实践）轻一档，但它是一个**岔路口**：它把 Agent 的动作从『结构化协议』（API 的 schema / 工具的参数）换成了『像素世界』（截图 + 坐标 + 点击），所有前几课的护栏技术到这里都要**重新推导**——因为 GUI 没有 schema，API 时代的"参数校验"这一整套护栏体系直接失效（账 D）。同时它也是**多模态→Agent 的交汇点**（§10.8 / §17.7.6 都把 Computer Use 列为"看一眼屏就走"的下一跳）：**看懂是第一步，动手是第二步**，Computer Use 就是那个"动手"。

为什么必须专门讲，而不是引用一遍 §9.9 原文？因为 §9.9 的四句话——"无需 API"、"截图→视觉理解→坐标/动作→执行"、"难点在像素级理解"、"难点在误操作控制"——**每一句都是一本需要量化的账**：无 API 时真的只有 GUI 通吗（账 A）？一次 GUI 操作和一次 API 调用成本差多少（账 B）？记坐标为什么在真实屏幕上不可靠（账 C）？没有 schema 的 GUI 靠什么兜住点错（账 D）？这四本账一起，才把一个"新型接口"讲成学习者能理解、能上手排查的原理课。

## 1. 先把问题拆开：Computer Use 是什么、技术点、难点都在哪

§9.9 一句话定义 + 技术点，拆成一条链：

```
截图（感知）→ 视觉理解（读屏：找元素）→ 坐标/动作输出（想：点哪、敲什么）→ 执行（动手）→ 新截图（观察，喂回 loop）
```

去掉中间的语言部分，它就是一个 **02 章六状态机的"感知→行动→观察"循环**，只是：感知从"JSON 状态"变成"一张图"，行动从"call API"变成"click(x,y) / type(文本)"。这条链的每一步都比 API 时代多一个失败点：

| 环节 | API 时代 | GUI 时代 | 失败点 |
|---|---|---|---|
| 感知 | 服务端给我结构化状态 | 截图=像素，没人告诉我控件在哪 | 截屏糊 / 分辨率不同 / 元素堆叠 |
| 理解 | schema 写死了字段 | 视觉模型要「读懂屏幕」 | 认错按钮 / 文本被图标遮蔽 / 多语言 |
| 行动 | 参数已校验 | 坐标是物理像素 | 缩放、窗口移动→坐标全漂（账 C） |
| 执行 | 有返回值/报错 | 点下去可能点错东西（误操作） | 误删、误付、误配置（账 D） |
| 观察 | 新 JSON | 新截图 | 状态没变但截图变了（动画/闪烁） |

**两个"难点"（§9.9 原话）贯穿整条链**，也是本篇四账的两根轴：

1. **GUI 像素级理解**——怎么从一串像素里找到"那个按钮"？不是记坐标，是看图认元素（账 C 的核心）。
2. **误操作控制（安全护栏）**——GUI 没有 schema，点错就是真点错，怎么兜住（账 D 的核心）。

评测（§9.9）正好对应这两根轴：**OSWorld**（桌面 OS 像素级操作，自动验证靠视觉/人工）、**V\* Bench**（GUI 多模态视觉问答：看清截图内容）、**Mind2Web**（网页操作，DOM+视觉混合）——它们不是"聊天评测"，是"动手能力评测"，所以 06 账 A 里它们都被归进『环境类』（真实环境逼真、自动验证难）。

**和 Coding Agent 的分界**（§9.11 放 05 课讲过）：Coding Agent 的动作落在**文件+测试**——可验证（编译/测试就是真值），因此 SWE-bench 能全自动。Computer Use 动作落在**像素+点击**——像素没有编译器，真假只能靠 OSWorld 这类环境人工看/视觉判，所以自动验证天生难一档（06 账 A 里『OSWorld 桌面像素人工/视觉=唯一例外』）。**代码任务是 Agent 最佳落地，GUI 操作是 Agent 最难落地——难在哪，本篇就讲在哪。**

## 2. 把概念降维成本机测量（探针设计：四本账）

§9.9 是概念清单，没有一台"能跑的 GUI 沙盘"（Operator/UI-TARS 都要真实 OS + 视觉模型，非本机可用）。探针 `computer_use_demo.py` 把四块分别降成确定性可复现的四本账——**不跑任何视觉模型 / 操作系统 / 框架**，用屏幕状态表、元素表、坐标、确认框文本做纯逻辑仿真：

| 本账 | 地图锚点 | 探针实测量 | 一张表看清什么 |
|---|---|---|---|
| **A 无 API 账** | §9.9『无需 API』+ 06-05 FC + 07-11 MCP | 3 个任务 × 3 种接法前置（FC 要接口文档·MCP 要 Server·GUI 要屏幕）→ 可用性 3×3 矩阵 | 无 API 的世界 FC 1/3、MCP 1/3、CU 3/3 唯一全覆盖；有 API 时 API 1 次调用 vs GUI 4 轮 |
| **B 管线账** | §9.9『截图→视觉理解→坐标/动作→执行』 | 虚拟"偏好设置"窗口 7 元素，任务「亮度调到 80%」→ 逐轮 截图-理解-动作-执行-新截图 | 一次正确 GUI 操作=多次小循环：4 步收敛（3 次 + 1 保存），每步一个失败点 |
| **C 像素账** | §9.9『难点：GUI 像素级理解』+ §10.8 UI-TARS 路线 | 同一「立即购买」按钮 × 4 屏（默认/缩放125%/平移/纯图标）× 3 定位法 → 逐屏命中 | 固定坐标 1/4（缩放/平移/图标全漂）· OCR 3/4（图标无文本死）· 视觉语义 4/4（认形状+标签） |

## 3. 实验 A · 无 API 账：为什么必须会 Computer Use

把 §9.9 的第一句"无需 API"放到三个真实场景里检验——**两个没有 API，一个有 AI，再看三种接法的前置条件卡在哪**：

| 任务 | 场景 | Function Calling(要接口文档) | MCP(要 Server) | Computer Use(要 GUI) |
|---|---|---|---|---|
| 旧计费系统·月度报表 | 纯桌面 GUI 老系统 | ❌ | ❌ | ✅ |
| 运营后台·改缓存配置 | 网页后台(内网) | ❌ | ❌ | ✅ |
| 内部服务·生成汇总邮件 | 内部 API 服务 | ✅ | ✅ | ✅ |

**可用性：FC 1/3 · MCP 1/3 · Computer Use 3/3。**

三个读数：

**第一个，无 API 的世界只有 GUI 通。** 前两个任务没有接口文档（FC ❌）、没有 Server（MCP ❌），但屏幕是有的——**Computer Use 的前置条件只有一个：这个系统长得出来**，桌面端/内网网页都能截图定位。这就是 §9.9『无需 API』的确切含义：**FC 卡接口文档、MCP 卡 Server、GUI 什么都不卡，只要看得见**。老桌面系统、内网后台、第三方 SaaS，恰恰是"长得出来却没接口"的大户——这正是 Computer Use 存在的市场。

**第二个，有 API 时 API 是更便宜的接法。** 第三个任务有文档有 Server，FC/MCP/CU 三路都通，但成本差一个量级：**API 一次调用返回结构化结果 vs GUI 要 4 轮『截图→理解→点击』小循环**（这就是账 B 的数字）。所以 Computer Use 不是"比其他方法好"，是"**在 API 不存在时唯一能进的方法**"——选型顺序应该是：**有 API 走 API（便宜）→ 有 Server 走 MCP → 都没有才走出屏点（贵但能通）**。

**第三个，别把 GUI 当彻底替代。** 第三个任务标"也可（绕远）"：能用 API 的任务用 GUI 也能完成，只是多 N 轮、多 N 个失败点（账 B 那"每步一个失败点"会伴随全程）。**Computer Use 是补 API 的缺，不是替 API 的优**——生产里两者共存：能 API 的走协议，壳系统/第三方走屏幕。

**账 A 的总结论（断言 1/1 全过）**：

> **Computer Use 的存在理由 = 没有 API 的世界，屏幕点得通。** FC 卡文档、MCP 卡 Server、GUI 只要屏幕看得见（3/3 唯一全覆盖）；但它是补缺不是替优——有 API 时 API 1 次调用 vs GUI 4 轮小循环，能 API 的先 API。

## 4. 实验 B · 管线账：一次正确操作=多次小循环

§9.9 技术点"截图→视觉理解→坐标/动作输出→执行"，探针用一个虚拟"偏好设置"窗口跑一条真实任务循环——**把亮度从 50% 调到 80%**。窗口由 7 个元素组成（标题/亮度 label/亮度条/减号/加号/保存/取消），每轮：**截图（采样当前窗口状态）→ 视觉理解（OCR 读文本，找到亮度 label 那行的 [ + ]）→ 动作输出（click(plus)，坐标）→ 执行（亮度 +10）→ 新截图**：

```
   步  动作输出          坐标        亮度条        状态
   1  click(plus)      (37,3)   ██████░░░░   未达标·继续调亮
   2  click(plus)      (37,3)   ███████░░░   未达标·继续调亮
   3  click(plus)      (37,3)   ████████░░   亮度达标·准备保存
   4  click(save)      (8,5)   ████████░░   完成:保存已点
```

**收敛 4 步：3 次 [ + ]（50→60→70→80）+ 1 次 [保存]**（断言 4 步 · 亮度精确停在 80 · 保存被点击=全闭环）。四条读数：

**第一个，一次正确 GUI 操作=多次小循环。** 第 1-4 步每步都走完一轮"截图-理解-动作-执行-新截图"。API 一次调用完事（账 A 第三个任务），GUI 同一个任务要 4 轮。**这就是 Computer Use 贵而慢的机制：不是点一次，是一次操作 = N 次感知-行动-观察**。每多一轮就多一个失败点（第 5 节会看到失败长什么样）。

**第二个，每步一个失败点，四步各有各的坑。** 第 1-3 步失败在"视觉理解"——截图糊了/OCR 认错 [ + ] 当 [ − ]（亮度往 50 走，永远到不了）；第 4 步失败在"坐标"——保存钮和取消钮挨着（8,5 vs 16,5），点偏一格就取消。**22 章里那种"Agent 卡在 GUI 任务半天"的已知现象，机械根源就是这里：每个动作前都要先读懂一遍屏幕**。

**第三个，收敛判据要"验证"而不是"感觉"。** 循环不会在亮度"看起来差不多"处停——它每次点完都重新截图、看实时亮度条，**到 80 才切换动作（从 + 到保存），保存后再截图确认保存已生效才收手**。这跟 05 课 Coding Agent 的"每改必测"同源：**GUI 操作的自我验证 = 每次动作后的新截图/新状态，而不是"我觉得点到了"**。

**第四个，视觉理解环节是整条链的命门。** 整个循环里唯一的"智能"在 `_perceive_find_plus`（OCR 读文本→锁定目标控件→输出坐标），其余全是确定性执行。**Computer Use 的能力上限 = 视觉理解的上限**——这解释了为什么 Operator/UI-TARS 都押视觉模型（§10.8『看懂是第一步』），也解释了下一节为什么"认元素"比"记坐标"重要得多。

**账 B 的总结论**：

> **一次正确的 GUI 操作 = 多次小循环：每步『截图→理解→动作→执行→新截图』，4 步收敛（3 次 + 1 保存）；每步一个失败点，视觉理解是命门，验证靠每步后的新截图而不是『觉得点到了』。**（账 A 里"有 API 时 API 1 次 vs GUI 4 轮"的"4 轮"就是这里。）

## 5. 实验 C · 像素账：GUI 坐标不是稳定契约

§9.9 难点①『GUI 像素级理解』——探针用一个杀手场景钉死"记坐标"为什么不可靠：**同一个「立即购买」按钮，在四种屏幕上下文中出现，三种定位法逐屏命中**：

| 屏幕背景 | 固定坐标(记基准 (580,400)) | OCR 文本定位 | 视觉语义定位 |
|---|---|---|---|
| 默认 100% | ✅ 中点 | ✅ 重定位 | ✅ 认出 |
| 缩放 125% | ❌ 点空 | ✅ 重定位 | ✅ 认出 |
| 窗口平移(+120,+40) | ❌ 点空 | ✅ 重定位 | ✅ 认出 |
| 纯图标版(🛒) | ❌ 点空 | ❌ 无文本 | ✅ 认出 |

**固定坐标 1/4 · OCR 文本 3/4 · 视觉语义 4/4**。三条读数：

**第一个，固定坐标只在默认屏成立（1/4）。** 记住"这个按钮在 (580,400)"，在默认屏一记一个准；**窗口一缩放 125%（按钮从 (520,380) 挪到 (650,475)）、一平移（挪到 (640,420)）、一换成图标版（物理位置还是默认屏位置但按钮本身是纯图标），那一个点全部落空**。为什么？**屏幕坐标 = 按钮位置 × 窗口大小 × 分辨率 × 缩放**的乘积——它不是按钮的属性，是"布局快照里的瞬时位置"。**记坐标 = 记住了一张照片里的位置，照片一变就全错**。真实世界里浏览器窗口随时会被拖拽、操作系统缩放会触发，这就是为什么**直接对真实 OS 发 (x,y) 点击的操作系统级 Computer Use 必须要先视觉定位**（Operator 全程在浏览器里重新布局就是这个原因）。

**第二个，OCR 文本定位（3/4）比记坐标稳，但对图标死。** 文字按钮『立即购买』在缩放/平移后，OCR 能重新把文本读出来、（重）定位回按钮——**它锚定的是"文本"这个稳定的身份，不是位置**（文字不会因为窗口动了就消失）。但**纯图标按钮（🛒）没有文本可读，OCR 直接认不出 = 死路**。UI 世界里纯图标按钮（购物车/垃圾桶/齿轮/汉堡菜单）比想象中多，这正是纯 OCR 路线在实际 GUI 里的天花板。

**第三个，视觉语义定位（4/4）才接得住真实屏幕。** 认"形状 + 标签"：『立即购买』文字按钮读文本、纯购物车图标按形状（+上下文知晓是购物车）认出来——四屏全过。**这就是 §10.8 / §17.7.6 里 16-Qwen2.5-VL / UI-TARS 路线的核心主张：看图找元素，不是按坐标点**。真实 GUI 的稳定锚点不是 (x,y)，是**元素身份**（这个按钮是"立即购买"，不是"它在哪"）——坐标是窗口/分辨率的函数，身份才是跨画面稳定存在的东西。

**账 C 的总结论**：

> **GUI 的坐标不是稳定契约，元素身份才是屏幕里的锚点。** 固定坐标 1/4（缩放/平移/图标全漂）· OCR 文本 3/4（图标无文本死）· 视觉语义 4/4（认形状+标签）。所以 Computer Use 的解是『截图→视觉理解→定位』而不是『记坐标』——**记坐标=记住一张照片的位置，看语义=认出画面里的东西**（Qwen2.5-VL / UI-TARS 路线的全部理由）。

## 6. 实验 D · 护栏账：GUI 无 schema，确认框护栏三层兜底

§9.9 难点②『误操作控制（安全护栏）』——探针先立住一个前提：**API 时代的安全护栏是"参数校验"（06-05 账 B 的入参校验器：缺必需/类型错/range 越界全拦），GUI 没有 schema，没有"参数"可以校验**。那护栏还剩什么？**探针把 6 个真实 GUI 触点跑过三档护栏配置**：

| 护栏配置 | 漏网 | 仍触发的动作（残留影响） |
|---|---|---|
| 无护栏（直出） | 6/6 | 删除月度报表 · 支付 ¥520 · 恢复出厂设置 · 跳过二次确认 · 点击外部链接 · 误触『跳过确认』钮 |
| 审核 + 确认框文本匹配 | 2/6 | 点击外部链接 · 误触『跳过确认』钮 |
| 全配（审核+匹配+限额+快照回滚） | 0/6 | 无（全部拦截） |

**漏网 6 → 2 → 0**。三条读数：

**第一个，GUI 护栏的组件变了：确认框匹配顶替参数校验。** 无护栏 6/6 = 三个真危险（删报表 / 付款 / 恢复出厂）一个不拦全直出：**Agent 误删报表直接落盘、误付 ¥520 已扣款**——这就是 GUI 误操作的默认命运。+确认框文本匹配：**识别弹窗里的是危险『确定』（删除/付款/出厂设置都带），匹配就拦**——这是 GUI 护栏里最像"参数校验"的一块，但对象是『确认框文本』而不是『参数值』。

**第二个，高危动作进人工审核（还剩 2/6）。** 永久操作（恢复出厂/跳过二次确认）这种不可逆、确认框可能被代码跳过的，匹配不住→ **转人工审核**。但剩下 2 条——点击外部链接（低危）、误触『跳过确认』诱导钮（没确认框、非高危类型）——**确认框匹配不认、人工审核不拦，自动放行**。注意这 2 条的性质：**不是"危险"，是"诱导"**（诱导按钮混进危险流程旁、外链骗点击）——匹配管危险确认、审核管永久操作，**都拦不住"看着无害但会引去别处"的**。

**第三个，全配加上『限额 + 快照回滚』才到 0/6。** 付款限额（先拦大额）、**快照回滚（任何误触都能恢复）**——前两种护栏是"拦得住"，这层是"兜得住"：*拦没拦住都无所谓了，点错了能退回去*。**这就是 §9.9/OSWorld 评测里『动作可逆/影响可控』独立维度的数字版**：GUI 误操作没法像 API 那样"参数校验拦截"，只能把代价降到"可逆"——截图存档、状态回滚、撤销。这跟 07/08 的"审计回滚"同源，只是 GUI 版把回滚做到了像素/状态级。

**和 07 对照，GUI 护栏矩阵发生了什么（关键洞察）**：

| | API 时代（07 六护栏） | GUI 时代（本篇账 D） |
|---|---|---|
| 主拦截机制 | 参数 schema 校验 | 确认框文本匹配（GUI 没有 schema） |
| 高危兜底 | 人工确认高风险动作 | 高危人工审核（永久操作） |
| 计数/预算 | token/调用预算 | 动作限额（限制高频有代价动作） |
| 可逆性 | 审计日志 + 回滚 | 快照回滚（回到上一屏幕状态） |
| 追不上的 | —（schema 内全可拦） | 诱导性低危触点（外链/诱导钮）——只能兜住 → 0 |

**账 D 的总结论**：

> **GUI 无 schema 可校验，护栏从 API 的『参数校验』退化成『确认框文本匹配 + 高危人工审核 + 动作限额 + 快照回滚』：漏网 6→2→0。关键是误操作『可逆』——前两层管『确认对不对』，快照回滚管『点错了能退回去』（OSWorld 动作可逆独立维度）。诱导性低危触点（外链/诱导钮）拦不住也兜得住（回滚→0）。**

## 7. 这篇 Computer Use 怎么用（一页带走 + 掌握度检验）

**一页带走：**

- **计算机使用 = 把 Agent 的『手脚』接到操作系统 GUI，专治没有 API 的世界**（§9.9『无需 API』）。账 A：三任务 FC 1/3（卡文档）、MCP 1/3（卡 Server）、GUI 3/3（只要屏幕看得见）唯一全覆盖；**但它补缺不替优——有 API 时 API 1 次调用 vs GUI 4 轮**。
- **管线 = 截图→视觉理解→坐标/动作输出→执行→新截图**（账 B）：一次正确操作=多次小循环（4 步收敛：3 次 + 1 保存），每步一个失败点，验证靠每步后的新截图。
- **坐标不是稳定契约，元素身份才是锚**（账 C）：固定坐标 1/4（缩放/平移/图标全漂）· OCR 文本 3/4（图标无文本死）· 视觉语义 4/4（认形状+标签）→ **看图找元素不记坐标**（Qwen2.5-VL / UI-TARS 路线）。
- **GUI 无 schema，护栏三层兜底**（账 D）：确认框文本匹配（管危险确认『确定』）+ 高危人工审核（管永久操作）+ 限额（管大额）+ 快照回滚（管一切）：漏网 6→2→0，**关键是误操作『可逆』**（OSWorld 动作可逆独立维度）。
- **选型顺序**：有 API 走 API（便宜）→ 有 Server 走 MCP → 都没有才走下屏点（贵但能通）；业界落地 = Operator / Claude Computer Use（云端/沙箱浏览器+桌面）+ UI-TARS 一套视觉语义 + Playwright MCP 协议化（下一课 09-10）。

**掌握度检验（自问自答）：**
1. 为什么 Computer Use 能"无需 API"？条件是哪个？（答案：它直接操作 GUI——点击/输入/截图，不需要服务端接口。前置条件只有一个：**系统长得出来**（屏幕在），老桌面系统/内网网页/第三方 SaaS 都能截图定位。账 A 的 FC 卡文档、MCP 卡 Server、GUI 什么都不卡。）
2. 一次 GUI 操作 vs 一次 API 调用，成本差在哪？（答案：API 一次调用返回结构化结果；GUI 一步小循环=截图→理解→动作→执行→新截图，一次正确操作要 4 步=4 轮小循环（账 B 数字：3 次 + 1 保存），每步一个失败点。）
3. 为什么"记坐标"在真实屏幕上不可靠？（答案：屏幕坐标是按钮×窗口×分辨率×缩放的乘积，不是按钮属性。同一按钮缩放/平移后位置全变（账 C 固定坐标 1/4），只有默认屏中。元素身份（文本/形状/标签）才是跨画面稳定的锚——视觉语义定位 4/4。）
4. GUI 没有 schema，护栏还能靠什么？（答案：确认框文本匹配（管危险确认『确定』）+ 高危人工审核（管永久操作）+ 动作限额（管大额）+ 快照回滚（管一切）。API 的『参数校验』在 GUI 里退化成『确认框文本匹配』——账 D 漏网 6→2→0。）
5. 为什么 OSWorld 评测把『动作可逆』单列一个维度？（答案：因为 GUI 误操作没法像 API 那样参数拦截，点错了就是真点错了；能否恢复（快照回滚）直接决定事故伤害——『可逆』是 GUI 护栏的最后一道兜底（账 D 全配到 0 靠的就是回滚）。）

## 8. 常见坑（Computer Use 的 7 个）

1. **以为 Computer Use 比 API 更快**（账 A 的靶子）：GUI 4 轮小循环 vs API 1 次调用，视觉理解还要算，反而更慢更贵。**修法**：能 API 走 API，GUI 只留给"没有 API 的世界"（选型顺序：API→MCP→GUI）。
2. **直接对真实 OS 发固定 (x,y) 点击**（账 C 的靶子）：缩放/窗口移动后坐标全漂、点错东西。**修法**：先截屏→视觉定位（读文本/认形状）→再点元素；不能裸点坐标。Operator 全程重排布局就是这原因。
3. **只会 OCR 文本，认不出图标按钮**（账 C 第二读数）：购物车/齿轮/汉堡菜单纯图标无文本，OCR 直接死。**修法**：视觉语义兜底（认形状+标签），UI-TARS/Qwen2.5-VL 路线。
4. **没有"每动作后验证"就发下一步**（账 B 第三读数）：点完不截屏确认就认为"点到了"，实际点偏了/没生效，后续动作全乱。**修法**：每步后回到"新截图"观察状态，收敛判据看状态不是看"我认为"。
5. **GUI 任务不配护栏，裸执行**（账 D 第一读数）：Agent 误删报表直接落盘、误付 ¥520 直接扣款——GUI 没有参数校验兜底。**修法**：确认框文本匹配 + 高危人工审核至少配齐再上真实系统。
6. **以为护栏能拦一切**（账 D 第二读数）：确认框匹配不认诱导钮、审核不认低危外链——漏网 2/6 拦不住。**修法**：能拦的拦（危险确认/永久操作），拦不住的一定要么再叠拦截要么用回滚兜住（漏网→回滚→0）。
7. **拿 GUI 任务当 Coding Agent 评**（§9.12 的坑）：代码可验证（测试/编译器），GUI 像素没有编译器，自动评测难一档（OSWorld 人工/视觉）。**修法**：区分——代码任务用 SWE-bench 类、GUI 任务用 OSWorld/V\* Bench/Mind2Web 类，别拿同一把尺量两种"动手"。
