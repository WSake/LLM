## 0. 为什么第 6 课是「Agent 评测」？

05 把 Coding Agent 讲完了——但那篇自带一个隐藏前提：**你凭什么信那个 Agent 能把任务做对？** 05 的答案是"过全套测试才接受"——那是把评测塞进提交前的一扇小门。可 Agent 不是只有代码 Agent，代码 Agent 也不只有提交那一刻需要评测。§9.12 开宗明义：**不评测的 Agent 不可信。** 这句的潜台词是：

- **测评是 Agent 开发的正循环起点**：不评测，你的 Agent 改版不会收敛——改一次凭感觉、改十次还是凭感觉，RL 燃料更无从谈起（04 说过 RL 需要可验证奖励，评测台就是那条燃料管）。
- **Agent 比模型更容易被"看起来对"骗过**：普通 LLM 的输出只有文本，文本的好坏靠文字衡量；Agent 有工具、有动作、有副作用，任务成败 = 一系列动作在环境里留下的真实痕迹，**"看起来像完成了"和"真的完成了"之间的裂缝比模型评测深得多**。
- **评测的坑是代理式的**：你让 LLM 打分（judge）、你数成功率、你只看步数……每一种"省事评测"都声称接近真相，§9.12 只给一个红字结论：**好的评测 = 固定环境 + 可验证终结条件 + 成本指标；不要用'看起来像'的 LLM-judge 替代环境真实验证。**

所以本篇是 09 章的"质检课"：05 是"会干活的 Agent"，本篇是"凭什么说它会干活"。§9.12 的三件事一次钉完：**有什么基准**（三类坐标系）、**量哪些指标**（六指标台账）、**怎么算通过**（固定环境 + 可验证终结 + 成本 = 评测台）。配上 §11.5 的 Agent 评测联动（四指标口径：成功率/步数/成本/安全性），再用 §9.14 趋势①收束：**Agent 系统化 = 评测 + 护栏 + 人工审批进生产**——本篇（06 评测）+ 下篇（07 安全）就是这个系统的两块地基。

## 1. 先把问题拆开：Agent 怎么被"看起来对"骗过

评测"模型"和评测"Agent"是两种难度。模型只需要一个正确的答案；Agent 需要一个**在环境里可验证的事实状态**。看一张对比：

| 维度 | 评测纯语言模型 | 评测 Agent | §9.12 应对 |
|---|---|---|---|
| 验证对象 | 文本本身 | 环境状态（文件/API/页面/终端） | **可验证终结条件**：测试/断言/真实返回 |
| 谁来判 | 通常 LLM-judge | 最好环境自动检查 | **不要用"看起来像"的 judge 替代** |
| 成本账 | 几乎不算 | token/步数/时长都烧钱 | **成本指标**进评测 |
| 可复现 | 同 prompt 同输出 | 环境不固定就复现不了 | **固定环境** = 隔离容器/沙箱 |
| 危险面 | 几乎无 | 工具调用可能越权 | 安全事件计入指标 |

拆成三块，就是本篇的账 A/B/C，最后装成账 D 的台子：

- **第一块——"用什么基准测"（账 A）**。§9.12 给了三类：通用（GAIA/AgentBench/τ-bench/τ²-bench）、环境（WebArena/VisualWebArena/OSWorld/Mind2Web/Terminal-Bench）、代码（SWE-bench/RepoBench/LiveCodeBench）。不是随便挑几个出名而已——**三类基准的"真实性"和"自动性"是两回事**：有的真实环境却人工判，有的自动化却模拟环境。先看清坐标系，才知道拿哪把尺量自己。
- **第二块——"量哪些指标"（账 B）**。§9.12 六指标：成功率、时长/步数、token 成本、工具正确率、安全事件、人工通过率。**单指标会骗人**——成功率 9/10 的 Agent 可能是 2× 的 token 换来的，还顺手搞出安全事件。六指标一起看才是账本。
- **第三块——"怎么判通过"（账 C）**。同一批轨迹，环境真值和 LLM-judge 判的结果不一样。**judge 判准 0.85≠1.00，会漏放坏 Agent（FP）也会误杀好 Agent（FN）**。§9.12 红字就在这一块：终结判据换不得 judge。
- **装台（账 D）**：把这些装成"固定环境 + 可验证终结条件 + 成本指标"三件套的评测台，跑三版 Agent，给"上不上生产"的硬判定（里程碑 014）。

## 3. 实验 A · 基准谱系账：三类基准，只有 3/12 是"真"的

先解决"拿什么尺量"。§9.12 列的 12 个成名基准，探针把每个基准在四个维度上摊开：**是否真环境/真问题、能否自动验证、是否侧重成本、哪年出名**。跑出来的表（节选核心行）：

| 基准 | 类别 | 年份 | 真环境 | 自动验证 | 成本侧重 |
|---|---|---|---|---|---|
| GAIA | 通用 | 2023 | ✓ | ✓ | — |
| AgentBench | 通用 | 2023 | — | ✓ | — |
| τ-bench（工具调用） | 通用 | 2024 | — | ✓ | ✓ |
| τ²-bench | 通用 | 2025 | ✓ | ✓ | ✓ |
| WebArena | 环境 | 2024 | — | ✓ | — |
| OSWorld | 环境 | 2024 | — | — | — |
| Terminal-Bench | 环境 | 2025 | — | ✓ | — |
| SWE-bench | 代码 | 2023 | ✓ | ✓ | — |
| LiveCodeBench | 代码 | 2024 | — | ✓ | ✓ |

**合计 12 个基准：真实环境/真实问题只有 3/12（GAIA 真实问题 · τ²-bench 真实 API · SWE-bench 真实 issue）；可自动验证 11/12（OSWorld 桌面像素需人工/视觉=唯一不可自动）；侧重成本 3/12。** 按年份摊开：2023 年 5 个全自动、2024 年 5 个含 1 个不可自动（OSWorld）、2025 年 2 个全自动。

三条读数：

1. **评测的瓶颈不在『自动验证』，而在『环境真实性』。** 11/12 都能在模拟或真实环境里自动核答案了——自动评分已经随处可见。真正稀缺的是「真」：**只有 GAIA（真实问题）、τ²-bench（真实 API）、SWE-bench（真实 issue）3 个是环境/问题都真**。WebArena、OSWorld 这类模拟环境保证的是"固定 = 可复现"，但"真"要靠基准设计者把关。这解释了一个工程现象：**自制评测台最该投入的地方不是评分函数，而是"你的环境到底多接近生产"。**
2. **2025 的新基准把自动验证与成本指标做成了默认。** τ²-bench（真实 API + 双系统评测）和 Terminal-Bench（终端壳）自动验证率 2/2；τ-bench/τ²-bench/LiveCodeBench 三个基准开始带**成本报告**——成本指标正在从"可选的加分项"变成"好评测的默认配置"，恰好印证 §9.12 的公式。
3. **给"同情心式断言"打个码**：探针里"真环境/自动验证/成本侧重"的标记是作者对 §9.12 清单的定性，不是在这些基准上跑了真实 Agent——这是整个账 A 的诚实边界。

## 4. 实验 B · 指标台账：六指标一起看，才看见成功率的代价

有了基准坐标，还要知道量哪些数。§9.12 六指标：**任务成功率 · 完成时长/步数 · token 成本 · 工具调用正确率 · 安全事件数 · 人工通过率**。探针让**同一个客服任务集**（10 个任务，挂靠 02 的客服场景）被同一 Agent 操作系统用两台调法跑完：

| 指标 | A 稳重型 | B 激进型 | 谁占优 |
|---|---|---|---|
| 任务成功率 | 9/10 | 8/10 | A |
| 完成步数 | 13 | 9 | B |
| 完成时长 (s) | 260 | 150 | B |
| token 成本 | 12,000 | 6,000 | **B（A 是 B 的 2×）** |
| 工具调用正确率 | 1.00 | 0.83 | A |
| 安全事件数 | 0 | 2 | A |

**只看成功率：A 9/10 > B 8/10，好像 A 更好。六指标齐看一眼推翻——**

- **token 成本 A = B 的 2×**：A 的"更稳"是多花一倍的量换来的。如果评测只报成功率，你会给一个贵一倍的 Agent 发奖励；成本指标在场的评测台，这单瞬间变成"贵 1× 求 10% 成功率"的待议项。
- **安全事件 A 0 vs B 2**：B 的 2 次失败里有 1 次是工具越权——**成功率把"差点闯祸"和"完成"记成一模一样的 1 分**。安全指标不采集，B 的 0.80 和"0.80 但 2 起越权"在报告上是同一个数。
- **工具正确率 A 1.00 > B 0.83**：B 省步数、省 token，代价是 6 次工具调用里错 1 次——**"看着快"和"做得对"是两条轴**，只看步数/时长会被"快而错"骗过。

一条读数：**六指标不是六个"并列加分项"，是六个不同的事实层**——成功率说"结果对不对"，时长/步数说"绕了多远"，token 说"烧了多少"，工具正确率说"动作准不准"，安全事件说"闯没闯祸"，人工通过率说"人认不认"。**单指标是视图，六指标才是账本。** 成本与安全最容易被"只看成功率的评测"骗过——这正好是 05 账 D 为什么要在"过测试"之外加安全台席的原因，本篇只是把 05 那张只有一扇门的台子扩成了六指标全量采集。

## 5. 实验 C · 真值 vs judge 账：判准 0.85 换不得 1.00

§9.12 全节最重要的一句话是红字：**不要用"看起来像"的 LLM-judge 替代环境真实验证。** 这句话在中文本地教程里常被当作"谨慎原则"跳过，但它是可以用数字证明的。探针取**同 20 条 Agent 轨迹**，两端各判一次：

- **环境真值（可验证终结条件）**：12 条通过、8 条失败——这是台子上的硬事实，如测试通过/API 返回/断言踩中。
- **LLM-judge**：给出另一套判定，算出混淆矩阵：TP 11 · TN 6 · **FP 2 · FN 1** → **判准 17/20 = 0.85**。

| 真值\judge | judge 判"通过" | judge 判"失败" |
|---|---|---|
| 真值通过 (12) | TP 11 | **FN 1（误杀好 Agent）** |
| 真值失败 (8) | **FP 2（放行坏 Agent）** | TN 6 |

读数（这也是 §9.12 红字的"为什么"）：

- **FP = 2：judge 说"通过"，其实真值失败的 2 条 → 坏 Agent 被放行上线。** 这是评测里最贵的错误——评估的终点本来是拦，judge 把它变成了凭感觉放行。上线后坏 Agent 的工具调用是白花的花销，甚至可能升级成安全事件。
- **FN = 1：judge 说"失败"，其实真值通过的 1 条 → 好 Agent 被埋没。** 开发期误杀，成本是返工和错误迭代方向，不如 FP 致命但同样伤。
- **为什么 judge 不能替代真值的根因**：judge 判的是"文字看起来是否像成功"，真值判的是"环境里的事实是否成真"。**语言模型的好话术 ≠ 环境里的真实状态**；Agent 的任务是后者，所以终结判据必须锚在后者。02 的客服里停止判据三态（完成/放弃/转人工）各有可验证触发，就是这个原则的最小组装——本篇把它明确成"终结条件=环境检查器，不是 judge"。

注意分寸：账 C **不是说 judge 一文不值**——judge 便宜、快、适合"先粗筛"；§9.12 禁的是"替代"（拿它当唯一终结判据）。所以务实姿势是：**judge 做开发期预筛，上线判定一律回到环境真值**（§9.14 趋势①"评测进生产"正是这个姿态）。

## 6. 实验 D · 评测台装配账：三件套 + 门禁判定

前三账是零件，账 D 把它们装成台子，回答"到底上不上生产"。§9.12 公式：**好的 Agent 评测 = 固定环境 + 可验证的终结条件 + 成本指标**（教学表编号 `014 Agent 评测台`）。探针装配三件套跑三版 Agent（每版都是 10 任务，预算 8000 token，成功率门槛 ≥0.85，安全事件必须 0）：

| Agent 版本 | 成功率 | token | 安全事件 | 判定 |
|---|---|---|---|---|
| **C · 优化版** | 0.90 | 7,200 | 0 | ✅ **上生产**（全闸通过） |
| A · 稳重型 | 0.90 | 12,000 | 0 | ⛔ 不上生产（token 12,000>8000 预算） |
| B · 激进型 | 0.80 | 6,000 | 2 | ⛔ 不上生产（成功率 0.80<0.85 · 安全事件 2>0） |

三条读数——这台子为什么是"门禁"而不是"打分器"：

1. **A 版成功率 0.90 照样被拦**：token 12,000 超预算。**评测台把"成功率的代价"变成可执行红线**——正是账 B 要防的"只看成功率"被门禁堵死。成本指标不止是报告里的一列，它是一条决定生死的 SQL。
2. **B 版最便宜照样被拦**：token 最省（6,000）但成功率不足 + 2 起安全事件。**"看着快、看着省"不是放行理由**；安全事件是硬门槛，不为省 token 让步。
3. **C 版是全闸都过的优化姿势**：0.90 成功率 × 7,200 token（在预算内）× 0 安全事件。台子不仅会拦，还能告诉你"往哪个方向修"——读报告即知道 A 该砍 token、B 该修工具权限，**评测台是迭代的方向盘，不是考试的打分器**。

把账 D 和 05 账 D 对上：05 是"3 份候选补丁过全套测试才接受"的提交前闸；本篇是把同一把尺换成**完整评测台**——任务集 + 固定环境 + 每任务一个可验证检查器 + token/步数/时长成本计 + 五列汇总报告 + 上生产判定。§11.5 的四指标口径（成功率/步数/成本/安全性）在这张报告里四列齐了。这也正是 §9.14 趋势①"Agent 系统化：评测+护栏+人工审批进生产"里"评测"那一块的形状。

## 7. 这篇 Agent 评测怎么用（一页带走 + 掌握度检验）

**一页带走：**

- **评测不评，Agent 不立（§9.12 红字）**：Agent 有工具、有副作用，"看起来像完成"和"真的完成"之间的裂缝比模型评测深得多。评测是 Agent 改版收敛 + RL 燃料的起点。
- **三类基准 = 坐标系**：通用（GAIA/AgentBench/τ-bench/τ²-bench）、环境（WebArena/VisualWebArena/OSWorld/Mind2Web/Terminal-Bench）、代码（SWE-bench/RepoBench/LiveCodeBench）。但**真环境只有 3/12（GAIA·τ²·SWE-bench），自动验证却 11/12**——瓶颈在"真"不在"分"；2025 新基准把自动验证+成本指标做成默认（2/2）。
- **六指标 = 账本**：成功率/时长步数/token 成本/工具正确率/安全事件/人工通过率。**单指标是视图**——A 成功率 9/10 是 B 8/10 的 2× token 换的，还多了安全事件 2 起。
- **真值 ≠ judge**：同 20 条轨迹 judge 判准 0.85，FP 2 放行坏 Agent、FN 1 误杀好 Agent。**judge 做预筛可以，当唯一终结判据不行**（§9.12 红字）。
- **评测台 = 固定环境 + 可验证终结条件 + 成本指标**（里程碑 014）：每任务一个真检查器（非 judge），加成本计，输出五列，'上不上生产'是硬判定——C 优化版全闸过，A/B 各有拦截理由。

**掌握度检验（自问自答）：**
1. 为什么"只看成功率"会骗人？A 和 B 的数据怎么反驳？（答案：账 B——A 9/10 是 2× token 还叠加 2 起安全事件换的，六指标才是账本。）
2. LLM-judge 的 FP 和 FN 分别代什么损失？为什么 FP 更贵？（答案：FP 放行坏 Agent 上线，FN 误杀好 Agent；前者拦不住坏动作甚至升级安全事件，最贵。）
3. §9.12 好评测公式三件套是？账 D 里哪一列对应成本指标？（答案：固定环境+可验证终结条件+成本指标；token 列——预算 8000 是硬门槛。）
4. 哪些基准是"真环境/真问题"？（答案：GAIA 真实问题、τ²-bench 真实 API、SWE-bench 真实 issue——3/12。）
5. 下篇 07 会补哪块？（答案：Agent 安全——§9.13 威胁模型 + 基线护栏，账 D 的"安全事件=2 不上生产"就是 07 的先声。）

## 8. 常见坑（Agent 评测的 7 个）

1. **把成功率当全部**（账 B 全篇的靶子）：A 9/10 被 2× token + 安全事件拖累。**修法**：六指标全量采集，token/安全设硬门槛。
2. **用 LLM-judge 当唯一终结判据**（账 C 的靶子）：0.85≠1.00，FP 放行坏上线。**修法**：judge 只做预筛，上线判定回到环境真值（§9.12 红字）。
3. **把"模拟环境"当"真实环境"**（账 A 的提醒）：WebArena/OSWorld 保证固定可复现，不代表生产真实。**修法**：报告里注明"模拟环境结果"，真实环境另做小样本人工核。
4. **评测环境不固定，复现不了**："每次跑结果不一样"通常不是模型随机，是环境有状态。**修法**：隔离容器/沙箱/固定种子，乃§9.12 第一项。
5. **终结条件没定义就已经在测**：任务是"完成电商下单"，但"完成"没检查器。**修法**：先给每个任务写可自动检查的终态（断言/返回/文件变更），再开跑。
6. **成本指标只报告不落地**：token/时长列了 report，但不上生产线。**修法**：把成本线写成门禁条件（账 D 的 A 版就是 demo）。
7. **收集六指标但忽略安全事件**：安全事件数是"0/2"就不是教程故事，是真线上事故。**修法**：安全事件设硬门槛（>0 不通过），别让成功率把它稀释成同一个 1 分。

## 9. 诚实边界（AAA 自我审查）

- **要素事实 vs 本机实测**：基准清单、年份、六指标定义、§9.12 公式、"τ²-bench 真实 API/SWE-bench 真实 issue"、"2025 新基准全自动"等定性 = 按知识地图与公开资料整理的**要素事实（写作环境无外网，未在线复核）**；不是本机在这些基准上跑了真实 Agent 的通过率。**请在引用时保留"要素事实"前缀**。
- **仿真 vs 真实运行**：账 B 的 A/B 两台调法、账 C 的 20 条轨迹与 judge 判定、账 D 的三版 Agent = **作者按 §9.12 预置的确定性数据表**（`agent_eval_demo.py` 内固定常量），不是真实 Agent/真实 LLM-judge 的输出。judge 判准 0.85 是"这类误差会发生"的教学演示数字；实际 judge 在不同任务上的正确率可高可低，但"不是 1.00 且会有 FP"的方向性结论与 §9.12 红字一致。
- **统计 = 本机确定性计算**：四账全部计数/比例/混淆矩阵/门禁判定为纯 stdlib 逻辑运算，stdout 三个独立进程 md5 恒一 `eae60048…`，墙钟 ≈0.000 s 仅进 stderr——不依赖任何随机种子、网络或第三方库。
- **边界不自留坑**：本篇没有把"真实 Agent 在这三个真基准上的平均通过率"冒充成本机测量；没有把 judge 贬成"完全没用"（它仍是开发期预筛的合理工具）；下篇 07-Agent 安全会接续"安全事件"这根线。
