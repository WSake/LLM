## 0. 为什么第 10 课是「浏览器 Agent」？

09 讲完 Computer Use，把"无权用 API 的世界让 Agent 用手脚点屏幕"这条线钉死：GUI 没有 schema，只能靠视觉语义 + 确认框护栏。本篇把同一个『动手』问题收进一个奇妙的中途点——**浏览器**。浏览器既是 GUI（像素世界，09 的坐标漂移/误操作全都在），又比 GUI 多了一样东西：**DOM**。

> **Agent 直接操作操作系统 GUI 无需 API（§9.9）→ 浏览器 Agent：同一个动作，但浏览器给了一棵可访问性树，读屏从『看』升到『读』。**

为什么这点重要？09 账 C 里视觉语义 4/4 是"**没有结构**的通用 GUI 兜底"；浏览器有 HTML 结构（DOM）,就有一条更稳的锚。§9.10 的定位是 🟢 了解、和 Computer Use 一起被归入 §17.7.6 的『Computer Use / Browser Agent』——它们共享同一个主循环（截图/DOM→理解→动作→执行→新状态），但浏览器这条路承接口子更多：**订票、比价、数据分析抓取、Deep Research**（§9.10 应用四行），而 CU 更多是"老系统兜底"。2025 年 OpenAI Operator 出圈、Gemini in Chrome 内置，**浏览器是 2026 年 Agent 落地密度最高的环境**。

这也是**多模态 Agent（§9.14 趋势③ / §10.8）的必经中点**：Operator 云端浏览器截屏+视觉理解，同时又能拿到 DOM；UI-TARS 教模型操作 UI。浏览器 Agent 恰好站在『能看屏幕』（视觉）与『能操作 UI』（结构）两条路线交汇的地方——本篇把这两条路都量一遍（账 B），你就知道真实产品为什么 DOM 优先、视觉兜底。

**和前几课的分界**：06-05 的 Function Calling 走 API，动作有 schema 校验；09 的 Computer Use 走像素，没有 schema 只能确认框兜底；本篇的浏览器 Agent 走 DOM——**结构在、名字在，介于 API 与像素之间**（账 B 的核心洞察）。三课连起来正好是"接口谱系的三个档位"。

## 1. 先把问题拆开：Browser Agent 是什么、三种形态、技术点在哪

§9.10 的四行原文就是骨架，一行一拆：

| 原文 | 拆成什么 | 本篇哪账 |
|---|---|---|
| 代表：Gemini in Chrome / AgentKit / Operator / Anthropic 浏览器工具 / browser-use / Skyvern / Playwright MCP | 三条技术路线并存：云端执行、本地插件、协议化 | 账 A（形态✓） |
| 形态：云端浏览器（Operator 类）、浏览器插件（本地）、协议化（Playwright MCP server 暴露给任何 Agent） | **三形态 = 三种『浏览器在哪跑、谁在驱动』** | 账 A |
| 技术点：DOM 可访问性树比纯视觉更可靠 | 读屏两法：DOM（结构）vs 纯视觉（像素） | 账 B |
| 技术点：登录/验证码是工程难点 | 认证档位从公开页到 MFA 的自动化坡度 | 账 C |
| 技术点：anti-bot 对抗 | 反爬识别的是机器特征，护栏四件套抹掉它 | 账 D |
| 应用：订票、比价、数据分析抓取、Deep Research | 应用不是新原理，是"浏览器 Agent 能把人从重复点击里解放" | 全文串场 |

**首先把『形态』这个概念说清**——这是浏览器 Agent 和 Computer Use 最大的新手沟。Computer Use 是"一个 Agent + 一套屏幕"，形态只有一种（要么本地要么云端跑的整机）。浏览器 Agent 有**三种部署形态**：

1. **云端浏览器（Operator 类）**：浏览器跑在厂商云环境里，Agent 也跑在云里，从云端看这个浏览器、操作它。好处：零本地部署、天然沙箱隔离、横跨登录态由厂商管；代价：**数据经过云端**（内网报表不能往外送）、**每次启动成本高**（开一个云端浏览器环境）、批任务贵。
2. **浏览器插件（本地）**：浏览器装个插件，Agent 在你的本地浏览器里运行。好处：数据不出域、免部署；代价：**绑一个浏览器实例**，跨标签/独立调度难，规模上不去。
3. **协议化（Playwright MCP server）**：把浏览器操作封装成一个 MCP server（Playwright MCP 就是干这个的），**任何 Agent 只要会调 MCP 就能驱动它**。MCP server 可以部署在目标网络侧（内网也行），常驻、可调度、可复用。这是三形态里"最像 API 的浏览器"。

**技术点三件**（§9.10 原文）：DOM 可访问性树（读屏）、登录/验证码（身份）、anti-bot（对抗）。这三件正好是浏览器 Agent 管线"读→想→动"三个环节里最容易踩坑的地方——本课四账逐个数值化。

主循环依然是 09 章的同一套（04 ReAct / 02 六状态机）：

```
读屏幕（DOM a11y 树 / 截图）→ 理解（选目标元素：'确认下单'按钮）→ 动作（click/text）→ 执行 → 新页面/DOM（观察，喂回 loop）
```

只是"截图"这一行多了一个可选项（读 DOM），"动作"多了填表、滚动、切换标签页——**浏览器把"单手点屏幕"扩展成"双手操作整套网页界面"**。

## 3. 实验 A · 形态账：三种形态怎么选——没有一个包打天下

把 §9.10 第一行"形态："展开成三个真实浏览器任务 × 三种部署形态的矩阵——**同一个任务换形态，可用性差在哪**：

| 任务 | 网络边界·调度 | 云端浏览器(Operator类) | 浏览器插件(本地) | Playwright MCP(协议化) |
|---|---|---|---|---|
| 第三方网站订票 | 公开网·即点即用 | ✅ | ✅ | ✅ |
| 内网 BI 报表拉取 | 仅内网·按需/定时 | ❌ 内网进不来/数据出域 | ✅ | ✅ |
| 每天批量抓价落库 | 公开网·脚本化·全天候 | ❌ 启动成本高 | ❌ 绑浏览器难调度 | ✅ |

**可用性：云端 1/3 · 插件 2/3 · 协议化 3/3。**

三个读数：

**第一个，云端浏览器是"开箱即用"但被网络边界框死（1/3）。** Operator 类云端浏览器第一出汗在哪？公开网任务（订票）零配置就能跑——登录态由厂商管着、环境自带截图/点击。但**内网报表**这一格直接❌：云端浏览器跑在厂商云环境，物理上"进不了你的内网"；就算勉强代理进去，**数据出域**这一条在多数公司就否了。批量抓价也❌——每次干活要起一个云端环境，批任务天天起、成本线性涨。**云端形态的适用域 = 公开网 + 低频 + 不敏感**。

**第二个，插件"本地执行"时有保留，但绑死一个浏览器（2/3）。** 浏览器插件在本地跑：内网报表可以进（数据不外走）、订票也行。**但"每天批量抓价落库"这一格❌**——插件住在某个浏览器实例里，生产者开插件在哪、调度器就得到哪，很难做成夜里无人值守，也扛不住水平扩展。**插件形态适用域 = 数据敏感 + 骨灰级用户本地用**。

**第三个，协议化三格全过（3/3）——因为它把浏览器变成了"标准工具"。** Playwright MCP server 常驻在目标网络侧：内网就部署内网、公开网就部署公开网，Agent 通过 MCP 协议驱动它。订票/报表/批量抓价都能接；批量任务尤其适配——server 常驻，任何调度器深夜叫它就行。**为什么它能全覆盖？因为形态 1/2 的问题是"浏览器在哪跑"（云端/本地），形态 3 的问题是"怎么暴露给 Agent"——把浏览器包成 MCP server 之后，网络边界由部署位置决定、调度由常驻保障，三格天然可过。**

**值得注意的收敛**：这和 09 账 A 是一个递进的洞察——09 说"无 API 的世界用 GUI（CU 3/3）"，本篇说"有浏览器且要用浏览器时，协议化（MCP）3/3"。**Computer Use 是屏幕级的兜底，协议化浏览器是结构级的正路**；真实落地常两者并存（Operator 云端起浏览器=计算机视觉 + 可拿 DOM 双管齐下）。

**账 A 的总结论（断言 1/1 全过）**：

> **三种形态没有一个包打天下：云端 1/3（内网进不来/数据出域/批任务成本高）、插件 2/3（本地但绑浏览器难调度）、协议化 Playwright MCP 3/3 最通用。选型看三问：浏览器在哪跑（网络边界）？数据允不允许出域（敏感度）？要不要常驻调度（批任务）？——三问都指向协议化时，就是 Playwright MCP。**

## 4. 实验 B · 读屏账：DOM 可访问性树 vs 纯视觉，有结构就不该猜像素

§9.10 技术点第一句——**『DOM 可访问性树比纯视觉更可靠』**。这句大白话要一个数字撑住。探针用同一『确认下单』按钮、四个典型页面状态、两种读屏法逐个命中：

| 页面状态 | DOM 可访问性树 | 纯视觉（截图） |
|---|---|---|
| 静态正常 | ✅ 读 role/text/aria | ✅ 看清 |
| 促销浮层遮挡按钮 | ✅ 元素在树里自带 rect | ❌ 看到的是浮层文字 |
| JS 动态后加载 | ✅ 轮询 a11y 树等进树 | ❌ 拍到 loading |
| 无文本图标钮(aria-label) | ✅ aria-label 兜底 | ❌ 无文本=盲 |

**DOM 可访问性树 4/4 · 纯视觉 1/4。** 三个读数：

**第一个，DOM 的精要：元素从树里可定位 = 有身份 + 有坐标。** 静态页两法都行。但浮层遮挡下，截图看到的是**浮层上飘着的促销文案**，你认不出底下还有个『确认下单』；DOM 树里元素还在——**有 role/text/aria + 自己的 rect**，可以先"关浮层"再点它。这跟 06-05 的参数校验是同一逻辑：**结构在、名字在，就像 API 的 schema;像素没有 schema，只能猜**。

**第二个，动态加载是 DOM 的"等待"、视觉的死穴。** 按钮首帧不在 DOM——JS 1 秒后才把它插进去。DOM 法：**轮询 a11y 树，等到它出现再操作**（Playwright 的 `wait_for` 就是这个）。纯视觉法：截图拍到的是 loading 转圈，认不出目标。**"等元素出现"是浏览器世界最常见的 DOM 必杀技**，而视觉必须靠命中等帧率恰好拍对。

**第三个，无文本组件：aria-label 是给机器的名字。** 纯图标按钮（🛒/⚙/☰ 汉堡菜单）在 09 账 C 里直接把 OCR 逼进死路；浏览器里它们都有 `aria-label`（无障碍标签，屏幕阅读器用）——**DOM 法读 aria-label 就拿到了名字**，视觉法依然抓瞎。这正好把 09 账 C 的"图标死法"升维成"有名字，只是名字在树里不在画面上"。

**和 09 课连起来看，这是同一个结论的两面**：09 账 C 说"通用 GUI 没有 schema，视觉语义 4/4 是兜底"；本账 B 说"浏览器有 DOM 结构，就别再猜像素"。**选读屏的顺序 = 有 DOM 用 DOM，DOM 拿不到的（动态canvas、视频帧）视觉兜底**——真实产品（browser-use/Operator）就是这个叠加策略。

**账 B 的总结论**：

> **有结构就不该猜像素：DOM 可访问性树 4/4 vs 纯视觉 1/4——遮挡（元素还在树里自带 rect）、动态加载（轮询等进树）、无文本组件（aria-label 兜底），DOM 全接得住；纯视觉每帧都是快照，遮挡/未加载/无文本=盲。§9.10『DOM 可访问性树比纯视觉更可靠』的数字版 = 结构先见、像素单帧。**

## 5. 实验 C · 登录账：登录/验证码为什么是工程难点

§9.10 技术点第二句——『登录/验证码是工程难点』。难点在哪？探针把同一"拉取我的个人报表"任务放在四个认证档位上，测自动化成功率与人工接管率：

| 认证档位 | 自动化成功率 | 人工接管率 |
|---|---|---|
| 公开页（无需登录） | 100% | 0% |
| 表单登录 + session 保持 | 100% | 0% |
| 图形验证码 | 30% | 70% |
| SSO + 二次认证（MFA） | 10% | 90% |

三个读数：

**第一个，表单登录其实不难——难的是"登录态要管好"。** 表单纯用户名+密码页，注入凭证就能过（**自动化 100%**）。但前提是 **session 保持**：一次登录成功后，把 cookie/token 带进后续每个请求，**而不是每次都重复登录**。浏览器 Agent 的登录态管理 = 凭证仓库 + session 复用 + 过期刷新——这是基本功，但九九归一在真实工程里踩的坑（登录态掉线、多标签会话串、Cookie 过域）全在这一行。*注意 09 账 C 的教训在这里回传：session 是 HTTP 层的东西，跟页面像素坐标完全无关——又是一条"结构>像素"的证据。*

**第二个，验证码和 MFA 是反自动化的护城河（30%/70%、10%/90%）。** 图形验证码：只有规则恰好能过的简单图形能自动（30%），剩下 70% 转人工；SSO+MFA：OAuth 前段（点登录、选账号）可以自动化，但 **TOTP 动态码/设备确认把这扇门真正锁死**——自动化成功率 10%，90% 要人。这也是 §9.10 把『登录/验证码』并列成"工程难点"的原因：**难不在"会不会操作"，难在"站方不想让你自动化"**。

**第三个，工程现实 = 三层兜底而不是硬刚。** 真实浏览器 Agent 的做法从来不是"死磕验证码识别"（那是打猫鼠游戏），而是：**能自动的全自动（公开页+表单登录+session），到验证码/MFA 这道墙就转人工接管**（账 D 的护栏①会再用一次）。Deep Research 这类应用能跑起来，正是因为它们的站点大多没有硬验证码——**选好目标、把自动化的边界画在验证码之前，才是工程正确姿势**。

**账 C 的总结论**：

> **登录/验证码是工程难点，难在"站方不要你自动化"：表单登录+session 保持自动化 100%（登录态要管好，cookie/token 复用是基本功），图形验证码 30%/人工接管 70%，SSO+MFA 10%/人工 90%。工程现实不是死磕验证码，是把自动化边界画在验证码之前 + 到墙转人工。**

## 6. 实验 D · 反爬账：anti-bot 对抗与护栏四件套

§9.10 技术点第三句——『anti-bot 对抗』。反爬（anti-bot）识别的是你的**机器特征**，不是任务本身。探针用同一任务（10 分钟抓取 100 个商品页）跑两种配置：

| 配置 | 被拦（429/403/验证码） | 成功 |
|---|---|---|
| 无护栏（120ms 连发·同 UA·无重试） | 38/100 | 62/100 |
| 配护栏（限速2s·指纹稳·退避重试·验证码转人工） | 3/100 | 97/100 |

**被拦 38 → 3。** 三个读数：

**第一个，反爬的三张机器脸：节奏、指纹、不重试。** 无护栏的 38 拦从哪来？①**节奏**——120ms 连发，10 分钟 100 请求像自杀式打击，滑动窗口直接判你是脚本；②**指纹**——同 UA 同头，一眼看穿自动化工具特征；③**无重试**——429 一到就断，任务中途死掉。合在一起就是"长了一张机器的脸"，站方不针对任务、针对的就是这张脸。

**第二个，护栏四件套正好是 07 六护栏的浏览器版（账 D 的核心）。** 对照着看：

| 浏览器护栏四件套 | 07 六护栏对应 | 在管什么 |
|---|---|---|
| 限速 ≥2s/请求 | 动作限额 | 把高频机器节奏降回人类节奏 |
| UA/指纹稳定 | 最小权限 | 伪装成正常用户=最小暴露面 |
| 429 退避重试(上限2次) | 错误重试 | 被限速不被封号 |
| 验证码 → 转人工接管 | 人工确认 | 自动化做不到的确定性兜底 |

**第三个，护栏不是"教打爬虫"，是"别骚扰服务器"——双赢。** 限速让请求节奏像人、退避让 429 自动续上、指纹不暴露工具——**对站点的冲击小了、任务的成功率反而高了**（97 对 62）。剩 3 拦全是真验证码页，转人工（账 C 的墙在这里第二次出现）。**伦理上完全站得住：合法抓取/自动化操作要尊重服务条款与 robots，本题的护栏恰恰是那个"尊重"的载体。** 反爬对抗的正确姿态不是"绕开 CAPTCHA"，是"先做守法用户，再谈自动化"。

**账 D 的总结论**：

> **anti-bot 对抗 = 别长着一张机器的脸：无护栏 38 拦（高频节奏+同指纹+不重试全暴露自动化）→ 护栏四件套 3 拦（限速 2s=动作限额·指纹稳定=最小权限·推避重试=错误重试·验证码转人工=人工确认），成功率 62%→97%。反爬识别的不是命令行是行为模式，做守法用户（限速）才能跑得久。**

## 7. 这篇 Browser Agent 怎么用（一页带走 + 掌握度检验）

**一页带走：**

- **浏览器 Agent = 把 Computer Use 收进有 DOM 的浏览器**（§9.10『浏览器智能体』）：同样的读屏→理解→动作→执行→新状态主循环，但浏览器给了结构，从"看像素"升到"读树"。
- **三种形态没有一个包打天下**（账 A）：云端 1/3（内网进不来/数据出域/批任务成本高）、插件 2/3（本地但绑一个浏览器）· **协议化 Playwright MCP 3/3 最通用**（server 常驻目标网络侧，任何 Agent/调度器驱动）。选型三问：网络边界、数据敏感度、要不要调度。
- **读屏：有结构就不用猜像素**（账 B）：DOM 可访问性树 4/4 vs 纯视觉 1/4——遮挡（元素自带 rect）、动态加载（轮询等进树）、无文本组件（aria-label），DOM 全接得住；纯视觉单帧=盲。（09 账 C 视觉语义 4/4 是"没有结构"时的兜底，本篇让位于更稳的 DOM。）
- **登录/验证码是工程难点**（账 C）：表单+session 保持 100%（登录态要管好）、验证码 30%+人工 70%、SSO+MFA 10%+人工 90%——把自动化边界画在验证码之前，到墙转人工。
- **别长着一张机器的脸**（账 D）：无护栏 38 拦（高频+同指纹+不重试）→ 护栏四件套（限速+指纹稳定+退避重试+验证码转人工）=07 六护栏浏览器版，拦截 38→3。
- **落地形态**：Operator 类云端浏览器（公开网低频）、browser-use/Skyvern（开源浏览器自动化）、Playwright MCP（协议化标准件）、Deep Research（多 Agent 各开浏览器分头调研）。

**掌握度检验（自问自答）：**
1. 浏览器 Agent 三种形态，各自最大的短板是什么？（答案：云端——内网进不来/数据出域/批任务成本高；插件——绑死一个浏览器实例难调度；协议化 Playwright MCP——最通用。账 A：云端 1/3、插件 2/3、协议化 3/3。）
2. 为什么 DOM 可访问性树比纯视觉可靠？（答案：元素在树里就有 role/text/aria/rect——遮挡能先关浮层再点、动态加载能轮询等进树、无文本组件有 aria-label；截图是"单帧快照"，遮挡/未加载/无文本全盲。账 B：DOM 4/4 vs 纯视觉 1/4。）
3. 登录/验证码哪个能自动、哪个必须转人工？（答案：表单登录+session 保持自动 100%（cookie/token 复用是基本功）；图形验证码 30% 自动、SSO+MFA 10% 自动——后两个要人工接管 70%/90%。验证码/MFA 是反自动化的护城河，别硬刚。）
4. anti-bot 到底在识别什么？（答案：行为模式——请求节奏（高频=机器）、指纹（同 UA=工具）、无退避（429 就到）。护栏四件套=限速+指纹稳定+退避+验证码转人工，把机器脸抹掉：38 拦→3 拦。）
5. 和 09 Computer Use 的分界？（答案：同一动手主循环，但 GUI 没结构只能视觉语义兜底（09 账 C 4/4），浏览器有 DOM 结构就该用结构（本账 B 4/4 vs 1/4）——09 管"无 API 的螺丝壳/老系统"，本篇管"有 DOM 可结构化的网页"。）

## 8. 常见坑（Browser Agent 的 7 个）

1. **默认上云端浏览器**（账 A 的靶子）：Operator 类开箱即用，但内网报表进不去、数据出域要被合规卡、批任务每次起环境的成本线性涨。**修法**：先问三问（网络边界/数据敏感/要调度），三问指向非公开→用插件或协议化。
2. **靠纯视觉读屏，不读 DOM**（账 B 的靶子）：截一张图让模型认——浮层遮挡/动态加载/无文本组件全翻车（1/4）。**修法**：优先 DOM 可访问性树（Playwright 默认就有）；视觉只兜 DOM 覆盖不到的（canvas、视频帧）。
3. **登录态只管一次**（账 C 的靶子）：拿到一次 session 不复用、过期不刷新，任务后半段反复重登。**修法**：凭证仓库 + cookie/token 全 session 复用 + 过期重登，把登录做成"一次成功、全程带带"。
4. **死磕验证码**（账 C+账 D 联合靶子）：验证码、滑块、MFA 是站方主动防自动化，识别精度天花板就在那里（自动化 30%/10%）。**修法**：到墙转人工（账 D 护栏①），业务上把目标站点选在"无硬验证码"区（Deep Research 能跑起来正是这个原因）。
5. **一味限制速反成自杀**（账 D 的靶子）：无护栏 120ms 连发，10 分钟 100 请求像攻击，38/100 被拦还打扰站点。**修法**：限速到人类节奏（≥2s）是第一步，再把 UA 指纹稳定 + 429 退避重试（上限 2 次）。
6. **把反爬当"绕验证码"**（账 D 的伦理靶子）：Anti-bot 对抗不是教你撞 CAPTCHA，是教你别被行为特征误伤。**修法**：先做守法用户（尊重 robots、限速、不过载），护栏是"合规自动化"的载体而非破解工具。
7. **拿浏览器 Agent 当万能接口**（全章收束的靶子）：浏览器自动化永远比 API 慢几个量级、且处处是墙（登录/验证码/反爬/页面变迁）。**修法**：**有 API 走 API（06-05 FC）、有 MCP server 走 MCP（07-11）、最后才下浏览器（本篇）**——浏览器是"最后一公里的兜底"不是第一选择。

- **仿真 vs 真实运行**：账 A 的任务集与形态判定（"云端进不来内网/数据出域/插件绑浏览器"）、账 B 的四个页面状态与两法判定、账 C 的四个认证档位百分比、账 D 的 100 请求拦截计数（38→3）与护栏四件套映射 = **作者按 §9.10/§17.7.6 预置的确定性数据表**（`browser_agent_demo.py` 内固定常量），不是真实 Playwright/browser-use/Operator 在真实站点上的结果。真实浏览器的 DOM 稳定度、登录态复杂度、反爬强度因站点而异；但"三形态各有短板协议化最通用、DOM 结构比单帧像素可靠、表单登录能自动验证码/MFA 要转人工、高频+同指纹会被反爬拦"这些方向性结论与 §9.10 一致。
- **统计 = 本机确定性计算**：四账全部可用性矩阵/命中计数/百分比/拦截数 = 纯 stdlib 逻辑运算，stdout 三个独立进程 md5 恒一 `c073988a…`，墙钟 ≈0.000 s 仅进 stderr——不依赖任何随机种子、网络或第三方库。
- **边界不自留坑**：本篇没有把"真实浏览器 Agent 的 DOM 命中率/登录成功率/反爬拦截率"冒充成本机测量（A-D 全是教学任务上的确定性刻度）；没有把浏览器当"万能解法"（常见坑 7 明示 API→MCP→浏览器是选型顺序，浏览器是兜底）；没有把 anti-bot 讲成"破解"（账 D 强调守法限速，护栏是合规自动化的载体）。
