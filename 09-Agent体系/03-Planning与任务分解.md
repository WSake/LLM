## 0. 为什么第 3 课是「Planning 与任务分解」？

02 把 Agent 的骨架画出来了：**目标→感知→计划→行动→观察→评估→循环**。但那份六状态图里最不起眼的「计划」环点，恰恰是 Agent "会不会做事"的分水岭——同一个任务，有的 Agent 先想 1 次就冲，有的想 3 次边做边想，有的拆成树一层层展开，最后的结果可能一样，但**钱和时间不一样、中途变故来了谁先崩也不一样**。

02 的账 D 只给了三个安静的数字：**计划调用 1 < 3 < 4**（P&E / ReAct / 分层）。本课把它从「三档」展开成「两把可算的账 + 一把评测尺」：

- **形态轴**（想几次才做）：一次性 / 逐步 / 分层不是越好越高级，而是**按任务确定性强弱选**——把 02 的静态数字丢进「中途条件变了」的动态场景，一次性计划会白做一步、被迫显式重规划；逐步计划把重规划摊进每步思考，0 白做 0 显式重规划。选型的真正分水岭不在「哪个模式强」，在「任务会不会变」。
- **粒度轴**（拆多细才稳）：同一任务，平铺拆成 8 步一次跑 vs 分层拆成 根→3 子→8 叶 两棵树，差别在一次「中间某步阻塞」上：平铺后面 2 叶全白排，分层只重拆那个叶子分支。**分层的代价是 3 次子级编排税，收益是故障隔离。**
- **一把尺**（计划可信吗）：§9.3 点名的 PlanBench（2024）思想——计划质量不能靠「看起来像计划」，要用**可执行性 / 前提满足 / 覆盖 / 冗余**四指标在执行前量一遍。计划幻觉（plan hallucination）与最终答案幻觉是同族，但**计划幻觉在行动之前抓，是最便宜的验证回路**。

一句话定位：**02 教你「画 Loop」，本篇教你「在 Loop 里把『计划』这一个节点做专业」——别的节点在真金白银地跑，计划节点是唯一不要执行成本就能提前修的地方，不把这里修好，后面每一步都在为一份坏计划买单。**

## 1. 先把问题拆开：规划 ≠ 列步骤

一个常见的错觉：规划 = 「把任务用编号列成年列表」。列了 8 步计划 ≠ 有一份能执行的计划。区分在于——**列单子只回答『有哪些事』，规划要回答『下一步到底干什么、凭什么一定能原来那么干下去』**：

| 规划要回答的问题 | 列单子漏掉的 | 一坏就坏在哪 |
|---|---|---|
| 每步**真的可执行**吗？ | 步骤里混进了不存在的动作 | 行动节点拿着幻觉步骤去调不存在的 API（§9.3 的 PlanBench「可执行性」判据） |
| 每步的**前提**被前面的步满足了吗？ | 跳过了「解析数据」直接「做统计」 | 走到中途发现材料的形态不对，回头补步=白做前面的 |
| 每步最终**覆盖**目标任务了吗？ | 计划做完不等于目标完成 | 目标验收点在计划里根本没覆盖到 |
| 有没有对目标**没用**的步？ | 夹带打印日志之类的「仪式动作」 | 白烧 token 还拖长循环（§9.12 成本指标） |
| **条件变了**怎么办？ | 计划是一次性的，中途就作废 | 白做步 + 显式重规划，多付钱多付轮数 |

所以本课把「规划」拆成三个可测量的小问题：

1. **想几次才做？** —— 一次性 / 逐步 / 分层，形态不同省的东西不同（账 A）。
2. **拆多细才稳？** —— 平铺 vs 分层，深度换的是故障隔离（账 B）。
3. **计划可信吗？** —— 四指标评测，执行前把计划幻觉拦下来（账 C）；以及拦不住时，**重规划花得起几次**（账 D）。

## 3. 实验 A · 计划形态执行账：静态 vs 动态谁更稳

同一个 3 子任务旅行计划（`s1 查可行日期 → s2 订酒店 → s3 租车`）跑两种场景：**静态**（全程顺利）和**动态**（`s2` 处酒店满房→被迫换城市），三种规划方式各报四列：计划调用 / 执行动作数 / 白做步 / 显式重规划。

| 形态 | 场景 | 计划调用 | 执行动作 | 白做步 | 显式重规划 |
|---|---|---:|---:|---:|---:|
| 一次性计划（P&E） | 静态 | **1** | 3 | 0 | 0 |
| 一次性计划（P&E） | 动态 | 2 | 3 | **1** | **1** |
| 逐步计划（ReAct） | 静态 | 3 | 3 | 0 | 0 |
| 逐步计划（ReAct） | 动态 | 3 | 3 | **0** | **0** |
| 一次性 + 条件分支 | 动态 | **1** | 3 | **0** | **0** |

三个直接结论：

1. **静态场景，确定性任务用一次性省 2 次思考**：1 次计划列全 3 步清单，比逐步少 3−1=2 次思考调用——这正是 02 账 D 那个「1<3」的字面展开：**确定性任务把『想几次』降到最低，是纯赚的。**
2. **动态场景，形态分水岭露出来了**：一次性计划在 `s2` 卡住——这一步白做了（白做步 1）、计划作废（显式重规划 1）；逐步计划每步先思考再动手，`s2` 的变化自然被**下一步的思考**吸收，0 白做、0 显式重规划。**选型的真问题不是『P&E vs ReAct 谁好』，是『任务会不会变』。**
3. **一次性 + 条件分支 = 确定性任务对冲变化的外挂**：预先把分支写进计划（`若 s2 满房 → 换城市`），动态场景回到计划调用 1 / 白做 0 / 重规划 0。它比上 ReAct 便宜（不增加思考次数）、比裸 P&E 稳健（不用中途重规划）——**对『能预判的不确定性』，写进计划比换形态便宜。**

> 探针断言：静态 1<3 · 动态 P&E（白做1/重规划1）vs ReAct（0/0）· 分支计划（1/0/0）全部锁定。
> 挂靠：02 账 D 的 1<3<4 是静态三档，本篇把它升级成「静态省思考、动态看浪费、分支吞风险」的二维账——**形态选择 = 任务确定性的函数。**

## 4. 实验 B · 任务分解粒度账：平铺与分层，深度买什么

同一个 8 单元任务（如「写一份行业报告」：收集 3 + 分析 2 + 撰写 3 = 8 叶），两种分解方式，模型是「中间某叶（第 6 叶）阻塞」：

| 分解 | 分解结构 | 计划事件 | 子级编排税 | 第 6 叶阻塞 |
|---|---|---|---|---|
| 平铺 flat | depth=1，一次 8 步 | 9（1 计划 + 8 执行） | 0 | 波及后面 **2 叶白排** |
| 分层 tree | root → 3 子 → 8 叶 | 12（根计划 1 + 子级编排 3 + 叶执行 8） | **3** | **0**（只重拆该分支） |

这笔账的读法：**分层的代价是 3 次子级编排（每棵子树一层汇总/一次启动），收益是故障隔离 2 个叶子。** 平铺看着「事件最少」（9 vs 12），但第 6 叶阻塞的瞬间，后面 2 叶的步骤全作废，得整段重来；分层把故障封在叶子分支内，重规划成本按分支计而非按剩余清单计。

> 对应到 02 账 D 的「分层计划调用 4」：本篇把它摊进一棵真实的树里——1 次根计划 + 3 次子任务细化（=子级编排税 3）正是 02 那个「1+3」的树展开。**深度买的是隔离，隔离值钱的前提是任务里故障概率不低；纯确定性低风险任务，平铺的白赚那 3 次编排税。**
> 探针断言：flat（9/0/2）vs tree（12/3/0）· 3 次编排税换 2 叶故障隔离，全部锁定。

## 5. 实验 C · 计划质量评测账：四指标，执行前最后的闸门

§9.3 点名的 PlanBench（2024）思想落到本课：计划质量不能靠「看起来像计划」，用四个**可执行前验证**的指标量一遍——**可执行性**（每一步是真实可执行的动作吗，有没有幻想动作）/ **前提满足**（第 i 步的前提有没有被前 i−1 步的产出满足）/ **覆盖**（最终产出集覆盖目标任务验收吗）/ **冗余**（有没有对目标任务毫无贡献的步）。

探针同一份「下载→解析→按列统计→生成报告」的动作库（含一个**不存在**的 `HyperDB 幻方索引 API` 和一个**无用**的 `打印日志`），评测四份计划：

| 计划 | 结论 | 抓到哪个缺陷 |
|---|---|---|
| 好计划（四步齐全） | ✅ 全指标通过 | 0 缺陷 |
| 坏计划①跳过解析直接统计 | ❌ | **前提不满足** |
| 坏计划②调用不存在的 HyperDB API | ❌ | **不可执行** |
| 坏计划③夹带打印日志 | ❌（打印日志产出与任何后续需求无关） | **冗余步(1)** |

三行坏计划各被**恰抓出 1 类**缺陷，好计划 0 缺陷。这笔账的价值一句话：**「看起来像计划」≠「能执行的计划」——缺前提、幻想动作、冗余步这三类计划幻觉，全都能在行动**开始前**、不花任何执行成本的地方判掉。** 这就把 02 账 C 的验证回路思想往前拨了一格：02 在评估节点用规则验证器抓**最终答案**的幻觉（7→8，多付 1 遍循环）；本篇在计划节点先抓**计划本身**的幻觉——**越早的验证越便宜，计划闸是整条 Loop 里最便宜的那道闸。**

> 与 §9.7 严格对齐：「Agent 可靠性来自验证回路，而不是更好的提示词」——这里「更好的提示词」换不成一个能执行的计划，四指标能。
> 挂靠：02-20 规则验证器 best-of-k≈覆盖率 78/80%——同一「真值来源 = 可执行计算，不是『看起来像』」的判据，本篇把它用在计划步骤上。

## 6. 实验 D · 重规划成本与工具台账：花有限的钱，做好重规划

**重规划预算（刹车片）**：账 A 告诉我们再完美的计划也有动态衣服穿破的一天，所以重规划不是要不要做、是**做几次封顶**。探针给重规划装预算 `cap=2`：

| 需要的重规划 | 接受次数 | 终局 | 判据 |
|---|---|---|---|
| 2 次 | 2 | **完成** | 都在预算内 |
| 3 次 | 2 | **转人工** | 第 1 次重规划被拒（预算 cap=2） |

和 02 账 B 的护栏①（步骤上限 cap=4 触顶→放弃·转人工）同构：**重规划也受步骤上限约束**——「再想想」不能无限想，多付 1 次重规划就交人兜底。真实的「先重试再重规划」顺序挂靠 06-05：行动层瞬时错误先自愈（报错自愈 3/3），自愈不了的才轮到计划层重规划，重规划本身再吃 cap。

**工具台账（要素事实 = 非本机实测）**，§9.3 的四个落点一次性钉出：

| 工具/方法 | 年份 | 一句话机制 | 定位 |
|---|---|---|---|
| Plan-and-Execute | 2023 | 先列全步骤再执行 | 三种方式之一（一次性计划的方法化） |
| LLM Compiler | 2024 | 把计划编译成可执行步骤图 | 图上计划 · 显式控制流 |
| 代码即计划 | 天然形态 | 代码本身就是可执行计划的天然形态 | Coding Agent 首选 |
| PlanBench | 2024 | 规划质量评测基准（可执行/前提/覆盖） | 规划能力测量（账 C 的思路来源） |

四笔账合起来给第五条路线：**确定性任务→一次性省思考 · 开放/会变→逐步少浪费 · 复杂大任务→分层买隔离 · 要可靠→计划先过评测闸（账 C）· 重规划→有预算地做（账 D）。**

## 7. 这篇 Planning 怎么用（一页带走 + 掌握度检验）

一页带走（四条硬记忆）：

```
① 形态轴（想几次）：一次性 < 逐步 < 分层 —— 静态省思考(1<3) · 动态逐步零浪费(P&E 白做1+重规划1 vs 0/0) · 分支计划预先把不确定写进计划=0 白做 0 重规划
② 粒度轴（拆多细）：分层用 3 次子级编排税换 2 叶故障隔离（flat 波及 2 vs tree 0）——深度买隔离，确定性低风险任务平铺更赚
③ 一把尺（可信吗）：可执行性 / 前提满足 / 覆盖 / 冗余 四指标 —— 计划幻觉在执行前抓，是最便宜的验证回路（漏前提/幻想动作/冗余步各被抓出 1 类）
④ 一个刹车：重规划预算 cap=2 —— 超 1 次就转人工，重规划也受步骤上限约束（接 02 账 B 护栏①）
```

**掌握度检验**：不看资料，回答三个问题——(a) 一个「读数据库→算 KPI→写周报」的确定性任务，用哪种形态？省下什么？(b) 一个「跟客户来回沟通需求」的开放咨询任务，用哪种形态？为什么 P&E 在这种任务上会白做步？(c) 你拿到一个 12 步的「大计划」，在动手执行前，你要先检查它的哪四件事？（答案：(a) 一次性，省 2 次思考；(b) 逐步（或一次性+条件分支），因为需求会变，一次性计划遇变即作废要白做步+显式重规划；(c) 可执行性/前提满足/覆盖/冗余——四指标先跑一遍。**答不全 = 回看账 A 的差异与账 C 的四计划评测。**）

## 8. 常见坑（Planning「列单子病」的 6 个）

1. **把「列步骤」当规划**：列了 8 步但没查可执行性/前提 → 计划幻觉混进计划节点，到行动节点才爆（幻想 API、跳过前提）。规划 = 列 → 编译 → 四指标校验（账 C）。
2. **形态一刀切**：所有任务都上 P&E 或都上 ReAct。开放任务用 P&E → 白做步 + 显式重规划（账 A 动态）；确定性任务用 ReAct → 白烧 2 次思考（账 A 静态）。**形态是任务确定性的函数。**
3. **忘了「条件分支计划」这个选项**：一遇到「可能会变」就直接上 ReAct。对能预判的不确定性（满房就换城市），把分支写进计划就行——**0 白做 0 重规划，还比 ReAct 便宜（账 A 第 3 行）**。
4. **分解只看「好不好读」**：平铺好读、一眼看到头，但中间一步阻塞就波及后面所有步骤；分层读着深一点，故障却能封在分支里（账 B）。**按故障成本选粒度，不是按美观选。**
5. **重规划无限做**：「再想想」不设上限 = 每次失败都是跨国度重来 → 预算 cap 封顶（账 D：需 3 次、cap 2 → 转人工；接 02 账 B cap 触顶同构）。
6. **只靠「执行完看结果」评价计划**：计划质量永远等循环结束才知道，等于把计划幻觉的执行成本全付了——**PlanBench 思路：动手前先跑四指标（账 C），是最便宜的验证回路（§9.7 原话）。**
