## 0. 为什么收束章单开一本"诊断手册"？

08-RAG 体系前面的章节各讲**一个机制**：03 讲怎么混合、04 讲怎么分块、06 讲怎么压缩、10 讲什么时候多跳、11 讲怎么建图。它们回答的都是"**想变强，去哪改**"。可实际做 RAG 的人碰到的问题是反着来的：

> 我的回答答非所询——是 embedding 的问题？chunk 的问题？还是 prompt 的问题？
> 我的引用标错源了——是检索坏了？元数据坏了？还是生成侧自己编的？
> 我更新了知识库，它还在答旧内容——是索引没刷新？缓存没失效？还是检索根本就没召回新版？

同一个"看起来很普通"的症状，三个完全不同的根因，对应的修复站点在三个不同的章节。这就是本手册存在的理由：**前面八篇是"机制词典"，本篇是"症状索引"**。它把 §8.14 的七行表当目录，每行症状都配一个**本机可复现的信号读数**，再指到对应章节拿现成修复。

知识地图 §8.14 的原话是路线图：`症状 → 根因 → 修复`。本篇只干一件事——把右边这列"修复"换成**我们仓库里真跑出来过的实测条目**，让诊断不仅是"理论对得上"，而且是"数字看得见"。

## 1. 一页台账：§8.14 七行「症状→根因→修复」全本

先把知识地图 §8.14 的七行表搬到页首当索引（要素事实，即原文），这样后面每个实验都挂在这张表上：

| # | 症状 | 根因 | 修复（地图原文） | 修复站点（本仓对应章节） |
|---|---|---|---|---|
| ① | 答非所询查不到 | 检索召回差 | hybrid + rerank + 查询改写 | 03-混合检索与重排 / 05-查询侧技术 |
| ② | 答案与文档矛盾 | 忠实度差 | 上下文压缩、约束 only-from-evidence、减少噪声块 | 06-上下文压缩 |
| ③ | 专有名词查不到 | 分词/嵌入对专名不敏感 | 提高 BM25 权重、词典、别名扩展 | 03（BM25 权重）/ 05（词典/同义扩展） |
| ④ | 跨章节问题答不全 | chunk 太碎 | 父子块、结构化元数据、multi-hop | 04-分块与元数据 / 10-Agentic-RAG |

| ⑦ | 成本暴涨 | 检索+上下文过大 | 压缩、控制块数、缓存、路由 | 06（压缩）/ 08（缓存路由） |

这张表给出两个重要观察，也是本篇的骨架：

- **七行症状横跨四层**：①③是"查得对不对"（**检索层**）、④⑥是"存得碎不碎/新不新"（**索引层**）、⑤是"拼装时编号跟错了"（**编撰层**）、②⑦是"喂给模型的东西不干净/太多"（**生成层**）。**同名"RAG 问题"，不在同一层，修法完全不同。** 这就是为什么先要"定位"再"动手"。

## 2. 把诊断做成可复现信号（探针设计：信号 → 层 → 站点）

诊断手册的难点不是讲机制，是**给每个症状一个可复现的"度"**——不然"查不到"是个感觉，没法排查、没法回归。探针 `rag_diagnosis_demo.py` 复用与 05/06/10/11 完全相同的检索栈（`_demo_corpus.json` 100 篇中文百科，**第 i 条问题的答案就在第 i 条文档** + `BAAI/bge-small-zh-v1.5` + faiss `IndexFlatIP` + BM25），把 7 行症状逐一做成实验：

| 实验 | 信号（探针读数） | 对应症状 |
|---|---|---|
| A | 全语料 dense gold-rank 直方图 + 首屏 miss 名单 + dense∪bm25 混合救回率 | ① 查不到 |
| B | top-20 窗口：相关行/陪跑行、证据纯度、k=5/10/20 窗口字符成本线 | ② 矛盾（噪声账）+ ⑦ 成本 |
| C | 中文名提问 vs 语料里的英文缩写：BM25/Dense 命中 + 别名扩展救回 | ③ 专名 |
| D | 3 篇文档改 v2 但索引仍 v1：版本戳检测 vs 内容余弦"看着没问题" | ⑥ 答旧内容 |
| E | 检索后按显示顺序重编 [1..3] vs 编号跟随真实 doc_id：引用↔来源错位 | ⑤ 引用错误 |
| F | 跨章节粒度：挂靠 04 章父子分块 0.67→1.00（既有实测，本篇不重测） | ④ 跨章节 |

两个贯穿的设计口径：

- **信号必须落在"那一层"**：比如 ⑥"答旧内容"不测"模型答了什么"，而是测"**索引侧的版本戳 vs 内容侧的新旧**"——因为病根在索引层，信号就得到索引层抓。
- **读数直接变成修复站点指针**：每个实验收尾都写 `→ 修复: XX 章`，台账汇总把这些指针攒成一列（§9 一表流）。

确定性：单线程 BLAS + 固定种子，stdout 三遍逐位一致（md5 `72c4ed4d…`）；墙钟只进 stderr（模型加载 ~9s 占大头，总墙钟 ≈15s）。

## 3. 实验 A · 查不到 → 检索召回差：首屏 rank 诊断 + 混合修复

**症状 ①**：用户问"知识蒸馏是怎么做的"，检索回来的前十名里没有"知识蒸馏"。先别怪 embedding——先诊断：gold 文档到底排第几？

探针做**全语料 gold-rank 诊断**：对第 i 个问题，用 dense 检索 top-5，看它的答案文档 `doc[i]` 落进几号槽：

```text
Dense gold-rank 直方图（0=首屏命中）：0档98条 · 1档1条 · 3档1条
首屏查不到（rank>=1）count = 2 条
```

- **100 个问题 98 个答案在 top-1**，2 个掉出了首屏（rank 1 和 3）——这俩就是"查不到"的**候选名单**。
- 手册的读法不是"召回 98% 真好"，而是"**那 2 个是谁、为什么掉、掉在哪一层**"。

掉队的两条立刻做**混合修复**（dense∪bm25 合并 top-k）：

```text
期望 doc[21] 长短期记忆网络…  dense top5=含gold?Y · bm25 top5=含gold?Y → 混合 top9saved=Y
期望 doc[22] 知识蒸馏…          dense top5=含gold?Y · bm25 top5=含gold?Y → 混合 top7saved=Y
→ 混合救回 2/2 首屏 miss；救不回的走查询改写（05）
```

两个关键细节：

- **巧的是这两条各自单路都命中**，只是排在第 2/第 4 位没进 top-1；混合后把名次并进来，`doc[21]` 在 top-9、`doc[22]` 在 top-7——**legacy top-1 看"答案在不在",top-k 看"答案排第几"，前者更苛刻**。这本手册的信号口径全部取**首屏（top-1）**，因为真实问答截图里用户看得见的就是第一屏。
- 混合不是银弹：如果 gold 被排到 top-8 以外，加了 BM25 也只是并集变大、第 N 条未必进得去。**真救不回的，走 05 的查询改写**（同义扩展把 Hit@1 从 0.75 拉到 1.00，是 05 章的既有实测）。

> 修复站点：**① → 03-混合检索与重排**（min-max/RRF 融合正是"并集再排"）、**05-查询侧技术**（改写/同义词）。诊断动作=`gold-rank` 直方图，判据=`首屏 miss 数`。

## 4. 实验 B · 答不对 + 贵 = 噪声账 + 成本账（一体两账）

**症状 ②**和**⑦**放在一起，因为它们是同一枚硬币的两面：**检索条数决定"喂给模型多少噪声"（答不对）和"要付多少 token 钱"（贵）**。噪声账用三问实测，成本账用 k 刻度实测。

**噪声账**：对三条诊断问题取 dense top-20 窗口，数"相关行 vs 陪跑行"（相关=窗口行与查询有共词），算证据纯度 = 相关字符 / 窗口字符：

```text
q[ 0] 窗口 k=20： 1 行相关 · 19 行陪跑 · 证据纯度 0.065（41B相关/629B窗口）
q[22] 窗口 k=20： 4 行相关 · 16 行陪跑 · 证据纯度 0.200（125B相关/624B窗口）
q[55] 窗口 k=20： 4 行相关 · 16 行陪跑 · 证据纯度 0.207（129B相关/623B窗口）
```

读法：top-20 里一屏 **16~19 行是陪跑**，纯度只有 0.07~0.21。这就是"答案与文档矛盾"的直接来源——**生成模型看到的大半上下文跟答案没关系，凭什么指望它忠实**。6 章那个更狠的数字（`compress_demo.py` 实测）是：全量 614→宽松相关句 72.5，压缩率 **88.2%**——噪声主要就是检索 top-k 灌进去的。

**成本账**：窗口字符成本 = 每次查询喂给模型多少字。把 k 从 5 拉到 20，成本翻 4 倍：

```text
100 问平均窗口字符成本线：k=5→154.4 · k=10→307.9 · k=20→614.1 字符（控制块数=直接省钱）
06 章对照：每问 top-20 全量 ≈614 字符 → 宽松压缩 ≈72.5（-88.2%）
```

两个修复的落点都在这里：**控制 k**（154.4→614.1 是纯线性翻倍，每减一块直接省一块的钱）和**压缩**（06 的 88.2%）。这两条是"成本暴涨"的 80% 解——**在把缓存/路由（08）这种重武器搬出来之前，先问自己 k 是不是给太大了**。

> 修复站点：**②/⑦ → 06-上下文压缩**（减小噪声 + 压缩）；**⑦ → 08-向量数据库选型**（缓存/路由，§8.9 运维面）。诊断动作=`证据纯度` 与 `k 成本线`，判据=纯度 < 0.3 说明噪声账超标、k=20→614 是贵的主导项。

## 5. 实验 C · 专有名词查不到：词面断裂的三种形态 + 别名扩展

**症状 ③**：用户问"第五代移动通信"，文档里写的是"5G 网络"——**字面上一个 token 都对不上**。这不是 embedding 坏了，是**词面断裂**：中文名提问 vs 语料里的英文缩写，BM25 的共享词为 0，dense 靠语义勉强搭桥（本语料里全 HIT，但这是语料限制，见 §10）。

探针构造 3 个"中文全称/别名 提问 × 语料存缩写"的错位对，跑 BM25（词面严格）和 Dense（语义宽松）两条路 + 别名扩展：

```text
目标[59] 5G网络…  别名=5G   BM25 miss→doc1 →HIT · Dense HIT→HIT
目标[96] 提示注入… 别名=LLM  BM25 miss→doc34 →HIT · Dense HIT→HIT
目标[ 4] 图灵测试… 别名=图灵 BM25 miss→doc44 →HIT · Dense HIT→HIT
```

- **BM25 词面断裂 3/3 miss**：`"第五代移动通信"` 打进 `BM25.get_scores(cut(q))`，与 `doc[59]` 的 token 零重叠，分数排不上 top-1（错落进 doc1/34/44）。
- **别名扩展 3/3 救回**：查询后拼上别名 token（`"第五代移动通信 5G"`），`5G` 与 `doc[59]` 强重合，BM25 首屏回到 target。**别名扩展 = 往查询里塞一个词，代价是一个 token，赚回一个首屏命中。**
- **Dense 语义搭桥 3/3 HIT**：bge 把"第五代移动通信"和"5G 网络"都嵌到"通信标准"附近，词面断了但嵌入没断、首屏已命中。所以**专名问题在混合检索下其实最容易被 Dense 那一腿兜住**，真正的风险是 pure-BM25 场景（或 DB 里只有 ES 词法索引）。

诊断动作很便宜：**对 top-1 检索失败 + 已知语料里有别名的 query，先做一次"词面重叠检查"**——`cut(q) ∩ cut(doc[j])` 是不是空集。空了，就是词面断裂，直接上别名/同义扩展（05 章实测把 BM25 Hit@1 0.75→1.00）。

> 修复站点：**③ → 词典/别名扩展 + 调 BM25 权重**（03 章可调 b/k1 权重、05 章同义扩展）；Dense 那腿在 01 章（选择对专名更敏感的 embedding 或词典路由）。

## 6. 实验 D · 更新后仍答旧内容：版本戳 vs 内容比对

**症状 ⑥**：知识库凌晨更新了，用户的检索还是把旧版 doc 捞回来、模型还在答旧内容。**层级归因**：不是模型笨，是**索引没增量**——文档改了，向量库里还躺着旧向量。

探针演一遍"3 篇文档已改 v2、索引仍 v1"的现场，给两种检测法：

```text
3 篇已改（doc 3 8 21 → v2），索引仍是 v1
版本戳诊断：陈旧篇数 = 3（doc3,doc8,doc21）——干净、可靠、每条都能标
  doc[ 3] 内容余弦(旧vs新) = 0.9759 ← 内容层看着像同一条 → 必须靠版本戳
  doc[ 8] 内容余弦(旧vs新) = 0.9528 ← 内容层看着像同一条 → 必须靠版本戳
  doc[21] 内容余弦(旧vs新) = 0.9519 ← 内容层看着像同一条 → 必须靠版本戳
增量重索引（更新 v1→v2）后陈旧篇数 = 0
```

核心发现是**"内容比对"这道防线本身就不可靠**：旧版加一句"本章已更新至第五章 v2"再重嵌入，新旧向量的内容余弦高达 **0.95+**——**内容层看着像同一条**，用"向量差异"判断会漏判。而**版本戳（元数据 `version` 字段）是逐条显式标记**：`version[d] != cur[d]` 就是陈旧，3 条一次性全标出来，增量重索引（把索引侧 version 更新到 v2）后归零。

这就是 §8.14 说"增量更新+TTL、缓存失效"的原因——**判断"旧不旧"必须是可信信号，不能靠比对内容的隐性信号**。生产里的版本戳就是文档元数据（mtime / 内容哈希 / 业务版本号），TTL 是兜底保险丝。

> 修复站点：**⑥ → 增量更新 + TTL / 缓存失效（08-向量数据库选型的运维面）**。诊断动作=`版本戳 陈旧计数`，判据=陈旧 > 0 就是索引没跟上前端；`内容余弦`作反面教材（0.95+ 照样看不出，别用它判新旧）。

## 7. 实验 E · 引用来源错误：编号跟谁走

**症状 ⑤**：模型说"根据[1][2]可知"，可点开 [1] 不是你引用的那篇。**层级归因**：多数时候不是模型编造，是**元数据/编号错位**——检索完按显示顺序重编了 [1..3]，编号和你真实引用的 doc_id 脱钩了。

探针模拟 3 个问答的拼装现场：dense 检索 top-3，编撰层"按文档长度从长到短"重排，然后两个方案给引用编号：

```text
目标[ 4] 检索top3=doc4,0,2 · 按长度重排=[2,0,4]
  naive 按显示序编号 → 引用[1]=doc2 ≠ 来源 doc4  错位=Y
  管线化 编号跟随 doc_id   → 来源在槽 1 引用对齐=Y
目标[22] 检索top3=doc97,22,34 · 按长度重排=[34,22,97]
  naive 按显示序编号 → 引用[1]=doc34 ≠ 来源 doc22  错位=Y
  管线化 编号跟随 doc_id   → 来源在槽 2 引用对齐=Y
目标[30] 检索top3=doc30,33,26 · 按长度重排=[30,33,26]
  naive 按显示序编号 → 引用[1]=doc30 ≠ 来源 doc30  错位=N
  管线化 编号跟随 doc_id   → 来源在槽 1 引用对齐=Y
→ naive 编号 3 问错位 2/3；引用管线化 3/3 对齐（来源槽位 = 真实 doc_id 槽位）
```

- **naive（按显示顺序重编）错位 2/3**：doc[4] 被重排到槽 3，但"引用[1]"却标给了槽 1 的 doc[2]；doc[22] 同理标给了 doc[34]。**编号跟着"显示顺序"走，来源跟着"原始 doc"走，两者一脱钩就是错位**。
- **管线化（编号跟随真实 doc_id）3/3 对齐**：先从真实 top-3 里找到 target 的**原始槽位**（doc[4]→槽 1、doc[22]→槽 2、doc[30]→槽 1），编号就引用那个原始槽位的文档。**引用编号在管线里"出生"时就绑定了 doc_id，而不是拼装完再重编**——这是"引用管线化"四个字的具象。

> 修复站点：**⑤ → 引用管线化 + Post-hoc 引用校验**（04-分块与元数据管的元数据质量是前提）。诊断动作=`引用槽位 vs 真实 doc_id 槽位 是否一致`，判据=3 问错位 2/3 vs 0/3。真管线里再加一道 Post-hoc 校验：生成出的 [i] 往回查一下它指的 doc 是不是检索结果里的真实条目。

## 8. 实验 F · 跨章节答不全：粒度观（挂靠 04 章，不重测）

**症状 ④**：问题横跨两章（比如"知识蒸馏在长短期记忆网络里怎么用"），单块召回抓不住另一半。**根因是 chunk 太碎**——答案横跨多个块，检索只捞回一块。修复是**粒度**问题，不是召回问题。

本探针不给 ④ 新造实验，**诚实挂靠 04 章的既有实测**（`011-父子分块与元数据过滤.ipynb`）：

- 整篇作 chunk（粗粒度）：答案散在多段，检索召回失败比 **0.67**（3 问只答上 2 问）。
- 子块建索引 + 父块回填（父子分块）：子块小到能命中问题所在段，命中后**回填父块**（放大 **3.14×** 上下文），补答 4/4 → **1.00**。
- 另一条腿在 10 章：Agentic RAG 实测多跳 naive 2/4 → agentic 采信 **4/4**（平均 1.5 轮）。

为什么本篇不重测：04 章已经把"粒度差"焊在数字上了（0.67→1.00），10 章把"多跳"也焊上了（2/4→4/4）。**本手册的职责是"症状→触点"翻译，不是再造一遍数字**——再测一遍同一批语料只是浪费墙钟。这句"诚实挂靠"本身就是手册的立场（§10）。

> 修复站点：**④ → 04-父子分块 / 结构化元数据 / 10-多跳**。诊断动作=看问题是否横跨多段（子问题拆分），判据=跨章节问题在单块召回下的遗留数。

## 9. 收束方法论：症状 → 触点 → 站点，一表流

六个实验做完，回到一页台账。探针把 7 行症状的**本机信号读数**和**修复站点指针**收进一张汇总——这就是手册的"成一册"：

```text
台账汇总  §8.14 七行「症状→根因→修复」· 信号=本机读数 · 修复=站点指针
  ①答非所询查不到  · 信号: 首屏 rank>=1 2/100（混合救回 2，A） → 修复: 03 混合重排 / 05 查询改写
  ②答案与文档矛盾  · 信号: top-20 陪跑行（B: 证据纯度 0.06~0.21 档·陪跑 16~19/20 行） → 修复: 06 压缩 + only-from-evidence
  ③专有名词查不到  · 信号: BM25 词面断裂 3/3 miss（C: 别名扩展 3/3 救回·本语料 Dense 语义搭桥全 HIT） → 修复: 词典/别名扩展 + 调 BM25 权重
  ④跨章节问题答不全· 信号: 单块召回不足 1.0（04 章父子实测 0.67→1.00） → 修复: 04 父子分块 / 10 多跳
  ⑤引用来源错误    · 信号: 引用↔来源错位（E: naive 2/3 vs 管线化 0/3） → 修复: 引用管线化 + Post-hoc 校验
  ⑥更新后仍答旧内容· 信号: 版本戳陈旧 3 条（D: 内容余弦 0.95+ 看不出来） → 修复: 增量更新 + TTL / 08 运维
  ⑦成本暴涨        · 信号: 窗口字符成本（B: k=20→614 字符/问） → 修复: 06 压缩 + 控制块数 + 08 缓存路由
```

排故障时按这个顺序走：

1. **症状→信号**：用户抱怨落到一张七行台账（答非所询→①、答旧内容→⑥…）；每行给一个"怎么测出来"的信号（gold-rank / 证据纯度 / 版本戳 / 槽位错位…）。
2. **信号→层**：信号在哪一层被抓就定位到那一层——**检索层 ①②③ / 索引层 ④和⑥ / 编撰层 ⑤ / 生成层 ②⑦**。层定了，搜索范围就缩到一个章节内。
3. **层→站点**：→ 修复列里的站点指针，回对应章节拿现成修复（全是既有实测）。

> 🧩 **三选一判断力**（本篇想留给你的）：先测信号再换方案——"答不对"先看**证据纯度**（低了是噪声多了，不是模型笨）；"查不到"先看 **gold-rank** 首屏 miss 数（是召回问题就去改检索，别去改 prompt）；"答旧内容"先看**版本戳**（陈旧>0 是索引没跟上，不是模型幻觉）。**大多数 RAG 问题不是模型问题，是信号没先在那一层被抓到。**

## 10. 诚实边界（AAA 自我审查）

每篇都有边界，本篇尤其要交底——因为它干的是"把信号读出话"的活：

1. **专名语料小样本（3 对）**：实验 C 只有 3 组错位对，结论是"机制演示 + 语料内观察"，不是"专名召回率统计"。特别是 **Dense 语义搭桥 3/3 HIT 是本语料的观察，不是普适保证**——bge 对这 3 组错位恰好能搭桥；换更冷门的专名、更白的 embedding，Dense 也会断。诚实表述=**"BM25 词面断裂 3/3 miss、别名扩展 3/3 救回；本语料 Dense 全 HIT（勿夸大普适）"**。
2. **版本戳是元数据信号，不是内容判断**：实验 D 的版本戳 = 我们自己按 `version` 字段比对（干净、确定）；**真实生产里"文档改了没"本身就难**（mtime / 哈希 / 业务版本号各有漏判），TTL 是保险丝不是银弹。实验只证明"一处比对靠版本戳 vs 一坨内容比对靠余弦"的机制，不证明哪套生产方案最优。
3. **实验 E 是"编号错位"的模拟，不是真实 Post-hoc 校验管线**：我们演示"编号跟随真实 doc_id"能把错位归零，但**没有在本机跑真实 LLM 的引用生成 + Post-hoc 校验**（那需要模型接入，超本探针零下载范围）。"引用管线化"是管线设计原则，"Post-hoc 校验"是配套建议，均为作者经验陈述。
4. **实验 F 是挂靠，不是本机重测**：0.67→1.00 与 3.14× 全部来自 04 章既有实测（`011` notebook），10 章的 2/4→4/4 同理；本篇没有在 100 篇语料上再跑跨章节新实验。诚实声明=**挂靠站点的数字权威在 04/10 章节**。
5. **信号口径都取首屏 / top-1**：实验 A 的"miss 2 条"是 top-1 语义下的掉队；top-5 语义下这 2 条都命中（直方图 rank<=3）。读数字时注意口径，别拿 top-1 的 miss 数说"召回坏了大半"。
6. **墙钟浮动只进 stderr**：实验耗时（encode+index ≈9s、总 ≈15s 量级）在 run 间有浮动，stdout（信号读数）才是确定性部分。

## 11. 常见坑（5 条）

探针自身踩过的、以及读者复现时最容易踩的，五条：

1. **拿 top-1 当唯一标准**：`s_bm25(q, 1)[0]` 返回的是**列表** `[docid]`，不是整数。写 `if ded == tgt` 永远 False → 全是"miss"。**取单条结果一定要 `[0]` 取号**（探针实验 C 踩过的坑：`list == int` 恒 False）。
2. **专名断裂查询选太"善"**：先用中文名问"分词/算法/词表"这种词，BM25 naive 早就命中了（共词非空），根本测不出断裂。**真正的断裂要求查询 token 与目标文档 token 零重叠**（"第五代移动通信" vs "5G网络"）——先做一次 `cut(q) ∩ cut(doc)` 验证再当案例。
3. **混着读 Dense 的语义搭桥**：专名问题在 Dense 那腿经常被兜住（本语料 3/3 HIT），于是有人得出"专名不是问题"。**只在 pure-BM25 / 词法型后端上它才是问题**——结论要带后端语境。
4. **台账行写"感觉"不写读数**：⑦ 的"成本暴涨"不写 `k=20→614.1 字符/问` 就是空话；① 不写 `2/100 → 混合救回 2/2` 就无从回归。**每行修复列都配一个首次诊断能复现的读数**。
5. **诊断先于动手术**：症状 ① 先做 gold-rank（几行代码），别一上来就换 embedding / 换 reranker。**信号定位到层之前，任何"修复"都是在猜**。
