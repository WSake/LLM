## 0. 为什么大家都在调模型，忽略了分块

RAG 的一切收益都来自这样一条链路：

```
文档 → 分块(chunks) → Embedding → 索引 → 检索 → 生成的证据
            ↑       ↑
       你的内容粒度 = 你的命中粒度
```

**检索器拿到的是"块"，不是"文档"**。如果一块里混了两个主题，它找到这块也说不清你要的是哪半截；如果用 2000 字大块检索，top-5 塞进去的是 1 万字，Prompt 又装不下。所以：

> **分块是最便宜的检索"提效阀"**——不换模型、不建新索引，只是把"怎么切"设计好，Hit@k 和最终回答质量都可能上一个台阶。反过来说，模型调得再溜，切得稀碎的内容也救不回来。

---

## 1. 分块的目标三角：语义自包含 · 不丢信息 · 长度适中

分块没有唯一正确答案，但有三个互相拉扯的目标：

```
①  语义自包含   —— 每块自己要说清一件事（一块 = 一个可独立回答的"知识单元"）
②  不丢信息     —— 上下文被切散后，前面的指代、定义、结论不能被切没
③  长度适中     —— 块太短则检索信号稀薄，块太长则噪声进入 Prompt、成本上升
```

**没有万能 chunk 大小，跟着内容结构走**：法律条款可以按"条"切，代码按"函数"切，Markdown 按"章节"切，对话记录按"轮次"切。**先从内容的天然结构出发，再用长度作兜底。**

## 2. 六种分块方法（选型表）

| 方法 | 怎么切 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| 1. 固定长度 | 每 N 字符/词一刀 | 最简单、耗时固定 | **结构被锯断**（表格行、代码、标题） | 快速原型、无结构的纯文本 |
| 2. 递归字符 | 按分隔符优先级（`\n\n > \n > 句子 > 单词`）依次折叠 | 尊重行/段结构、实现快 | 不理解语义；遇超长段落仍会硬切 | **通用默认**（LangChain `RecursiveCharacterTextSplitter` 即此） |
| 3. 结构感知 | 按 Markdown 标题 / HTML 标签 / PDF 大纲切 | 块天然带章节上下文 | 需要结构化源 | 有道礼仪结构的文档 |
| 4. 语义切分 | 用 embedding 检测"相邻句子语义突变"当切口 | 块内语义更纯 | 多一次编码、慢 | 语义漂移明显的长文档 |
| 5. 父子块 | 小块做检索（准），父块做喂入（全） | 兼顾"准"与"上下文完整" | 存储双份、查询多跳 | **生产主流**（§8.9 Advanced 模式） |
| 6. LLM / 版面解析 | 用 LLM/OCR 把 PDF 抽成结构化 JSON | 语义单元最干净 | 慢、贵 | 企业知识库（PDF 报表、多栏版式） |

> 趋势：**先用 LLM/文档理解模型做结构化抽取（把 PDF 变 JSON），再按结构分块**，远胜无条件切字符。工具链：MinerU、Docling、Unstructured、Qwen2.5-VL 版面理解。

## 3. 实测：哪一刀切得准（拿本仓库的知识地图开刀）

为了不虚空写理论，本章直接拿仓库里最大的一篇中文文档开刀——`00-知识地图/大模型知识地图_完整版.md`，**93,188 字符、1,978 行、323 条标题**，用两种策略各切一遍：

```
源文档               : 93,188 字符 / 1,978 行 / 323 条标题

固定 512 字符硬切     : 183 块；切分线落在"行中间" 174 处
                        ｜ 表格行、代码块、标题行都可能被拦腰锯断
换行递归分块（512 上限）: 392 块；中位块长 246 字符（≈ 160~250 token，中文）
                        ｜ 在"段间有空行"的常规文档上，切线贴着行边界走
```

**最有意思的发现**是最后这点：知识地图这类**超高密度文档（几乎不空行）**，会让"换行递归分块"也无处可切——没有空行就没有天然的停靠点，最终只能在长度上限处**强制硬切**，退化回和固定切几乎一样的结果（实测 377 处中行切）。

**这说明一个常被忽略的工程动作**：

> 分块质量的上限，在**源文档的规范性**里。给知识库建个"预处理脚"（结构化 + 补空行 + 归一换行），比研究任何花哨分块算法都先见效。

**怎么换算 token**：中文一般 1~1.5 字 ≈ 1 token。块长 246 字符 ≈ 150~250 token，配合 `top-5 × 500 token` 的 Prompt 预算正好。

> 想复现：仓库根 `python -c "exec(open('code/notebooks/_tools/chunk_demo.py',encoding='utf-8').read())"`（见第 5 节）。

## 4. 元数据：索引的「地址簿」

分块之后，每一块都该带上**元数据**——它就是索引的地址簿：

```python
chunk = {
    "text": "…块文本…",
    "meta": {
        "source":   "大模型知识地图_完整版.md",
        "section":  "8.3 检索技术基础",
        "page":     12,            # 原文档页码（可溯源引用）
        "updated_at": "2026-09-20", # 增量更新/TTL
        "tenant_id": "team_a",     # 多租户隔离
        "doc_type":  "md",
    }
}
```

**没有元数据的 RAG 无法给引用**：答案要带出处（来源文件/章节/页码），全靠检索时把 meta 一并吐出来。元数据的三个实际用途：

1. **过滤（Filter）**：查询时先按 `sec 部门 / 更新时间 / 文档类型` 过滤再检索——比语法检索快且准；
2. **溯源（Citation）**：`[3] 来源：08-RAG体系/03-混合检索与重排.md · 8.3 节` 面板直接可用；
3. **多租户隔离（Tenancy）**：`tenant_id` 过滤是安全底线，忘了就是串数据事故。

## 5. 怎么跑：20 行分块脚本

一个零依赖的换行递归分块器（和 LangChain `RecursiveCharacterTextSplitter` 同思路），可以把任意 Markdown/正文按行+长度切块：

```python
# tools 示例：换行递归分块（尊重行边界，超出毁灭折成硬切）
def split_md(text, limit=512):
    lines, chunks, cur = text.split("\n"), [], ""
    for line in lines:
        if len(cur) + len(line) + 1 > limit and cur.strip():
            chunks.append(cur); cur = line          # 行边界天然停靠点
        elif not line.strip() and cur.strip():
            chunks.append(cur); cur = ""             # 空行 = 段落边界
        else:
            cur = (cur + "\n" if cur else "") + line
        if len(cur) >= limit * 3:                     # 兜底：超长段硬切
            for i in range(0, len(cur), limit):
                chunks.append(cur[i:i+limit])
            cur = ""
    if cur.strip():
        chunks.append(cur)
    return chunks
```

把 009 的 `CORPUS` 换成你自己的文档集 + 这个分块器，就是最快的"我的第一个 RAG"。**父子块**则在此之上加两行：小块检索、命中后取父块喂入。

## 6. 评测/验证：分块与元数据的账

分块改动和检索算法改动一样，必须走同一套评测（参考 01/03 章的评测集方法）：

```
同一份 100 条评测集，三行对比：
                       Hit@5    MRR@10    引用命中率
固定 512 硬切
换行递归分块
父子块 + 元数据过滤
```

**看数字时注意**：
- `Hit@5` 提升 → 分块粒度真的和问题粒度对上了；
- `MRR` 提升但 Hit 没动 → 只是排位变好，说明块本身没错，是"切得太碎/太糊"影响排序；
- **引用命中率**（答案出处的 meta 是否和 gold 一致）→ 这是元数据的专属指标，检索再准、meta 挂错也白搭。

选型建议：**第 1 次迭代先上"换行递归 + 结构感知（Markdown 标题优先）"**，能覆盖 80% 场景；schema 复杂/PDF 居多的知识库一步到位上父子块 + 版面解析。

## 7. 常见坑（5 条）

1. **不看源文档结构直接硬切**：PDF 表格被从行中锯断、代码 fence 被一分为二——先看你的文档长什么样，再选切法。
2. **块长得离谱**（> 1500 token）：top-5 直接爆 Prompt 预算，生成质量崩塌。**设块长上限 + top-k 预算联动**。
3. **块长得太短**（< 50 token）：语义信号太稀，检索变成碰运气。
4. **Meta 没挂或挂错**：引用无出处、过滤失效、租户数据串。**定义 meta 结构 + 在评测里加"引用命中率"指标**。
5. **源文档不规范就追求算法**：连空行都没有、标题乱起名的文档，任何分块器都在打胶拳。**先跑一次"预处理规范化"，再谈切法。**
