## 0. 为什么：RAG 的进阶不是「更多组件」

基线 RAG（检索 → 拼上下文 → 生成）在 Demo 上都能跑，一上生产就漏出四种「坏」：

| 症状 | 病根 | 对应模式 |
|---|---|---|
| 找到的文档不对/不精 | 单一检索器、无重排 | ②Hybrid+RRF、③Rerank |
| 答得空、没有证据密度 | 上下文一大坨，相关的那句淹了 | ①父子分块、⑤查询侧 |
| 混进旁类噪音被带偏 | 主题/部门/时间不隔离 | ④元数据过滤、⑦多租户 |
| 数据变了检索结果还是旧的 | 索引静止不动 | ⑥增量更新 |

地图 §8.9 给了 7 个模式：**Parent-Child、Auto-merging、Hybrid+RRF、Rerank 必配、Metadata 过滤、增量更新与删除、多租户隔离（tenant_id）**。本章逐个给「是什么 / 解决什么 / 代价」，并把前四个**在已有实测数字的地方直接挂靠**（01→05→07→010/011），证明它们是「测过的」，不是「教程里说的」。

## 1. 七模式总览：是什么 / 解决什么 / 代价

| # | 模式 | 是什么 | 解决什么 | 代价 | 本仓库实测锚点 |
|---|---|---|---|---|---|
| ① | **Parent-Child / Auto-merging** | 小块建索引、大块喂上下文 | 检索粒度 vs 上下文完整性 | 双索引存储、回填逻辑 | 011：整篇 top-1 0.67 → 子块 1.00，回填 3.14× |

| ③ | **Rerank 必配** | 候选 top-N 再过一遍交叉编码/列表选择 | 向量相似 ≠ 相关 | Rerank 模型推理成本 | 03：bge-reranker / ColBERT 定位 |
| ④ | **Metadata 过滤** | 时间/部门/分类/tenant_id 硬过滤 | 噪音、权限、时效 | 索引打标、Filter 逻辑 | 011：纯度 0.57 → 1.00；04：元数据是索引的地址簿 |
| ⑤ | **查询侧增强** | Rewrite / Expansion / Decompose | 用户话 ≠ 文档话 | LLM 调用 / 多余 token | 05：扩展救 BM25 Hit@1 0.75→1.00 |
| ⑥ | **增量更新与删除** | doc 变更 → 增量 upsert / delete | 数据漂移、隐私合规 | 版本管理、级联删除 | 待产线数据（模式是工程项） |
| ⑦ | **多租户隔离** | tenant_id 进索引 + 强制过滤 | 跨租户数据串味 | 权限模型、索引爆炸 | 生产要求；用 ④ 的机制实现 |

## 2. 模式①：父子分块 + Auto-merging（已实测）

**是什么**：语料建两级块——**子块**（句/段级）进索引，**父块**（篇级）做回填上下文。查询检索「子块」（找得准），生成时用「父块」（喂得足）。

**为什么有效（本仓库 011 实测）**：把 90 条语料每 3 条合 1 章，同一套 bge：

- 整篇 top-1 命中「所在章」**16/24（0.67）**——大块 embedding 被平均化，具体问题检索飘
- 子块 top-1 命中「gold 子块」**24/24（1.00）**
- 子块命中后回填父块：gold 依然在上下文里 **24/24**，上下文放大 **3.14×**

读数：**索引粒度决定检索精度，回填粒度决定上下文充足度**。Auto-merging（LlamaIndex 实现）就是把这套做成「可折叠块」——大块命中自动展开成小块，避免一次性全塞。

**代价**：双索引（存储 × 1.3 上下）；回填逻辑要跟 Rerank 配合——回填的是整章，得在生成前再筛一遍，否则「喂得足」变「喂得杂」。

> 动手：`code/notebooks/011-父子分块与元数据过滤.ipynb`，全部数字可复现。

## 3. 模式②：Hybrid + RRF（已实测）

**是什么**：BM25 管「准词」，Dense 管「换词」，用 **RRF（倒数排名融合）**把两路排名合起来；min-max 归一化是另一条路。

**为什么有效**：检索有互补性——BM25 对「文中有原词」的问题稳，Dense 对「同义改写」的问题稳。本仓库 [03-混合检索与重排](03-混合检索与重排.md) 实测过两路 top-5 **重合率仅 0.40**（60% 的结果是互补的），融合后 Hit@5 顶格 1.0000。

**代价**：双路延迟叠加（可分主从）；min-max vs RRF 的相差不大，别再花时间纠结权重——**先固定一个、拿评测台看整链指标**。

> 三线并进见 [009-中文RAG全管线.ipynb](../code/notebooks/009-中文RAG全管线.ipynb)；融合细节看 [03-混合检索与重排](03-混合检索与重排.md) 第 3 节。

## 4. 模式③：Rerank 必配（已实测）

**是什么**：向量检索先给 top-20~100 候选，**Reranker**（bge-reranker / CoBERT 式 late-interaction）再算「查询-文档」相关度，取 top-5~10。

**为什么**：向量相似度靠余弦近似，「近似」意味着 top-1 不是正确答案时，它往往在 top-5 里；Rerank 是把 top-3 里藏着的真答案「提上来」。实测锚点：[03-混合检索与重排](03-混合检索与重排.md) 的判别性对照演示了**检索 Hit 高≠答案对**（[010-RAGAS评测](../code/notebooks/010-RAGAS评测一个RAG系统.ipynb) 里 Faithfulness 1.00→0.17 才是答案层真相）。

**代价**：交叉编码 Rerank 是 O(候选数 × 文档长) 的注意力，别对全库跑，只对候选跑；筛选「候选数」是延迟 × 质量的平衡点。

## 5. 模式④：元数据过滤（已实测）

**是什么**：每个块挂元数据（分类 / 时间 / 部门 / 租户），检索时按 `index.filter` 硬过滤，**检索结果只来自符合条件的块**。

**为什么有效（011 实测，6 个主题题）**：no-filter 的 top-5 里混进旁类（平均主题纯度 **0.57**），同名过滤后纯度 **1.00**，gold 依然命中 6/6。

**关键认知**：元数据过滤**保精度、不涨召回**——把噪声挡在外面，但不会找回它过滤掉的东西。所以它是「正确性的低保」，不是「效果的特效」。文档属谁、什么时间、什么分类，在建索引那一刻就写死（[04-分块与元数据](04-分块与元数据.md) 讲透了「索引的地址簿」）。

## 6. 模式⑤⑥⑦：增量更新 / 多租户隔离 / 查询侧增强

- **⑥ 增量更新与删除**：文档变动 → upsert（覆盖向量）与 delete（删向量 + 元数据 + 级联子块）。这一步没有「做不做」：语料一漂，检索结果就是旧世界的。机制上向量库都原生支持，难在**版本号与回滚**。
- **⑦ 多租户隔离**：`tenant_id` 进每个块的元数据，检索强制 filter。机制就是 ④；难在权限设计与「默认可视性」的默认值。至少 `CROSS_TENANT_LEAK` 要建成评测用例。
- **⑤ 查询侧增强**：Rewrite（口语→书面）、扩展（补同义实体词）、分解（复合问题拆两跳）。这是「进阶第一刀」——[05-查询侧技术](05-查询侧技术.md) 实测：扩展把 BM25 的 Hit@1 从 **0.75 救到 1.00**，而多跳问题 naive 首屏只有 2/4。但**顶格语料上全是零收益**，先测张力再上。

> 这三个没有新的「魔法」，前两个是工程纪律，第三个是「先探张力」的检索法。

## 7. 落地顺序：三层优先级 + 一张诊断表

**别七剑下天山**。地图说「掌握 3-5 个」，生产上建议按这个顺序上：

| 层 | 模式 | 理由 |
|---|---|---|
| **L1 必做** | ②Hybrid+RRF、③Rerank、①父子分块 | 一辈子都该有：补召回、提精度、防粒度漂 |
| **L2 需求驱动** | ④元数据过滤、⑤查询侧增强 | 有噪音/权限再来；查询侧先探张力 |
| **L3 看体量** | ⑥增量更新、⑦多租户 | 数据漂/多客户才需要工程投入 |

**诊断表（坏在哪 → 上哪把刀）**：

| 症状 | 先看 | 后上 |
|---|---|---|
| 找到的文档不对 | 跑 [010 评测](../code/notebooks/010-RAGAS评测一个RAG系统.ipynb) 看检索层 | ③Rerank、②Hybrid |
| 找到了但答得空 | 看 [010](../code/notebooks/010-RAGAS评测一个RAG系统.ipynb) 的生成层（Faithfulness） | ①父子回填、Rerank 提序 |
| 总是答出旁类观点 | 翻检索 top-5 来源 | ④元数据过滤 |
| 口语/问题含糊 | 看 Hit@1（首屏做的对吗） | ⑤查询侧（先探张力） |
| 要跨全局总结/实体关系 | 语义检索不擅长 | 转 §8.10 Agentic / §8.11 GraphRAG（见后续章节） |

## 8. 评测：怎么证明「Advanced」真的 advanced

地图 §8.9 的清单如果不用评测台验证，就是「装」，[07-RAG评测-RAGAS](07-RAG评测-RAGAS.md) 讲了标准动作：

1. **先有基线**（[009](../code/notebooks/009-中文RAG全管线.ipynb) 或 [010](../code/notebooks/010-RAGAS评测一个RAG系统.ipynb) 默认管线）——三层指标：检索层 Hit@k/MRR、生成层 Faithfulness/Relevance。
2. **加一个模式，重测，同度量**。判别性对照（1.00/0.74→0.17/0.40）是评测台「有耳朵」的质检。
3. **只报「变好了多少」的差**：每个模式的代价（延迟/存储/token）同步上表，决策才成立。

> 把「Advanced 模式 + 评测差 + 代价」三个数字放进 PR 描述——这是仓库里每一篇、每个 notebook 的执念：**能跑、带数字**。
