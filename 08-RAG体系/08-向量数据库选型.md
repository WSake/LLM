## 0. 为什么"选库"值得单开一篇？

[01-Embedding与检索基础](01-Embedding与检索基础.md) 已经把 ANN 索引的**内部**讲透了：HNSW 是"跳表化的近邻图"、IVF 是"先聚类再分区扫"、PQ 是"向量拆子向量量化存码"。那都是"索引怎么建"。可当你打开 Milvus / Qdrant / Chroma / pgvector 的部署文档时，不会看到有人在叫你手写 HNSW——**你会看到分片、副本、过滤、事务、备份、监控、多租户隔离**。

这就是本篇的分工：**索引内部是"索引层"，选库是"工程外壳层"**。01 章解决"怎么建索引"，本篇解决"同一个检索需求，装进哪只壳"。

一个反直觉的事实先立起来（本篇 A0 实测，§3）：在 100 篇的小库上，Exact / IVF / HNSW **三种索引的检索质量一模一样**（都是 Hit@1=98/100）。换句话说——**召回根本不是库与库的分水岭**：近似索引的差距要等到几十万上百万条才现形，而且拉到足够旋钮都能逼近精确。你选 Milvus 不选 FAISS，**不是因为 Milvus 召回更高，而是因为它的工程面（云原生分片、副本、多租户过滤、HA）给你的运维省心**。这一条正是 §8.8 "选型关键" 的脚注：别为了"向量库"而引入重型组件，先想清楚场景再掏钱。

> 一句定位：**01 章在"索引怎么建"，03 章在"怎么混合召回"，04 章在"怎么分块挂元数据"，本篇在"整条检索管线的存储层装进哪只壳"——它服务的是索引端的长期运维，不是单次查询的召回。**

## 1. 机制拆解：索引层小三角 + 工程层大三角

把任意一个向量库拆开，都是三层堆起来的（要素事实），而选型时你其实在做**两个不同三角形的权衡**：

```text
┌─────────────────────────── 工程外壳（库这一层）───────────────────────────┐
│  服务层：过滤 / 分片 / 副本 · 事务 / 备份 / 多租户 / 增量删除 · 运维监控        │
│           ↑ 这是「选库」的战场 —— 决定 Milvus vs Qdrant vs pgvector          │
├─────────────────────────── 索引层（机械，01 章讲内部）───────────────────────┤
│  Exact(flat) / IVF / HNSW / IVFPQ 四种机械 × 旋钮（nprobe / efSearch）       │
│           ↑ 这是「召回-延迟-成本」小三角的战场                                │
├─────────────────────────── 存储层 ──────────────────────────────────────────┤
│  向量本体 + 元数据（过滤字段）→ 落到磁盘/内存                                 │
└─────────────────────────────────────────────────────────────────────────────┘
```

- **索引层小三角（召回-延迟-成本）**：本例 A1/A2 本机真跑（§3）。HNSW 摆出"召回≈精确 + 体积 ~2×"、IVFPQ 摆出"体积 1/12 + 召回让位"、Exact 摆出"召回满格 + 体积原样"——**同一批数据，怎么扫、扫多少，换来多少召回与多少钱**。
- **工程层大三角（规模-运维-功能）**：同一份检索需求，单机 10 万条用 FAISS 够了；100 万条 24×7 生产、多租户过滤要 Qdrant/ES；已有 PG 业务库要事务一致选 pgvector；极热路径怕延迟选 Redis Stack。**这一层才是"先定场景"四个字的落点。**

§8.8 把九家放进了同一张表（要素事实，非本机实测）：系统类型（库 / 分布式向量库 / PG 扩展 / 全文+向量双引擎 / 内存 KV / 嵌入式）× 适合场景（原型单机 → 中规模生产 → 大规模生产 → 极热 / 边缘）。选型钥匙就两句——**检索要混合**（词法+向量+重排，03 章）、**别为"向量库"引入重型组件**（§8.8 原话）。

下文先实测索引层（实验 A/B），把"工程面才是分水岭"这句话焊在本机数字上，再用决策引擎把"先定场景再选库"做成 9 条断言（实验 B）。

## 2. 把同层比较做成本机实测

探针 `vector_db_demo.py` 复用与 05/06/10/11 完全相同的检索栈（`_demo_corpus.json` 100 篇 + `BAAI/bge-small-zh-v1.5` + faiss），并在同脚本里再建一个 **20k×64d 的确定性合成集**（`RandomState(2026)`）把近似索引的差距"放大到现形"。两套数据一句话分工：

- **100 篇真实语料** —— 回答 A0：小库上三种索引召回一模一样（近似层在小库不是分水岭）。
- **20k 合成集** —— 回答 A1/A2：把旋钮拉开的召回曲线 + 每索引写盘字节账（这才是索引层三角的真身）。

口径先行（诚实声明）：**recall@10 = 每个查询「精确 top-10 中被近似 top-10 捕获的个数 / 10」再对查询平均**，[0,1]，1.000 ≈ 精确；IVF/IVFPQ 的旋钮是 `nprobe`（扫多少个聚簇）、HNSW 的旋钮是 `efSearch`（探索多少候选）。确定性：合成集固定种子、FAISS 聚类/构建内部种子固定、单线程 BLAS——**召回率与字节数三遍逐位一致，墙钟只进 stderr**。

## 3. 实验 A · 同层机械：100 篇小库 vs 20k 合成集，四款索引的召回与体积

### A0：小库上三种索引的召回一模一样

```
A0 Exact(flat)          ：Hit@1=98/100 · Hit@5=100/100 · 排位 0:98 1:1 3:1
A0 IVFFlat(nlist=10,nprobe=10)：Hit@1=98/100 · Hit@5=100/100 · 排位 0:98 1:1 3:1
A0 HNSW(M=16,efSearch=128)：Hit@1=98/100 · Hit@5=100/100 · 排位 0:98 1:1 3:1
```

三个读数与 06 章 A0 一字不差（同一语料同一底板不是巧合）：Exact（每问全扫）、IVFFlat（nprobe=10=扫全 10 簇）、HNSW（efSearch=128）在 100 篇上**返回完全相同的黄金排位 0:98 1:1 3:1**。教学意义就在这一行：

> **召回分水岭不在这里。** 只要数据小到 BM25/精确扫描都扛得住，近似索引省下的那点时间毫无存在感，召回自然顶格。**所以"选哪个库"真正的决策变量在工程面**——这正是 §8.8 的表为什么按"类型 × 运维 × 适合"排，不按"召回"排。

### A1：20k 合成集上，旋钮把差异拉出来

```
A1 Exact(flat)=基准 recall@10 1.0000（精确穷举，代价=每查询全扫全库）
    IVFFlat  recall@10 vs nprobe：p=1→0.0696 · p=5→0.2234 · p=10→0.3439 · p=20→0.5068 · p=50→0.7604 · p=200→1.0000
    IVFPQ    recall@10 vs nprobe：p=1→0.0634 · p=5→0.1494 · p=10→0.1919 · p=20→0.2311 · p=50→0.2682 · p=200→0.2806
    HNSW     recall@10 vs efSearch：ef=16→0.5333 · ef=32→0.7174 · ef=64→0.8801 · ef=128→0.9737 · ef=256→0.9973
```

三个机械各自的"油门"曲线（图 1 的裸数据）：

1. **IVFFlat：最诚实——旋钮开到底 = 精确**。nprobe 从 1 → 200（=nlist 全覆盖），recall@10 从 0.07 一路爬到 **1.000**。代价线性的：probe 扫多少簇，就是花多少倍的时间。**IVF 的召回是可调的，代价是延迟**。
2. **IVFPQ：旋钮开到底也到不了精确**。同样 nprobe=200，停在 **0.2806**——不是没有扫够，是**量化噪声**（每个向量被压缩成 8 个子码，邻居在码本里糊掉了）。同一预算（nprobe=20）IVFFlat=0.51 vs IVFPQ=0.23：**体积省 12 倍，是以召回让位换来的，不是白拿**。
3. **HNSW：起点最高、收尾最陡**。efSearch=16 就 0.53（candidate 少也远超随机），efSearch=256 到 **0.9973**。HNSW 的召回-延迟曲率最漂亮，代价在体积（见 A2）与构建复杂度。

> 一句话：**索引层的差异是"数学上早已注定的"，哪家库都包着这几种机械——真到选库时，这些曲线是"给定库被你调 nprobe 后能到哪"的地图，而不是"该选哪家"的答案。**

### A2：写盘字节账，把"成本"落成数

```
A2 Exact      ： 5120045 B（≈256 B/向量，fp32 原样）      · recall@10 1.0000
   IVFFlat    ： 5332939 B（≈267 B/向量）                  · 工作点 nprobe=20 → recall@10 0.5068
   HNSW(M=32) ：10562530 B（≈528 B/向量，图边把体积顶到 ~2×）· 工作点 efSearch=128 → recall@10 0.9737
   IVFPQ      ：  438516 B（≈22 B/向量，压缩到 1/12）       · 工作点 nprobe=20 → recall@10 0.2311
```

字节账三个读数：

1. **裸向量是成本地板**：20k×64 fp32 = 5.12MB（256 B/向量）。Exact 就是这数，IVFFlat 只多 4%（聚簇表 + 链表开销），**HNSW 却顶到 2×**——那多出来的 5.4MB 是图的邻接边。**"召回最漂亮"的 HNSW 不是免费的，图要存**。
2. **IVFPQ 把体积压到 1/12**（22 B/向量），但它没省对地方：**省的是内存和带宽，丢的是召回**——这是给"向量必须住进有限内存"的场景用的，不是给"要更高召回"用的。
3. **操作级结论**：你要算的从来不是"裸向量多大"，而是**裸向量 + 图边/聚簇 + 元数据过滤字段 + 备份副本**四个加起来的驻留。这篇的 C2 外推账把这条拿到百万级算一遍（§5）。

> A1/A2 合起来就是短语版的索引层小三角：**Exact = 召回满格 + 体积原样；IVF = 召回可调 + 体积近原样；HNSW = 召回接近精确 + 体积 ~2×；IVFPQ = 体积 1/12 + 召回封顶让位。**

## 4. 实验 B · 工程外壳：§8.8 九家对照 + 场景决策引擎 9 断言

索引层被 A1/A2 拉平之后，选库的重心整个落到工程面。先给九家同层比较的对照表（**要素事实，非本机实测**，知识地图 §8.8 原表）：

| 系统 | 类型 | 优势 | 适合 |
|---|---|---|---|
| FAISS | 库（进程内） | 快、轻、研究友好；HNSW/IVF-PQ 全支持 | 原型/单机 |
| Milvus | 分布式向量库 | 云原生、大规模、多索引、GPU 支持 | 生产大规模 |
| Qdrant | 分布式向量库 | 过滤能力强、Rust 性能好、易部署 | 中大规模生产 |
| Weaviate | 分布式向量库+图 | 混合检索、模块化 | 中规模 |
| Chroma | 轻量嵌入式 | 零运维、本地优先 | 原型/个人 |
| pgvector | Postgres 扩展 | 与业务数据同库、事务一致 | 已有 PG 的中小应用 |
| ES/OpenSearch | 全文+向量双引擎 | BM25 极强、运维成熟、企业标配 | 混合检索生产 |
| Redis Stack | 内存 KV+向量 | 超低延迟、缓存热路径 | 极热查询 |
| LanceDB/SQLite-VSS | 嵌入式新秀 | 零服务、列式存储 | 本地/边缘 |

这张表本身是"事实"，而"先定场景再选库"是一条**可以跑断言的规则**——探针把它做成场景决策引擎：每个场景压缩成六个维度（事务 / 规模 / 延迟 / 运维 / 混合 / 图），按 §8.8 的适合栏编码成优先级规则，9 个场景全断言锁死：

```
B  s01 原型/个人·本地优先·零运维 -> Chroma               [决策锁: lock]
B  s02 单机研究·轻量·四款索引都要测 -> FAISS                [决策锁: lock]
B  s03 生产大规模·云原生·GPU -> Milvus               [决策锁: lock]
B  s04 中大规模生产·过滤强（多租户/时间过滤） -> Qdrant               [决策锁: lock]
B  s05 已有 PG 业务库·订单与向量同库要事务一致 -> pgvector             [决策锁: lock]
B  s06 企业混合检索·BM25+向量·运维成熟优先 -> ES/OpenSearch        [决策锁: lock]
B  s07 极热查询·超低延迟·缓存热路径 -> Redis Stack          [决策锁: lock]
B  s08 本地/边缘·零服务·列式存储 -> LanceDB/SQLite-VSS   [决策锁: lock]
B  s09 中小规模·混合检索+图也要·模块化 -> Weaviate             [决策锁: lock]
```

三个读数——

1. **九个场景九个答案，互不撞车**。看起来"都是向量检索"，但 s01 与 s08 都满足"零运维"却不同答案（原型 vs 边缘），s06 与 s09 都是"混合检索"却不同答案（企业运维 vs 要图）——**区别全在工程维度上**。这正是 A0 那条"召回拉了平"的推论：既然召回不区分，那就让工程维度来区分。
2. **决策引擎 = 这章的"教学浓缩装置"**：把 §8.8 的适合栏从"读过"变成"能对任意新场景给答案"。规则表本身是 author 写的（诚实边界 §6），但 9 条断言是**本机真跑**——同一输入永远同一推荐。
3. **一条粗口径记忆**：小 → Chroma/FAISS；中 → Qdrant/Weaviate；生产大 → Milvus；混合且要运维成熟 → ES；事务同库 → pgvector；极热 → Redis；边缘 → LanceDB。

> 和 06 章对照一眼：06 是**生成侧**的闸（进生成前的相关句抽取），本篇是**索引端存储层**的闸（检索跑在什么引擎上）。一个管"喂进嘴里的干不干净"，一个管"存库的壳够不够撑"。候选 A 四站至此各管一段：**02 全图 → 10 决策要不要多查 → 11 要不要换数据形态 → 06 进生成前 → 本篇存进什么壳**。

## 5. 实验 C · 成本账：墙钟 + 生产外推

### C1：索引层的建造与查询都不贵，贵的是模型加载与数据量大之后

墙钟（stderr `[wall]`，run1 实测 ≈26.9s，三遍浮动 26.82~27.07s）：

| 打点 | run1 |
|---|---|
| A0 encode+index+100 问排位（含模型加载 ~9s） | 12.56 s |
| A1/A2 建四款索引 + 全部 recall 核算（20k×64d） | 13.83 s |
| C 100×4 次查询（合成集） | 311.46 ms |
| C 决策引擎 9×判断 | 0.011 ms |
| total | 26.86 s |

三个读数：

1. **建索引本身不贵**：20k 条量级，IVF <0.2s、HNSW ~2s、IVFPQ ~3s（run 间浮动，量级稳定）。**模型加载 ~9s 反而是总墙钟的大头**——这正是"向量库"与"embedding 模型"的分工：库不管编码，只存与查。
2. **查询是毫秒级**：100 条 × 4 款索引一次全扫 ≈ 311ms，平均每款每查询亚毫秒——再次说明**小数据上延迟根本不是选库因素**。
3. **决策引擎 0.011ms**：规则表的快是"快得没意义"，因为它的价值在"答案是规则锁死的、可追溯的"，不在速度。

### C2：百万级外推账（非本机实测，要素账）

把 A2 的字节账按比例放到 **1,000,000 条 × 768 维 fp32**（裸向量 ≈ 768×4 = 3072 B/条 ≈ 2.9 GiB）：

- **裸向量只是地板**：1M 条 768-d fp32 ≈ 2.9 GiB；按本篇 A2 实测比例，HNSW(M=32) 体积 ≈ 2× 裸向量（图边把体积顶上去）→ **同数据 HNSW 总驻留 ≈ 8~9 GiB 量级**（裸 + 图边，不含过滤字段的倒排与副本/备份）。
- **"生产大规模看 Milvus/Qdrant/ES" 说的是工程面**：分片、HA、增量删除、多租户过滤、运维监控——这些在 A1/A2 的技术里**根本没有答案**，它们是 §8.8 优势栏里的东西。**建库前先按"四件套"估容量：裸向量 + 图边/聚簇 + 元数据过滤字段 + 备份副本**，别只按裸向量对账。
- **极热路径选 Redis Stack 是缓存账**：内存驻留的价格换"热查询不进磁盘 scan"；同样的数据住内存还是住盘，决定了你要不要它为这个场景买单。

> 与 11 章的成本账并排：GraphRAG 建图 = 文档 → 三元组，向量库建索引 = 文档 → 向量列 → 可查结构——**都是"一次构建成本换长期查询体验"，构建成本与查询模式的匹配才是选型，不是谁更"新"**。

## 6. 诚实边界（AAA 自我审查）

以下为本实验的边界，必须诚实交接（对应仓库"每篇带实测量、不吹不黑"的原则）：

- **§8.8 九家表与决策规则是"要素事实 + 作者规则"，不是本机测出来的能力评测**：系统类型/优势/适合来自知识地图（官方文档口径，写作环境无外网未在线复核）；场景决策引擎的优先级编码是 author 写的规则表，脚本只做「同一输入 → 同一推荐」的断言锁——**不是"我装了九个库跑了 benchmark"**。真到生产，每个库的功能集（分片策略/过滤支持/HA 细节）要对着官方文档核对。
- **A1/A2 的 20k×64d 是合成高斯集，不是真实语义语料**：合成集让"旋钮 → 召回"的曲线干净可复现（随机数据没有主题结构可作弊），但它不是 embedder 产出的真分布——**真实语料的曲线只在你的数据上算数**。真实 100 篇这边（A0）只证明"小库召回拉平"，不证明大库里各机械的比例关系。
- **recall@10 是相对精确的近似覆盖率**：1.000 = "和前 10 一样"，不是"答案正确"。选库基准要看你的评估集（RAGAS 那套，07 章），不是 recall@10 一个数。
- **墙钟没有生产可比性**：本机单线程、20k 数据、单机进程内 faiss——**只反馈"哪档操作费几次调用"，不翻译成生产 QPS/延迟**。生产延迟 = 网络往返 + 分片路由 + 磁盘/缓存层级，全部非本机实测。
- **"决策引擎 9/9 全过"是作者规则的自我一致性，不是九家功能实测**：它锁的是"这张表我写得自洽"，不是"Chroma 真的适合千人项目 / Milvus 真的支持你的分片需求"。规则与官方能力之差要打问号。

## 7. 常见坑（5 条）

1. **把"选索引"当"选库"**。A0/A1 已经给证据：召回在索引层，而库与库的差异在工程层。你连 HNSW 都不用自己选（现在库都默认包一个），真正要选的是"要不要分布式、要不要事务、要不要过滤、谁来运维"。**先答场景六问，再翻 §8.8 表**。
2. **按"裸向量大小"估容量**。A2 的字节账砸的就是这个：20k 数据 HNSW 就已经是裸向量的 2 倍，真实生产还得再加元数据过滤字段（倒排）+ 备份副本。**建库前的容量单 = 裸向量 + 结构开销 + 元数据 + 副本**（C2 四件套），别只算第一个数就掏钱。
3. **为了"向量库"上重型组件**。§8.8 原话："别为了'向量库'而引入重型组件"。单机 10 万条、试 prototype——一个 FAISS/Chroma 半小时搞定；为了"看起来专业"上一个分布式集群，运维成本比检索收益大得多。**先定场景再选库，倒过来就是给自己上套**。
4. **以为"压体积 = 白赚"**。IVFPQ 的 1/12 是从召回里抠出来的：A1 里同一 nprobe 下 IVFFlat=0.51 vs IVFPQ=0.23。**体积换召回是硬交易**，只在"向量必须住进有限内存"时才划算（对话式记忆/百万级内存约束）。
5. **拿"召回上限"读曲线，不拿"工作点"读**。A1 给的是旋钮曲线：IVF 开到底 1.000、HNSW 开到 256 才 0.997——但生产不会开满（延迟受不了）。**每个引擎要挑一个"工作点"（nprobe/efSearch）+ 一版评测集**，像 06 章 C1 那样拿答案支持率复盘，而不是拿规格表复盘。
