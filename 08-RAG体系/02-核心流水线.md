## 0. 为什么先把全图画给你

你多半听过 "RAG"：检索增强生成，先搜资料再写答案。但当你真的想搭一个，会撞上**一整面墙的零件**：分块、Embedding、向量库、BM25、Reranker、元数据过滤、RAGAS 评测……每个名词都有独立教程，但**教程和产线之间隔着一条整合的河**——零件回答"这一个怎么用"，产线回答"它们先后怎么串、卡点在哪、怎么验证、坏在哪儿怎么修"。

多数初学者在这个墙前慌，不是因为难，是因为**没见过那张全图**。本章就把全图画出来：

```text
【索引端】数据源 → 解析 → 清洗 → 分块 → 元数据 → Embedding → 向量库（+倒排） → 增量维护
                                                                    ↓
【查询端】问题 → 查询理解/改写 → 检索（向量+BM25 混合） → 重排 → 上下文压缩
        → 拼装 Prompt → 生成（带引用） → 评测 / 反馈（回灌索引端）
```

这张图**几乎包含了 RAG 全部的技术命题**：每一段的选型与坑（分块选多大、Embedding 中文选哪个、重排必配）、每一段的工程纪律（元数据是引用的地址簿、增量更新不能停）、以及贯穿全线的评测（不评测等于没做）。`08-RAG体系` 目录后面的每一章，都是这张图里某一段的深挖——**读任何一章时先问"现在是图里的哪一段"，比记住任何单个 API 都值钱**。

> 一句话（为什么有本章）：**流水线不缺零件，缺路标。你先拿到一张图，后面 12 章往里填细节，读起来才有坐标感。**

## 1. 一条流水线：两端七段通行

真实 RAG 系统分**两端**，先各自独立完工、再在"生成"处会师：

### 1.1 索引端（把文档变成"可检索的库"，离线做一次）

```text
① 解析      PDF/HTML/扫描件 → 结构化文本（版面、表格一并考虑）
   ↓
② 清洗      去水印/页眉页脚/噪声 → 干净正文
   ↓
③ 分块      正文切成"语义自包含"的块——整段 embedding 的平均化是检索飘的根源
   ↓
④ 元数据    每块打标（来源/页码/章节/分类/时间/租户）→ 引用的地址簿
   ↓
⑤ 向量化    块/ 子块 → Embedding 向量（词面信息另存倒排索引给 BM25 用）
   ↓
⑥ 入库      向量进向量库 + 倒排进搜索引擎 → 增量更新/删除随时待命
```

**这一段最容易忽视的是"块"和"粒"的两本账**：块太堆 → embedding 平均化、具体问题检索飘；块太碎 → 上下文不足、答案没证据密度。仓库 `011` notebook 在 90 条语料（每 3 条合 1 章）上实测过这套落差的全部读数：**整篇级 top-1 命中所在章只有 0.67，切子块后 gold 子块 top-1 命中拉到 1.00，命中后再回填父块上下文仍在、代价是上下文放大 3.14×**（见 `09-Advanced-RAG模式清单` 模式①）。**索引粒度决定检索精度，回填粒度决定上下文充足度**——这两个旋钮，就在这一段。

### 1.2 查询端（把问题变成"带证据的答案"，在线每问一次）

```text
① 查询理解/改写  口语 → 书面、指代消解、补全（用户话 ≠ 文档话）
   ↓
② 检索          向量 + BM25 混合 → 双路召回 → 融合（RRF / min-max 加权）
   ↓
③ 重排          top-100 候选过交叉编码器 → top-3~10 进上下文
   ↓
④ 上下文压缩     块太多太长时，用 LLM/小模型挑"与问题相关的句子"（LLMLingua 类）
   ↓
⑤ 拼装 Prompt    片段按相关性排序、控制总量、标注来源编号 → 强制"只依据证据回答"
   ↓
⑥ 生成（带引用） LLM 读证据写答案 → 每句可溯源
   ↓
⑦ 评测/反馈     三层指标打分 → 差 → 回去调索引端或查询端（回归机制）
```

**这一段最容易被跳过的是 ④ 和 ⑦**。④ 压 token 降噪声（地图 §8.6）；⑦ 是 RAG 的刹车——仓库 `010` notebook 做过判别性对照：**把错误来源的答案馋给模型，Faithfulness 从 0.74 直接跳水到 0.40**（`07-RAG评测-RAGAS` 有完整口径），不评测的 RAG 系统在"答错还自信"的状态下根本无从察觉。

> 一句话（两端）：**索引端管"库的质量"，查询端管"问的智慧"。索引端错了，查询端再聪明也回不了天——所以先确认"找没找对那段话（Hit@5），再谈"答得忠不忠实（Faithfulness）"。**

## 2. 演进主线：这条线不是一天长成的

地图 §8.1 给出了主线。看懂这条线有个额外收获：**RAG 的每一步演进，都是治上一代的一个具体病**：

```text
Naive RAG（2020–2023）：分块 → 向量检索 → 拼接 → 生成
   治什么？：让 LLM 在"事实类问题"上不再瞎编（外部知识落进来）
   ↓
Advanced RAG（2023）：查询改写 / 重排 / 混合检索 / 父子分块 / 元数据
   治什么？：Naive 版"找到的文档不对、除了答不细"——把索引端和查询端各补一刀
   ↓
Modular RAG（2024）：组件模块化、可任意组合、加评测
   治什么？：一切组件都能自由替换，评测才能告诉"换哪个真有效"
   ↓
Agentic RAG（2024–2025）：Agent 自主决定"查不查、查什么、查几轮、要不要反思"
   治什么？：单轮固定管线答不了多跳/条件查询——让"查"变成决策而不是死步骤
   ↓
GraphRAG（2024）：实体关系图谱上检索，擅长全局性问题
   治什么？：向量检索擅长"找相似片段"、不擅长"跨全局总结与实体关联推理"
   ↓
Multimodal RAG（2024–2025）：图、表、版式都参与检索与回答
   治什么？：纯文本分块把 PDF 里的图表信息全丢了
```

每个新范式没有杀死老范式，而是**叠上去**：2026 年的工程实践里，向量检索仍然是地基，Agentic RAG 是"要不要、怎么用这地基"的决策层，GraphRAG 负责全局问题，Multimodal 负责图像——**当你要爆料某人"旧"的时候，先确认你要治的病是不是已经被新版治了**（`09` 章诊断表现出过这张反直觉：Advanced 模式清单的反面是"顶格语料上全是零收益"）。

> 一句话（演进）：**每一代 RAG = 上一代 + 治它一个病。要选型，先定位你要治的病是"检索不准、答不细、全局查不了、还是图表看不见"，再决定要不要升级。**

## 5. 常见坑

1. **把"总览"当"全部"**：本篇只有路标，没有配方。想复现任何一行数字，去对应章节/notebook 一键跑；想学任一段，去 §4 地图找那一章。
2. **把不同语料的数字拼成"同一管线曲线"**：§3 旅程表是**全景拼图**，不是连续测量。引任何一行的数字要对准出处与口径（100 条 vs 90 条 vs 6 主题 vs 8 查询），跨口径不并表。
3. **先调模型，后查索引**：RAG 里**检索层失误的代价先于生成层**——gold 都不在 top-5 里，生成再强也是无米之炊。出问题先跑检索层指标（Hit@5/MRR），再谈换提示词。
4. **只答不对**：`010` 的判别性对照（1.00/0.74 → 0.17/0.40）展示的是"检索 Hit 全中、答案照样错"——**检索指标不是答案指标**，三层分开看。
5. **跳过评测上生产**：RAG 是"检索工程"，**唯一的刹车就是评测**。每次换 embedding / rerank / chunk 都跑同一套评测集对比，否则 Advanced 模式就是"装"。
6. **把"演进"当"淘汰"**：Agentic/GraphRAG 不到 2026 就替代向量检索——它们是**叠加**不是替代；选型先定位"要治的病"，再看该上哪一层（接 `09` 诊断表）。
