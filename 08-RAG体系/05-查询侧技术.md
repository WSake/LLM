## 0. 为什么需要查询侧：三个「失配」

RAG 的输入是**用户的一句话**，而索引里是**文档的一段话**。两者是两种语言，失配来自三处：

1. **口语/省略/指代**：用户说「它那个靠注意力的模型是啥来着」，文档里写的是「Transformer 是 2017 年提出的基于注意力机制的网络结构」。直接拿原话检索，「它」「啥来着」全是噪音，关键实体还缺位。
2. **词面断裂**：用户说「用一串数字表示词的意思」，文档的关键词是「词向量」——两个句子没有任何公共词。BM25 这类词面模型直接归零；语义模型能扛住大部分，但代价是必须重 embedding。
3. **复合/多跳**：用户把两个子问题拧成一句（「联邦蒸馏结合出的那套……本质让谁模仿谁」），答案要跨两篇文档才能拼出来。单句一杆子插到底，通常只中一头。

查询侧技术（Query side）就是在这三个失配上动手：**改写（Rewrite）、扩展（Expansion）、分解（Decompose）**，外加它们的变体。

## 1. 六种查询侧技术全景（选型表）

| 技术 | 干什么 | 典型实现 | 对应失配 | 适用场景 |
|---|---|---|---|---|
| **Query Rewrite（改写）** | 口语转书面、补指代、去噪音 | LLM 重写 / 模板规则 | ① 口语省略 | 用户输入随意、日志杂乱时收益最大 |
| **Query Expansion（扩展）** | 给原查询补同义词/相关词，扩大词面覆盖 | 词表扩展 | ② 词面断裂 | 词面类检索（BM25）必备；语义检索边际收益低 |
| **Multi-query / RAG-Fusion（多路查询）** | 一题拆 N 个角度分别检索，RRF 融合 | 拆 3 路 + [RRF](03-混合检索与重排.md) | ②③ 多义/多角度 | 开放式问题（答案方向多） |
| **HyDE** | 先用 LLM 写一段「假设答案」再拿它检索 | LLM 生成伪文档 | ① 问得含糊 | 查询很短很怪、长文档语料时效果可观 |
| **Multi-hop（多跳检索）** | 第一轮结果扶出实体，第二轮带实体再查 | 迭代检索 + 重排 | ③ 复合多跳 | 关系推理、事实拼图；Agentic RAG 的雏形 |
| **Step-back / Decompose（退一步/分解）** | 大问题拆成语义子问题分别检索再聚合 | LLM 拆题 | ③ 复合 | 问题明确含多子问、或需要先定位大主题再答细问 |

> 共性：这些方法**都靠 LLM 参与（Rewrite/HyDE/分解）或额外 token（扩展）**——所以先测量值不值得，再花这笔钱。这一点在「实测」里看得特别清楚。

## 2. 怎么跑：一套探针，两个实验

探针脚本 `code/notebooks/_tools/query_side_demo.py` 复用 009/010 的 100 条中文语料与检索栈（rank_bm25 + jieba + faiss + bge-small-zh），跑约 40 秒：

```bash
cd 仓库根
python code/notebooks/_tools/query_side_demo.py
```

- **实验 1**：8 条「问题不含目标实体词」的查询，对比 BM25 / Dense 在 naive 与「同义词扩展」下的 Hit@1。
- **实验 2**：4 条复合/多跳问题（答案实体不出现在问题里），对比单句 naive 与「hop1 扶实体 → hop2 检索」并集。

核心就一行——**扩展 = 把缺位的同义实体词补回查询**：

```python
def expand(q, entities):
    return q + " " + " ".join(entities)     # 例：原词面 0 命中 → 补「词向量」

# naive
BM25: "用一串数字表示词的意思"          → Hit@1 = 0
# 扩展后
BM25: "用一串数字表示词的意思 词向量"     → Hit@1 = 1
```

## 3. 实测①：词面断裂 → 同义扩展救 BM25（0.75 → 1.00）

8 条查询全部**不出现目标文档的专属实体词**（卷积核/注意力机制/知识蒸馏/联邦学习/词向量/剪枝/图灵测试/词嵌入），模拟「用户用大白话问专业词」。

| 检索器 | naive Hit@1 | +同义扩展 Hit@1 | 变化 |
|---|---|---|---|
| **BM25（词面）** | **0.750**（6/8） | **1.000**（8/8） | **+0.250** |
| Dense（bge-small-zh） | 1.000（8/8） | 1.000（8/8） | ±0.000 |

BM25 的两次失败非常典型（问题与文档无公共词，4-gram 全断）：

| 用户原话 | 期望文档 | naive 命中的错误文档 |
|---|---|---|
| 「用一串数字表示词的意思」 | doc[30] 词向量… | doc[27] **自编码器**通过无监督学习…（兜底到同主题旁的「压缩表示」） |
| 「区分机器和人的那个古老检验」 | doc[4] 图灵测试… | doc[44] **分布式系统**通过多台机器协同计算…（「机器」一词的双义陷阱） |

**而 Dense 两道全过**——bge 把「用一串数字表示词的意思」和「词向量用低维稠密向量表示词义」映射到了同一片语义空间，词面断裂对它是常数级噪音。这就是为什么现代 RAG 的默认底座是「BM25 + Dense 混合」（见 [03-混合检索与重排](03-混合检索与重排.md)）：**词表模型负责准词，向量模型负责换词**。

## 4. 实测②：复合/多跳问题 → 分解扶实体（H1 2/4 ≠ H5 4/4）

4 条复合问题，**答案实体（知识蒸馏/注意力机制/联邦学习/卷积核）都不出现在问题里**，只能经由「桥文档」扶出来：

| 目标（doc[22] 知识蒸馏 ∕ 8 ∕ 25 ∕ 5） | 单句 naive H1 | 单句 naive H5 | hop1 正确扶出桥文档 | 分解并集 H1 |
|---|---|---|---|---|
| doc[22] 知识蒸馏让谁模仿谁 | 0 | 1 | ✓ doc[97] 联邦蒸馏… | 0 |
| doc[8] 注意力机制让模型干嘛 | 0 | 1 | ✓ doc[2] Transformer… | 0 |
| doc[25] 联邦学习靠上传什么 | 1 | 1 | ✓ doc[97] 联邦蒸馏… | 0 |
| doc[5] 卷积核的作用 | 1 | 1 | ✓ doc[5]（首跳即中） | 1 |
| **聚合** | **2/4** | **4/4** | – | **1/4** |

三个诚实到有点扎心的读数：

1. **H5 全中（4/4）**：bge 在 100 条易语料上把目标塞进了 top-5——单句检索「没有崩」，所以你不会察觉异常。
2. **首屏已失（H1 只有 2/4）**：doc[22] 的 naive top1 是桥文档 doc[97]，doc[8] 的 naive top1 是 doc[2]。用户看到的第一屏答案不对，但系统「觉得」自己找到了。**用 Hit@1/MRR 看首屏，才能照出这类失配。**
3. **naive 并集不是银弹**：hop1+hop2 并集后 H1 反而更低（1/4）——并集把桥文档顶到第一，不做重排/LLM 聚合，光「检索出来并列放着」解决不了「哪一段才是答案」。

这正是指向 Agentic RAG（知识地图 §8.10）与 Rerank（[03-混合检索与重排](03-混合检索与重排.md)）的理由：**多跳是「检索两次 + 判断一次」，判断那步才是要害。**

## 5. 评测/验证：从这些数字读出的三条结论

1. **先测张力，再上技术**。本仓库的 100 条易语料上，Fatihfulness/检索 H5 全部顶格（[007 判别性对照](07-RAG评测-RAGAS.md)、[notebook 010](../code/notebooks/010-RAGAS评测一个RAG系统.ipynb) 都演示过）——此时盲目堆 Rewrite/分解，收益≈0 还白付 token。正确顺序：**拿自己的失败样本清单说话**，比如跑一遍 [notebook 010](../code/notebooks/010-RAGAS评测一个RAG系统.ipynb)，挑 R/A 最低的 20 条看。
2. **视角决定看到什么**。H5 全中 ≠ 首屏正确：同一套检索，Hit@1 2/4 vs Hit@5 4/4，观感完全不同。线上系统用户只看前几条，评测至少同时报 Hit@1 与 MRR。
3. **每种查询侧技术都有账单**。Rewrite/HyDE/分解要多一次 LLM 调用（延迟+成本）；扩展多 token；RAG-Fusion 多 N 路检索+融合。**收益（Hit 差）和成本（延迟差）一起上表**，才是工程决策。

## 6. 常见坑（5 条）

1. **在易语料上「验证」了查询侧技术**。naive 0.75 但有 6/8 本来就中——先构造能让 naive 失败的样本（词面断裂、复合问法），否则你测的是自己想像中的技术。
2. **分解只拆不聚**。子查询结果靠「并集摆着」不重排，桥文档会把首屏顶错（实测② H1 1/4 就是这么来的）。拆完之后必须有一层聚合/重排/判断（Reranker 或 LLM）。
3. **扩展无克制**。盲目 append 一堆同义词会稀释 BM25 得分，把查询向量拖偏；扩展词在 3-6 个内，且优先「目标实体名」而非随机邻近词。
4. **把口诀当圣旨**。「默认 Hybrid」是对的，但**混合权重不是常数**（[03-混合检索与重排](03-混合检索与重排.md) 用 0.40 重合率说明了这一点）；查询侧同理，Rewrite 对正式书面查询反而可能引入漂移。
5. **HyDE 生成什么就检索什么**。伪答案里若带着 hallucination，检索方向就被带偏；HyDE 适合「短而含糊的查询」，长而明确的查询收益为负——同样先测再上。
