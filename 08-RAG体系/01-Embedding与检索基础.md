## 0. RAG 为什么要先解决「检索」

上一章（§8.0 为什么需要 RAG）已经讲过：RAG 解决**知识静态、幻觉、不可溯源**三个问题。但在"生成"之前，它必须先把相关文档**找**出来。

这一个环节直接决定后面所有环节的天花板：

```
检索引擎 找错段落 → 拼进 Prompt 的是噪声 → 生成器再聪明也说不出正确答案
检索引擎 找到对段落 → Prompt 里证据充分     → 生成器只需要"组织语言"
```

所以做 RAG 的第一课不是调 Prompt，而是**把检索指标打上去**。本文只讲一件事：怎么"更快、更准、更便宜"地找到对的那段话。

> 一句话判断你的 RAG 该先优化哪：**答案"答非所问"→ 先查检索（本文）；答案与文档内容矛盾 → 先查生成与压缩（见后续章节）。**

## 1. 稀疏 vs 稠密：两个世界的差异

检索要回答的问题只有一个：**判断"问题"和"文档片段"像不像**。两套主流方案给出了完全不同的答案：

| | 稀疏检索（Lexical） | 稠密检索（Dense / Bi-encoder） |
|---|---|---|
| 表示 | 高维稀疏向量（词袋/词频） | 低维稠密向量（如 512/768/1024 维） |
| 匹配方式 | **字面词项**匹配（术语、专名精确命中） | **语义**匹配（同义改写也能命中） |
| 代表 | BM25、TF-IDF | Sentence-BERT、BGE、GTE、E5、OpenAI-Embedding |
| 速度 | 极快，毫秒级 | 快（但没有倒排索引级别的暴力快） |
| 可解释性 | 高（能告诉你命中了哪个词） | 低（一个向量，说不清"为什么像"） |
| 弱项 | 同义词、口语、改写后就失效 | 专有名词、代码变量名、英文简称 |
| 中文注意 | 必须先分词（用 jieba 等） | 选对中文预训练模型比什么都重要 |

它们不是竞争关系，而是**互补**关系：

```
"我还了房贷"  → 语义检索命中「抵押贷款」
"ERM-3X"     → 词法检索命中「ERM-3X」（稠密检索对专名不敏感）
```

> **生产标配 = 混合检索（Hybrid）**：两路并行，各自召回 top-k，再融合。原因很简单——任何单一方案都有结构性盲区。融合方法（加权、RRF）在「03-混合检索与重排.md」讲；本文先把两路上半身讲透。

## 2. BM25：词法检索的「凯撒」

BM25（Best Matching 25）是目前**事实标准的词法检索算法**，搜索引擎用它几十年，至今在 RAG 里不可替代。

**核心直觉**：一个词在一篇文档里出现越多越重要（词频），但那些到处都有的词（"的""在""是"）不重要（逆文档频率）。再加两条工程修正：
- **词频饱和**：出现 10 次和 20 次差别很小，不是线性叠加（用 `k1` 控制）；
- **文档长度归一**：长文档天然词多，不能天然得高分（用 `b` 控制长度惩罚）。

打分公式（对每个查询词求和）：

```
score(D, Q) = Σ_{q ∈ Q}  IDF(q) × ─────────────────────────
                                   tf(q,D) + k1×(1 − b + b×|D|/avgdl)

IDF(q) = ln( ────────────── + 1 )
            df(q) + 0.5
```

- `tf(q,D)`：词 q 在文档 D 中的词频；`|D|` 是文档长度，`avgdl` 是所有文档平均长度
- 常用参数：`k1 = 1.2 ~ 1.5`，`b = 0.75`（笔记本里 rank_bm25 默认即此区间）

**中文必须先分词**：BM25 按"词"统计，而中文没有天然空格。`"机器学习很强大"` 不切分就变成一个词，任何查询 `"机器"` 都命中不了。用 `jieba` 切成 `["机器","学习","强大"]` 即可。

**为什么生产上还留着它**：快、可解释、对专名/代码/型号/年份极其准确——这些恰恰是语义模型最弱的。

## 3. 稠密检索：让语义相近的两个词也挨在一起

稠密检索（Dense Retrieval）把 **query 和文档分别编码成低维向量**，然后计算向量相似度。用的是 Bi-encoder（双塔）架构：

```
query: "如何提前还房贷" ──→ 编码器 ──→ [0.12, -0.35, 0.88, ...]  ←─ 余弦/内积 ─→
doc:   "提前还款的利息计算方式" ─→ 编码器 ─→ [0.10, -0.30, 0.90, ...]         ↑
    （同一个编码器，两塔共享权重的孪生结构）                        相似度 ≈ 0.97
```

**它强在哪**：query 写 "自动扣款失败" 也能命中 "代扣业务异常导致扣款未成"——字面上没一个词相同，语义上却是同一件事。

**相似度用什么**：
- 余弦相似度 = 归一化后的内积，`cos(a,b) = a·b / (‖a‖‖b‖)`
- **工程上先 normalize 再算内积**：编码完把向量归一化，相似度就等价成内积运算，Faiss 用 `IndexFlatIP`（内积）加速，结果和余弦一模一样，但快很多
- 维度越低存储越便宜、推理越快，但表达能力弱：512 维（bge-small）适合小集大致够，1024 维（bge-large）更准但更贵——**取舍永远在自己数据上定**

**一个 3 行版的语义检索**（示意，完整代码见第 7 节）：

```python
from sentence_transformers import SentenceTransformer
model = SentenceTransformer("BAAI/bge-small-zh-v1.5")
vec = model.encode(["如何提前还房贷"], normalize_embeddings=True)
print(vec.shape)  # (1, 512) —— 512 维向量
```

## 4. 向量是怎么被存放和比对的（索引）

100 条文档时，暴力计算（Flat）足够快。但**生产是十万、百万级向量**，暴力比对无法接受。索引就是把"全量比对"变成"先粗筛再精算"。

| 索引 | 思想 | 速度 | 内存 | 适合 |
|---|---|---|---|---|
| `Flat`（暴力） | 逐条算内积 | 慢 | 最小（只存向量） | 原型、<1 万条 |
| `IVF`（倒排文件） | 聚类分桶 → 先定位最近几个桶 | 快 | 中 | 百万级，召回稍降 |
| `HNSW`（分层小世界图） | 图跳转逼近最近邻 | 极快 | 较大（图要占内存） | 生产主流，召回高 |
| PQ / SQ 量化 | 压缩向量位数 | 更快 | 小 | 超大规模、可接受精度损失 |

**一句话选型**：单机小规模用 `IndexFlatIP`（本文和 009 都是它，忠实展示"相似度本身"）；百万级生产默认 HNSW；再大的库交给向量数据库（Milvus/Qdrant/pgvector 等，见「02-向量数据库选型.md」）。

Faiss 建平扫索引只需 2 行：

```python
import faiss
index = faiss.IndexFlatIP(dim)                 # dim = 向量维度，如 512
index.add(normalized_vectors)                  # 先归一化，内积≈余弦
scores, idx = index.search(normalized_query, k)  # 返回 top-k 分数与 id
```

## 5. 怎么评测检索：Hit@k / Recall@k / MRR / nDCG

没有评测的检索 = 玄学。一篇文档的对错不好定，但**检索对错非常好定**：一条 `(问题, 标准答案所在文档)` 测试集 + 看答案文档是否出现在召回里。

**评测集怎么造（关键）**：从**生产真实问题**里抽 50–200 条，人工标出"正确答案来自哪段"。别用论文题目凑数。

| 指标 | 定义 | 一句话直觉 |
|---|---|---|
| **Hit@k** | top-k 里是否**出现过**正确答案（0/1） | "找没找到过"，最直觉 |
| **Recall@k** | top-k 命中的相关文档数 / 相关文档总数 | "该捞的捞上来多少" |
| **Precision@k** | top-k 里相关文档占比 | "捞上来的不相关多不多" |
| **MRR** | 正确答案**排位**的倒数，取均值 | "答案排第几，越靠前越好" |
| **nDCG** | 加权排序质量（越相关越靠前给越多分） | "排位 + 相关度 综合打分" |

**多模态注意**：Hit@k 不惩罚"排第 5 还是第 1"；MRR 惩罚。落地评测把 **Hit@5 + MRR@10** 一起看——前者管"答案在不在袋子里"，后者管"袋子翻起来够不够快"。

## 6. Embedding 模型怎么选（中文场景）

中文检索选模型的优先级：**双语/中文能力 > 榜单分数 > 维度大小**。榜单（MTEB/C-MTEB）只做参考，最终以自己数据集上的 Hit@k 为准。

| 模型 | 维度 | 特点 | 中文适配 |
|---|---|---|---|
| `bge-small-zh-v1.5`（BAAI） | 512 | 轻量、CPU 可跑、效果稳 | ★ 入门首选（009 用这个） |
| `bge-base-zh-v1.5` / `bge-large-zh-v1.5` | 768 / 1024 | 更大更准，成本更高 | 效果敏感场景 |
| `bge-m3`（BAAI） | 1024 | 多语言 + 多粒度 + 稀疏融合 | 多语言/长文本 |
| `GTE` 系（阿里） | 768/1024 | 开源效果第一梯队 | 中文能力强 |
| `text-embedding-3-*`（OpenAI） | 1536/3072 | 闭源 API，省运维 | 通用，多语 |

**BGE 系使用要点**（官方规范）：
- query 侧加指令前缀 `"为这个句子生成表示以用于检索相关文章："`（bge v1.5 起**文档侧不需要**指令，只有 query 侧加）；
- 统一用 `normalize_embeddings=True`；
- 中文不要少分词标点，给足 512 token 以内的完整段落。

## 7. 怎么跑：5 分钟复现一套检索基线

**推荐路径**：直接跑 [notebook 009 · 中文文档 RAG 全管线](../code/notebooks/009-中文RAG全管线.ipynb)。它内置 100 条中文百科语料 + 100 条带答案标注的测试问题，Colab 免费 CPU 约 5–8 分钟，跑完得到：

```
BM25   Hit@5: 1.0000     ← 100 问里 100 问，正确答案都在 top-5（词法层）
Dense  Hit@5: 1.0000     ← 语义层同样全中
Hybrid Hit@5: 1.0000     ← 融合后仍全中（融合在此例不出错，真实数据通常互有胜负）
```

> 本例语料的 100 条百科知识点**彼此区分度高**，所以三路都满分——这不代表生产环境，而是**证明这套评测台是对的**：检索器准 → 分数 1.0。真实场景换成你自己的文档集，分数才会分化，那时才是优化的开始。
> 别只看绝对分数，做两件事：① 换成你自己的语料重跑；② 把 `USE_LLM` 打开，看生成层的 judge 分数。

**只想自己起一个最小闭环**（不装重模型版）：

```python
import jieba, numpy as np
from rank_bm25 import BM25Okapi
from sentence_transformers import SentenceTransformer
from faiss import IndexFlatIP

docs = ["房贷提前还款的利息计算方式", "银行代扣业务说明", "车贷与房贷的区别"]
q    = "如何提前还款"

# —— 稀疏路：BM25 ——
cut = lambda s: [w for w in jieba.cut(s) if len(w.strip()) > 1]
bm  = BM25Okapi([cut(d) for d in docs])
top_bm25 = np.argsort(bm.get_scores(cut(q)))[::-1][:1]

# —— 稠密路：bge + faiss ——
model = SentenceTransformer("BAAI/bge-small-zh-v1.5")
emb   = model.encode(docs, normalize_embeddings=True)
index = IndexFlatIP(emb.shape[1]); index.add(emb)
_, top_dense = index.search(model.encode([q], normalize_embeddings=True), 1)

print("BM25  命中:", docs[top_bm25[0]])
print("Dense 命中:", docs[top_dense[0][0]])
```

实际输出（bge 对"如何提前还款"）：

```
BM25  命中: 房贷提前还款的利息计算方式
Dense 命中: 房贷提前还款的利息计算方式
```

**跑完看什么数字**：Hit@5 / MRR@10 的变化，就是你换模型、换分块、换索引时的唯一裁判。

## 8. 常见坑（5 条）

1. **忘了归一化**：不 normalize 做内积，相似度受向量长度污染——明明语义相近却因为一个长文档向量被挤低。**编码时统一 `normalize_embeddings=True`**。
2. **中文不分词就上 BM25**：Whole 段落当一个词，任何差异查询全部落空。先 `jieba`，再过滤单字与停用词。
3. **一看榜单选模型**：MTEB 高分不等于你的业务高分。**永远在自己数据上先出 Hit@k 基线**再决定换不换。
4. **query 忘了加 BGE 指令前缀**：bge 系列搜索场景 query 侧必须加指令前缀，否则相似度整体漂移。
5. **只盯准确率、不盯延迟/成本**：百万级全 Flat 索引能让你从毫秒变秒。规模到了就该换 IVF/HNSW 或向量库，评测指标要带上 **p95 延迟 + 单 QPS 成本**。
