## 0. 为什么"检索多用"必须配"生成用精"

回看 [02-核心流水线](02-核心流水线.md) 那张两端流水线：索引端切块编码，查询端取 top-k，生成端把取来的块**原样塞进上下文**。问题正出在最后一截——检索端和生成端的目标是反的：

- **检索端要"多用"**：k 太小会漏答案。本篇实测 top-20 能把答案行 100/100 捞回来（A0，§3），这正是"多用"的价值——**答案位已经进窗口了**。
- **生成端必须"用精"**：k=20 意味着每次生成吞下 **614.1 字符 ≈ 答案本体（~29 字符）的 20 倍**。其中 **约 77% 的 token 与问题无关**（陪跑行，§4）。模型要在 15.5 行噪声里找 1 行答案，忠实度与成本两头吃亏。

[10-Agentic-RAG](10-Agentic-RAG.md) 已经给过一记警钟：**盲目加深 k=2 vs k=40 答案位不变，只加 token 量**——"多查"不解决"喂进生成的东西太脏"。本篇补的是拿到 K=20 之后的那一步：**把加进来的 token 淘洗干净再送生成端**。这正是 §8.14 诊断表写在"忠实度差"和"成本暴涨"两行同一列的处方——上下文压缩。

> 一句定位：**Agentic 是在"检索这一层外面"加判断要不要再查；GraphRAG 是在"检索这一层底下"换数据站；Context Compression 是在"生成这一层前面"加一道闸——把检索结果从"20 行原文"压缩成"与问题相关的句子"。** 三者不同层，可叠加（§8 衔接）。

## 1. 上下文压缩三步：评分 → 裁剪 → 重组（+ Prompt 拼装与引用）

知识地图 §8.6 给的目标很白（此处为要素事实，非本机实测，精确实现以官方为准）：

```text
检索结果（top-20 原文块）
   │  ┌──────────────────────────────────────────────┐
   │  │ LLMLingua 类压缩器：                          │
   │  │  1. 评分  —— 给每个句子/token 打"与问题有多相关"│
   │  │     （LLMLingua 用语言模型算困惑度/条件概率）    │
   │  │  2. 裁剪  —— 按预算砍掉低分句子/token（保留）   │
   │  │  3. 重组  —— 把保留内容拼回一条干净上下文        │
   │  └──────────────────────────────────────────────┘
   ▼
压缩后的证据片（只含相关句 + 来源编号）
   ▼
生成：强制"只依据证据回答、不知道就说不知道"（only-from-evidence）+ 引用编号溯源
```

配套 §8.6 的三件套一起记：

1. **Context Compression**：块太多太长时，把"与问题相关的句子"提取出来——降 token 成本、降噪声。这是本篇的主菜。
2. **Prompt 拼装**：片段按相关性排序、**控制总量**（如 top-5 × 500 token）、标注来源编号 → 逼模型"只依据证据说"。
3. **引用**：生成时带段落编号，前端可溯源（对应 07 章"答案要能指向证据"）。

三件套里 2、3 是工程纪律（拼装模板与编号管线），本篇用探针实测的是 1（压缩机制本身）——下面把三步做成全本机可跑、可复核的数字。

## 2. 把那三步做成本机实测：相关句压缩 vs 全量直喂

> **诚实声明先行**：生产 LLMLingua 的"评分"是拿一个语言模型逐 token 算困惑度/条件概率——这在本机不可能零成本复现（模型调用 + 无外网）。本篇改用**规则相关句压缩**：BM25(q, line) 打分 + 词面交叠校验，把"与问题相关的句子"整行选出来。它是确定性的、零下载，且每条保留行都可回溯到原文档 = 断言可溯源。代价是：没有 token 级跨句重组、没有困惑度重排——这些留到 §6 诚实边界。**

探针复用与 009/010/05/10/11 完全相同的语料与检索栈（`code/notebooks/_demo_corpus.json` 100 篇中文短篇 + `BAAI/bge-small-zh-v1.5` + faiss），数字全部本机实测。跑一遍先看到赛前基准：

```
A0 检索多用·赛前基准：dense Hit@1=98/100 · Hit@5=100/100 · gold 行排位 0:98 1:1 3:1
  -> 「多用」= top-20 把答案行 100/100 捞回；分水岭在下游：20 行全送生成 vs 压缩后送
   k=20 平均每问吞 20 篇 × 平均 29 字 ≈ 614 字符（答案本体才 ~29 字符）
```

**A0 立的第一条是底数**：Hit@1=98/100、Hit@5=100/100——和 11 章 GraphRAG 的 A0 一字不差，因为同一份语料、同一条检索栈。**"检索多用"这一步没有悬念：top-20 已经把答案 100/100 捞进窗口**（gold 行 98 篇排第 1、1 篇排第 2、1 篇排第 4）。

但随即露出真矛盾：**答案本体才 ~29 字符，生成端却要吞下 614 字符的候选**——上下文:答案 ≈ **20:1**。后面三场实验就是在问：这 20 倍里有多少是必须的、多少是可以压缩掉的、压缩有没有代价。

## 3. 实验 A·token 账：614 字符 → 72 字符，压缩率 88.2%

实验 A 量化"生成用精"省下的 token。看 stdout（完整副本见文末 📎 附）：

```
A1 全量：每问 top-20 行 ≈ 614.1 字符（答案本体 ~29 字符 → 上下文/答案 ≈ 20×）
A2 宽松压缩（BM25>0 相关行 top-3，控制总量≈§8.6）：保留 ≈ 2.4 行 / 72.5 字符 → 压缩率 88.2%
   100 问总量：61.4k 字符 → 7.3k 字符（省 88.2%）
A3 现场抽样（Q0/Q5/Q10，宽松压缩保留 vs 裁掉）：
  Q#00  压缩保留：引力波是时空弯曲的涟漪，由大质量天体加速运动时产
         陪跑裁掉：Transformer是2017年提出的基于注意 | 梯度下降通过沿损失函数负梯度方向迭代更新参数，是
  Q#05  压缩保留：卷积神经网络通过卷积核在局部区域提取特征，特别适 | 思维链提示让模型分步骤推理问题，能显著提高复杂推
         陪跑裁掉：梯度下降通过沿损失函数负梯度方向迭代更新参数，是 | Transformer是2017年提出的基于注意
  Q#10  压缩保留：强化学习通过奖励信号引导智能体在环境中探索并优化 | 元学习的目标是让模型学会学习，在少量样本上快速适
         陪跑裁掉：学习率决定了参数更新的步长，过大导致震荡过小导致 | 批归一化通过在每层对激活值做归一化，加速深度学习
```

三个读数：

1. **压缩率 88.2% 是硬压缩**：614.1 → 72.5 字符/问，100 问总量 61.4k → 7.3k。这就是"生成用精"的 token 账——**生成侧的成本直接缩到 1/8**，而且这个量是"控制总量"出来的（§8.6 的"控制总量≈top-3 相关句"）。
2. **压缩掉的是陪跑，不是答案**（A3 现场）：Q0 问引力波，压缩保留引力波答案行，裁掉的是 Transformer、梯度下降；Q10 问强化学习，裁掉学习率、批归一化。**噪声块在公开处刑**——这正是压缩要干的活。
3. **保留行也能带出强邻**（Q5 保留两行）：卷积答案行 + 思维链提示行。这不是漏网，是"有关插"的证据（§4 B3 详述）——压缩求的是"删干净无关"，不是"只留答案"。

> 一句话：**上下文的 88.2% 是陪跑行，压缩就是把这 88.2% 在进生成前拿掉。成本降 8 倍，答案位不动（A0 与 C1 两条支持率保证）。**

## 4. 实验 B·噪声账：15.5 行陪跑、纯度 0.226→1.000、压不掉的强邻

实验 B 回答"这些 token 到底是什么、删得干不干净"。看 stdout：

```
B1 陪跑行：每问 20 行中「宽松相关行」（≥1 词交叠）均 4.5 行 → 15.5 行无条件陪跑
B2 证据纯度（相关 token / 上下文 token）：RAW 0.226（约 77% 上下文 token 与问题无关）→ 压缩后 1.000（保留即相关，按定义）
   压缩率与纯度一体两面：抽走陪跑行的同时把上下文 token 砍掉 88.2%
B3 强邻入窗：宽松压缩保留的 top-3 里非答案行均 1.4 行（语义近邻，词面也重）——别指望词面压缩把它们挤掉
   Q#01：压缩保留里混入的强邻：量子计算利用量子叠加和纠缠特性，在特定问题上可远超经典计算机
```

三个读数：

1. **B1 陪跑行 15.5/20**：一问 20 行里，只有 4.5 行和问题有任何词面交叠，**15.5 行是无条件陪跑**。这条与 A2 的压缩率互为因果——正因为陪跑占 77%，才压得动 88%。
2. **B2 证据纯度 0.226 → 1.000**：问题相关 token 在原始上下文里只占 **22.6%**，压缩后 100%（保留行按定义就是相关行）。纯度与压缩率是一体两面：**抽走陪跑行的同时砍掉 88.2% 的上下文**。
3. **B3 是诚实的一课：压缩删得掉无关，删不掉"有关"**：压缩保留的 top-3 里，非答案行平均还有 **1.4 行**——它们是语义/词面都近的"强邻"。Q#01 保留行里混进"量子计算……远超经典计算机"，因为它和问题共享词又语义相关。这份"强邻"是**词面压缩的边界**：词面阈值能筛掉空泛句，筛不掉像答案的近邻。剩余这一层要靠 **only-from-evidence + 引用编号**（§8.6）在生成侧兜底——模型若被强邻带偏，答案仍可追溯、可质疑。

> 对照 11 章的 B2：GraphRAG 的"图上未断言噪声 23 条"是**语义近邻进向量袋**的问题；本篇 B3 的"强邻 1.4 行"是**语义近邻进上下文**的问题——机理相同（语义近 ≠ 答案），阵地不同（图断言层 vs 生成输入层）。两篇合起来就是完整的一句话：**距离近不代表答案对，检索管线每一层都要对"近邻"设防。**

## 5. 实验 C·成本账：忠实权衡曲线 + 墙钟 + 生产外推

最后的问题是压缩有没有副作用。看 stdout：

```
C1 忠实权衡曲线（07 章 4-gram 支持率 proxy，答案=gold 行逐字可溯源）：
   全量直喂     ：614.1 字符/问 · 压缩率  0.0% · 答案行支持率 1.000
   宽松相关压缩 ：72.5 字符/问 · 压缩率 88.2% · 答案行支持率 1.000
   严格相关压缩 ：41.0 字符/问 · 压缩率 93.3% · 答案行支持率 0.970   <- 砍过头：3 问答案行一起被砍
   -> 压缩不是免费的：越狠越省 token，但答案行支持率掉（严格档 1.000→0.970）；预算要按答案支撑回调，不是无限压
```

### C1：压缩不是免费的——忠实权衡曲线

沿用 07 章的 4-gram 支持率口径（答案行逐字 4-gram 能否被给定上下文覆盖）画一条权衡曲线：

| 压缩档位 | 每问字符 | 压缩率 | 答案行支持率 |
|---|---|---|---|
| 全量直喂 | 614.1 | 0% | **1.000** |
| 宽松相关压缩（≥1 词交叠，top-3） | 72.5 | 88.2% | **1.000** |
| 严格相关压缩（≥2 词交叠，咔咔到点） | 41.0 | 93.3% | **0.970** |

- **宽松档赚得盆满钵满**：88.2% 省 token 的同时支持率纹丝不动 1.000——因为按 BM25>0 宽松选，答案行永远在窗里（它是与问题相关的行之一）。
- **严格档暴露代价**：想再省 5 个点（93.3%），支持率跌破 1.000 到 **0.970——3 问的答案行因为和问题共享切词不足 2 个，被一起砍了**。压缩率多赚 5 个点，末尾吃掉忠实。

这条曲线的教学意义就是 §17.6.5 那句实践要求的落点："**对 20 个检索块压缩后测忠实度**"——**压缩率要拿"答案支撑率"复盘，不是拿预算表复盘**。生产上调 LLMLingua 的 `ratio` 参数时，每档都要配一版评测集确认答案支持率不掉，否则就是把自己的答案也压掉了。

### C2：压缩器不便宜，但比生成便宜得多

墙钟（stderr `[wall]`，三遍浮动）：

| 打点 | run1（三遍） |
|---|---|
| encode+index | 8.28 s（8.28 / 8.35 / 8.18） |
| compressor 100 问（含每问 dense top + BM25） | 2.454 s（2.454 / 2.480 / 2.533） |
| total（含模型加载 ~9s） | 13.68 s（13.68 / 13.73 / 13.58） |

**100 次查询的压缩一共 ~2.5 秒**——对每次生成来说是一次毫秒级的便宜 pass。对比它省的：**每次生成缩掉的 88.2% token，才是成本的 2 次方**（生成 token 数 × 单价，省在输出端）。

### C3：生产 LLMLingua 的外推账（非本机实测，要素事实）

生产 LLMLingua 把本文的"规则相关句"换成"语言模型逐 token 打困惑度"：模式 = 小模型对上下文每 token 算条件概率，按预算裁掉低分 token，再把保留 token 拼回。相比句级整行压缩，**token 级粒度更细**（可跨句保留片段），成本量级 = **每问一次小模型 forward + 一次 token 重建**。

与 11 章的成本账放一起看：

> **GraphRAG 建图 = 文档 → 实体三元组；Context Compression = 检索结果 → 相关句子。两者都是"生成前花一次便宜 pass，换生成侧更少 token、更少噪声"。** 这也是为什么 §8.14 把"答案与文档矛盾"和"成本暴涨"两行都指向压缩——它同时在可追溯与账本两条线上发力。

## 6. 诚实边界（AAA 自我审查）

以下为本实验的边界，必须诚实交接（对应仓库"每篇带实测量、不吹不黑"的原则）：

- **压缩器是规则替代，不是 LLMLingua**：BM25 相关句整行选取、无 token 级困惑度打分层、无跨句重组。生产 LLMLingua 的机制（语言模型打分）是非本机实测，本篇验证的是**"抽取相关句子 → 降成本降噪声"这一机制层的方向**，不替代对 LLM 压缩器质量的评测。
- **token 估算 = 字符数**：全文的"字符"是 `len()` 粗估的相对账，不是真实 BPE token 数。压缩率是相对量（88.2%），绝对 token 数请用真实 tokenizer 复核。
- **支持率口径是行级/4-gram proxy**：沿用 07 章 proxy（答案行逐字可溯源）；生产请用 RAGAS claims-based 忠实度（07 章 §3.1 的完整版）。
- **本语料的高压缩率来自单主题结构**：陪跑占 77% 是因为 20 篇主题相关短篇本来就有 15.5 行无关。长块、多主题生产语料里陪跑占比会低、压不动这么多——**末位压缩率请在你自己语料上跑，别拿 88.2% 当普适**。
- **强邻 1.4 行是词面压缩的残留**：压缩删得掉无关、删不掉"有关"，剩余强邻靠生成侧约束兜底——本文没有测量"强邻误导生成"的最终概率（那需要真 LLM 生成），只锚定了"强邻确实会被带进来"这一条客观事实。

## 7. 常见坑（5 条）

1. **检索端贪心、生成端也贪心**。k 从 1 加到的 20 很爽（召回上去了），但 20 行原样塞进上下文 = 把成本与噪声一起打包送给生成端。**检索多用、生成用精**是配套动作：加 k 的同时加压缩。
2. **只会"截断"不会"压缩"**。截断（只留前 k 块）丢的是**排在后面的相关证据**；压缩（全量打分后按相关性选）保的是**最相关的句子**。两者预算相同，覆盖的是不同证据——本篇宽松与严格两档就是压缩强度的两个端点。"长上下文能装下，没必要压缩"——装得下的代价是每一次生成的 token 账单和噪声污染。
3. **压缩率只对预算表，不对评测集**。C1 那条权衡曲线就是全部理由：严格档 93.3% 压缩率光鲜，答案行支持率却掉了 3 个点。**每次调压缩率都要用评测集复查忠实度**（07 章"先测张力再上技术"纪律的应用）。
4. **相信词面压缩能把噪声删干净**。B3 的强邻 1.4 行说得很清楚：词面阈值筛不掉语义近邻。压缩器减的是量，**"答案只依据证据 + 引用编号"（§8.6）才是保质量的另一半**，两者缺一不可。
5. **把压缩当终点**。压缩只处理"检索结果进生成前"这一段；它解决不了"检索没召回"（那是 01/03/05 的活）也解决不了"答案要跨多文档综合"（那是 GraphRAG/Agentic 的活）。把它钉在"生成前的一道闸"这个位子上，别让它越位。
