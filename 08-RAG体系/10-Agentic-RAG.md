## 0. 为什么是纸「判断」而不是纸「技术」

先回看 05 章那个把静态管线打回原形的读数（不重复跑，引既有实测）：

- **复合/多跳问题 naive 首屏（Hit@1）只有 2/4**，答案实体（知识蒸馏/注意力机制/联邦学习/卷积核）一个都不出现在问题词面里；
- 但**检索层没崩**（Hit@5 4/4）——目标文档其实都在候选池里；
- 更扎心的是无脑「分解并集」后 H1 反而降到 **1/4**：桥文档（doc[97] 联邦蒸馏、doc[2] Transformer）被并列顶到第一。

05 章得出的结论是：**多跳 = 检索两次 + 判断一次，「判断」那步才是要害**。

这一章就把那个「判断」正式装进管线。注意对比两者的性质差异——静态管线里你只能加技术（Rewrite、分解、HyDE，见 05 选型表），Agentic 管线的对象不是技术清单，而是**决策序列**：

```text
静态： 用户问题 ──固定管线──> 检索一次 ──> 首屏直采 ──> 生成
Agentic：用户问题 → 判断要不要查 ─(不查)→ 直接答（省检索）
                    └(查)──> 检索 → 判断够不够 ─(够)→ 采信生成
                                            └(不够)→ 再查/反思 → 再判断 → 止损
```

Agentic 不是"更聪明的检索"，是**给检索层装了个 LLM 控制器**。这也解释了它为什么被知识地图标为 🔴 掌握：它是 RAG 与 `09-Agent体系`（待开篇）的十字路口，2026 年的 Deep Research 类产品（深度研究代理）本质就是 Agentic RAG 的长跑版。

## 1. 一张图：决策装进哪三步

知识地图 §8.10 把 Agentic RAG 的循环写得很白：

> **将静态管线变成 Agent 决策：判断要不要检索 → 选哪个工具 → 多轮检索/追问 → 评估结果够不够 → 不够再查/反思。**

落到工程实现，就是三个决策点 + 一个止损闸：

```text
┌─────────────────────────────────────────────────────────────┐
│  Agentic 循环（LLM 当控制器，检索/改写/评测当工具）           │
│                                                              │
│  问题 → [决策1] 要不要查？────不查──> 直接生成（省一次检索）   │
│                │ 查                                           │
│                ▼                                              │
│         [选工具] 检索(向量/BM25/Web) → 候选片段                 │
│                │                                              │
│                ▼                                              │
│         [决策2] 够不够？(自评证据是否支撑) ─够──> 采信生成      │
│                │ 不够                                          │
│                ▼                                              │
│         [再查/反思] ↓ 改写查询 / 换工具 / 拆子问 / 批判性复查    │
│                │                                              │
│         ┌──────┴────────┐                                     │
│         │  [止损闸] ≥N 轮仍不够 → 坦率说"没查到"，不硬编       │
│         └────────────────────────────────────────────────────┘
```

- **决策1（要不要查）** 对应 Self-RAG 的 *Retrieve* 反思 token：模型自评"这问库里用得上吗"，用不上就不查。
- **决策2（够不够）** 对应 Self-RAG 的 *Relevant / Support* token 与 CRAG 的检索质量分级（correct / ambiguous / incorrect）：自评证据是否真的支撑答案，不支撑就走再查分支。
- **再查/反思** 对应 CRAG 的纠正分支（精炼重查或换 Web 搜索）与 ReAct 的 *Thought → Action → Observation* 循环。
- **止损闸** 是 Agent 的纪律：轮数上界 + 证据不收敛就**放弃并明说放弃**——比"自信地答错"（05 章那 2 条无声错答）好十个量级。

关键认知：**这三个决策点不是 RAG 之外的新轮子，它们是 05 章所有查询侧技术的调度器**——Rewrite、分解、HyDE 全都还在，只是从"管线里写死的步骤"变成"Agent 判断必要才调用的工具"。

## 2. 三个决策点，每步的账本

正因为 Agentic = 决策，它的成本结构就不再是"一次检索的固定价"，而是一张**分支账单**。每个决策点都同时有收益和代价：

| 决策点 | 收益（什么时候赚） | 代价（什么时候亏） | 典型实现 |
|---|---|---|---|
| **决策1 · 要不要查** | 库外/常识/闲聊题被省掉检索 → 省 token 与延迟 | 误判"不查"漏检（最危险：直接答错）；误判"要查"白检 | Self-RAG Retrieve token；检索相似度阈值 |
| **选工具** | 词面断裂选 BM25/混合、语义选 Dense、实时选 Web，各取所长 | 每多一个候选工具 = 一次额外调用/判断 | ReAct 的 Action 类型；[03 混合检索](03-混合检索与重排.md) |
| **决策2 · 够不够** | 证据不足及时发现 → 再查救回，避免"首屏直采错答案"（05 那 2/4） | 每多一轮 = 再一次检索 + 再一段上下文 token + LLM 再判断的延迟 | Self-RAG Support/Utterance、CRAG 分级、LLM-as-judge |
| **止损闸** | 防止死循环烧 token / 无限重查 | 太早止损会漏掉靠多轮才能找到的答案（W 进 05 教训） | max_iterations + 证据收敛判据 |

一句话：**Agentic 的花钱点就是"判断"本身——每判断一次都要 LLM 看一眼；它值不值，取决于"省掉的错答/白查"比"多付的判断轮次"多多少。** 这正是第 §4 要算的账。

> 位置注记：决策1/2 在文献中常称为 LLM **自反思（self-reflection / critique）**，Self-RAG 2023 把它做成一组分类 token（Retrieve/IsRel/IsSup 等），CRAG 2024 再把"检索质量"显式分级。这一节论文要素均为**知识地图既录的要素事实（非本机实测）**。

### 3.1 决策1：要不要查——judge 先行 vs 无脑每问必检

12 条混合查询 = 8 条「库内」事实题（答案在语料里，必须查）+ 4 条「库外」常识题（如"一年有多少个季度""一公斤等于多少克"，模型直接答，查库纯浪费）。对照两种流水线：

| 流水线 | 检索调用 | 进入上下文字数 | 关键读数 |
|---|---|---|---|
| **无脑·每问必检** | 12（4 次白查） | 370 | 库外 4 条全检索，其中 3 条 top1 完全无关（闲聊常识 top1 sim≈0.41~0.46） |
| **judge·先判断再查**（Dense top1 相似度 >0.50） | 9 | 276 | 省 3 次检索 / 94 字 ≈ **省 25.4%** |

混淆统计（这是最有信息量的一行）：**TP 该查的查 = 8/8 · TN 可省的省 = 3/4 · FP 白查 = 1 · FN 漏检 = 0**。

三个读法：

1. **漏检为 0（FN=0）**：8 条库内题全部正确判定"要查"，这里没漏。这是 judge 型控制器的底线——漏检一次就是一次"明明该查却直接答错"，比白查严重得多。
2. **白查只有 1（FP=1）**："太阳东升西落月亮绕地球转"的 top1 相似度恰为 0.50，卡在阈值边缘被判成"要查"，白付一次检索。**judge 不完美**——阈值切分把边界样本切错一个，真实系统要用"置信区间 + 人类样本校准"来降 FP，而不是假设阈值完美。
3. **节省是分支性的**：省的是"库外用不上"那一路。若业务里 80% 是库内问题，judge 几乎不省钱（全要查）；若一半是闲聊会话，它就是每两问省一问的检索。

### 3.2 决策2：查几轮 / 够不够 → 再查采信——4 条多跳问题

复用 05 章 4 条复合问题（答案实体不出现在问题词面，经桥文档才能定位）。对照 `naive 首屏直采`（1 轮，查完就信 top1）与 `Agentic`（首轮后**自评**：用 LLM 分解出的子问再查一次，与首轮 top1 一致性判定"够不够"，不一致则判断"该再查"）：

| 目标 | 答案实体 | naive top1（=无声错答） | Agentic 采信 | 轮数变化 | 判断理由 |
|---|---|---|---|---|---|
| doc[22] 知识蒸馏 | 让谁模仿谁 | doc[97] **桥文档·联邦蒸馏**（首屏错） | doc[22] ✓ | 1 → 2 | 首轮投桥文档，自评不够 → 子问再查 |
| doc[8] 注意力机制 | 让模型干嘛 | doc[2] **桥文档·Transformer**（首屏错） | doc[8] ✓ | 1 → 2 | 首轮投桥文档，自评不够 → 子问再查 |
| doc[25] 联邦学习 | 靠上传什么 | doc[25] ✓ | doc[25] ✓ | 1 → 1 | 首轮即中，自评够 → 1 轮收手 |
| doc[5] 卷积核 | 靠什么提取 | doc[5] ✓ | doc[5] ✓ | 1 → 1 | 首轮即中，自评够 → 1 轮收手 |
| **聚合** | — | **2/4（2 条无声错答）** | **4/4** | 平均 1.5 轮 | 检索 4 次 → 6 次 |

两个读数：

1. **首轮没崩，是"判断"崩了，然后被判断救回来**：4 条里首轮 top1 有 2 条本来就对（联邦学习、卷积核），**naive 的 H1 是 2/4 不是 0/4**——问题出在另外 2 条：检索结果在第 1 位放的是桥文档，naive 毫不犹豫采信，于是"寻找到的东西对了，答的东西错了"。Agentic 的自评把这 2 条拦下来（首轮与子问重查不一致 → 判断不够），只多花一轮就采信到真正答案。
2. **多付 2 次检索，换回 2 条原本无声错答**——这就是 Agentic 的核心账单：**不是"一定更便宜"，而是"该停的时候停（2 条首轮即中的只查 1 轮）、该补的时候补（2 条被顶位的补一轮）"**。平均 1.5 轮，比无脑每问必检多 2 轮，换来 H1 翻倍。

这个对照和 05 章「分解并集 H1 反而 1/4」放一起读，就是完整的因果链：**分解只拆不聚 → 并集把桥文档顶上来 → 缺的是 Aggregation/判断层；Agentic 的判断层把 1/4 救回 4/4，而它做的恰恰不是"多检索"，是"哪一轮才算数"。**

### 3.3 决策3：止损值不值——无判断盲目加深 vs 及时收手

对照"无判断地把检索深度 k=1..5 一截截放大（Top-k 全量进上下文）"与 Agentic 的判断后采信，测**盲目加深会不会自己撞到终点**：

| 检索深度 k | Hit@k | 累计上下文 | 现象 |
|---|---|---|---|
| k=1 | **2/4** | 135 字 | 首屏直采，2/4 无声错答 |
| k=2 | 4/4 | 261 字 | 命中票满了，但**首屏仍是 top1 那 2/4** |
| k=5 | 4/4 | 622 字 | 每层都白付 130+ 字，命中不再变 |

Agentic 对照：**采信命中 4/4，上下文仅 187 字**——比盲目加深到 k=2（261 字）还省 28%，且采信的就是正确文档而不是"候选池里有"。

结论：**无判断的加深只加 token、不加正确答案位**。k=2 时目标文档已全部进池，但没人告诉生成层"第 1 位是错的桥文档、第 2 位才是答案"——加深逃票，判断才让票数算数。止损闸在这里等价于"证据已收敛（k=2 不再有新命中）就该停下，不把预算烧进 k=3/4/5"。

## 4. 值不值：Agentic 的 ROI 框架

实测三节的数字拆开看每步都合理，但组合起来必须回答工程问题：**平均 1.5 轮、多 2 次检索，值吗？** 这不是"技术先进"能回答的，要量。给出落地判据（对应 [07-RAG评测-RAGAS](07-RAG评测-RAGAS.md) 的"先测张力再上技术"）：

```text
Agentic 净收益 ≈ 靠"判断"救回的错答价值（命中增益+避免的 FA 幻觉成本）
              − 多付的检索轮数 × 本单位检索价（token + 延迟配额）
              − LLM 控制器的判断成本 × 判断次数（每轮判断都要 LLM 看一眼）
```

把实测数字代入这套框架，四类项目各归各队：

| 业务画像 | 值得上 Agentic 吗 | 依据（本仓库实测） |
|---|---|---|
| 多跳/复合/条件查询占比高的知识库 | **强值得** | 多跳 H1 2/4→4/4，救回 2 条无声错答只花 1.5 轮 × 单轮检索价 |
| 大量闲聊/库外会话 | 值得（省检索） | judge 省 25.4% 上下文；但先校准阈值降 FP |
| 单轮事实问答占比 80%+ | **不建议** | 基本没有"判断"发挥的空间，全是决策1 的"必查"分支，白白长延迟 |
| 实时性要求苛刻（每问 ≤300ms） | 谨慎 | 每多一轮判断约等于多一次 LLM + 一次检索的延迟；用 max_tokens/轮数上限锁死 |

还有一条反面纪律：**Agentic 的衡量口径必须看"首屏/采信命中"而不是"池子里有没有"**。本实测里 Hit@2 已经是 4/4 了，但首屏是 2/4——你若用 Hit@5 验收，Agentic 的收益会被判成 0（"反正都找得到"），而用户看到的仍是错答案。**评测指标要贴着"用户拿到的那一版答案"设计（首屏 / 采信文档），不是候选池。**

> AAA 自我审查区（以下为本仓库实验边界，须诚实交接）：
> - 决策1 用相似度阈值替代 LLM Retrieve 判断，决策2 用"子问交叉验证"替代 LLM 自评——本实测验证的是**机制方向有效**，真实 LLM 控制器的判断错误率只会更高（尤其 FP/FN），阈值站点要配校准与回归；
> - token 口径是"字符数粗估"，非真实 BPE token——只做相对账；Agentic 真正的计费还含 LLM 判断的输入 token，比本文展示的纯检索上下文更大；
> - 4 条多跳 + 12 条 mixed 是小样本，方向性演示，不是压测结论。

## 5. 常见坑（5 条）

1. **把 Agentic 当"更强的检索"**。它是"调度检索的控制器"，检索器还是那套（[03 混合检索](03-混合检索与重排.md)）。先确认索引端和检索底座没问题（Recall 崩了 Agent 再会判断也补不回来），再谈上控制器。
2. **用 Hit@k 验收而不看首屏/采信**。本实测两侧 Hit@k 都 4/4，但首屏 2/4——指标贴着"用户拿到的那版答案"设计，否则 Agentic 收益被算成 0。
3. **判断不做校准**。FP 白查只是费钱，**FN 漏检是直接答错**（决策1 的 FN=0 是本实验特意维持的底线）；上生产前必须在真实问题上采 judge 的混淆矩阵，FN 压到接近 0 再放行。
4. **没有止损闸**。不设轮数上界 + 收敛判据，复杂问题会把预算烧进死循环；本实测 k≥2 后命中不再增长，正是"该停的信号"，闸要接这个信号。
5. **把 Agentic 当前置必配**。单人知识问答的 RAG 未必需要控制器——**先测张力再上技术**（[07-RAG评测](07-RAG评测-RAGAS.md) 的判别性对照）:多跳/库外会话占比高才值得那平均 1.5 轮。
