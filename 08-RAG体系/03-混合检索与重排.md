## 0. 上一章没解决的问题

[01-Embedding与检索基础.md](01-Embedding与检索基础.md) 讲了 BM25 与稠密检索"各擅胜场"。但它们有一个共同缺陷：**是两套独立的排序器，各自对一批文档排序，而生产环境必须给 Reader（生成器）一个统一、可靠的 Top-k。**

这里有两层问题：

```
第 1 层 融合：BM25 说 A 第一、Dense 说 C 第一——到底听谁的？
第 2 层 精排：第一轮粗召回了 top-100，能不能把最相关的 5 条挤到最前面？
```

**数据层面的证据**（本章在 009 语料上实测，100 问）：BM25 与 Dense 各自 Hit@5 都是 1.0000，看似"谁都行"——但**两路 top-5 平均重合率只有 0.40**，也就是说它们在 60% 的位次上选的是**不同文档**：

```
两路 top-5 平均重合率 = 0.40   → 两路是真正意义的互补（选法分歧大），不是复读机
两路 top-1 一致率     = 0.96   → 但谁是第一，两路高度一致
```

这个组合很常见：**两路在"谁最好"上共识度高，在"谁次好/该不该进袋"上分歧大**。混合的意义正是把这些分歧的候选并进袋里，扩大 Hit@k 的上限。

## 1. 融合第一路：分数派（加权）与排名派（RRF）

把两路检索结果合成一路，有两条主流路线：

| 流派 | 思路 | 是否需要归一化 | 调参 |
|---|---|---|---|
| **分数派**（Score-based） | 两路各自归一化分数 → 加权求和 | **必须**（BM25 分数几十、余弦 0~1，不能直接加） | 需要调 α |
| **排名派**（Rank-based / RRF） | 只看"排第几"，用排名倒数求和 | **不需要**（排名无单位） | 一个固定 k |

> 一句话选型：图省事/多路来源 → **RRF**；想精细控制两路权重 → **加权融合**。生产上两者都有人用，RRF 因为不依赖分数尺度、加第三第四路不用重调，越来越主流。

## 2. min-max 归一 + 加权融合

090 notebook 用的就是这条路。做法三步：

```
① 把每路的分数做 min-max 归一化到 [0, 1]：   s' = (s - min) / (max - min)
② 每路 top-k 各自合并进同一个 dict（按 doc id）
③ 加权求和：  score_final(d) = α·s'_bm25(d) + (1-α)·s'_dense(d)
④ 按最终分数排序取 top-n
```

对应代码（009 内 Hybrid 一节的简化版）：

```python
def nn(xs):                                    # min-max 归一
    a = np.array([s for s, _ in xs], dtype=float)
    r = a.max() - a.min()
    if r == 0:
        return [(1.0, i) for _, i in xs]
    return [((s - a.min()) / r, i) for s, i in xs]

def hybrid(bm25_hits, dense_hits, alpha=0.5, n=5):
    merged = {}
    for s, i in nn(bm25_hits):
        merged[i] = merged.get(i, 0.0) + alpha * s
    for s, i in nn(dense_hits):
        merged[i] = merged.get(i, 0.0) + (1 - alpha) * s
    return [i for i, _ in sorted(merged.items(), key=lambda kv: -kv[1])][:n]
```

**α 怎么理解**：α 靠近 1 偏向词法（专名、术语越多越该偏），靠近 0 偏向语义。经验值 0.5 在中文语料上稳健；正式项目请在你自己的评测集上扫一遍 α ∈ {0.3, 0.5, 0.7}。

## 3. RRF 排名融合：不调参的稳健选择

RRF（Reciprocal Rank Fusion）来自 2009 年一篇信息检索论文，公式简单到不可思议：

```
score_final(d) = Σ_{检索路 L}  1 / (k + rank_L(d))

k 常规取 60（可当常数用）
```

**只给"这条 doc 在这路排第几"，完全无视分数本身**。所以 BM25 的 23.5 分和余弦的 0.81 根本不需要对齐，来几路都不怕。

**手算一次**（两条路，各 4 条，k=60）：

```
BM25  排序:  A(1)  B(2)  C(3)  D(4)
Dense 排序:  C(1)  E(2)  F(3)  A(4)

A: 1/61 + 1/64 = 0.0320
B: 1/62         = 0.0161
C: 1/63 + 1/61 = 0.0323   ← C 胜出
...
```

看起来 BM25 把 C 排第三，但因为 Dense 把它排第一，**两路都上榜的候选拿到了双重倒数票，C 反超 A**——这就是排名融合"让大家都认的文档出头"的机制。注意到 `k` 越大，位次差异带来的分数差异越小（更接近平均主义）；k=60 是论文与社区广泛使用的值。

实现（纯 Python，无依赖）：

```python
def rrf(ranked_lists, k=60, n=5):
    merged = {}
    for lst in ranked_lists:                  # lst = [(score, doc_id), ...]，只用 doc_id 与位次
        for rank, (_, doc_id) in enumerate(lst, 1):
            merged[doc_id] = merged.get(doc_id, 0.0) + 1.0 / (k + rank)
    return [i for i, _ in sorted(merged.items(), key=lambda kv: -kv[1])][:n]

# 用法：rrf([bm25_hits, dense_hits])
```

**它的升级版**：RAG-Fusion（2023）把"单问题多路检索"升级为"一个问题拆成多个子查询各自检索，再 RRF 融合"——融合的对象从「检索方式」变成「查询方式」，公式一模一样。

## 4. 重排（Rerank）：RAG 质量提升最划算的一步

融合解决"袋子里有什么"，**重排解决"袋子里谁在前"**。这一步由 Reranker 完成，它和上一章的检索模型是**两种不同的架构**：

| | Bi-encoder（检索用） | Cross-encoder（重排用） |
|---|---|---|
| 输入 | query 编码一次，doc 独立编码 | `"[CLS] query [SEP] doc [SEP]"` 拼接后整体再过 Transformer |
| Qt | query 与 doc **无交互**，向量化后靠余弦 | query 与 doc **全交互**（自注意力看得到二者关系） |
| 精度 | 中 | **高**（Reranker 系最强的那档） |
| 速度 | query 一次编码 + 全库近邻，秒级 | **每个候选项一次前向**，O(k) 次（k=候选数） |
| 用在哪 | 全库粗召回（top-100） | 对 top-100 精排取 top-5 |

> **为什么说这是"最划算一步"**：Reranker 不用改索引、不用调融合参数，**只把交叉编码器套在粗召回结果上**，通常就能显著提升最终 Hit@k 排序质量。代价是每个候选都要过一遍模型——所以**永远只重排粗召回的 top-100，不要当全库检索器用**。

**ColBERT / Late Interaction（晚期交互）**：它是介于两者之间的折中——query 与 doc 各自编码成 `逐 token 向量序列`，再对每个 query token 找 doc 里最像的 token 求和（`Sum(maxsim)`）。比 cross-encoder 快、比纯 bi-encoder 准，常被直接当作"召回+精排一体"的模型或在二级精排中使用。

**中文 Reranker 选型**：

| 模型 | 特点 |
|---|---|
| `BAAI/bge-reranker-base` / `bge-reranker-v2-m3` | 中文事实标准；v2-m3 多语言 |
| `Jina Reranker` / `Cohere Rerank`（API） | 免运维，多语 |
| `MonoT5` / `MonoBERT` | 英文强、研究者常用 |
| ColBERT-v2 | Late Interaction 代表 |

**入选格式注意**：Cross-encoder 的输入顺序是 `(query, document)`，有的版本（如 bge-reranker）推荐 `"query 寻处理的问题 [SEP] 文档"` 式的拼接；丢了这个格式，分数会整体漂移（与 01 章「query 指令前缀」同类的坑）。

## 5. 怎么跑：009 的 Hybrid 一节 + 本章实测数字

[notebook 009](../code/notebooks/009-中文RAG全管线.ipynb) 第 6 节就是一次完整的**融合实测**（min-max + α=0.5），第 5 节给出单路基线。跑完输出四行：

```
=== 检索 Hit@5 基线（测试集 100 条） ===
BM25   Hit@5: 1.0000
Dense  Hit@5: 1.0000
Hybrid Hit@5: 1.0000（min-max 融合 alpha=0.5）
```

本章另外跑了 RRF 对照并获得**相同的实测证据**：

```
BM25   Hit@5 = 1.0000     Dense Hit@5 = 1.0000
min-max(α=0.5) Hit@5 = 1.0000     RRF(k=60) Hit@5 = 1.0000
两路 top-5 平均重合率 = 0.400  │  两路 top-1 一致率 = 0.960
```

**该怎么读这些数字（关键，别误读）**：

1. 这个语料 100 条知识点了很容易，**任何合格检索器都能全中**——所以混合/RRF 的收益在这张表里是「不降分」，而不是「涨分」。
2. 但它确凿证明了**机制在工作**：两路选了 60% 不同的文档，融合后依然全对 = 融合**吞掉了分歧**。
3. 真实验收混合的价值，要换**有干扰项的生产语料**：正确答案不止一条相关文档、存在长尾专名、query 有口语化改写——那时单路 `Hit@5≈0.8`、融合升到 `0.9+` 才是混合的回报（参见第 6 节怎么造这样的测试集）。

想跑 RRF 对照：在 009 的 notebook 里把 `hybrid()` 换成上面的 `rrf()` 函数即可，输入就是它俩各自的 hits 列表。

## 6. 评测/验证：混合与重排值不值

**第一步：造一张"有张力"的检索评测集**（比 009 更难一档）：

- 50–200 条**生产真实问题**，每条标注 `gold 文档 id`；
- 故意混入**相似但不正确**的干扰文档（同主题不同结论）；
- 保留专有名词/英文型号/口语改写，至少 1/3 在语义模型与词法模型上**意见相左**。

**第二步：三行对比表**（在完全相同的数据、索引上跑）：

```
                    Hit@5    MRR@10
BM25（单路）
Dense（单路）
Hybrid（min-max/α=0.5）
Hybrid（RRF）
Hybrid + Reranker（top-100 → cross-encoder → top-5）
```

**第三步：怎么判断迭代方向**：

- `混合比两路单路都好`（通常在 0.05 以上）→ 融合是值的，往重排走；
- `仅其中一路明显更差` → 排查那一路（分词/embedding 模型），别急着加第二路；
- `加了 Reranker 没提升` → 看 MRR 而非 Hit@k：重排主要改善的是**排序位置**（MRR/nDCG），Hit@k 可能已到顶；
- 任何改动都要看 **p95 延迟 + 成本**：Reranker 每 query 多 ~k 次模型前向，别让收益被延迟吃掉。

## 7. 常见坑（6 条）

1. **两路分数直接相加**：BM25 是几十到几百分、余弦是 0~1，直接加权 = 让 BM25 当裁判。**要么归一化，要么改用 RRF。**
2. **α 推到 0.05 / 0.95**：等于退化成单路。α 要扫，但别把它当救火。
3. **RRF 的 k 乱给**：k=60 是社区惯例，k 过小（<10）会把"只在一路里排第 1"的文档权重抬得过高，产生噪声。
4. **把 Reranker 当全库检索器**：交叉编码器对每个候选都要做一次前向，全库用 = 延迟爆炸。**先用 bi-encoder/BM25 粗召回 top-100，再重排。**
5. **中英文模型错配**：bge-reranker 排中文常用，但拿英文预训练的小 reranker 排中文 = 分数失真。重排模型的领域/语言要和语料对齐。
6. **查询时临时补算 embedding / 索引**：索引（embedding + 倒排）必须在**索引端**建好并做增量更新，查询只读索引。否则每次查询都重新编码全库，成本与延迟失控。
