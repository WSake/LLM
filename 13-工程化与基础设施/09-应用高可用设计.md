## 0. 为什么第 9 课是「大模型应用高可用设计」？

前八课的叙事是"把系统造出来、跑起来、管起来"：

| 课 | 回答的问题 | 交付物 |
|---|---|---|
| 01 算力账 | 卡怎么选？ | 显存/带宽/算力/选型四本账 |
| 02 分布式训练 | 多机怎么连？ | 通信账单 + 拓扑判断 |
| 03 推理服务 | 从裸机到可上线？ | 装配五环 + 副本/灰度/计费 |
| 04 Ray | 任务级调度怎么加？ | 三原语 + 墙钟账 |
| 05 MLOps | 模型怎么被管理？ | CI/CD + 数据飞轮 |
| 06 模型注册 | 版本怎么被引用？ | 7 件套 + 发布策略 |
| 07 可观测 | 线上怎么看见？ | 指标/日志/追踪/告警一条链 |
| 08 API 网关 | 流量怎么进服务？ | 六功能一条受理链 |

到这，系统已经"能跑、能管、能看"。但还剩最后一个问题：**灾难真的来的时候，会不会死？** 这恰恰是工程化三主线（资源/流程/观测）之外最容易漏的一环——大家都搭好了"正常路径"，却没人演练"故障路径"。

**垃圾 vs 高可用的分界线**：报告里写"我们发布很规范"是在答"流程"；只有当你回答得出"OpenAI 挂了怎么办""GPU 掉了一张怎么办""用户把上下文塞爆了怎么办""账单翻了三倍怎么办"——四件事各有预案、且预案的成本算得清——才叫有高可用设计。

所以这一课：**把"灾难"列成账本（四类 × 每类配套应对），把"活着"算成数字（回退兑付率 / 降级省比 / 闸线触发日）。** 承接 13-08：网关管"单请求失败"，本篇管"整站灾难"——网关是第 1 层，高可用是最后防线。

## 1. 先把高可用拆开：四类灾难 × 五件设计的坐标（§13.9）

§13.9 给的不是长篇清单，而是一个极干净的框架：**灾难四类，应对五件**。先背坐标，再补肌肉。

**四类灾难（这是"会不会死"的四个死法）：**

| # | 灾难 | 一句话 | 判死特征（这么认脸） |
|---|---|---|---|
| 1 | API 厂商故障 | 你依赖的第三方模型供应商挂了 | 连续 5xx / 网关挂起；时延膨胀 10× 不回落 |
| 2 | GPU 损坏 | 你的算力硬件掉了 | ECC 报错 + 掉卡；重启后显存减半 |
| 3 | 上下文溢出 | 输入/状态超出模型窗口 | max_len 截尾；KV 分配 OOM |
| 4 | 成本爆炸 | 账单不受控地冲顶 | 周环比 +24%；思考档输出翻倍超预算 |

**五件应对设计（"会不会死"的五个续命药）：**

| # | 设计 | 一句话 | 挂靠（只引不重测） |
|---|---|---|---|
| 1 | 多供应商回退 | OpenAI → 自托管 → 规则兜底 | 13-08 提供商优先级 |
| 2 | 降级 | 强模型 → 轻模型 → 规则 | 11-08 三档单价 |
| 3 | 限额 | 单用户 token 上限 | 13-08 配额/429 |
| 4 | 超时与重试退避 | 重试 ≤3 · 指数退避 | 06-01 wait=[0.5,1,2,4] |
| 5 | 缓存 | prompt 缓存免 prefill | 13-08 命中走 KV |

> 关键区别（本篇的"为什么不是上一课的重复"）：**13-08 网关解决"单次请求的失败"（认证拒、限流 429、熔断跳闸）——请求维度；本篇解决"整个服务的灾难"（供应商/算力/预算整个垮掉）——服务维度。** 网关的熔断是"快速失败不浪费上游"，高可用的回退是"换个供应商继续服务"：前者保单请求，后者保整站。

## 2. 把高可用降维成本机测量（探针设计：四本账）

高可用听起来像"要看真实的服务器/多区域/混沌工程"——但教学目的只需要"把原理讲透 + 数字落表"。所以探针 `ha_design_demo.py` 用纯 stdlib 把四件事测出来：

| 账 | 问 | 怎么答（确定性仿真） |
|---|---|---|
| A | 认脸：灾难怎么归类？ | 四类灾难字典 + 8 条信号×归类 + 处置映射 + 五件设计 |
| B | 续命：回退/降级怎么省？ | 确定性故障注入 {1,4,6}/{6}；降级梯 75/20/5 分派 |
| C | 兜住：限额/溢出怎么挡？ | 三用户用量表→三档判定；20k 输入对 8k 窗口三策略 |

全程无网络、无随机、无第三方：故障注入是**确定性 index 集**，不是随机数。三条独立进程逐字节恒一（md5 `334cf85f…`），任何一步出错立即 assert 暴露。

## 3. 实验 A · 灾难识别账：先认脸，再动手

**一句话：高可用第一件事不是加服务器，是"把灾难列成清单"——认不出脸，预案就无从谈起。**

运行结果：
```
A1 四类灾难（§13.9）：api_failure, cost_blowout, ctx_overflow, gpu_loss
A2 8 条信号归类（5xx→厂商 / ECC→GPU / 截尾→溢出 / 超预算→成本）: 8/8 命中
A3 四类灾难各挂一件设计：回退→厂商 / 降级→GPU / 限额→溢出 / 预算闸→成本 : True
A4 设计五件套（§13.9）：多供应商回退 · 降级 · 限额 · 超时与重试退避 · 缓存
```

**A1 四类灾难归位 4/4**——把 §13.9 的四类灾难建字典，断言有且只有四类。这步的反而是全文最重要：**灾难清单是"已知风险清单"，写下来才谈得上应对**（对应 §12 威胁建模、09 章 Agent 安全——同样是先列威胁再看护栏）。

**A2 信号→灾难 8/8**——这是"认脸"的实操：给一条症状，归到对的灾难类。8 条信号两两一组，同类的两条是"物理级/服务级"两个侧面：

- 5xx + 时延膨胀 → **厂商故障**（依赖方出事，信号在外侧）
- ECC 报错 + 显存减半 → **GPU 损坏**（硬件出事，信号在主机上）
- 截尾 + KV OOM → **上下文溢出**（数据太大，信号在请求尺寸）
- 周环比 +24% + 思考档超预算 → **成本爆炸**（账单太大，信号在财务）

> 教学点：**同样一个网关 429，到底是"限流正常拒绝"（13-08 账 C）还是"上游厂商挂了"（本篇）？** 区别在持续性和量级：单请求 429 是配额，全网 5xx + 时延与账单同步恶化才是灾难。

**A3/A4 处置映射 + 五件设计**——每类灾难挂一件主设计（回退→厂商 / 降级→GPU / 限额→溢出 / 预算闸→成本），五件设计全验证。这张映射表就是高可用的"预案索引"：**它把四张"会死的脸"和五件"续命药"钉在一张表上，运维值班时先看脸再拿药。**

## 4. 实验 B · 回退与降级账：一条请求怎么活下来

**一句话：单点永远会挂，回退链是"保险"，降级梯是"省钱但保活"。**

运行结果：
```
B1 故障注入：openai 挂 3 次（其中 1 次 selfhosted 也挂）→ 10 请求全部兑付
   （openai 7 · selfhosted 2 · rules 1），单点 openai 只剩 7/10
B2 降级梯 75 强+20 轻+5 规则：全强 $0.42 → 分派 $0.32 = 省 $0.10 (-24%)
   质量加权 0.949 ≥ 0.90（降级省预算，可用性不塌）: True
```

**B1 多供应商回退 10/10 vs 单点 7/10**——确定性故障注入：请求 1/4/6 时 openai 挂掉（3/10），其中请求 6 连自托管也挂（1/10）。结果：

- 单点 openai：只兑付 7/10
- 加了回退链 [openai→自托管→rules]：**10/10 全兑付**（openai 7 次直接成功 → 2 次落到自托管 → 1 次双故障兜到底层规则）

**教学数字**：回退链多花的"配置成本"是零（就是链上一个箭头），换来的是 3 个不该死的请求活了下来。这就是"保险"的数学：**你付的不是保险费，是"先把供应商列表写出来"的一行配置。**

**B2 降级梯省 24% 且质量不塌**——降级的场景是"不出灾难，但预算紧张"：把 100 个请求从全走强模型，改成 75 强 + 20 轻 + 5 规则（触发条件=耗时超阈值/预算水位高）：

| 方案 | 成本 | 质量加权 |
|---|---|---|
| 全强 | $0.42 | 0.75×0.98 + 0.20×0.98 + 0.05×0.98 = 0.98 |
| 降级梯 | $0.32（省 24%） | **0.949**（强 0.98·轻 0.92·规则 0.60 加权） |

省了 24% 的钱，质量只从 0.98 掉到 0.949——**降级的正确姿势是"该重的重、该轻的轻"，不是一刀切全降**（78 个可简单请求让轻模型答，只有 5 个最难的掉给规则兜底，典型 QPS 平滑期质量无感知）。

> 联动：降级梯的三档单价 $0.0042/$0.00037/$0 与思考档放大 = **11-08 只引不重测**；回退链的"优先顺序 + 兜底"结构 = **13-08 提供商优先级只引**。

## 5. 实验 C · 限额与溢出账：把"爆"挡在账上

**一句话：限额不是"拒绝用户"，是三档闸（放行/预警/拒）逐级收口；上下文溢出不是一次失败，是三档取舍。**

运行结果：
```
C1 单用户日上限 100000 token：alice 87k→ok · bob 96k→warn · carol 102k→block
C2 20k 长输入对 8k 窗口（溢出）：截断召回 0.33 不花成本 → 摘要 0.67 → 换长窗 1.00 成本 ×8.0
```

**C1 限额三档闸** ——单用户 token 日上限 100000，三个用户的用量给出三种语义不同的处置：

| 用户 | 用量 | 判定 | 处置 |
|---|---|---|---|
| alice | 87k（<90%） | ok | 正常放行 |
| bob | 96k（≥90%） | warn | 预警：降速（停思考档/排队） |
| carol | 102k（≥100%） | block | 拒绝（限额=硬边界，拒绝不是排队） |

**教学点**：限额如果只做"一刀切拒绝"，用户体验最差；**三档闸把"限制"变成"逐步收口"**——先预警让用户知难而退，最后才硬拒。限额的语义承接 13-08 的 429：**拒绝不是排队，但预警给了用户选择权**。

**C2 上下文溢出三策略**——一条 20k 长输入撞上 8k 窗口（溢出故障），有三种解法，**没有一个绝对优**：

| 策略 | 召回 | 成本 |
|---|---|---|
| 截断尾部 | 0.33 | $0（丢关键信息） |
| 分段/摘要 | 0.67 | 原文成本（保留主体） |
| 换 128k 长窗 | 1.00 | ×8.0（窗口越贵越全） |

**教学点**：上下文溢出（账 A 灾难 #3）第一次出现时，工程师常陷入"无解"（max_len 是死的）。但高可用设计里它是**三档取舍**：缺钱→截断，缺质量→长窗，折中→摘要。**胜负手是"在成本与召回之间找到你的档位"，而不是哀嚎"窗口不够大"。**

> 联动：限额的 429 硬拒语义 = **13-08 账 C 只引**；上下文长度/KV 显存 = **02-10/02-17 只引**；换长窗成本 ×8.0 = **作者教学数（真实成本取决于具体窗口与计费）**。

## 6. 实验 D · 成本爆炸防波堤账：预算闸四线

**一句话：成本爆炸不是"命运",是"缺一道闸"——闸线越级越狠（告警→停思考→降级→熔断），账单就压得住。**

运行结果：
```
D1 无护栏 10 日 $630 → 预算闸后 $315 = 省 $315 (-50%)
D2 预算闸四线触发日：80%→天1 · 90%→天2 · 100%→天3 · 120%→天5
   动作=告警 / 停思考档 / 降级轻模型 / 熔断（13-07 告警线动作同构只引）
```

**D1 无护栏 vs 有护栏，$630→$315 省一半** ——确定性账单：无护栏 10 日实际支出 **40/45/50/55/60/65/70/75/80/90**（思考档占比逐日升高，账单加速上冲）→ 累计 $630。

加入**预算闸四线**（日预算 $50）：

| 闸线 | 水位 | 动作 | 触发日 |
|---|---|---|---|
| 1 | 80%=$40 | 告警（邮件+降速） | 第 1 天 |
| 2 | 90%=$45 | 停思考档 | 第 2 天 |
| 3 | 100%=$50 | 降级轻模型 | 第 3 天 |
| 4 | 120%=$60 | 熔断非关键流量 | 第 5 天 |

执行后：day1-3 原样（40/45/50）→ day4 起降级轻模型（30/天）→ day5 熔断（0）→ day6-10 恢复（30/天）= 累计 $315，**省 $315 = 50%**。

**教学点**：成本爆炸（账 A 灾难 #4）是四类里最隐蔽的——硬件故障会叫（亮红灯），成本爆炸是"悄悄拱顶"。所以 D 账演示的是**自动化闸线而不是人工盯账单**：四线动作与 13-07 告警四线同构（扩容/回滚/缓存/降档），越往上是"提醒型"，越往下是"断臂型"。**第 5 天那刀最狠（熔断）——但正因为前 3 线逐级警告，熔断才显得"有备而来"，而不是"突然切断"。**

> 联动：周环比 +20% 告警线 = **13-05 只引**；成本单价/思考档放大 = **11-08 只引**；告警四线动作 = **13-07 只引**；缓存省 prefill = **13-08 只引**（成本爆炸的慢性解药在缓存，急性闸线在预算）。

## 8. 常见坑（高可用的 8 个）

1. **把高可用当"不出事"**——高可用的前提是**认命灾难会发生**，然后配预案；"我们很稳"不是高可用。
2. **只做回退不做降级**——厂商不挂但预算紧张时，回退链用不上；降级梯才是"平时省钱"的那一手（B2 省 24%）。
3. **降级一刀切**——全降=质量全塌；正确的做法是分派（75/20/5），该重的重、该轻的轻。
4. **限额只做拒绝**——没有预警档（warn），用户被直接 429；三档闸给缓冲与选择权。
5. **溢出只有"换大窗"**——直接换 128k ×8 成本；截断/摘要先救急，钱花在刀刃上（C2）。
6. **预算靠人工盯**——成本爆炸是"悄悄拱顶"，必须自动化闸线（D2 四线动作，越级越狠）。
7. **把网关熔断当灾难兜底**——网关熔断是"单请求快速失败"，不处理"整个厂商挂了换一个"；两件事是两层。
8. **预案写成文档不演练**——写了不用=没有；探针的可复现数字（10 判全 PASS）就是"演练的最小单元"。
