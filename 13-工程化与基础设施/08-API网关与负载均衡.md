## 0. 为什么第 8 课是「API 网关与负载均衡」？

13 章主线是"资源怎么分、模型怎么上线"：13-01 选卡、13-02 多机互联、13-03 **把推理服务装配到可上线（五环图里第二环就叫 API 网关）**、13-04 Ray 弹性、13-05 MLOps 管生命周期、13-06 版本管理、13-07 可观测。但前七篇有个画面一直是"示意图"：**所有请求进门的那道闸**。13-03 的装配图是 `Client→API 网关→K8s Service→Pod(vLLM)→GPU`——网关挂着名字，六种能力却一笔带过。§13.8 就是"这道门到底干什么"。三个非讲不可的理由：

1. **它是 13-03 装配链的第二环，也是唯一"多模型多版本"收口的地方。** 你的服务上线后要接的不止一个模型实例：qwen-7b 有 v9/v10 两个版本在灰度、qwen-chat 可能同时路由到内网镜像/云主/备厂商。**每一台上游都对着网关，客户端只对网关说话**——"多模型多版本"这句话 13-06 在版本侧讲过，本篇是它在流量侧的兑现。
2. **六功能不是六个插件，是一条有先后顺序的受理链。** 认证不先走，伪造请求就占 token；限流不走在转发前，超配额就烧钱；熔断不走在缓存后，雪崩就传染上游。§13.8 把六件东西列成"功能"，本篇把它们排成"执行顺序"——**顺序本身就是工程**。
3. **它把前几篇的部署动作全部接到流量侧。** 13-06 的回滚是"改引用"，本篇讲这个引用落在路由表的哪一行；13-03 的令牌桶是"网关内限流"一笔带过，本篇讲 per-user 配额怎么算、超发怎么办；13-07 的告警是"发现"，本篇讲熔断/限流本身就是**发现问题后的第一动作**。**网关是部署策略（13-06）、配额（13-03）、告警动作线（13-07）三者的执行点。**

**读完这篇你会：（a）背出 §13.8 六功能并按顺序排一条受理链：认证→路由→限流→熔断→缓存→计费，讲清"认证先行零成本、缓存命中才省钱"（账 A）；（b）写一张版本路由表，讲清多厂商/多版本怎么选路、金丝雀 95/5 怎么切、回滚怎么改一行，并会画 round-robin 的均匀分发（账 B）；（c）讲清"配额≠速率"：per-user RPM 是会计上限、超发 429 硬拒（拒绝不是排队），并连接 13-03 的突发桶（账 C）；（d）画出熔断三态（Closed→Open→Half-Open）并讲清 Open 期快速失败=网关的刹车、重试 ≤3 次就放弃（账 D）。（本篇 🟢 掌握模式 = 13-08 API 网关与负载均衡——联动 13-03·13-06·13-07·13-05·13-04·11-08·06-01，无专属里程碑。）**

## 1. 先把网关拆开：一个入口 + 六功能一条受理链（§13.8）

§13.8 知识地图原文两行，正好一张图拆成**六功能一条链**：

| §13.8 原文 | 拆到哪本账 | 受理链上的位置 | 回答的问题 |
|---|---|---|---|
| **认证鉴权** | 账 A | ① 最先 | 你是谁？凭证没过直接 401，**不占上游资源** |
| **路由（多模型多版本）** | 账 B | ② 选路 | qwen-7b/9 还是 qwen-7b/10？走内网镜像还是云主？ |
| **限流配额** | 账 C | ③ 把关 | 你这个用户今天/这分钟能用多少？超了 429 硬拒 |
| **重试熔断** | 账 D | ④ 刹车 | 上游在抖/在挂，网关拦在悲剧前（快速失败） |
| **缓存（prompt 缓存：相同前缀命中走 KV cache）** | 账 A | ⑤ 抄近道 | 相同前缀命中 → 免 prefill → 只付输出钱 |

## 3. 实验 A · 受理流水账：六功能一条链——认证先行 + 缓存命中省钱

**账 A 回答"§13.8 六功能在生产上按什么顺序跑、怎么省钱"。探针把一次请求放进网关六关，逐步留痕：**

**A1 六功能归位（探针实测 6/6）：认证鉴权 · 路由 · 限流配额 · 重试熔断 · 计费计量 · 缓存——§13.8 原文六件全落位，一个不少。** 六个词不是并列清单，是**依次响应的六个开关**。

**A2 一次请求穿六关（探针实测）：`auth → route → ratelimit → circuit → cache → bill` 顺序自洽。** 顺序为什么不能乱？（a）认证必须最先——**凭据错了连路由都不该做，骗子别想进内网**；（b）限流在转发前——超配的请求在进入上游之前就被拒掉，不占 GPU；（c）计费在最后——钱在服务落地后才记（缓存命中也记，只是记得少，见 A5）。

**A3 认证先行·零成本（探针实测）：未认证请求 → 返回码 `401` · 计费 `$0.0`。** 这是账 A 最想让你带走的一格：**门卫在门口就把骗子拦了，一次 token 都不花。** 对照 A4：认证通过 → `200` · 计费 `$0.005`。一个 401 一个 $0.005，差的就是"认证先行"这格账。

**A4 计费计量（探针实测）：单请求 1000 入 + 250 出 = `$0.005`（13-03 账 D4 同式只引，输入 $2.5/M·输出 $10/M·输出 ×4 价）。** 网关把每一次调用记到租户名下——**计费计量 = 记账，不是收钱，是"每个入口的每笔钱去哪了"的可审计账本**（13-05 的成本管理就落在这里）。

**A5 prompt 缓存（探针实测）：60% 请求前缀命中 → 走 KV cache，免 prefill——命中只计输出 250 tok × $10/M = `$0.0025`，未命中 40 请求全价 `$0.005`。100 请求总账 `$0.35` vs 无缓存 `$0.50` = 省 `$0.15`（**-30%**）。** **缓存省的是 prefill 那段**：命中相同前缀（如长 system prompt / 检索上下文），输入部分不用重新算 KV（13-03 前缀亲和 3.0× 的流量面落地件）——**命中率 60% 来自"前缀复用度"，真实业务取决于 prompt 有没有共同的头部；能复用的业务，网关自动把 prefill 的价钱砍掉。** 六功能里"缓存"是唯一一个直接改变成本的（把 $0.50 变成 $0.35）。

## 4. 实验 B · 路由与负载均衡账：多模型多版本——表/金丝雀/回滚/轮询

**账 B 回答"§13.8 路由——多模型多版本怎么决定一次请求去哪台上游"。探针把路由拆成四格：**

**B1 多厂商选路（探针实测）：`qwen-chat` → provider 优先级 `[内网镜像→云主→备]` 命中 `pri_q`。** §13.8 说 LiteLLM 这类是"统一多厂商 API 代理"——**同一模型名可以同时接 3 个厂商，按可用性/价格/区域排序**（内网镜像便宜又合规，13-06 的镜像常态；它挂了自动掉到云主，再掉备）。多厂商路由是"多模型多版本"的横向扩展。

**B2 版本路由表（探针实测 4/4）：`qwen-7b/9 → upstream_v9` · `qwen-7b/10 → upstream_v10` · `qwen-chat/9 → svc_black` · `qwen-chat/10 → svc_lark`——2 模型 × 2 版本一张表。** 这句是 13-06 的兑现：**13-06 的版本是"注册中心里的一行"，这里它是"路由表里的一行"**——`model` 名是固定的（客户端只报 qwen-7b/9），真正去哪个 upstream 由表决定。**灰度与回滚都是改表：v10 可以只吃 5% 流量（B3），出了问题把 qwen-7b/9 的引用改回 upstream_v9 即 2 步（13-06 蓝绿同动作只引）。**

**B3 金丝雀 95/5（探针实测）：100 次路由 → 主 v9 `95` 次 · 新 v10 `5` 次。** 发布策略里的"灰度"在网关上的长相就是**一个权重（95:5）**——不需要动应用代码，只要改路由权重。13-05 的"5% 灰度放行"、13-06 的"金丝雀逐步 8→20→50→100"，执行点都在这一格。

**B4 负载均衡（探针实测）：round-robin 30 请求 → 3 副本各 `10/10/10`。** 均匀分发的前提是**无会话粘性**（13-03 只引：KV 随请求生灭，副本无状态）——**无状态才能随便轮，有状态就只能粘住一台，那 HPA 横扩就没意义了。** 网关把流量摊平，K8s/HPA 的副本才真均匀受力（13-03 账 C）。

## 5. 实验 C · 限流配额账：per-user 配额——超发 429 硬拒

**账 C 回答"§13.8 限流配额——每个用户能用多少、超了怎么办"。探针用三租户把配额语义算清楚：**

**C1 三租户配额（探针实测）：`free 10 RPM · basic 50 · pro 200`，各连打 100 请求 → 拒绝 `{'free': 90, 'basic': 50, 'pro': 0}`。** **配额是 per-user（每用户/每租户）的会计上限，不是全站总速率**——free 用户第 11 发就不给了，pro 打 100 还早。（RPM=requests/min；实际生产常按 RPM+TPM 双维：既限次数也限 token 量。）

**C2 429 硬拒（探针实测）：free 第 11 发 → 返回 `429`。** **配额语义 = 拒绝，不是排队，更不是降速。** 排队的请求会占住网关连接、进而占住上游——超配用户就该被立刻挡在门外（转付费/转等分钟窗口）。这是配额与速率的区别：**速率（13-03 令牌桶）管"每秒放多少"，配额管"你这个号这分钟能用多少"，一个给流体加阀，一个给用户设上限。**

**C3 突发桶（探针实测）：窗口内瞬间 `120` 发 → 全过。** 这是连接 13-03 令牌桶（rate 60 + bucket 120 只引）的一格：**稳态 60/s，但桶的容量允许短时 120 突发**——突发（如定时任务/夜维脚本集中打）不该被一刀切，配额管总量、桶管突发。**比例是"突发多久"的答案：120 打完后桶空，回稳态 60/s。**

## 6. 实验 D · 重试熔断账：三态机 + 快速失败刹车

**账 D 回答"§13.8 重试熔断——上游在抖/在挂，网关怎么刹车"。探针跑一遍三态机 + 一次瞬态重试：**

**D1 熔断状态机（探针实测）：Closed → Open：连续 `5` 次失败触发熔断。** 三态就是"闸门的三个位置"：**Closed（正常放行）→ Open（上游不可信，闸门全关，直接快速失败）→ Half-Open（试探性放 3 个，看上游缓过来没有）**。

**D2 Open 期快速失败（探针实测）：Open 期间 3 个请求 → 全部快速失败，上游调用 `saved=3`。** 这是熔断最值钱的一格——**开闸期间请求根本不进上游，网关直接说"现在不行"**。为什么宁愿说不行也不排队等？排队=连接占着=上游雪崩时大厅塞满人（每锅锅都等不及），**快速失败=把失败挡在门口，让上游有时间缓过来**（13-07 告警"扩容/回滚"之前，网关做的第一件事就是这里）。

**D3 Half-Open 探测（探针实测）：探测 3 个 → 2 成 1 败 → 回 Open（说明还在抖）；再探测 3 个全成 → Closed（恢复放行）。** 熔断不会无限关下去**——Half-Open 是"探头出去摸一下水温"，摸到还烫就再关，摸到正常就全线开闸。** 状态机本身是判定逻辑，探针把它跑成确定性的 7 格脚印。

**D4 瞬态重试（探针实测）：瞬时 `503` → 指数退避重试 `2` 次成功（≤3 上限）。** 重试要"退避"（0.5s→1s→2s），不是立刻重打——**立刻重试第 2 次还是 503，等于追着拥堵再撞一次**；重试 ≤3 次是红线，超过就放弃走熔断/快速失败（11-08 的重试成本放大 ×1.025 只引不重测——重试不是免费的）。

## 7. 这篇网关账怎么用（一页带走 + 掌握度检验）

**一页带走——给你的 7B 服务在门口装一道闸，按 §13.8 六功能排受理链：**

1. **认证先行（账 A3）**：没凭证的请求第一关就 401，零 token 成本——别让裸请求进内网。
2. **路由定版本（账 B）**：`model` 名固定，去哪个 upstream 由路由表决定；版本表 4/4、金丝雀 95/5 改权重、回滚改一行引用。
3. **配额限流（账 C）**：per-user RPM/TPM，free 10/basic 50/pro 200 分档，超发 429 硬拒（不排队）；token 突发桶 120 容短时突发。
4. **重试熔断（账 D）**：5 连败熔断、Open 期快速失败把雪崩挡在门口、Half-Open 探测 3 恢复/再关、重试 ≤3+退避。
5. **缓存命中走 KV（账 A5）**：前缀复用度高的业务命中 60%、100 请求 0.50→0.35 省 30%（免 prefill）。
6. **计费分价（账 A4）**：入+出=$0.005 记到租户，输出 ×4 价——钱去哪了可审计。

**掌握度检验（读完自答）：**

1. "六功能的执行顺序是什么？为什么认证要最先？"（auth→route→ratelimit→circuit→cache→bill；401 在门口拦下，零 token 成本，账 A2/A3。）
2. "多模型多版本在哪里落地？"（版本路由表一格——客户端只报 `model`，upstream 由表决定；canary 5% 改权重、回滚改一行，账 B2/B3。）
3. "配额和速率差在哪？"（速率=令牌桶管每秒（13-03 只引）；配额=per-user 会计上限，超发 429 硬拒不排队，账 C1/C2。）
4. "熔断为什么是'拒绝'而不是'排队'？"（Open 期 3 请求快速失败 saved=3——排队=占连接传染雪崩，快速失败=把失败挡在门口，账 D2。）
5. "缓存省的是什么钱？"（命中走 KV 免 prefill——$0.50→$0.35 省 30%，只付输出部分，账 A5。）
6. "重试的底线在哪？"（退避重试 ≤3 次就放弃，否则变成本放大：11-08 ×1.025 只引，账 D4。）

## 8. 常见坑（网关的 8 个）

1. **把网关当透明转发层**：只求"转发快"，六功能一个不装——§13.8 的网关是"把 LLM 变成内部服务的第一层"，价值在受理链（认证/路由/限流/熔断/缓存/计费），不在带宽（账 A 六关）。
2. **认证放业务层**：请求先到模型再验凭证——401 应该是网关门口最早的拦截（$0.0），不是 GPU 前的最后一道（账 A3）。
3. **版本切换靠改代码发版**：换 v10 是改路由表一行 + 给 5% 流量，不是重发一行 if-else——网关的版本表把发布变成配置变更（账 B2/B3）。
4. **配额当全站速率**：全站只压一个总 QPS，free 用户和 pro 用户在同一个池子——配额必须 per-user，超配额 429 硬拒（账 C1/C2）。
5. **熔断期还往里转发**：上游挂了让请求继续排队——Open 期必须快速失败，把雪崩挡在门口（账 D2）。
6. **重试无限/不退避**：503 立刻再打 = 追着拥堵再撞一次——退避重试 ≤3，超限走熔断（账 D4）。
7. **缓存只认 CDN/前缀不认**：prompt 缓存靠"相同前缀命中走 KV"——命中率取决于业务前缀复用度，无共用头就 0% 命中，别指望空手省钱（账 A5）。
8. **熔断没有 Half-Open**：全开就是风暴，永久关就是宕机宣称——探测 3 个、2 成 1 败回 Open、全成恢复（账 D3）。
