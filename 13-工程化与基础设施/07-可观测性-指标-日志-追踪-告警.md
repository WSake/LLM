## 0. 为什么第 7 课是「可观测性·指标-日志-追踪-告警」？

13 章主线是"资源怎么分、模型怎么上线"：13-01 选卡、13-02 多机互联、13-03 推理服务装配扩缩、13-04 Ray 弹性、13-05 MLOps 管生命周期、13-06 把模型注册封装成不可变版本。但**前六篇有一句话始终没说透**：版本换上去之后，**怎么知道它是好是坏？在没出大事故之前怎么提前看见问题？出了事怎么定位是权重、数据、检索还是外部工具？** 这就是 §13.7——可观测性。三个非讲不可的理由：

1. **部署只解决"能不能换"，观测解决"换得对不对"。** 13-06 教你把 v9 通过蓝绿/金丝雀换上去，但**蓝绿只是"切引用"，不是"这道闸的值"**——线上 P95 悄悄翻倍、成本悄悄 ×3、judge 悄悄下滑，这些就是可观测性的账。没有观测，金丝雀提档靠猜；有观测，提档靠四条告警的判据。
2. **它把评测从"离线压测"升级成"在线护城河"。** 11-08 的六把尺是"换模型时跑一遍混合负载看 P95 过不过"——那是**评测**；§13.7 是"**持续在线采集**，每分钟都在报 P50/P95/P99/GPU/成本"——那是**监测**。离线压测是"改变时看的快照"，在线观测是"运行时看的仪表盘"，两个都要有，本篇补的是后者。
3. **它跟 11-09 在同一卡位（§17.9.3），但换了一个视角。** 11-09 从**评测章**讲"先有 trace 再有指标、工具链/平台怎么选"（里程碑 025）；本篇从**工程章**讲"指标口径怎么报、日志怎么留、Agent 链怎么读、告警怎么定"——**11-09 问"用什么看到"，本篇问"看到之后怎么办"。** 这是一对，不是重复。

**读完这篇你会：（a）报出 §13.7 六指标口径并各配一个数：延迟报分位（P50 1415 vs P99 8731=6.2×）、错误率分母=总请求（43/2000=2.15%）、QPS=固定时间窗（10）、GPU busy 采样（64%）、token 分价（$0.005）、成本预算（$500/天）（账 A）；（b）写出一条脱敏规则并讲清顺序为什么关键，四要素归位（账 B）；（c）会画一次 Agent 请求的 span 树，定位最慢 call_api 950ms，讲清 Agent 慢在工具调用不是模型生成（账 C）；（d）背出四类告警：SLO（p95≤2s）/容量（GPU>85% 持续 5min）/成本（周环比>20%）/质量漂移（judge 距目标 0.05），每条配一个动作（扩容/加副本/降档/回滚）（账 D）。（本篇 🔴 工程必备 = 13-07 可观测性——联动 11-09·11-08·13-06·13-05·13-03·13-02·09-07·11-03，无专属里程碑。）**

## 3. 实验 A · 指标账：六口径持续采样 + 报分位不报均值 + token/成本

**账 A 回答"§13.7 六个指标在生产上怎么采、怎么报"。探针用 600 条确定性延迟把每个口径算成可复现的数：**

**A1 延迟分位（探针实测）：600 条 = 主体 560 条均匀带 700–2075 ms + 40 条长尾掐尖 5.2–9.4 s（模拟超时/重试被掐尖）——P50 1415 · P95 6163 = P50 的 4.4× · P99 8731 = 6.2× · 均值 1769。** **为什么报分位不报均值：长尾把均值 1769 拉得比 P50 1415 高 25%——"平均 1.8 秒"骗过你，P99 用户实际等了 8.7 秒。** 这是 11-08 "均值君陷阱"（P50 0.93 vs P99 2.98=3.2×）在本篇的同一课，只把"压测一次"换成"持续采样"——**线上的 P95/P99 每个小时都在变，观测就是定时算它。**

**A2 错误率（探针实测）：43 / 2000 = 2.15%，分母 = 总请求（成功+失败+超时），不是成功请求。** 错误率先问分母——"错误率 5%"到底除以谁是第一口径（11-08 账 A 同式）；且 11-08 D3 提醒：错误率 5%≠成本 5%，重试还要放大（×1.025），本篇只报分母口径、不重测放大。

**A3 QPS（探针实测）：600 / 60s = 10。** QPS 必须有**固定时间窗**才有意义——"QPS 是多少"必须问"哪个窗口"（1s / 60s / 峰值 / 均值），账 D 容量告警的触发线就挂在峰值 QPS 上。

**A4 GPU 利用率（探针实测）：4 卡 busy 采样 [0.58, 0.66, 0.63, 0.69] → 平均 64%。** GPU 利用率的正确口径 = **busy 采样占比**（`Σbusy/total`），不是 one-shot 读数；**<50% 在浪费算力（13-01/13-02 的卡没吃满）· >80% 逼近容量（13-03 该扩容了）**——账 D 容量告警的 85% 阈值就长在 64% 的上面。

**A5 token 分价 + 成本（探针实测）：单请求 1000 入 + 250 出 → $0.005（13-03 账 D4 同式：输出 ×4 价 $10/M vs 输入 $2.5/M）→ 100k 请求/天 ≈ $500/天（13-05 账 C4 同口径 $15k/月）。** **token 必须输入/输出分开记**——输出 token 只占 22%（250/(1000+250)）却花了 50% 的钱（250×10 / (1000×2.5+250×10)），这是 11-08 那把尺在观测层的延续。**$500/天就是账 D 成本告警的输入。**

## 4. 实验 B · 日志账：先脱敏后落盘 + 四要素留痕

**账 B 回答"§13.7 日志——线上怎么留才合规、才可追"。探针做两件事：脱敏规则 + 四要素归位：**

**B1 四类 PII 脱敏（探针实测）：原始日志含手机号/邮箱/身份证/API key → 脱敏后 `138****5678 · z***@qq.com · 1101**********4515 · sk-***`，四类逐字不再残留，判定 PASS。** 三条规则模板：**手机** `(1[3-9]\d)\d{4}(\d{4})` → 前 3 星 4 后 4；**邮箱** `(\w)[\w.-]*@` → 首字母+`***@`；**身份证** `(\d{4})\d{10}(\d{4})` → 前 4 后 4 中间 10 位全盖；**API key** `(sk-)\S+` → 前缀+`***`。

**B2 规则顺序是脱敏的隐藏坑（探针实测的细节）：身份证必须排在手机前面。** 若手机规则先跑，18 位身份证里的 `1990030745…` 会被 11 位手机正则当"号码"吃掉，留下 `110101199****74515` 这种**身份证还剩 9 位原始数字**的残次品——后面的身份证规则再追也追不上。**脱敏规则 = 更长/更具体的先跑**，这是工程装配课才讲得到的次序问题。

**B3 日志四要素归位（探针实测 4/4）：① 输入输出（脱敏后）——prompt 原文 + 模型回复，先脱敏再落盘；② 模型/版本/温度参数——`model=qwen-7b/9 · revision hash · temp=0.7`（13-06 版本寻址，回滚时知道是哪一版）；③ 工具调用记录——`tool=search args=… result=…`（Agent 干了什么可回放，09-07 红线复盘要原文）；④ 评测集与审计的来源——点踩/慢请求 → 评测集（11-09 遥测回流），出事会话 → 红线复盘。** **§13.7 那句"日志是评测集与审计的来源"拆开就是这四件**——缺了脱敏不能合规留存（B1/B2），缺了版本/工具记录退无可退（③），缺了回流评测集就少了一半活样本（④）。

## 5. 实验 C · 追踪账：一次 Agent 请求一棵树——慢在工具调用

**账 C 回答"§13.7 追踪——一次请求的完整链路怎么读"。探针把一次 Agent 请求（规划→检索→读文档→调外部 API→子 Agent→应答）画成一棵 8-span 树【root 2600ms 是整段请求的容器，子 span 依次 plan 100 · retrieve 300 · read_doc 320 · call_api 950 · sub_agent 520（内含 llm.chat 350）· respond 200】：**

**C1 时间轴自洽（探针实测 0 越界）：每个子 span 的起止必须落在父 span 区间内**——trace 数据能当"证据"的前提是它自洽（11-09 账 B 同法，Agent 版同样要验）。

**C2 最慢 span 定位（探针实测）：`call_api` 950ms = 次名 `sub_agent` 520ms 的 1.83×。**注意 run 顺序里最贵的不是"模型调用"而是"外部 API"——**这条和 11-09 的 RAG 树正好相反**：RAG 请求慢在 `llm.generate`（生成 850ms=检索 4.7×），Agent 请求慢在**外部工具调用**（`call_api` 950ms）——**模型调度（plan+llm）一共才 450ms=17%，工具三件（retrieve+read_doc+call_api）1570ms=60%。** 这是怎么读树的关键对照：**RAG 看生成段，Agent 看工具段——谁是大头取决于请求形态，trace 才告诉你答案。**

**C3 关键路径（探针实测）：依赖链 plan→retrieve→read→api→sub→respond 累计 2390ms = root 的 92%，并行支不叠加。** trace 树上的串行依赖才是瓶颈，并行支只取 max——和 11-09 账 B 是同一句记账规则，本篇用 Agent 树再验一遍。

## 6. 实验 D · 告警账：SLO / 容量 / 成本 / 质量漂移四线 + 动作绑定

**账 D 回答"§13.7 告警四类——每条线怎么判定、触发了干嘛"。探针给出四条护栏，每条都是「判据 + 动作」绑死，不是"看一眼"：**

| 告警线 | 判据 | 探针实测 | 动作 |
|---|---|---|---|
| **D1 SLO 延迟**（§13.7 原例：p95 TTFT<2s） | p95 TTFT > 2000ms 触发 | 正常批 1652ms 不警 ✔ · 翻倍批 5460ms 触发 P1 ✔ | **扩容 / 回滚**（13-03 加副本 · 13-06 切引用） |
| **D2 容量** | GPU 利用率 > 85% 持续 ≥5min 触发 | 平均 64% 不警 ✔ · 峰值 91% 触发 ✔ | **加副本 / 扩卡**（13-03 的 HPA 账） |
| **D3 成本** | 周环比 > +20%（13-05 同阈值） | +24% > 20% 触发 ✔ | **缓存 KV（13-03 D2 前缀亲和）/ 降档 / 换更优模型（13-06 换引用）** |
| **D4 质量漂移** | judge 线上分距目标 < −0.05（§13.7 原文：线上 judge 下降） | 0.79 距目标 −0.01 不警 ✔ · 0.71 距目标 −0.09 触发 ✔ | **回滚到上一版**（13-06 账 D 定位→切回） |

**判据多硬不重要，重要的是"触发了有人知道该干嘛"。** 四条线各绑一个 13 章已算过的动作：扩容（13-03）· 加副本（13-03）· 降档/换版（13-06）· 回滚（13-06）——**告警不是让你"看一眼"，是把"看到"接回 13 章前面的能力，变成"能动的"**。这正是 §13.7 标题"工程必备"的意思：**指标/日志/追踪是眼睛，告警是手——四件套合起来才算完整。** 质量漂移线尤其要讲：它直接吃 11-03/13-06 的 judge 数据流，**线上 judge 分一掉就触发回滚，这是"模型在线上变烂"的唯一主动刹车。**

## 7. 这篇可观测账怎么用（一页带走 + 掌握度检验）

**一页带走——给你上线的 7B 服务按这条链配可观测：**

1. **先采后报（账 A）**：六指标持续在线采样——延迟报 (P50, P95, P99) 不报均值（1415/6163/8731）；错误率分母=总请求；QPS 钉死时间窗；GPU 报 busy 采样平均；token 输入/输出分开记；成本配预算（$500/天）。
2. **报后能追（账 B）**：日志先过脱敏（四类 PII，身份证规则排最前）再落盘；记全四要素（输入输出·模型版本温度·工具调用·评测审计来源）。
3. **追能定位（账 C）**：每次请求一棵树；先验时间轴自洽；再找最慢子 span（Agent 看工具段 call_api 950ms，RAG 看生成段——形态决定大头）。
4. **定后即警（账 D）**：SLO p95≤2s / GPU>85% 持续 5min / 成本周环比>20% / judge 距目标 0.05——每条绑一个动作（扩容/加副本/降档/回滚），警了就有事做。

**掌握度检验（读完自答）：**

1. "延迟该报哪个数？"（(P50, P95, P99) 三值，均值 1769 会被长尾 8731 骗——P99 用户等了 8.7 秒，账 A1。）
2. "错误率的分母是什么？"（总请求 = 成功+失败+超时，不是成功请求；43/2000=2.15%，账 A2。）
3. "日志为什么要先脱敏？顺序有什么讲究？"（PII 落盘即合规风险；手机/身份证规则顺序错了，身份证就残留 9 位原始数字（`110101199****74515` vs 正确 `1101**********4515`），更长更具体的先跑，账 B1/B2。）
4. "怎么读一次 Agent 请求的树？"（先验时间轴→找最慢 call_api 950ms=1.83×→归因工具三段 60% vs LLM 17%——Agent 慢在工具调用不是生成；RAG 才慢在生成，账 C。）
5. "四类告警各绑什么动作？"（SLO→扩容/回滚 · 容量→加副本 · 成本→缓存KV/降档/换版 · 质量漂移→回滚上一版——每一条警了都有事做，账 D。）

## 8. 常见坑（可观测的 7 个）

1. **只上仪表盘不接告警**：Prometheus 面板都摆了，没人看——§13.7 是"指标/日志/追踪/告警"四件套，**告警才是让它动起来的最后一截**（账 D）。
2. **延迟报均值**：均值 1769 看着还行，P99 8731 才是会骂人的那档——**永远报 (P50, P95, P99)**（账 A1）。
3. **脱敏规则顺序错了**：手机正则先跑把身份证吃残（`110101199****74515`）——**更长更具体（身份证）的先脱**（账 B2）。
4. **日志不记版本**：回滚了都不知道线上跑的是 v8 还是 v9——**model/version/temp 是四要素之一**，跟 13-06 的 revision 寻址对着接（账 B3②）。
5. **Agent 慢查生成**：Agent 请求慢在外部 API（call_api 950ms=60%）不是模型（450ms=17%）——**跟着 trace 走，不拿着 RAG 的结论套 Agent**（账 C2）。
6. **告警只告不动作**：SLO 触发了没人知道干嘛——**每条告警绑一个动作（扩容/加副本/降档/回滚）**，13 章前面的账才能接上（账 D）。
7. **质量漂移没刹车**：judge 分数慢了半个月才发现，流失的是真实用户——**judge 距目标 0.05 就回滚**，线上质量掉是最贵的静默（账 D4）。

## 9. 诚实边界（AAA 自我审查）

- **要素事实 vs 本机实测**：六指标清单、日志四要素、追踪四段链路、告警四类（SLO p95 TTFT<2s · 容量阈值 · 成本异常 · 质量漂移=线上 judge 分数下降）= **§13.7 要素事实（按知识地图整理，写作环境无外网未在线复核）**。请引用时保留"要素事实"前缀。
- **真实平台 vs 本机算法**：**Prometheus/Grafana/Langfuse/Phoenix/ELK 不部署、不连接**（需联网/需服务端，跳不出"纯 stdlib 零网络"的硬约束）——本机"实测"的是观测数据的**口径与判定算法**（分位数、脱敏规则、时间轴校验、四类告警阈值判定、动作绑定），不是面板本身。真实观测平台装配 = 读者在自家环境实操。
- **数字 = 作者预置 + 本机确定性计算**：600 条延迟样本（P50 1415/P95 6163/P99 8731）、错误率 43/2000、GPU 4 卡 [0.58,0.66,0.63,0.69]、token 分价 $0.005（13-03 同式只引）、日成本 $500/天（13-05 同口径只换一条线）、Agent 8-span 树、四类告警阈值（2000ms / 85%+5min / +20% / −0.05）= 本机确定性算术，不依赖随机种子/网络/第三方库。
