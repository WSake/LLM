## 0. 为什么第 3 课是「推理服务基础设施」？

13 章主线是"资源怎么分"：13-01 教你**选卡**（单张能装什么、多快、多贵），13-02 教你**多机怎么连**（通信账单）。但选了卡、连了机，**把模型真正变成"可上线服务"还差一整层**：一个用户点进来，请求怎么被处理、挂了怎么扩、新模型怎么灰度上线、流量尖峰怎么扛、账单怎么记。这就是 §13.3——推理服务基础设施。三个非讲不可的理由：

1. **"本地能跑"与"能上线"之间差一个完整的装配层。** 本地 `python serve.py` 是一条直路；生产是一个五环链路（Client → API 网关 → K8s Service → Pod(vLLM) → GPU），每一环管一件事。§17.9.6 的实践动作原话就是"把 vLLM 服务容器化并用 K8s 部署+HPA 扩缩容"——本篇就是把它拆成一笔一笔能算的账。
2. **副本数量不是拍脑袋，是算出来的。** 13-01 账 B 给的 `239 tok/s` 是**串行单请求的带宽界**——真实服务靠连续批（continuous batching）放大，B=8 就 ≈1914 tok/s。**副本数 = ceil(峰值 tok/s ÷ (单副本额定 × 目标利用率))**。会算这笔账，就知道 6 副本从哪里来、为什么换快卡能省副本（=省显存=省钱）。
3. **它是 13 章的"上线"正式展开，并向下游喂料。** 13-04 Ray（弹性调度）回答"集群怎么被调度"，13-05 LLMOps 回答"模型怎么被管理"——它们的编排对象，都是本篇三层装配里被管起来的那批副本。本章不带里程碑——它是 13 章"能上线"的公共骨架。

**读完这篇你会：（a）报出一次流式请求穿哪 5 环、各环管什么，背出服务形态三层装配链（账 A）；（b）讲清"无会话粘性"为什么是 LLM 服务能水平扩容的前提，会用带宽界→连续批→副本数三步给服务配副本（账 B）；（c）会用 HPA 期望副本公式判断扩缩方向，讲清灰度 5% 与滚动发布零停机的组合拳、令牌桶的 rate 与 burst 两段话（账 C）；（d）讲出数据平面三件事（模型缓存/前缀亲和/跨 region 容灾）各省什么，能按示例价算一次请求的 token 账单（账 D）。（本篇 🟢 了解 = 13-03 推理服务基础设施——联动 13-01 · 13-02 · 06-01 · 11-08 · 02-17 · §17.9.6，无专属里程碑。）**

## 3. 实验 A · 装配账：一次请求穿 5 环，三层各管一段

**账 A 回答"一次流式请求到底穿过哪些东西"。服务形态三件套（§13.3 原文第一行）+ 数据平面（第三行），探针把 14 项功能按归属分层归位：**

**A0 一次请求穿 5 环（探针实测）：Client → API 网关 → K8s Service → Pod(vLLM) → GPU。** 用户以为自己在跟"模型"对话，真实路径是穿过网关（路由/限流/计费）→ Service（服务发现/负载均衡）→ Pod 里的推理引擎（连续批 + KV 缓存）→ GPU 算完流式返回。**每一环各管一层，缺一环都能跑通 demo，都不能扛生产流量。**

**A1 引擎层（vLLM/SGLang）管吞吐（探针实测 4/4 归位）：continuous batching（连续批调度，请求即到即拼批）· Paged KV Cache（按页分配 KV，显存不浪费）· prefix cache（同前缀只算一次，省 prefill）· 引擎是权重+KV 的驻地。** 引擎外包不了：它管的是"同一张 GPU 上怎样塞进更多请求还不爆显存"——这就是吞吐心脏。

**A2 编排层（K8s Deployment+HPA）管副本与发布（探针实测 4/4 归位）：replicas 副本数声明 · HPA 自动扩缩容 · readiness/liveness 探针（就绪才接流量、挂掉重启）· 滚动发布（maxSurge/maxUnavailable）。** K8s 不关心模型是什么，它管"你声明的 6 个副本，我保 6 个活着、并按水位增减"——无脑管家。

**A3 网关层（Kong/APISIX/自研）管流量与钱（探针实测 4/4 归位）：蓝绿/灰度按权重切流（5% 先试新模型）· 令牌桶限流/配额 · token 计费与配额记账。** 网关不碰 GPU，它管"谁能进来、一次放多少、这笔多少钱"——流量与钱的闸。

**A4 数据平面管缓存/亲和/容灾（探针实测 4/4 归位）：模型缓存/权重共享（多副本共用一份权重）· KV 前缀亲和路由（同前缀到同一实例，2025 前沿）· 跨 region 容灾/健康检查切流。** 数据平面是三层的"层外之层"——不服务实时请求，但决定服务水平（省显存、省 prefill、省停机）。

**账 A 一句话：推理服务 = 引擎（吞吐） + 编排（副本/发布/水位） + 网关（限流/计费/灰度） + 数据平面（缓存/亲和/容灾）——四块各管一段，拆开才能逐环优化。**

## 4. 实验 B · 容量账：无会话粘性 + 副本数会算

**账 B 是推理服务的算术核心：放几个副本。13-01 账 B 给的是串行带宽界——那是"菜单价"，真实服务必须靠批放大。第一步先钉死口径（11-01）：**

**B1 带宽界（探针实测）：serial 单请求 = 3.35 TB/s ÷ 14 GB = 239.3 tok/s（13-01 账 B 的 239 同式；70B 权重 140 GB 只有 23.9）。** 这是"一次只有一个请求、每生成一个 token 都要从 HBM 重读一遍全部权重"的速度——任何不做批处理的本地 demo 都停在这个数量级。

**B2 连续批放大（探针实测）：continuous batching 让每次权重读取同时服务批内多个请求 → B=8 有效吞吐 ≈1914 tok/s、B=16 ≈3829 tok/s。** **为什么能放大：带宽界买的是"读一次权重"，批大小决定"这一次能换多少 token 回来"。** vLLM/SGLang（与 Triton/TGI）都存在，只是效率与特性的差异——这就是这两家成为 §13.3 首选的原因。

**B3 副本数 = ceil(峰值 tok/s ÷ (单副本额定 × 目标利用率))（探针实测）：峰值 8000 tok/s ÷ (1914 × 70%) = ceil(5.97) = 6 副本。** 峰值不是平均；利用率目标下预留 30% 水位给 HPA 动作空间。**先报峰值，再算单副本，再除以目标利用率——三位一体才是"会配副本"。**

**B4 换快卡会算账（探针实测）：单副本吞吐翻倍 → 副本数 ceil(8000÷(3828×70%)) = 3，省 3 副本。** 每省一个副本 = 省一张卡、一份显存、一份电力——**这就是 13-01 里"选卡"在服务端的钱形：卡快一倍的收益不只在单请求更快，还在副本数减半。**

**B5 无会话粘性（探针实测判据）：KV Cache 随一次请求生灭，不做跨请求会话 → 副本天然无状态、任意副本服务任意请求。** 这跟带登录态的 web 会话根本不同：**LLM 的"状态"在两个地方——权重（所有副本共享）和一次请求内的 KV（每次独立），服务端没有跨请求会话可粘。** 所以负载均衡可以纯按流量分，不需要会话粘性；而"跨 region 切流""无脑横扩"能成立，都是因为这一条。**这也是"KV 前缀亲和路由"（账 D）的意义——它在数据平面重新造出一点点"粘性"，为的是命中缓存而不是为了会话。**

## 5. 实验 C · 扩缩容发布账：HPA 公式 + 灰度 + 滚动 + 令牌桶

**账 C 回答"上线之后怎么管"。§13.3 的关键工程点，装成四条：**

**C1 HPA 期望副本公式（探针实测，K8s 官方公式）：期望 = ceil(当前副本 × 当前水位 ÷ 目标水位)。当前 6 副本：水位 85% 目标 70% → ceil(6×85/70) = 8（扩 2）；水位 45% → ceil(6×45/70) = 4（缩 2）。** 这个公式务必背下来——它告诉你"HPA 不是拍一个目标副本数，而是每个采样周期按水位换算期望值再增减"。

**C2 GPU 水位判据（探针实测判据）：HPA 照 GPU 利用率扩缩容，不数 CPU。** 推理是 GPU 密集型负载：GPU 忙（算力打满/带宽打满）才是真需要加副本，CPU 忙≠GPU 忙（13-01 账 B「瓶颈在带宽不在算力」同源）。**K8s 默认 HPA 只懂 CPU/内存，GPU 水位要靠自定义指标（prometheus-adapter）接进来——这是"按 GPU 水位扩缩容"的真实落地姿势。**

**C3 灰度：新模型先吃 5% 流量（探针实测）：老版本权重 95% / 新版本 5%，看错误率/延迟达标再逐步加权重。** 网关切流、不重启副本——**灰度是流量问题不是部署问题：旧模型 5% 时也在跑，错了一起进去一起回滚，全程用户无感知。**

**C4 滚动发布零停机（探针实测）：maxUnavailable=0（不关旧）+ maxSurge=1（先多起 1 个新的）→ 新副本就绪才摘旧副本。** 6 副本场景峰值在线 7，全程有可用副本。**滚动与灰度是两件事：灰度决定"流量怎么分"，滚动决定"副本怎么换"——可以组合用（新副本走滚动起，流量走灰度切）。**

**C5 令牌桶限流（探针实测）：rate 60 req/s + bucket 120 → 空桶 2.0 s 补齐，瞬时容得下 120 突发、稳态钉在 60。** 令牌桶 = **两个数字的账：rate（稳态速率，每秒回填多少令牌）+ bucket（突发容量，桶里最多攒多少）**。它比"简单限 60"高级在：能放行瞬时尖峰又不让长期超速——对应 §13.3 的"配额限流"。

## 6. 实验 D · 数据平面计费账：缓存/亲和/容灾 + token 计费

**账 D 回答"重复工作怎么省、挂了怎么切、钱怎么算"。§13.3 第三行 + token 计费，装成四件事：**

**D1 模型缓存（探针实测）：8 副本跑同一 14.0 GB 权重 → 共享模型缓存/前缀池（读一次、副本共用）；不共享 = 8×14 = 112 GB 重复加载。** 生产里的权重不是每个副本各拉一份，而是节点级缓存/对象存储 + 副本共享——**省的是启动时间和与分布式存储之间的带宽，这也是"模型缓存"出现在数据平面第一行的原因。**

**D2 KV 前缀亲和路由（探针实测）：同前缀路由到同一实例 → 命中 prefix cache → prefill 免重算。02-17 同机实测 10.2ms vs 3.4ms = 3.0×；真实模型通常 2–4× TTFT 差。** **[2025 前沿]** 系统 prompt / few-shot / RAG 检索结果前缀在大量请求间高度重复——**让它们落在同一实例，前缀的 KV 就能被第二批请求直接复用（省 prefill，prefill 是首 token 延迟大头）。** 这就是 §13.3 数据平面第二行：前缀亲和路由 = 无会话粘性（账 B5）的政策性例外，为了缓存命中而造的"弱粘性"。

**D3 跨 region 容灾（探针实测判据）：每 region 一份副本 + 健康检查 → 主 region 探针失败即 DNS/LB 切流备地域。** 因为请求无状态（账 B5），**只读切流是纯流量问题**——不会出现"session 断了用户要重登"的 web 式痛苦。跨 region = 双份基础设施的钱，买的是"主 region 挂了用户还能继续"。

**D4 token 计费（探针实测）：示例价 输入 $2.5 / 输出 $10 每百万 token（06-01 同档）→ 一次 1000 入 + 250 出 = $0.00500，输出 token 只占 20% 却花 50% 的钱。** **这是 11-08「输出 token 是小头却是钱大头」的账单版**：输出价格是输入的 4 倍，所以"输出 token 20%"等价于"钱 50%"——**读账单永远先拆输入/输出两段，别被总 token 数骗了。**

## 7. 这篇服务账单怎么用（一页带走 + 掌握度检验）

**一页带走——给你下一个模型服务写"从裸机到上线"的清单：**

1. **先画装配（账 A）**：Client → API 网关 → K8s Service → Pod(引擎) → GPU，五环各管一段——引擎吞吐、编排副本、网关流量与钱、数据平面缓存容灾。
2. **再算副本（账 B）**：串行带宽界 → 连续批放大 → `ceil(峰值 ÷ (单副本×目标利用率))`。先报峰值，再除目标利用率。
3. **再定扩缩与发布（账 C）**：HPA 照 GPU 水位、期望 = ceil(当前×水位/目标)；灰度先 5% 网关切流；滚动 maxUnavailable=0 + maxSurge=1；令牌桶 rate 与 bucket 两个数。
4. **数据平面配缓存与亲和（账 D）**：模型权重节点共享；系统前缀做亲和路由命中 prefix cache；主 region + 备 region + 健康检查。
5. **上线带两把尺（11-08 + 账 D）**：延迟报分布（P95 才算）、账单拆输入/输出两段（输出 token 20% 却花 50% 钱）。

**掌握度检验（读完自答）：**

1. "一次流式请求穿过哪 5 个环节？"（Client→API 网关→K8s Service→Pod(vLLM)→GPU，账 A0。）
2. "为什么 LLM 服务不需要会话粘性？"（KV Cache 随请求生灭、跨请求无状态——状态在请求里不在服务端会话里，账 B5。）
3. "6 副本从哪里算出来？"（ceil(峰值 8000 ÷ (1914×70%)) = ceil(5.97) = 6，账 B3。）
4. "HPA 是怎么扩缩的？"（每个周期按 GPU 水位：期望 = ceil(当前×水位/目标)——85%→6 副本扩到 8、45%缩到 4，账 C1/C2。）
5. "灰度 5% 与滚动发布是一回事吗？"（不是：灰度=网关切流分 5% 流量试新模型；滚动=副本先起新再摘旧换版本，可组合用，账 C3/C4。）
6. "令牌桶的 rate 和 bucket 各管什么？"（rate=稳态速率每秒回填；bucket=突发容量，空桶 2s 补齐——容尖峰又不超速，账 C5。）
7. "KV 前缀亲和路由解决什么问题？"（同前缀路由到同一实例，命中 prefix cache 省 prefill——系统 prompt/RAG 前缀重复时 TTFT 3.0×（02-17 实测），账 D2。）

## 8. 常见坑（推理服务算账的 7 个）

1. **拿串行带宽界当服务吞吐**：demo 测出 239 tok/s 就以为"服务只能这么快"——没算连续批放大（账 B1/B2，B=8 ≈1914）。
2. **副本数拍脑袋（只算平均不算峰值）**：拿平均 QPS 配副本，尖峰一来队列爆——必须拿峰值 8000 算，且除以目标利用率留水位（账 B3）。
3. **忘掉无会话粘性**：照 web 后端惯性做会话粘性/会话管理——LLM 服务不需要，做了反而绑死负载均衡（账 B5）。
4. **HPA 数 CPU**：默认 HPA 只懂 CPU/内存——推理要接 GPU 自定义指标（prometheus-adapter），否则 GPU 打满 CPU 不忙就不扩（账 C2）。
5. **全量发布替代灰度**：新模型直接换副本——灰度 5% 是"先试错再逐步加权"，错了一起进一起回滚（账 C3）。
6. **滚动发布 maxUnavailable=1**：先关旧再起新，窗口期没服务——零停机 = maxUnavailable=0 + maxSurge=1（账 C4）。
7. **账单只看总 token 数**：输出只占 20% token 却花 50% 钱（输入 $2.5/输出 $10）——不拆输入/输出两段就看错成本结构（账 D4）。
