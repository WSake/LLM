## 0. 为什么第 5 课是「MLOps/LLMOps」？

13 章主线是"资源怎么分"：13-01 选卡、13-02 多机怎么连、13-03 推理服务怎么装配扩缩、13-04 Ray 怎么把资源变成任务级调度。但**有一件事前四篇从头到尾没回答**：一个模型训练完、部署上去之后，**团队怎么知道哪个版本更好？怎么在数据漂移时自动重训？怎么保证新版本上线不炸？上线之后线上流量怎么变成下一版模型的训练集？** 这就是 §13.5——MLOps 与 LLMOps。三个非讲不可的理由：

1. **"能跑的模型"和"能被管理的模型"是两回事。** 本地 `python serve.py` 能跑，不等于团队能在三个月里持续发布 6 个版本还不出错。线下 demo 只要"这个版本能用"；生产要的是"**哪个版本好、怎么判好、怎么换上去、怎么发现问题**"——这四问全是管理问题，不是模型问题。MLOps/LLMOps 就是回答这四问的学科，也是 §17.9.6 的最后一格。
2. **线上模型会腐烂，必须有一条回流流水线。** 数据分布漂移、用户行为变化、成本缓慢上涨——**模型上线的第一天就在过时**。§13.5 给的解药是"CI/CD 在 LLM 世界的形态"：数据变更 → 训练/微调 → 评测门禁 → 自动部署 → 灰度 → 线上遥测回流。这条流水线把"线上坏了"变成"下一版马上来"，正是数据飞轮的工程化。
3. **它是 13 章的结算动作，并完成 §17.9.6。** 13-01/13-02 铺完「GPU 调度」、13-03 铺「K8s 部署+HPA」、13-04 铺「Ray」，本篇铺最后的「LLMOps」——四格齐，§17.9.6 工程基础设施整卡翻绿（✅×5·⬜×3）。下一篇 13-06 模型注册与版本管理，再把账 A 里"模型注册"那一格单独展开。本章不带里程碑——它是 13 章"能上线"的收口层。

**读完这篇你会：（a）报出传统 MLOps 六件套与 LLMOps 六新增各管什么，讲清"传统管产线过程、LLMOps 管模型输入输出与效果"的阵营口诀（账 A）；（b）背出 LLM 世界 CI/CD 六节点，会算手工 vs MLOps 的发布周期差、用评测门禁三判决定放不放行（账 B）；（c）六新增每件各带一个数：prompt 6 版唯一解析、评测集锁哈希、8 span 的 trace、$15k/月与 22.5% 告警、护栏 400 误拒/200 漏放、2.9 GB/月日志（账 C）；（d）画出数据飞轮：4 类回流信号 4%=4000 条/天 → 抽样 25% → 5000 条/周进训练集 → 数据集月版、模型季 3 版，闭环回账 B（账 D）。（本篇 🟢 掌握职责划分 = 13-05 MLOps与LLMOps——联动 11-10·11-09·11-08·13-03·13-04·09-07·09-06/11-06·04-10·§17.9.6，无专属里程碑。）**

## 3. 实验 A · 职责分工账：12 项归位 + 阵营口诀 + 邻居映射

**账 A 回答"谁管什么"。§13.5 两行清单，探针把 12 项按阵营归位：**

**A0 传统 MLOps 六件套（探针实测 6/6 归位）：数据版本（DVC，数据集打版本+哈希，复现时旧版照样拉）· 实验跟踪（MLflow/W&B，超参·指标·产物一记录，别靠文件命名考古）· 模型注册（MLflow Registry/HF Hub，权重+配套进注册中心，13-06 正式展开）· CI/CD 三子件 = 训练流水线（数据变更自动触发）· 评测门禁（质量/回归/成本三闸）· 发布（自动部署+灰度）。** 这六件套回答的是**"产线过程"**：数据集是哪个版本、实验谁做的、模型有没有注册、发布有没有走管道——都是"过程可追溯"。

**A1 LLMOps 六新增（探针实测 6/6 归位）：Prompt/上下文版本管理（提示词也换代，锁版本号防漂移）· 评测集管理（评测集也版本化+哈希，锁住才可比）· LLM 调用可观测（Langfuse/Phoenix，一请求一棵 trace）· 成本管理（token 计费仪表，分输入/输出记账）· 护栏管理（注入/越狱防线也版本化+灰度）· Agent 日志回放（能回放轨迹，审计与复盘的前提）。** 这六件回答的是**"模型的输入输出与效果"**：提示词对不对、评测集稳不稳、调用贵不贵、护栏拦不拦得住——**LLM 比传统 ML 多出来的管理面，全在这六件上**。

**A2 阵营口诀（探针实测）：传统 MLOps = 管『产线过程』；LLMOps 新增 = 管『模型的输入输出与效果』。** 一句话分清两阵营：**传统管的是"这个模型怎么来的"（过程），LLMOps 管的是"这个模型用起来怎么样"（效果）。** 这是 §13.5"职责划分"四个字的全部含义——不是取代，是叠加。

**A3 与已交付篇章的邻居映射（探针实测 4 连）：可观测 → 11-09 里程碑 025（Langfuse trace 8 span 实测）· 成本 → 13-03 账 D4（token 计费同式）· 护栏 → 09-07 六护栏（Agent 安全）· 日志回放 → 11-06/09-06（Agent 轨迹评测）。** MLOps 不是新大陆——**六新增每一件都能在已交付篇章里找到它的算术根**。

## 4. 实验 B · CI/CD 流水线与发布账：六节点 + 发布周期 + 门禁三判

**账 B 是 MLOps 的算术核心：模型怎么被持续更新。§13.5 的"CI/CD 在 LLM 世界的形态"一整句，拆成六节点 + 周期 + 门禁：**

**B1 六节点流水线（探针实测 6/6 归位）：数据变更 → 训练/微调 → 评测门禁 → 自动部署 → 灰度 → 线上遥测回流。** 记忆锚：**这六节和 13-03 的服务五环（Client→网关→Service→Pod→GPU）是两种环——五环是"一次请求穿什么"，六节是"一版模型怎么迭代"。** 传统 CI/CD 管代码，LLM 世界的 CI/CD 管模型 + 数据 + 评测集三样东西。

**B2 发布周期账（探针实测）：手工 3.50 天 = 数据准备 0.7 + 触发排队 0.7 + 找版本 0.7 + 部署验证 0.7 + 复盘 0.7（5 步×平均 0.7 天）；MLOps 0.70 天 = 自动训练 4h + 自动门禁 0.5h + 灰度观察 12h ≈ 0.7 天。周期压到 5.0×。** 关键区别不只是快——**手工流程的大头是"人等"（排队、找版本、约时间），自动化把"人等"换成"机器跑"**。这是"会算 MLOps 的第一笔账"。

**B3 评测门禁三判（探针实测，对 200 条评测集）：① 准确率：v3 候选 90%（180/200）≥ 阈值 85% → 过；② 回归：v3−v2 = +2.0 pp ≤ 上限 +2.0 pp → 贴线过；③ 成本：v3 $0.00625 vs v2 $0.0050 = +25% > 预算 +20% → 拦。** **门禁不是"模型好不好"的一票，是质量/回归/成本三把闸**——v3 更准、不回落，但贵 25% 超预算，照样进不了生产。这就是 11-10 门禁链（冒烟→回归→安全→工程）在模型发布域的具体化：**"质量过 ≠ 上线"。**

**B4 放行节奏（探针实测）：每周出候选 → 月度全量门禁放行 1 个 → 季度 3 个生产模型版本。** 与账 D 的数据飞轮联动：**回流数据足够，才撑得起"周候选/月放行"的节奏**——数据要是不回流，两周后就没有"下一版"可放了。

## 5. 实验 C · LLMOps 六新增账：六件各带一个数

**账 C 回答"LLMOps 六新增每一件到底管什么、交多少钱"。探针给每件一个能算的数（六件 6/6）：**

**C1 Prompt/上下文版本管理（探针实测）：6 版进版本库、7 处调用引用 prompt_id 唯一解析 6/6；未版本化对照：7 处手工 copy 有 3 处与『该是谁的版本』对不上。** **Prompt 也是资产，也要版本化**——改了系统提示词不改版本号，线上出问题连回滚目标都没有。

**C2 评测集管理（探针实测）：同一 v3 在 评测集 v1（100 条）上 +2.0 pp（虚高『变好了』）vs 评测集 v2（150 条，+50 条线上回流）上 −1.0 pp（真实回落）。** **这是 11-02 防污染的评测侧翻版**：评测集不锁版本+哈希，跨集对比毫无意义——"比上次好 2 个点"可能只是评测集换了。

**C3 LLM 调用可观测（探针实测）：一次 RAG 请求 8 span（11-09 同口径）→ 100,000 请求/天 = 800,000 span/天；最慢 span llm.generate 850 ms = 检索 4.7×（11-09 实测）。** Langfuse/Phoenix 把"哪贵哪慢"从猜变成查——**可观测是成本管理和门禁的数据底**（11-09 里程碑 025 的工程形态）。

**C4 成本管理（探针实测）：单请求 1000 入 + 250 出 = $0.005（13-03 账 D4 同式）→ 100,000 请求/天 = $500/天 ≈ $15,000/月；周环比 $3,675 vs $3,000 = +22.5% > 预算 +20% → 告警。** **成本是运行指标不是财务指标**——日粒度记账、周粒度告警，才会在月份账单吓人一跳之前发现上涨。

**C5 护栏管理（探针实测）：护栏 v1 拦真违规 99.5%·误杀 0.4%·漏放 0.20% → 100,000 请求/天 = 400 正常请求被误拒 + 200 风险流量放行；换护栏新版本先 5% 流量灰度看误杀率（09-07 六护栏同纪律）。** **护栏不是一次性部署，是长期维护的规则资产**——太严误杀用户、太松漏放风险，换版必须小流量灰度。

**C6 Agent 日志回放（探针实测）：会话 10 步 × 1 KB/步 × 10,000 会话/天 = 98 MB/天 ≈ 2.9 GB/月，留 90 天审计 ≈ 9 GB；出事故会话 5 条 → 回放定位 3 条根因。** **能回放 = 可审计 + 可复盘**（09-06 轨迹评测的工程前提）——Agent 干了什么，出事要能回头看到每一步。

## 6. 实验 D · 数据飞轮账：回流 → 标注 → 版本节奏，闭环回 B

**账 D 回答"线上数据怎么变下一版模型"——§13.5"CI/CD 形态"第六节『线上遥测回流』的正式展开：**

**D1 四类回流信号（探针实测 4/4）：点踩/差评 2% → 2,000 条/天 · 重试/次好 1% → 1,000 条/天 · 护栏低分拦截 0.5% → 500 条/天 · 慢请求 0.5% → 500 条/天，合计 4% = 4,000 条/天。** **回流信号不是"收集所有线上流量"，是四种带信号的流量**——用户明确不满（点踩）、系统判重做（重试）、护栏判有害（低分）、延迟兜底（慢），各占一档。

**D2 抽样标注（探针实测）：4,000 条 × 25% = 1,000 条/天 × 5 工作日 = 5,000 条/周进训练集。** 4% 流量全灌进训练集 = 垃圾进垃圾出——**标注入库前要抽样 + 人工复核**，25% 是"自动化标签 + 人工复核抽查"的常见配比。

**D3 版本节奏（探针实测）：周 5,000 条 → 月 20,000 条（训练集基线 100,000 条 → 每 4 周数据集版本 +1，季度 3 版）；模型 = 账 B 节奏：周候选 → 月放行 → 季度 3 个生产版本。** 数据版本和模型版本是两行并跑的账——**数据先变，模型才跟着变**；没数据的版本号是空的。

**D4 闭环点（探针实测）：本周 5,000 条回流标注入训练集 = 账 B 流水线的『数据变更』输入——CI/CD 形态五段合龙。** **数据飞轮的工程化，就是把账 D 的输出接回账 B 的输入**：线上信号 → 回流 → 标注 → 进集 → 触发下一轮训练。闭环得越快，模型更新越快——这就是 §13.5 那句"数据飞轮的工程化"的全部意思。

## 8. 常见坑（MLOps 的 7 个）

1. **把 MLOps 当 K8s**：以为 13-03/13-04 的部署调度就是管理全部——K8s/Ray 管"模型跑在哪"，MLOps 管"模型怎么被迭代"，后者才是生命周期，前者只是底座（账 A）。
2. **prompt 靠文件命名/聊天记录管**：改了系统提示词不升版本号，线上出问题没有回滚目标——prompt 也要进版本库锁 prompt_id（账 C1）。
3. **评测集不锁版本**：同一模型在旧评测集上"变好了"+2.0，换新集再看是 −1.0——跨集对比无效，评测集必须 hash 锁定（账 C2 / 11-02 同源）。
4. **门禁只查质量不查成本**：更准但贵 25% 的 v3 被成本闸拦——质量过 ≠ 上线，成本是门禁第三把闸（账 B3）。
5. **回流数据全收不标注**：4% 线上流量全灌进训练集 = 垃圾进垃圾出——抽样 25% + 人工复核才入库（账 D2）。
6. **护栏改规则不灰度**：新护栏直接全量，误杀 0.4%×100k = 400 正常请求/天被仿拒——换版先 5% 流量看误杀率（账 C5）。
7. **Agent 不回放日志**：出事故只能猜"它哪步做错了"——会话 10 步×1 KB = 100 MB/天、留 90 天审计 9 GB，能回放才有根因（账 C6）。
