## 0. 为什么第 4 课是「Ray 分布式运行时」？

13 章主线是"资源怎么分"：13-01 选卡、13-02 多机怎么连、13-03 推理服务怎么装配与扩缩。但**上一课管的是"你声明的副本数保活"（K8s），粒度是容器/Pod**——一个 Agent 任务派出去若干个子任务、一批缓存要重新构建、一篇文档要切 10 万片，这些**任务级的调度 K8s 不擅长**。§13.4 讲的 Ray，就是补这一层。三个非讲不可的理由：

1. **它是"Agent 时代"的弹性底座。** §13.4 原话"为什么重要"第一句：**Agent 大规模并行（成百上千个任务）**。10 个页面抓取、100 段 RAG 检索+生成、1000 个并行的验证/评测任务——靠 for 循环串行跑，是 13-03 账 B 里那种"239 tok/s 串行带宽界"的翻版；靠 Ray 一层，就变成"先报任务数、算并行度、把墙钟除下来"的算术。
2. **它是"在线-离线混合负载的通用胶水"。** 同一个集群白天给在线推理（Ray Serve）、跑批任务（Ray Data）、晚上跑超参（Tune）/训练（Train）——一段代码一套 API，资源按水位随时切。这是单掰 OpenMP/多线程/手写 task queue 给不了的东西。
3. **它是 13 章"能上线"的第二张正式的账，并向下游喂料。** 13-03 把副本交给 K8s，这一课讲 K8s **上面**那一层；下一站 13-05 LLMOps 讲模型怎么被管理——它管理的模型，就在 Ray 编排的这份弹性上跑。本章不带里程碑——它与 13-03 同属"公共骨架"。

**读完这篇你会：（a）报出 Ray 五件套各管什么、三原语 task/actor/ObjectRef 的差别，讲清 K8s 与 Ray 的两层边界互不替代（账 A）；（b）会用 `墙钟 = ceil(N ÷ 有效并行) × 单任务耗时` 给 Agent 大规模 fan-out 估墙钟，会算一次重试把成功率提到多少（账 B）；（c）会用"状态三问"判定一个负载该不该用 actor，讲清它和 13-03「无会话粘性」怎么不打架（账 C）；（d）讲出 Ray Serve 在线两层扩缩、Ray Data 离线借机、峰值在线优先三件事各算一笔账（账 D）。（本篇 🟢 掌握概念 = 13-04 Ray 分布式运行时——联动 13-01·13-02·13-03·04-07·06-05·09-02/09-03·07-02·11-08·§17.9.6，无专属里程碑。）**

## 3. 实验 A · 定位装配账：五件套归位 + 三原语 + 两层边界

**账 A 回答"Ray 是什么、和 K8s 什么关系"。§13.4 定位第一行 + 13-03 底座，探针把 11 项按归属归位：**

**A0 Ray Core 三原语（探针实测 3/3 归位）：`@ray.remote` 有两条路——`@ray.remote` 包一个函数 = task（无状态远程函数，一次调用一个结果），`@ray.remote class` = actor（有状态类实例，串行执行方法）；两个都返回 ObjectRef（未来句柄，`.remote()` 即返回不阻塞，`ray.get()` 才收值）。** 三原语是理解后面所有账的钥匙：task 是"派出去了"的样子、actor 是"有状态常驻"的样子、ObjectRef 是"我还没拿但会拿到"的凭证。

**A1 五件套各管一段（探针实测 5/5 归位）：Ray Train 管分布式训练（DataParallel/Torch 组装进同一套弹性调度）· Ray Serve 管在线推理（Deployment 多副本 + HTTP）· Ray Data 管批量数据（百万行并行 map/batch）· Ray Tune 管调参（分布式跑 trial）· Ray Workflows 管编排（多步有向图 + 检查点，挂掉从断点续）。** 术语别被吓到——它们共享同一个 Core 三原语，只是"调度什么"不同：Train 调度训练任务、Serve 调度推理副本、Data 调度数据管道。**§13.4 把它叫做"统一……的弹性底座"，意思是：学完三原语，五件套都是同一套 API 的换皮。**

**A2 一次远程调用 4 步（探针实测）：driver `ray.init` → 提交 N 个 `.remote()` 任务（不阻塞、即返 ObjectRef）→ 各自拿句柄 → `ray.get` 收拢。** 关键词是"**并行提交与阻塞收值是两件事**"——就像流式输出（发请求是发请求、等首 token 是等首 token，中间可以干别的）。Ray 的弹性调度就藏在这两件事之间。

**A3 与 K8s 的两层边界（探针实测 3/3 归位）：K8s 管第一层——Node/容器/Pod/网络，你声明的副本数保活（13-03 账 C 的 HPA）；Ray 管第二层——Pod 内的 task/actor/数据，同一个 Pod 里的精细调度。** 关键句：**K8s 的 HPA 扩副本做不了 task 级编排——它看到的是"有没有副本"，看不到"这个副本里 100 个 Agent 任务跑到第几个"。** 所以生产真实装配是两层叠用：K8s 拉起带 GPU 的 Pod 并在 Pod 级保活，Ray 在 Pod 内外调度任务。**"谁也不会替谁" = 谁都不能单独交付"Agent 大规模并行"。**

## 4. 实验 B · 弹性并行账：Agent 大规模 fan-out 的墙钟算术

**账 B 是 Ray 最实用的算术核心：一批任务要跑多久。第一步先钉死口径（11-01）：墙钟不算"总计算量"，只算"一排能并行多少、有几排"。**

**B1 串行基线（探针实测）：1000 个子任务 × 单任务 12 s = 12000 s（≈3.3 小时）。** 这是"for 循环逐个跑"的账单——Agent 在浏览器/网页/RAG 检索上 fan-out 后，如果串行执行，墙钟就是 ∑单任务耗时，谁也救不回来。

**B2 单机并行（探针实测）：一台 32 worker 的机器并行度拉满 → ceil(1000/32) = 32 批 × 12 s = 384 s（≈串行的 1/31）。** **为什么能除：一批 32 个任务同时跑，墙钟只跟"批数"挂钩。** 这就是 task 语义的威力——同一段 Python 代码，把函数用 `@ray.remote` 包起来提交，就自动摊到 N 个工作进程。

**B3 加机器（探针实测）：4 台机器 × 32 worker = 128 worker → ceil(1000/128) = 8 批 × 12 s = 96 s。** 墙钟公式**= ceil(N ÷ 总 worker) × 单任务耗时**。加机器 = 批量买墙钟——不是把 12 s 缩短，是把"批数"除下来。

**B4 利用率折损（探针实测）：目标利用率 70% → 有效并行 = floor(128×70%) = 89 → ceil(1000/89) = 12 批 × 12 s = 144 s。** **同一个 13-03 账 B3 的纪律：别拿理论并行度算墙钟，留 30% 水位给调度、给 HPA、给队列。** 弹性调度不是"全塞满"，是"按水位控制多少任务在飞"。

**B5 失败重试（探针实测）：单任务成功率 98%、最多重试 1 次 → 终成功率 = 1-(1-98%)² = 99.96%，1000 任务期望失败 0.40 个。** 公式 `1-(1-p)²` 的意义：**失败是任务级事件（这个网页超时、那次 API 5xx），不是整批事件——重试一次，失败概率从 2% 压到 0.04%。** Ray 的天然 retry 语义就是 "task 失败自动重启一次"，这就是 Agent 世界敢开 1000 个并发任务的底气之一。

## 5. 实验 C · Actor 状态账：有状态原语 vs「无会话粘性」纪律

**账 C 回答"Ray 给了有状态 actor，可我 13-03 刚学了无会话粘性，打架吗？"——不打架，因为无状态和有状态各有适用的负载。判据是"状态三问"：谁持状态 / 状态可拆吗 / 状态能丢吗。探针把五个典型负载过一遍（五场景 5/5）：**

**场景 1 在线 LLM 服务 → 否（无状态横扩）。** 状态=KV Cache 随请求生灭（13-03 账 B5）。**状态能丢、也在请求里** → 不需要 actor，副本无状态才能被 HPA 横扩。**这是 13-03 的核心纪律，在 Ray 世界里同样成立：别给在线 LLM 服务挂 actor。**

**场景 2 Agent 会话上下文 → 否（不押在 actor）。** 状态在多轮对话的会话段与编排层 checkpoint（07-02 LangGraph）。**状态在"谁在指挥"那里，不在"谁被调度"那里** → 让 worker 无状态可调度，会话丢给编排层管。**这是 Agent 大量并行的前提：100 个会话 100 段 checkpoint，工作进程本身一文不剩。**

**场景 3 前缀 KV 缓存 → 可（actor 承载弱粘性）。** 状态=数据平面的 prefix cache（13-03 账 D2）。**状态不能丢（丢了就要重算 prefill）、又恰恰"想粘在某一个实例"** → actor 完全适合：同前缀路由到同一实例，命中缓存。**actor = 13-03「KV 前缀亲和路由」里"弱粘性"的承载者——五场景里唯一真该上 actor 的。**

**场景 4 批量累加 → 否（每 worker 局部再归约）。** 状态=任务内 count/sum。**状态可拆** → 每个 task 局部累加、末尾 reduce 归约（这正是 Ray Data 的 map→reduce 模型）。**该用归约语义，不需要跨任务共享状态。**

**场景 5 共享只读模型权重 → 对象广播（非 actor）。** 状态=全局只读的权重（13-03 D1 模型缓存）。**状态不持写者、所有 worker 引用同一份** → ObjectRef 广播给各 worker，不是 actor 串行化，也不是各拉一份。**权重共享用对象广播，不用 actor。**

**账 C 一句话：先问状态三问——能丢走无状态（横扩）、可拆走局部+归约、只读走对象广播、只有"真得粘在一个实例且不能丢"才轮到 actor（前缀缓存）。** 第五路子题：同一 actor 串行调 5 次按序执行 → 计数器 = 5（顺序一致性）；5 个无状态 task 并行各 +1 反而丢更新——actor 的价值和代价是一体的。

## 6. 实验 D · 在线-离线混合账：Serve 两层扩缩 + Data 离线 + 峰值抢占

**账 D 回答 "白天给在线服务、晚上跑批任务，一个集群怎么分"（§13.4"在线-离线混合负载的通用胶水"）。**

**D1 Serve 在线两层扩缩（探针实测）：deployment 4 副本 × 每副本 16 并发 = 总并发 64。** 注意两层的分界：**外层 K8s 扩 Pod 数（13-03 账 C HPA），内层 Ray Serve 扩"副本数 × 每副本并发"**——同一个访客进来，K8s 决定在哪个 Pod、Serve 决定 Pod 内几个 worker 接。**在线服务的并发不是单看 Pod 数，而是 Pod 数 × Pod 内 worker 并发。**

**D2 Ray Data 离线墙钟（探针实测）：100 万行 × 1 ms/行，32 worker → 串行 1000 s vs 并行 ceil(÷(32×1000)) = 32 s ≈31×。** 批处理和大规模 Agent fan-out 是同一本账（账 B 公式现用）——**Data 的意义在"数据管道也是 @ray.remote 的 task 集合"，map/batch 都摊到 worker。**

**D3 混合借机（探针实测）：8 台在线保留 60% → 离线可借 floor(8×40%) = 3 台 = 96 worker → 同一批任务 11 s（比单机 32 s ≈快 2.9×）。** **借机是借"空闲"**：在线服务没打满的那 40%，离线批任务拿去秒算。**这是"胶水"的省钱面——不用给离线任务单独买机。**

**D4 峰值抢占（探针实测）：在线高峰要满 8 台 → 离线可用 0 台。** 批任务被抢占暂停/重启=**任务级事件**（账 B5 的重试容器又用上）——**在线优先、离线可弃，因为是 task 不是进程。** 这跟 13-03 账 B5"无状态切流"是同一条纪律在任务域的翻版。

**D5 利用率账（探针实测）：在线单独平均占 45%（峰谷空转）vs 混合后全集群平均 78%（离线批任务填谷）。** 数字口径：45% 与 78% 为作者预置的示例均值。**同一个 8 台集群，只跑在线 = 半夜一堆机器空转；离线任务永远能找到没人要的时段 = 利用率翻着涨。这就是大厂 Agent 平台底层"很多用 Ray"的（算得出来的）理由。**

## 7. 这篇 Ray 账怎么用（一页带走 + 掌握度检验）

**一页带走——给你下一个"要跑成百上千个任务"的服务配 Ray：**

1. **先识别负载归属（账 A）**：并行任务分批 → Ray Data / task fan-out；有状态共享 → 前缀缓存 actor；会话态 → 编排层 checkpoint；只读权重 → 对象广播。两端对齐：K8s 管副本、Ray 管任务，两层都要。
2. **再算墙钟（账 B）**：先报 N（任务数）→ 并行度 = 机器 × worker × 利用率 → 墙钟 = `ceil(N ÷ 有效并行) × 单任务耗时`；失败按任务级重试一次。
3. **再判状态（账 C）**：状态三问——能丢走无状态、可拆走局部+归约、只读走对象广播、粘一个实例才用 actor。
4. **在线-离线分账（账 D）**：在线两层扩缩（Pod 数 × 副本内并发）、离线借空闲、峰值在线优先、填谷利用率才高。

**掌握度检验（读完自答）：**

1. "Ray 五件套各管什么？"（Train 训练 / Serve 在线推理 / Data 批量数据 / Tune 调参 / Workflows 编排——共享同一个 Core 三原语，账 A1。）
2. "task 和 actor 的区别？"（task=无状态远程函数、一次调用一个结果；actor=有状态类实例、串行执行方法——留状态用 actor、没状态用 task，账 A0。）
3. "K8s 和 Ray 谁替代谁？"（都不替代：K8s 管 Node/容器/Pod 副本保活，Ray 管 Pod 内 task/actor/数据——HPA 扩副本做不了 task 级编排，账 A3。）
4. "Agent 开 1000 个任务墙钟怎么估？"（ceil(N÷有效并行)×单任务耗时：128 worker 留 70% 水位 ≈ ceil(1000/89)=12 批×12 s=144 s，账 B3/B4。）
5. "重试一次把成功率提到多少？"（单任务 98%+重试 1 次 → 99.96%、期望失败 0.40——失败是任务级不是整批，账 B5。）
6. "Agent 会话状态放哪？"（编排层 checkpoint，不押在 worker 上——worker 无状态才能大量调度，账 C 场景 2。）
7. "在线-离线怎么共用集群？"（在线两层扩缩保在线、离线借空闲秒算、峰值在线优先、离线填谷利用率从 45%→78%，账 D。）
8. "RAY 的 actor 在什么时候真的必要？"（状态不能丢、又必须粘在一个实例——前缀 KV 缓存的弱粘性（13-03 账 D2），账 C 场景 3。）

## 8. 常见坑（Ray 弹性的 7 个）

1. **拿串行墙钟当任务账单**：写完 for 循环就以为"1000 个任务就是 1000 × 单任务耗时"——没算并行批数（账 B1/B2，384 s vs 12000 s）。
2. **拿理论并行度当有效并行**：128 worker 就算 1 批 8 s——调度排队、水位、失败重跑都要占，留 70% 目标（账 B4，144 s）。
3. **把会话状态塞给 worker**：多轮 Agent 会话让每个 worker 记上下文——状态在编排层 checkpoint，worker 要无状态才好调度（账 C 场景 2）。
4. **看到「有状态 actor」就在一切地方用 actor**：在线 LLM 服务用 actor = 把 13-03 的无会话粘性好牌打烂（hang 住副本、扩不动）（账 C 场景 1）。
5. **只算在线不打混合账**：白天推理机半夜空转——不借机离线批任务，集群利用率停在 45%（账 D3/D5）。
6. **把 Ray 和 K8s 当二选一**：只上 K8s、任务级 fan-out 没人管；只上 Ray、Pod 级保活与网络没人管——两层叠用（账 A3）。
7. **拿"并行提交"当"结果已就绪"**：`.remote()` 即返 ObjectRef 不阻塞——忘了 `ray.get` 收拢，所有任务都以为提交成功（账 A2）。
