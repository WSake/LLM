## 0. 为什么 06 章第二课是 Prompt？

上一章（01-Model-API与流式）教会你"能调模型"：会发请求、会流式、会算账。但"能调"和"调得好"之间隔着一整个类别——**用户得到什么样的输出，一半由模型能力决定，一半由你喂进去的那几行字决定**。Prompt Engineering 回答的就是这另一半：怎么把任务、约束、边界组织成模型能稳定执行的输入（§17.5.2 一句话）。

能力谱系（§6.0）里 Model API → **Prompt** → 结构化输出 → Tool Calling → RAG → Workflow → Agent，Prompt 是"把话说明白"的那一格——它是唯一在每一层都会被反复用到的能力（RAG 的检索结果要靠 prompt 组织和喂进去、Agent 的每一步思考都要 prompt 框架住）。所以 06 章第二课落在它。

一个必须先划清的概念线（§6.3）：

- **Prompt 是"怎么说"**——指令、角色、示例、格式约束，教模型该怎么答。
- **Context 是"给什么"**——检索结果、记忆、工具结果、系统约束，决定模型"看到"什么。
- Prompt 是主语，Context 是宾语；RAG/Agent/Memory 最终都以"把东西装进上下文再写一句好 Prompt"为落点。全章拆开教：本文管 Prompt 那半边（工程化与评测纪律），03-Context-Engineering 管 Context 那半边。

> 🧩 一句话立于全章之先：**Prompt 工程 = 用工程手段（预算、覆盖、评测闸）驯化一段自然语言，而不是把希望寄托在"多加点词"。**

## 1. 一次 Prompt 的六要素链：角色 → 任务 → 输入 → 约束 → 示例 → 边界

§6.2 把一段好 Prompt 的要素列成链：**角色（system）→ 任务 → 输入 → 约束/输出格式 → 示例（few-shot）→ 边界（不知道就承认）**。组装成一次调用就是：

```text
system  你是一名资深的餐厅预订助理，只输出 JSON，
        把用户消息分类为【订位/查询/投诉】三类。← 角色(1) + 任务(2)
user    用户：帮我查一下明天下午的订位情况。      ← 输入(3)
        （约束：只输出 JSON，不解释。…）         ← 约束/格式(4)
        （示例：用户：今晚还有位置吗？→"订位" …）← few-shot(5)
        （边界：若无法分类，输出"unknown"。…）  ← 边界(6)
```

经典模式的演进线（§6.2，要素事实）：`Zero-shot → Few-shot（2020）→ CoT（2022）→ Self-Consistency → ReAct（Agent 雏形）→ Least-to-most / ToT 等进阶`。每一个新模式的本质都是"给模型更多结构"：示例给答案形状，CoT 给思考路径，Self-Consistency 给多次投票，ReAct 给行动空间——**都不是给模型更多知识，而是给更稳的执行框架**。

两个更高级的判断力，先埋在这：

1. **越强的模型越不需要技巧**（§6.2）：2025 年的趋势是 prompt 在"瘦身"（小模型靠多写，强模型一句就够）、context/工具在"变胖"。所以 Prompt 工程的价值曲线是**先陡后平**——格局里有没有微调空间，取决于模型档位。
2. **Prompt 的成本不在"写"，在"每句都要付 token"**：上一章教过计费=输入段+输出段两段收。Prompt 每多一句工程化措辞，都是一次调用里**永远要付的输入 token**——本文实验 A 就是把它量给你看。

> 🧩 本节给你的心智模型：**Prompt = 用 6 个槽位组装的一段输入**。一个槽位一句话，每一句都有 token 成本，选哪些槽位、怎么填，就是工程决策，不是玄学。

## 2. 把"咒语"降维成本机测量（探针设计）

探针 `prompt_engineer_demo.py` 只做一件事：**把 Prompt 工程里一切能用本机算出来的数量，全部量出来**——token 数目、成本、词面覆盖、示例冗余、风格词频、输出预算。四本账对应四件事：

| 实验 | 本机可测的量 | 它默默替你说出的话 |
|---|---|---|
| A 模板账本 | 六版要素链逐版 token/成本/增量 + batch 缓存账 | "prompt 不是免费的，每一句都是预算" |
| B 示例预算 | 词面覆盖率 × 示例集去掉冗余（Jaccard） | "few-shot 是预算不是数量，示例要覆盖全输入面" |
| C CoT 成本 | 模板输入增量 + 输出步数预算表 | "CoT 该留给需要可验证多步推理的任务" |
| D 偏置评测闸 | 5 版 prompt 的 token/句数/风格词/输出预算 + 双口径排序 | "评测选优先过长度/风格/同质/基线四闸" |

两个口径铁律（与全仓一致）：

- **模型侧认知增益一律挂靠，不本机乱测**：探针不训练模型、不假装能测"哪个 prompt 让 LLM 答得更对"。真实的 few-shot ICL 增益是 02-01 `gpt_demo.py` 的解锁相变（同窗 0.320→1.000），真实的 CoT 成本结构来自 02-20 `reasoning_demo.py`（think≈6×）。本文的探针只量**确定性的工程性质**，并把"模型侧该信什么"明确指给既有实测。
- **词面覆盖/示例冗余=规则代理，诚实标注**：B 实验用 jieba 词面重叠定义"覆盖率/冗余度"，这是示例集合的**工程性质**（多样/冗余），不是真实 ICL 增益。就像 06-上下文压缩用 BM25 规则压缩替代 LLMLingua 的"逐 token 打分层"——代理是代理，边界写清楚。

> 🧩 一句话记住探针哲学：**能本机算的，本机算；不能本机算的，指名道姓挂靠——绝不把"感觉"写成"实测"。**

## 3. 实验 A · Prompt 模板账本：每一句工程化都是 token 预算

探针拿同一个任务（"把用户消息分为订位/查询/投诉、输出 JSON"），从 v1 裸任务开始、按 §6.2 要素链一步步**累积**（v2 +角色 → v3 +输入格式 → v4 +约束 → v5 +few-shot → v6 +CoT 提示），逐版量输入 token 与成本（挂靠 01 章计费档 PIN=2.50/百万 token）：

```text
  版本                输入tok    增量tok      成本($)
  v1 裸任务               34      +34    0.00009
  v2 +角色               50      +16    0.00013
  v3 +输入格式             63      +13    0.00016
  v4 +约束               74      +11    0.00018
  v5 +few-shot        112      +38    0.00028
  v6 +CoT提示           130      +18    0.00032
```

三个读数直接进结论：

1. **每一句都是预算**：要素链全长后最重的版本（v6）比裸任务多 **96 token（3.8×）**——你"觉得该写的"每一句角色/格式/约束/示例/CoT，全都在每一次调用里付钱。
2. **few-shot 是增量最大的那一句**：v5（+few-shot）增量 **+38 token**，是全链最贵的单步——示例不是"多放几条无妨"，几条示例 ≈ 一个小型模板的体量（接实验 B 的"少而精"）。
3. **长 system 在批量调用里有缓存杠杆**：同一个长 system（v6）在 batch=10 次调用里复用，命中缓存后输入段打折（挂靠 01 章缓存半价）——无缓存 $0.0036 → 缓存 $0.0022，**省 40.3%**。所以工程化的长 system 不是"贵"，是"建一次、复用很多次"的投资；真正贵的是"每条请求都换一套"的长 prompt。

> 修复站点：A 的实操结论=**prompt 模板做版本管理（要素链分层），长 system 一次性建设并靠缓存复用；few-shot 示例单独管理，不要每版都重抄一遍**。你省下的不只是一个版本的 token，是那个版本在全流量里的每一分钱。

## 4. 实验 B · few-shot 示例预算：示例是预算，不是数量

few-shot 有个经典误区：**"示例越多越好"**。探针把这个误区拆成可测的工程问题：给定 8 条候选示例（4 个意图 × 2 条），预算 k 条，两种"选示范"的策略，谁的**输入面覆盖率**（触达多少意图）高、谁的**示例集冗余**（两两 Jaccard 自我重叠）低：

```text
  覆盖曲线（k=1..4 两种选法：输入面覆盖率 / 示例集内部冗余）
    k=1  相似优先: 0.25 / 冗余 0.00  |  覆盖优先: 0.25 / 冗余 0.00
    k=2  相似优先: 0.50 / 冗余 0.00  |  覆盖优先: 0.50 / 冗余 0.00
    k=3  相似优先: 0.75 / 冗余 0.03  |  覆盖优先: 0.75 / 冗余 0.00
    k=4  相似优先: 0.75 / 冗余 0.05  |  覆盖优先: 1.00 / 冗余 0.00
```

两条线分开读：

- **覆盖率**：相似优先在 k=3 后封顶在 **3/4**（k=4 仍 3/4），覆盖优先 k=4 到 **4/4**。同样把 4 条示例预算全部用完，相似优先漏 1 个意图。查选例——相似优先按"总词面重叠"一把尺子挑，选出 [酒店×2, 天气, 机票]：**词面充足的"酒店"被重复下注 2 次，"外卖"整组落空**（外卖示例几乎不与任何查询词重叠。
- **冗余**：相似优先的示例集内部重叠更高（k=4 时 0.05 vs 覆盖优先 0.00）——重复钓同一个词面 = **同样的 token，花在重复的信息上**。

教学落点（这正是 §17.5.2 衍生里的"few-shot 管理"）：

> **few-shot 是任务级离线预算，不是查询级在线检索**。示例要覆盖整个任务输入面（多样、不冗余），选一次、全流量复用；而"在线挑最相似的片段"是**检索**的活（08-05 查询侧，RAG 的主场）。把检索的"相似优先"误用到 few-shot 上，就是本文实测的这个坑：预算被重复下注、冷门输入面落空。
>
> 真实 ICL 增益（模型侧）：同任务同预算，few-shot 何时解锁、效果随 shot 数的曲线，见 02-01 `gpt_demo.py`（解锁相变 0.320→1.000、shot-scaling 0.673→0.995）——那才是"示例让 LLM 变化"的真实测量，本文的覆盖/冗余是示例集合的工程性质。

> 修复站点：B 的实操结论=**写 few-shot 时先枚举生产会遇到的所有输入面，每面至少 1 条示例、各面互不重复**；预算紧就"少而全"，不要"多而重"。

## 5. 实验 C · CoT 成本账：该留给谁

Chain-of-Thought（CoT，2022）是 §6.2 经典模式里最能"无脑加语句"的一条——但它的成本结构是实打实的。探针量两段：

**输入侧（本机实测）**：裸 system 11 token → 加一句"先一步一步推理，把每一步写在输出里，再给出 JSON" **+17 token（$0.00004·输入档价）**。这句模板是每次调用都付的固定成本。

**输出侧（预算表，模拟性设定、非真实 TPOT）**：

```text
  模式              输出tok        成本($)
  直答                 20      0.00020
  1 步                32      0.00032
  3 步                56      0.00056
  5 步                80      0.00080
  8 步               116      0.00116
```

直答 20 token -> 8 步 116 token，**输出 5.8×**（输出段单价更贵，成本从 $0.00020 涨到 $0.00116）。挂靠 02-20 `reasoning_demo.py` 实测：think 段 ≈ 直答 6 倍输出 token（账单 ×6）；k↔token↔KV 收益递减（k=8 前最陡、k=16 封顶）——**预算买得到的增益是递减的，且上限=分布可达性**。

判断表（要素事实）：

| 任务类型 | CoT 值得吗 | 原因 |
|---|---|---|
| 多步/可验证/数字推理（数学、多跳检索、逻辑） | ✅ 值得 | 一步 exp 贵在有回报：可验证答案让 CoT 的每一步都可检查，预算换正确率 |
| 单步查证/风格/闲聊、被检索结果直接喂答案（RAG）| ❌ 别开 | CoT 只烧 token：对已有答案的复述/重述，增益≈0 |
| 你需要格式化输出 | ⚠️ 用约束（见 04 结构化输出），不是用 CoT | CoT 产生散文式中间过程，不如 JSON 约束直接 |

> 修复站点：C 的实操结论=**CoT 是"预算换可验证增益"的生意，不是默认开关**。做多步推理才值得开；单步查证、RAG 直答、聊聊天的场景开了 CoT，等于白付 5.8× 的输出账（挂靠 02-20）。

## 6. 实验 D · 偏置评测闸：5 版选优的防混料

§17.5.2 的实践是"同一任务写 5 版 system prompt 评测选优"。但评测选优有个反直觉的事实：**你评测的维度常常在替"长度/风格"打工**。探针拿同一任务（提取日期/时间 → ISO 8601）的 5 版 system prompt，量它们的确定性维度：

```text
  版本                  输入tok       句数       风格词数      输出预算tok
  D1 最小指令                16        2          0           40
  D2 +礼貌措辞               34        4          3          100
  D3 +长度通用               31        3          4          120
  D4 +few-shot           42        5          1           60
  D5 +CoT长格式             34        3          3          100
```

然后跑两个"口径"排名（同一组模板）：

- **长度口径**（按模板要求的输出预算排）：前三 = D3（120）→ D5（100）→ D2（100）
- **效率口径**（按输入 token + 风格词最少排）：前三 = D1（16）→ D3（35）→ D2（37）

**同一组模板，长度口径的榜首是 D3，效率口径的榜首是 D1。** 谁赢，不是"模板质量"决定的，是**你选了哪把尺子**决定的。由此引出评测闸四断言（§17.5.2 实践 + 11 评测联动的工程纪律）：

1. **闸1 长度偏置**：D3 的输出预算最高（120 token）——若评测按"篇幅更像真人"或"更详细"打分，它系统性靠前。❌ 先问：你的评分卡把长度混进去了吗？
2. **闸2 风格混料**：D3 的风格词最多（请/详细/完整…，4 个）——若按"礼貌度/认真度"打分，它系统性靠前。❌ 礼貌≠执行正确。
3. **闸3 样本同质**：query 集固定几条、同场景——未覆盖全部输入面，"单样本变好"不可外推。❌ 评测集必须覆盖任务输入面（与 11-评测的分布公平一脉相承）。
4. **闸4 无基线**：5 版都没有纯裸版对照组——选优必须有 baseline，否则你选出的不过是"这 5 版里最不差的那个"。✅ 对照实验第一原则。

> 修复站点：D 的实操结论=**想选优，先建评分卡（任务正确率为主维度），再让上面四闸把"长度/风格/同质/无基线"的污染拦在门外**；样本集要覆盖输入面、必带裸版 baseline。这是"从咒语到科学"的最后一颗钉子：不是"哪个 prompt 灵"，而是"在我的评测口径下、用我的正确率标尺、过完四闸后，哪个值得上线"。

## 7. 常见坑（5 条）

1. **拿"例句多"当兜底**：few-shot 不是越多越好——示例是预算，冗余示例花同样的 token 不增信息（本文 B：相似优先把 4 条预算花出 3/4 覆盖、0.05 冗余）。**写示例先枚举输入面（每面一条、互不重复），预算少而全**。
2. **把检索当 few-shot**：在线挑最相似的片段是检索（RAG，08-05），few-shot 是任务级的离线预算。把"相似优先"用在示例集上 = 重复下注同意图、冷门输入面落空（本文 B 实证）。
3. **无脑开 CoT**：CoT 的输出账是直答的 5.8×（本文 C）。多步/可验证才值得；单步查证/风格/直接 RAG 喂答案的场景，CoT 只烧 token（挂靠 02-20 think≈6×）。
4. **评测选优只信"感觉更好"**：同一组 5 版 prompt，长度口径榜首和效率口径榜首不同（本文 D）。**选优必须 = 正确率评分卡 + 长度/风格/同质/基线四闸**，否则你在替"措辞风格"打分。
5. **把 Prompt 当万能药（prompt 瘦身趋势）**：越强的模型越不需要技巧（§6.2）。先想清楚"是模型不知道，还是你没说清"——如果模型知识/检索/工具是瓶颈，加 Prompt 只能安慰自己（§6.3：Context 是"给什么"，Prompt 是"怎么说"）。

## 8. 诚实边界（AAA 自我审查）

1. **词面覆盖/冗余=规则代理，不是真实 ICL 增益**：实验 B 的"覆盖率 3/4 vs 4/4、冗余 0.05"是 jieba 词面重叠算出来的示例集合工程性质；真实 few-shot 让 LLM 变化的效果（解锁相变/ shot-scaling）是 02-01 `gpt_demo.py` 的既有实测，本文只替它指路、不本机复测。把"示例集合多样"说成"模型会答得更准"，是越界。
2. **CoT 输出预算是模板设定，不是真实 TPOT**：C 实验的"每步 12 token、直答 20 token"是模拟设定，表里数字只演示"步数×步长×单价"的成本结构；真实模型 CoT 的 token 分布（think≈6×）与预算上限挂靠 02-20。价格表 PIN/POUT=要素事实（非本机实测）。
3. **jieba token 非真实 tokenizer**：所有 token 数（34→130、+17、直答 20 等）都是 jieba 分词计数，与真实模型 BPE 计费 token 不同（真实 API 以 `usage` 为准）；本文用它演示"每句措辞的**相对**成本结构"，不假装是真实计费数。
4. **风格词频只量词面**：D 实验的"风格词数"是字符串计数（请/详细/完整…出现次数），"礼貌度"是模拟口径——它演示的是"口径能改变榜首"的机制，不是真实评估该用什么口径。
5. **B 的"覆盖优先"是一个构造策略**：它按意图显式去重，是 few-shot 管理的教学代理；真实生产还混杂任务语义、领域分布等更细腻的取舍。本文只证明"词面级的多样 vs 冗余可测"，不宣称覆盖优先是最优策略。
6. **四闸是工程纪律不是数值定律**：闸1-闸4 是评测工程的做法（要素/经验），不是数值上可证明的结论；"长度口径榜首 D3"是确定性读数，但"该选谁"必须等真机评测。
