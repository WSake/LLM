## 0. 为什么 06 章第五课是工具调用？

06 章的能力谱系里，每一级都在回答一个问题（§6.0）：04 解决了「怎么拿到机器可用的结果（Structured Output）」，这一级再往前推一格——**「怎么让模型真去调外部工具、并让结果回流」**。结构化输出只规定了「结果长成什么样」；工具调用规定的是「结果要不要直接变成一个函数调用」。二者共享同一种 Schema 语言，但作用点不同：04 是**结果侧**的契约，本篇是**入参侧**的契约。

为什么需要单独一课？因为「工具调用」不是提问技巧，是**接口纪律**——它把 04 的 Schema 从「约束输出」升级为「约束入参」，并带来四个结构性新问题：

1. **入参形态**：同一件事，散文回答、JSON 回答、`tool_calls` 调用，哪一种能把参数直接交给函数执行？
2. **入参校验**：FC 给了「形状」，值域的规矩（必需/类型/范围/格式/未知参数）谁来守？
3. **并行调度**：一次要调多个工具时，哪些可以并行、哪些必须串行？
4. **回喂循环**：工具报错、结果超长、多轮收敛——错误/长结果/轮次怎么收（这就是 Agent Loop 最小闭环）。

§6.5 给的时间线：2023 年 6 月 OpenAI 把它做成 API 原语后，Agent 的地基才成立；§17.5.4 给的两个论文起点：**Toolformer（2023）**（让模型自己学"何时调工具/调什么"）与 **Gorilla（2023）**（调用庞大 API 集合）。这三个外部坐标都是「要素事实，非本机实测」。

> 🧩 一句话立于全章之先：**04 定义「结果长什么样」，本篇定义「结果能不能直接执行」——同一种 Schema 语言，作用点从结果侧挪到入参侧，再加上一个把错误与超长收进闭环的循环。**

## 1. 先把问题拆开：把 Schema 从「结果约束」写成「工具入参约束」

工具调用的完整闭环（§17.5.4 实践题：做一个「查天气+订日程」双工具助手）：

```
声明：把工具用 JSON Schema 讲清楚——名称 / 描述 / 参数类型与要求（get_weather(city, date) …）
调用：模型在回复里"请求调用"——给 name + arguments（不再是散文，是结构化的函数调用）
执行：应用端查表运行真实函数（get_weather 打天气接口、add_event 写日历）
回喂：把执行结果（含报错）拼进上下文 → 模型看到结果再决定下一步
循环：思考 → 调工具 → 看结果 → 再思考 …… 直到任务完成 = Agent Loop（§9 的行动接口）
```

方法演进主链（04 已有）：提示词「请输出 JSON」→ JSON mode → Structured Outputs → **function 参数复用**。前三档约束的是「输出的样子」，第四档约束的是「输出的**用途**」——它要直接变成函数入参。§6.5 原话：**function 参数复用 = 各家 API 一致的第四档**。

四个可度量的工程问题（与 04 同构，本片逐一定实验）：

| 问题 | 你在决定什么 | 对应实验 | 可度量指标 |
|---|---|---|---|
| Q1 靠哪一档 | 散文 / JSON mode / Function Calling | A | 可直接派发率、键名对齐率 |
| Q2 入参校验器管什么 | 必需/类型/范围/格式/未知参数 | B | violations 台账、直接执行比例 |
| Q3 并行还是串行 | 工具依赖 DAG | C | 往返轮次、省轮率、依赖强制 |
| Q4 循环怎么收 | 报错/超长/收敛轮次 | D | 自愈率、回喂 token、收敛轮次 |

探针的业务题取 §17.5.4 的「实践」原话：**查天气 + 订日程双工具助手**。同一批预置任务/产出，对同一套工具 Schema 跑三档 + 并行分层 + 回喂闭环。于是每个数字都是确定性的、随时可复现。

## 2. 把「工具调用」降维成本机测量（探针设计）

探针 `function_calling_demo.py` 照 04 模式：零网络、零下载、不训练模型、纯 stdlib 确定性计算。三项工程声明立规矩：

1. **双工具助手 Schema**：`get_weather(city 必需, date 必需·格式 YYYY-MM-DD)` 与 `add_event(title 必需, start_time 必需·格式 YYYY-MM-DD HH:MM, duration_min 15–240, remind 0–120)`——参数语义写清楚（陷阱一），日期用格式强约束。
2. **三档管法**：
   - 散文：只给自然语言答复，参数埋在句子里；
   - JSON mode：输出能 `json.loads` 的 JSON，但工具名/键名/封装因模型而异（键名对齐率是它的命门）；
   - Function Calling：托管侧按 `tools` 声明给 `name+arguments`（形状 promise），值域规则由应用端校验器把守。
3. **两套判据**：A 量「能否不经样板解析直接派发」；B 量「10 条 FC arguments 过入参 Schema 的台账」。

四账与四个问题一一对应：**A 入参形态账 · B 入参校验账 · C 并行调用账 · D 循环回喂账（+ 选择树 8 场景）**。

## 3. 实验 A · 入参形态账（散文 vs JSON mode vs FC）

同一个 7 任务集（查天气/订日程/查多城…），三档「产出」分别交给执行层看「谁能直接被函数执行」：

```
[实验 A] 入参形态账 —— 同一个 7 任务集，三档产出谁能不经样板解析直接派发
  散文档   自然语言陈述结果、参数埋在句中 → 可直接派发 0/7（需人读/正则拆参数）
  JSON mode  格式必合法，但工具名/键名/封装因模型而异 → 键名对齐可解包执行 2/7
  Function Calling  托管侧按 tools 声称 name+arguments 形状 → 可直接派发 7/7
  → 三档差价不在「能不能生成 JSON」，在「参数能否按函数签名对齐」：FC 把对齐做成强制的
  台账：散文=全无结构 · JSON=结构随缘（5 条漂移：别名/嵌套缺层/未知键→映射补丁）· FC=形状兜底
```

**教学落点：**
- **三档差价不在格式，在对齐**：散文 0/7——参数埋句子，没有可编程的边界；JSON mode 2/7——5 条漂移（工具名写成 `weather`、参数键写成 `城市`、多包一层、多塞 `mode`）都要靠你自己的映射补丁撑过去；FC 7/7——`name`+`arguments` 的形状是托管侧 promise。**散文/JSON 的差价=解析样板代码与键名漂移，FC 的兜底是把「对齐」从 prompt 挪进 API 声明层。**
- **json.loads 通过 ≠ 能执行**（04 的翻版）：即使 `json.loads` 成功，键名对不上函数签名，你的 dispatch 照样拿不到参数。键名对齐是「能落库」在入参侧的对应物。
- **映射补丁就是技术债**：JSON mode 的 5 条漂移，每一条在你代码里都对应一行 `.get()`/改名/拆包逻辑；工具结构一变，这些补丁全要跟着改（§8 口径：「改 Schema 一处，解析侧校验侧同步变」）。

## 4. 实验 B · 入参校验账（10 条 FC arguments 台账）

FC 保证「壳」：`name` 必在 `tools`、`arguments` 必是声明参数的合法 JSON。但**值域的规矩仍是业务规则**——把校验器写在调用执行之前，对 10 条 FC `arguments` 逐条跑（复用 04 同一把 Schema 尺，只是作用点换成入参）：

```
[实验 B] 入参校验账 —— 10 条 FC arguments 过入参 Schema（FC 只兜'形状'，值域规则仍归你）
  get_weather(city 必需·date 必需·date 格式 YYYY-MM-DD) · add_event(title 必需·start_time 必需·duration 15-240·remind 0-120)
  b   参数形状                    校验结果（violations）
  b1   合法(对照)                      ✓ 通过（可直接执行）
  b2   缺必需-city                    缺必需字段: city
  b3   类型错-duration 字符串            类型错: duration_min（期望 integer）
  b4   range 越界-duration 5         range 越界: duration_min=5 < 15
  b5   range 越界-remind 300         range 越界: remind=300 > 120
  b6   缺必需-title                   缺必需字段: title
  b7   格式错-date 下周一                格式错: date（期望 YYYY-MM-DD）
  b8   类型错-remind 小数               类型错: remind（期望 integer）
  b9   未知参数-mode                   未知参数: mode
  b10  合法(get_weather 两参)          ✓ 通过（可直接执行）
  统计：缺必需 2·类型错 2·range 越界 2·格式错 1·未知参数 1 → 可直接执行 2/10
  台账：FC 兜「壳」（name+arguments 必为声明形状）；值域=必需/类型/范围/格式/未知仍由入参校验器把关——
         04 那把 Schema 尺原样复用——一次写好校验器，结果侧与入参侧共用（FC≠免校验）
```

**教学落点：**
- **FC 是「半程保证」**：10 条里直接执行 2/10——形似合法，值域各异。缺必需/类型错/range 越界/格式错/未知参数，一个都不少。**FC 兜形状、校验器兜值域，两条线各管一截**；把「FC 有了校验器就免了」等同于把「JSON mode 有了语法就免校验」。
- **校验器分类即业务分类**（04 同构）：缺必需（b2/b6）→ 完整性；类型错（b3/b8）→ 契约违约；range 越界（b4/b5）→ 业务边界；格式错（b7）→ 规格违约；**未知参数（b9 `mode`）→ FC 特有的坑**——模型塞了工具不认识的参数，校验器应标注/拒绝（静默忽略会让调用语义偷偷跑偏）。
- **生产纪律**：入参校验写在 `dispatch` 门口（执行真实函数之前），校验结果落日志一般，供 04-10 / 08-13 式复盘（挂靠：评测门禁、失败模式诊断）。一次写好，结果侧（04）与入参侧（本篇）共用同一把尺。

## 5. 实验 C · 并行调用账（依赖 DAG → 拓扑分层）

一个回复同时请求多个工具 = 并行调用（§6.5：**Agent 效率的关键**）。但「能不能并行」由工具间的数据依赖决定——把它建成 DAG，按拓扑分层（每层内的工具彼此无依赖，可一次并行）：

```
[实验 C] 并行调用账 —— 独立并行省轮 vs 依赖强制串行（工具依赖 DAG → 拓扑分层）
  t1  查北京天气+订团队会（无依赖）          → 层1 {get_weather, add_event} · 1 轮往返
  t2  查北京+上海两城天气（同工具）          → 层1 {get_weather, get_weather} · 1 轮往返
  t3  先查天气按天气订跑步日程（依赖）         → 层1 {get_weather} → 层2 {add_event} · 2 轮往返（并行=add_event 参数凭空编造，断言不可行）
  往返账：独立任务并行 2 轮 vs 串行 4 轮（t1/t2 每例省 50% 模型往返）· 依赖任务并行=编造参数，断言不可行
  台账：并行的判据不是「看着不相关」而是「DAG 同一拓扑层」——有数据依赖的步骤必须等上游结果回喂
  断言：拓扑分层 3/3（层数=依赖链长度 1·1·2，独立必入同一层）
```

**教学落点：**
- **并行省的是「模型往返轮次」**：t1/t2 各自 1 轮搞掂 vs 串行 2 轮=省 50% 往返。Agent 效率的关键，就藏在把无依赖的调用合并进同一轮里（§6.5 原话）。省的不只是延迟，还有顺着轮次累积的上下文（每轮重发全部历史）。
- **依赖是硬边界**：t3 若强行并行，`add_event` 时 `get_weather` 的天气还没回来——日程参数凭空编造（这正是真实 Agent 幻觉的一大来源）。**并行的判据不是「看着不相关」，而是「DAG 同一拓扑层」**：有依赖边的步骤必须等上游结果回喂。
- **分层即答案**：把依赖 DAG 做拓扑分层（每轮一批入度 0 的工具），轮数=链长（1·1·2）。这就是 Agent 执行器的「并行度」解释（挂靠 09-Agent：工具并行是其效率内建设施；框架层 LangGraph/MCP 帮你固化成原语）。

## 6. 实验 D · 循环回喂账（报错自愈 · 结果截断 · 收敛 + 选择树）

Agent Loop 的最小闭环：模型思考 → 调工具 → 看结果（含报错）→ 再思考 → 直到完成。三个可度量维度：

**① 报错自愈**——工具报错是常态，错误文本必须回喂给模型（错误即上下文），让其修正参数重试（§6.5 陷阱三：**工具报错要喂回去让模型自愈**）：

```
[实验 D] 循环回喂账 —— 报错自愈 · 结果截断 · 收敛轮次（Agent Loop 最小闭环）
  工具报错回喂（错误文本喂回 → 模型修正参数 → 重试，修正路径为本模拟预置）：
  e1  get_weather 城市 'BeiJing' 不在已知城市列表 → 重试1: 改 city='北京' → 成功（重试 1 次）
  e2  add_event duration_min=5 低于下限 15 → 重试1: 改 duration_min=30 → 成功（重试 1 次）
  e3  get_weather 日期 '下周一' 无法解析 → 重试1: 仍无法解析 → 重试2: 改 date='2026-09-28' → 成功（重试 2 次）
  自愈台账：报错 3/3 经错误文本回喂修复 · 总重试 4 次 · 轮上限 5 未触发（死循环由轮次上限兜底）
  结果超长回喂（挂靠 08-06 上下文压缩）：原样回喂 83 tok vs 压缩摘要 23 tok → 每轮上下文增速省 72.3%（工具结果不截断=上下文被工具占满）
  收敛轮次（完成任务的 loop 往返轮数，3 个任务）：2·3·2 → 平均 2.33 轮 · 轮上限 5 未触发
```

**② 结果截断**——工具结果超长要截断/压缩（§6.5 陷阱二）。一次日程冲突明细原样 83 tok vs 压缩摘要 23 tok，**每轮上下文增速省 72.3%**；轮次越多省得越狠（挂靠 08-06 上下文压缩的「检索多用、生成用精」：回喂的量也要按需压缩）。

**③ 收敛**——循环必须收敛：3 条任务完成轮数 2·3·2，平均 2.33 轮；**轮上限 5 兜死循环**（这就是 Agent 循环的保险丝）。工具描述不清、长结果不截断、报错不回喂，三个陷阱全都会把轮数往上顶。

**选择树（8 场景，规则：真实外部工具→FC；多工具无依赖→FC 并行；工具间数据依赖→FC 串行；内部标量→JSON mode；纯问答→直接生成；结果超长→FC 截断回喂；工具报错→FC 错误回喂；多工具固定链式→FC+Workflow）**：

```
  选择树 8 场景（规则：真实外部工具→FC；多工具无依赖→FC 并行；工具间数据依赖→FC 串行；
                   内部标量→JSON mode；纯问答→直接生成；结果超长→FC 截断回喂；
```

## 7. 常见坑（5 条）

1. **嵌入式 JSON 手动解析 + 键名漂移补丁**：`json.loads` 后一堆 `.get()`/改名/拆包，每个工具一份 = 技术债。用 FC 的 `name+arguments` 直出 + 入参校验器（A：JSON mode 键名对齐仅 2/7，漂移 5/7）。
2. **以为 FC 参数免校验**：FC 只兜形状，值域（必需/类型/范围/格式/未知）由你的校验器把守（B：直接执行 2/10）——**04 的尺子原样复用，别再造一个**。
3. **见到多工具就并行**：依赖 DAG 有边时并行=参数凭空编造（C：t3 并行=`add_event` 编造日程）；「看着不相关」≠「同一拓扑层」，分层后再并行。
4. **工具结果原样回喂**：一次长结果占满上下文，轮次越多爆得越快（D：83→23 tok 省 72.3%，挂靠 08-06）。长结果截断/压缩，报错也要回喂（不沉默）。
5. **循环没有轮上限 / 工具描述写不清**：必须设轮次上限防死循环（D：上限 5、收敛 2·3·2）；工具描述要写清参数语义（§6.5 陷阱一）——语义不清=模型瞎传参=回喂闭环里多磨几轮。

**口径声明（哪些是近似/非本机）：**
- **散文/JSON/FC 的「模型产出」= 作者预置仿真样例**（词面代理，覆盖常见失败形态 + FC 形状 promise），非真实模型在真实 prompt 下的采样；真实行为因模型/温度/工具定义而异——但机制结论（形态差价、入参校验、依赖分层、回喂闭环）与输入无关，换个数据集比例会变、方向不变。
- **FC 形状保证**（`name` 必在 `tools`、`arguments` 必为声明参数的合法 JSON、一次回复可并行多条）= 托管侧 promise，**非本机实测**（写作环境无外网未在线复核，精确行为以各家 API 文档为准）。
- **报错自愈修正路径 = 预置仿真**：e1/e2/e3 的「模型改参数」是固定路径；真实模型在真实错误文本下的修正行为非本机实测。
- **收敛轮次（2·3·2）** = 3 条预置完成路径的样例，非采样统计；平均 2.33 轮仅代表这批预置路径。
- **论文/时间线**（Toolformer 2023 · Gorilla 2023 · OpenAI 2023-06）= 要素事实，非本机实测；**token 估算** = 中文 1 字 1 + 英文/数字连续段 1（非真实 tokenizer，相对账同口径不变）。
