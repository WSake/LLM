## 0. 为什么 06 章第四课是结构化输出？

06 章的能力谱系里，每一级都在回答一个问题（§6.0）：03 解决了「怎么把话说明白（Prompt）」和「给什么（Context）」，这一级解答 **「怎么拿到机器可用的结果」**——业务系统要的是可落库的 JSON/表格，不是散文。

为什么需要单独一课？因为「机器可用」是个**双层**问题，只靠提示词解决不了第二层：

1. **第一层 · 合法（语法层）**：输出得能被 `json.loads` 解析——不能有前缀散文、尾随逗号、单引号。
2. **第二层 · 合规（结构层）**：即使解析成功，字段得齐全、类型要对、枚举值得合法、年龄不能是 175。这一层**与模型强弱无关**——越强的模型格式服从越好，但「必须带 insured_name、age 必须 ∈[0,120]」是业务契约，不是文采。

§6.4 给的方法演进把两层分别交给谁管：提示词「请输出 JSON」（不稳定，两层都靠运气）→ **JSON mode**（2023，强制第一层合法）→ **Structured Outputs / JSON Schema 约束解码**（2024，按 Schema 逐 token 约束，**两层都 100%**）。落到实现原理上，就是 constrained decoding：SGLang 的 Structured Outputs、vLLM 的 guided decoding、Outlines 库，把 Schema **编译成 token 级状态机**——模型只能从当前 Schema 允许的 token 里选。

> 🧩 一句话立于全章之先：**JSON 合法 ≠ Schema 合规。合法是及格线，合规是契约线；结构化输出的进化史，就是契约线从「生成后修补」走到「解码中被强制」。**

## 1. 先把问题拆开：合法 vs 合规 · 三档方法的进化脉络

| 档位 | 谁在保证 | 保证了什么 | 结构不合怎么办 | 上手成本 |
|---|---|---|---|---|
| **提示词**「请输出 JSON」 | 模型自觉 | 不保证 | 重试 / 后处理 / 落库报错 | 零 |
| **JSON mode**（2023） | 托管侧 | 输出一定可解析（第一层） | 校验器兜底（第二层仍靠自觉） | 一行参数 |
| **Structured Outputs**（2024） | 解码侧状态机 | 输出一定可解析 **且** 符合 Schema（两层） | 生成时根本走不出来 | 传 Schema |
| **function 参数复用** | 解码侧 + 轮询 | 与上同，且参数就是工具入参 | 同左（各家一致） | 声明工具 |

四个可度量的工程问题（与 03 同构，本片逐一定实验）：

| 问题 | 你在决定什么 | 对应实验 | 可度量指标 |
|---|---|---|---|
| Q1 靠哪一档 | 提示词 / JSON mode / 约束解码 | A | 语法合法率、结构达标率、全程落库率 |
| Q2 校验器管什么 | 必需字段/类型/枚举/范围/嵌套 | B | violations 台账、直接落库比例 |
| Q3 解码侧拦到哪 | 语法层还是结构层 | C | 解码侧拦截数、拦截层位 |
| Q4 用哪家定档 | JSON mode vs SO vs func 调用 | D | 成本、一次过率、8 场景选择树 |

探针的业务题取 §17.5.3 的「实践」原话：**让模型输出一份保单抽取结果**。10 条「模型原生输出」预置好（覆盖语法层 + 结构层的常见毛病），对同一张业务 Schema 跑三档。于是每个数字都是确定性的、随时可复现。

## 2. 把「结构化」降维成本机测量（探针设计）

探针 `structured_output_demo.py` 照 03 模式：零网络、零下载、不训练模型、纯 stdlib 确定性计算。三项工程声明立规矩：

1. **业务 Schema（保单抽取）**：required=`insured_name/age/policy_type`；`age`∈整数[0,120]；`policy_type`∈枚举 {medical, life, auto, property}；`premium`≥0；`address.city` 必需。
2. **三档管法**：
   - 提示词法：只跑 `json.loads`——合法靠运气，合规靠模型自觉；
   - JSON mode：模拟「语法必合法」，看结构层还漏多少；
   - 约束解码：字段级状态机最小模拟——每字段报告「第一违规点」在哪被拦。
3. **指标**：语法合法率 / 结构达标率 / 落库率 / violations 台账 / 解码侧拦截数 / 输出当量（重试按再生成一遍计）。

## 3. 实验 A · 方法演进：稳定性账（提示词 vs JSON mode vs 约束解码）

同一批 10 条保单抽取的「模型原生输出」，逐条交给解析层看，再交给完整业务 Schema 看：

```
[实验 A] 方法演进 —— 同一批 10 条原生输出，三档各自拦到哪一层
  提示词"请输出 JSON"（只靠 json 解析）：语法合法 7/10
  其中过完整业务 Schema（必需+类型+enum+range+嵌套）= 1/10
  → 提示词法全程达标（能直接落库）1/10 —— 解析合法≠结构合规：7 条能 parse、只有 1 条真能落库
  台账：方法演进=把「合法」从碰运气挪到受控：提示词(碰运气)→JSON mode(文法层强制)→约束解码(结构层强制)
```

**教学落点：**
- **提示词法是「碰运气式」的**：10 条里 7 条能 parse，但只有 1 条真能落库——**合法率 70%、全程达标率 10%**。两层的巨大落差，正是「合法 ≠ 合规」的数字证据：解析成功只是入场券，结构契约才是考卷。
- **JSON mode 治标不治本**：它把这 3 条语法失败的兜回来了（输出必合法），但 6 条结构不合（缺字段/类型错/枚举错/范围错）依旧原样进生产——**JSON mode 管「能不能解析」，管不住「该不该长这样」**。
- **约束解码治本**：结构不合的 6 条在解码途中就出不来（见实验 C），全程落库率 10/10。方法演进的本质，是把两层责任从「模型自觉」移交到「系统强制」。
- **与模型强度正交**（挂靠）：模型越强，散文式「请输出 JSON」的遵守率越高——但这只是把第一层失误概率压低，第二层的业务校验任何模型都不该背（§6.4 实践原话：**优先用 Schema 约束，不要正则清洗散文式输出**）。

## 4. 实验 B · Schema 校验：落库账（逐条 violations 台账）

把校验器写在落库之前，对 10 条逐条跑，得到一张 violation 台账（每字段只报第一处违规，确定性顺序）：

```
  c1   合法(对照)            ✓ 通过（可直接落库）
  c2   语法-前缀散文          语法层: 首个非空字符应为 '{'，实际为散文文本
  c3   语法-尾随逗号          语法层: 对象闭合前多余 ','
  c4   语法-单引号           语法层: JSON 规范只允许双引号包裹字符串
  c5   缺必需字段            缺必需字段: insured_name
  c6   类型错-age字符串       类型错: age（期望 integer）
  c7   enum 拼错           enum 越界: policy_type='medicl' ∉ {medical, life, auto, property}
  c8   range 越界-age 175  range 越界: age=175 > 120
  c9   range 越界-premium 负 range 越界: premium=-5.5 < 0
  c10  嵌套缺必需 address.city 缺必需字段: address.city
  统计：语法层失败 3 · Schema 层失败 6（缺必需 2·类型错 1·enum 越界 1·range 越界 2）· 直接落库 1/10
```

**教学落点：**
- **校验器的分类就是业务的分类**：缺必需（c5/c10）→ 数据完整性；类型错（c6 「30」写成字符串）→ 契约违约；enum 越界（c7 `medicl` 拼错）→ 词表违约；range 越界（c8 175、c9 -5.5）→ 业务边界违约。这张台账就是**结构化输出检查表**，逐条修 = 逐条把风险关掉。
- **「能解析」与「能落库」中间隔着一整个校验层**：直接落库 1/10。没有校验器，这 9 条会以各不相同的方式进库（坏的进库比不进库更可怕——查询时静默返回错的字段/值，08-13 的失败账本里就有这一族的根因）。
- **生产纪律**：Schema 校验器是**落库前唯一的一道闸**，写在解析与写入之间；校验结果必须落日志（哪条、哪个字段、哪个规则），供 04-10 / 08-13 式诊断复盘（挂靠：评测门禁、失败模式诊断）。

## 5. 实验 C · 约束解码：拦截账（解码侧 9/10 被叫停）

这是与 JSON mode 的分水岭。约束解码 = 把 Schema 变成解码时的状态机：每生成一个 token 之前，先问「下一步允许是什么」。模拟器逐字段报告「第一违规点被叫停」：

```
  c2   语法-前缀散文       L1 语法·对象起始      首字符'已'即被挡——解码器只许 JSON 字面量开头
  c3   语法-尾随逗号       L1 语法·对象收尾      闭合','前即被挡——对象不允许尾随逗号
  c6   类型错-age字符串    L2 Schema·类型栅栏   生成该字段处被拦（age 期望 integer，字符串引号进不来）
  c7   enum 拼错        L2 Schema·词表筛选   生成该字段处被拦（'medicl' 不匹配任何 enum 成员前缀）
  c8   range 越界-age175  L2 Schema·range 校验 生成该字段处被拦（175 越过上限 120）
  解码侧拦截 9/10 · 放行 1/10（c1 合法对照）——语法 3 挡在 L1，结构 6 挡在 L2
```

**教学落点：**
- **约束解码把「重试」变成「不存在的路径」**：9 条里有 8 条（3 语法 + 6 结构）在做后处理/重试前就被拦在解码侧——模型**根本说不出**`medicl`/`175`/缺 `insured_name` 的 JSON。对比 JSON mode：拦 3 个语法，6 个结构照样进流。这就是「JSON mode=文法保险丝、约束解码=契约保险丝」的可测含义。
- **拦截是「车道」不是「芭蕉扇」**：状态机不是把 bad 输出扫掉，而是**从一开始就不让 bad token 进入采样分布**（该位置不可用的 token 置 0 概率）。e.g. `age` 期望 integer 时，`"`（字符串引号）在该位置概率就是 0——所以 c6 的错发生在「值开头」，而不是「解析之后」。
- **range 约束是分层技巧**：`age≤120` 并非不可做——解码器对数字 token 做前缀约束（首位只许 0/1/2…，到大数边界逐位收紧）。这解释了为什么「枚举/类型」好保证、「范围/长度」是真工程（本机最小模拟=字段级截停，真实实现的 token 级细节=非本机实测，见 §8）。
- **挂靠**：真实库是把 Schema 编译成 token 级状态机——SGLang Structured Outputs / vLLM guided decoding / Outlines；论文起点 JSONformer / Guidance（§17.5.3，要素事实，非本机实测）。

## 6. 实验 D · 成本与选择树（输出当量账 + 8 场景定档）

**成本账**：重试/后处理的每一遍 = 重发输入 + 再生成 + 再校验。把「每条修复按再生成一遍计」（等长近似），10 条批量的输出当量：

```
  输出当量账（10 条首次 + 每条修复按再生成一遍计，等长近似）：base=167 tok
  方法            当量倍数   输出 token      $(10.0/M)    落库一次过率
  提示词法          ×1.9    317       $0.00317      1/10  · 9 条需重试/后处理
  JSON mode     ×1.6    267       $0.00267      1/10  · 语法全过·6 条结构后处理
  约束解码          ×1.0    167       $0.00167      10/10  · 0 重试 0 后处理
```

**教学落点：**
- **「碰运气」最贵**：提示词法当量 ×1.9——9 条里有 9 条需要再生成一遍（3 语法 + 6 结构），每遍都是 full round trip。省的不是几行 prompt，是**结构化输出不能靠返工**：返工最不可预测的就是它还未必一次就修对。
- **一次过率是三个档位最硬的 KPI**：10/10 vs 1/10（JSON mode 语法全过、结构仍 1/10）。落库一次过率直接决定你后端的 if-else 数量与报警量。
- **省下的钱去哪了**：×1.9→×1.0 不只是少付 token，还少付「重试逻辑的存在感」——重试、退避、幂等这些 01 章讲过的分布式纪律，在约束解码下从「每轮都要防」降为「兜底路径」（挂靠 01 章重试超时、02 章 token 账）。

**选择树（8 场景，规则：要调工具→FunctionCalling；嵌套或严格落库/强类型下游→StructuredOutputs；标量+内部→JSON mode）**：

```
  s1  保单抽取(嵌套+枚举+严格落库)  → StructuredOutputs
  s2  订单地址归档(嵌套+落库)      → StructuredOutputs
  s3  分类标签(标量枚举·内部)      → JSON mode
  s4  摘要自由文本(仅打包)        → JSON mode
  s5  调保存笔记工具             → FunctionCalling
  s6  调天气工具(宽松参数)        → FunctionCalling
  s7  内部批量解析标量           → JSON mode
  s8  合规审计导出(严格+落库)     → StructuredOutputs
  断言：8 场景判定全部给出 = 8/8
```

- **定档口诀**：图省事但有下游契约 → 至少 JSON mode + 校验器；**结构复杂（嵌套/枚举/强类型落库）→ Structured Outputs**；要把输出直接当工具参数 → **function 参数复用**（各家一致，下一站）。（官方口径=要素事实：JSON mode 是「best-effort」schema 遵守，Structured Outputs 才保证完整遵守且对不支持的 Schema 直接报错。）

## 7. 常见坑（5 条）

1. **以为「请输出 JSON」就够了**：合法靠运气（语法 7/10）、合规靠自觉（结构 1/10）。上线前先跑一遍自己的样本集，量「直接落库率」（实验 A）。
2. **`json.loads` 通过就放行**：解析通过 ≠ 业务合规——缺字段/类型错/枚举错/范围错照旧（实验 B 台账）。必须配有 Schema 校验器，且校验器是落库前唯一一道闸。
3. **校验器散落各处 / 用正则补丁撑结构**：每条查询各写各的 `.replace()` 修补 = 每条都是技术债。把「校验 → 修复 → 落库」收敛成一个入口；结构改了，改 Schema 一处，解析侧校验侧同步变（§8 口径）。
4. **一律上 Structured Outputs**：标量 + 内部低风险场景（s3/s4/s7）用 JSON mode + 代码校验足够——省的是状态机复杂度，不是省钱（×1.6 vs ×1.0 的差距远小于耦合的复杂度代价）。
5. **忘了「约束」本身也是上下文**：03 实验 A 里那句自然语言约束（「回复用一句话」）在格式敏感任务上会被陪跑块冲淡——把**格式约束从 prompt 搬进 Schema**，就是本课对 03 的四口衔接：约束变状态机，就不靠模型记住。

## 8. 诚实边界（AAA 自我审查）
