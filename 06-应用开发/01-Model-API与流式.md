## 0. 为什么 06 章第一课是 Model API？

知识地图 §6.0 把能力的成长画成一条谱系：

```text
Model API（最基础） → Prompt → 结构化输出 → Tool Calling → RAG → Workflow → Agent → Multi-Agent → 行业产品
   每次升级都在回答一个问题：
   ① 怎么把话说明白（Prompt）
   ② 怎么拿到机器可用的结果（Structured Output）
   ③ 怎么让模型"动手"（Tool Use）
   ④ 怎么让它"知道更多"（RAG）
   ⑤ 怎么把多步任务串起来（Workflow）
   ⑥ 怎么让它自己规划、试错、反思（Agent）
```

**Model API 是这条链的最底层**——后面所有环节（RAG 的检索结果要喂给模型、Agent 的每一步要调模型、工具调用要模型给出结构化参数）最后都收敛到"以某种方式调用模型"。所以 06 章从它开篇：概念先于框架（§6 章首原话），而 Model API 是"概念层的第一个概念"。这一章不教你用某个 SDK 的某个函数，而是教你**接口背后那三件与 SDK 无关的基本功**——换任何一家 API、任何一套 SDK，叁件都成立。

本篇同时是**路线 B（应用/工程）的起点**：路线 B 不碰模型权重，从"会调用模型"干起。接下来 02-Prompt 教"怎么把话说得让模型听懂"、04/05 教"怎么拿到机器可用的结果和让模型动手"，一层层往 Agent 走；到了 08-RAG 你回头看——RAG 手册里反复出现的"检索栈接模型 API"，接的就是这一篇毕业的能力。

## 1. 一次调用解剖：请求 → 服务器 → 响应

一次模型调用，拆开是三段（协议形态为要素事实，与 OpenAI 兼容接口同构图）：

```text
你的客户端                        API 服务器（远程干活）
    │ POST /v1/chat/completions        │
    │   {"model": "...",               │
    │    "messages": [system, user],   │
    │    "stream": true/false,         │
    │    "max_tokens": ...,            │
    │    "temperature": 0.7}           │
    │────────────────────────────────▶ │  逐 token 生成
    │                                  │
    │（stream=false）                 │（stream=true）
    │  一个完整 JSON：                │  一串 SSE 帧：
    │  choices[0].message.content     │  data: {"choices":[{"delta":{"content":"..."}}]}
    │  一次等 3 秒                    │  data: ...（每到一个 token 一帧）
    │                                  │  data: {"choices":[{"delta":{},"finish_reason":"stop"}]}
    │                                  │  data: [DONE]
    │◀────────────────────────────────│
    │  解析 JSON → 全文一次渲染        │  边收边渲染 → 首 token 秒到
```

核心参数（要素事实）：`model`（选模型）、`messages`（system+user+assistant 历史）、`temperature/top_p`（采样）、`max_tokens`（输出上限）、`stop`（停止词）、`stream`（是否流式）、`seed`（可复现）。**讲接口基本功时最重要的一条分水岭就是 `stream`**：它不改变响应内容，只改变"响应怎么到达"。

本篇三件基本功的落点：

- **同步 vs 流式** 回答的是"用户要等多久才能看到第一个字"——流式把首 token 到达时间从"全量生成完"提前到"第一个词生成完"（§3 实测：85 token 同步 0.85s vs 流式首 token 0.01s）。
- **token 计费** 回答的是"这单多少钱"——账单跟着 token 数走，输入段+输出段两段计，与同步/流式、与调用次数都无关（§4 实测：同步 $0.0009 = 流式 $0.0009；若误按帧收则翻 85 倍）。
- **重试与超时** 回答的是"挂了怎么办"——指数退避不轰炸服务器、首 token 超时有限的等、非幂等请求坚决不盲目重试（§5 实测）。

> 🧩 一句话立于全章之先：**Model API 不是"网络请求能用就行"——三件基本功决定你写的是"会跑的最小脚本"还是"能扛用户的客户端"。**

## 2. 把基本功做成本机实测（探针设计）

探针 `api_stream_demo.py` 会在**内存里模拟一个"逐 token 生成的 LLM 服务"**：一段固定模型回复（85 个 token，jieba 分词）被服务端以 `data: {"choices":[{"delta":{"content":"好"}}]}` 这样的 SSE 帧逐 tokent 吐出，再接 `finish_reason: stop` 帧和 `[DONE]` 帧。**帧格式与真实 OpenAI 兼容接口逐字符同构**，所以本页学到的解析/重组/断线判断，可以直接平移到真实 API。

三个实验对应三件基本功：

| 实验 | 信号（探针读数） | 回答问题 |
|---|---|---|
| A 同步 vs 流式 | 两条路径重组文本逐字节一致 + 帧数 = token 数 + TTFT/全量墙钟（stderr） | 流式改了内容吗？省了什么？ |
| B token 计费 | 同步/流式账单相同 + 按帧误算的差额 + 缓存半价 + 开源档 | 这一单为什么是这么多钱？ |
| C 重试与超时 | 退避计划 wait×4 + 首 token 超时上限 + 429 覆盖 + 幂等纪律 | 服务器挂了/慢了，客户端该怎么做？ |

两个设计口径：

- **确定性优先**：回复固定、帧固定、假时钟注入（C 的退避 sleep 只推进假时刻不真等）→ stdout 三遍逐位一致；墙钟（TTFT/全量/总量）只进 stderr、run 间浮动。**stdout 上出现的每一个"信号"都是确定性的科学数字，墙钟都标注为 stderr 观测**。
- **挂钟只进 stderr**：实验 A 会真的睡 `GEN_DELAY=0.01s` 来模拟逐 token 生成——但这部分走 `time.sleep` 与 `time.monotonic`，浮动，一律只进 stderr；stdout 只留"重组一致 Y""帧数=85"这种与时钟无关的读数。

## 3. 实验 A · 同步 vs 流式：内容不变，节奏变

探针让服务端按统一 `GEN_DELAY=0.01s/token` 生成同一段 85 token 回复，客户端两条路径各取一遍：

- **同步**（等价于 `stream=false`）：服务端攒齐全部 85 token，一次返回完整 JSON。
- **流式**（等价于 `stream=true`）：服务端边生成边吐 SSE 帧，客户端**边收边渲染**，首帧到达即首 token 到手。

实测（stdout 读数）：

```text
同步路径完整内容 : 137 字
流式路径重组内容 : 137 字 · chunk 数 = 85（= token 数 85）
逐字节一致 same = Y  ← 流式不改变内容，只改变到达节奏
首 chunk = '好'  · 末 chunk finish_reason = stop · 尾帧 [DONE] 存在 = Y
```

三个结论一次焊死：

1. **流式不改变内容**：两条路径重组出来逐字节一致（`same = Y`）。流式不是"又问了一遍"，是把一次响应切成 N 个**子事件**（chunk 数 85 = token 数 85）。
2. **协议形态可平移**：首帧是 `data: {"choices":[{"delta":{"content":"好"}}]}`、末帧 `finish_reason:"stop"` 再 `data: [DONE]`——这个抓法在真实 API 上能直接抄作业。
3. **流式省的是 TTFT，不是总时长**：墙钟（stderr，本批观测）——

```text
[wall] 实验A 流式TTFT                0.010 s   ← 首 token 秒到
[wall] 实验A 同步全量总时长           0.850 s   ← 同步必须等完全部
```

同一段回复，**同步用户要等 0.85s 才看到第一个字，流式 0.01s 就看到了**。总时长两者差不多（流式也是 85×0.01s 全额生成，只是边生成边送达），但**首 token 到达是体感指标**——聊天/流式打字机体验、长报告边写边看，省的都是这一步。这就是 `stream=true` 该开就用、默认就该给聊天场景开会的原因。

> 修复站点：A 的实操结论=**聊得越像"实时对话"越该开 `stream`**；内容与账单都不会因流式而变（§4 实测证明账单也不变），所以"开流式会变贵/会变乱"是误读。

## 4. 实验 B · token 计费账：账单跟着 token 走

计费这一项，探针拿固定输入（system+user=22 token）+ 固定输出（85 token），跑同一笔调用在两种档位下的账目：

```text
同一回复：同步账单 = $0.0009 · 流式账单 = $0.0009 · 差额 $0（token 相同，与帧数/次数无关）
若误按 chunk 计费则 = $0.0009 × 85 帧 = $0.0769 ← 这是误读，API 按 token 收
相同 system 二次命中缓存：输入 $0.00090→$0.00088（省 3.0%·缓存命中半价示例）
换成开源平替档：$0.0001（输入 $0.15/M 输出 $0.60/M 示例价）
挂靠 06 章：窗口字符成本线 k=5/10/20→154.4/307.9/614.1 字符 ≈ token 越多账单越贵（控制块数=直接省钱）
```

账目拆开：

- **按 token 计费，不按帧/不按次数**：同步与流式产出同样的 85 个 token → **账单一模一样（$0.0009）**。若有人理解成"流式每帧收一次钱"，同一回复会被误算成 $0.0009×85=$0.0769——错 85 倍。这是最常见的计费误读。
- **输入段+输出段两段价**：输入（system+user+历史）和输出（模型生成）单价不同；本示例价输入 $2.5/M、输出 $10/M（输出更贵）。所以**省钱的重点在输出 token**：prompt 越长、检索窗口越大，输入段在涨；但只要模型在"长篇大论"，输出段才是大头。
- **缓存命中半价**：相同 system（长 system prompt 常见）二次命中缓存时输入段打半价。本示例 22 token 的节省只 3.0%（太小），但**长 system/长上下文场景输入段大时，缓存是看得见的优惠**（`08-向量数据库选型` 的缓存路由同理）。
- **档位差**：开源平替档（输入 $0.15/M、输出 $0.60/M 示例价）同一回复 $0.0001，比标准档便宜约一个数量级——**选模型不止看跑分，也看单位 token 价格**。
- **挂靠 06 章成本线**：08-RAG `06-上下文压缩` 实测过窗口字符成本线 k=5/10/20→154.4/307.9/614.1 字符——"字符≈token，token 越多账单越贵"。**控块数、做压缩（06 章实测压缩率 88.2%），就是直接省 token 钱**，这条线从 RAG 一端一直穿到 API 账单一端。

> 修复站点：B 的实操结论=**做预算先算"这单几个 token"，不是"调了几次"**；优化对象永远是 token 数（压缩、控块、短输出），流式不会让账变贵。

## 5. 实验 C · 重试与超时：退避计划 + 幂等纪律

最后一件基本功应对的是"服务器挂了/慢了"。探针用**可注入假时钟**（退避 sleep 只推进假时刻不真等，全跑 <1s）跑三个确定性场景：

**C1 · 指数退避** 计划=前 4 次首 token 超时，第 5 次成功：

```text
计划=前4次首token超时后成功 → 实际 attempts=5 次（1 原始 + 4 次重试）· 状态=ok
退避计划 base=0.5 factor=2.0 → wait=[0.5, 1, 2, 4] s（假时钟累计 7.5 s，未真睡）
首 token 超时上限 timeout=1.0 s：超过即视为失败→退避→重试（保用户体感，不无限等）
```

指数退避的意义：**前几次失败多半是瞬时抖动，短等就好（0.5s）；连续失败说明服务器真有问题，拉长间隔（4s）不轰炸**。首 token 超时上限 `timeout` 保障客户端不无限等——"调用模型"这种在线服务，**等不动就该退**，用户不会等你 10s。

**C2 · 429 + Retry-After** 服务器回 429（限流）并带 `Retry-After` 建议恢复时刻：

```text
429+Retry-After=1.7 s → wait=[1.7, 1.7] s（覆盖指数退避，尊重服务器恢复时刻）· attempts=3
```

服务器比你更懂它自己的恢复时间，**写在协议里的建议值优先于本地的指数退避**——这是对服务器节流语义的尊重，也是避免"自己退避完还是撞上 429"的最优选择。

**C3 · 幂等纪律**（探针只讲纪律，不问服务端）：

> 重试只对幂等请求安全——聊天补全（补全同一个 prompt）是幂等的，可重试；若同一请求触发副作用（扣费 / 写库 / 下单），必须带去重键 / 幂等键，**否则"超时自动重试"= 同一笔操作被重复执行两次**。

> 修复站点：C 的实操结论=**封装在 SDK 层的重试（传 `retries`/`timeout` 参数）要理解其默认值**；带副作用的应用层调用，重试策略永远要自己审视——幂等键加得上才放心让重试自动跑。

## 6. 常见坑（5 条）

1. **拿"调用次数"当预算指标**：Api 计费按 token，不按调用数。两个 1000-token 的调用比一个 100-token 的调用贵 20 倍——**做预算先算 token，看日志先看 prompt 量**。
2. **把流式当成"更贵的并发"**：流式既不更贵（账单同，§4）也不改变内容（§3），它只是 TTFT 更低的**同一笔调用**。不开流式的聊天=用户等 0.85s 空白屏，开了=0.01s 看到字。
3. **重试不加退避，或退避没上限**：写 `for i in range(3): call()` 不加 sleep，失败高峰直接三连轰；反过来无限重试扛不住持续性故障。**指数退避 + 上限（如 5~6 次）+ 429 Retry-After 优先**（§5）。
4. **超时只在"请求结束"上设**：对流式，超时应该设在**首 token**——请求发出去了但 10s 没有第一个 token，说明服务器卡住或后端排队；等 10s flirt重试，比等 `read` 超时（可能 60s+）体感好得多。本篇 C1 用的正是 first-token 超时口径。
5. **非幂等请求盲目重试**：扣费/写库/下单的调用自动重试 = 重复执行。**要么加幂等键，要么重试只到"已确认收到"为止**（§5 C3）。

## 7. 诚实边界（AAA 自我审查）

1. **协议是模拟，不是真实接口调用**：探针在内存中构造 SSE 帧，零网络。帧结构与 OpenAI 兼容接口逐字符同构（`data:` / `[DONE]` / `choices[0].delta`），但**没有真实服务器、没有真实网络抖动、没有真实 429 头细节**——"真实 API 上 429 的 Retry-After 在哪个 header、SDK 默认重试几次"以各厂商文档为准（要素事实）。
2. **时延是模拟值**：`GEN_DELAY=0.01s/token` 是我们设的"每生成 1 token 的耗时"，TTFT 0.010s vs 同步 0.850s 是**这个模型设定下的比值**，不是真实模型的 TTFT/TPOT 分布。真实模型 TTFT 从几十 ms 到秒级、TPOT 因距离/负载/量化浮动——结论（流式省首token等待）是机制性的，具体毫秒数必须看真机压测（05-推理与部署 / 11-评测）。
3. **价格是示例档，不是报价**：$2.5/$10 per M、$0.15/$0.60 per M、缓存半价均为公开示例价（要素事实）演示计费结构；各家实时报价随模型/时间/套餐变化，**以官方定价页为准**。token 计费（输入+输出两段、缓存命中）的结构是通用的，具体数字不是。
4. **token 数是 jieba 分词，不是模型 tokenizer**：实验 B 的 85/22 是按本语料 jieba 切的"token 数"，与真实模型 tokenizer（BPE 等）的 token 数不同（真实 API 会返回 `usage` 字段，以它为准）。这里只用它演示"输入段+输出段计账"的结构，不假装它是真实 usage。
5. **重试/超时策略是经典配置与经验**：base=0.5/factor=2.0/上限 5 次、429 优先、first-token 超时，是行业通行做法（要素/经验），**"最佳参数"随业务重试成本与服务器行为调**——文章给的是"为什么这么设"的原理，不是万能参数表。
