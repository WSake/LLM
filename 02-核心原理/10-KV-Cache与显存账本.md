## 0. 为什么会有 KV Cache：自回归的一步一重算

Autoregressive（自回归）模型的生成是一个"while 循环"：已生成的序列给回模型，预测下一个 token，把新 token 拼进去再回喂。关键在第二步——**把"全部序列"回喂给模型**：

```
第 n 步:  序列 [t0, t1, ..., t_{n-1}]  ──模型──▶  预测 t_n
第 n+1 步: 序列 [t0, t1, ..., t_{n-1}, t_n]  ──模型──▶  预测 t_{n+1}
                                   ↑ 前面 n 个 token 又要从头算一遍！
```

每一步都要重过一遍所有层，其中每一层注意力都要重新算**全体历史 token 的 K 和 V**——可那些历史 token 一个都没变过。这就是"KV Cache"出生前的纯浪费：**不变的输入，被不断地重复计算**。

KV Cache 的答案与编译器缓存、HTTP 缓存共享同一个世界观：**把不变的中间结果记下来，下次直接用**。每一层算完当前步的 K/V 后存进缓存，下一步注意力读"缓存里的历史 K/V + 刚算的本位 K/V"，绝不重算。

> 一句话：**KV Cache 就是"别重复计算没变过的历史"。它是自回归生成里最朴素、也最影响成本的一个优化。**

## 1. 因果注意力的结构性浪费：prefill 与 decode 两副面孔

把一次请求拆成两阶段，浪费就看得更清楚：

| 阶段 | 干什么 | 计算特征 | 没有 KV Cache 时 |
|---|---|---|---|
| **Prefill（预填充）** | 把整段 prompt 一次性前向 | 计算密集（一次大矩阵乘），每个 token 的所有注意力都算得出 | 就是 prefill 本身 |
| **Decode（逐token生成）** | 每步只产生 1 个新 token | 访存密集（矩阵不大，但要从 cache 读全部历史） | 每步把"已生成的 n+1 个 token"**整段重算一遍** → 生成 n 个 token 总代价 O(n²) |

所以"没有 KV Cache"最痛的是 **decode**：生成 n 个 token，要重算 1+2+…+n 段，代价随生成长度平方增长。而 **prefill 只有一次**，代价与输入长度约二次方（第 5 节实测）。这就解释了推理系统为什么把两者分开优化（拆分 prefill/decode、PD 分离等，见 `05` 后续）。

> 记忆抓手：**prefill 重 prompt、decode 重历史；KV Cache 专治 decode 的"重复重算"。**

## 2. KV 的字节账：一行公式（手算 A1，实践题）

每个 token 存起来的 KV 有多少字节？逐层逐头累计：

```
每 token KV 字节 = 2(K、V 各一份) × 层数 × KV头数 × 头维 × 每值字节(2B fp16)
```

把 LLaMA-2-7B 的公开配置代入：32 层、32 头（MHA，KV 头=32）、头维 128 → **`2×32×32×128×2B = 512 KiB`**，即每多生成一个 token，缓存每层每头都要多吃半兆字节。总账随序列长度线性放大：

```text
实测 A1 手算 7B 系 KV 账（fp16, 账算可复现）：
  模型                               1k      2k      8k     32k    128k   单token
  LLaMA-2-7B 风 MHA (Hk=32)      0.50G   1.00G   4.00G  16.00G  64.00G  512 KiB
  LLaMA-3-8B 风 GQA (Hk=8 )      0.12G   0.25G   1.00G   4.00G  16.00G  128 KiB
  核对 03 章 8k：MHA = 4.00 GiB，GQA-8 = 1.00 GiB，逐格相等

  权重复习：7B fp16 ≈ 14 GB。KV@32k = 16.0 GiB(MHA) / 4.0 GiB(GQA)
  → MHA-32k 占(权重+KV)的 53%，GQA-8-32k 占 22%
  → 拉到 128k：MHA 64 GiB = 权重(14G)的 4.6 倍 → 占 82% 以上
```

这就是知识地图"**长上下文时 KV 占显存 60%+**"这句话的手算版：32k 已经过半，128k 直接反客为主——**上下文越长，模型的"工作内存"从权重让位给 KV Cache**。

> 一句话带走：**KV 的账是一行乘法。7B 级一个 token = 512 KiB(MHA)/128 KiB(GQA)；32k 下 16 GB vs 4 GB、占权重+KV 的 53%/22%，这是"推理为什么贵"的第一张总表。**

## 3. 谁来省这笔账：GQA / MQA / MLA（复习 03–04）

KV 公式里唯一"可控"的乘数之一是 **KV 头数**——这正是 03、04 讲过的谱系，现在它们有了最终落点：省 KV 就是省推理成本。

| 方案 | KV 头比例 | 效果（相对 MHA 的 KV） | 已掌握在哪 |
|---|---|---|---|
| **MQA**（2019） | 所有 Q 头共享 1 份 KV | ÷h（几十倍） | `03` |
| **GQA**（Llama-2） | 分组共享 | ÷g（实测 8k 上下文 4 GB→1 GB） | `03` |
| **MLA**（DeepSeek-V2） | 低秩压缩后再缓存 | ÷十几倍（账算 128k：MHA 488→GQA-8 30.5→MLA 8.6 GiB） | `04` |

三笔账互相咬合：GQA/MQA 走"少存"，MLA 走"压缩后存"，两者可叠加。**KV Cache 是这一切决策的裁判——省下来的每一字节都落到第 2 节的账上。**

## 4. 实测 A2：带缓存的重生成一步到底快多少

理论说得再对，还是看一眼计时。A2 在迷你 attention 上（hidden 64、T=128），三种情况各取 15 次耗时最小值：

```text
实测 A2（迷你 attention, T=128, hidden=64, 本机 CPU）：
  prefill（一次算 128 位置）        1574 µs
  cached decode（只算最后 1 个）      76 µs
  recompute decode（拼回全量重算）   1060 µs
  → 同一步 decode，带缓存比全量重算快 14.0×
```

- **带缓存 decode 76 µs vs 重算 1060 µs ≈ 14×**——和执行理论一致：重算要跑完整段序列（T 个位置），带缓存只跑新到的 1 位（O(T) vs O(1)，且这里的 T=128 只是个小玩具，真实 4k/32k 上下文时倍数随 T 放大）；
- 与 `01-Transformer` 里那条 T=96 时 **≈12×** 的实测互为印证——两处独立测量，同一定律。

> 记忆抓手：**KV Cache 让每个生成步从"重算全部历史"变成"只算最后一位"，实测快 ~14×，且随上下文拉大而拉大。**

## 5. prefill 的平方律：输入多一位，代价涨一格

decode 有 cache 兜底，剩下的瓶颈回落到 **prefill**：它一次性前向全部输入 token，注意力分数矩阵是"全部 token × 全部 token"，代价随 T 约平方式涨。A2 第二阶段实测 prefill 时间随 T 的缩放（取多次最小值）：

```text
实测 A2 prefill 时间随 T 缩放：
  T=  64 →   227 µs
  T= 128 → 1,493 µs
  T= 256 → 3,189 µs
  T= 512 → 10,339 µs
```

T 每翻一倍，时间约 ×2.1–4.5（本脚本逐行做因果掩码，CPU 小矩阵下斜率实测 ~1.8；商用 GPU+FlashAttention 下限接近理论 2）。这条曲线就是——**长 prompt 为何贵**：用户问一个 30 页文档，prefill 直接把整场的二次方消耗掉，这正是推理系统 Chunked Prefill / PD 分离要处理的头部效应（`05` 展开）。解码也很重要的提醒：**"缓存"本身不省 prefill，它只救 decode。**

> 一句话：**prefill 是平方律、decode 是线性律（有 cache）；长上下文系统把两个阶段分开伺候。**

## 6. 衍生 A —— 系统层：PagedAttention 与碎片账（A3）

KV Cache 的第二个战场是**显存怎么分**。朴素做法是每个请求预留一整块"最长上下文"的连续内存——碎片惊人。vLLM 的 **PagedAttention**（2023）把 KV 按**固定大小的一页**（如 16 token）管理，类似操作系统虚拟内存：请求的 KV 由若干页拼成，页表映射、按需申请。

A3 用一个参数化模拟验证"碎片差多少"（200 个 seq∈[256,2048] 均匀的请求、LLaMA-3-8B 风 GQA-8）：

```text
A3 PagedAttention 玩具（账算模拟）：
  200 请求, seq∈[256,2048] 均匀, 页=16 token：
    实际用到（sum seq）     29.34 GiB
    连续分配（全开 max_len）50.00 GiB   → 内部碎片 70%
    分页分配（按需按页）    29.51 GiB   → 内部碎片 1%
  → 分页把内部碎片压到每请求最多 1 页（16 token）
  前缀缓存（512 token 系统提示, 200 请求共享）≈ 省 12.50 GiB = 全部 KV 的 42%
```

两个数的直觉：请求实际只用均值 ~1150 token，但连续分配给每请求开满 2048 上限 → **70% 是"预留了没用到"的内部碎片**；分页按需给整页 → 每请求最多浪费不足 1 页（16 token，约 1%）。同一次模拟里还顺带证了 **Prefix Cache**：200 个请求共享 512 token 的系统提示词，这 512 token 的 KV 页只需算一次、大家共享 → 省下全部 KV 的 42%。——这也是知识地图"显存碎片/浪费 → PagedAttention；复用 → Prefix Cache"两条对策的机制出处。

## 7. 衍生 B —— 减负：KV 量化、前缀缓存、剪枝

除架构层（GQA/MLA，第 3 节）和系统层（分页，第 6 节），KV Cache 的减负还有两条常打的牌：

- **KV 量化**：KV 也按 INT8/FP8 存（而不是 fp16）→ 字节减半起步；长上下文中收益最大，标注"量化对象要分清"（`05-推理与部署` 展开，注意它跟权重量化是两回事）；
- **剪掉不重要的 token**：H2O/SnapKV 一类方法按注意力权重判断哪些历史的 KV 可以丢（"attention sink" 附近保留、远端丢弃），把"有效记忆"压缩进更小的缓存——是**近似**，牺牲一点质量换显存；
- **前缀缓存** 已在上节账过（同前缀共享页）；**MLA** 已在 04 账过（压缩后存）。

一句话把这节并进大图景：**省 KV 四条路——架构层少存（GQA/MLA）、系统层管好（分页/前缀共享）、数值层变窄（量化）、策略层丢会议（剪枝）。**

## 8. 常见坑

| 坑 | 症状 | 修法 |
|---|---|---|
| 混淆"每 token KV"与"总 KV" | 手算 7B@32k 得不出 16 GB | 总账 = 每 token 字节(512 KiB) × 序列长度；先算单 token，再乘 |
| 忘记"序列长度"包含 prompt | 只乘生成 token 数 | KV 缓存里存的是**全部已在上下文的 token** 的 K/V |
| 以为 KV Cache 能省 prefill | 长 prompt 依然慢 | 缓存只救 decode（O(n)→O(1)）；prefill 是平方律（实测 §5），单独优化 |
| 拿 MHA 配置算新模型 | 新模型带 GQA 却按 32 头算 | 看 model 卡 `num_key_value_heads`：LLaMA-3-8B = 8（实测 32k 只要 4 GB） |
| KV 量化当权重量化 | 量化了权重还嫌 KV 大 | KV 是独立一笔账，要单独量化/单独评估收益 |
| 把"分页"当"压缩" | 以为 PagedAttention 减少 KV 大小 | 分页只消灭碎片（70%→1%，实测 A3），不改变总字节 |
| 共享前缀白算 | 重复算系统提示词的 KV | Prefix Cache：同前缀只算一次、页共享（实测省 42%） |

## 9. 衔接下一章

生成循环走到这一步：`prefill 算完 KV → 循环{ decode 用缓存算第 t 个 token 的 logits → ... }`。要把 logits 变成"下一个词"，还需要最后一环——**采样**。它决定同一个 logits 向量下你得到什么样的文本（贪心？随机？多宽？），是"推理质量与多样性的旋钮"：

> **`11-Logits与采样-Temperature-TopK-TopP`**（下一章, 规划）：`decode` 每步产出的 logits 向量怎么变成下一个 token——temperature 重塑分布、Top-k/Top-p 截断长尾、以及重复惩罚；这篇把"生成"收尾，之后 `12-` 起进入预训练/SFT/RLHF 的训练主线。

> 一句话带走：**KV Cache 是"不重算没变过的历史"——手算公式 `2×L×H_kv×d×seq×2B` 让 7B@32k 的 KV = 16 GB(MHA)/4 GB(GQA)、占权重+KV 的 53%/22%（实测 A1）；带缓存生成步快 14.0×（实测 A2）；prefill 是平方律；省 KV 的谱系=GQA/MLA（架构少存）+ PagedAttention（系统分页、碎片 70%→1%）+ 前缀缓存（省 42%）+ 量化、剪枝（数值与策略）。**
