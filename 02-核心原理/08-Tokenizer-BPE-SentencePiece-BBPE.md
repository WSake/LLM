## 0. 为什么要分词：电脑只认整数

训练和推理的每一步都是矩阵乘、注意力、非线性——它们只能对**数字**运算。所以任何文本进入模型的第一件事，是把字符串变成一串整数 id。Tokenizer 干的就是这件事：

```
"大语言模型正在改变软件工程"  →  [ 341  521  1986   ... ]  （整数 id 序列）
```

这层"翻译"的质量直接决定三件事：**上下文长度能装多少文本**（token 越少，塞进 128k 窗口的内容越多）、**词表该多大**（下节账算 1M embedding 参数的量级）、以及**模型能不能处理见过的字**（OOV 越少越好）。`01-Transformer` 那篇里 `token (2,5)` 的 `5` 就是这个维度——本篇拆开讲这一层本身。

> 一句话：**Tokenizer 是"字符串 ↔ 整数 id"的翻译官；它的输出直接决定上下文能装多少、词表占多少显存、生僻字见不见过。**

---

## 1. 基线方案：查表，以及它的三个问题

最朴素的方案：拿一个**固定的词表**（比如 5000 个常用字词），字词查表得 id。Toy 版就是 A0 的"每字符一个 token"。它有三个绕不开的问题：

1. **OOV**：词表外的字（生僻字、新词）无 id 可用，只能扔 `[UNK]`——信息直接丢失；
2. **词表大小 vs 粒度**：词表小 → 每 token 携带的语义太少（上下文被稀释）；词表大 → 查表矩阵巨大（见 A4）；
3. **多语言失衡**：英文按词切时 26 个字母足够，中文按词切需要几千常用字、还没算组词——**没有一个"每语言通用"的固定单元**。

BPE 的答案很优雅：**词表不是人设计的，是拿语料统计出来的；单元不是字词，是"数据最常一起出现的相邻片断"。**这样 OOV 几乎消失（任何文本都能被切／被拼回）、语言一个个自然适配。

## 2. BPE：把「最常共现的相邻对」合并进词表

Byte Pair Encoding（BPE，2016 年引入 NMT）：初始化时词表 = **语料里出现过的全部字符**；然后一遍遍扫描，把**出现次数最多的相邻对**合并成一个新词表项。比如语料里"模"后总跟着"型"，就合并出"模型"；`attention` 里 `tt`、`en` 高频，先合出 `att`，再合 `ention`……最终词表里既有字、也有高频词、还有子词。

```text
A0 语料账（内嵌 56 条中英短句, 中英各重复 2 遍）：
  字符集 187 个 → base 词表 187 起步
  总字符数 1460（不合并时 = 1460 tokens）
```

算法核心就一个 while 循环：

```python
while 词表没到预算:
    统计当前序列所有相邻对的出现次数        # ("模","型"): 17 次, ("t","t"): 9 次, ...
    取次数最多的相邻对 (a, b)              # 并列时取字典序小的, 保证确定性
    把这个 pair 替换成一个新词表项 id, 记进 merges
```

要点：**每次合并后重新数**——因为合并会制造新的相邻对（"大语言"合并成"大语言"后，"大语言"和"模型"又成为新对）。这就是"从零学词表"，不需要任何语言学知识。

---

## 3. 训练与编码：train 与 encode 是两次对称的算法

分词器一生做两次不同的操作：

- **训练（train）**：在全部语料上跑上面的循环，得到 `merges`（合并序列）和词表；
- **编码（encode）**：对新文本，按 `merges` 的优先级（训练顺序 = 优先级：越早的 merge 越优先）对原始字符序列做同样的合并。

这一个"优先级"细节值得留意：标准 BPE 编码**按 rank 重放**训练时的合并。我们第一次实现时在这里踩过坑——合成的新 token 若不给它**训练时分配的真实 id**，而是都用同一个占位码，那么"合并后的码再参与合并"（深层合并，比如 `(大语言, 模型)`)就永远配不上，encode 会比训练结果少压缩一半（实测特征见下节 A1 的正常数字，bug 会让 token 数翻倍）。**写任何 tokenizer 复现，先把"新码的唯一性"打对，再谈数字。**

下面每一数字都来自这个从零实现，可与 `code/scripts/tokenizer_demo.py` 一键对账。

## 4. 实测 A1：词表越大，压缩比越高

在 1460 字符的语料上，从 base 词表开始逐档加 merges，统计 encode 出的总 token 数与"平均每 token 覆盖多少字符"（压缩比）：

```text
A1 压缩比 vs 词表（chars/token, 全语料 1460 字符）：
  vocab  187（base+  0 merges）  token 数 1460   压缩比 1.00
  vocab  237（base+ 50 merges）  token 数 1038   压缩比 1.41
  vocab  337（base+150 merges）  token 数  756   压缩比 1.93
  vocab  487（base+300 merges）  token 数  456   压缩比 3.20
  vocab  687（base+500 merges）  token 数   56   压缩比 26.07   ← 退化：每句恰好 1 token
```

两条可带走的规律：

1. **词表越大压缩越狠**：每加 50 merges，token 数清清楚楚往下掉（1460→1038→756→456）——这是 BPE 的"预算-收益"左半边：**同样的窗口长度，能装的文本越来越多**；
2. **小语料的尽头是退化**：词表涨到 687 时，**每句恰好被压成 1 个 token**（56 句 = 56 token，26 倍压缩）——词表这时候装的不是"词"而是"整句模板"，没意义。真实模型的词表 3.2 万到 15 万，正是词表大到"常见词、子词、特殊 token 各得其所"但与语料规模匹配的平衡点。

> 记忆抓手: **BPE 的滑杆在"词表预算 ↔ 压缩比"上,**当你看到"为什么 Llama 3 把词表开到 128k"——那是想用更多 token 覆盖更多语言与领域, 换上下文里更多的有效文本（代价是 A4 的显存）。

## 5. 中英逐句：同一套词表下各切几个 token（A2）

知识地图的实践题是"统计中英文每句 token 数与压缩比"——A2 用**同一套** BPE（487 词表）逐句切：

```text
A2 同一套词表（487 vocab）逐句：
  中文『大语言模型正在改变软件工程』 13 字 →  6 token（0.46 token/字）
  中文『注意力机制让模型能处理长序列』 14 字 →  4 token（0.29 token/字）
  中文『训练数据需要清洗与去重』      11 字 →  4 token（0.36 token/字）
  英文『attention is all you need』            25 字符 → 7 token（0.28 token/字符）
  英文『the model predicts the next token』    33 字符 → 8 token（0.24 token/字符）
  英文『quantization reduces memory』          27 字符 → 9 token（0.33 token/字符）
```

在这个迷你语料上中英的"每字符 token 数"落在同一档（0.24–0.46）——因为**词表只认识语料里出现过的组合**，高频词（注意力、模型、the、model）都被合并成了单 token。这反而是个好演示：**分词器的"语言观"是语料统计出来的，不是人规定的。**真实验证会想看两点差异：① 语料规模更大时英文每词≈1~1.5 token、而中文"未化解"的常规文本每字≈1 token 起步（中文没有空格天然分段，合并慢）；② 分词粒度放粗/token 变少 ≠ 更聪明——只是更省窗口。"每句多少 token"要结合预算看，才是完整判断。

## 6. 字节级 BPE（BBPE）：救无空格语言，也带来 3× 膨胀（A3）

BPE 有个前提让中文吃亏：初始字符集 = **语料的字符**。中文字符几十万（含生僻字），而英文只需要转写拉丁字母+符号——词表容易失控。**字节级 BPE（BBPE）**的解法很霸道：**初始词表 = 256 个字节值，任何文本都先按 UTF-8 转成字节流，然后在字节流上跑同一个合并算法。**

```text
A3 BBPE（UTF-8 字节流, 300 merges, 词表 396）：
  中文『大语言模型正在改变软件工程』 13 字/39 字节 → BBPE 23 tokens（char-BPE 是 6 tokens, 膨胀 3.8×）
  英文『attention is all you need』 25 字符/25 字节 → BBPE  7 tokens（char-BPE 是 7 tokens, 膨胀 1.0×）
  全语料：2500 字节 → 972 tokens（2.57 bytes/token）
```

punchline 在**膨胀系数**：同一句中文，char-BPE 是 6 个 token，BBPE 是 23 个——**每个汉字被拆成 3 个字节 token（UTF-8 下汉字 = 3 字节），3.8× 的膨胀就来自这里**；而英文是严格的 1 字节/字符，两者 token 数相同（1.0×）。

这个实测解释了行业里两件事：

- **为什么 GPT-2/Llama 的优势在"任何语言都能编"**：字节级 256 起步，不必为日韩、emoji、生僻字预置词表，也不会 OOV；
- **为什么它是中文的痛**：**token 数 ≈ 3× 文本表现力**——同样一段中文，在字节级分词模型里要花 3 倍窗口/预算。所以中文环境的主流做法还是「带字符或子字初始化 + 更大词表」体系（Qwen/DeepSeek 的 tokenizer 就是面向中文把字节级与词表扩展结合）。

> 记忆抓手：**BBPE 用"3× 中文 token 膨胀"换来了"任何语言零 OOV"。**

## 7. SentencePiece：把「要不要空格」也交给算法

BPE/BBPE 是**算法**；SentencePiece 是**训练框架**（2018, Google），也是"生产线 vs 机器"这对概念里最常被误读的一个。它解决一个 BPE 的隐藏坑：**很多语言没有空格**（中文、日文），而 NLP 里按空格预分词是个默认假设——SentencePiece 干脆**把所有输入当"字符序列"，连空格都当作一个普通字符**加到词表里，需要时用 `<w>` 之类标记给空格一个 id，反向还无损。

它支持 BPE 和 Unigram 两种训练模式（Unigram 用 EM 思路对语料做概率分词，那种"每字符有概率地合并"的思路在建模侧另有用途，本篇不展开），并且常配 **byte-fallback**：词表外的字符自动退化到字节级 token 来兜底。你看到 `spm` / `sentencepiece` / `byte_fallback=True`，就知道模型走的是这一套。"框架"与"算法"的关系不要混：**SentencePiece 是生产线，BPE/Unigram 是其中的具体机器。**

## 8. 词表是显存的第一笔账（A4）与衍生

词表第一件事的**成本**是 `vocab × hidden` 的查表矩阵——它直接量化（也是"关系：影响 embedding 大小、成本与训练"）：

```text
A4 embedding 账（参数量 = vocab × hidden, 显存 = 参数 × 2 字节 fp16）：
  vocab  32,000 × hidden  4,096 =  131.1M 参数   0.26 GB(fp16)   LLaMA-2 7B 风格
  vocab 128,256 × hidden  8,192 = 1050.7M 参数   2.10 GB(fp16)   LLaMA-3 8B 风格
  vocab 151,936 × hidden  4,096 =  622.3M 参数   1.24 GB(fp16)   Qwen1.5-7B 风格（账算）
  vocab 100,278 × hidden  5,120 =  513.4M 参数   1.03 GB(fp16)   DeepSeek-V2 风格（账算）
  → Qwen1.5-7B 风格 embedding 622M ≈ 全模型 7.5B 参数的 8.3%
```

- **词表是 7B 参数里默默吃掉 0.25~2.1 GB 的一块**（fp16），还不算输出层常用共享这一矩阵；
- **词表扩展（衍生）的代价就在这行账上**：加 1 万个专业 token = `10000×hidden` 新参数，且新 token 没有历史 id，需要对齐/初始化——这就是"给领域加词表"为什么是个要专门评估的动作；
- **字节级 token（另一个衍生）把账往"省词表、费 token"推**：上文 3× 膨胀就是它的机会成本。

下节配合 [`09-Embedding与词表`](../02-核心原理/09-Embedding与词表.md)，把"token id → 向量"的查表层补完；本篇只要立住："**词表是显存的第一笔账，Tokenizer 决定了这笔账的规模。**"

## 9. 常见坑

| 坑 | 症状 | 修法 |
|---|---|---|
| 以为 BPE 是"分词→再学一套词" | 写代码时先做英文空格分词 | BPE 就是对**字符序列**做合并；空格自身也是一个字符 |
| encode 不按训练顺序（rank）重放 | 复现出的 token 数与训练对不上, 明显偏少 | merge 用训练时分配的真实 id, 优先级=训练顺序（见第 3 节教训） |
| 词表只图大 | 小语料下词表疯狂合并出"整句 token" | 词表要跟语料规模匹配；真实模型 32k–152k 是平衡点 |
| 对中文直接上纯 BBPE | 中文 token 数莫名 ×3 | 膨胀 = UTF-8 3 字节/字（实测 3.8×）；中文场景用带中文初始化/更大词表的体系 |
| 把 SentencePiece 当 BPE | 分不清"框架"和"算法" | SentencePiece=训练框架（BPE/Unigram 两种机器）；BPE/BBPE=具体算法 |
| 忽略词表对显存的贡献 | 算模型显存只数 Q/K/V×L | embedding = vocab×hidden, fp16 下 7B 级就 0.25–2.1 GB（A4 账） |
| 给领域加活词表当儿戏 | 加词后行为不一致/训练要重来 | 新 token 无 id 需对齐；参数增量 = 10000×hidden |

## 10. 衔接下一章

Tokenizer 把文本变成了整数 id，但**整数 id 还不能直接进注意力**——它们要过一层"查表"，变成稠密向量。这层就是模型的入口通道：

> **[`09-Embedding与词表`](../02-核心原理/09-Embedding与词表.md)**：token→稠密向量的查表层，输出层常共享同一矩阵（`01-Transformer` 里那条 shape 链的 `x = emb(token)` 就是它）。它接住本篇章的"词表显存账"，把 Vocab×D 大矩阵的初始化、共享、Low-Rank 优化一并展开。

> 一句话带走：**Tokenizer 是"文本 ↔ 整数 id"的翻译官，现代事实标准是 BPE——从 187 个字符起步，把最常共现的相邻对一次次合并（实测压缩比随词表 1.00→3.20 chars/token），词表涨过头则每句塌成 1 token（实测 26× 退化）；中文在同一套词表下逐句 0.3–0.5 token/字（实测 A2）；字节级 BPE 让中文膨胀 3.8×（实测 A3）而英文不变——换来任意语言零 OOV；SentencePiece 是管线、BPE/BBPE 是机器；全部映射进 0.26–2.1 GB 的 embedding 第一笔账（实测账算 A4）。**
