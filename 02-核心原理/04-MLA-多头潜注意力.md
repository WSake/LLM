# 🧠 MLA 多头潜注意力：把 KV 压进一个低维潜向量

> 对应知识点：知识地图 **§17.2.5 MLA（Multi-head Latent Attention）**（🟢 掌握）——"把 KV 压缩到低维潜空间，KV Cache 与训练成本双双大降"；前置：GQA、低秩。这是 GQA 的"更激进版本"。
> 一句话：**GQA 是"几头共用同一组 K/V"，MLA 是"把所有头要的 K/V 用一个低维潜向量表达，打分时再解压"——KV 账从「头数 × 头维」变成「潜向量维」；DeepSeek-V2 靠它把长上下文 KV 做出数量级账差（128k 总账账算：MHA 488 GiB → MLA 8.6 GiB）。**
> 可复现：本文数字来自 `code/scripts/mla_demo.py` 实验 A–C（纯 CPU 秒级；A 实证"低秩瓶颈"，B/C 给迷你三档账 + DeepSeek-V2 规格账算）。

## 0. 从共享到压缩：GQA 之后还能省什么

上一章 (`03-多头注意力`) 走到 MHA → GQA → MQA：**省 KV 的第一招是"共享"**——几个查询头去同一个 K/V 库查资料。但仔细看那张账：

$$\text{KV Cache} = 2 \times N_{KV} \times DH \times 2\text{B} \times T \times L$$

GQA 把 `N_KV` 从"查询头数"降到了"几组"，可 **K/V 本身还是每 token 一个 `N_KV × DH` 的大矩阵**。就算只有 8 组 K/V，`8 × 128 × 2（K、V 两份）= 2048` 个元素一个 token，乘上上下文长度、层数，依然是大头。

MLA 换个路子：不共享了，**压缩**。加一个"N_KV × DH 维到底，先缩到一个只有 512 维的小潜向量"，要算注意力时再临时展开。

> 类比：「共享」是公司所有部门共用一份档案室；「压缩」是档案室本身只留一个索引卡片盒，谁要用哪份档案，临场开盒取。卡片盒只有一个，但足够小。

## 1. 机制：先压进潜向量，用时再逐头解压

### 1.1 三张投影

MLA 的注意力层不再是"隐层 → 直接投影成每头 K/V"，而是拆成**三个连续步骤**：

$$
\begin{aligned}
c^{KV}_t &= W^{DKV}\, h_t    &\text{（下投影：压缩到 } D_c \text{ 维潜向量）} \\[2pt]
k^h_t &= W^{UK}_h\, c^{KV}_t + k^{\rm rope}_t  &\text{（每头上投影：解压出这一头的 Key）} \\[2pt]
v^h_t &= W^{UV}_h\, c^{KV}_t &\text{（每头上投影：解压出这一头的 Value）}
\end{aligned}
$$

- `W_DKV`：(Dc, C)，把隐层 `h` 压到 Dc 维——**这是要长期缓存的那一份**；
- `W_UK` / `W_UV`：(H, *头内部维*, Dc)，每个头各一张"从潜向量解压"的投影，**推理时现算**；
- `k^rope_t`：位置相关的一段 Key（详见第 5 节），无法压进潜向量，单独存。

关键直觉：**所有的头、所有代的 K/V，最终都由同一个 Dc 维潜向量衍生**。压缩得越狠（Dc 越小），要存的越少，但 K/V 能表达的"区别"也越少——这就是第 3 节的低秩瓶颈。

### 1.2 shape 链

`mla_demo.py` 实验 A 打印了迷你版（`H=8, dh=32, dr=8, Dc=16`）的完整数据流：

```text
h (2,6,64)
  ├─ W_D (16,64)  → 潜向量 c (2,6,16)                  ← 每 token 只缓存这一份
  ├─ 每头上投影    → Knope (2,8,6,24) / V (2,8,6,32)    ← 推理时才展开
  └─ 位置段直接投影 → Kr  (2,6,8)                       ← 位置相关，另存
```

相比 `03` 篇 MHA 的 (2,8,6,32) 全套 K/V 都进缓存，MLA 的 K/V 只是"临时计算出来的中间量"。这就是显存账质变的来源。

## 2. 为什么只存潜向量就够：反推走同一条路

有人会问：反正打分时要 `q·k`，我把下投影和上投影合并不行吗？**完全可以**——但那种"合并后"的大矩阵恰好是低秩的：

$$W^{UK}_h \cdot W^{DKV} \approx \underbrace{W_h}_{\text{rank}\le D_c}$$

也就是说，MLA 真正学习到的"隐层 → Key"映射，是**秩最多为 Dc 的矩阵**。训练为什么能接受？因为每个 token 只需要用一个 Dc 维向量描述自己"想被关联的方式"，大多数情况下足够——**潜向量就是 K/V 语义的压缩表示**。反过来说，一个"完全独立、每个头每种关系都很特别"的注意力，它是表达不出来的（第 3 节就是它的实测）。

所以"只存潜向量"不是技巧，而是数学成立：有 `c`，所有头的 K/V 都能无信息损失地再算一遍（对同一个潜向量而言）。

## 3. 实测 A：低秩的代价（潜向量看不到的方向被丢掉）

把话说透：省显存不是无代价的。`mla_demo.py` 实验 A 用 SVD 构造了两个方向相反的扰动，扰动幅度相同（0.50）：

```text
沿潜向量 nullspace 扰动一个 token：
  潜向量 c 最大差 = 2.22e-16
  解压出的 K/V 最大差 = 2.22e-16  → 不是「小」，是全零：该方向的信息被压缩机制直接丢弃
沿潜向量可感知方向扰动同样幅度：
  潜向量 c 最大差 = 0.268，K/V 相应变化 = 0.284  → 这个方向能留下来
```

注意两个幅度相同的扰动，却一个"一点不动"、一个"显著变化"——差别只在于该方向是否落在 `W_D` 的 nullspace 里。**压缩把"与潜向量无关的方向"判了死刑**：训练阶段模型学会把所有重要关系塞进 Dc 维，塞不进去的就丢了。

> 一句话：MLA 的 K/V 表达能力 ≈ 潜向量维度 Dc（低秩瓶颈）。显存省了多少，表达空间的上限就砍了多少——这是它与 MLP 隐身参数量不同、与"无损简化"不同的根本原因。

这也是论文里 MLA 要和"多头"搭配的原因之一：Dc 太小装不下的关系，靠更多的并行注意力头（多头）分摊。省显存和保质量，永远是同一个天平的两端。

## 4. 实测 B：三档缓存账（迷你规格）

`mla_demo.py` 实验 B，迷你模型 `DH=32, 8 查询头`（账本规则与真实模型完全一样——**乘同一个公式**）：

```text
MHA(8头)        2×8×32   = 512 元素/token/层 →  1024 字节 (bf16)
GQA(4组)        2×4×32   = 256 元素/token/层 →   512 字节 (bf16)
MLA(潜向量16+位置8) 16+8 =  24 元素/token/层 →    48 字节 (bf16)

MLA vs MHA = 21.3×；MLA vs GQA(4组) = 10.7×
```

注意最后一行的公式：**MHA/GQA 的账正比于「KV 头数 × 头维」，MLA 的账正比于「潜向量维」(+位置段)**。头再多，MLA 这格基本不动——这正是长上下文模型普遍从 GQA 迁移到 MLA 的原因（DeepSeek 全系、MiniMax-M1 等）。

## 5. 实测 C：DeepSeek-V2 规格与长上下文总账

`mla_demo.py` 实验 C 按 **DeepSeek-V2 公开配置**折算（账算非实测；配置：`kv_lora_rank=512`、128 头、head_dim 128、位置段 64）：

```text
每 token 每层（元素 → bf16 字节）：
  MHA(128头)    2×128×128 = 32768 元素 →  65536 B
  GQA(8组)      2×8×128   =  2048 元素 →   4096 B
  MLA(潜512+位置64)       →   576 元素 →   1152 B

128k 上下文 × 61 层（把 per-token 常数乘 T = 131072 × L = 61）：
  MHA(128头)  → 488.0 GiB
  GQA(8组)    →  30.5 GiB
  MLA         →   8.6 GiB      ← 与 GQA-8 差 3.6×，与 MHA 差 57×
```

这笔账的意义：**长上下文的 KV 缓存以「T × L × 每 token 常数」线性增长，谁把常数压低，谁就能多扛几条长请求**。同 128k 上下文，同样一层：MLA 只用 GQA 的 1/3.6、MHA 的 1/57 就能装下所有历史 K/V。多房推理时，这就是"能并发几个请求、显存够不够"的物理差距。

> ⚠️ 诚实声明：以上是**按公式折算的账算**，不是 DeepSeek-V2 实测值；总账里的"61 层 × 128k"是我取的演示放大倍数。实践口径还有很多实现细节——第 6 节的第二问专门讲这个。

## 6. 落地：读模型卡三连问

看到模型卡写着"MLA"或"节省 90% 推理显存"，值得问三句：

**① 潜向量维度 Dc 是多少？** 这是 MLA 的"KV 头数"，直接决定每 token 每层缓存。`kv_lora_rank`：DeepSeek-V2/V3 是 512。

**② 位置段（rope 尾巴）是按每 token 还是每头缓存的？** 这是最容易被忽略的一问。位置相关的那段 Key 压不进潜向量，实现里如果**逐头存**（d_r × H 而非 d_r），账能一下大十几倍：

```text
同样 DeepSeek-V2 规格：
  位置段按 token 存（dr=64）     → 576 元素/token/层 → 128k×61层 ≈ 8.6 GiB
  位置段逐头存（64×128=8192）    → 8704 元素/token/层 → 128k×61层 ≈ 129.6 GiB  ← 差 15×！
```

同一套机制、两种实现口径，总账差 15×——所以读模型卡不能只记住一个数，得看清它写的缓存口径（这也是 `10-KV-Cache与显存账本` 要展开的："账本公式 + 实现把 Parts 藏在哪"）。

**③ 支持它的 serving 框架认识这个潜向量吗？** MLA 当时是新范式，常规 kernel（MHA/GQA 的 flash 版本）不认识"先压后解压"。工程上 `vLLM` 从 0.4.3+ 起支持 MLA（DeepSeek-V2 同代），官方也用专门 kernel——这解释了为什么"论文发了很久、部分框架跑不快"，工程差距往往卡在**注意力 kernel 会不会解压**。

## 7. 常见坑

| 坑 | 症状 | 修法 |
|---|---|---|
| 把 MLA 当成"参数更少" | 以为省的是模型体积 | MLA 省的是 **KV 缓存与注意力算量**；每头解压的投影还在，参数量几乎没减 |
| 以为 MLA 训练时也是"只算投影一行" | 想"那反传怎么算" | 训练时潜向量 → 解压 → 注意力全程数值参与；它只是**每层每 token 的中间量不必落存到 KV 缓存**而已 |
| 把位置段当免费的 | 算账漏了 rope 尾巴 | 位置相关段压不进潜向量、必须另存；逐头存的话账差 15×（实测 C 第 2 问） |
| 背一个"MLA 省 90%"的结论 | 换模型、换实现就对不上 | 永远回公式算：`per-token = Dc + 位置段`，再乘 `T × L × 字节` |
| 以为 GQA → MLA 是无缝替换 | mla forward 需要 U-proj 与专门 kernel | 注意力前先 `解压`，Serving 需支持（vLLM MLA 路径），读框架 release note |

## 8. 衔接下一章

MLA 和角度其实共享一个"压缩"思想，更早出现在**跨模态**：`02-Attention家族` 的 Cross-attention 里，Q-Former 正是"把视觉信号压成少量 token 当 K/V 用"。MLA 是这个思想在最引擎层的极端形态。

本篇的位置段 `k^rope` 和"长上下文怎么继续拉长"是下一章的主线：

> **[`05-位置编码-Sinusoidal-RoPE与窗口扩展.md`](05-位置编码-Sinusoidal-RoPE与窗口扩展.md)**（下一篇）：RoPE 是"每个头都要给位置感"的机制，而 MLA 能压缩 K/V 却不能压缩位置——为什么？RoPE 的窗口外打分为什么会"失态"、位置插值怎么救回来，下一篇用一整套可复现实验讲透。

同链路的其它挂载：

- `10-KV-Cache与显存账本`：把本篇"per-token × T × L"的账展开成 PagedAttention / prefix cache / KV 量化，`05-推理与部署` 的地基。
- `03-模型家族`：读各厂商模型卡时，把本文的三连问套在 Qwen / MiniMax / DeepSeek 上逐家解构。
- `17-长上下文`：MLA（省 KV）+ RoPE 外推（拉长有效上下文）在此汇合，是长上下文体系的两大支柱。

> 一句话带走：**MHA/GQA 的 KV 账和头数成正比，MLA 把 K/V 压进一个 Dc 维潜向量，账只跟 Dc 走（+一小段位置尾巴）——DeepSeek-V2 规格 128k 总账从 MHA 的 488 GiB 砍到 8.6 GiB（账算）；代价是低秩瓶颈：潜向量看不到的方向，K/V 就没法表达。**
