# 🧭 Embedding 与词表：token 迈出向量的第一步

> 对应知识点：知识地图 **§17.2.10 Embedding 与词表**（🟢 掌握）——"token→稠密向量的查表层，输出层常共享同一矩阵"；前置：Tokenizer；**衍生**：多模态 patch embedding；**关系**：信息流的入口；**实践**：查看 128k 词表模型的 embedding 参数占用。紧承 Tokenizer（`08`）。
> 一句话： **Tokenizer 把文本切成了整数 id，但整数 id 自己落在"标签空间"，不能直接进注意力——Embedding 层就是那张"id → 稠密向量"的查表，是模型里第一次出现"向量"的地方。它前向只按索引取行（实测与 one-hot 矩阵乘严格相等 maxerr=0.0），所以前向成本跟着序列长度走、跟词表早晚无关（实测 4096 token 只碰到 128k 词表的 3%）；它的参数和输出层常共享同一张 128k×D 的大表（实测 tied 省一半参数）；而它"长什么样"，是语料统计的影子（同一语料 PPMI+SVD 就能把 model/练/数 的成对字聚到 0.8 的相似度）。**
> 可复现：本文数字全部来自 `code/scripts/embedding_demo.py` 实验 A1–A4（纯 CPU 秒级、语料与 08 章同一套；A1 查表恒等、A2 稀疏访问账、A3 权重共享账、A4 共现语义近邻）。

## 0. 为什么要再包一层：id 在标签空间

回顾 `01-Transformer` 里那条 shape 链的第一跳：`token (2,5) → x (2,5,8)`。Tokenizer 给了你 `(batch, seq)` 的**整数 id 矩阵**——但整数本身是"标签"，不是"数值"：`id=341` 与 `id=342` 之间没有"1 号含义接近"这种关系，你不会想在整数上做线性组合（`341×0.5 + 342×0.5` 是什么？毫无意义）。

所以任何自回归模型的第一步，都必须把每个整数 id **查表**成一个固定维度的稠密向量：

```text
token id  341 ──(embedding 查表)──▶  1×D 向量（hidden dim）
(batch, seq)            (batch, seq, D)
```

这一层就是知识地图说的"**信息流的入口**"：从这里开始，文本彻底变成了向量空间里的点，后面 Attention、FFN 对它们做的全部运算才有意义。本篇就拆这一层：它**怎么做**（查表）、**多贵**（稀疏访问 + 参数账）、**怎么和输出层共用**（tied）、**长什么样**（语义影子）。

---

## 1. 查表 = 按 id 取一行（实测 A1）

Embedding 层在 PyTorch 里就是 `nn.Embedding(V, D)`：一个形状 `(V, D)` 的可学习参数矩阵，前向时**按 id 取对应那一行**。为什么不是矩阵乘？因为"取行"本身就等价于最原始的教学写法——**one-hot 向量 × 权重矩阵**：

```python
# 教学写法（等价, 但浪费）       # 生产写法（等效, 零 FLOP）
x = onehot[id] @ W                x = W[id]           # 只取索引对应行
```

A1 直接验证这个恒等：随机权重下，两种写法逐元素误差 **maxerr = 0.0e+00**——一模一样，只是 one-hot 展开了 V 维。

```text
实测 A1 查表恒等：
  V=1000 H=64：lookup = W[id] 与 one-hot@W 恒等（maxerr=0.0e+00）
  one-hot 的代价是要先造 eye(128k, 128k)——本机实测直接 OOM：128k×128k×8B ≈ 128 GiB
```

这行自己演示了 the punchline：**词表越大，one-hot 展开越不可行**。工程实现在 3 万~15 万词表前就彻底放弃了"one-hot→矩阵乘"的写法，全部退化成 gather（取行）。这也是为什么 `nn.Embedding` 的权重就是一个 `(V, D)` 矩阵、梯度直接落在被取的那几行上。

> 一句话：**Embedding = 按 id 取行。写法上等价于 one-hot 乘矩阵，但 one-hot 展开在 128k 词表上物理上不可行（实测 128 GiB OOM）。**

## 2. 稀疏访问：前向成本 ∝ 序列长度，不 ∝ 词表（实测 A2）

既然是一次取值，embedding 前向的**时间成本只和取了多少行有关**——也就是 `batch × seq`，跟词表 `V` 无关。A2 把这个反差算给你看：

```text
实测 A2 稀疏访问（V=128,256 词表, H=4096）：
  batch=1  seq=4096：触碰 4,096 行 = 词表 128,256 的  3.19%（lookup 0 FLOP）
  batch=8  seq=4096：触碰 32,768 行 = 词表 128,256 的 25.55%（lookup 0 FLOP）
  one-hot 展开的对照：batch=1 要白算 4.3 TFLOP，batch=8 要白算 34.4 TFLOP
```

注意"3.19%"的反直觉点：**加一个零 embedding 参数都没加，前向却不变**。这跟"词表影响训练成本"的直觉并不矛盾——词表影响的是**参数数量与显存**（下下节），影响的是**后处理**（把 logits 投影回词表时 `(b,s) × (D,V)` 那一下是跟 V 成比例的，属于输出头）；但**入口这层**是稀疏访问，只跟序列长度走。

> 记忆抓手：**embedding 前向便宜，贵的是前向之后要跟 V 打交道的输出头，以及词表本身占的显存。**
> 小对照：`seq=4096` 的上下文在 128k 词表中只碰到 3.2% 的行——大多数词表的"书面价值"在这场前向里根本没被访问。这就是"行为 token 稀疏、参数连续存在"的第一课。

## 3. 输出层：反着用的同一张矩阵（tied embedding，实测 A3）

Transformer 的输出头（`nn.Linear(D, V)`，把最后隐藏向量投影回词表分数）和入口 embedding 形状**正好互为转置**：一个 `(V, D)`，一个 `(D, V)`。既然形状对称，一个久经考验的省参技巧就成立了——**tied embedding / weight tying：让两处共用同一张矩阵**。输出 logits 就是 `E · h`（`E` 是 embedding 矩阵，`h` 是最后隐藏向量），入口是 `x = E` 查表，方向相反、参数一份。

```text
实测 A3 权重共享账（V=32,000 × H=4,096）：
  共享（tied）：  131.1M 参数
  不共享：       262.1M 参数   → tied 省 50%
  账算 LLaMA-2-7B 全参 ~7B：131M / 7000M ≈ 1.9%——占 7B 参数的近 2%
  迷你验证：logits = E·h（同转置矩阵），argmax id=10687，该 id 的行就在 embedding 里
```

两个要点：

1. **省的不是零头**：`vocab × hidden` 在 7B 级是 1.3 亿参数，不共享 = 双份（2.6 亿）。早期 GPT 系（GPT-2 时代）爱 tied，后来 GPT-3/Llama 部分改不共享、把"词表/隐藏维度解耦"做进去——上表就是你在 OpenReview 里看到"130M 参数能省一半"时的那张账面；
2. **共享还有一个意思**：梯度会同时从"入口查表"和"输出投影"两条路径累加到同一张矩阵上——**embedding 既管"怎么把词变向量"，也管"怎么把向量变回词"，两套任务吃一份参数**。tied 是"参数-质量"接口处最直白的一次工程决策。

> 记忆抓手：**输出头是 embedding 的反向用法。词表头贵（(D,V) 成比例的那次乘），是它跟上下文长度挂钩；共享与否是"省一半表"与"解耦表达"的取舍。**

## 4. 实践任务：128k 词表的 embedding 参数账

知识地图 §17.2.10 的实践题是"查看 128k 词表模型的 embedding 参数占用"——`08-Tokenizer` 的 A4 已经把这笔账算全了，这里把它接上下文结论化：

```text
embedding 参数账（参数 = vocab × hidden，显存 = 参数 × 2B fp16）：
  vocab  32,000 × hidden  4,096 =  131.1M 参数   0.26 GB(fp16)   LLaMA-2 7B 风格
  vocab 128,256 × hidden  8,192 = 1050.7M 参数   2.10 GB(fp16)   LLaMA-3 8B 风格
  vocab 151,936 × hidden  4,096 =  622.3M 参数   1.24 GB(fp16)   Qwen1.5-7B 风格（账算）
  → Llama-3 的 128k 词表把 embedding 顶到 1.05B 参数（全模型的 ~13%）
```

- **"128k 词表模型的 embedding 怎么查"**：打开 model card 的 config，`vocab_size` × `hidden_size`，乘 2 字节（fp16）就是最小显存；上面三行就是步骤实例（Llama-3 竟然 1.05B，是 08 章"显存第一笔账"的正主）；
- **跟第 3 节串起来**：128k 词表 + 不共享输出头 = 两份 1.05B；tied 能砍到一份——所以**词表越大的模型，"输出头 vs embedding 共享套利"越诱人**；
- **给"衍生"留个钩子**：词表扩展（给领域加 token）就是在 151,936 行的矩阵尾部追加新行，`10000×hidden` 的新参数 + 无历史 id 的对齐成本（08 章 §9 已列）。

> 一句话带走：**embedding 是模型里"参数跟着词表走、显存跟着参数走"的第一笔固定账——128k 词表 (Llama-3) 已经 1.05B 参数 ≈ 13% 全参。**

## 5. 信息流的入口：向量几何 ≈ 语料统计的影子（实测 A4）

"入口"不只是在说位置，也在说**它装的是语义**。知识地图说"模型里一切都是向量运算"——那这些向量里到底有没有"语义的形状"？**Embedding 不学它自己，它的每一行都来自语料统计**：词与词同现越多，它们的位置越近。

A4 用最简单的非神经网络方法验证这一点：完全不用训练，直接在 08 章那套 56 句语料上统计共现 → PPMI → SVD 压到 32 维 → 算余弦相似度：

```text
实测 A4 同一语料 PPMI+SVD（词表 218 个基础单元, ±2 窗口, 32 维）：
  『模』 → 型(0.81)  坏(0.68)      ← 模型 / 模型好坏（语料里"决定模型好坏"）
  『型』 → 模(0.81)  坏(0.66)
  『数』 → 量(0.74)  据(0.72)      ← 数量 / 数据（"语料数量更能…"与"训练数据"）
  『训』 → 练(0.84)  定(0.71)      ← 训练（强共现）
  『token』 → size(0.74)  maps(0.73)  ← "vocabulary size"、"token vocabulary maps..."
  『the』 → controls(0.99)  predicts(0.99) ← 停用词稀释：和几乎所有词同现 → 向量≈语料平均
```

这组数字里藏着三个可以带走的判断：

1. **高频成对确实被"粘"出来了**：「模型」「训练」「数据」这些中文字对的相似度 0.74–0.84——**没有任何神经网络，光靠统计学，向量空间就把高频共现当成"近义结构"**。这就是模型的"先验观感"从哪来；
2. **`the` 的 0.99 是个教学彩蛋**：停用词和几乎所有词同现，向量退化成语料平均，于是跟谁都是"最相似"——**相似度高 ≠ 语义相关，还可能是"哪里都有它"**。真实模型的 embedding 里 stopword/标点也常出现这种"边缘扁化"；
3. **方法诚实**：这是 2013 年之前的 count-based（PPMI+SVD）路径，Word2Vec/GloVe 与它同源、后来才是可训练的 embedding——**"预训练"把"手写统计+降维"让位给了"梯度学出来的更圆滑版本"**，机制和这里的入口观感一脉相承。

> 一句话：**embedding 的几何先于任何训练就存在——它是语料共现的影子（实测「训→练」0.84）；模型后面的所有向量运算，解读方式和这里完全一样。**

## 6. 衍生：patch embedding 把"查表"换成"投影"

知识地图的衍生是"多模态 patch embedding"。它提示了 embedding 概念的**泛化**：只要"把一种东西变成向量，喂给 Transformer"的，都是 embedding 家族。再看文本——查表是"离散 id → 向量"；而图像没有天然的 token id，ViT 的办法是**把图像切成的 patch（如 16×16×3）摊平成向量，再用一个 `nn.Linear(patch_dim, D)` 线性投影到 D 维**——形状上这就是 "embedding"，只是"查表"换成了"投影"：

```text
patch embedding（ViT 风格）：
  图像 224×224×3 → 196 个 16×16×3 patch → (196, 768)  —— 形状上跟文本 (seq, 768) 一模一样
```

记住这个平行：**文本查表 × 图像投影 = 同一张"进 Transformer 的入口票"**，这也是多模态模型能"一个 Transformer 吃两种模态"的先决条件——进入后都是 `(seq, D)` 张量，Attention 不关心输入是查表还是投影来的。（完整展开在 `10-多模态` 的 ViT 章。）

## 7. 常见坑

| 坑 | 症状 | 修法 |
|---|---|---|
| 以为 embedding 是线性层 | 尝试 embedding 在大词表上做矩阵乘，内存炸/极慢 | embedding = 查表/gather（maxerr 0.0 等价 one-hot；128k 下 one-hot 物理不可行，实测 OOM） |
| 给 embedding 前向算 FLOP 蹭成本 | 报告"embedding 很贵" | 前向是稀疏访问，成本 ∝ `batch×seq`（实测 4096 token 触碰 3.2% 行）；贵的是输出头和参数显存 |
| 词表头另起炉灶 | 输出头 262M、多付一次 `(D,V)` | 可 tied 共享（省 50%）= 输出 logits 直接 `E·h`；128k 模型 tied 价值最大 |
| 拿近邻相似度当"语义"证据 | `the→controls 0.99` 看着像强相关 | 停用词/高频词向量≈语料平均（实测 A4），相似度高要先排除稀释 |
| 以为 embedding 是"学会的语义" | 觉得向量语义只来自训练 | 语义形状是语料共现给的（PPMI 也有同样近邻），训练只是让它更圆滑 |
| 忽略参数账 | 评估显存只数 head | embedding = vocab×hidden，Llama-3 128k 词表 = 1.05B ≈ 13%（A4 实践表） |

## 8. 衔接下一章

Embedding 做完了"信息流的入口"，下一个"贵"的点在**进去之后**：自回归逐 token 生成时，每一层注意力都要重新算所有历史的 K/V——把历史 K/V 缓存起来就是 KV Cache，它和这里的词表账同属"显存怎么花"的主战场，而且**量级大得多**。`03`/`04` 已经分别账过 GQA 与 MLA 的 KV 省法，下一章把它们收拢成一个统一账本：

> **[`10-KV-Cache与显存账本`](../02-核心原理/10-KV-Cache与显存账本.md)**：`03-多头注意力` 说过 GQA 把 8k KV 从 4GB 压到 1GB，`04-MLA` 说过 128k 长上下文 MHA 要 488GB 而 MLA 只要 8.6GB——都源自同一个公式：`2×层数×KV头数×头维×序列长度×字节`。本章把"KV Cache 为什么这么贵、怎么在 7B 模型 32k 长度下手算它"讲成一个完整账本（实测：MHA 16GB vs GQA 4GB、decode 快 14.0×、分页碎片 70%→1%、前缀缓存省 42%）。紧承 09-Embedding 之后，[`11-Logits 与采样`](../02-核心原理/11-Logits与采样-Temperature-TopK-TopP.md) 接力。

> 一句话带走：**Embedding 是 token 迈出向量的第一步——查表取行（恒等 one-hot、128k 物理不可行）、前向稀疏（∝序列长度、3.2% 触碰）、可与输出头共享（省 50%）、128k 词表占 1.05B 参数（≈13%）；它的语义形状先于训练就已藏在这套语料统计里（PPMI 近邻实测 0.8 档）。**
