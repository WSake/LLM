## 0. 为什么非要多头：一种关系不够用

先回到 `02` 篇的最后一句话：**注意力的每个头只能学会"一种关系"**。比如"剪刀"这个词：

- 一个头学到"剪刀 ↔ 剪刀"（主语一致性）
- 另一个头学到"剪刀 ↔ 纸张"（搭配关系）
- 第三个头学到"剪刀 ↔ 社区"（文化梗）

如果只有一个头，模型就只能在"剪纸张"和"剪头发"里挑一样学。**真实句子里的关系远不止一种，所以要并行开很多个会**。这正是 Multi-Head Attention 的设计动机（论文原话是"让不同的表示子空间去关注不同的关系"）。

> 类比：单头 = 只有一种出席角色的例会；多头 = 同时开 NHEAD 个会，每个会各盯各的关系。

## 1. MHA：把隐层切成 NHEAD 份并行打分

### 1.1 定义：从 1 个头到 NHEAD 个头

单头是 $y = \mathrm{att}(Q,K,V) V$（其中 Q=K=V=x），多头只是把它**切成 NHEAD 份同时做**：

$$
\text{MultiHead}(x) = \bigoplus_{h=1}^{H} \,\, {\underbrace{\mathrm{att}(xW_q^h, xW_k^h, xW_v^h)}_{\text{第 }h\text{个头各打各的分}}} \cdot W_o
$$

代价在于形象：把隐层 `C` 均分成 H 份（每份 `DH=C/H`），每个头用一份去算"一种关系"，最后拼回 `C` 维再过一个输出投影 `W_o`。**"并行"是数学上同时做，物理上就是一次矩阵乘。**

### 1.2 关键 shape 直觉

```text
x (B, T, C) —— 切成 H 个头
  → Q/K/V 各 (B, H, T, DH)
  → 打分矩阵（每头） (B, H, T, T)
  → 加权求和后拼回 (B, T, C)
```

每个头拥有**自己的一套 Wqᵏ、Wkᵏ、Wvᵏ**，它学会的关系互不干扰；最后的 `W_o` 把所有头的结果"翻译"成一句话。

## 2. 痛点：KV 头数 = 查询头数，显存与头数成正比

### 2.1 KV Cache：多头最贵的副产品

推理的时候（`01` 篇第 6 节），历史的 **K/V 会被缓存**起来不复算。但缓存不是白拿的——

- MHA 里**每个查询头配一组独立的 K/V**；
- 每组的 K/V 形状是 `(T, DH)`；
- 于是每层每 token 的 KV 缓存元素数 = $2 \times H \times DH$（K、V 两份）。

藏在里面的总账一句话：**KV 缓存的大小正比于 KV 头数 × 序列长度 × 层数**。头越多、上下文越长、模型越深，这笔账越贵——LSTM 时代完全没有这个账单，它是 Transformer 推理独有的。

### 2.2 完整显存账本公式（`10-KV-Cache` 的核心，这里先给雏形）

$$\text{KV\ Cache}=\underbrace{2}_{\text{K+V}}\;\times\;\underbrace{N_{KV}}_{\text{KV 头数}}\;\times\;DH\;\times\;2\mathrm{B}\;\times\;T\;\times\;L$$

当模型是 **7B 级别 + 32 图层**时，光是 KV 就能吃下几十 GB——`05-推理与部署` 天天算的就是这张账。而这一整章的核心问题只有一个：**这 $N_{KV}$ 真的要等于查询头数吗？**

## 3. 谱系三档：MHA / GQA / MQA 的同一行代码

### 3.1 为什么能共享：查询是"问"，K/V 是"线索库"

想一想：`q` 是每个 token 各自的"我在找什么"，必须每头一份（每个头问的问题不一样）；但 **K/V 是"线索库"——大家完全可以去同一个库查**。所以：

- **MHA**（每头一份 KV）：`KV头数 H_q = H`。表现上限最高，但 KV 最贵。
- **GQA（Grouped Query Attention）**（Llama-2 起标配）：`H_q` 头查询共用 `N_KV < H_q` 组 K/V（比如 Llama-2-7B 是 32 个查询头配 8 组 K/V）。质量损失很小，KV 大降。
- **MQA（Multi-Query Attention）**（Shazeer 2019，早于 GQA）：所有查询头共用**一组** K/V，KV 最小，但容易伤质量——GQA 是它的"插值"。

### 3.2 三种写法本质相同：共享 = 复制 N 份后照常打分

```python
# GQA/MQA 的"逐组共享"写法：查询头 h 用第 h // kpg 组 K/V
for h in range(NHEAD):
    a[:, h] = softmax(q[:, h] @ kv[:, h // kpg].T / sqrt(DH))

# "广播复制"写法：先把 nkv 组 K/V 复制成 NHEAD 份，再照常打分
kv_b = np.repeat(kv, NHEAD // nkv, axis=1)
a = softmax(q @ kv_b.transpose(0, 1, 3, 2) / sqrt(DH))
```

**两种写法数学上完全等价**（广播只是重新排列，不改变任何打分）。这一点非常重要，因为它是公平比较的基础：用 MHA 和 GQA 在相同打分下，**唯一区别是 KV 显存**。

## 4. 实测：两种写法打分一致 + 三档 KV 显存账

`attention_demo.py` 实验 D、E（迷你 `B,C,NHEAD,DH=2,8,4,2`，但账本规则与大模型完全一样——**乘同一个公式**）。以下为本机真实输出（seed 固定；账本为规格计算值而非实测值，已标注）。

### 4.1 打分一致性（实验 D）：共享不改变注意力

```text
MHA（K/V 头数 = 查询头数）| K/V 组数 (2,4,4,2) → 每组被 1 个查询头共享 | 两种写法 α 最大差 0.0e+00
GQA（K/V 头数 = 2）        | K/V 组数 (2,2,4,2) → 每组被 2 个查询头共享 | 两种写法 α 最大差 0.0e+00
MQA（K/V 头数 = 1）        | K/V 组数 (2,1,4,2) → 每组被 4 个查询头共享 | 两种写法 α 最大差 0.0e+00
→ '共享 K/V'不改变打分：广播复制 NHEAD 份后照常点积，结果逐元素一致（1e-16）
```

结论：**MHA / GQA / MQA 在相同输入下注意力权重决定性地相同**（数值甚至到 1e-16）。所以选哪档纯粹是"用多少 KV 显存/算量换多少头"的取舍。

### 4.2 三档 KV 显存账（实验 E，迷你）

```text
MHA(KV=查询头 4):  2×4×2×2B = 32 字节/token/层 × 4 token = 128 字节/层
GQA(KV=2):        2×2×2×2B = 16 字节/token/层 × 4 token =  64 字节/层
MQA(KV=1):        2×1×2×2B =  8 字节/token/层 × 4 token =  32 字节/层
→ GQA 省 2.0×，MQA 省 4.0×
```

**规则很简单：KV 省的比例 = 查询头数 ÷ KV 头数。** 这个乘数对任何规模都成立。

### 4.3 真实规格账算：LLaMA-2-7B（实验 E，账算非实测）

用公开规格（32 层、32 查询头、GQA 8 KV 头、hidden 4096、bf16）套同一个公式：

```text
每 token 每层 4 KB → 每 token 128 KB → 8k 上下文全 Cache ≈ 1.00 GB
同为 MHA（32 KV 头）→ 8k 全 Cache ≈ 4.00 GB（GQA 把 KV 账砍到 1/4）
```

**就这一个超参（KV 头数 32→8），8k 上下文的 KV 从 4 GB 降到 1 GB。** 这 3 GB 在多卡推理、长上下文、并发 batch 里就是实打实的成本。`10-KV-Cache与显存账本` 会把这个账算到 PagedAttention、KV 量化的级别，本文只要记住**"KV 头数是显存的总开关"**。

## 5. 选型：该用哪一档

| 档位 | KV 头数 | KV 账（相对 MHA） | 质量 | 当前定位 |
|---|---|---|---|---|
| **MHA** | = 查询头数 | 1× | 上限最高 | 老模型、对质量极致敏感的任务、注意力内部还要再砍（MLA）的兜底 |
| **GQA** | 头部数 / KV 组数（如 32/8） | ≈ 1/4× | **接近 MHA，几乎无损** | **Llama-2 起的事实标准**，绝大多数开源模型 |
| **MQA** | 1 | 1/H× | 掉点可见 | 历史上起过桥，现在少见；GQA=1 是它对质量与显存的折中 |

选型口诀：**先想"这任务多依赖细粒度的 multi-hop 关系"，再去看显存预算**。开源模型出厂就定死了 KV 头数，你真正要选的是"用哪家、撑多少上下文"——这两个数字对上了，GQA 的账就明白了。

## 6. 常见坑

| 坑 | 症状 | 修法 |
|---|---|---|
| 以为"多头"= "模型更宽" | 算参数量、显存时按 H×C 算 | 多头是**把 C 拆成 H 份并行**，参数量不变！只增加"打的分数"和（MHA 的）KV 量 |
| GQA 打分时维度接不上 | `q (B,H,T,DH)` 直接乘 `kv (B,nkv,T,DH)` 崩 | 先广播 `kv → (B,H,T,DH)`（`np.repeat(kv, H//nkv, axis=1)`），或逐组循环——**两者打分一致**（实测 1e-16） |
| 把 KV 头数当成查询头数 | 算 KV 账时用 32 而不是 8 | KV 账只跟 **KV 头数**走；查询头数再多也不增加缓存的 K/V |
| 以为 KV 缓存是"可选优化" | 只在显存不足才想起 | KV 是**推理必需**（复用免重算，`01` 第 6 节验证过差别 12×）；这里选的是"它多大" |
| 读模型卡只记"32 头" | 不理解 GQA 8 KV 头意味着什么 | 记住：**32 查询 / 8 KV → KV 账是满 MHA 的 1/4**，读模型卡时直接算这笔 |
