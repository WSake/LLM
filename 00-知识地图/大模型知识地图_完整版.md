 ## 0.2 技术演进的四条主线（理解主线 = 理解为什么不断有新东西）
 
 1. **规模主线（Scaling）**：算力、数据、参数一起增长（GPT-2 → GPT-3 → Llama → DeepSeek-V3 → 更大 MoE）。直接催生了：MoE（同样算力做更大的参数）、长上下文（上下文窗口是模型的工作内存）、多模态（把更多数据类型当作数据）、Scaling Law（决策该不该继续涨）、数据墙与合成数据（数据不够时怎么办）。
 2. **对齐主线（Alignment）**：预训练只能学续写，要变成听话的助手必须对齐人类偏好。催生了：SFT → RLHF(PPO) → DPO 家族 → GRPO → 推理模型（用 RL 把思考训出来）。这是 2022–2023 年 ChatGPT 爆发、2024–2025 年 o1/R1 等推理模型爆发的根源。
 3. **应用主线（Application → Agent）**：模型从聊天变成做事。催生了：Prompt → Structured Output → Function Calling → RAG → Workflow → Agent → Multi-Agent → Computer Use / Coding Agent → Agent 基础设施（MCP/A2A/ADK）。2024 年是 RAG 与 Agent 元年，2025 年是 Agent 生产化之年，2026 年进入「Agent 基础设施 + 推理成本工程」阶段。
 4. **效率主线（Efficiency）**：模型太大装不下、推理太慢太贵。催生了：量化（FP16→FP8→INT4）、KV Cache 优化、PagedAttention、Continuous Batching、投机解码、PD 分离、蒸馏、SLM/端侧、FP8 训练。这条主线决定了产品能不能赚钱、用户愿不愿等。

 ## 1.3 机器学习（🔴 必须掌握）
 - 核心概念：监督/自监督/无监督/强化学习的区别；过拟合与泛化；train/val/test 划分；正则化；偏差-方差。
 - 经典模型（了解）：线性回归、Logistic、决策树、SVM、KNN。

 ## 1.5 Transformer 前置知识（🟢 掌握）
 - NLP 基础：n-gram 语言模型、词法/句法/语义、分词（空格分词→BPE）。
 - 词向量：Word2Vec/GloVe/FastText（历史定位，但“分布语义”概念终身受用）。
 - 序列到序列（Seq2Seq）与 Attention 起源：Bahdanau 2015 / Luong 2015——Attention 先于 Transformer 出现，是 Transformer 的直接前身。
 - 关键认知：**语言模型 = 对 token 序列的联合概率建模；自回归 = 逐个预测下一个 token**。
 
 ## 1.6 GPU / CUDA / 并行计算基础（🟢 概念，🔴 推理/训练优化方向深入）

 - **实践**：跑通一个 AMP 训练脚本；用 `torch.profiler` 定位一次训练中的瓶颈（哪一步最慢、显存哪去了）。

 # 2. 大模型核心原理：按依赖链组织的技术演化
 
 > 本章是整个知识地图的心脏。同样一个名词（如 Attention），在不同时间点出现、被不同模型改写。下面按「为什么出现 → 解决什么问题 → 衍生了什么」讲述。
 
 ## 2.0 先建立一条“演化时间线”
 
 ```
 2017 Transformer（Attention is All You Need）
   → 2018 GPT-1（decoder-only 自回归）/ BERT（encoder-only 双向）
   → 2019 GPT-2（规模 + 零样本）
   → 2020 GPT-3（175B，In-context Learning 爆发）
   → 2022 InstructGPT/ChatGPT（SFT+RLHF）；CoT 提示词
   → 2023 Llama 1/2（开源范式：RMSNorm+RoPE+SwiGLU+GQA）；GPT-4；FlashAttention；LoRA 普及
   → 2024 DeepSeek-V2（MLA、MoE 极致化）；o1（推理模型）；长上下文 1M（Gemini 1.5）；DPO/GRPO 普及
   → 2025 DeepSeek-R1/V3、Qwen3、Llama 4、Kimi K2、GLM-4.5/5；MCP 标准化；Agent 生产化；FP8 训练主流化
   → 2026 推理模型普及、Test-time Compute、Agent 基础设施、Native Multimodal、混合架构、数据飞轮
 ```
 
 ## 2.1 Transformer（🔴 深入；前置：Attention、Embedding、深度学习基础）
 - **是什么**：2017 年提出的纯注意力序列模型（论文《Attention Is All You Need》），由「多头自注意力 + FFN + 残差 + LayerNorm」堆叠而成。
 - **为什么革命**：相对 RNN 的三点胜利——① 全序列并行计算（不再时间步串行）；② 任意两位置直接交互（O(1) 步解决长程依赖）；③ 训练可扩展（GPU 吃得饱）。
 - **两种形态**：Encoder-Decoder（原论文，翻译）；Decoder-Only（GPT 系，现代 LLM 主流）；Encoder-Only（BERT，已边缘化的 NLU 形态）。
 - **为什么 LLM 最终选择 Decoder-Only**：自回归目标 = 通用概率建模，天然支持 zero-shot/In-context；Encoder-Decoder 生成任务吃亏且架构复杂。GPT-2/3 的成功验证了这条路。
 - **衍生**：Attention 的每一种改法（MHA→GQA、RoPE 等）都是“补 Transformer 的短板”。
 
 ## 2.2 Attention 家族：Self / Cross / Masked（🔴 深入）
 - **Self-Attention**：每个 token 与其他所有 token 算相似度（Q·K），加权聚合 V。位置 i 输出 = Σ softmax(Qi·Kj/√d)·Vj。
 - **Cross-Attention**：Q 来自一方（如文本），K/V 来自另一方（如图像、检索文档）→ 多模态融合、RAG 的“注意力读取”。
 - **Masked（因果）Attention**：只允许看前面 token，保证自回归因果性。
 - **演化**：Bahdanau(2015) 加法注意力 → Luong(2015) 点积 → Vaswani(2017) 缩放点积多头 → FlashAttention(2022) 把 I/O 复杂度打下来（不存大矩阵、分块计算）→ 稀疏/线性注意力探索（Longformer/BigBird 历史尝试）。
 - **衍生**：KV Cache（重复计算优化）、PagedAttention（显存管理）、滑窗注意力（Mistral）、分层注意力（Llama 4 / NSA）、MLA（低秩压缩）。
 
 ## 2.3 多头注意力家族：MHA → MQA → GQA → MLA（🔴 掌握）
 - **MHA（2017）**：h 个头独立 Q/K/V。表达力强，但推理时 KV Cache 显存巨大。
 - **MQA（2019）**：所有头共享一份 K/V。KV Cache 缩小 h 倍，质量略降。
 - **GQA（Llama2，2023）**：把 h 个头分成 g 组，组内共享 K/V。g=1 即 MQA，g=h 即 MHA。**现在几乎所有开源模型标配 GQA**。
 - **演化关系**：推理成本压力越来越大 → 从“质量优先”走向“MHA→GQA”的显存-质量折中。
 - **MLA（DeepSeek-V2，2024）**：把 KV 压缩到低维潜空间，训练压缩、推理只缓存压缩向量，KV Cache 再降一个数量级。**GQA 是“少存”，MLA 是“压缩后存”**，两者可组合（DeepSeek-V3 即 MLA 系）。
 
 ## 2.4 位置编码：从“没有位置感”到 RoPE（🔴 掌握）
 - **问题**：Attention 是“集合运算”，不注入位置就无法区分“我打你”和“你打我”。
 - **演化链**：Sinusoidal(2017) → 可学习位置嵌入（GPT-2/BERT）→ ALiBi(2022，按距离线性衰减、外推好) → **RoPE**(2022，旋转位置编码，把相对位置编码进 Q/K 内积，当前绝对主流) → M-RoPE（多模态坐标）。
 - **RoPE 何以胜出**：① 内积形式天然表达相对位置；② 支持**位置外推**，配合 NTK-aware / YaRN / LongRoPE 能把 4k 窗口扩到 100k+；③ 实现简单，Llama/Qwen/Mistral/DeepSeek 全在用它。
 - **衍生**：窗口扩展（YaRN、NTK、LongRoPE）、M-RoPE（Qwen 多模态）、上下文蒸馏。
 - **注意**：位置编码与长上下文强相关，学 RoPE 必须同步学窗口扩展（§2.13）。
 
 ## 2.5 FFN 与激活函数：ReLU → GELU → SwiGLU（🟢 掌握）
 - **为什么需要 FFN**：Attention 是“token 间信息交换”，FFN 是“每个 token 自己的非线性变换/知识仓库”。**Transformer 约 2/3 参数在 FFN**——这正是 MoE 都做在 FFN 上的原因。
 - **演化**：ReLU(2017) → GELU(GPT-2 起) → **SwiGLU**(2020，门控线性单元，Llama 2 起默认)。
 - **SwiGLU 一句话**：输出 = Swish(W1·x) ⊙ (W2·x)，用“门控”选择信息流；质量好但参数多，需缩小隐藏层补偿（因此有 up/gate/down 三个矩阵）。
 - **衍生**：MoE（FFN 是天然“专家”）、Gated MLP 变体。
 
 ## 2.6 归一化：LayerNorm → Pre-Norm → RMSNorm（🟢 掌握）
 - **问题**：深层网络训练不稳定。
 - **演化**：Post-LN(2017，训练不稳) → Pre-Norm(2020，残差前归一化，稳定为主流) → **RMSNorm**(2021，去掉均值，省算力且效果相当，Llama 系标配) → DeepNorm(2022，深层训练稳定)。
 - **衍生（2024-2025 新趋势）**：QK-Norm（对 Q/K 再归一化，提升 FP8 训练稳定性，DeepSeek-V3/Qwen3 在用）。
 
 ## 2.7 Tokenizer：BPE → SentencePiece → BBPE（🟢 掌握）
 - **是什么**：把文本切成词表内的 token，是模型理解世界的“最小单位”。
 - **演化**：空格分词 → BPE(2016，GPT-2 起标准) → WordPiece(BERT) → Unigram(SentencePiece) → **BBPE/Byte-level BPE**（按字节再合并，LLaMA/Qwen 词表 3.2 万~15 万）。
 - **为什么重要**：① 词表大小直接决定嵌入层显存；② 分词效率 = 中文一个 token 还是几个 token，影响成本和速度；③ 换 tokenizer = 必须重新预训练。
 - **实践认知**：**不要自研 tokenizer**，直接用成熟词表；LLaMA-3 用 128k 词表（强压缩但 embedding 大）；Qwen 对中文友好。
 
 ## 2.8 Embedding 与词表（🟢 掌握）
 - Embedding = 查表把 token id 映射为稠密向量；输出层常用其转置（tied embedding）。
 - 大词表时 Embedding 参数巨大（128k × 4096 ≈ 5 亿参数），是显存重要构成。
 - 关键认知：**信息流 = token → Embedding → 多层 Attention/FFN → Logits**；模型里一切都是向量运算。
 
 ## 2.9 KV Cache：推理为什么那么贵（🔴 掌握）
 - **是什么**：自回归推理逐 token 生成，每步都要重新计算历史 K/V。**KV Cache = 缓存历史 K/V 空间换时间**。
 - **为什么重要**：① 长上下文时占显存 60%+；② 决定吞吐与延迟；③ 一切推理优化的主战场。
 - **问题与对策（这就是推理优化的大部分内容）**：
   - 显存碎片/浪费 → PagedAttention（按页管理）
   - 缓存太大 → GQA/MQA、MLA、KV 量化、H2O/SnapKV（剪不重要 token）
   - 重复计算 → Prefix Cache、Chunked Prefill
   - 超长上下文 → 滑动窗口、稀疏注意力、KV 卸载
 - **显存预算公式（要会算）**：KV 大小 ≈ 2 × 层数 × 头数 × 每头维度 × 序列长 × 字节(2) × 批量。
 
 ## 2.10 Logits / 采样与解码（🟢 掌握）
 - **Logits**：输出层每个 token 的分数，softmax 后为生成概率。
 - **确定性解码**：Greedy；Beam Search（保留 k 条路径，翻译/摘要用）。
 - **随机采样**：Temperature → Top-k → Top-p(nucleus) → Min-p(2023 后流行) → Mirostat(自适应)。
 - **为什么随机**：语言有多样性；但代码/数学要确定性 → 推理模型往往“默认思考 + 低温度”。
 - **注意**：`temperature/top_p/max_tokens` 是 API 标配参数；JSON mode/结构化输出是“约束解码”（§6）。
 
 ## 2.11 预训练（Pre-training）：先学会“续写”。（🟢 概念掌握，🔴 研究者深入）
 - **目标**：在亿万级文本上最大化“下一个 token 的似然”（Next Token Prediction）。
 - **为什么“续写”够用**：语料隐含着知识、语法、推理、世界事实；预测下一个词 = 对世界做有损压缩。
 - **训练要点**：超大 Batch（百万级 token）、序列长（8k→256k）、warmup + cosine、AdamW、梯度裁剪、BF16/FP8 混合精度。
 - **衍生**：CPT（领域继续预训练）、多阶段训练（先普通长度，再长上下文续训）、数据配比（决定能力曲线）。
 - **误区**：PPL 低 ≠ 好用 → 必须配合下游评测，这正是对齐技术出现的动因。
 
 ## 2.12 SFT（监督微调）：教模型“怎么回答”。（🔴 掌握）
 - **是什么**：用「指令 → 理想回答」对做监督训练，把“续写机器”变成“助手”。
 - **关键认知**：预训练决定“知道什么”，SFT 决定“怎么表达”；**SFT 质量 >> 数量**（几千条优质数据常胜过百万条低质数据）。
 - **数据要点**：任务多样性、格式一致性（角色模板）、回复质量、错误标注的污染。
 - **衍生**：SFT 是对齐第一课；LoRA/QLoRA 使其成本大降；后续是否还要 RL 是争论点（结论：要，但 SFT 是必要起点）。
 ## 2.13 偏好对齐家族：RLHF(PPO) → DPO → GRPO（🔴 掌握原理，🟢 会跑）
 - **为什么需要**：SFT 只学“示例回答”，模型仍会敷衍、谄媚、胡说。对齐 = 让模型输出人类真正喜欢的结果。
 - **RLHF 标准范式（InstructGPT，2022）**：三步——① SFT；② 训练 Reward Model（对同一问题的人类偏好对打标，预测哪条更好）；③ 用 PPO 以 RM 为奖励优化策略，同时加 KL 惩罚防跑偏。
 - **PPO（2017，强化学习算法）**：stable、通用，但重——需要策略/参考/价值网络等 4 个模型、需要 on-policy 采样、超参敏感。代价高 = 催生了 DPO 家族。
 - **DPO（2023，《Direct Preference Optimization》）**：把“先训 RM 再做 RL”合并成一个简单的分类损失——直接基于偏好对更新策略，无需 RM、无需在线采样。效果接近 RLHF、训练成本低一个数量级，2023-2024 微调标配。
 - **DPO 家族（顺着“更简单/更稳”这条路）**：IPO（更少过拟合）、KTO（无需成对，只要好/坏标签）、ORPO（SFT 与对齐一步到位）、SimPO（去掉参考模型）、RSO（更好的偏好数据采样）、SPIN（自我对弈）、迭代式 DPO（Zephyr/Tulu 实践：SFT→DPO→重采样→再 DPO）。
 - **GRPO（DeepSeekMath 2024，DeepSeek-R1 核心）**：Group Relative Policy Optimization——对一个 prompt 采样一组回答，用组内相对优势代替价值网络（Critic），大幅省显存和实现复杂度。当前推理模型 RL 的事实标准（R1、Qwen3、Kimi K2、GLM 均使用或类似）。
 - **其他重要方法**：Rejection Sampling（先采样再筛好回答做 SFT，R1 用）、Best-of-N（N 个采样取最优，无梯度）、RLAIF/Constitutional AI（用 AI 打分代替人类标注，Claude 首创）、RLVR（基于可验证奖励的 RL，见 2.17）。
 - **关系总结**：PPO 是“重型万金油”，DPO 是“轻量离线替代”，GRPO 是“为推理 RL 而生”的在线方法。2025 年主流配方：SFT + 拒绝采样强化数据 + RL（GRPO/RLVR）；DPO 用于低成本微调。
 
 ## 2.14 MoE（混合专家）：用同样算力把模型做得更大（🔴 掌握）
 - **是什么**：把每一层的 FFN 换成 N 个“专家”FFN，每个 token 只激活 Top-k（如 8 选 2）个专家 → 总参数巨大，但单 token 计算量不变。
 - **为什么出现**：Dense 模型涨参数 = 涨算力；MoE 把“参数量”和“单 token 算力”解耦，是规模主线与成本约束妥协的产物。
 - **关键组件**：Router（路由）、Top-k 选择、负载均衡（经典 aux loss；DeepSeek-V3 改用无辅助损失的 bias 调节）、共享专家（DeepSeek 的 always-on 专家承载通用知识）、细粒度专家（把专家切小，组合更灵活）。
 - **演化链**：Shazeer 2017（稀疏门控 MoE 鼻祖）→ Switch Transformer(2021)/GShard → Mixtral 8x7B(2023，首个开源走红) → DeepSeek-V2/V3(2024-2025，MLA+细粒度专家+FP8，单 token 只激活约 5% 参数) → Qwen3-MoE/Llama4/Kimi K2(2025)。
 - **MoE 的问题**：显存占用大（全量参数常驻）、Expert Parallel 通信开销、路由不均衡导致专家闲置、推理时需要精细调度。
 - **实践认知**：MoE 的“总参数”很大，但“激活参数”决定推理速度；看模型先看 Active Params 而不是总参数量。
 
 ## 2.15 Dense vs MoE：怎么选（🟢 掌握）
 | 维度 | Dense | MoE |
 |---|---|---|
 | 结构 | 每个 token 过全部参数 | 每个 token 只过 Top-k 专家 |
 | 总参数/激活参数 | 相同 | 总参数远大于激活参数 |
 | 单 token 推理成本 | 高（全算） | 低（只算激活部分） |
 | 显存占用 | 相对小 | 大（全量专家要驻留显存） |
 | 训练成本 | 随参数线性涨 | 同算力下可做得更大更强 |
 | 适合场景 | 中小模型、端侧、延迟敏感 | 超大模型、极致性价比、云端 |
 | 代表 | GPT-4(推测)、Llama-3、Qwen3-Dense、Gemma | Mixtral、DeepSeek-V3、Qwen3-MoE、Llama4、Kimi K2 |
 
 > 2025-2026 趋势：30B 以上开源模型基本都 MoE 化，Dense 仍是 1B-32B 区间主力；“MoE 化 + 蒸馏”是开源做强模型的两条腿。
 
 ## 2.16 长上下文：让模型“读得下整本书”（🔴 掌握技术路径）
 - **为什么需要**：代码仓库、长文档、Agent 多轮工具日志、多模态视频都需要大窗口；上下文是模型的新“工作内存”。
 - **技术路径（四个层面叠加）**：
   1. **训练侧**：更长序列预训练/续训（成本随长度平方级上升）→ 一般“先短后长”两段式训练。
   2. **位置编码侧**：RoPE 窗口扩展（NTK/YaRN/LongRoPE）→ 给旧模型低成本扩窗。
   3. **架构侧**：滑窗+全局锚点（Mistral、Gemma2）、稀疏注意力（NSA）、MLA/KV 压缩、分层注意力（Llama 4 的 interleaved attention）、Infini-attention（压缩记忆）。
   4. **推理/系统侧**：KV 量化、PagedAttention、Prefix Cache、上下文压缩（LLMLingua）、长上下文评测（大海捞针）。
 - **评测**：RULER / LongBench / LongICLBench / Needle-in-a-Haystack（注意：能“找针”不等于真能用长文，要看 LongBench 类任务）。
 - **实践认知**：真实产品中“长上下文访问”常通过 RAG 与上下文工程实现（§6/§8），把“窗口”与“检索”结合，而不是无限追求窗口长度。
 
 ## 2.17 推理模型（Reasoning Model）：从“想都不想”到“思考后再答”（🔴 掌握）
 - **背景**：普通 LLM 是“第一直觉出词”；推理模型在回答前先生成一段内部思考（Chain-of-Thought / 思考 token），再给结论。
 - **演化链**：CoT 提示词(2022) → Self-Consistency(2022) → ReAct(2022) → Tree-of-Thoughts(2023) → STaR(2022)/RFT(2023，用正确推理样本做 SFT) → o1(2024，OpenAI 用 RL 优化思考链，涌现自我修正) → DeepSeek-R1(2025，GRPO + 可验证奖励，开源验证“RL 出推理”+ R1-Zero 无监督涌现) → Qwen3-thinking/QwQ、Kimi k1.5、GLM-Z1 跟进 → 2025-2026 推理能力成为标准能力。
 - **关键概念**：
   - **Test-time Scaling / Thought Budget**：给模型更多思考 token、更长时间 → 推理质量提升（推理时的 scaling law）；可理解为“用推理时算力换训练时算力”。
   - **RLVR（Verifiable Reward RL）**：只奖励“答案对不对”（数学、代码可自动验证），不需要人类偏好标注 → 推理 RL 的燃料。
   - **Distillation（蒸馏）**：R1 把思考数据蒸馏进小模型 → 推理能力低成本下沉到 1.5B/7B 级别。
 - **代价与问题**：思考 token 让延迟和成本上涨 3-10 倍 → 催生思考预算控制、快/慢模型路由（hybrid thinking mode 如 Qwen3）、推理系统优化。
 - **实践认知**：API 上注意 reasoning_effort / 思考预算参数；产品上“复杂任务用推理模型、简单任务用快模型”是 2026 年的标准成本策略。
 
 ## 2.18 Scaling Law（规模定律）：决定“要不要继续涨”（🟢 概念，🔴 研究者深入）
 - **提出**：Kaplan et al., 2020（loss 随参数/数据/算力幂律下降）；Chinchilla, 2022（参数-数据要均衡，约 20 tokens/参数）。
 - **核心结论**：模型能力 ≈ f(参数量, 数据量, 算力)；但最优比会漂移——2023 年后开源模型普遍“过度训练”（Llama3/Qwen 用 10-20T token 远超 Chinchilla 建议），因为推理期便宜、数据周期短。
 - **衍生概念**：数据墙（高质量自然文本将耗尽 → 合成数据、推理数据成新燃料）、Test-time Scaling（推理算力也是一条 scaling 曲线）、Emergent Abilities（2022 提出、2023 被质疑为 metric 假象——少谈“涌现神话”，多做实测）、蒸馏（另一种“免费”scaling）。
 - **实践认知**：shrink-and-replicate（训练一个大模型，蒸馏出一串小模型分层部署）与数据飞轮（用户数据→评测→再训练）是 2025-2026 的主流算账方式。
 
 ## 2.19 蒸馏（Distillation）与 CPT（继续预训练）：两条“低成本获得能力”的路径（🟢 掌握）
 - **蒸馏**：用教师模型输出训练学生模型。白盒（logits/KL）与黑盒（文本）之分；R1-Distill 是黑盒文本蒸馏标杆，是小模型性价比的来源。
 - **CPT（Continued Pre-training）**：通用预训练后用领域/语言/长文本数据继续预训练——注意防灾难性遗忘（加通用语料回放），领域模型的标准第一步。
 - **关系**：CPT 补“知识”，SFT 补“行为”，RL 补“偏好/推理”，蒸馏是“能力迁移”。四者组合 = 领域模型流水线（§14）。

 # 3. 主流大模型架构与模型家族
 
 > 读法：不要背参数，用统一的「八要素」去解构每个家族：模型架构 → Attention → FFN/MoE → 训练方式 → 推理方式 → 上下文 → 多模态 → Reasoning。每个家族 = 一次技术演进的实验报告。
 
 ## 3.1 GPT 系列（闭源范式定义者）
 - **技术节点**：GPT-1(2018, decoder-only 预训练+微调) → GPT-2(2019, 规模与 zero-shot) → GPT-3(2020, 175B, In-context Learning) → InstructGPT(2022, SFT+RLHF) → ChatGPT(2022) → GPT-4(2023, 视觉) → GPT-4o(2024, 原生音频) → o1/o3(2024-2025, 推理模型) → GPT-5.x(2025—, 统一各能力的方向)。
 - **八要素速写**：架构=decoder-only；Attention=自回归+MHA 系（细节不公开）；训练=预训练+SFT+RLHF+RLVR；推理=闭源 API + 推理预算；上下文=128k~1M；多模态=原生化（GPT-4o/GPT-5）；Reasoning=o 系列开创者。
 - **影响力**：每个“GPT 概念”（预训练-微调范式、In-context Learning、RLHF、推理模型、Agent 接口）都定义了行业术语与 API 标准。
 - **学习价值**：论文与官方文档的价值大于模型本身；重点读 GPT-2/3、InstructGPT、o1 报告。
 
 ## 3.2 Llama 系列（开源范式的发动机）
 - **技术节点**：Llama1(2023, RMSNorm+RoPE+SwiGLU) → Llama2(2023, GQA 全系+商用许可+公开对齐细节) → Llama3(2024, 128k 词表, 8B/70B Dense, 15T token) → Llama3.1(2024, 405B Dense, 128k 上下文) → Llama3.2(2024, 1B/3B 小模型+11B/90B 视觉) → Llama4(2025, MoE Scout 109B-A17B / Maverick 400B-A17B, 原生多模态, interleaved attention)。
 - **影响力**：**Llama 骨架 = 开源模型事实标准**（RMSNorm/GQA/SwiGLU/RoPE 的组合拳成为默认装配）；百万社区微调模型基于它；Llama4 把 MoE 与多模态带入开源主流。
 - **学习价值**：Llama2 论文是“如何做对齐”的最佳入门材料；架构上 Llama 系是理解其他开源的基准线。
 
 ## 3.3 Qwen 系列（阿里；中文最强 + 全家桶生态）
 - **技术节点**：Qwen1.5(2024) → Qwen2(2024, GQA, 32k→128k) → Qwen2.5(2024, 0.5B-72B, 长上下文与代码数学强化) → Qwen3(2025, Dense 0.6B-32B + MoE 30B-A3B/235B-A22B, hybrid thinking mode, 原生工具调用) → Qwen3-VL / Qwen2.5-Coder / QwQ(推理) 等。
 - **八要素速写**：架构=经典 Llama 骨架+自有工程细节；Attention=GQA（多模态用 M-RoPE）；FFN=SwiGLU（MoE 版细粒度专家）；训练=超长预训练+强化学习；上下文=128k~1M；多模态=Qwen-VL 系列（动态分辨率、视频、Agentic UI）；Reasoning=QwQ→Qwen3 思考模式。
 - **影响力**：开源“全栈能力王”：语言/VL/Coder/Embedding/量化/API 生态最完整；中文能力长期第一梯队；是学习“Dense 与 MoE 两条腿走路”的最佳范本。
 
 ## 3.4 DeepSeek 系列（技术创新发动机）
 - **技术节点**：DeepSeek-V2(2024, **MLA**+细粒度 MoE) → DeepSeek-V3(2024-12, 671B MoE/37B active, **FP8 训练**, MTP 多 token 预测, 无辅助损失负载均衡) → DeepSeek-R1(2025, **R1-Zero 纯 RL 涌现反思** + R1 冷启动+RL+蒸馏, GRPO) → R1-Distill(把思考蒸馏进 1.5B-70B 小模型) → V3.1/V3.2(2025)。
 - **八要素速写**：Attention=MLA（KV 压缩省显存）；FFN=细粒度 MoE+共享专家；训练=FP8 混合精度+多 token 预测+GRPO；推理=长思考输出+开源权重可自部署；上下文=128k 级；多模态=R1-V 视觉推理；Reasoning=开源推理模型标杆。
 - **影响力**：MLA 被多家采用；FP8 训练成为事实标准；**开源 RL-for-Reasoning 路径奠基者**；API 定价战拉低全行业推理成本。
 - **学习价值**：读 MLA 核心章节、R1 论文、V3 技术报告——这是近三年开源界最有价值的三个文档。
 
 ## 3.5 Mistral / Mixtral（欧洲；MoE 与滑窗的示范）
 - **技术节点**：Mistral 7B(2023, 滑窗注意力 SWA + GQA) → Mixtral 8x7B(2023, 首个走红开源 MoE) → Mixtral 8x22B(2024) → Mistral Large/Small 系、Codestral/Mathstral。
 - **八要素速写**：Attention=SWA（滑窗+滚动）；FFN=MoE(8x7B 每 token 2 专家)；训练=公开权重+少量细节；上下文=32k；多模态=弱；Reasoning=一般。
 - **影响力**：让“MoE 不神秘、可落地”成为共识；SWA 是长上下文低成本的早期尝试。
 
 ## 3.6 Gemma 系列（Google 开源；小模型质量标杆）
 - **技术节点**：Gemma1(2024, 2B/7B) → Gemma2(2024, 9B/27B, 局部+全局注意力交替) → Gemma3(2025, 1B-27B, 图像输入, 128k)。
 - **八要素速写**：架构=decoder-only；Attention=交替局部/全局；FFN=标准 SwiGLU；训练=Google 数据（含蒸馏传闻）；上下文=8k→128k；多模态=Gemma3 起支持图像；Reasoning=弱（通用任务向）。
 - **影响力**：Dense 小模型的质量参考系；适合端侧、蒸馏底座、合规部署。
 
 ## 3.7 Claude 系列（Anthropic；安全与 Agent 标杆）
 - **技术节点**：Claude1/2(2023, **Constitutional AI**) → Claude3(2024, Opus/Sonnet/Haiku, 视觉) → Claude3.5 Sonnet(2024, 编程/Agent 强) → Claude3.7(2025, **混合推理 extended thinking**) → Claude4/4.5(2025, 长 Agent 任务优化)。
 - **八要素速写**：架构=闭源；训练=宪法 AI/RLAIF + 大规模 RL；上下文=200k~1M；多模态=文档/截图理解强；Reasoning=思考切换（快/慢）；Agent=Computer Use、Artifacts、**MCP 发起者(2024-11)**。
 - **影响力**：定义“安全对齐可产品化”；MCP 成为 Agent 工具互操作事实标准；SWE-bench/tau-bench 常青树。
 
 ## 3.8 Gemini 系列（Google；原生多模态 + 超长上下文）
 - **技术节点**：Gemini1.0(2023-12, Pro/Ultra/Nano) → Gemini1.5(2024, MoE, **1M~2M 上下文**, 原生音频/视频) → Gemini2.0/2.5(2025, Agentic：代码执行/搜索/浏览器, thinking) → Gemini3(2025 末起, 大版本迭代)。
 - **八要素速写**：架构=原生多模态（不靠 adapter 拼接）；Attention=MoE+超长上下文训练；训练=多模态语料直训；上下文=1M+（第一梯队）；多模态=全模态原生（文本/图像/音/视频）；Reasoning=thinking 模式；Agent=与 Google 搜索/生态深度绑定。
 - **影响力**：把“上下文即工作内存”与“原生多模态”变成产品现实；长上下文评测的参照系。
 
 ## 3.9 GLM 系列（智谱；国内开源主力）

 # 4. 大模型训练体系：数据 → 预训练 → 对齐 → 微调 → 评测
 
 ## 4.0 全链路总览（一条流水线）
 
 ```
 Web/Crawl/书籍/代码/多模态
   → 过滤清洗（质量/毒/隐私/去重/去污染）
   → 数据配比（语言/领域/质量分层）
   → Tokenization → 预训练（CPT 可插队）
   → SFT 数据（指令-回答）
   → SFT（LoRA 或全参）
   → Preference 数据（好/坏对）→ DPO 或 RM+PPO
   → RL 数据（可验证任务）→ GRPO/RLVR
   → 蒸馏（大→小）
   → 评测（Benchmark/人工/LLM-judge）→ 回到数据与训练
 ```
 
 **核心原则**：数据决定能力上限；SFT 决定行为；RL 决定偏好与推理；评测决定是否放行。**训练不是一次跑完，而是一个不断回环的数据-训练-评测飞轮。**
 
 ## 4.1 预训练数据工程（🔴 数据工程师/研究者）
 - **采集**：Common Crawl（网页）、GitHub（代码）、arXiv/书籍/论文、维基、多语言语料、专利/新闻；多模态还需图像/音视频字幕。
 - **清洗**：HTML 解析、去模板/广告/导航、语言识别（fastText/LID）、质量过滤（启发式规则 + 分类器打分，如 Gopher/RefinedWeb）、毒性/色情过滤、PII 脱敏。
 - **去重**：精确去重（MinHash/LSH、SimHash）与近似去重（句子级、文档级）；**去重直接影响训练效率与记忆污染**。
 - **去污染（Decontamination）**：把评测集从训练语料中剔除（用子串/Embedding 匹配）——这是评测可信度的前提。
 - **数据配比**：语言配比（中文/英文/多语）、领域配比（网页/代码/数学/书）、质量分层（高质量重复抽样）；**配比是最便宜的“能力配方”**。
 - **Tokenization**：按语言特性选词表与字节模式；坏 tokenizer 会浪费 10-20% 训练预算。
 - **实践**：读 FineWeb/RedPajama/TinyStories 的论文与代码；用 `datasets`/`Dolma` 跑通一个 10GB 语料的小型处理管线。
 
 ## 4.2 合成数据（Synthetic Data）（🟢 掌握；2024 年后核心议题）
 - **为什么**：高质量自然文本接近枯竭（数据墙）；合成数据可定向“造”难题（数学、代码、推理、多语言、指令）。
 - **方法**：蒸馏（教师模型产数据）、Self-Instruct（模型自问自答）、拒绝采样（采样+过滤）、增强（改写/翻译/对话展开）、代码执行器（验证正确性）。
 - **对与错**：对——扩大覆盖、控制分布、用于 SFT/偏好/推理；错——纯合成容易“模型自欺”、分布坍塌、夹生知识；**合成数据永远要和真实数据/评测交叉验证**。
 - **数据飞轮**：线上反馈（点赞/纠错/评测失败样本）回流 → 新一轮训练。这是 2025-2026 各家组织的核心资产。
 
 ## 4.3 SFT 数据（🟢 掌握构造方法）
 - **来源**：人工标注、LLM 蒸馏、社区（OpenHermes/UltraChat/OpenAssistant）、内部模板。
 - **质量维度**：指令多样性、回答正确性、格式一致性（chat template）、拒绝能力（知道什么不该答）、难度梯度。
 - **数量认知**：指令跟随几千条就有效，知识注入需要更多；**一个错误标注的伤害约等于 N 条正确数据**。
 - **格式**：System/User/Assistant 角色模板必须与推理/训练时一致（chat template 是“软接口协议”）。
 
 ## 4.4 Preference 数据 与 Reward Model（🟢 掌握）
 - **偏好数据**：同一 prompt 的 (chosen, rejected) 对，来源为人标注或 AI 比较；Bradley-Terry 模型是把“二元偏好”转为标量奖励的数学基础。
 - **RM 的类型**：标量打分模型（传统，Bradley-Terry）、多维度 RM、结果奖励 ORM/过程奖励 PRM（过程奖励适合推理、代价高）、作为数据（DPO 不需要 RM）。
 - **DPO 对齐时的数据坑**：偏好对要“区分度够”（两条差不多就学不到东西）、避免长度偏置（长回答被偏好 → 需要长度正则）、prompt 分布要与真实使用一致。
 
 ## 4.5 RL 数据与可验证奖励（🟢 掌握；推理模型的关键）
 - **RL 数据的形态**：无需人类偏好，只要“任务 + 可自动验证的结果”（数学答案、代码通过率、格式约束、检索命中）。
 - **奖励设计**：规则打分（对错）、LLM-as-judge（开放式任务）、过程奖励（每步对错）、组合奖励（正确性+格式+拒绝）。
 - **实践要点**：奖励有噪声时要大采样取多数票；prompt 难度要覆盖“会与不会”之间；RLVR 数据来自评测失败样本与真题。
 
 ## 4.6 全参微调与 PEFT（🔴 掌握 LoRA，🟢 熟悉全参）
 - **Full Fine-tuning**：全参数更新，效果上限最高、显存需求最大；适合任务剧变或需要新知识时的短程微调。
 - **LoRA（2021，Low-Rank Adaptation）**：冻结原权重，训练低秩矩阵 A·B（W + BA）；参数量降到 0.1-1%，效果接近全参（越大模型越接近）。**为什么有效**：微调的本质更新是低秩的。
 - **QLoRA（2023）**：4-bit NF4 量化 + 分页优化器 + LoRA，4090 也能微调 70B 级模型；个人/单卡微调的事实标准。
 - **LoRA 变体**：DoRA（分解权重幅值/方向）、LoRA+（不同学习率）、rsLoRA、PiSSA（初始化改进）；Adapter/Prefix/Prompt-Tuning 已边缘化（了解即可）。
 - **分布式微调**：LoRA 也要过 Data Parallel/FSDP；长上下文微调用序列并行。
 - **其他全参变体**：DoRA/Freeze（冻结部分层只训 classifier 的旧做法已过时）。
 
 ## 4.7 训练并行策略（🔴 掌握概念）
 - **DP(数据并行)**：每卡一份模型，各训各的数据，梯度 all-reduce。最简单；模型装不下时失效。
 - **ZeRO/FSDP（分片数据并行）**：数据并行 + 把优化器/梯度/权重分片到各卡，按需聚合。**训练大模型的首选起点**（DeepSpeed ZeRO-1/2/3；PyTorch FSDP）。
 - **TP(张量并行)**：把单个矩阵切成多卡各算一块（Megatron 风格），卡间通信密集（NVLink 友好）。
 - **PP(流水线并行)**：按层切分，前向像流水线；通信少、但有空泡（bubble），多用于超大模型。
 - **SP(序列并行)**：把长序列的激活分片；长上下文训练的钥匙。
 - **EP(专家并行)**：MoE 专属，专家分布在不同卡上（DeepSeek/Qwen3 都用）。
 - **3D/混合并行**：TP×PP×DP(+EP) 组合使用，一张 H100 的集群怎么排布是系统工程；“算力-显存-通信”三角权衡。
 
 ## 4.8 训练框架横向对比（同层比较，不评“谁最好”）
 
 | 框架 | 定位 | 擅长 | 短板/注意 |
 |---|---|---|---|
 | PyTorch | 底层运行时 | 张量/自动求导/分布式原语 | 生产级并行需组装 |
 | DeepSpeed（MS） | 训练引擎 | ZeRO/Offload/混合精度/管线优化 | 与最新模型版本需适配 |

 > 选型建议：个人/单卡 → Transformers + PEFT + Unsloth；中小团队微调 → LLaMA-Factory / Axolotl；预训练或大集群 → Megatron-Core 或 DeepSpeed；RL/推理训练 → verl / TRL；国产算力 → MindSpore/PaddleNLP/MindIE 系。
 
 ## 4.9 训练工程细节（🟢 会排错）
 - **精度**：FP32（参考）→ BF16/FP16（主力，BF16 尾数宽更稳）→ FP8（超大模型，DeepSeek-V3 示范）。
 - **显存五件套**：权重 + 梯度 + 优化器状态（Adam 占权重的 16 倍） + 激活 + 通信缓冲——看懂每个 batch 的显存计算才能选并行策略。
 - **关键参数**：学习率（预训练 ~3e-4，LoRA ~1e-4~2e-4）、warmup、batch 大小（预训练以“多少 token per step”计量）、梯度累积、梯度裁剪、max length。
 - **检查点（Checkpoint）**：safetensors 为格式标准；断点续训必须做；Megatron/FSDP 各有分片格式。
 - **可复现问题**：数据集 shuffle 种子、分布式随机性、Dropout 关闭策略。
 - **监测**：loss 曲线（PPL）、梯度范数、学习率曲线、GPU 利用率、显存水位、通信占比；用 W&B / TensorBoard / MLflow。
 
 ## 4.10 评测在训练闭环中的位置（🟢 掌握）
 - 训练循环里要有“评测门禁”：预训练看 PPL + 少量下游抽样；SFT/RL 后跑全量精选集（能力回归 + 上线导向集）。
 - **训练失败模式**：loss 降但能力跌（数据污染/过度训练）；SFT 后通用能力崩（遗忘，需回放）；RL 后格式崩（奖励黑客）。
 - 评测的完整体系见第 11 章。

 # 5. 大模型推理与部署
 
 ## 5.0 推理为什么难：先建立三个认知
 1. **两阶段本质**：推理分 Prefill（处理全部输入，计算密集、矩阵乘法吞吐大）与 Decode（逐 token 生成，访存密集、显存带宽主导）。优化要分开做。
 2. **三大瓶颈**：显存容量（权重+KV Cache）、显存带宽（decode 时“读权重都快不过来”）、调度效率（请求多了要抢算力）。
 3. **一条主链路**：模型权重格式 → 加载/量化 → 显存布局 → 调度（batching）→ 解码优化 → 多卡并行 → 服务层（API/网关/监控）。
 
 ## 5.1 模型加载与权重格式（🟢 掌握）
 - **HF safetensors**：开源 Python 生态的标准权重格式（安全、支持切片加载）；transformers/vLLM 默认。
 - **bin/ckpt**：PyTorch 原生格式（早期流行，现在默认转 safetensors）。
 - **GGUF**：llama.cpp 系的量化分片格式（单文件、任意精度、端侧友好）。
 - **Engine/Plan**：TensorRT-LLM 编译产物（绑定硬件与 batch 形状，性能最好但不可移植）。
 - **加载显存账**：参数量 × 精度字节 = 最小显存（如 7B FP16 ≈ 14GB）；还要留 KV Cache 与激活空间。
 
 ## 5.2 精度与量化（🔴 掌握概念与选型）
 - **FP32 / FP16 / BF16**：训练与推理的全精度选项；BF16 动态范围大最稳；FP16 省一半。
 - **FP8**：E4M3/E5M2，2024-2025 推理新标配（性能翻倍、损失小）；训练侧 DeepSeek-V3 示范。
 - **INT8（W8A8）**：权重+激活都量化，配合 SmoothQuant（把激活尖峰挪到权重）几乎无损；属于真正的系统级优化。
 - **INT4（W4A16，权重 4bit+激活 16bit）**：GPTQ（训练后量化，校准集）、AWQ（激活感知，按通道保留重要权重）、GGUF（llama.cpp 的 k-quants，混合位宽）。
 - **量化对象要分清**：只量化权重（weight-only，最常用）、量化激活（难，需 SmoothQuant）、量化 KV Cache（FP8/INT8，长上下文收益大）。
 - **工具链**：bitsandbytes（NF4，QLoRA 训练用）、auto-gptq、awq、llama.cpp quantize、vLLM 原生量化；**量化后必须跑评测对比**（质量-速度-显存三角）。
 - **历史定位**：PTQ 为主流；QAT 成本高用得少；INT3/INT2 仅极限场景。
 
 ## 5.3 KV Cache 的系统级优化（🟢 掌握）
 - 压缩：GQA/MQA/MLA（架构层，见 §2.3）；KV 量化（FP8/INT8）；KV 剪枝（H2O/SnapKV）。
 - 复用：**Prefix Cache**（相同系统提示词/文档前缀只算一次，vLLM/SGLang 标配）。
 - 显存管理：**PagedAttention**（按页分配，仿操作系统虚拟内存，碎片趋零、支持共享前缀）。
 - 卸载：KV 换出到 CPU/统一内存（长上下文性价比方案）。
 
 ## 5.4 推理并行（🟢 掌握；与训练 §4.7 复用概念）
 - **TP**：单卡装不下时按矩阵切（8 卡 70B 常用）；要求卡间高速互联（NVLink）。
 - **PP**：按层切，减少跨卡矩阵通信，但流水线延迟上升。
 - **DP**：多副本各接一批请求 = 吞吐线性扩展（配合调度器）。
 - **EP**：MoE 专家分卡（MoE 推理必备思路）。
 - **并行组合**：TP x DP 是 serving 最常见组合；超大模型（1T 级）才用 TP x PP x EP。
 
 ## 5.5 核心 Serving 技术（🔴 掌握，这是生产核心）
 - **Continuous Batching（连续批处理，2022）**：不再“凑满一批再跑”，而是请求随到随进、token 级动态进出 batch → 吞吐提升数倍。**现代推理引擎的基石**。
 - **PagedAttention（vLLM，2023）**：KV Cache 分页管理，碎片近零、显存利用率大幅提升、支持前缀复用。
 - **Chunked Prefill（分块预填充）**：把长 Prompt 的 prefill 切成小块，与 decode 请求交错执行，**消除“长 prompt 卡住整批”的头部效应**。
 - **Speculative Decoding（投机解码，2022-2023）**：小模型先猜若干 token，大模型一次验证；短序列生成提速 2-3x。变体：Medusa/EAGLE（额外头）、self-speculation。注：对长思考类生成收益有限。
 - **PD 分离 / Disaggregated Serving（2024-2025）**：Prefill 与 Decode 集群分开（Kimi Mooncake 等架构），按需伸缩各自算力；**长上下文/推理模型时代的架构方向**。
 - **LoRA Serving**（Punica/S-LoRA/vLLM 内置）：同一底座注入多个 LoRA，多租户微调服务性价比方案。
 - **其他**：CUDA Graphs（减少 kernel 启动开销）、FlashAttention-3、FP8 kernel、MoE 专家卸载。
 
 ## 5.6 Serving 框架对比（同层比较，选型用）
 
 | 引擎 | 定位 | 优势 | 注意 |
 |---|---|---|---|
 | vLLM | 通用生产首选 | 生态最全、PagedAttention、Prefix Cache、多模态/量化支持广 | 极致硬件效率略逊专用引擎 |
 | SGLang | 高吞吐研究前沿 | RadixAttention 前缀复用极致、结构化输出/路由原生、联合调度 | 上手稍难、生态略窄 |
 | TensorRT-LLM | NVIDIA 极致优化 | 编译级性能、FP8/INT4 支持、工业级 | 绑定 NVIDIA、编译流程重 |
 | llama.cpp | 端侧/CPU/本地 | GGUF、跨平台、单机零依赖 | 生产规模化能力弱 |
 | Ollama | 本地一键体验 | 基于 llama.cpp 的桌面分发 | 不适合生产并发 |
 | TGI（HF） | 老牌生产引擎 | 起步早、文档多 | 性能已被 vLLM 反超 |
 | LMDeploy（InternLM） | 国产高效引擎 | TurboMind 推理快、AWQ 支持好 | 生态绑定 InternLM/Qwen 系 |
 | MLX（Apple） | Apple 芯片 | 统一内存、端侧 Mac 推理 | 仅 Apple 生态 |
 | ONNX Runtime / OpenVINO | CPU/跨平台 | 企业集成、异构（OpenVINO 支持 GPU/NPU/CPU） | 大模型推理非其强项 |
 | MindIE / vLLM-Ascend | 昇腾 NPU | 国产算力唯一主线 | 与 CUDA 生态有差距，需适配 |
 | Ray Serve | 编排层 | 与 Ray 生态/自动扩缩容集成 | 不是推理引擎，是上层 |
 
 > 选型逻辑：NVIDIA 云上大规模 → vLLM 或 TensorRT-LLM；极致吞吐与长前缀 → SGLang；端侧/个人 → llama.cpp/Ollama/MLX；国产 NPU → MindIE/vLLM-Ascend；CPU 企业集成 → OpenVINO。
 
 ## 5.7 部署形态（🟢 了解工程全貌）
 - **谱系**：本地 CLI（Ollama/llama.cpp）→ 单机多卡（vLLM TP）→ 多机 K8s 集群（vLLM+K8s 自动扩缩）→ 云端托管（各家 API）。
 - **上线要素**：API 网关（鉴权/限流/计费）、监控（延迟/QPS/GPU 利用率）、日志与追踪（OpenTelemetry）、灰度与回滚（模型版本）、数据流控。
 - **异构**：CUDA（NVIDIA）、ROCm（AMD）、NPU（昇腾等）——kernel 与引擎支持是选型关键。
 
 ## 5.8 性能指标与压测（🔴 掌握指标口径）
 - **TTFT**（Time To First Token）：首 token 延迟，用户体感“快不快”，长 prompt 由 prefill 决定。
 - **TPOT / ITL**（每 token 时间）：生成速度，约 200ms 是流畅线。
 - **吞吐**：单请求 tokens/s 与整机输出 tokens/s、QPS。
 - **GPU 利用率**：计算/显存/带宽利用，过低说明调度或数据搬运有问题。
 - **成本**：$/1M tokens（输入/输出分开计）；推理成本 = 吞吐优化的结果。
 - **压测方法**：vLLM 自带 bench、OpenAI 兼容端点用 locust/wrk；**永远用混合长度+混合并发压测**，不要单测一个 prompt。

 # 6. 大模型应用开发（概念层）
 
 > 本章先讲“用模型做事”的概念，第 7 章再讲实现这些概念的框架。**概念先于框架，框架只是概念的机械实现。**
 
 ## 6.0 从“调用模型”到“产品化”的能力谱系
 
 ```
 Model API（最基础） → Prompt → 结构化输出 → Tool Calling → RAG → Workflow → Agent → Multi-Agent → 行业产品
    每次升级都在回答一个问题：
    ① 怎么把话说明白（Prompt）
    ② 怎么拿到机器可用的结果（Structured Output）
    ③ 怎么让模型“动手”（Tool Use）
    ④ 怎么让它“知道更多”（RAG）
    ⑤ 怎么把多步任务串起来（Workflow）
    ⑥ 怎么让它自己规划、试错、反思（Agent）
 ```
 
 ## 6.1 Model API（🔴 必须熟练）
 - 形态：OpenAI 的 Chat Completions（旧）→ Responses API（新，统一工具/搜索/文件）；各家兼容 OpenAI 协议；部分提供原生 JSON/工具参数。
 - 核心参数：model、messages/system、temperature、top_p、max_tokens、stop、stream（SSE）、seed。
 - 流式（Streaming）：首 token 延迟体验的关键；SSE 协议要会抓、要会断线重连。
 - 统一抽象：`openai` SDK、`anthropic` SDK、LangChain 的 `chat_models`、Vercel AI SDK（前端友好）。
 - **实践**：用 Python 写一个带流式、工具调用、重试与超时的最小客户端。
 
 ## 6.2 Prompt Engineering（🔴 掌握；从“咒语”到科学）
 - 要素：角色（system）→ 任务 → 输入 → 约束/输出格式 → 示例（few-shot）→ 边界（不知道就承认）。
 - 经典模式：Zero-shot → Few-shot → CoT（逐步推理，2022）→ Self-Consistency（投票）→ ReAct（思考+行动，Agent 的雏形）→ Least-to-most、ToT 等进阶。
 - 与模型能力的交互：**越强的模型越不需要技巧**（2025 年趋势：prompt 在“瘦身”，context/工具在“变胖”）；但 system prompt 的稳定性与安全性仍需工程化。
 - 工程化要点：模板版本管理、评测驱动（同 prompt 不同模型对比）、长度控制、防注入（见 §12）。
 
 ## 6.3 Context Engineering（上下文工程）（🟢 掌握；2025 年关键词）
 - **定义**：不只是“写 prompt”，而是系统设计“喂给模型什么上下文”：检索内容 + 记忆 + 工具结果 + 系统约束 + 压缩。
 - 手段：RAG（外部知识）、Memory（历史）、Truncation/压缩（LLMLingua 类）、路由（要不要带上下文）、多模态上下文。
 - 与 Prompt 的区别：Prompt 是“怎么说”，Context 是“给什么”——后者是 RAG/Agent/Memory 的统一上层概念。
 
 ## 6.4 Structured Output（结构化输出）（🔴 掌握）
 - **为什么**：业务系统要 JSON/表格，不要散文。
 - 方法演进：提示词“请输出 JSON”（不稳定）→ JSON mode（强制合法 JSON，2023）→ **Structured Outputs / JSON Schema 约束解码**（2024，按 Schema 逐 token 约束，100% 合法）→ 工具调用的 `function` 参数复用（各家一致）。
 - 实现原理：constrained decoding（SGLang 的 Structured Outputs、vLLM 的 guided decoding、Outlines 库）——把 Schema 编译成 token 级状态机。
 - **实践**：优先用 Schema 约束，不要正则清洗散文式输出；生产系统从第一天就要让输出可落库。
 
 ## 6.5 Function / Tool Calling（工具调用）（🔴 必须掌握）
 - **是什么**：声明工具（JSON Schema：名称/参数/描述）→ 模型在回复中“请求调用”并给出参数 → 应用执行 → 把结果再喂回模型。2023 年 6 月 OpenAI 上线后成为 Agent 的地基。
 - **并行调用**：一个回复同时请求多个工具；**Agent 效率的关键**。
 - **循环模式**：模型思考 → 调工具 → 看结果 → 再思考……直到完成任务（这就是 Agent Loop，见 §9）。
 - **陷阱**：工具描述要写清楚参数语义；工具结果超长要截断/压缩；工具报错要喂回去让模型自愈。
 
 ## 6.6 RAG（检索增强生成）（🟢 概念先修，体系见 §8）
 - 一句话：先检索外部知识，再带着检索结果生成，解决“知识静态、幻觉、私有知识”三个问题。
 
 ## 6.7 Agent（智能体）（🟢 概念先修，体系见 §9）
 - 一句话：能自主规划、调用工具、记忆、反思并多步执行任务的系统；“Workflow 是确定性的，Agent 是决策性的”。
 
 ## 6.8 Workflow（工作流）（🟢 掌握）
 - 确定性编排：把任务拆成固定步骤（如：意图识别 → 检索 → 生成 → 校验），步骤之间数据管道连接。
 - 与 Agent 的取舍：**能用 Workflow 就用 Workflow**（可预期、可测、便宜）；只有需要“在运行中决定下一步”时才用 Agent。这是 2025 年从“All-in Agent”回调后的共识。
 
 ## 6.9 Multi-Agent（多智能体）（🟢 概念；体系见 §9）
 - 模式：角色分工（研究员/写手/审校）、对话式协作、层级控制（supervisor）；框架：AutoGen/CrewAI/LangGraph 等。
 - 成本警示：多 Agent = 多倍 token 与延迟，**先证明单 Agent 不行再上多 Agent**。
 
 ## 6.10 Memory（记忆）（🟢 掌握分类）
 - 短期：对话上下文（模型窗口，用压缩/摘要控制）。
 - 长期：向量记忆 + 结构化记忆 + 用户画像；存取时机由“Memory Manager”决定；与 RAG 同源（都是“检索-注入”）。
 - 产品价值：个性化、连续性；但受隐私监管约束（GDPR/个保法）。
 
 ## 6.11 Human-in-the-loop（人在回路）（🟢 了解）
 - 高价值场景（医疗/金融/审批）必须在关键节点人工确认；机制：审批节点、人工改写反馈、置信度阈值转人工。
 - 双向价值：机器先做、人审结果 → 同时是数据飞轮的一环。
 
 ## 6.12 应用架构模式总结（🔴 会选型）
 ```
 单次调用（Q&A/翻译）→ Prompt 模板化
 多步固定（客服分流）→ Chain / Workflow
 带知识库（文档问答）→ RAG
 动态决策（复杂任务）→ Agent（ReAct）
 多角色配合（写书/带审校）→ Multi-Agent
 企业级稳定输出 → Workflow + Structured Output + 评测 + HITL
 ```
 > 判断口诀：任务是否可枚举步骤？→ 是 = Workflow；否 = Agent。是否需要最新/私有知识？→ 是 = 加 RAG。输出是否进系统？→ 是 = Structured Output。

 # 7. 大模型应用开发框架（工具层）
 
 ## 7.0 框架为什么出现（先理解问题再理解工具）
 - **痛点一：状态**——LLM 调用要携带上下文状态（对话、流程、工具结果），纯手写容易失控。
 - **痛点二：组装**——模型、检索、工具、记忆、向量库之间需要标准化接口。
 - **痛点三：可观测与评测**——Agent 多步执行，必须能 trace、能回放、能量化。
 - **痛点四：成本与可靠性**——重试、限流、缓存、结构化输出的通用实现。
 - 结论：框架 = 把“LLM 应用工程惯例”沉淀为库/平台。**框架会消亡、概念永存**——学的重点是概念，不是某个库的 API。
 
 ## 7.1 框架分类学（同层比较的前提：先分类型）
 | 类型 | 代表 | 解决什么 |
 |---|---|---|
 | 通用编排 SDK | LangChain / Haystack / Semantic Kernel | 把模型+工具+检索串成链 |
 | Workflow/图引擎 | LangGraph / Temporal 实践 | 有状态、可分支、可恢复的流程 |
 | RAG 框架 | LlamaIndex / Haystack / RAGFlow | 知识库摄取、检索、问答 |
 | Agent 框架 | LangGraph / AutoGen / CrewAI / OpenAI Agents SDK / Google ADK / Pydantic AI | Agent Loop 与多 Agent 协作 |
 | 低代码平台 | Dify / Flowise / Coze / n8n | 非工程师也能搭应用 |
 | Prompt 编程/优化 | DSPy / Outlines | 把 prompt 当程序、可编译可优化 |
 | 协议层 | MCP（工具接入）/ A2A（Agent 间通信）/ ACP | 跨栈互操作标准 |
 | 前端 SDK | Vercel AI SDK / Mastra / LlamaIndex.TS | 浏览器/Node 端开发 |
 
 ## 7.2 LangChain（2022，概念普及者；位置：通用编排 SDK）
 - 历史贡献：第一个把 Chain 概念普及（LLMChain、RetrievalQA），生态最大、模板最多。
 - 问题：抽象多而杂、版本变动剧烈、过度封装——社区戏称“套娃”；性能与调试成本高。
 - 2024-2025 转型：重心转向 LangGraph 与 LangSmith，LangChain 退化为“库集合”。
 - 学习建议：用它入门理解 Chain 概念即可，生产逐步看 LangGraph 或直写。
 
 ## 7.3 LangGraph（2024，LangChain 官方；位置：Workflow/Agent 图引擎）
 - 核心：把应用建模为**有向状态图**（节点=函数，边=条件路由），支持循环、状态持久化（checkpoint）、human-in-the-loop、流式输出。
 - 为什么重要：给“任意复杂的 Agent/Workflow 拓扑”一个可调试的运行时；DAG 满足不了的（循环、恢复）它都能做。
 - 生态：LangSmith（可观测）、LangChain 组件可直接嵌入；LangGraph Platform 托管版（2025）。
 - 学习建议：当前“确定性流程+Agent”最主流的工程底座之一。
 
 ## 7.4 LlamaIndex（2023；位置：RAG/数据框架）
 - 核心：把“任意数据源 → 可查询索引 → 检索 → 生成”标准化：Document/Node/Index/Retriever/QueryEngine/LlamaHub（插件集市）。
 - 优势：文档解析、多种索引（向量/树/关键词/知识图谱）、高级检索（auto-merging、Recursive、Agentic）；对 RAG 的理解深度超过 LangChain。
 - 2025 方向：加入 Agent 层（ReAct Agent、Workflows 引擎）、评测与可观测（RAGAS 集成）。
 - 学习建议：RAG 专项首选；先读它的 Understanding RAG 教程系列。
 
 ## 7.5 Dify / Flowise / Coze / n8n（低代码平台）
 - Dify（国内最流行）：拖拽工作流 + RAG 管线 + Agent 配置 + 发布为 API；企业知识库应用起手最快。
 - Flowise：纯 UI 的 LangChain 风格拖拽；适合原型。
 - Coze（扣子，字节）：国内 C 端/B 端 Agent 平台，插件生态好。
 - n8n：通用自动化平台，LLM 只是其中一个节点，适合企业流程集成。
 - 学习建议：非工程背景或快速交付用 Dify；工程师了解其背后机制（就是 Workflow/Agent 的低代码化）即可。
 
 ## 7.6 Haystack（deepset；位置：生产级 RAG 管线）
 - 特点：类型安全、组件化、可测试性强，企业级文档问答管线（与 Elasticsearch 深度集成）；比 LangChain 收敛、规范。
 - 定位：欧洲/企业 RAG 架构的框架；学习价值在于“严谨的 pipeline 思维”。
 
 ## 7.7 Semantic Kernel（微软；位置：企业 .NET/云 SDK）
 - 特点：与 Azure AI、.NET/C#/Python/Java 深度绑定；把“技能（Skill）+规划器（Planner）”封装；企业级治理与传统开发语言友好。
 - 定位：微软技术栈企业的选择；独立开发者用得少。
 
 ## 7.8 AutoGen / AG2 / Microsoft Agent Framework（多 Agent 对话范式）
 - AutoGen（2023，微软）：多 Agent 对话式协作（group chat），开创“Agent 之间互聊”范式。
 - 分支：AG2（社区维护）；微软 2025 年推出 Microsoft Agent Framework（承接 AutoGen，与 Semantic Kernel 统一）。
 - 适用：研究/原型多 Agent 场景；生产需自己加状态管理。
 
 ## 7.9 CrewAI（2024；位置：角色化多 Agent）
 - 核心：Role/Goal/Backstory 定义 Crew（团队），流程（sequential/hierarchical）；上手极快、demo 效果好。
 - 定位：多 Agent 编排的“低门槛层”，生产深度弱于 LangGraph/自研。
 
 ## 7.10 DSPy（2023 斯坦福；位置：Prompt 编程与优化）
 - 核心：把 LLM 应用写成语义程序（signature → module → optimizer），用编译与自动优化（针对真实指标）替代手写 prompt，并内置 bootstrapping（用示例自动构造 few-shot）。
 - 哲学：把玄学 prompt 变成可评测可优化的对象。
 - 适用：对质量敏感、可自动化评测的任务（分类/抽取/转换）；与 RAG/Agent 结合（DSPy 2.0 支持 ReAct 等）。
 - 学习价值：像“编译器”思路看 LLM 应用的人，必读。
 
 ## 7.11 OpenAI Agents SDK（2025；位置：轻量 Agent 运行时）
 - 核心：Agent（tools+instructions）→ Handoff（Agent 之间转移权）→ Guardrails（输入输出校验）→ Sessions/Tracing；代码量极小、完全可控。
 - 意义：代表“回归轻量、靠原生功能”的趋势——不再追求大而全框架；Swarm（2024 实验）是其前身。
 - 同类：Google ADK（Agent Development Kit，2025）、Pydantic AI（类型安全，Python 生态 2025 爆火）、Mastra（TS）、Vercel AI SDK（前端）。
 - 趋势判断：2025-2026 的框架正在瘦身——厂商各出轻量 SDK，重量框架往平台化（托管编排）走。
 
 ## 7.12 MCP（Model Context Protocol，2024-11 由 Anthropic 提出，2025 成为开放标准）
 - 定位：**不是框架，是协议**——统一“模型/Agent 与外部工具/数据源”的接口（client-server：MCP Host 与 MCP Server）。
 - 为什么是分水岭：此前每个 Agent 框架都要自己接工具 SDK；MCP 后，工具一次实现、处处可用（官方 SDK + 社区服务器指数增长）。
 - 配套：A2A（Google，Agent-to-Agent 通信）、ACP（Zed/Cognition）；2025 年 OpenAI/谷歌宣布支持 MCP。
 - 实践：会写一个 MCP Server（stdio/HTTP+SSE、工具/资源/提示三大原语）是 2026 年应用工程师的标配技能。
 
 ## 7.13 框架继承关系图（重点理解“为什么出现”）
 
 ```
 2022 LangChain（概念普及：Chain）
   ├─ 2023 LlamaIndex（RAG 专精）
   ├─ 2023 AutoGen / CrewAI（多 Agent 范式）
   └─ 2024 LangGraph（状态图，LangChain 正式接班）
          ├─ 2025 LangGraph Platform（托管）
          └─ 影响：所有框架加“图/状态/Agent Loop”
 2023 DSPy（prompt 编程化）→ 2025 与 Agent 结合
 2024 Swarm（实验）→ 2025 OpenAI Agents SDK（轻量）
 2025 MCP（工具协议标准化，成为所有框架的公共底座）
 趋势：框架分层 = 协议层(MCP/A2A) + 轻量SDK(Agents SDK/Pydantic AI) + 图引擎(LangGraph) + 平台(Dify/Coze)
 ```
 
 ## 7.14 怎么选（决策树）
 - 快速做 Demo / 企业知识库 → Dify 或 LlamaIndex 起步。
 - 严谨生产级 RAG → Haystack / LlamaIndex。
 - Agent 或复杂流程 → LangGraph；多 Agent 协作 → CrewAI/AutoGen/Agents SDK(handoff)。
 - 想少依赖框架 → OpenAI Agents SDK / Pydantic AI + 自己写工具协议（套 MCP）。
 - .NET 企业 → Semantic Kernel；前端团队 → Vercel AI SDK。
 - 质量敏感型任务 → DSPy。

 # 8. RAG 技术体系
 
 ## 8.0 为什么需要 RAG（解决三个问题）
 1. **知识静态**：模型训练完知识就冻结，无法覆盖最新/私有内容。
 2. **幻觉**：没有依据时模型会“一本正经胡说”；RAG 把答案锚定到检索证据。
 3. **可溯源**：企业合规要求“答案能引用出处”，RAG 天然带证据。
 - RAG 的本质 = “检索（说前的依据） + 生成（组织语言）”两段式，是信息检索（IR）与 LLM 的结合——**它的根在搜索引擎领域**。
 
 ## 8.1 演进谱系（看懂 RAG 的“升级路线”）
 ```
 Naive RAG（2020-2023）：分块 → 向量检索 → 拼接 → 生成
   → Advanced RAG（2023）：查询改写/重排/混合检索/更好分块/元数据/父子检索
   → Modular RAG（2024）：组件模块化、可任意组合、加评测
   → Agentic RAG（2024-2025）：Agent 自主决定“查不查、查什么、要不要多步查/反思”
   → GraphRAG（2024）：在实体关系图谱上检索，擅长全局性问题
   → Multimodal RAG（2024-2025）：文档里的图、表、版式都参与检索与回答
 ```
 
 ## 8.2 核心流水线（必须默写）
 ```
 【索引端】数据源 → 解析(PDF/HTML/扫描件OCR) → 清洗 → 分块 → 元数据(来源/页码/层级)
           → Embedding → 向量库（+倒排索引）→ 增量更新
 【查询端】问题 → 查询理解/改写 → 检索(向量+BM25 混合) → 重排(Reranker) → 上下文压缩
           → 拼装 Prompt → 生成（带引用）→ 评测/反馈
 ```
 
 ## 8.3 检索技术基础（🔴 掌握）
 - **BM25（词法检索）**：关键词匹配 + TF-IDF 思想，快、可解释，适合专有名词/代码/产品名。
 - **Dense Retrieval（Bi-encoder 向量检索）**：query 与 doc 分别编码成向量算相似度；语义泛化强。基础模型：Sentence-BERT → BGE/GTE/E5 等。
 - **Hybrid（混合检索）**：词法+向量并行检索 → 加权/RRF 融合；**生产标配**。
 - **Late Interaction（ColBERT 类）**：query 与 doc 逐 token 交互打分，精度最高、代价高，多用做 reranker。
 - **Reranker（重排）**：第一轮召回 top100 → 交叉编码器精排取 top5——**RAG 质量提升最划算的一步**。
 - 检索指标：Recall@k、Precision@k、MRR、nDCG、Hit Rate（检索层）；Faithfulness/Relevance（生成层，见 8.13）。
 
 ## 8.4 分块（Chunking）（🟢 掌握选型）
 - 目标：块内语义自包含 + 块间不丢信息；**没有万能 chunk 大小，跟着内容结构走**。
 - 方法：固定长度（最弱）、递归字符（Markdown/标题感知，常用）、结构感知（按章节）、语义切分（embedding 突变检测）、父子块（父块给上下文、子块做检索）。
 - 元数据：来源/标题/页码/章节路径/更新时间——**没有元数据的 RAG 无法给引用**。
 - 趋势：用 LLM/文档理解模型做结构化抽取（把 PDF 变 JSON）优于盲目分块。
 
 ## 8.5 查询侧技术（Query side）（🟢 掌握）
 - **Query Rewrite（改写）**：口语转书面、指代消解、补全文义。
 - **Multi-query / Query Expansion（扩展）**：一个问题拆多个子查询并行；HyDE（用生成的伪答案去检索）是变体。
 - **RAG-Fusion（2023）**：多路检索 → RRF 融合 → 再生成，适合开放式问题。
 - **Multi-hop（多跳检索）**：第一轮结果引出实体再查第二轮（关系推理必用）；Agentic RAG 的雏形。
 - **Step-back / 问题分解**：大问题拆成语义子问题再分别检索。
 
 ## 8.6 生成侧与上下文压缩（🟢 掌握）
 - **Context Compression**：块太多太长时用 LLM/小模型提取与问题相关的句子（LLMLingua 类）→ 降 token 成本与噪声。
 - **Prompt 拼装**：片段按相关性排序、控制总量（如 top5 x 500 token）、标注来源编号 → 强制“只依据证据回答、不知道就说不知道”。
 - **引用**：生成时带段落编号，前端可溯源。
 
 ## 8.7 Embedding 模型与 Reranker 生态（🟢 会选型）
 - 通用：OpenAI text-embedding-3、Cohere embed、BGE（BAAI）、GTE（阿里）、E5（微软）、Jina；中文推荐 BGE/GTE 系。
 - 多模态/多语言：BGE-M3（多语言+多粒度+稀疏）、ColPali（视觉文档检索）、Voyage。
 - Reranker：bge-reranker、Cohere Rerank、Jina Reranker、MonoT5、ColBERT-v2。
 - 选型要点：中文 vs 多语、维度/存储成本、长文本支持；榜单（MTEB）只做参考——**永远在自己数据上评测**。
 
 ## 8.8 向量数据库与检索后端对比（同层比较）
 
 | 系统 | 类型 | 优势 | 适合 |
 |---|---|---|---|
 | FAISS | 库（进程内） | 快、轻、研究友好；HNSW/IVF-PQ 全支持 | 原型/单机 |
 | Milvus | 分布式向量库 | 云原生、大规模、多索引、GPU 支持 | 生产大规模 |
 | Qdrant | 分布式向量库 | 过滤能力强、Rust 性能好、易部署 | 中大规模生产 |
 | Weaviate | 分布式向量库+图 | 混合检索、模块化 | 中规模 |
 | Chroma | 轻量嵌入式 | 零运维、本地优先 | 原型/个人 |
 | pgvector | Postgres 扩展 | 与业务数据同库、事务一致 | 已有 PG 的中小应用 |
 | Elasticsearch / OpenSearch | 全文+向量双引擎 | BM25 极强、运维成熟、企业标配 | 混合检索生产 |
 | Redis Stack | 内存 KV+向量 | 超低延迟、缓存热路径 | 极热查询 |
 | LanceDB / SQLite-VSS | 嵌入式新秀 | 零服务、列式存储 | 本地/边缘 |
 
 > 选型关键：检索要混合（词法+向量+重排）；大规模看 Milvus/Qdrant/ES；和业务同一个数据库看 pgvector；别为了“向量库”而引入重型组件。
 
 ## 8.9 Advanced RAG 模式清单（🟢 掌握 3-5 个）
 - Parent-Child（父子块）、Auto-merging（小块检索+大块喂入）、Hybrid + RRF、Rerank 必配、Metadata 过滤（时间/部门/分类）、增量更新与删除、多租户隔离（tenant_id 过滤）。
 
 ## 8.10 Agentic RAG（🔴 掌握方向；2025 热点）
 - 本质：把“静态管线”变成“Agent 决策”：判断要不要检索 → 选哪个工具（向量库/知识图谱/SQL/网页）→ 多轮检索/追问 → 评估结果够不够 → 不够再查/反思。
 - 典型实现：ReAct 循环 + 检索工具 + 自反思（Self-RAG）；Deep Research 类产品（OpenAI/Gemini）是其产品化。
 - 代表：LlamaIndex Agentic RAG、LangGraph 检索 Agent。
 - 代价：多轮检索 = 更多 token/延迟 → 需要评测“值不值”。
 
 ## 8.11 GraphRAG（🟢 掌握；2024-2025 新热点）
 - **为什么**：向量检索擅长“找相似片段”，不擅长跨全局总结、实体关联推理、多跳问题。
 - **是什么**：用 LLM 抽取文档实体+关系建知识图谱 → 社区划分（Leiden）→ 为社区生成摘要 → 查询时先定位社区再回答。微软 GraphRAG 开源；LightRAG 等轻量替代。
 - **适用**：全局性问题（“这篇文档讲了哪些主题”）、实体关系问答、知识密集低重复语料。
 - **代价**：建图成本高（LLM 抽取贵慢）；中小知识库用不上；常用混合：GraphRAG（大问题）+ 向量 RAG（事实查询）。
 
 ## 8.12 Multimodal RAG（🟢 了解；方向）
 - 问题：PDF 里大量信息在图表，纯文本分块把图丢了。
 - 方案：版面分析（文本块+图片块）→ 图像描述（captioning）或向量化（CLIP/ColPali）→ 混合检索 → VLM 生成。
 - 代表：ColPali、Qwen2.5-VL 文档理解、Unstructured/Docling/MinerU 解析管线。
 - 方向：让 VLM 直接读“整页版面”比切碎更接近人眼；OCR 从“识别”走向“理解”（Document Understanding）。
 
 ## 8.13 RAG 评测（🔴 会跑；RAG 不评测等于没做）
 - 三层指标：检索层（Recall@k、Hit Rate、MRR）；生成层（**Faithfulness 忠实度**、**Answer Relevance**）；系统层（延迟/成本/端到端质量）。
 - 工具：**RAGAS**（最常用）、DeepEval、LangSmith/Langfuse 评测面板、Trulens；评委：规则/LLM-judge/人工抽样。
 - 常见误区：只看“答案对错”不看检索漏洞；评测集用生产真实问题而非论文题目；只看平均分不看长尾类型。
 - **回归机制**：每次换 embedding/rerank/chunk 都跑同一套评测集对比——RAG 是“检索工程”，唯一的刹车就是评测。
 
 ## 8.14 常见失败模式与修复路线（🟢 会排查）
 | 症状 | 根因 | 修复 |
 |---|---|---|
 | 答非所查询不到 | 检索召回差 | hybrid + rerank + 查询改写 |
 | 答案与文档矛盾 | 忠实度差 | 上下文压缩、约束 only-from-evidence、减少噪声块 |
 | 专有名词查不到 | 分词/嵌入对专名不敏感 | 提高 BM25 权重、词典、别名扩展 |
 | 跨章节问题答不全 | chunk 太碎 | 父子块、结构化元数据、multi-hop |
 | 引用来源错误 | 元数据/编号错位 | 引用管线化、Post-hoc 引用校验 |
 | 更新后仍答旧内容 | 索引没增量 | 增量更新+TTL、缓存失效 |
 | 成本暴涨 | 检索+上下文过大 | 压缩、控制块数、缓存、路由 |

 # 9. Agent 技术体系
 
 ## 9.0 Agent 是什么
 - **定义**：能感知环境、基于目标规划、调用工具执行、观察结果并迭代，直到完成任务的系统。
 - 与 Chatbot 的分界：Chatbot 是“一轮对话输出”，Agent 是“多步行动并负责结果”。**Agent = LLM（大脑） + 工具（手脚） + 循环（机制） + 记忆（状态） + 目标（任务）**。
 
 ## 9.1 演进谱系（必须理解路线）
 ```
 Chatbot（单轮问答）
   → Tool Calling（2023：模型能调用函数）
   → Workflow（固定步骤编排）
   → ReAct（2022：思考→行动→观察的循环范式）
   → Agent（2023-2024：自主规划+多工具+记忆+反思）
   → Multi-Agent（多角色协作）
   → Agentic System（2025-2026：Agent + RAG + 人工审批 + 评测 + 治理 = 企业级系统）
 ```
 
 ## 9.2 Agent Loop（Agent 主循环，🔴 必须会画）
 ```
 目标（用户任务）
   → 感知（读取上下文/检索/工具结果）
   → 计划（分解步骤、选择策略）
   → 行动（调用工具：搜索/代码/数据库/网页）
   → 观察（读取结果）
   → 评估（够了吗？出错了吗？）
   └─ 循环 → 直到完成/放弃/转人工
 ```
 - 每个环节的可失败点：计划太抽象、工具用错、观察被噪声淹没、评估放过幻觉。**工程重点 = 给循环加护栏（步骤上限、错误重试、人工确认、评测）**。
 
 ## 9.3 Planning（规划，🟢 掌握）
 - 方式：一次性计划（先列全步骤再执行，适合确定性任务）；逐步计划（ReAct 式边做边想，适合开放任务）；分层计划（任务-子任务树）。
 - 工具：Plan-and-Execute（2023）、LLM Compiler（2024，把计划编译成可执行步骤图）、代码即计划（Coding Agent 的天然形态）。
 - 规划质量评测：PlanBench（2024）。
 
 ## 9.4 行动-推理范式（🔴 掌握经典方法）
 - **ReAct（2022）**：Thought（想）→ Action（做）→ Observation（看）循环，标准 Agent 骨架。
 - **Reflexion（2023）**：执行失败后生成“反思”，写入记忆再试——自我提升的关键机制。
 - **Self-Refine（2023）**：生成→自我批判→修订（不用执行器）。
 - **Tree-of-Thoughts（2023）**：多思路分叉+回溯搜索，探索充分、成本高。
 - **LATS（2023）**：树搜索与反思、价值函数结合。
 - 2025 现实：**推理模型（o1/R1 系）在模型内部就做“思考”，Agent 框架的 Thought 层与模型 thinking 模式融合**；框架手里只剩 行动/观察/反思 与工具编排。
 
 ## 9.5 Memory（记忆，🟢 掌握分层）
 - 工作记忆：对话上下文 + 工具结果 + scratchpad（思考草稿）。
 - 长期记忆：向量记忆（语义检索）、结构化记忆（用户画像/实体）、程序性记忆（历史步骤复盘）。
 - 关键问题：何时写、何时读、何时遗忘（上下文窗口是硬约束）；Memory Bank/记忆管理器是 2025 年 Agent 框架的新基础设施。
 
 ## 9.6 Tool Use 与 MCP（🔴 掌握）
 - 工具是 Agent 的“传感器和执行器”；工具设计（Schema、错误信息、超时）直接决定 Agent 成功率。
 - **MCP** 统一工具接入（见 §7.12）：Agent 框架通过 MCP Client 连接任意 MCP Server。
 - 常见工具：代码执行（沙箱）、搜索/网页抓取、数据库、文件系统、浏览器（Playwright）、办公文档。
 
 ## 9.7 反思与自纠错（🟢 掌握）
 - 验证器模式：自评（模型自己打分）、LLM-judge（另一模型）、规则验证（测试通过、计划满足）、执行器反馈（编译错误、测试失败）。
 - 迭代机制：Reflexion / Self-Refine / 工具错误回喂（把失败原因写回 prompt 再试）。
 - **2025 关键认知**：给 Agent 输出“结果验证”比 100 行 prompt 更有效——**Agent 可靠性来自验证回路，而不是更好的提示词**。
 
 ## 9.8 Multi-Agent（多智能体，🟢 掌握取舍）
 - 为什么：任务天然多角色（写手/审校/执行）、可并行、可分工；代价：token 爆炸、错误传导、协调复杂。
 - 常见拓扑：星型（supervisor 分配）、环型/链式（流水线）、网状（自由对话）、层级（子 Agent 再分）。
 - 实现层：LangGraph（显式图）、AutoGen/AG2（group chat）、CrewAI（角色化）、Agents SDK（handoff）、A2A 协议（跨厂商 Agent 通信，2025）。
 - 决策原则：**先单 Agent，再上多；一个清晰的 loop 胜过三个混乱的 Agent**。
 
 ## 9.9 Computer Use（计算机使用，🟢 了解；2025 关键词）
 - 是什么：Agent 直接操作操作系统 GUI（点击/输入/截图），无需 API。
 - 代表：Anthropic Computer Use（2024-10）、OpenAI Operator（2025-01，云端浏览器）、UI-TARS（字节开源端到端 UI Agent）、OS-Copilot（研究基线）。
 - 技术点：截图→视觉理解→坐标/动作输出→执行；难点在 GUI 像素级理解与误操作控制（安全护栏）。
 - 评测：OSWorld、V* Bench、Mind2Web。
 
 ## 9.10 Browser Agent（浏览器智能体，🟢 了解）
 - 代表：Gemini in Chrome、OpenAI AgentKit/Operator、Anthropic 浏览器工具、开源 browser-use / Skyvern / Playwright MCP。
 - 形态：云端浏览器（Operator 类）、浏览器插件（本地）、协议化（Playwright MCP server 暴露给任何 Agent）。
 - 技术点：DOM 可访问性树比纯视觉更可靠；登录/验证码是工程难点；anti-bot 对抗。
 - 应用：订票、比价、数据分析抓取、Deep Research。
 
 ## 9.11 Coding Agent（编程智能体，🔴 2026 必有实践）
 - 为什么是 Agent 的最佳落地：代码任务是“可验证的”（测试/编译器）→ 自动评测与强化学习燃料都齐了。
 - 代表产品：GitHub Copilot（补全）、Cursor/Windsurf（IDE Agent）、Claude Code（终端 Agent，2025）、OpenAI Codex（CLI）、Devin（云端全栈）、OpenHands（开源）、Aider、SWE-agent（科研基线）。
 - 核心技术：仓库索引（RAG over codebase）、Edit 工具（精确修改文件）、测试执行回路、LSP/编译反馈、并行探索多分支。
 - 评测：SWE-bench Verified（2025 事实标准）、LiveCodeBench、Terminal-Bench、RepoBench。
 - 趋势：**编程是测试 Agent 框架的最好试验田**；先做“能过测试的函数”，再做“能改仓库的 Agent”。
 
 ## 9.12 Agent 评测（🔴 会跑；不评测的 Agent 不可信）
 - 通用：GAIA（真实问题）、AgentBench、τ-bench（工具调用，2024）与 τ²-bench（2025 升级：真实 API+双系统评测）。
 - 环境类：WebArena/VisualWebArena（网页）、OSWorld（桌面）、Mind2Web、Terminal-Bench（终端）。
 - 代码类：SWE-bench（100% 真实 GitHub issue）、RepoBench、LiveCodeBench。
 - 指标：任务成功率、完成时长/步数、token 成本、工具调用正确率、安全事件数、人工通过率。
 - **好的 Agent 评测 = 固定环境 + 可验证的终结条件 + 成本指标**；不要用“看起来像”的 LLM-judge 替代环境真实验证。
 
 ## 9.13 Agent 安全（🔴 必须看过威胁模型；详见 §12）
 - 威胁：Prompt Injection（工具内容注入）、工具滥用（越权）、数据外泄、供应链（恶意 MCP Server）、权限逃逸。
 - 基线护栏：最小权限 + 沙箱执行 + 人工确认高风险动作 + 输入输出内容过滤 + 审计日志 + 可回滚。
 
 ## 9.14 Agent 框架生态与 2026 趋势（🟢 了解方向）
 - 分层：协议（MCP/A2A）→ 运行时（LangGraph/Agents SDK/ADK/Pydantic AI）→ 平台（Dify/Coze/Agent 云）→ 应用（浏览器/电脑/代码）。
 - 趋势：① Agent 系统化（评测+护栏+人工审批进生产）；② 长时任务（后台挂机数小时，需要持久化与恢复）；③ 多模态 Agent（看图、看视频操作）；④ 端侧/专用 Agent；⑤ **模型推理能力与 Agent 融合**（thinking 模式就是 Agent 的第一步思考）。

 # 10. 多模态大模型
 
 ## 10.0 为什么要多模态
 1. **数据即燃料**：文本语料接近见底，图像/视频/音频是下一座矿；多模态数据让模型获得“世界知识”（颜色、空间、实物）。
 2. **任务即接口**：用户输入不只是文字——截图、语音、拍照、视频都是入口；Agent 更要“看懂屏幕”。
 3. **能力互补**：视觉语义（空间、形状）与语言推理互相增强；文档智能、视频理解是明确的商业价值。
 
 ## 10.1 三种融合路线（理解这条演化就理解了整个领域）
 ```
 路线 A｜早期桥接：Flamingo(2022)、BLIP-2(2023)、LLaVA(2023)
    冻结预训练 LLM，接一个“投影器”，LLM 权重不变 → 快、省，但上限受制于桥的质量
 路线 B｜视觉-语言联合指令微调：LLaVA 系列、Qwen-VL、InternVL
    开放全部或部分参数做多模态 SFT/RL → 今天开源主流的做法
 路线 C｜原生多模态（Native/Omnimodal）：GPT-4o、Gemini、Llama4
    从预训练开始就把文本/图像/音频统一建模 → 融合最彻底、成本最高
 ```
 
 ## 10.2 视觉基础组件（🟢 掌握）
 - **ViT（Vision Transformer，2020）**：把图像切成 16x16 patch 线性投影成 token，用 Transformer 处理——视觉版 Transformer；现代 VLM 的视觉编码器基本都是 ViT 变体。
 - **图像编码器**：SigLIP（开源常用）、CLIP ViT、DINOv2（自监督）；编码器输出 patch 特征再进 LLM。
 - **动态分辨率**：Qwen-VL 的关键工程——不同分辨率缩放切块（2x2/3x3 等）送进模型，避免“压小图丢信息”或“放大图失真”。
 - **位置编码**：M-RoPE（Qwen）把 2D 位置与文本位置统一成 3D 坐标（t, h, w），多模态位置感知的关键。
 
 ## 10.3 文本-图像对齐（🟢 掌握）
 - **CLIP（2021）**：对比学习（图文配对互为正样本），学到对齐语义空间；是图像编码器预训练的事实底座，也催生了图文检索。
 - 对齐方式演化：Cross-Attention（Flamingo/BLIP-2 的可训练 Q-Former 提取视觉 token）→ 纯投影器（LLaVA 的线性/MLP 投影，简单有效）→ 全参数混合训练（原生路线）。
 - **多模态对齐训练**：视觉指令微调（LLaVA-Instruct 类数据）→ 多模态 DPO → 多模态 RLVR（R1-V 等 2025 探索）。
 
 ## 10.4 视觉语言模型路线对比（🔴 掌握代表）
 | 模型 | 路线 | 特点 |
 |---|---|---|
 | LLaVA(2023-2024) | 投影器+全参微调 | 开源教育价值最高：数据配方透明、代码清晰 |
 | Qwen-VL(2023-2025) | 大 ViT+M-RoPE+全参 | 动态分辨率、中文强、视频/Agentic（Qwen2.5-VL 可操作 UI）、文档理解强 |
 | InternVL(2024-2025) | 原生多模态 token | 开源榜单常青树、训练细节公开；InternVL3 进入推理 |
 | GPT-4o / GPT-5 | 原生 | 实时语音/视频、Agent 接入（Operator）；闭源 |
 | Gemini 系 | 原生 | 1M+ 长视频上下文、与搜索/YouTube 生态绑定 |
 | Claude 系 | 后接入视觉 | 文档/截图理解一流（用于 Computer Use） |
 | Llama4 | 早期原生 | 多模态 MoE、任意图片尺寸原生支持 |
 | MiniCPM-V / Phi-Vision | 端侧 | 小模型多模态（INT4 可跑手机） |
 
 - 关键点：**今天的开源 VLM = ViT（冻结或微调）+ 投影 + LLM 全参微调/RL**；原生多模态仍是闭源主导，开源 2025 年快速追赶（Llama4/InternVL/Gemma3 方向）。
 
 ## 10.5 视频 + 文本（🟢 了解）
 - 技术点：抽帧（每秒 1-2 帧或按场景）+ 帧间时序编码 + 长视频分段（1M context 后可以“整片塞进去”）。
 - 代表：Qwen2-VL（开源视频理解标杆之一）、Gemini 1.5/2（长视频强）、GPT-4o 实时类。
 - 评测：VideoMME、LongVideoBench、VideoArena。
 
 ## 10.6 音频 + 语音（🟢 了解）
 - 组件：ASR（Whisper 开源霸主）、TTS（CosyVoice/Qwen-TTS）、语音模型（Qwen-Audio、Gemini 原生音频）。
 - 里程碑：GPT-4o 实时语音对话（2024，端到端、情绪/打断），2025 年 Realtime API 成为语音 Agent 的标准接口方向。
 - 语音 Agent：级联（语音转文字→LLM→TTS）仍是生产主力（廉价稳定）；端到端语音用于“真人感”场景。
 
 ## 10.7 OCR 与文档理解（🟢 掌握；商业落地最密集）
 - OCR：PaddleOCR（中文强）、Tesseract、docTR；版面分析模型接管早期 LayoutLM 的位置。
 - 文档理解模型：DocLLM、Nougat（公式）、Qwen2.5-VL / GPT-4o 直接“看图读文档”；**趋势：从 OCR 抽取 → 文档智能（直接理解版式）**。
 - 开源管线：MinerU（PDF→Markdown，2024-2025 爆火）、Docling（IBM）、Unstructured、LlamaParse；这是 RAG 数据侧的“第一公里”。
 
 ## 10.8 Multimodal RAG 与 Multimodal Agent（🟢 了解）
 - 多模态 RAG：见 §8.12；代表检索器 ColPali（2024，直接对页面图像做 late interaction 检索，绕过 OCR）。
 - 多模态 Agent：能看屏幕（Computer Use）、能看实时视频（实时助手）、能操作 UI（Qwen2.5-VL / UI-TARS 路线）；“看懂”是第一步，“动手”是第二步。
 - 评测：OSWorld（桌面）、GUI-Bench、WildVision Arena。
 
 ## 10.9 多模态评测（🟢 会用）
 - 理解类：MMMU（大学多科）、MMBench、MMStar、SEED-Bench。
 - 细粒度：OCRBench、ChartQA（图表）、DocVQA、TextVQA、ScreenSpot；视频：VideoMME。
 - 注意：多模态榜单刷分现象严重；用真实业务数据（合同/表格/截图）评测永远比榜单可信。
 
 ## 10.10 趋势与学习建议
 - 趋势：① 原生多模态成为大厂标配，“LLM+VLM 拼装”退到中小模型；② 多模态推理模型（看图做题，2025 新标杆）；③ 实时多模态（语音+视频）进入 Agent；④ 端侧多模态（手机 NPU）下沉。
 - 学习路径：先看懂 CLIP + ViT + LLaVA 三篇（30 小时投入），再用 Qwen2.5-VL 或 InternVL 跑通“文档理解 + 视觉 RAG + UI Agent”三件套，最后读 Gemini/GPT-4o 报告中的多模态训练细节。

 # 11. 模型评测与可观测性
 
 ## 11.0 评测为什么是“地基工程”
 - 没有评测 = 无法做技术决策（选模型/调 prompt/改 RAG 全靠感觉），也无法防止回归（新版本悄悄变笨）。
 - **评测的三种角色**：选型评测（横向比能力）、开发评测（迭代对比）、上线评测（线上效果与护栏）。
 - **评测分层**：能力层（知识/推理/代码/数学）→ 任务层（你的业务任务）→ 系统层（RAG/Agent 端到端）→ 安全层 → 工程层（延迟/成本）。
 
 ## 11.1 Benchmark 体系（🟢 会用，🔴 会解读）
 - 通用知识：MMLU（历史地位极高，2024 后饱和）、MMLU-Pro、HellaSwag、WinoGrande、ARC-C、BBH。
 - 推理/数学：GSM8K、MATH、AIME（2024 后推理模型主战场）、GPQA（研究生级科学）、Humanity's Last Exam（2025 最难）、BBH。
 - 代码：HumanEval（2021，已饱和）、MBPP、LiveCodeBench（防污染）、SWE-bench（真实仓库任务）。
 - 指令跟随/对话：IFEval、MT-Bench、Arena-Hard、LMArena 人工对战（原 Chatbot Arena）。
 - 长上下文：Needle-in-a-Haystack、RULER、LongBench、LongICLBench、LOFT。
 - 多模态：MMMU、MMBench、OCRBench、ChartQA、VideoMME。
 - 中文：C-Eval、CMMLU、SuperCLUE、AlignBench。
 - **解读基准的常识**：① 看是否可能被污染（LiveCodeBench 这类更新快的更可信）；② 看与你任务的相关性；③ 看方差与抽样子集；④ 榜单刷分是常态，业务自建评测集才是最终裁判。
 
 ## 11.2 LLM-as-a-Judge（🟢 会搭）
 - 原理：让强模型（或专用 judge 模型）给输出打分/比较，取代昂贵人工。
 - 已知问题：自夸偏好、长度偏置（长=好）、位置偏置、格式偏置；缓解：匿名化、打乱顺序、多 judge 投票、评分 rubrics。
 - 变体：成对比较（win-rate）与绝对打分（1-5 分+rubric）；G-Eval、Prometheus、JudgeLM、GPT-4o-mini 类通用 judge。
 - **实践**：judge 也要定期校准（用人工标注子集对齐）——judge 是模型，就会漂移。
 
 ## 11.3 Human Evaluation（🟢 了解）
 - 形态：内部专家标注、众包、盲评、对战（arena）。
 - 价值：不可自动化替代的“真实感受”；成本高、量小、一致性难；用于关键门禁与 judge 校准，而不是日常迭代。
 
 ## 11.4 RAG 评测（🟢 掌握指标；详见 §8.13）
 - RAGAS：Faithfulness（忠实度）、Answer Relevance（相关性）、Context Precision/Recall、Noise Robustness 等。
 - DeepEval 的 RAG 模块、LangSmith 评估器、TruLens。
 
 ## 11.5 Agent 评测（🟢 掌握；详见 §9.12）
 - 环境类 GAIA / WebArena / OSWorld / τ-bench / SWE-bench；指标：成功率、步数、成本、安全性。
 
 ## 11.6 Safety Evaluation 与幻觉（🟢 掌握概念）
 - 幻觉检测：事实核对（检索对照）、NLI 立场判定、采样一致度。
 - 幻觉分类：内在（编造事实）、外在（错误引用）；检测工具：RAGAS Faithfulness、SelfCheckGPT、FactScore。
 - 安全评测：XSTest（拒绝过度）、HarmBench、JailbreakBench、StrongREJECT、WMDP（有害知识）。
 
 ## 11.7 工程指标（🔴 必会；见 §5.8）
 - 质量之外必须同时测：Latency（TTFT/TPOT/端到端）、Throughput、Token Usage（输入/输出/思考 token 分开看）、Cost（$/query；Agent 任务按“每任务成本”）、GPU 利用率、错误率/重试率。
 
 ## 11.8 可观测性工具链（🔴 应用工程师必装）
 - **LangSmith**：LangChain/LangGraph 生态的 trace + 评估工作台（dataset、eval、在线监控）。
 - **Langfuse**：开源可替代，trace/评测/成本面板，与框架无关，国内部署友好，2025 社区热门。
 - **Arize Phoenix**（开源）：OpenInference + OpenTelemetry 标准，LLM 领域专用追踪，本地免费。
 - **OpenTelemetry GenAI 语义约定**：把 LLM 调用标准化为 spans（input/output/token 用量），是自建可观测的底层标准。
 - 其他：W&B（训练 tracking）、MLflow（实验管理）、Helicone（API 成本代理）。
 - **自建最小系统**：日志中间件 → trace（一次请求完整调用链）→ 指标（均值/分位数/告警）→ 评测作业（离线批量）。
 
 ## 11.9 评测工程最佳实践（🔴 总结）
 1. 评测集分层：5-10 个精选用例（每日冒烟）+ 100-500 条业务集（每周回归）+ 大榜单（选型时）。
 2. 固定评测环境：同 prompt 模板、同 temperature（评测用 0）、同 judge 版本。
 3. 每次改动跑同一套回归（调 prompt/换模型/改 RAG 都要）。
 4. 线上遥测回流成评测集（不满意、重试、纠错 → 加进评测集）。
 5. 用“每任务完成指标”而不是“每 token 质量指标”评价产品。

 # 12. 大模型安全
 
 ## 12.0 威胁模型总览（先建立框架）
 ```
 输入侧：Prompt Injection / Jailbreak / 恶意上下文
 模型侧：训练数据投毒 / 后门 / 记忆泄漏 / 幻觉
 系统侧：RAG 投毒 / 工具误用 / Agent 权限逃逸 / 供应链(MCP)
 输出侧：有害内容 / 隐私泄漏 / 代码漏洞建议 / 版权
 治理侧：合规（个保法/EU AI Act）/ 审计 / 红队 / 应急预案
 ```
 
 ## 12.1 Prompt Injection（提示注入，🔴 懂原理会防）
 - 直接注入：对话内容里藏指令（“忽略上面的指令…”）；间接注入：网页/文档/邮件内容注入（RAG 或浏览 Agent 读到时被触发执行）。
 - 为什么难防：模型分不清“数据”和“指令”——transformer 的先天弱点，只能缓解不能根治。
 - 缓解：输入输出分类器（Llama Guard）、分隔与转义、工具结果标注为数据、最小权限、输出侧规则校验、隔离执行。
 
 ## 12.2 Jailbreak（越狱，🟢 了解）
 - 种类：角色扮演、编码混淆、多语言、GCG 自动后缀、DAN 人格分化、many-shot（海量示例稀释防线，2024）。
 - 防御：对齐训练、输入过滤、对抗评测、护栏；没有不破的盾，目标是“攻击成本 > 收益”。
 
 ## 12.3 Data Leakage（数据泄漏，🟢 掌握）
 - 形态：训练数据记忆背诵、RAG 越权（租户隔离失效）、Agent 工具输出敏感数据、日志记录敏感输入。
 - 缓解：脱敏、最小化、租户隔离、输出过滤、日志脱敏、访问审计。
 
 ## 12.4 Hallucination（幻觉，[工程解法]）
 - 层面：知识幻觉（编事实）、逻辑幻觉、引用幻觉。
 - 缓解组合拳：RAG+引用、检索校验、自我一致投票、拒绝机制（不知道就说不知道）、judge 复核、高风险任务人工兜底。
 
 ## 12.5 Tool / Agent Security（🔴 必须设计）
 - 攻击面：工具滥用（删除/转账）、工具输出注入（把指令写进查询结果）、竞态与重放。
 - 基线：最小权限 + 沙箱（gVisor/Firecracker/容器）+ 危险操作二次确认 + 参数白名单 + 全链路审计日志 + 限额 + 回滚。
 
 ## 12.6 RAG 中毒（RAG Poisoning，🟢 了解）
 - 攻击：向知识库注入恶意文档 → 答案被污染或触发恶意指令。
 - 防御：来源治理、可信校验、检索结果风险标注、输入输出过滤、权限隔离、周期审计。
 
 ## 12.7 Model Extraction（模型抽取，🟢 了解）
 - 通过 API 大量查询蒸馏出近似模型；防御：限流、指纹检测、服务条款、输出扰动；2025 年后“蒸馏他人模型”也成为行业常态争论点。
 
 ## 12.8 Privacy 与合规（🟢 掌握）
 - 国内：个保法、数据出境、生成式 AI 服务管理办法、算法备案；海外：GDPR、EU AI Act（2024 生效、分阶段适用）、版权诉讼。
 - 工程动作：脱敏、私有化部署选项、可删除、审计日志、DPIA。
 
 ## 12.9 Content Safety 与 Guardrails（🟢 会部署）
 - 开源：Llama Guard 2/3、Guardrails AI、NeMo Guardrails、ShieldGemma（2025）；商业：OpenAI Moderation、Azure Content Safety。
 - 架构位置：输入护栏 → 模型 → 输出护栏 → 执行护栏；护栏放两端的思路已成共识。
 
 ## 12.10 Red Team（红队，🟢 了解方法论）
 - 流程：定义风险面 → 自动化+人工攻击 → 修复 → 复测；工具：PyRIT（微软）、Garak、HarmBench。
 - 组织：持续红队而非一次性审计；攻击报告驱动“训练数据 + 护栏 + 策略”三层修复。
 - **安全不是“加一个过滤器”，而是把安全当成对齐、评测、工程的常态输入**。

 # 13. 大模型工程化与基础设施
 
 ## 13.0 从“能跑”到“能上线”的差距
 - 本地 Demo（单卡、单请求）→ 生产系统（多租户、SLA、成本、安全、可观测）之间的差距，都是本章内容。
 - 工程化的三条主线：**资源（GPU/NPU 怎么分）、流程（模型怎么发布更新）、观测（线上怎么发现问题）**。
 
 ## 13.1 算力资源：GPU / NPU / 集群（🟢 会算账）
 - 关键参数：显存容量、HBM 带宽、FP16/BF16/FP8 算力（TFLOPS）、卡间互联（NVLink/NVSwitch/InfiniBand/RDMA）。
 - 主流：NVIDIA A100/H100/H200/B200；AMD MI300X（ROCm）；华为昇腾 910B/910C（NPU，Atlas 集群）；国产化路线基本绑定昇腾。
 - 选型账本：训练看算力+集群互联，推理看带宽+显存，微调看显存；单位成本（$/TFLOPS·小时或单卡·小时）比单卡价格更重要。
 - 资源虚拟化：MIG（A100/H100 切片）、MPS、K8s 设备插件+时间切片；GPU 配额与抢占策略。
 
 ## 13.2 分布式训练基础设施（🟢 了解；深度在 §4.7）
 - 通信库：NCCL（GPU 集体通信事实标准）、RCCL（AMD）；传输：NVLink 机内、InfiniBand/RoCE 跨机。
 - 框架：Megatron-LM/Core（3D 并行）、DeepSpeed（ZeRO/offload）、Ray（弹性调度与数据/训练编排）、Slurm（科研集群）、Volcano/Kueue（K8s 算力调度）。
 - 平台形态：裸机脚本（研究）→ 内部训练平台 → 托管服务（Vertex AI/SageMaker/ModelScope Studio 类）。
 
 ## 13.3 推理与服务基础设施（🟢 了解；深度在 §5）
 - 服务形态：vLLM/SGLang 容器 → K8s Deployment + HPA → API 网关（Kong/APISIX/自研）。
 - 关键工程点：多副本负载均衡（无会话粘性）、按 GPU 水位扩缩容、灰度（新模型先 5% 流量）、滚动发布、配额限流（令牌桶）、token 计费。
 - 数据平面：模型缓存、KV 前缀亲和路由（同前缀到同一实例，2025 前沿）、跨 region 容灾。
 
 ## 13.4 Ray（🟢 掌握概念；Agent 时代更重要）
 - 定位：分布式 Python 运行时——统一训练（Ray Train）、推理（Ray Serve）、数据（Ray Data）、调参（Tune）、编排（Workflows）的弹性底座。
 - 为什么重要：Agent 大规模并行（成百上千个任务）、批处理数据、在线-离线混合负载的通用胶水；大厂 Agent 平台底层很多用 Ray。
 
 ## 13.5 MLOps / LLMOps（🟢 掌握职责划分）
 - 传统 MLOps：数据版本（DVC）、实验跟踪（MLflow/W&B）、模型注册（MLflow Registry/HF Hub）、CI/CD（训练流水线、评测门禁、发布）。
 - LLMOps 新增：Prompt/上下文版本管理、评测集管理、LLM 调用可观测（Langfuse/Phoenix）、成本管理（token 计费）、护栏管理、Agent 日志回放。
 - **CI/CD 在 LLM 世界的形态**：数据变更 → 训练/微调 → 评测门禁 → 自动部署 → 灰度 → 线上遥测回流（数据飞轮的工程化）。
 
 ## 13.6 模型注册与版本（🟢 会做）
 - 版本管理：模型权重（safetensors+元数据）+ 配套（tokenizer、chat template、量化产物、评测报告、许可）打包成“模型版本”。
 - 注册中心：Hugging Face Hub（开源）、MLflow Model Registry、各云 Model Registry；内网镜像（代理 HF）是合规常态。
 - 发布策略：蓝绿、金丝雀（5-10%）、A/B（对照评测）、阴影流量（shadow，录流量不返回）。
 
 ## 13.7 可观测性（Monitoring/Logging/Tracing，🔴 工程必备）
 - 指标：延迟分位数（p50/p95/p99）、错误率、QPS、GPU 利用率、token 消耗、成本。
 - 日志：输入输出（脱敏）、模型/版本/温度参数、工具调用记录；日志是评测集与审计的来源。
 - 追踪：一次请求的完整链路（LLM → 检索 → 工具 → 子 Agent），OpenTelemetry GenAI 标准或 Langfuse/Phoenix。
 - 告警：SLO（如 p95 TTFT < 2s）、容量阈值、成本异常、质量漂移（线上 judge 分数下降）。
 
 ## 13.8 API 网关与负载均衡（🟢 掌握模式）
 - 功能：认证鉴权、路由（多模型多版本）、限流配额、重试熔断、计费计量、缓存（prompt 缓存：相同前缀命中走 KV cache）。
 - 常见：Kong/APISIX/Envoy/LiteLLM（统一多厂商 API 代理）；网关是把 LLM 变成内部服务的第一层。
 
 ## 13.9 大模型应用高可用设计（🟢 了解）
 - 灾难：API 厂商故障、GPU 损坏、上下文溢出、成本爆炸。
 - 设计：多供应商回退（OpenAI→自托管）、降级（强模型→轻模型→规则）、限额（单用户 token 上限）、超时与重试退避、缓存。

 # 14. 医疗、金融、代码等垂直领域大模型
 
 ## 14.0 垂直模型 = 通用模型 + 领域资产（数据/知识/流程/合规）
 - 核心公式：**通用基座 → 领域 CPT → 领域 SFT →（领域 RL）→ RAG/Agent 工程 → 合规与评测**。
 - 真正稀缺的：① 领域数据（难点在治理）；② 领域知识库（RAG 语料）；③ 业务流程建模（Agent 工作流）；④ 合规与责任边界。
 
 ## 14.1 通用 → 行业的完整演化链（🔴 会画架构）
 ```
 通用底座（Qwen/Llama/闭源API）
   → 领域语料 CPT（医学教材/财报/代码库/法条）——补知识
   → 领域 SFT（问答对/报告模板/专家改写）——补行为
   → 领域偏好 RL（专家打分/可验证标准）——补偏好
   → RAG（实时知识：指南/台账/私有库）
   → Agent（检索+调用系统+流程编排）
   → 产品化：权限/审计/人审/评测/合规
 ```
 
 ## 14.2 医疗大模型（🟢 了解）
 - 价值点：病历书写、辅助诊断、报告摘要、患者问答、药物查询、质控。
 - 现实红线：**不能替代执业判断**——产品形态几乎都是“辅助+人工确认”；数据：病历脱敏合规、结构化（FHIR）。
 - 代表：Med-PaLM 2/Med-Gemini（Google）、开源医学底座（PMC 系）、国内厂商医疗大模型；评测用 MedQA/MedMCQA+院内真实病历集。
 
 ## 14.3 金融大模型（🟢 了解）
 - 价值点：研报摘要问答、财报结构化、信贷审核辅助、投顾助手、反洗钱、客服。
 - 特点：强时效（实时数据）、强合规（留痕、不得荐股）、数值敏感（不许编数字——RAG+校验+落库）。
 - 代表：BloombergGPT（早期）、FinGPT/Fin-R1 类开源、各家私有金融基座。
 - RAG 关键：公告/财报增量更新快，向量库要“今天的数据问得准”。
 
 ## 14.4 Coding Agent / 代码领域（🔴 值得动手；见 §9.11）
 - 通用模型大多已强于代码；垂直化重点在工具链与系统：仓库索引、CI/测试反馈、IDE/CLI 集成、安全审查。
 - 路线：代码补全 → 代码问答（RAG over repo）→ Agent（改仓库+跑测试）→ 企业 Coding Copilot（权限/策略/合规）。
 
 ## 14.5 法律大模型（🟢 了解）
 - 价值点：法条检索问答、合同审查、法律文书起草、判例分析。
 - 要点：判例/法规更新快、法域差异大、引用必须可溯源；代表：Lexis+AI、ChatLaw 类开源。
 - 与 RAG 的关系：法律是 GraphRAG+向量 RAG+引用校验的典型场景（实体关系密集）。
 
 ## 14.6 企业知识库（🔴 商业落地最高频）
 - 技术栈：文档解析（MinerU/Unstructured）→ RAG（§8）→ 权限模型（文档级 ACL 必须进检索过滤）→ Agent（多步问答/审批）→ 可观测。
 - 高频坑：权限泄漏、多轮追问、表格/图表丢失、更新滞后、引用不可信；**企业知识库成败 80% 在数据和权限，20% 在模型**。
 
 ## 14.7 行业 Agent 的产品形态（🟢 了解）
 - 形态谱系：知识问答（RAG）→ 流程助手（Workflow+HITL）→ 流程代理（Agent 自动化+审批）→ 数字员工（多 Agent+权限治理，2026 概念）。
 - 共性工程：隔离（租户/环境）、审计（每个动作可回溯）、权限（最小化）、评测（领域评测集）、降级（人工兜底）。
 
 ## 14.8 垂直领域的评测与合规（🟢 会用）
 - 领域评测集：通用基准+领域真题+专家盲评+安全用例；评测集本身也是商业资产。
 - 合规动作：数据来源合法、脱敏、模型备案/审计、输出留痕、人审视情况、风险评估（医疗/金融有专门监管要求）。

 # 15. 前沿技术（2024-2026 热区：标注成熟度）
 
 > 读法：每个方向都标注【成熟】【在途】【探索】——区分“该学”与“该看”。前沿变化快，以下以 2025 年中期为基准描述方向，请务必以最新论文/发布为准。
 
 ## 15.1 推理模型与 Test-time Scaling【成熟，必学】
 - 已从“特技”变成“标准能力”：o1/R1 之后主流厂商全部接入 thinking 模式；接口层出现 reasoning_effort/思考预算。
 - 前沿子问题：思考 token 压缩、验证器（Verifier）代替“越磨越长”、推理蒸馏常态化、推理时搜索（并行采样+best-of-n/树搜索）。
 
 ## 15.2 MoE 极致化【成熟】
 - 大模型基本 MoE 化；前沿：更细粒度专家、动态路由（条件计算）、MoE+长上下文、MoE 推理调度（EP 与 offload 取舍）。
 
 ## 15.3 超长上下文【成熟，走向 1M/10M】
 - 1M 已是旗舰标配；10M（Llama 4 宣称）营销与实用并存；前沿：上下文压缩/蒸馏、KV 缓存工程化（量化+offload+PD 分离）、稀疏注意力（NSA 等）生产化。
 
 ## 15.4 Agentic AI【成熟，从 Demo 走向生产】
 - 不再是“能不能跑通”，而是“要不要相信”：评测、护栏、审批、权限治理成为标配；Deep Research 类产品化证明商业价值。
 
 ## 15.5 多模态原生【在途】
 - 统一 token 化（文本/图/音/视频一体建模）成为旗舰方向；开源仍以 VLM 拼装为主；多模态推理（看图做题）是 2025 新增长点。
 
 ## 15.6 World Model（世界模型）【探索】
 - 目标：模型学会“世界如何运转”，用于视频生成、具身智能、决策模拟。代表：Sora（视频）、Genie、视频预测类研究；离商业主流较远，属研究前沿。
 
 ## 15.7 Diffusion Language Model【探索】
 - 想法：把扩散过程用于文本生成（非自回归、可控重写）。代表：Diffusion-LM(2022)、LLaDA(2025 引起关注)。尚不能与自回归全面竞争，但保留了“非自回归生成”的路线。
 
 ## 15.8 State Space Model / Mamba【在途-边缘化边缘】
 - Mamba(2023)/Mamba-2(2024)：线性复杂度序列建模，理论上长上下文更便宜；但纯 SSM 质量始终追不上 Transformer。
 - **趋势是混合**：Jamba(2024)、Falcon-H1(2025)、Zamba、Hymba——注意力和 SSM 按层混合。**纯 Mamba 替代 Transformer 的叙事基本落幕，混合架构在座**。
 
 ## 15.9 Hybrid Architecture（混合架构）【在途】
 - 主流方向：Attention + 线性层（SSM/滑窗/MLA/KV 压缩）混搭；Llama 4 interleaved attention、MLA 本质都是“省 KV 的混合思路”。
 - 趋势判断：2026 年不会出现“取代 Transformer 的新架构”，而是 Transformer 自我改造（稀疏、压缩、混合、分层）。
 
 ## 15.10 Small Language Model / On-device AI【成熟，快速增长】
 - 代表：Phi、SmolLM、Gemma 3n、Qwen3 小尺寸、MiniCPM、Llama 3.2 1B/3B；端侧推理栈：MLX（Apple）、llama.cpp、NPU 集成。
 - 技术点：蒸馏+高质量数据是小模型关键；int4/GGUF 端侧部署；**小模型 = 成本 + 隐私 + 离线场景的答案**。
 
 ## 15.11 AI Agent 全栈【成熟，见 §9】；15.12 Computer Use / Coding Agent【成熟，见 §9.9/§9.11】；15.13 MCP【成熟，见 §7.12】——均不重复展开。
 
 ## 15.14 合成数据与数据飞轮【成熟-核心资产】
 - 合成数据从“补数据”升级为“造能力”（推理数据闭环）；数据飞轮成为大厂壁垒；前沿问题：合成数据毒化检测、质量评估自动化。
 
 ## 15.15 值得跟踪的其他方向（简要）
 - **搜索增强生成**：web 搜索接入模型（2024-2025 各家标配）。
 - **代码执行/沙箱推理**：让模型“跑出来验证”（验证回路）。
 - **端侧 Agent**：手机助理、PC Agent。
 - **模型身份与安全**：水印、来源标注（C2PA）、AI 内容检测。
 - **长时任务与 Agent 云**：在云上长期运行的 Agent。

 ## 17.2 大模型核心原理
 
 ### 17.2.1 Transformer
 - **一句话**：用注意力替代循环的序列模型，现代 LLM 的骨架。
 - **掌握**：🔴深入 ｜ **前置**：17.1 全部 ｜ **论文**：Attention Is All You Need(2017) ｜ **代表模型**：全部 ｜ **框架**：PyTorch/transformers。
 - **衍生**：Attention 全部变体、MoE、KV Cache ｜ **关系**：一切模型的根 ｜ **实践**：从零实现一个 1-2 层 GPT（nanoGPT）。
 
 ### 17.2.2 Self-Attention
 - **一句话**：token 间按相似度加权聚合信息，O(n²) 的序列交互。
 - **掌握**：🔴深入 ｜ **前置**：Transformer ｜ **论文**：Vaswani 2017 ｜ **框架**：PyTorch、FlashAttention。
 - **衍生**：多头、滑窗、稀疏、线性注意力 ｜ **关系**：是 FFN 之外的第二个基本原语 ｜ **实践**：手写 QKV 并对比 FlashAttention 数值。
 
 ### 17.2.3 Cross-Attention
 - **一句话**：Q 来自一方、K/V 来自另一方，是模态/来源间的信息桥梁。
 - **掌握**：🟢掌握 ｜ **前置**：Self-Attention ｜ **论文**：Transformer 原文(Decoder 部分)、Flamingo(2022) ｜ **代表模型**：早期 VLM、T5 ｜ **框架**：transformers。
 - **衍生**：Q-Former、多模态融合 ｜ **关系**：多模态与 encoder-decoder 的核心机制 ｜ **实践**：给 mini-GPT 加一个图像 cross-attention 层。
 
 ### 17.2.4 MHA → MQA → GQA
 - **一句话**：多头注意力的显存-质量折中谱系（GQA 是当前标配）。
 - **掌握**：🔴掌握 ｜ **前置**：Self-Attention ｜ **论文**：MQA(2019)、GQA(Llama2 2023) ｜ **代表模型**：Llama3/Qwen3/Mistral ｜ **框架**：transformers/vLLM。
 - **衍生**：MLA（压缩版）｜ **关系**：直接决定 KV Cache 大小与推理成本 ｜ **实践**：对比同模型 MHA 与 GQA 的显存占用。
 
 ### 17.2.5 MLA（Multi-head Latent Attention）
 - **一句话**：把 KV 压缩到低维潜空间，KV Cache 与训练成本双双大降。
 - **掌握**：🟢掌握 ｜ **前置**：GQA、低秩 ｜ **论文**：DeepSeek-V2(2024) ｜ **代表模型**：DeepSeek-V2/V3、MiniMax-M1 ｜ **框架**：vLLM(支持)/DeepSeek 官方。
 - **衍生**：低秩 KV、量化缓存的结合 ｜ **关系**：GQA 的“更激进版本” ｜ **实践**：读 MLA 章节并复现其显存账。
 
 ### 17.2.6 位置编码（Sinusoidal→RoPE）
 - **一句话**：给序列注入位置信息；RoPE 是当前事实标准。
 - **掌握**：🔴掌握 ｜ **前置**：Attention ｜ **论文**：RoFormer/RoPE(2022)、ALiBi(2022) ｜ **代表模型**：Llama/Qwen/DeepSeek ｜ **框架**：transformers。
 - **衍生**：YaRN、NTK、LongRoPE、M-RoPE ｜ **关系**：长上下文与多模态的共用基石 ｜ **实践**：实现 RoPE 并做 2x 外推实验。
 
 ### 17.2.7 FFN 与 SwiGLU
 - **一句话**：每 token 独立的非线性变换与“知识存储”，占模型 2/3 参数。
 - **掌握**：🟢掌握 ｜ **前置**：Transformer ｜ **论文**：GLU Variants(2020) ｜ **代表模型**：Llama 系 ｜ **框架**：任何模型库均带。
 - **衍生**：MoE（专家=FFN）｜ **关系**：MoE 的物理载体 ｜ **实践**：观察 SwiGLU 与 ReLU 的输出差异。
 
 ### 17.2.8 LayerNorm / RMSNorm
 - **一句话**：稳定深层训练；RMSNorm 去掉均值、省算力更稳。
 - **掌握**：🟢掌握 ｜ **前置**：DL ｜ **论文**：RMSNorm(2021) ｜ **代表模型**：Llama 系 ｜ **框架**：transformers。
 - **衍生**：QK-Norm、DeepNorm ｜ **关系**：FP8 训练稳定的前置条件 ｜ **实践**：在 mini 模型上对比 post/pre-norm 训练曲线。
 
 ### 17.2.9 Tokenizer（BPE/BBPE）
 - **一句话**：文本↔token 的双向映射，决定词表、压缩率与语言适配。
 - **掌握**：🟢掌握 ｜ **前置**：NLP 基础 ｜ **论文**：BPE(2016)、SentencePiece(2018) ｜ **框架**：tokenizers、sentencepiece。
 - **衍生**：词表扩展、字节级 token ｜ **关系**：影响 embedding 大小、成本与训练 ｜ **实践**：统计中英文每句 token 数与压缩比。
 
 ### 17.2.10 Embedding 与词表
 - **一句话**：token→稠密向量的查表层，输出层常共享同一矩阵。
 - **掌握**：🟢掌握 ｜ **前置**：Tokenizer ｜ **论文**：无独立经典（随 Transformer）｜ **框架**：PyTorch nn.Embedding。
 - **衍生**：多模态 patch embedding ｜ **关系**：信息流的入口 ｜ **实践**：查看 128k 词表模型的 embedding 参数占用。
 
 ### 17.2.11 KV Cache
 - **一句话**：缓存历史 K/V 避免重复计算，推理成本与显存的中心变量。
 - **掌握**：🔴掌握 ｜ **前置**：Attention ｜ **论文**：无独立首创（vLLM PagedAttention 2023 是系统化代表作）｜ **框架**：vLLM/transformers。
 - **衍生**：PagedAttention、KV 量化、Prefix Cache、MLA ｜ **关系**：连接模型架构与推理系统 ｜ **实践**：手算一个 7B 模型在 32k 长度下的 KV 显存。
 
 ### 17.2.12 Logits 与采样（Temperature/Top-p 等）
 - **一句话**：把输出分数变成生成文本的决策机制。
 - **掌握**：🟢掌握 ｜ **前置**：概率基础 ｜ **论文**：Top-p(2019)、Min-p(2023) ｜ **框架**：transformers generate()。
 - **衍生**：约束解码、结构化输出 ｜ **关系**：推理质量与多样性的旋钮 ｜ **实践**：对比温度 0 vs 1 的采样效果与困惑度。
 
 ### 17.2.13 预训练（Next Token Prediction）
 - **一句话**：在万亿级语料上自监督学习，目标是预测下一个 token。
 - **掌握**：🟢概念+🔴研究者 ｜ **前置**：Transformer、数据工程 ｜ **论文**：GPT-2(2019)、GPT-3(2020) ｜ **框架**：Megatron/DeepSpeed。
 - **衍生**：CPT、多阶段训练 ｜ **关系**：一切能力的来源，对齐的起点 ｜ **实践**：小语料训练一个 100M 模型并观察 loss 曲线。
 
 ### 17.2.14 SFT
 - **一句话**：用指令-回答对把“续写模型”训练成“助手”。
 - **掌握**：🔴掌握 ｜ **前置**：预训练、LoRA ｜ **论文**：InstructGPT(2022)、Alpaca(2023) ｜ **框架**：LLaMA-Factory/TRL/Unsloth。
 - **衍生**：LoRA、RFT、格式对齐 ｜ **关系**：RLHF 之前的第一个对齐动作 ｜ **实践**：用 1k 条中文指令微调 Qwen 并对比前后。
 
 ### 17.2.15 RLHF / PPO
 - **一句话**：先训奖励模型再用 PPO 优化策略，把“喜欢”变成优化目标。
 - **掌握**：🟢原理+🟢会跑 ｜ **前置**：SFT、RL 基础 ｜ **论文**：InstructGPT(2022)，PPO(2017) ｜ **框架**：TRL。
 - **衍生**：DPO/GRPO 等全家族（都是它的简化）｜ **关系**：对齐主线的“重型武器” ｜ **实践**：TRL 里跑一遍完整 RLHF（需小数据集）。
 
 ### 17.2.16 DPO 家族（DPO/KTO/ORPO/SimPO）
 - **一句话**：用偏好对直接做损失优化，免掉 RM 与在线采样。
 - **掌握**：🔴掌握 DPO ｜ **前置**：偏好数据、Bradley-Terry ｜ **论文**：DPO(2023)、KTO(2024)、ORPO(2024) ｜ **框架**：TRL/LLaMA-Factory。
 - **衍生**：迭代 DPO、RSO ｜ **关系**：RLHF 的低成本替代 ｜ **实践**：构造 500 对偏好数据做 DPO 并评估长度偏置。
 
 ### 17.2.17 GRPO / RLVR
 - **一句话**：组内相对奖励 + 可验证任务，推理模型 RL 的事实标准。
 - **掌握**：🟢原理+🔴研究 ｜ **前置**：RL、PPO ｜ **论文**：DeepSeekMath(2024)、DeepSeek-R1(2025) ｜ **代表模型**：R1/Qwen3-thinking ｜ **框架**：verl/TRL。
 - **衍生**：RLVR、过程奖励、推理蒸馏 ｜ **关系**：推理模型时代的关键训练法 ｜ **实践**：用小模型跑一次 GRPO（数学题）并观察思考长度变化。
 
 ### 17.2.18 长上下文技术
 - **一句话**：让模型读得下长文档，靠训练、位置编码、架构、系统四层协作。
 - **掌握**：🔴掌握路径 ｜ **前置**：RoPE、KV Cache ｜ **论文**：YaRN(2023)、LongRoPE(2024) ｜ **代表模型**：Gemini/Llama4/Qwen ｜ **框架**：vLLM/SGLang。
 - **衍生**：上下文压缩、长上下文评测 ｜ **关系**：RAG 的竞争者与合作者 ｜ **实践**：把自己的论文 PDF 直接塞进 128k 上下文做问答。
 
 ### 17.2.19 MoE
 - **一句话**：FFN 改造成多个稀疏激活的专家，同算力下把参数做大。
 - **掌握**：🔴掌握 ｜ **前置**：FFN、路由 ｜ **论文**：Switch Transformer(2021)、DeepSeek-V3(2024) ｜ **代表模型**：Mixtral/DS-V3/Qwen3-MoE/Llama4 ｜ **框架**：transformers/vLLM。
 - **衍生**：EP、共享专家、细粒度专家 ｜ **关系**：Dense 的成本解耦方案 ｜ **实践**：比较 Mixtral 与同量级 Dense 的激活参数量与显存。
 
 ### 17.2.20 推理模型与 Test-time Scaling
 - **一句话**：用 RL 训出“先思考再回答”，并用推理时算力换质量。
 - **掌握**：🔴掌握 ｜ **前置**：GRPO、CoT ｜ **论文**：o1 报告(2024)、DeepSeek-R1(2025) ｜ **代表模型**：o系列/R1/Qwen3-thinking ｜ **框架**：verl，API reasoning_effort。
 - **衍生**：思考预算、验证器、蒸馏 ｜ **关系**：对齐主线的最新一章、Agent 的大脑升级 ｜ **实践**：同一数学题对比普通与思考模式输出的思考 token 与正确率。
 
 ### 17.2.21 Scaling Law 与数据墙
 - **一句话**：能力随参数/数据/算力幂律增长，但自然数据接近见底。
 - **掌握**：🟢概念 ｜ **前置**：预训练 ｜ **论文**：Kaplan(2020)、Chinchilla(2022) ｜ **框架**：无。
 - **衍生**：合成数据、test-time scaling、蒸馏 ｜ **关系**：决定训练预算与架构选择的“地图” ｜ **实践**：画一条自己小模型的 loss vs 数据量曲线。
 
 ### 17.2.22 蒸馏与 CPT
 - **一句话**：前者迁移大模型能力到小模型，后者用领域数据续训补知识。
 - **掌握**：🟢掌握 ｜ **前置**：预训练、SFT ｜ **论文**：MiniLM(2019)、CPT 综述 ｜ **代表模型**：R1-Distill ｜ **框架**：transformers/LLaMA-Factory。
 - **衍生**：数据蒸馏、流程蒸馏 ｜ **关系**：领域模型与端侧模型的两种主流来源 ｜ **实践**：用 Qwen 蒸馏 500 条数据训练 0.5B 模型并对比。
 ## 17.3 训练体系
 
 ### 17.3.1 预训练数据工程（采集/清洗/去重/配比）
 - **一句话**：决定模型能力上限的“施工队”，质量比数量重要。
 - **掌握**：🟢掌握 ｜ **前置**：无（数据处理）｜ **论文**：RefinedWeb(2023)、FineWeb(2024) ｜ **框架**：datasets、Dolma、Spark。
 - **衍生**：去污染、合成数据 ｜ **关系**：预训练的直接上游 ｜ **实践**：处理 10GB 网页语料做去重与质量过滤。
 
 ### 17.3.2 合成数据（Synthetic Data）
 - **一句话**：用模型或规则造数据，解决“数据墙”并定向造能力。
 - **掌握**：🟢掌握 ｜ **前置**：SFT 数据 ｜ **论文**：Self-Instruct(2022)、WizardLM(2023) ｜ **框架**：LLaMA-Factory 数据工具、distilabel。
 - **衍生**：数据飞轮、拒绝采样 ｜ **关系**：数据墙时代的新原材料 ｜ **实践**：用强模型合成 200 条领域推理题并人工抽检。
 
 ### 17.3.3 SFT 数据 / Preference 数据 / RL 数据
 - **一句话**：三种微调数据分别对应“怎么做”“更喜欢哪个”“对没对”。
 - **掌握**：🟢掌握 ｜ **前置**：SFT/DPO/RLVR ｜ **论文**：Alpaca(2023)、UltraFeedback(2023) ｜ **框架**：datasets。
 - **衍生**：偏好对增强、过程监督数据 ｜ **关系**：对齐三阶段的“弹药” ｜ **实践**：把同一批问答改造成三种数据形态（指令对/偏好对/RL 题）。
 
 ### 17.3.4 LoRA / QLoRA
 - **一句话**：冻结权重只训低秩增量，把微调成本降两三个数量级。
 - **掌握**：🔴掌握 ｜ **前置**：SFT、SVD ｜ **论文**：LoRA(2021)、QLoRA(2023) ｜ **框架**：PEFT、Unsloth、LLaMA-Factory。
 - **衍生**：DoRA、rsLoRA、LoRA 服务化 ｜ **关系**：个人与中小企业微调的事实入口 ｜ **实践**：单卡 4090 用 QLoRA 微调 7B 并对比全参。
 
 ### 17.3.5 Full Fine-tuning / PEFT 全谱
 - **一句话**：全参更新上限最高；PEFT（LoRA/Adapter/Prompt）是参数效率路线。
 - **掌握**：🟢掌握 ｜ **前置**：LoRA ｜ **论文**：Adapter(2019，历史定位)、LoRA ｜ **框架**：transformers/PEFT。
 - **衍生**：多任务 LoRA、LoRA 合并 ｜ **关系**：全参=上限，LoRA=性价比 ｜ **实践**：同数据用全参与 LoRA 各跑一遍对比。
 
 ### 17.3.6 训练并行（DP/FSDP/ZeRO/TP/PP/SP/EP）
 - **一句话**：把模型、梯度、显存、计算拆到多的 GPU 上的六种切法。
 - **掌握**：🔴掌握 ｜ **前置**：显存账本 ｜ **论文**：ZeRO(2020)、Megatron-LM(2019)、DeepSeek EP 实践 ｜ **框架**：DeepSpeed/FSDP/Megatron。
 - **衍生**：3D 并行、offload ｜ **关系**：训练与推理共用的底层并行语言 ｜ **实践**：用 FSDP 把 7B 模型放到两张卡训练。
 
 ### 17.3.7 训练精度（BF16/FP8）
 - **一句话**：混合精度保速度与显存，FP8 是超大模型训练的新常态。
 - **掌握**：🟢掌握 ｜ **前置**：数值表示 ｜ **论文**：FP8-LM(2022)、DeepSeek-V3(2024) ｜ **框架**：PyTorch AMP/TransformerEngine。
 - **衍生**：QK-Norm、loss 缩放 ｜ **关系**：与推理量化同源但要求更高 ｜ **实践**：同一模型对比 FP16/BF16 训练曲线。
 
 ### 17.3.8 训练框架选型（Megatron/DeepSpeed/FSDP/TRL/LLaMA-Factory/verl）
 - **一句话**：从“模型库”到“预训练引擎”再到“RL 引擎”的三类选择。
 - **掌握**：🟢会选会用 ｜ **前置**：全部训练概念 ｜ **论文**：无（工程）｜ **框架**：见 §4.8 表。
 - **衍生**：微调平台、RL 平台 ｜ **关系**：框架封装训练算法 ｜ **实践**：用 LLaMA-Factory 微调、DeepSpeed 理解 ZeRO、verl 看 RL。
 
 ### 17.3.9 训练工程（显存账本/checkpoint/日志）
 - **一句话**：能算显存、会断点续训、看得懂 loss 的训练基本功。
 - **掌握**：🟢掌握 ｜ **前置**：训练并行 ｜ **论文**：无 ｜ **框架**：safetensors/MLflow/W&B。
 - **衍生**：训练平台、故障恢复 ｜ **关系**：任何训练项目的“隐形工作量” ｜ **实践**：给 7B-LoRA 训练写一份显存预算单并实测。
 
 ## 17.4 推理与部署
 
 ### 17.4.1 精度与量化（FP16/BF16/FP8/INT8/INT4）
 - **一句话**：用更低位宽换速度与显存，量化是推理性价比的第一杠杆。
 - **掌握**：🔴掌握 ｜ **前置**：数值基础 ｜ **论文**：GPTQ(2022)、AWQ(2023)、SmoothQuant(2022) ｜ **代表模型**：任何 HF 模型 ｜ **框架**：bitsandbytes/auto-gptq/awq/llama.cpp。
 - **衍生**：W8A8、KV 量化、FP8 推理 ｜ **关系**：量化对象=权重/激活/KV 三种 ｜ **实践**：同一个 7B 模型跑 FP16/INT8/INT4 三种并对比质量与速度。
 
 ### 17.4.2 GGUF 与 llama.cpp 系
 - **一句话**：端侧/本地推理的量化分发格式与引擎。
 - **掌握**：🟢掌握 ｜ **前置**：量化 ｜ **论文**：无（工程）｜ **框架**：llama.cpp/Ollama。
 - **衍生**：Ollama 桌面分发、MLX ｜ **关系**：个人电脑与手机上的大模型 ｜ **实践**：用 Ollama 跑本地模型并做 API 调用。
 
 ### 17.4.3 PagedAttention 与 KV 缓存管理
 - **一句话**：把 KV Cache 按页管理，消除碎片并支持前缀复用。
 - **掌握**：🔴掌握 ｜ **前置**：KV Cache ｜ **论文**：vLLM 论文(2023) ｜ **框架**：vLLM。
 - **衍生**：prefix cache、chunked prefill ｜ **关系**：现代 serving 引擎的显存地基 ｜ **实践**：vLLM 对比开启/关闭 prefix cache 的吞吐。
 
 ### 17.4.4 Continuous Batching
 - **一句话**：请求动态进出 batch，是吞吐翻倍的调度革命。
 - **掌握**：🔴掌握 ｜ **前置**：服务概念 ｜ **论文**：Orca(2022) ｜ **框架**：vLLM/SGLang/TGI。
 - **衍生**：调度策略、抢占 ｜ **关系**：所有并发 serving 的前提 ｜ **实践**：并发压测对比静态与动态 batching。
 
 ### 17.4.5 Speculative Decoding
 - **一句话**：小模型草稿大模型验证，投机式加速解码。
 - **掌握**：🟢掌握 ｜ **前置**：解码 ｜ **论文**：SpecInfer(2023) ｜ **框架**：vLLM/TensorRT-LLM。
 - **衍生**：Medusa、EAGLE、self-speculative ｜ **关系**：短输出场景收益大 ｜ **实践**：vLLM 开启投机解码测加速比。
 
 ### 17.4.6 Disaggregated Serving（PD 分离）
 - **一句话**：Prefill 与 Decode 集群分离，各按负载弹性伸缩。
 - **掌握**：🟢了解 ｜ **前置**：Serving 全貌 ｜ **论文**：Mooncake(2024)、DistServe(2024) ｜ **框架**：vLLM(实验)/自研架构。
 - **衍生**：KV 传输、prefix 亲和路由 ｜ **关系**：长上下文/推理模型的架构答案 ｜ **实践**：阅读 Kimi Mooncake 架构博客画部署图。
 
 ### 17.4.7 Serving 框架选型（vLLM/SGLang/TensorRT-LLM…）
 - **一句话**：把模型变成 API 的引擎，按场景选型。
 - **掌握**：🔴会用 vLLM ｜ **前置**：全部推理概念 ｜ **论文**：vLLM(2023)、SGLang(2024) ｜ **框架**：见 §5.6 表。
 - **衍生**：推理平台、多模型路由 ｜ **关系**：模型与应用之间的“高速公路” ｜ **实践**：vLLM 部署 Qwen，SGLang 部署同一模型，压测对比。
 
 ### 17.4.8 推理性能指标（TTFT/TPOT/吞吐/成本）

 ## 17.6 RAG 专项
 
 ### 17.6.1 Embedding 模型

 ## 18.3 ③ 两者的交叉知识（必须都懂的共同基础）

 ## 18.4 ④ 从初级 → 中级 → 高级 → 专家级的学习路线
 
 ### 算法路线（预训练/对齐/训练优化向）
 | 级别 | 时间(投入) | 里程碑 | 代表项目 |

 ### 共同铁律
 1. **每个阶段都要有一个“跑得通的完整项目”**——只读不做的知识在两个月后归零。
 2. **先项目后论文**：项目倒逼问题，再针对性读论文，效率远高于从头背书。
 3. **保持 2-3 个“活项目”**：一个练手小模型、一个个人知识库、一个 Agent，跟着技术演进持续迭代，这就是长期查漏补缺的载体。
