## 0. 为什么 04-低代码 值得单独讲一课？

07 章的路牌上，00-框架分类学把它分在**账 A 类 5「低代码平台」**，代表四家 Dify / Flowise / Coze / n8n；账 B 的 24 框架矩阵里它是**唯一全员覆盖 4/4 维、还出了一位「主主主主」（Dify）**的类。这两个坐标指向同一个独特之处：**别的框架是把代码世界的惯例打包成库，低代码是把它们打包成「能拖的积木」**——所以你猜得到的任何框架概念（工具调用、知识库、工作流、Agent 配置、重试），它都有个对应的格子等着你拖。

但它也是 07 章最容易被两句口号误解的一类：

- **「低门槛」**——拖一拖就有，那「客服重试」是不是就不用搭了？账 B 会把它打回原形：重试是循环，同一条回路在代码侧和图画布侧都得亲手搭（回边 1/1/2）。
- **「全兜底」**——00-章账 B 里 Dify 四痛点全主，那是不是全能？账 C 会给出精确答案：**『四痛点全主』既是真的（Dify 主业 4/4 单店达成）也有口径**（靠把观测与成本做进平台产品，不是代码侧白给），再给你 5 条逃离清单（递归/评测/深度 RAG/全工程师 什么时候该回车库）。

和 03-章 LlamaIndex 的对照正好互为镜像：LlamaIndex 把 RAG 工序**做成对象**，低代码把应用开发**做成积木**——前者是多一层封装让你少写，后者是换一个入口让非工程师也能拼。**同理，学框架的手搓，是为了看穿积木里封的是什么**（账 A 就是拆封过程：每个积木对着 06-07 章的一个代码原语）。

> **本篇与 00-章 B 账的一致性**：2026-09-22 交付 04-低代码 时，账 C 曾先按"四痛点全主是广告"的口径自打分，随后发现与 00-章账 B 存疑矩阵冲突（n8n 组装/可观测/成本分布全反）——**立即改为 00-章账 B 的 4 行原样搬入**，全篇以此为唯一口径。跨章数据一致是硬纪律。

## 1. 先钉死事实：低代码类贡献了什么（§7.1 / §7.5 / §17.5.10）

三类来源各给一句可复核的定位：

1. **§7.1 分类学盖章（类 5）**：低代码平台 =「**非工程师也能搭应用**」。它不是"更弱的一种代码框架"，而是**换了一个用户侧**：不面向会用 Runable/状态图的工程师，面向"有业务、没工程"的人。
2. **§7.5 逐家定位（四家四张脸）**：原话是 **Dify（国内最流行）：拖拽工作流 + RAG 管线 + Agent 配置 + 发布为 API，企业知识库应用起手最快**；**Flowise：纯 UI 的 LangChain 风格拖拽，适合原型**；**Coze（扣子，字节）：国内 C 端/B 端 Agent 平台，插件生态好**；**n8n：通用自动化平台，LLM 只是其中一个节点，适合企业流程集成**。**学习建议**：非工程背景或快速交付用 Dify；工程师了解其背后机制（就是 Workflow/Agent 的低代码化）即可。
3. **§17.5.10 能力章盖章（Dify / 低代码平台）**：「**平台版 AgentOps · 关系：工程师提效工具 · 实践：用 Dify 搭企业知识库问答并接入渠道**」——把"可观测/评测/运维"（AgentOps）也做进了平台本身，这正是账 C 判断 Dify 能「四痛点全主 4/4」的产品事实依据。

再钉一条反向边界（本文诚实边界也挂在这）：低代码**不解决概念引入**（Prompt/上下文/工具定义，归 06 章）、**不替代深度实现**（GraphRAG/自定义评测/复杂状态机，要逃到 03/11/02 章）。**它给出的是"快速送达 80% 标准需求"的积木，不是"任意需求"的编程环境。**

## 2. 把「积木化」降维成本机测量（探针设计 + 全量实录）

一篇"低代码很好用"的口水文章不稀奇；稀奇的是把**"四家平台到底把应用开发哪些功能做成了积木、画布上的一个任务要用几块、『全兜底』到哪一步、什么时候该逃离"变成可复排的本机实验**。由于平台本体是 SaaS/自托管 Web 应用，本机无法嵌入运行（与 00-章同一诚实口径），探针改用**纯 stdlib 确定性测量产品结构**，量 4 本可复排的账：

- **A 积木库账**：把四家公开的节点积木清单（Dify 13 / Flowise 9 / Coze 14 / n8n 18）编码进程序，按六族（触发/模型/工具/逻辑/数据/观测）做分类分布 + 跨平台覆盖指纹 + 主投族；
- **B 编排颗粒账**：把 02-章里程碑 012 的「客服问答+重试」在各平台画布做**等价移植编码**（作者按平台公开节点能力换算），从编码 DAG 本机算出节点/边/条件边/回边，对照 02-章真实引擎 7 节点 1 自环与 03-章 6 行真码；
- **C 能力-边界账**：把 00-章账 B 的低代码 4 行矩阵（Dify 主主主主 · Flowise 主主次次 · Coze 主主主次 · n8n 主次次主）**原样搬入**，量化『全主』判定、主投家数，并给 5 条逃离清单；
- **D 选择树账**：8 场景决策断言 8/8（该在哪儿用 §7.14）。

确定性纪律：`warnings.filterwarnings("ignore")` 最先执行（stderr 纯净，不污染 md5）；全程序不引入网络、不引入 RNG、不打印随机对象 ID；所有统计对编码后的清单/矩阵做确定性计算。**stdout md5 `698dd7f1…` 三个独立进程逐字节恒一**，墙钟 ≈0.001 s 仅进 stderr。

## 3. 实验 A · 积木库账（四家积木清单 → 六族分类分布 + 跨平台覆盖指纹）

**目标**：把"低代码=把应用开发做成积木"降成可复排的清单统计——四家平台各有多少公开积木、分布在六族（触发/模型/工具/逻辑/数据/观测）各几只、哪几家覆盖同一族、每家最密的是哪族。

**过程**：把 Dify 13 / Flowise 9 / Coze 14 / n8n 18 个公开节点积木（按 §7.5 定位与公开产品文档整理）编码进探针，逐块归类到六族，程序对编码做确定性统计。

**实测**：

```
  Dify     13 块 · TRIG 1 · LLM 1 · TOOL 4 · LOGIC 4 · DATA 2 · OPS 1 · 覆盖 6/6 族
  Flowise   9 块 · TRIG 1 · LLM 1 · TOOL 2 · LOGIC 3 · DATA 2 · 覆盖 5/6 族
  Coze     14 块 · TRIG 2 · LLM 1 · TOOL 3 · LOGIC 4 · DATA 3 · OPS 1 · 覆盖 6/6 族
  n8n      18 块 · TRIG 3 · TOOL 2 · LOGIC 6 · DATA 4 · OPS 3 · 覆盖 5/6 族
  → 全 4 家齐备的族=4/6（TRIG/TOOL/LOGIC/DATA）· Dify/Coze 6/6 · n8n 5/6（无 LLM 族）
  · Flowise 5/6（无观测族）· 主投族普遍=LOGIC
```

**结论**：

1. **积木 = 06-07 章代码原语的一一曝光**：参数提取器/工具/HTTP 请求/知识库检索（TOOL）对着 06-04 结构化输出+06-05 工具调用+08-RAG 检索；条件分支/代码执行/迭代/循环（LOGIC）对着 02-章图引擎的边与自环；数据库/变量（DATA）对着 06-06 记忆系统。**拖一个积木 = 召唤一个你已经在代码侧学过的原语**——这就是"学 06-07 的代码，是为了看穿积木"。
2. **全齐族 4/6（TRIG/TOOL/LOGIC/DATA）= 低代码共性骨架**：四个平台都有的恰恰是"触发、组装、逻辑、数据"——**这是"应用"的最小四件套**；而「模型」（LLM）与「观测」（OPS）并不是每家都当积木卖。
3. **例外指纹三家各说一种战略**（这正好把 §7.5 的定位量化了）：**n8n 是唯一没有 LLM 族积木的**——它卖的是"通用自动化 + LLM 只是其中一个节点"（§7.5 原话）；**Flowise 是唯一没有观测族积木的**——它卖"纯编排画布"，观测回 01-章代码侧兜；**Dify/Coze 六族最全（6/6）**——它们卖"LLM 应用侧全兜底"，于是最贴近新闻里的"低代码大模型平台"。
4. **主投族普遍 = LOGIC（逻辑/控制族是每家的积木重心）**：Dify=LOGIC+TOOL(4)、Coze=LOGIC(4)、n8n=LOGIC(6)、Flowise=LOGIC(3)——**"低代码"里长得最密的是控制流积木**，说明即便在拖拽世界，"怎么连、怎么分流、怎么循环"依然是应用的中枢，和 02-章"边=判定函数才是图引擎的灵魂"同一回事。

## 4. 实验 B · 编排颗粒账（同一客服重试：代码侧两基准 vs 三画布换算）

**目标**：把"拖拽即出"打回原形——同一个「客服问答+重试」任务（02-章里程碑 012），在代码侧和三家画布侧各要"几块结构"。代码臂=02/03 章真实引擎实测（挂靠不重测），画布臂=等价移植编码（作者按各平台公开节点能力换算），从编码 DAG 本机算出节点/边/条件边/回边。

**过程**：把里程碑 012 的图语义（问答→条件→重试）按各家积木能力等价移植：Dify 用 参数提取器+问题分类器+知识库检索+迭代（7 块）；Coze 用 知识库-插件+循环（6 块）；n8n 用 HTTP+IF+**ErrorWorkflow 作错误域重试**（6 块，双回边）。节点/边/条件/回边从编码本机算。

**实测**：

```
    代码-LangGraph（02 章） : 7 节点 · 6 条件支 · 自环 1（recursion_limit 兜底）——本机真实引擎实测，不重测
    代码-LlamaIndex（03 章）: 最小闭环 6 行真码（Settings 注入 2+四方法 4）——本机真实引擎实测，不重测
    Dify 画布        节点 7 · 边 7 · 条件边 3 · 回边 1（重试）
    Coze 画布        节点 6 · 边 7 · 条件边 4 · 回边 1（重试）
    n8n 画布         节点 6 · 边 7 · 条件边 4 · 回边 2（重试）
```

**结论**：

1. **等量结构，不是零结构**：同一个任务，代码侧 7 节点（02）/ 6 行（03），画布侧 5-7 块——**"低代码不减少你要搭的结构，只换你搭的方式"**：肉眼连线 vs 手写节点编排。全景上没省，局部上（不用写 `|` 链、不用 import）确实省。
2. **重试 = 循环，两个世界都得亲手搭**：三块画布**全部**有回边（1/1/2）——Dify 的迭代积木、Coze 的循环积木是"正常域回边"；n8n 甚至要 **IF 重试 + ErrorWorkflow 双份（错误域也回边）**。这和 02-章真实测到的"客服重试要 1 个自环、还配 recursion_limit 兜底"是同一个结论：**"自动化重试"这件事，从不会因为你换了个拖拽界面就免费。**
3. **口径诚实交付**：代码臂是 02/03 章**真实引擎实测**（挂靠，不重测）；画布臂是**规整的工作流规格编码 + 本机确定性计算**——不是四家平台本体的实际运行（本文诚实边界 AAA，见第 9 节）。

## 8. 常见坑（5 个）

1. **把"低代码"当成一个平台**（本课第一个坑）：四家四套骨架、主投族全是 LOGIC 但形状不同（账 A：n8n 无 LLM 族=通用自动化、Flowise 无观测族=纯画布、Dify/Coze 6/6=应用侧全兜底；账 C：n8n=状态+成本、Coze=3 主、Flowise=2 主）——选型先按 §7.5 对家，再在类内比较，别问"低代码哪个好"。
2. **以为拖拽免了"重试/循环"**：账 B 实测三块画布客服重试全部有回边（1/1/2，n8n 甚至错误域双回边）——『重试是循环』两个世界都得亲手搭，和 02 章 1 个自环 + recursion_limit 是同一门课。
3. **把"四痛点全主"当免费午餐**：Dify 主业 4/4 达成靠的是把可观测（应用内日志/标注）和成本（托管计费/自托管/发布 API）**做成平台功能**（账 C）——这是产品设计取舍，不是"拖一拖就白拿四维能力"；自托管你还得自己运维引擎。
4. **把"知识库问答"也交给低代码深度调优**：Dify 的知识库检索积木是封装好的黑盒（账 A TOOL 族一格），要 GraphRAG/压缩/自定义检索/Agentic 就逃到 03-章/08-RAG 12 篇（账 C 清单③）——平台积木擅长"标准 RAG 温启动"，不擅长"自定义检索策略"，这是两件事。
5. **全工程师团队也上低代码**：团队本就会写代码时，低代码=重复基建+黑盒运维边界（账 C 清单⑤）——直写 06-章原语或 01-章轻量运行时，把可复现、可 diff、可测试留在代码世界。
