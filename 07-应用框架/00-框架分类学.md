## 0. 为什么 07 章第一课是框架分类学？

06 章走完了应用开发的概念主线：API 与流式、Prompt、上下文、结构化输出、工具调用、记忆。**但这些全是你自己写的代码**——一次 `requests`、一个 `json.loads`、一张自己维护的记忆表。到了 07 章，读者会被无数框架砸到脸上：LangChain、LangGraph、LlamaIndex、Haystack、Dify、DSPy、CrewAI、OpenAI Agents SDK、MCP、Vercel AI SDK……

多数教程的写法是把这些框架**排成一条榜单**“LangChain vs LangGraph vs LlamaIndex 谁更强”——这是最典型的选型错误。原因在 §7.1 的标题里说得最清楚：**“同层比较的前提：先分类型。”** 一个 Agent 图引擎（LangGraph）和一个低代码平台（Dify）从来不构成竞争关系，就像“框架”和“协议”（MCP）根本不是同一层东西。跨类比高低，结论必然是一句正确的废话（“都挺好”或“都不完善”）。

所以 07 章第一课不急着跑任何框架的代码，而是**先把「框架为什么出现」和「框架分几类」钉死**。这篇文章+探针做四件事：

| 账 | 回答什么 | 关键产出 |
|---|---|---|
| A 分类学账 | 8 类 × 24 框架怎么切 | 类代表数、跨类双栖、类间 Jaccard 重叠 |
| B 痛点覆盖账 | §7.0 四痛点谁在当“主业” | 主业家数矩阵、覆盖维度分布、协议层特判 |
| C 继承影响账 | §7.13 谱系图长什么样 | 最长承袭链、hub、递归影响面、MCP 底座 |
| D 选型决策树 | “该在哪用”怎么回答 | 10 场景决策 + 2026 四层收敛断言 |

一句话收束（§7.0）：**框架会消亡、概念永存。** 学框架的 API 会被下一次迭代淘汰；学“四痛点谁在解决、怎么被解决（状态机/接口/追踪/退避）”不会过期。本课的量程就是把这句口号变成一张可计算的表。

## 1. 先把问题拆开：框架在解决哪四个痛点（§7.0）

§7.0 给了框架出现的四个理由——**框架 = 把「LLM 应用工程惯例」沉淀为库/平台**。这四个惯例就是四类“每次都要重写一遍”的活：

| # | 痛点 | 没有框架时的样子 | 框架里对应的那层 |
|---|---|---|---|
| 1 | **状态** | 对话流/流程走到哪一步、工具结果存哪，全在自己进程里东拼西凑，一崩就没 | checkpoint / session / context channel |
| 2 | **组装** | 模型、检索、工具、记忆各自一套接口，接线全手写 | Retriever / Tool / Loader / ChatModel 统一抽象 |
| 3 | **可观测与评测** | Agent 多步执行，出错了不知道它走到哪、为什么这么走 | trace / 重放 / eval 工作台（LangSmith 等） |
| 4 | **成本与可靠性** | 重试、限流、缓存、结构化输出、轮次上限，每个项目重写一遍 | retry / cache / guardrail / recursion_limit |

第 1 节的分量在于：**这四类痛点不随框架迭代而消失**——2022 年 LangChain 用“链”解决组装，2024 年 LangGraph 用“图”解决状态与恢复，2025 年 MCP 用“协议”重新定义工具的组装接口。痛点没变，方案在换。这就是本课 B 账要量出来的那张表：**当下每个痛点谁在当“主业”。**

第 2 节的分量在于：**协议层不是框架的一种，是另一层东西。** MCP/A2A/ACP 不承诺状态、不承诺观测、不承诺成本控制——它们只统一“组装”里最痛、最该先定死的一小块（工具接口 / Agent 间通信）。把协议当框架比，或者把框架当协议比，都是维数错误。B 账会用“覆盖维度=1”这个数字把这点钉死。

## 2. 分类学：8 类先分类型再比优劣（§7.1）

§7.1 的八类（含代表框架与“解决什么”），这就是本课 A 账的数据底座：

| # | 类型 | 代表框架 | 解决什么（§7.1 原文口径） |
|---|---|---|---|
| 1 | 通用编排 SDK | LangChain / Haystack / Semantic Kernel | 把模型+工具+检索串成链 |
| 2 | Workflow/图引擎 | LangGraph / Temporal | 有状态、可分支、可恢复的流程 |
| 3 | RAG 框架 | LlamaIndex / Haystack / RAGFlow | 知识库摄取、检索、问答 |
| 4 | Agent 框架 | LangGraph / AutoGen / CrewAI / OpenAI Agents SDK / Google ADK / Pydantic AI | Agent Loop 与多 Agent 协作 |
| 5 | 低代码平台 | Dify / Flowise / Coze / n8n | 非工程师也能搭应用 |
| 6 | Prompt 编程/优化 | DSPy / Outlines | 把 prompt 当程序、可编译可优化 |
| 7 | 协议层 | MCP / A2A / ACP | 跨栈互操作标准 |
| 8 | 前端 SDK | Vercel AI SDK / Mastra / LlamaIndex.TS | 浏览器/Node 端开发 |

读这张表的三条纪律（贯穿全章）：

1. **先问“这需求属于哪一类”**——要状态机/恢复 → 图引擎；要知识库检索 → RAG 框架；要非工程师可搭 → 低代码；要跨栈工具 → 协议层。需求定类，类里再挑代表。
2. **跨类不比较**——`LangGraph（图引擎）vs Dify（低代码）` 没有意义；`LangGraph vs LangGraph Platform（图引擎类内）` 才有意义。
3. **一个框架可以双栖**——下一节 A 账会量出 Haystack（通用编排 × RAG）和 LangGraph（图引擎 × Agent）这两个双栖点：**分类 = 主次，不是互斥标签。**

## 3. 把「分类学」降维成本机测量（探针设计）

一张 8 类 × 24 框架的静态表不稀奇；稀奇的是把**表的“结构”量出来**。探针做了 4 件本机可复现的确定性计算（纯 stdlib）：

- **A 分类学账**：24 框架的类别归属矩阵 → 统计**跨类双栖**数、**类代表数**、**类间 Jaccard 重叠**；判断“先分类型”这一步到底把矩阵切稀疏了没有。
- **B 痛点覆盖账**：24 框架 × 四痛点，每格标“主业/顺带/不碰”（作者按地图定性）→ 统计**每痛点主业家数**与**每框架覆盖维度分布**；用“覆盖=1 维”单拎出协议层。
- **C 继承影响账**：§7.13 谱系编码成 10 节点 DAG（承袭边 6 + MCP 底座边 9）→ 算**最长承袭链**、**直接后代 hub**、**递归影响面**；把“LangChain 是概念普及者、MCP 是 2025 公共底座”变成图算法输出。
- **D 选型决策树**：10 个“该在哪用”场景 → (类别, 代表框架, 理由)；断言决策确定性 + 类别归属 + 层划分互斥。

确定性纪律：全 stdlib、零随机；图算法全部用排序保证平票唯一（**rope 教训：set() 迭代序跨进程不稳定**，见 02-20）；stdout md5 `9df64ce4…` 三个独立进程逐字节恒一，墙钟仅进 stderr（≈0.001 s）。

## 4. 实验 A · 分类学账（8 类 × 24 框架 · 双栖 · Jaccard 重叠）

**目标**：把“先分类型”这一步变成可测量的结构——跨类双栖有几个、哪类最挤、类与类重叠多深，从而判断“切类”是不是真的把矩阵切稀疏了。

**过程**：24 框架按 §7.1 表编码归属矩阵（可多属）；统计：① 跨类双栖数；② 每类代表数；③ 任意两类代表集合的 Jaccard 系数 `|A∩B| / |A∪B|`。

**实测**（stdout 关键行）：

```
  → 跨类双栖 2：Haystack · LangGraph ——「分类=主次不是互斥标签」
  → 类代表数（降序）：Agent 框架 6 > 低代码平台 4 > ... > Workflow/图引擎 2
  → 类间重叠 Jaccard（仅非零 2 对）：
       [通用编排 SDK × RAG 框架] = 0.200（共享 Haystack）
       [Workflow/图引擎 × Agent 框架] = 0.143（共享 LangGraph）
      其余 26 对 = 0
```

**结论**：

1. **分类确实把矩阵切成稀疏的了**：8 类两两之间 28 对 Jaccard 只有 2 对比零——其余 26 对完全不相交。这意味着“这需求属于哪类”是一个**有效筛子**：先定类，候选集从 24 降到 2-6 个，比“24 家拉通比拼”少一个数量级。
2. **双栖点 = 设计意图的边疆，也是后续各章的看板位**：Haystack 双栖在“通用编排 × RAG”，LangGraph 双栖在“图引擎 × Agent”。这两处恰恰是后文 `03-LlamaIndex/Haystack`（RAG 专项，接 08-RAG 的 12 篇实测）与 `02-LangGraph`（已交付：里程碑 012 真实引擎实测）的坐标——**双栖框架是哪两类的公共交集，你就知道该去哪篇读它**。
3. **A 账最大的实际用途是“不比较”**：看到这 28 对 → 0，就明白为什么“LangChain vs LangGraph vs LlamaIndex 谁最强”是伪问题——前两个是「通用编排 vs 图引擎」，后两个更连类都不同。§7.1 的“同层比较的前提 = 先分类型”不是教学口号，是这张稀疏矩阵的事实结论。

## 5. 实验 B · 痛点覆盖账（四痛点的“主业”分布 · 协议层特判）

**目标**：把 §7.0 的“框架为什么出现”量开——四痛点（状态/组装/可观测·评测/成本·可靠）当下各被几家当“主业”，谁覆盖几个维度，从而回答“框架到底在兜什么底”。

**过程**：24 框架 × 四痛点，每格按地图 §7.2–7.12 定性标“主业=2/顺带=1/不碰=0”（作者整理=要素事实）；统计每痛点的**主业家数**、每框架的**覆盖维度数**（>0 的个数）。

**实测**：

```
  主业家数 · 状态 = 9：AutoGen Coze Dify Flowise Google ADK LangGraph OpenAI Agents SDK Temporal n8n
  主业家数 · 组装 = 11：Coze Dify Flowise Haystack LangChain LlamaIndex LlamaIndex.TS Mastra RAGFlow Semantic Kernel Vercel AI SDK
  主业家数 · 可观测·评测 = 3：Coze DSPy Dify
  主业家数 · 成本·可靠 = 2：Dify n8n
  覆盖维度数分布：4 维 10 家 · 3 维 8 家 · 2 维 3 家 · 1 维 3 家
        1 维：MCP A2A ACP
```

**结论**：

1. **组装与状态是框架的“共同主业”**（11/9 家）：接口组装几乎人人做（这是“框架”的定义性功能），状态跟着 Agent/图/低代码走。**框架 = 把“状态执行 + 接口组装”两类惯例打包**——这句不是口号，是统计结论。
2. **可观测·评测与成本·可靠是冷板凳**（3/2 家）：只有 DSPy/Dify/Coze 把评测当主业、只有 Dify/n8n 把成本可靠当主业。这恰好解释了两件事——① 为什么 11-评测与可观测是全仓库的横切章（框架们普遍不兜，你得自己接 Langfuse/Phoenix）；② 为什么“重试/限流/缓存”在 §7.0 被单列为痛点（多数框架是“顺带”实现，不是“主业”）。
3. **覆盖 = 1 维的恰好是协议层 3 家（MCP/A2A/ACP）**——它们只碰“组装·工具接口”这一格。这就是“协议不是框架”的量化证据：**框架承诺状态/观测/成本的多维兜底，协议只承诺“接口怎么统一”**。所以选型第一刀是“要协议还是框架”——协议 bundle 最小、耦合最松、最该先固定（这也是里程碑 `013`（手写 MCP Server）成了 2026 标配的原因）。
4. **B 账与后文的呼应**：DSPy 的标格（评测主业、状态不碰）让它在本目录 09-DSPy 的专题顺理成章；Dify/Coze（四痛点全主）让 04-低代码 章的第一句话就是“平台 = 低门槛 + 全兜底”。

## 6. 实验 C · 继承影响账（§7.13 谱系 DAG · “框架会消亡、概念永存”的可计算版本）

**目标**：§7.13 的继承关系图从“一张 ASCII 图”升级成可计算的 DAG——最长承袭链、hub、递归影响面，把“LangChain 是概念普及者 / MCP 是 2025 公共底座”量化出来。

**过程**：10 节点（带年份）编码谱系：承袭边 6 条（`LangChain→LlamaIndex/AutoGen/CrewAI/LangGraph`、`LangGraph→LangGraph Platform`、`Swarm→OpenAI Agents SDK`）+ MCP 底座边 9 条（MCP → 其余全部节点，2025 公共底座=要素事实）。做三件图算法：最长有向路径（DP 记忆化）、直接后代最多的 hub、显式栈 DFS 的递归影响面（排序保证确定性）。

**实测**：

```
  → 最长承袭链 3 节点：LangChain(2022)→LangGraph(2024)→LangGraph Platform(2025)
  → 概念普及者 = LangChain：直接后代 4(hub 第一) · 递归影响面 5（AutoGen, CrewAI, LangGraph, LangGraph Platform, LlamaIndex）
  → MCP 底座影响面 9：2025 的 hub 从『框架』换成『协议』
  → DSPy 无承袭边 = Prompt 编程范式走 LangChain 之外的独立路径
```

**结论**：

1. **“框架会消亡、概念永存”有了可计算版本**：一个 2022 年的“Chain”概念，直接长出 4 个后代（LlamaIndex/AutoGen/CrewAI/LangGraph），递归影响 5 个节点——**概念（状态执行、接口组装）沿继承边传播，框架（LangChain 本体）被 2025 的 LangGraph/MCP 取代。** 学概念、别背 API，这句话在 6 条承袭边上得到了图论表达。
2. **2025 的 hub 从“框架”换成“协议”**：MCP 底座影响面 = 9——工具接口不再每家自己接（SDK+社区服务器指数增长=要素事实）。这是 2025-2026 最大的结构变化，也是 12-收束章“该不该引入框架”判断的首条判据：**引入协议（接口统一）的收益 < 自己维护接口债的代价时，先上协议。**
3. **DSPy 无承袭边**：Prompt 编程范式走的是 LangChain 之外的独立路径（斯坦福、可评测/编译视角）。它的“独立”既是卖点（不欠链式包袱）也是风险（生态绑定浅）——09-DSPy 章会展开，这里只给出拓扑事实。

## 7. 实验 D · 选型决策树（“该在哪用” 10 场景 + 2026 四层收敛断言）

**目标**：把 §7.14 的“怎么选”做成可执行的决策表——每个需求场景先定“类”再点“代表框架”，并断言决策的确定性（同一输入永远同一结论）。

**过程**：10 场景编码成 `(场景 → 类别, 代表框架, 理由)`；断言 ① 决策稳定（同样输入同结论）、② 代表框架确实属于该类、③ 2026 四层（协议/轻量SDK/图引擎/平台）成员互斥。

**实测**：

```
   3. 有分支/循环/恢复/重试的流程 → 类别 2【Workflow/图引擎】· 代表 LangGraph
   8. 跨栈工具互操作 · 一次实现处处可用 → 类别 7【协议层】· 代表 MCP（协议非框架）
  → 选择树断言 10/10 全过：决策确定性 + 类别归属有效 + 框架∈该类
```

**结论**：

1. **决策树的第一层永远只回答“哪一类”**：加分支/恢复 → 图引擎；知识库 → RAG 框架；跨栈工具 → 协议层；前端 → 前端 SDK。类别一拄，候选集从 24 个崩到 2-6 个——**这正是 A 账稀疏矩阵的工程用法**。
2. **同一场景可以落到“不引入”**（决策表的隐式第 0 步）：线性调模型、无状态 → 直写（06 章已具备全部原语），“不引入框架也是框架决策”。12-收束章会专门量化“该不该引入”，本篇只给方向。
3. **四层收敛断言给的是 2025-2026 的“引入顺序”**：先协议（MCP）→ 轻量 SDK（Agents SDK/Pydantic AI）→ 复杂性不够再上图引擎/平台。这与 B 账的“覆盖维度越宽越重”同向——**协议最轻最先固定，平台最重最后引入**，避免一上来就背一个 4 维全部兜底的重量框架。

## 9. 常见坑（选型踩过的 6 个）

1. **给跨类框架排高下**（本课第一个坑）：拿 LangGraph（图引擎）和 LlamaIndex（RAG 框架）比“哪个更好”，必得一句废话；先落类再比，A 账的 28 对 Jaccard 里只有 2 对合法可比。
2. **把协议当框架**：MCP/A2A/ACP 标格=四个痛点里只有“组装·工具接口”一个，别期待它兜状态/观测/成本（账 B 特判）。
3. **把“生态最大”当唯一判据**：LangChain 生态第一（账 A），但它同时是覆盖 4 维的重量框架（账 B）——生态大 ≠ 匹配你当前的痛点；先看主痛点，再谈生态。
4. **按 GitHub stars 选型**：stars 是“概念普及度”代理（账 C hub），不是“你该引入它”的代理——Swarm 实验被 Agents SDK 取代（账 C 承袭边）说明普及度和存续是两回事。
5. **忘记“不引入”这个选项**：线性任务、无状态、单次工具 → 06 章原语已够，引入框架=白白背上状态/组装/成本三份兜底（账 B 覆盖分布的另一面）。
6. **把 2022 年的答案用到 2026 年的问题**：§7.13 的承袭链是“概念在进化”，链式（类 1）的 2026 适用面远小于 2024——用“链条一长就换图引擎”（账 C 衣钵）自检，而不是抱住 2022 年的教程不放。
