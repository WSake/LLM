## 0. 为什么收束章是「继承关系 + 选型决策」？

07 章从 00 分类学出发，一篇一篇把「组装（01-06）」「Agent（07/08/10）」「Prompt 编程（09）」「协议（11）」四格都填完了。但读者问得最多的问题恰恰不在任何单独一篇里：**「这些框架我一个一个都听过了，那我到底该不该引框架？引谁？」**

00 章账 D 只给了方向（每场景「先定类 → 点代表框架」），没有给**量化**：多重的需求才值得背框架的引入成本？引入成本怎么衡量？——答案落在「需求权重 × 解决度」与「引入成本」的两头对冲里。

所以收束章把 00 章账 C 那张「10 节点·承袭边 6·底座边 9」的谱系缩略图扩成**完整版**，再把选型做成一本书账：

| 账 | 回答什么 | 关键产出 |
|---|---|---|
| A 继承关系完整 DAG | 01-11 十二篇 + 11-MCP 怎么长成一棵 13 节点的树 | 最长承袭链 3、hub=LangChain（影响面 7）、MAF 入度 2（微软双线汇合） |
| B 概念溯源与普及率 | §7「框架会消亡、概念永存」如何被量化 | 8 概念×24 家族普及台账、老概念 6.50 > 新概念 4.75、DSPy 独立 DNA |
| C 该不该引入 | 「选谁」之前先答「要不要引」 | 10 场景类域决策、净分=Σ(需求×解决度)−成本、阈值 0.45、断言 10/10 |
| D 选型决策路牌 | 收束：07 章 13 站×何时到达 + 年谱 | 13 站判据、五主线年谱、里程碑 012 三套写法对照 |

一句话收束（§7.0 的口号的决策版）：**学 API 会过期，学「需求权重 × 解决度 − 引入成本」的算法不会。** 本课把 16 个数字（13 个候选 × 解决度/成本）合成一张「该不该引、引谁」的判定表。

## 1. 先把问题拆开：01-11 篇之后还差哪一问？

12 篇之后，读者手里有两大堆资产，但缺一块粘合胶：

- **一堆框架的「说明书」**：LangChain 的 MRO 13 层 56 字段（01）、LangGraph 的自环和 checkpoint（02）、LlamaIndex 的六行最小闭环（03）、Dify 的积木清单（04）、Haystack 的接线契约（05）、SK 的 `@kernel_function`（06）、AG2 的函数式重写（07）、CrewAI 的三一等公民（08）、DSPy 的签名编译（09）、Agents SDK 的一对象一 Runner（10）、MCP 的 17 方法（11）——**每篇都告诉你「这个引擎怎么干活」，没有一篇回答「我这个项目要不要用它」。**
- **一个散在各篇的数字抽屉**：版本存续表（01 的 7 FAIL / 05 的 ImportError / 06 的改名烈度 / 07 的整代换血 / 09 的 2.x 无 Auto）、框架护栏（02 recursion_limit / 05 max_runs / 06 FunctionChoiceBehavior / 07 ConfigNotProvidedError）、门槛证据（MRO 层数 / 16 参数 1 必填 / 编译产物 ×6.1）——**这些数字其实就是「引入成本」的实测代理，但没人把它们合在一起。**

本课补上这块胶：**把 11 篇的实测数字统一成一张决策模型的参数。** 模型就一个公式：

$$\text{净分} = \underbrace{\sum_i (\text{需求权重}_i \times \text{解决度}_i)}_{\text{该框架帮你解决多少}} - \underbrace{(\text{学习面} + \text{版本风险})}_{\text{引入成本（引自各篇实测）}}$$

- **需求权重** = §7.0 四痛点（状态 / 组装 / 可观测·评测 / 成本·可靠）在某个场景里的相对重要度，四元加起来 = 你的需求剖面。
- **解决度** = 该框架在 01-11 各篇实测里对每个痛点的本机解决能力（0..1，作者按实测定标）。
- **引入成本** = 学习面（MRO 层数/参数必填数/编译产物倍数这些门槛证据）+ 版本风险（改名烈度/存活表 FAIL 数这些存续证据）。

**阈值 0.45**：净分在阈值以下，说明「不引入」的收益都不输给任何框架——第 0 基准直写（06 章原语）出场。0.45 取的是一次「多花半天学习」的心理换算：低于它的净分差，不值得背任何学习面。

## 2. 把「选型」降维成本机测量（探针设计：四本账）

这个探针没有第三方依赖——因为它要量的是**「把 12 篇串起来的模型」，不是任何框架本身**（那些引擎已由 01-11 各篇本机实测过）。四本账：

- **账 A 继承关系完整 DAG**：13 节点（5 主线平铺 sorted），承袭边 9 条（00 章账 C 的 6 条 + 微软双线 3 条：AutoGen→AG2 社区 fork / AutoGen→MAF / SK→MAF），MCP 底座边 12 条（MCP → 其余全部）。图算法：`depth()` 有向 DP 记忆化求**最长承袭链**、`child` 长度求 **hub**、显式栈 DFS 求 **递归影响面**、入度统计 **入度台账**——全部 `sorted()` 保证平票唯一（00 章纪律：set() 哈希坑）。
- **账 B 概念溯源与普及率**：8 个核心范式（Chain/Runnable · 状态图 · 检索索引 · @装饰器 · 角色描述 · Agent+Runner · 签名即程序 · 工具协议）× 首发家族 (年份)，普及台账 = 该思路被多少家族实现/借用（作者按 01-11 实测 + §7 定性）。用**现年 = 2026 − 首发年**把概念按新旧两代（≤2023 老 / ≥2024 新）各取均值对比。
- **账 C 该不该引入**：10 场景 `(场景, 需求权重四元, 允许域, 预期胜者)`；候选 13 个 `CANDS`（12 篇代表 + 直写），每个带 `solve=[四痛解决度], importc, ver, domain`。**类域纪律（00 章）**：`cands = {k:v for k,v in CANDS.items() if v["domain"] & domain or k=="直写"}`——域外候选不参与比净分（防止 Dify 低代码域在别的域也碾压）。决策：`净分 = Σ(n*s) − (importc+ver)`；`chosen = "直写" if best < 0.45 else best`。
- **账 D 选型决策路牌**：13 站 `ROADMAP`（07 章 12 篇 + 直写）× 「路径→判据」；五主线年谱（LINES 直接打印，协议底座行附缀 A2A/ACP）；链路 012 客服重试三套写法的实测对照表（01 链式 / 02 图式 / 06 记忆系统裸写，全是既有章实测数字，挂靠不重测）。

确定性纪律：纯 stdlib、零随机；集合全部 `sorted()`；`assert` 三处硬校验（账 A：最长链=3·hub=LangChain·MAF 入度=2；账 B：老 > 新·普及王 Chain；账 C：10/10）——探针跑不过就是数据表自相矛盾。stdout md5 `43cec7de…` 三个独立进程逐字节恒一，墙钟仅进 stderr（≈0.001 s）。

3. **五主线年谱是 A 账的透视**：Chain 系从 2022 年到 2025（Platform），Agent 系最密（2023-2025 六家），协议底座从 2024（MCP）缀到 2025（A2A/ACP）——**2025 年谱的实际含义是「四层收敛」（00 账 D 的断言）：协议层 + 轻量 SDK + 图引擎 + 平台**，年谱就是收敛过程的快照。

## 7. 把这张决策图怎么用（一页带走 + 掌握度检验）

**一页带走（三步决策法）**：

1. **写需求剖面**：四痛点（状态/组装/评测/成本）各给 0..1 权重——不要模糊的「我需要个 Agent」，写「状态 1.0、组装 0.7、评测 0.4、成本 0.6」。
2. **定类域（00 章纪律）**：权重最高的痛点是哪个 → 那类框架才入候选（状态→图/状态域，组装→通用/RAG 域，评测→评测域，成本→低代码/轻量域）。Dify 再好，不在你的域里就不比。
3. **算净分（账 C 模型）**：`Σ(需求×解决度) − (学习面 + 版本风险)`，和 0.45 比——没到，直写（06 章原语），先固定协议层 MCP；到了，取域内第一名。

**掌握度检验（对应「动手」栏的收尾题）**：*「同一客服场景分别用框架 A、B、C 各实现一半，并写一段『为什么这次不引入框架更划算/更亏』的决策笔记。」*——账 D 的「链路 012 决策笔记」就是样本**：图式引入 = 拿 1 个引擎换回「可恢复 + 可循环」两把闸（LangGraph 域内净分 1.34）；当需求里状态/循环/恢复不占分，直写的 +0.45 说明**不引入更划算**。一句话：**引不引框架，取决于你项目里『状态/循环/恢复』值不值那两把闸。**（完整三段对照见账 D stdout）

## 8. 常见坑（选型收束踩过的 8 个）

1. **把「生态最大」当引入理由**：LangChain 是 hub（账 A 影响面 7）、概念普及王（账 B 11/24），但账 C 里通用链场景它 -0.20（MRO 13 层/56 字段 + 0.x→1.x 七处 FAIL 的成本双高）——**影响力 ≠ 你该背它**。
2. **不写需求权重就做决策**：净分 = Σ(权重×解决度)；不写权重 = 四个分全一样 = 任何域都被 Dify 类型的全域覆盖者带走（它四痛点全主）——**先写权重再选，不是先选再找理由**。
3. **让框架自己定义候选域**：Dify 在低代码域 +1.00，但「轻量单 Agent」域根本没有它（域=【低代码,RAG】）——**域是需求定的，不是框架名定的**（00 章 §7.1 纪律的量化版）。
4. **忘了「不引入」这个可选项**：线性场景净分 +0.45（直写第一）——账 C 明明白白告诉你 **10 个真实场景里就有 1 个该直写**；把「引用框架」当默认动作，等于主动交出状态/组装/成本三份兜底的自由。
5. **把「概念普及」当「库在存续」**：Chain 思想普及 11 家（账 B），但 LangChain 库本身 01 章版本存续 7 FAIL——**概念永存、库换血**，选型选的是「库」，别拿概念热度替库担保。
6. **所有痛点同权求稳**：`0.25×4` 的权重剖面会让所有框架的净分挤在一起（差别全在成本轴）——**把最值钱的痛点打到 0.8-1.0，决策才分得出高下**（账 C 每个场景都至少有一个 ≥0.7 的权重）。
7. **上协议层还想让它兜状态/观测**：MCP 域内净分 0.78（组装 0.90 解决度），但它 solve 的状态 0.10/评测 0.20——**协议只买「组装·工具接口」，状态/观测还得靠框架或自己写**（00 账 B「覆盖 1 维」与 11 章同源）。
8. **拿 2022 年的答案套 2026 年的需求**：最长链 LangChain→AutoGen→AG2（账 A）和年谱里的四层收敛（0.0 章账 D）都指向「图/状态」在往轻量收敛——**用「你需求里状态权重多高」自检，别用五年前教程的默认选择**。
