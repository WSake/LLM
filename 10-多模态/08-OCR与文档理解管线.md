## 1. OCR 是什么、为什么需要它

**是什么**：OCR（光学字符识别）把文档图片里的**字**变成**机器可读的文本**（并通常附上坐标框和置信度）。一次产出的最简三要素：`text`（认出的字符）+ `box`（这个字/词在哪）+ `conf`（多确信）。

**为什么会出现**：LLM/RAG 吃的是文本和向量，不吃像素。一份合同 PDF、一张发票扫描件如果不先变成文本，就永远停留在"人眼能看，机器用不了"——这是文档场景比纯文本场景多出来的第一道闸。它解决的不是"模拟识别的难度"，而是"数据输入侧的第一公里"。

**机制（一句话表）**：

| 三要素 | 直觉一句话 |
|---|---|
| `text` | OCR 认出了什么字 |
| `box` | 这些字在页面上哪块（坐标框——下一步版面分析的原料） |
| `conf` | 它自己有多肯定（低置信度 → 进人工复核队列） |

**边界（OCR 与"文档智能"的分界）**：OCR 只负责"字面转文本"，**不负责语义**——把「价税合计 ¥11.80」认成文本是 OCR 的活，理解"价税合计 = 金额 + 税额、这是一笔勾稽关系"是文档智能的活。商业落地里两者总是串成一条管线，但责任边界要讲清楚，否则会把"识别错字"和"理解错义"混成同一个 bug。

📎 **关联代码**（`ocr_doc_demo.py` 大纲1）——三要素 + 边界分类：

```python

assert doc_task_class("看懂表格哪几列合并")          == "文档智能"    # 版式/语义 → 文档智能
```

```text
PASS 1.3-1.4 字面三件事归 OCR · 语义+版式三件事归文档智能
```

## 2. OCR 组件三选一：PaddleOCR / Tesseract / docTR

**是什么**：地图 §10.7 点名三个代表性组件，它们的差异不在"能不能识别"，而在**部署形态、中文/表格能力、生态**三根的取舍。

**为什么会出现三个而不是一个**：OCR 是"成熟到可以二选一"的组件，没有一家通吃——中文档要精度（PaddleOCR），轻量服务器要省（Tesseract），端到端表格要结构（docTR）。选型 = 追语言密集度 + 要不要版面表格 + 部署预算。

**机制（三栏对照表 + 决策法）**：

| 组件 | 定位 | 强项 | 代价 |
|---|---|---|---|
| **PaddleOCR** | 开源工程全家桶 · 中文强 | PP-OCRv4 中文/多语言 + 版面/表格方向，商业落地最多 | 依赖较重（Paddle 引擎） |
| **Tesseract** | 老牌轻量 · 全平台 | 单进程轻量、多语言引擎、嵌入式/小资源能用 | 中文精度弱、无版面/表格 |
| **docTR** | 文档级端到端（TF/Keras · PyTorch） | 扫描表格 → 结构端到端、论文复现友好 | 生态小、社区少、部署资料少 |

选型三问：① 语言密集（中文/发票/证件 → PaddleOCR）？② 要不要版面/表格（要 → PaddleOCR 全家桶或 docTR）？③ 部署预算（边缘/轻量 → Tesseract）？

**边界**：PaddleOCR 是"全家桶自洽"，docTR 是"结构端的端到端"，别把"表格还原"需求甩给 Tesseract（它压根没这栏）——这是最常见的选错。

📎 **关联代码**（`ocr_doc_demo.py` 大纲2）——五场景点单：

```python
pick_ocr("中文发票")                                            == "PaddleOCR"   # 中文/发票密集
pick_ocr("扫描表格还原成 Excel", need_table=True)              == "PaddleOCR"   # 要版面+表格 → 全家桶
pick_ocr("扫描表格还原成 Excel", need_table=True, deploy="研究") == "docTR"       # 端到端表格研究
pick_ocr("中英混合看个大概", deploy="嵌入式")                  == "Tesseract"   # 轻量边缘
```
```text

```
**怎么看**：2.3–2.7 是"给场景 → 出组件"的确定性决策，跟着三问推理一遍就能复现。

## 3. 版面分析：从"逐字 OCR"到"版面结构化"

**是什么**：OCR 给你一行行带坐标的字，**版面分析（layout analysis）** 把这些带框的字重组成"视觉阅读顺序"上的块（标题/段落/图片/表格/页脚）。它是连接"认字"和"读懂版式"的中间层。

**为什么会出现**：因为**纯文本流会丢结构、也会读错顺序**。典型两处翻车——①双栏文档（期刊/报纸）按全局 y0 排序会把左右栏交叉读（L1→R1→L2→R2）；②表格在文本流里退化成一行行无形状的字符串，"A4 纸"「2」「15.00」的列关系全丢。没有版面层，第 6 节的结构化输出和勾稽校验就无从谈起。

**机制**：版面 = 先把内容分成块（用坐标框 + 类型识别），再按块重排阅读顺序；表格块被识别出来之后，单元格还能按 `(row, col)` 还原成二维数组——这是纯文本流做不到的。地图原话点名的历史脉络：**版面分析模型接管了早期 LayoutLM 的位置**（LayoutLM 2019 把"文字+版面坐标"一起喂进预训练，是文档理解的先行者；现在这块工作由专门版面模型完成）。

**边界**：版面分析解决"读的顺序对不对"，不解决"字认没认对"（那是 §1 的 OCR）——两个错误源要分开排查。

📎 **关联代码**（`ocr_doc_demo.py` 大纲3）——双栏阅读顺序 + 表格二维还原：

```python
ordered = layout_sort(blocks)                       # 按(栏, y0, x0)排 → 先读整左栏再右栏
assert [b[0] for b in ordered] == ["L1", "L2", "R1", "R2"]     # 正确阅读序
naive   = sorted(blocks, key=lambda b: (b[3], b[2]))           # 无版面：全局 y0
assert [b[0] for b in naive] == ["L1", "R1", "L2", "R2"]       # 交叉 → 读错
grid = table_rebuild(cells, 3, 3)                  # 表格块 → 3×3 二维数组
assert grid[2] == ["A4 纸", "2", "15.00"]          # 列关系保住
```
```text

PASS 3.7 要素事实：LayoutLM 2019 文字+版面坐标一起学，后被版面分析模型接管
```
**怎么看**：把 `naive` 那行换成你项目里"直接按 y0 输出 text"的做法，就是没做版面分析的现状；当它有表格/双栏时，结构就是丢的。

## 4. 趋势：OCR 抽取 → 文档智能（DocLLM / Nougat / VLM 看图读文档）

**是什么**：这条线上有三层楼梯——**L1 纯 OCR**（给字符）→ **L2 OCR+版面**（给结构化块）→ **L3 文档智能**（直接理解版式与语义：文档中的**布局、表格、公式**不用先"翻译成纯文本"，模型直接"看"整页）。地图原话就是这五个字：**从 OCR 抽取 → 文档智能**。

**为什么会出现**：纯 OCR/版面在两类场景力有不逮——**公式/杂志排版**（Nougat：Meta 2023，学术 PDF→Markdown，公式小节是招牌）和**版式即语义**（表格合并、页眉页脚的归属、一张图里的填空，先抽取必丢信息）。代表实现分两拨：文档专用模型（DocLLM：布局感知的文档 LLM，银行文档场景）和**直接看图读文档的 VLM**（Qwen2.5-VL / GPT-4o ——"看图读文档"写在章节掌握度检验里）。

**机制（为什么"直接看图"不是无脑最优）**：VLM 读整页要付 token 账。按 02 篇的动态分块口径，A4 300dpi（2480×3508px）≈ 2×3 = 6 片 × 576 + 缩略 256 = **3712 token**（与 02 篇发票账同锚）；对同一页 OCR 后文本 ≈ **50 token**——**74.2×**。所以生产默认路线是"先抽取，抽不干净才上 VLM"（第 5、7 节的管线就是为这条默认路线造的）。

**边界**：文档智能是"补充"不是"替换"——合同/发票/财报这类**信息密度低但结构强**的文档，先抽取再进 RAG 依然更省（token）、更快（延迟）、更可审计（字段是显式的）；VLM 上场的场景是"抽取把语义抽没了/公式/复杂图表"。

📎 **关联代码**（`ocr_doc_demo.py` 大纲4）——三层归位 + 整页 token 账：

```python
assert doc_intel_level("OCR+版面") == "L2 结构化(OCR+版面)"
assert doc_intel_level("Nougat")   == "L3 文档智能"
assert 576*6 + 256 == 3712        # 整页 A4 300dpi → VLM token（02 篇分块口径沿用）
assert round(3712 / 50, 1) == 74.2  # vs OCR 后文本 ≈50 token（02 篇发票锚点只引）
```
```text

PASS 4.5-4.8 3712 vs 50 ≈74.2× · Nougat 2023 学术 PDF→Markdown
```
**怎么看**：这段账是"要不要上 VLM/文档智能"的第一道算盘——先算 74× 的 token 差，再决定哪类文档够格"看图"。

## 5. 开源文档管线：MinerU / Docling / Unstructured / LlamaParse（第一公里）

**是什么**：把"一个 PDF"变成"一行行可入向量库/可检索的数据"，在开源里已经是一套成熟管线，地图点名四家——**MinerU**（PDF→Markdown，2024-2025 爆火，AI 版面识别 + 公式）、**Docling**（IBM 企业级，PDF/DOCX/HTML 统一进 Python API）、**Unstructured**（通用解析，生态大，清洗/分块集成好）、**LlamaParse**（LlamaIndex 官方，云服务，RAG 原生）。

**为什么会出现**：RAG 的成败 80% 在数据侧，而 PDF 是最难伺候的数据格式（嵌套版式、表格、扫描页）。这四家把"解析→结构化→清洗→分块"固化成可复用链路，省掉每家都手搓一遍 PDF 解析器的体力活。

**机制（一段 7 级链）**：

```
PDF → 解析(文本+版面+表格) → 结构化(Markdown/JSON) → 清洗归一 → 分块(chunk) → 向量化入库 → RAG 检索
```

定位一句话：**文档管线把非结构化 PDF 变成数据，是 RAG 数据侧的"第一公里"（检索是第二公里）**——08 章所有检索技巧都在消费这条链的产物。

**边界**：管线不是万能——扫描件（无电子文本）要靠 OCR 补一步；**什么时候不该用管线**：一两页能直接复制文本的文档，手敲/直接读比上一套 MinerU 更快。

📎 **关联代码**（`ocr_doc_demo.py` 大纲5）——四家归位 + 阶段排序：

```python

assert chain.index("结构化") < chain.index("清洗归一") < chain.index("分块") < chain.index("向量化入库")  # 后级消费前级
```

**怎么看**：5.4 的前后级顺序就是管线的数据流——每一步的输入是上一步的输出；你的文档出问题，沿链逐级查（解析坏了 vs 分块丢了 vs 入库错了）是定位姿势。

## 6. 文档理解评测（OCRBench / DocVQA / ChartQA / TextVQA + 字段级判别）

**是什么**：文档理解有四个常用基准（来自地图 §10.9，只引不重测）——**OCRBench**（文字识别：检测+识别，衡量 OCR 引擎本身）、**DocVQA**（文档问答：对着扫描/版面文档提问）、**ChartQA**（图表问答：VLM 读图）、**TextVQA**（自然场景文字：街拍/实物上的字）。它们测的是"榜单级能力"，不是"你的业务准不准"。

**为什么会出现**：第 8 章 RAG 评测讲过的道理在文档场景加倍成立——**榜单数字会骗人**。尤其文档字段这类"错一位数就出事"的任务，行级指标抓不住数量级错误。

**机制（判别性对照，和 08-RAG/11 章同法）**：模拟一次真实翻车——发票金额真值 ¥11.80，OCR 把"1"丢了认成 ¥1.80。如果评测只问"金额提取到了吗"，**¥1.80 也算"提取到了"→ 行级放行**；而**字段级校验**用文档自带的勾稽关系（**价税合计 = 金额 + 税额**）一查，1.80 + 1.00 ≠ 12.80 → **拦截、转重扫**。这就是"用业务数据自建一条勾稽校验，永远比榜单可信"的落地版。

**边界**：四基准管的是"通用能力横比"（选引擎/VLM 时用），字段勾稽管的是"上线的你不许读错钱"——两个尺子用途不同，别用榜单结果替业务验收。

📎 **关联代码**（`ocr_doc_demo.py` 大纲6）——四基准归位 + 判别性对照：

```python

assert _res.startswith("拦截")   # 1.80+1.00≠12.80 → 勾稽断链，拦下
assert field_check([{"金额": 10.00, "税额": 1.80, "价税合计": 11.80}]) == "通过 1/1"
```
```text

PASS 6.3-6.5 金额错位被勾稽拦下 · 无误放行 · 行级 vs 字段级教学点
```
**怎么看**：把 6.3 那行换成你真实合同/发票的勾稽（含税价、尾差容差、编号校验位），就是一份最小可用的文档验收台。

## 7. 实践：发票 → OCR+版面+校验 → 结构化输出 pipeline

**是什么**：本章掌握度检验原文——"把一张发票丢进一个 OCR→结构化输出 pipeline 并测准"。基于大纲 1–6 攒一条最小三档管线，输出五字段 JSON：发票号 / 开票日期 / 金额 / 税额 / 价税合计。

**为什么会出现**：发票是文档理解"商业落地最密集"的样板：格式规范（版面稳定）、字段要进财务系统（差错有真实代价）、错位可校验（勾稽关系现成）。它把大纲 1 必答三两题各按位置归一次。

**机制（三档能力）**：

| 档 | 管线 | 结果 |
|---|---|---|
| L1 纯 OCR | 只出文本流 | 字段只能靠人肉眼找，程序拿不到结构化字段 |
| L2 + 版面 | 键值块归位 → 字段 JSON | 五字段可提取，但读错数字照样进系统 |
| L3 + 校验 | 勾稽（价税合计=金额+税额） | 读错（11.80→1.80）→ 拦下转重扫 |

L3 是生产默认档——**文档理解上线，字段级校验是压舱石**（勾稽关系 + 低置信度转人工，是发票场景两条腿）。

**边界**：发票只是样板，同一套"版面块 + 字段映射 + 勾稽校验"搬到合同（编号+金额+签署日期）、财报（科目+数值+平衡关系）、证件（字段+有效期）只是换字段表和勾稽规则。

📎 **关联代码**（`ocr_doc_demo.py` 大纲7）——三档能力 + 两次错误拦截：

```python
f, ver, lvl = invoice_pipeline("OCR+版面+校验", good_blocks)
assert ver == "通过 1/1"                                         # 10.00+1.80=11.80 通过
f2, ver2, _ = invoice_pipeline("OCR+版面+校验", bad_amt)          # 金额错：1.80+1.00≠12.80
assert ver2.startswith("拦截")                                    # 勾稽断链 → 转重扫
f3, ver3, _ = invoice_pipeline("OCR+版面+校验", bad_tax)          # 税额错：10.00+0.18≠11.80
assert ver3.startswith("拦截")                                    # 每一位错都敏感
```
```text
PASS 7.1-7.5 三档能力 3/3 · 五字段提取 5/5 · L3 校验通过
PASS 7.6-7.7 金额错/税额错各拦截一次（判别性对照）
PASS 7.8 收尾对照：结构化字段走 OCR 文本量级 token，远小于整页 3712
```
**怎么看**：把 `good_blocks` 换成你手头一张真实发票的 OCR/版面输出，五字段全 PASS + 校验通过 = 这条 pipeline 对你这份文档"测准"了。

## 9. 常见坑（映射大纲点）

| 坑 | 症状 → 原因 → 修法 | 对应大纲点 |
|---|---|---|
| 直接上 VLM 读整页 | 延迟 $/token 双高，只因为"模型能看图"  →  没先算 74.2× 的抽取账  →  能抽取就先抽取（§4 的账） | 4 |
| 表格/双栏文本乱序进 RAG | 回答张冠李戴  →  纯文本流丢了版面结构  →  先过版面分析再拼文本（§3） | 3 |
| 金额读错一位数一路绿灯 | 财务对不上账才发现  →  评测只测"提取到了吗"不测"对不对"  →  加勾稽校验 + 低置信度转人工（§6） | 6 |
| 另一个团队也选 Tesseract | "开源免费"选了它，中文发票精度哭  →  选型只看了价格  →  按"语言/表格/部署"三问选（§2） | 2 |
| PDF 解析手搓库 | 每种格式一套代码，维护爆炸  →  没意识到这条链已开源固化  →  上 MinerU/Docling 等，专注上层业务（§5） | 5 |
