## §1 KV 是从「一本账」变成「瓶颈」的爬升

**是什么**：05-01 已经建立了 KV Cache 的世界观——Decode 每一步只算最后 1 个 token，历史 token 的 K/V 全部缓存复用。02-10 又把它的字节账算成了熟面孔：

```
每 token KV 字节 = 2(K、V 各一份) × 层数 × KV头数 × 头维 × 每值字节(2B fp16)
```

**为什么它是推理优化真正的瓶颈**：因为这套字节**随两个维度的乘积增长**。前半句是序列维度——KV 里存的是「全部已在上下文的 token」的 K/V，上下文越长缓存越大（02-10 A1：LlaMA-2-7B MHA 型，1k→0.5G、8k→4G、32k→**16 GiB**、128k→**64 GiB**）；后半句是并发维度——每个**同时在线**的请求都各占一份独立 KV，服务端实际的 KV 总量是「单请求 KV × 瞬时并发请求数」。两个乘号一叠，就是生产负载的真实瓶颈形态：

| 因素 | 单请求 KV | 影响 |
|---|---|---|
| 序列长度 seq | 线性 ×seq | 上下文越长，单条越贵（16 GiB@32k 是 4 GiB@8k 的 4 倍） |
| 并发请求 B | 各算一份 | 10 个并发 = 10 倍 KV；KV 是**全部请求共享**的显存池 |
| 架构（KV 头数） | ×KV头比例 | MHA vs GQA-8 vs MLA 差 1/8/十几倍（§2） |
| 精度 | ×字节/值 | fp16→fp8 省一半（05-03 已算） |
| 显存布局 | 碎片/预留 | 同一批请求碎片化可差 70%（§4 A3） |

这一行公式里，**seq、B 是业务侧定的（改不了），架构、精度、布局是工程侧定的（能动手）**——后者就是本文四条线的全部战场。02-10 的一句话最精炼：「上下文越长，KV Cache（模型的工作内存）就越膨胀，权重都要给它让位」。

> **记忆抓手**：KV 瓶颈 = 单请求 KV（seq 线性）× 并发请求（B 份）× 工程可调的四个乘数（架构/精度/布局/卸载）。

## §2 压缩线：架构少存 + 数值变窄 + 策略丢会议

压缩线的世界观最朴素：**让每个 token 的 KV 变小，或让变小的方式更聪明**。三条子线逐级递进——架构层从源头少存，数值层把存量变窄，策略层根据重要性决定丢谁。

### 2.1 架构层：GQA / MQA / MLA

这是「从源头少存」：把注意力里的 KV 头数从「等于 Q 头数」降下来。

| 方案 | KV 头比例（vs MHA） | 相对 MHA 的 KV | 出处 |
|---|---|---|---|
| **MQA**（2019） | 所有 Q 头共享 1 份 KV | ÷h（几十倍） | `02-03`（详讲） |
| **GQA**（Llama-2） | 分组共享 | ÷g（实测 8k 4→1 GB） | `02-03`（详讲） |
| **MLA**（DeepSeek-V2） | 低秩压缩后再缓存 | ÷十几倍（账算 128k：GQA-8 30.5→MLA 8.6 GiB） | `02-04`（详讲） |

> **不重测原则**：这三个方案的机制与全部数字已由 02-03/02-04 实测/账算，本文**只引不重测**——这是 v3 模板「锚点只引」的标准做法（与 05-01/05-03 一致）。

**边界与坑**：架构层一经预训练就焊死了，不是部署期能改的。它的作用是「选模型时（或改动模型架构时）的决定」，部署期的 KV 降本主要落在 2.2/2.3。

### 2.2 数值层：KV 量化（FP8/INT8）

KV 量化把缓存的每个值从 2 字节压到 1 字节（fp8/int8），**不改变 KV 的结构，只改表示精度**。注意它与权重量化是**两笔独立的账**——权重是「每参数多少字节」，KV 是「每 token 多少字节」。

**机制表：KV 量化省什么**

| 维度 | fp16 KV | fp8 KV | INT8 KV |
|---|---|---|---|
| 每值字节 | 2 | 1 | 1 |
| 存 LlaMA-3-8B 风 GQA-8 @128k | 16.0 GiB | 8.0 GiB | 8.0 GiB |
| 省比 | — | 50% | 50% |
| 质量代价 | — | 轻微（长上下文可测） | 轻微（可测） |
| 主要适用 | 默认 | 长上下文（收益最大） | 与 int8 权重搭配 |

**账（直接引 05-03，锚点只引）**：05-03 已用 `kv_gib = 2×L×H_kv×hdim×seq×B×bpp/(2^30)` 算过——32 层×8kv 头×128 维，32k 下 fp16 **4.0 GiB→fp8 2.0 GiB**；128k 下 fp16 **16.0 GiB→fp8 8.0 GiB**，各省一半。上下文越长收益绝对值越大——这正是「KV 量化在长上下文收益最大」的数值出处。

### 2.3 策略层：KV 剪枝（H2O / SnapKV）

KV 量化是把值变窄，KV 剪枝是**直接决定哪些历史 token 的 KV 值得保留**。H2O（Heavy Hitter Oracle，2023）与 SnapKV（2024）的思路：

- **观察**：注意力权重天然稀疏——每个 token 的注意力只集中在少数「重要」历史 token（近期 + attention sink 附近），大量远端 token 的注意力权重近乎 0；
- **做法**：按注意力权重排序，保留「最近 N + 最重要 M」的 KV，把不重要的丢出缓存；
- **效果**：把「有效记忆」压缩进更小的缓存，显存下降的同时尽量保住质量——但它与精确缓存不同，是**近似**：丢了的 token 不可恢复，极端剪枝会掉点。

**机制表：H2O vs SnapKV**

| 维度 | H2O（2023） | SnapKV（2024） |
|---|---|---|
| 思路 | 在线：观察历史注意力权重，动态决定保谁 | 离线：在 prompt 两次迭代的注意力分布上选「塘」（聚类） |
| 保留对象 | 最近 + 高注意力（Heavy Hitters） | 与 prompt 查询最相关的 token 簇 |
| 剪枝时机 | 生成过程中（decode 时） | 预计算 prompt 时（prefill 后） |
| 适合 | 流式/长生成 | 固定长 prompt + 后续问答 |

**边界与坑**：KV 剪枝是**质量换显存**的近似手段。生产上它通常出现在「显存实在紧张且评测证明掉点可接受」的场景，作为最后一层策略；**不是**默认选项——能先用 §3 复用、§4 分页、§2.2 量化解决的问题，不该先动近似剪枝。

> **压缩线一句话**：架构层少存（GQA/MLA，选型期决定）、数值层变窄（量化，部署期 50%）、策略层丢会议（剪枝，近似，最后手段）——三条依次递进，前两条无损，第三条有损。

## §3 复用线：Prefix Cache —— 相同的开头只算一次

**是什么**：Prefix Cache（前缀缓存）发现一个服务的日常真相——**大量请求共享同一段前缀**：系统提示词、in-context 示例、检索到的共享文档、多轮会话的历史。这些前缀的 KV 每次请求都从头重算一遍，纯纯的浪费。Prefix Cache 把这部分 KV 缓存下来，跨请求复用。

**为什么它单独成一条线**：压缩线是「把每个 token 的 KV 变小」，复用线是「相同 KV 只算一份」。两者正交：复用不影响精度、完全无损，是**数学零变化**的工程优化。

**机制（vLLM / SGLang 标配）**：
1. 请求进来，按前缀哈希/AutoPrefix 定位到已缓存的 KV 段；
2. 命中部分直接复用缓存里的 KV 页，**只对未命中部分做 prefill**；
3. 命中率 ≈ 前缀复用度：前缀越稳定/越共享，省得越多。

**账（02-17 D 层实测锚点，只引不重测）**：02-17 `long_context_demo.py` D 层用固定前缀 16 token、解码 16 步对照过——KV 复用 3.4ms vs 全量重算 10.2ms，**同机快 3.0×**，且两边 logits 逐位一致（True）：「KV 复用不改数学，只改工程」。02-10 A3 的同一次模拟里也顺带证了它——200 个请求共享 512 token 系统提示词，前缀共享页省下**全部 KV 的 42%**。

**机制表：命中率与收益**

| 场景 | 前缀复用度 | 收益形态 |
|---|---|---|
| 恒定系统提示词（不随用户变） | 高（100%） | 每请求省整段前缀 prefill |
| 检索增强（共享文档前缀） | 中高 | 共享文档段只算一次 |
| 用户自由聊天（前缀人人不同） | 低 | 只能靠热度/任务级共享 |

**边界与坑**：前缀缓存不是万能的——用户写的前缀各不相同（低复用度）时收益趋零；实现上还需要能识别「从第几个 token 开始前缀不再相同」的切分（这也是为什么 vLLM 的内部有 prefix caching 的哈希匹配）。**它的适用对象是「服务方可控的前缀」：系统提示词、few-shot、RAG 文档段**。

## §4 管理线：PagedAttention —— 把 KV 当虚拟内存来管理

**是什么**：前面三条线都在「减量」，管理线处理的是**「量放不下时的布局问题」**。朴素做法：每个请求预留一整块「最长上下文」的连续内存——很浪费，因为大多数请求的实际生成长度远小于上限。vLLM 的 **PagedAttention**（Kwon et al., 2023）把 KV Cache 按照**固定大小的一页**（例如 16 token 一页）管理，请求的缓存由若干页拼成，页表映射、按需申请。

**为什么它带来量级收益**：不是因为它把 KV 变小，而是它**消灭了「预留了却没用上」的碎片**，把同一块显存装下更多请求。

**机制表：连续分配 vs 分页分配（02-10 A3 实测锚点，只引不重测）**

| 维度 | 连续分配 | 分页分配（PagedAttention） |
|---|---|---|
| 分配方式 | 每请求预留整块 max_len | 按页按需申请（页=16 token） |
| 200 请求 seq∈[256,2048] 实际用到 | 实际 29.34 GiB | 实际 29.51 GiB（≈真实用量） |
| 预留量 | 50.00 GiB | ≈真实用量（29.51 GiB） |
| 内部碎片 | **70%**（预留给满额） | **~1%**（每请求最多浪费 <1 页） |
| 共享前缀 | 不支持（每请求独立） | **支持**（同一前缀页可跨请求共享） |

同一次模拟里 PagedAttention 顺带解决了「共享前缀」：512 token 系统提示词的页只算一次、各请求复用，省下全部 KV 的 **42%**（与 §3 复用线在同一机制上叠加）。

**为什么「仿操作系统虚拟内存」是准确的类比**：
- 物理内存按页给 ↔ KV 按页给；
- 页表映射虚→实 ↔ 逻辑 KV 序列 → 物理缓存页；
- 按需换页 ↔ decode 到哪申请到哪；
- 共享页 ↔ 同一前缀页被多个请求引用计数复用。

**边界与坑**：PagedAttention 只解决布局（碎片），**不改变 KV 总字节**——把「分页」当「压缩」是 02-10 明确列过的坑。它改变的是「同一显存在容量约束下能同时装多少请求」的**吞吐**，是 serving 层的核心杠杆，但工程实现（页大小、调度、CUDA 内核布局）留到 05-06 在 vLLM 语境展开。

> **管理线一句话**：PagedAttention 把 KV 从「连续大块」变成「按页虚拟内存」——碎片 70%→1%、支持前缀页共享，让显存利用率从「按上限预留」走向「按需分配」。

## §5 卸载线：KV 换出到 CPU / 统一内存

**是什么**：压缩、复用、分页都处理不了最后一个矛盾——**显存物理上不够，但请求还是得跑**。卸载线的答案是：把部分 KV 从 GPU 显存挪到更便宜、更大的存储（CPU 内存 / 统一内存崇），把「GPU 装不下」变成「GPU 只装热 KV」。

**机制**：与操作系统的换页（swap）同构——
1. 每个请求按「近期是否会被再次访问」给 KV 页打分；
2. 冷页换出到 CPU 内存（宿主 RAM）/统一内存，热页留在 GPU；
3. 需要时换回；极端场景甚至落盘（NVMe）。

**为什么它是长上下文的性价比方案**：长上下文场景（128k+）单请求 KV 可能 16+ GiB，且大量 token 属于「只在开头用一次就不再碰」的远端——全留在 GPU 是巨大浪费，换出后 GPU 只保留近程+活跃段的 KV，同一张卡能服务更长的窗口或更多请求。

**成本账（确定性估算，机制是「换出的代价是换回时的 PCIe/内存带宽」）：**

| 存储层级 | 带宽量级 | KV 换出代价 | 适合 |
|---|---|---|---|
| GPU 显存（HBM） | 2.0 TB/s（A100） | 0（热数据） | 活跃 KV |
| CPU 内存（DDR） | ~50 GB/s 级 | 换回一次 16 GiB ≈ 320 ms | 冷/长尾 KV |
| NVMe 盘（可选项） | ~5 GB/s 级 | 更慢，仅极限 | 超长历史/检查点 |

> **边界与诚实**：CPU 换出「能跑」的前提是**命中率足够高**——如果请求频繁回头访问换出的远端 KV，换入/换出的带宽开销会追平甚至超过省下的显存，得不偿失。该数字量级（DDR ~50 GB/s、NVMe ~5 GB/s）为公开规格常识，不是本机实测；具体平台以实测为准。卸载线是「长上下文性价比方案」，多在 128k+ 或推理记忆受限时启用，不是默认。

## §6 决策路径：长上下文的预算场景该先走哪条

四条线各有适用场景，生产上极少单打独斗——正确的姿态是**按预算场景组合**。决策顺序有讲究：

```
压缩（无损先做：量化+架构选定）
  → 复用（前缀共享：先看前缀复不复用）
  → 管理（分页：把碎片清零，让显存装下更多）
  → 卸载（最后手段：显存真不够才换出）
```

**决策表：5 个真实负载场景 → 路径（5/5 判定，内嵌确定性代码）**

| # | 场景 | 显存瓶颈 | 首选路径 | 补位 |
|---|------|---------|---------|------|
| 1 | 恒定系统提示词的客服/审批流（前缀高复用） | 前缀重复 prefill | 复用线（Prefix Cache） | + 管理线分页 |
| 2 | 128k 长文档问答（单请求超长） | 单请求 KV 过大 | 压缩线（KV 量化）+ 卸载线 | + 管理线分页 |
| 3 | 高并发自由聊天（前缀各异） | 请求多、每条都不长 | 管理线（分页，碎片→0） | + 压缩线量化 |
| 4 | 部署期已选 GQA/MLA 架构 + 激活量化 | KV 头已少、值已窄 | 管理线（分页）+ 复用线（若前缀可控） | 剪枝仅当评测可接受 |
| 5 | 推理记忆受限 + 极长历史 | GPU 显存物理不足 | 卸载线（冷 KV 换出 CPU） | + 压缩线减量 |

**内嵌确定性代码：5 场景判定（纯 stdlib，零网络零随机）**

```python
# 05-04 §6 · KV 预算场景决策路径判定（确定性，无随机）
def decide(prefix_reuse, seq_len, concurrency, arch_narrowed, vram_limited):
    """给定负载特征，返回首选路径与补位路径。
    prefix_reuse: 0~1 前缀复用度；seq_len: 单请求上下文长度；concurrency: 并发请求数；
    arch_narrowed: 是否已用 GQA/MLA 少存架构；vram_limited: 显存是否物理不足。
    """
    if vram_limited:
        primary, fallback = "卸载线（冷KV换出CPU）", "压缩线（KV量化）"
    elif prefix_reuse > 0.7:
        primary, fallback = "复用线（Prefix Cache）", "管理线（分页）"
    elif seq_len >= 131072:
        primary, fallback = "压缩线（KV量化）+ 卸载线", "管理线（分页）"
    elif concurrency >= 32:
        primary, fallback = "管理线（分页）", "压缩线（量化）"
    elif arch_narrowed:
        primary, fallback = "管理线（分页）", "复用线（前缀可控时）"
    else:
        primary, fallback = "压缩线（架构选定+量化）", "管理线（分页）"
    return primary, fallback

cases = [
    ("客服审批流·前缀高复用",  dict(prefix_reuse=0.95, seq_len=8192,     concurrency=48,  arch_narrowed=True,  vram_limited=False)),
    ("128k长文档问答",         dict(prefix_reuse=0.20, seq_len=131072,   concurrency=8,   arch_narrowed=True,  vram_limited=False)),
    ("高并发自由聊天",          dict(prefix_reuse=0.10, seq_len=4096,     concurrency=64,  arch_narrowed=False, vram_limited=False)),
    ("GQA架构已选定+量化",     dict(prefix_reuse=0.30, seq_len=16384,    concurrency=16,  arch_narrowed=True,  vram_limited=False)),
    ("推理记忆受限·极长历史",  dict(prefix_reuse=0.40, seq_len=262144,   concurrency=4,   arch_narrowed=True,  vram_limited=True)),
]
exp = [
    "复用线（Prefix Cache）",   # 1
    "压缩线（KV量化）+ 卸载线", # 2
    "管理线（分页）",           # 3
    "管理线（分页）",           # 4
    "卸载线（冷KV换出CPU）",    # 5
]
print("05-04 §6 KV 预算场景决策路径判定（5/5）")
ok = 0
for i, (name, kw) in enumerate(cases, 1):
    primary, fallback = decide(**kw)
    hit = primary == exp[i-1]
    ok += hit
    print(f"  [{i}] {name}: 首选={primary} | 补位={fallback} | 判定={'PASS' if hit else f'FAIL(期望{exp[i-1]})'}")
print(f"  结果: {ok}/5 判定通过")
```

**怎么读这张表/这段代码**：它不是「唯一的正确答案」，而是把四条线的**优先级**用负载特征编码成了可判定的规则——遇到「预算受限」先卸载、遇到「前缀复用高」先复用……这是把「该先走哪条」从拍脑袋变成可执行的决策模板；真实环境把 `prefix_reuse/seq_len/concurrency` 换成你的可观测指标即可。

> **决策路径一句话**：无损的先行（压缩+复用+分页），有损的最后（卸载、剪枝）；优先级锚在「前缀复用度 > 单请求长度 > 并发数量 > 架构/显存约束」。

## §8 常见坑

| 坑 | 症状 | 修法 |
|---|---|---|
| 把 KV 量化当权重量化 | 量化了权重还嫌 KV 大 | 两笔独立账，05-03 §6 对象三分；KV 单独量化 |
| 以为 PagedAttention 是「压缩」 | 上线分页后发现 KV 总字节没降 | 分页只消灭碎片（70%→1%），不改变总字节 |
| 前缀缓存设了但没收益 | 用户自由聊天，前缀各写各的 | 看复用度：前缀不可控时收益趋零，只对系统提示/RAG 段有效 |
| 高复用前缀没开 Prefix Cache | 每次请求都重算系统提示词 KV | 02-17 D 层 3.0×、02-10 A3 省 42%——先复用再分页 |
| 直接上 KV 剪枝 | 长文档掉点、评测打回 | 剪枝是有损近似；先走无损三线（压缩/复用/分页） |
| 长上下文全想靠卸载 | 换出 KV 频繁换回，PCIe 带宽耗尽 | 卸载命中率低时牺牲大于收益；冷热分离+量化先行 |
| 忘了 batch 放大 | 并发 10 就 OOM | 单请求 KV × B 并发是真实瓶颈总量；分页解决布局、量化/剪枝减量 |
