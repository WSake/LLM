## 1. 四种格式，各一句定位

**是什么**：模型权重训练完是一堆浮点数，保存在哪、用什么字节表示，就是"权重格式"。50 步看，格式五花八门；10 步看，就是四种生态。

| 格式 | 典型后缀 | 一句话定位 | 谁在用 | 精度 | 切片加载 | 可移植性 |
|---|---|---|---|---|---|---|
| **HF safetensors** | `.safetensors` | 开源 Python 生态**标准**：安全反序列化 + 支持切片加载，transformers / vLLM 默认 | transformers、vLLM | FP32/FP16/BF16/FP8 等全档 | ✅ 按张量名/形状加载部分权重 | 强（纯数据，跨框架） |
| **bin / ckpt** | `.bin` / `.ckpt` / `.pth` | PyTorch **原生**格式：`torch.load` 直接灌回，早期流行，如今默认已让位 | 早期 HF 仓库、旧训练代码 | 同上 | ❌ 整包反序列化 | 弱（绑 Python/pickle，有代码执行风险） |
| **GGUF** | `.gguf` | llama.cpp 系**量化分片**：单文件 & 任意精度（含 4bit/混合位宽）& 端侧友好 | llama.cpp、Ollama、LM Studio、llama-cpp-python | 以量化档为主，可存 FP16 | ⚠️ 按 seek 偏移读（底层支持分片拉取） | 强（单文件跨 OS 端侧，但计算内核绑 llama.cpp 系） |
| **Engine / Plan** | `.engine` / `.plan` | TensorRT-LLM 系列**编译产物**：算子已固化、绑定硬件与 batch 形状，**不可移植** | TensorRT-LLM、ONNX Runtime（对应的 `.onnx` 未做 engine） | 编译时选定（FP16/INT8/FP8…） | ❌ 编译即整体 | 极弱（换卡/换 max-batch 需重新编译） |

📎 **判定函数**（正文 §7 会抽成完整代码）——"给一句话格式名，返回它的定位四要素"，`4/4` 全对即过关。这四格是理解后续《量化》《引擎选择》两篇的骨架，先背语气再背细节。

## 2. HF safetensors：开源 Python 生态的标准

**是什么**：safetensors 是 Hugging Face 为模型权重设计的存储格式。核心三点——**安全**（不跑任意代码，拒绝 pickle 式反序列化攻击）、**零拷贝读取**（带偏移量索引，只读需要的部分）、**切片加载**（按张量名加载某层权重，不把整个文件灌进内存）。

**为什么它是标准**：生态即标准。transformers 的 `from_pretrained`、vLLM 的 model loader、微调框架 LoRA/QLoRA 都默认吃 safetensors；HF Hub 上几乎所有新发布开源模型的权重主文件就是 `.safetensors`。它不是"性能最好"，而是"所有人默认用它"。

**机制（为什么能切片）**：文件 = 一个 JSON 头（每张量名 → 形状 + 字节偏移）+ 连续字节区。加载时按 offset 精准读目标张量，不需要解析不可信对象的 `__reduce__`——安全问题是早期的 `.bin` pickle 路线逼出来的。

**与 13-06 的衔接**：13-06「模型注册与版本管理」里注册的 7 件套，权重这一件默认就是 safetensors；本篇补的是"它为什么能进生产"——安全 + 切片 + 生态默认，三个环是同一件事。

📎 **切片加载的最小直觉演示**（不真读大文件，讲清楚"偏移量"这个机制）：

```python
def safetensors_slice_frames(tensor_list):
    """模拟 safetensors 按字节偏移切片：只看 offset 段，不载入全文件。"""
    offset = 0
    frames = []
    for name, nbytes in tensor_list:
        frames.append((name, offset, offset + nbytes))   # (张量名, 起始, 结束)
        offset += nbytes
    return frames

frames = safetensors_slice_frames([("lm_head.weight", 4*1024*1024*4),   # FP32 4MB
                                    ("layers.0.self_attn.q_proj.weight", 8*1024*1024*2)])  # FP16 16MB
assert frames[1][1] == 4*1024*1024*4      # 第二张量从头一个张量末尾开始
assert frames[1][2] - frames[1][1] == 8*1024*1024*2
print("切片读取最小演示 PASS：按偏移读，不需要整包载入 →", frames)
```
```text
切片读取最小演示 PASS：按偏移读，不需要整包载入 → [('lm_head.weight', 0, 16777216), ('layers.0.self_attn.q_proj.weight', 16777216, 33554432)]
```

**边界**：safetensors 是"存权重"，不是"跑权重"。它不进计算图、不编译算子；真正决定算得快不快的，是**加载方（transformers/vLLM）怎么把它排进显存**——这正是本篇 §6 显存账的引子。

## 3. bin / ckpt：PyTorch 原生格式，曾经的默认

**是什么**：`.bin`（binaries）与 `.ckpt`（checkpoint）是把张量用 Python `pickle` 序列化后的 PyTorch 权重文件；`torch.load("model.ckpt")` 直接还原成"张量 dict / 模型对象"。早期 HF 仓库大量以 `.bin` 为主文件发布。

**为什么重要（历史定位）**：transformers 第一代加载路径就是这个；它见证了预训练→发布→加载的第一个黄金循环。今天你 clone 老仓库仍会撞见它。

**边界（为什么默认让位）**：三个致命点——① **安全**：pickle 反序列化可以执行任意代码，加载不可信的 `.bin` = 在自己机器上跑对方代码（safetensors 起家的初衷就是堵这个）；② **整包反序列化**：没有偏移索引，加载 13GB 权重不先把整个对象树还原进内存就取不到单层（切片加载无从谈起）；③ **绑定 Python**：decode 端、移动端没法轻量消费，跨语言生态直接断裂。

📎 **安全对比的直观演示**（不真执行恶意 pickle，演示"pickle 可带 payload 而 safetensors 只有字节"）：

```python
import struct

def pickle_payload_risk(kind):
    """演示两类负载的本质差异：pickle 可嵌入任意操作码（如 eval），safetensors 只有字节区。"""
    if kind == "pickle":
        return "contains __reduce__ → 反序列化时可执行任意代码（不可信源 = 险）"
    if kind == "safetensors":
        return "header(JSON 张量名+offset) + raw bytes → 只读操作，无代码执行面"
    return "unknown"

assert "任意代码" in pickle_payload_risk("pickle")
assert "只读操作" in pickle_payload_risk("safetensors")
print("安全对比 PASS：" + pickle_payload_risk("pickle") + "；" + pickle_payload_risk("safetensors"))
```
```text
安全对比 PASS：pickle 可嵌入任意操作码（不可信源 = 险）；safetensors 只有字节区（只读操作，无代码执行面）
```

**一句话记忆**：`.bin` 教会了生态"权重怎么存"，安全与整包两堵墙逼出了 `.safetensors` 与分片单文件（GGUF）两条替代路线。

## 4. GGUF 与 Engine/Plan：端侧友好 vs 生产编译

### 4.1 GGUF（llama.cpp 系 · 量化分片 · 单文件）

**是什么**：GGUF 先河是 llama.cpp 的 GGML 系列，后以 **GGUF** 稳定下来。定位一句话：**单文件 + 任意/混合精度 + 端侧友好**。一个 7B 模型量化成 Q4_K_M 就是约 4GB 一个 `.gguf` 文件，拷到手机/树莓派直接跑。

**为什么出现**：原生 FP16 的 safetensors 在桌上型 GPU 很自然，但到了**端侧**（本地消费级/无 GPU/移动端）就太奢——我们要能"低精度 + 单文件 + 免 Python 依赖"。两条诉求 GGUF 一并解决。

**机制（混合位宽）**：llama.cpp 的 **k-quants** 允许不同张量用不同位宽要点保留的层用更宽的 bit（如 transformer 的 attention 输出用 Q4、嵌入用 Q4_0、下有 Q8_0 结合），在"精度损失"与"体积"之间做细粒度取舍。

**边界与衔接**：GGUF 的"任意精度 + 单文件"是 05-03《量化》篇的地基；Ollama / LM Studio 背后就是拿 GGUF 在跑。它的计算内核高度绑 llama.cpp 系——**一格式一生态**，这是它与"引擎编译产物"共享的宿命。

### 4.2 Engine / Plan（TensorRT-LLM 系列 · 编译产物 · 不可移植）

**是什么**：TensorRT-LLM 把一个模型 **编译** 成面向特定 GPU 的算子图（`.engine`），ONNX Runtime 的 `.onnx` 是"计算图但未编译、相对更可移植"的中间形态，真正的"编译产物不可移植"指的是 engine/plan。它把算子融合、内存规划、量化内核在**编译期**一次雕好，推理期只剩执行。

**为什么它值得**：同为精度 × 字节数这一条（§6），TensorRT-LLM 的 engine 能用 FP8/INT8 + 融合算子把 H100 的 token/s 再顶一截——05-03 讲精度、05-08 讲引擎选型，本篇只负责把"不可移植"四个字钉进概念里。

**边界（最硬的边）**：**绑定硬件与 batch 形状**——为 A100 编的 engine 换到 H100 不能直接跑；`max_batch_size` 改了要重新编译。它是"生产墓碑"，不是"分发格式"。这也是新手最常踩的坑：看到 `.engine` 以为能拷走，一跑就炸。

## 5. 为什么有这么多格式：一条演进链 + 四条诉求

**演进链（安全 → 单文件 → 编译优化 → 端侧）**：

| 阶段 | 驱动问题 | 产物 | 对应格式 |
|---|---|---|---|
| 原生序列化 | 训练完直接能存 | PyTorch checkpoint | bin / ckpt |
| **安全** | pickle 反序列化 = 任意代码执行 | 纯数据 + 偏移索引 | **safetensors** |
| **单文件 / 低精度** | 端侧要单文件、要压体积 | 量化分片单文件 | **GGUF** |
| **编译优化** | 生产要高吞吐低延迟 | 算子融合 + 显存规划固化 | **Engine / Plan** |

**四条诉求**浓缩成一张表：

1. **安全**：不可信权重不能在你机器上跑代码 → safetensors；
2. **单文件 & 可分发**：低体积、拷走即用 → GGUF（INT4 3.26GiB vs FP16 13.04GiB，见 §6）；
3. **编译优化**：把几千个算子在你卡上编排好，推理期零判断 → TensorRT-LLM engine；
4. **端侧友好**：移动/嵌入式无 Python、无 GPU 也能跑 → llama.cpp 系 GGUF。

> **记忆钩子**：四种格式 = 站在四个"不可能"的门口——**不安全**（bin）、**不切片**（safetensors 解决）、**不小/不端侧**（GGUF 解决）、**不快/不绑定**（engine 解决）。每种格式都"为办成一件事而存在"，因此也各有边界，没有全能格式。

## 6. 加载显存账：参数量 × 精度字节 = 最小显存

**是什么**：模型进 GPU，第一笔开销（且是底仓）就是 **权重本身的字节数**。公式：

```
最小显存(GiB) = 参数量(个) × 每精度字节(bytes) ÷ (2^30)
```

**机制（为什么 × 精度字节）**：FP16/BF16 = 2 bytes、FP32 = 4、FP8 = 1、INT8 = 1、INT4 = 0.5。把 7B 个参数都按精度放大，就是权重显存的**下限**——**不包含** KV Cache 与激活（那 8 成时间才是真正的"预留空间"主力，见后）。

**账（7B/14B/70B × FP16/INT8/INT4，与 13-01 同式公式）**：

| 精度 | 字节/参数 | 7B | 14B | 70B |
|---|---|---|---|---|
| FP32 | 4 | 26.08 GiB | 52.15 GiB | 260.77 GiB |
| FP16 / BF16 | 2 | **13.04** GiB | 26.08 GiB | **130.38** GiB |
| FP8 / INT8 | 1 | 6.52 GiB | 13.04 GiB | 65.19 GiB |
| INT4 | 0.5 | **3.26** GiB | 6.52 GiB | 32.60 GiB |

> **口径注**：表中 GiB 均为两位小数近似（与 13-01 探针注释同位）；精确值见下方代码输出（如 7B FP16=13.0385…、70B FP16=130.385…）。

**三个锚点直接读出**（这就是本节的"数字肌肉"）：

- **7B FP16 ≈ 13.04 GiB**：小模型、单卡无压力装下（A100 80GB 富余极多）；
- **70B FP16 ≈ 130.38 GiB**：单卡装不下，必须 ≥2 卡 TP（13-01 B 账 70B 各卡 tok/s"÷10"的同源账）；
- **7B INT4 = 3.26 GiB**：体积只有 FP16 的 1/4——GGUF 端侧拆的这一档就是它。

**边界：权重账 ≠ 整卡账**。13.04 GiB 只是**底仓**。一次真实推理的显存 = 权重 + **KV Cache**（02-10：7B@32k 手算 16GB vs 4GB，长上下文 KV 反而能超过权重）+ **激活**（短序列小但非零）+ **框架开销**。这就是 plan3 原句"**还要给 KV Cache 与激活留空间**"的含义：权重用公式算死，KV/激活按实际吞吐算活。

📎 **确定性账目代码**（纯 stdlib，公式与 13-01 `gpu_account_demo.py` 同式 `n_b*bpp*1e9/(2**30)`）：

```python
def wt_gib(n_b, bpp):
    """与 13-01 探针同式：参数量(B)×每参精度字节×1e9 → GiB。n_b 单位=十亿。"""
    return n_b * bpp * 1e9 / (2 ** 30)

class GB:  # 精度档位，用属性代替下标写法（保持与 13-01 同式）
    fp16 = staticmethod(lambda n: wt_gib(n, 2))
    int8 = staticmethod(lambda n: wt_gib(n, 1))
    int4 = staticmethod(lambda n: wt_gib(n, 0.5))

# 三组锚点（7B/14B/70B × FP16/INT8/INT4）—— n 单位=十亿，wt_gib(7,2)=7×1e9×2÷2^30
assert abs(GB.fp16(7) - 13.04) < 0.01           # 7B FP16 ≈ 13 GiB
assert abs(GB.fp16(70) - 130.38) < 0.01         # 70B FP16 ≈ 130 GiB
assert abs(GB.int4(7) - 3.26) < 0.01            # 7B INT4 ≈ 3.26 GiB
assert abs(GB.int8(70) - 65.19) < 0.01          # 70B INT8 ≈ 65 GiB

# 单卡装不装得下的快判：80GB 卡
def fits_on_80g(n_b, bpp): return wt_gib(n_b, bpp) <= 80.0
assert fits_on_80g(7, 2) and not fits_on_80g(70, 2)   # 7B fp16→OK；70B fp16→需 TP≥2
print("PASS 所有权重显存账目：7B fp16=%.3f GiB · 70B fp16=%.3f GiB · 7B int4=%.3f GiB · 70B int8=%.3f GiB" % (
    GB.fp16(7), GB.fp16(70), GB.int4(7), GB.int8(70)))
```
```text
PASS 所有权重显存账目：7B fp16=13.04 GiB · 70B fp16=130.38 GiB · 7B int4=3.26 GiB · 70B int8=65.19 GiB
```

**怎么看**：把 `gpu_account_demo.py` 的 `wt_gib` 原样复用到本篇，就是不重测、同一口径。**如果卡只能放 80 GiB，70B FP16（130.38）就必 TP；放到 INT8（65.19）单卡勉可——这就是格式/精度直接决定部署拓扑的第一手证据。**

## 7. 边界：格式与"入口"解耦混用

**是什么**：格式 ≠ 谁在加载。同样的 `.safetensors`，可以走三种完全不同的"入口"：

| 入口 | 典型写法 | 语义 | 适用 |
|---|---|---|---|
| **transformers 自动下载/加载** | `AutoModel.from_pretrained("Qwen/Qwen2.5-7B")` | 从 Hub 拉整套（config+tokenizer+weights），**自动**组模型 | 新手、微调、实验、原型 |
| **切片/手动加载** | `safetensors` 打开 + 按张量名取每层 | 只取你需要的张量（如只取最后一层 probe、只替换某层） | 探针、LoRA、热换层 |
| **编译产物** | TensorRT-LLM build 一次 → `engine` | 不再"加载"，而是"执行编译好的图" | 生产高吞吐/低延迟 |

**机制（解耦的三种"格式×入口"正反例）**：

- ✅ **格式无关入口**：同一个 safetensors 文件，transformers 整包加载或 safetensors 切片取一两个张量都行——**格式解耦"存"与"用"**；
- ⚠️ **切片 ≠ 完整加载**：切片直接读偏移，省下整包反序列化，代价是**没有 Python 对象树、依赖你自己拼 config**；
- ❌ **编译产物不可移植**：**本质上不是"加载"**，engine 是给"某型号卡 + 某 batch 上界"烧好的执行图——**格式与硬件/形状耦合**，改任何一项都要重编。

**知识点的最后一格**：为什么经常"混用"？因为同一家公司生产里可以**三路并存**——`transformers` 做微调回灌、`safetensors` 切片做回归探针、`TensorRT-LLM engine` 做线上推理（05-08 讲引擎选型时展开）。**格式是底层载体，入口是上层用法，两者解耦才让"训练/实验/生产"共用同一套权重。**

📎 **场景判定函数**（`4/4` 全过 — 本节掌握度检验）：

```python
# 给"一段真实场景描述"，返回最合适的格式+入口
def pick_format(scene):
    if "端侧" in scene or "单文件" in scene or "Ollama" in scene:
        return "GGUF"            # 端侧四条诉求：单文件 / 低精度 / 免 Python / 到手机
    if "切片" in scene or "只取某层" in scene or "offset" in scene:
        return "safetensors"     # 按张量偏移读，不整包载入
    if "编译" in scene or "重编" in scene or "不可移植" in scene or "A100" in scene:
        return "Engine/Plan"     # 算子已固化，绑定硬件与 batch 形状
    if "整包" in scene or "from_pretrained" in scene or "python" in scene:
        return "save→safetensors / load→transformers"   # 生态默认入口
    return "bin / ckpt"          # 兜底：PyTorch 原生早期格式

scenes = [
    ("把 7B 量化成单文件 .gguf 拷到手机跑", "GGUF"),
    ("只想按 offset 读 lm_head 那 4MB 权重做探针", "safetensors"),
    ("为 A100 烧好的 .engine，换到 H100 得重编", "Engine/Plan"),
    ("AutoModel.from_pretrained 整包拉下来跑推理", "save→safetensors / load→transformers"),
]
for scene, want in scenes:
    got = pick_format(scene)
    assert got == want, (scene, got, want)
print("格式定位→适用场景判定 4/4 全 PASS")
```

```text
格式定位→适用场景判定 4/4 全 PASS
```

**一句话收束**：用格式的眼光看下载按钮，你看到的不是"文件"，而是**它承诺在什么环境、什么精度、什么耦合度下能跑**；safetensors——生态伞，GGUF——端侧单文件，Engine——卡上墓碑。

## 9. 常见坑（映射大纲点）

| 坑 | 表现 | 为什么 | 应对 |
|---|---|---|---|
| 把 `.bin` 当 `.safetensors` 信任 | 加载不可信 `.bin` 后机器被植入后门 | pickle 反序列化可执行任意代码（§3） | 一律改 safetensors；不可信权重只信纯数据格式 |
| 只算权重显存就估显卡容量 | 7B FP16 13.04 说"A100 稳了"，一上 32k 上下文就 OOM | **NN KV Cache + 激活**（02-10 长上下文 KV 反超权重）也占卡（§6） | 权重账 + KV 账 + 激活账三本一起算（13-01 三本账） |
| 拿 GGUF 的 INT4 数字跟 FP16 混比 | 甲方问"你们模型多大"，答"13GB"，结果那是 FP16 不是线上跑的 3.26 | 精度不同、体积不是同一把尺（§6） | 报数先报精度：**7B INT4=3.26 · FP16=13.04** |
| 把 TensorRT-LLM engine 当便携文件拷 | 换 H100 一跑就崩"engine built for different device" | 编译产物绑定硬件与 batch 形状（§4.2） | engine 按"卡型+max-batch"重编（05-08 展开） |
| 以为格式决定一切 | 同是 safetensors，transformers 与 vLLM 加载性能天差地别 | **格式是载体，加载方/引擎才决定算得有多快**（§2 边界 / §7） | 选格式看"承诺什么"，选引擎看"怎么跑" |
