## §1 为什么量化是推理的第一杠杆

**是什么**：量化（Quantization）是把模型参数的表示位数从「高精度浮点」压到「低位数、更低表示能力」的表示方式。推理侧最直白的量化，就是「每存一个参数，从 2 字节省到 1 字节甚至 0.5 字节」。

**为什么出现在推理语境**：05-01 已经算过——Decoder 每生成一个 token，都需要把所有权重从头到尾读一遍，Decode 是访存密集型，瓶颈在「读取权重字节数 × 每字节耗时」，而不在算力。于是对「读权重」这一动作本身压缩，就是极限优化的主战场。05-02 的三张账（13-01 的 `account_a/b/d`）里，`tok_s` 公式已经把「用多快带宽喂多大权重」写死了：

```
tok_s(bw, n_b, bpp) = bw × 1e12 / (n_b × bpp × 1e9)
```

**机制表：量化降了什么、提了什么**

| 维度 | 不量化（FP16） | 量化后（INT8） | INT4 |
|------|---------------|---------------|------|
| 每参数位数 | 2 字节 | 1 字节 | 0.5 字节 |
| 7B 权重显存 | 13.04 GiB | 6.52 GiB | 3.26 GiB |
| 70B 权重显存 | 130.39 GiB | 65.19 GiB | 32.60 GiB |
| 单卡 A100(80G) 能否装 70B | ✗ | ✓ | ✓ |
| 同等带宽下推理速度 | 基准 1× | ≈2× | ≈4× |
| 质量代价 | —— | 几乎无损 | 轻微可测掉点 |

这个「2 字节→1 字节→0.5 字节」的账，是从 05-02 的 `wt_gib` 直接延伸来的。先把它做成独立可核对的表。

## §2 全精度三档：FP32 / FP16 / BF16

**是什么**：全精度档位指「不做任何压缩」时的三种浮点表示。三者的区别只在**指数位**与**尾数位**的分配，以及字节数：

| 档位 | 位数(S+E+M) | 字节/参数 | 动态范围 | 尾数精度 | 一句话 |
|------|------------|-----------|----------|----------|--------|
| FP32 | 1+8+23 | 4 | ~1e±38 | 23bit | 训练离线精度黄金标准，推理几乎不用 |
| FP16 | 1+5+10 | 2 | ~1e±4（有限） | 10bit | 省一半显存，但小数值易下溢 |
| BF16 | 1+8+7 | 2 | ~1e±38（同 FP32） | 7bit | 与 FP32 相同动态范围，训练主流 |

**为什么 BF16 比 FP16 稳**：FP16 指数只有 5 位，小数值（如 1e-4、1e-5）表示不了会下溢成 0；去掉它干脆换成与 FP32 同款 8 位指数（BF16 的尾数砍到 7 位，但指数照搬 FP32），动态范围全局保住，牺牲的只是尾数里的细微精度——对训练的反向传播（梯度值大范围分布）和推理都更安全。这一「稳」是驯服后续一切量化的地基：**量化是对稳定表示的进一步压缩，而不是对不稳定表示的补救**。

**账一 · 三档全精度显存（`wt_gib`）**

```python
def wt_gib(n_b, bpp):
    return n_b * bpp * 1e9 / (2**30)   # 13-01 探针原式：B×字节/参数 → GiB

class P:   # 精度档位
    fp32, fp16, bf16 = 4, 2, 2          # 字节/参数

# 三种模型——7B/70B/671B（DeepSeek-V3 参数级）在三种精度下的权重显存
for n_b in (7, 70, 671):
    row = [f"{n_b}B"] + [f"{wt_gib(n_b, p):.2f}" for p in (P.fp32, P.fp16, P.bf16)]
    print(" | ".join(row))
```

```text
7B | 26.08 | 13.04 | 13.04
70B | 260.77 | 130.39 | 130.39
671B | 2499.67 | 1249.83 | 1249.83
```

**怎么看 ← 衔接 05-02/13-01**：`wt_gib` 就是 05-02 §6 原式，此表是它的**精度维度扩展**。三档里 **FP16 与 BF16 字节数相同（都是 2），显存账一模一样，差的只是数值稳定性**——这正是上一段「BF16 动态范围大更稳」的数字体现。FP32 的 4× 开销在推理侧只剩「离线校准工具的内部基准」这一类用途。

**锚点核对**（三道闸内复核）：
- 7B FP16 = 13.04 GiB、70B FP16 = 130.39 GiB —— 与 05-02 §6 ✅3 的 `assert wt_gib(7,2)==13.04; assert wt_gib(70,2)==130.39` 逐位一致。
- 671B FP16 ≈ 1249.83 GiB —— 与 13-01 `a_671_fp16 = wt_gib(671,2)` 同源，DeepSeek 官方用更高的 `bpp` 口径报 >1.3TB，此处按探针公式取 1249.83。

**边界**：FP32/BF16 的「尾数精度」对训练（梯度有效数字）意义远大于推理（输出已量化为整数/低精度），本文讨论范围限定推理侧的装载与带宽，训练侧不是本文重点——它出现在 13 章的分布式训练账里。

## §3 FP8（E4M3/E5M2）：2024-2025 推理的新标配

**是什么**：FP8 是 8 位浮点，两种格式的区别在指数与尾数位的分配：

| 格式 | S+E+M | 动态范围 | 用途定位 |
|------|-------|----------|----------|
| **E4M3** | 1+4+3 | ~±448 | 权重+激活（推理主力） |
| **E5M2** | 1+5+2 | ~±57344 | 梯度/反传（训练侧更稳，精度低但范围大） |

推理用 E4M3 装权重（精度够、范围对应用得上的模型数值），训练用 E5M2 兜梯度的大动态。

**为什么成了 2024-2025 推理标配**：FP8 把权重字节从 2 砍到 1 → 显存半降、带宽读入半降 → 按 §1 的 `tok_s`，同等带宽下**推理生成速度接近翻倍**，而质量损失两句话带过（见下账二）。对比 INT8，FP8 保留了浮点的尾数与「真实数值含义」，对激活/权重混合场景更平滑，硬件（H100/H200/B200/昇腾/L24x）原生支持。

**账二 · FP8 的带宽提速（`tok_s`）**

```python
def tok_s(bw_tbps, n_b, bpp):
    return bw_tbps * 1e12 / (n_b * bpp * 1e9)   # 13-01 原式：带宽÷(参数量×字节/参数)

# 70B 模型在 A100(2.0 TB/s) 上，FP16→FP8→INT4 的生成速度
for bpp, fmt in ((2, "FP16"), (1, "FP8"), (0.5, "INT4")):
    t = tok_s(2.0, 70, bpp)
    print(f"{fmt:5s} {t:6.1f} tok/s")
```

```text
FP16    14.3 tok/s
FP8     28.6 tok/s
INT4    57.1 tok/s
```

**怎么看**：A100 上 70B 从 FP16（14 tok/s）到 FP8（29 tok/s）是恰好 2.0×；到 INT4（57 tok/s）是 4.0×。**速度提升的来源就是「读权重的字节砍半」**——这正是 gpu_math_demo.py 里「量化主要不是为了省显存，而是为了喂饱带宽」那句原话的数值化。13-01 的 `account_b` 同样把「70B fp8 A100 ≈ 28.57 tok/s = fp16 的 2×」写进了探针（`token 输出`行），与我们这里一致。

**训练侧事实锚点 · DeepSeek-V3**：FP8 不是只属于推理。DeepSeek-V3（671B MoE）直接以 **FP8 精度训练**（E4M3 存激活、E5M2 存梯度/权重中间态），官方报告说训练时的显存开销与 FP16 相当但**带宽减半**——这是「FP8 能撑住前沿训练」的公开事实（非虚构数字，官方 blog/paper 有明细）。推理侧的 671B FP8 ≈ 624.92 GiB（上表 §2），仍超单卡，所以实际部署用 INT4 = 312.46 GiB 摊多卡才上得了节点级，这是 §5 的选择点。

**边界**：FP8 的 E4M3 尾数只有 3 位，对数值分布极宽的层（如极端重尾层）会轻微掉点；跨硬件对 FP8 的实现差异（NVIDIA vs AMD vs 昇腾）在部署前需要按§7 的三角评测实际校准，不宜默认「FP8=无损」。

## §4 INT8（W8A8）：权重+激活一起量化，SmoothQuant 几乎无损

**是什么**：INT8 分两种形态——**W8A8**（权重 8 位 + 激活 8 位一起量化）与 **W8A16**（只量化权重、激活保持 FP16）。本节主要讲 W8A8，因为正是它把「激活量化难」这个痛点拿到台面上，并催生了 SmoothQuant。

**为什么激活难量化**：权重是「训练收敛后的常量」，分布稳定；激活（中间层的张量）随输入变化，且**偶尔出现远大于均值的大数值——激活尖峰**。INT8 用 8 位整数能表示的档位有限，一旦某个激活出现尖峰（如 attention score 的 logits），量化步长被迫拉大，其余大量「小数值」被压进一个档里剧烈失真——这是 prompt 里「INT8 为什么不能直接做激活」的关键。

**SmoothQuant 的机制**：把「激活的尖峰」**迁移到权重里**。具体做法是给激活乘一个平滑因子 `s`（`X' = X / s`），同时给权重乘回 `s`（`W' = W · s`）——**两者的数学乘积不变**（`X·W = X'·W'`），但激活的尖峰被压到可 8 位表示的区间，而权重虽然变大，因为是常量、可以离线预缩放，量化损失小。这就是「把激活尖峰挪到权重」的字面含义。

**账三 · SmoothQuant 误差演示（纯确定性）**

```python
acts = [0.5, 0.4, 0.3, 0.2, 0.1, 8.0, 6.0]   # 7 个激活，含两个尖峰(8.0/6.0)
w    = [0.1, 0.2, 0.3, 0.4]                  # 4 个权重
S = 3.0                                       # 平滑因子：尖峰/均值比

def int8_rms(vals, scale):
    peak = max(abs(v * scale) for v in vals)  # 用峰值定量化步长
    step = peak / 127.0
    q = [round(v * scale / step) * step / scale for v in vals]
    return (sum((a - b) ** 2 for a, b in zip(vals, q)) / len(vals)) ** 0.5

r0 = int8_rms(acts, 1.0)                      # 基线：直接量化激活
r1 = int8_rms([a / S for a in acts], 1.0)     # SmoothQuant：先除平滑因子
print(f"直接量化激活  RMS误差 = {r0:.4f}")
print(f"SmoothQuant   RMS误差 = {r1:.4f}")
print(f"激活峰值      8.0 -> {max(acts)/S:.1f}   (尖峰被压到可表示区间)")
```

```text
直接量化激活  RMS误差 = 0.0159
SmoothQuant   RMS误差 = 0.0053
激活峰值      8.0 -> 2.7   (尖峰被压到可表示区间)
```

**怎么看**：基线直接量化激活时 RMS 误差 0.0159；经 SmoothQuant 平移尖峰后降到 0.0053——**误差降到三分之一**。核心机制在输出第三行：激活峰值从 8.0 被压到 2.7，INT8 的步长不再被极端值绑架。这正是「SmoothQuant 把激活尖峰挪到权重 → INT8 几乎无损」的定量演示。

**锚点**：W8A8 一旦 SmoothQuant 校准过，INT8 推理质量与 FP16 差距普遍在 1-2%（行业常用语），本讲不虚报为 0；真实掉点幅度以 §7 三角评测为准。

**边界**：SmoothQuant 需要**离线校准**（用一小批真实数据统计激活分布）与`数学上等价但字节不同的两套权重`，它只能降激活量化的随机误差，不能弥补「激活本身信息被砍」的极限场景（如超长上下文热区）；另外权重放大后，INT4 一段会碰到「权重也超出 8 位可表示范围」的二次问题——所以 SmoothQuant 的舞台主要停在 W8A8。

## §5 INT4（W4A16）：GPTQ vs AWQ vs GGUF k-quants

**是什么**：INT4 把权重进一步压到 0.5 字节，显存为 INT8 一半、速度上限为 INT8 二倍。三种主流方案围绕「**校准之后哪些位要保、哪些位可以砍**」给出不同答案：

| 方案 | 全名/来源 | 核心思路 | 是否激活感知 | 典型场景 |
|------|-----------|----------|--------------|----------|
| **GPTQ** | 校准集后量化（层内近似重建） | 用一小批校准数据，逐层最小化「量化后输出与原始输出的差」重建权重 | ✗（只对权重） | 通用 CPU/GPU 推理（HF Transformers 直接加载，广泛） |
| **AWQ** | 激活感知量化（按通道保留重要权重） | 先量化，再根据**激活分布**找出「对输出影响大的通道」并把它们的权重乘一个保护因子（放大保留精度的关键通道） | ✓（依赖激活分布） | 质量敏感、激活分布脏或长尾的部署 |
| **GGUF k-quants** | llama.cpp 混合位宽量化 | 把权重矩阵按数值分布打散成不同位宽的块（q4_k/q5_k/q6_k），**大矩阵用低 bit、敏感小矩阵用高 bit**，混合保精度 | 混合位宽 | CPU/边缘设备、Mac/Metal、llama.cpp 生态 |

**机制表 · 三方案量化对象与保护策略**

| | GPTQ | AWQ | GGUF k-quants |
|---|---|---|---|
| 量化什么 | 权重 | 权重（按通道） | 权重（按块+矩阵敏感性） |
| 校准依赖 | 校准集 | 校准集 + 激活分布 | 校准集 |
| 保护策略 | 层内误差重建 | 关键通道放大保护 | 位宽分级（低 bit 给冗余块，高 bit 给敏感块） |
| 保的代价 | 全层平均 | 只保激活关键通道 | 每块独立 |
| 生态入口 | `transformers`/`auto-gptq` | `transformers`/`awq` | `llama.cpp quantize` / GGUF |

**为什么三个方案长期共存**：三者的侧重量不同——GPTQ 是「端到端最稳的通用默认」，AWQ 是「输入分布敏感时能比 GPTQ 再救 1-2%」，GGUF 是「我在 CPU/边缘设备上，混合位宽才是生存策略」。**不存在一个方案全面压过另外两个**，选择句柄在 §7 的工具链与评测。

**账四 · INT4 的三角（显存/速度/质量）**

```python
def wt_gib(n_b, bpp):
    return n_b * bpp * 1e9 / (2**30)

print("模型 | FP16   | INT8  | INT4 ")   # GiB
for n in (7, 14, 70, 671):
    print(f"{n}B | {wt_gib(n,2):>6.2f} | {wt_gib(n,1):>6.2f} | {wt_gib(n,0.5):>6.2f}")
```

```text
模型 | FP16   | INT8  | INT4 
7B |  13.04 |   6.52 |   3.26
14B |  26.08 |  13.04 |   6.52
70B | 130.39 |  65.19 |  32.60
671B | 1249.83 | 624.92 | 312.46
```

**怎么看**：一眼看清 INT4 的「显存账一半」——70B 从 FP16 130 GiB 降到 INT4 33 GiB，**单卡 A100/H100 40/80G 装得下**；671B 从 2499 GiB 降到 312 GiB，才能摊上多卡节点（实际还需 KV cache 与激活空间，见 §6）。速度参照 §3 的 4.0× 上限。

**边界**：INT4 掉点比 INT8 明显，**激活敏感的模型（长上下文、数学推理）差异被放大**；AWQ 是应对这种场景的「挽救手段」而非万能；GGUF 混合位宽在 llama.cpp 生态有独特价值，但跨成 `transformers` 原生格式需要转换。所有「质量几乎无损」必须以实际评测为准——回到 §7。

## §6 量化对象分清：weight-only / 激活量化 / KV Cache 量化

**是什么**：量化不止发生在权重上。一张图看三块收益来源：

| 量化对象 | 字节/元素 | 是否可 Appx 无损 | 收益最大场景 | 典型做法 |
|----------|-----------|------------------|--------------|----------|
| **weight-only**（最常用） | 0.5-1 | 是（校准+平滑） | 任何部署 | W4A16/W8A16/W8A8 |
| **激活量化**（难） | 1 字节/激活 | 需 SmoothQuant | 激活分布脏时 | W8A8 + SmoothQuant |
| **KV Cache 量化**（长上下文收益大） | 0.5-1/元素 | 是（KV 缓存单调好量化） | 超长上下文/多轮 | KV-INT8/FP8/FP4 |

**为什么 KV Cache 量化是「长上下文收益大」**：05-01 与 13-01 `kv_gib` 公式已算过——7B GQA 模型，从 seq 4k 拉到 128k，KV 内存从 0.5 GiB 涨到 16.0 GiB（GQA 已先省了 4×，但量化再省 2-4×）。KV 是「已生成的 token 的压缩表示」，它随上下文长度线性增长且**单调加剧**——长上下文时 KV 是显存增长的主要推手之一。而 KV 的结构（K/V 单独存、新 token 追加）天然好量化：K/V 数值值分布比激活/权重更稳定。

**账五 · KV Cache 量化的长上下文账（`kv_gib`）**

```python
def kv_gib(layers, kv, hdim, seq, batch, bpp):
    return 2 * layers * kv * hdim * seq * batch * bpp / (2**30)   # 13-01 原式

# 7B 结构：L32 = layers, GQA kv=8, hdim=128；比较 seq=32k/128k × fp16/fp8
for seq in (32768, 131072):
    row16 = kv_gib(32, 8, 128, seq, 1, 2)
    row8  = kv_gib(32, 8, 128, seq, 1, 1)
    print(f"kv=8@{seq//1024}k:  fp16 {row16:5.1f} GiB | fp8 {row8:5.1f} GiB | 省 {row16-row8:4.1f} GiB")
```

```text
kv=8@32k:  fp16   4.0 GiB | fp8   2.0 GiB | 省  2.0 GiB
kv=8@128k:  fp16  16.0 GiB | fp8   8.0 GiB | 省  8.0 GiB
```

**怎么看**：128k 上下文时 KV fp16 占 16.0 GiB（对 32GiB 不是小数），量化到 fp8 直接省出 8 GiB——比 weight-only 的对象加一块还多。上下文越长，KV 在显存预算里的占比越大，KV 量化的收益越显著。**这与 13-01 的 `account_a`（seq128k fp16 = 16.0 GiB、seq4k = 0.5 GiB）与 02-10 的 MHA/GQA 锚点（7B@32k MHA 16.0 / GQA 4.0 GiB）逐位一致。**

**边界**：KV 量化省的是 KV 自身，不省权重/激活；如果部署目标是「装下 128k 上下文的对话而非最大权重」，KV 量化与 weight-only 是**互相独立的优化**（可叠加）。量化 KV 的代价极低（K/V 数值分布稳定），通常安排在 weight-only 之后第二步。

## §7 工具链与纪律：五件套 + 量化后必跑的三角评测

**是什么**：工具链把「量化方案」落成可执行的命令：

| 工具 | 位宽 | 入口/命令 | 适用 |
|------|------|-----------|------|
| **bitsandbytes (NF4)** | 4bit | `torch` 层内 `bnb.nn.Linear4bit` | 单卡快速加载推理/微调（NF4 是 bitsandbytes 特有归一化格式） |
| **auto-gptq** | 4bit | `AutoGPTQForCausalLM.from_pretrained(quantize_config=...)` | GPTQ 方案落地 |
| **awq** | 4bit | `AWQForCausalLM.from_quantized(...)` | AWQ 方案落地 |
| **llama.cpp quantize** | 2-8bit 混合 | `llama-quantize model.gguf Q4_K_M` | CPU/边缘/GGUF |
| **vLLM 原生量化** | FP8/INT4 | `vllm serve xxx --quantization fp8` | 生产 GPU 推理（05-08 展开） |

**纪律，最重要的一句：量化之后必须跑评测对比，质量-速度-显存三角。** 量化改的不是「能不能装下」这一个指标，而是同时动了三个（质量 / 速度 / 显存），任何方案都必须三比齐看——这正是 05-02 与 11 章评测纪律的延续。

**账六 · 三角评测表格模板**

| 方案 | 显存(GiB) | 生成速度(tok/s) | 质量(相对 FP16, e.g. 基准集得分) | 是否可上线 |
|------|-----------|-----------------|-----------------------------------|------------|
| FP16 基线 | 130.39 | 14.3 | 100% | 需要 2 卡 |
| INT8 | 65.19 | 28.6 | ~99% | ✓ 单卡80G |
| INT4 (GPTQ) | 32.60 | 57.1 | ~97% | ✓ 40G |
| INT4 (AWQ) | 32.60 | 57.1 | ~98% | ✓ 40G |

**怎么看**：仅看「装得下吗」会漏掉「AWQ 比 GPTQ 慢但质量高 1%」这类关键差异。**纪律就是每做一个量化方案，都把它填进这张表**——选哪个的决定因子是「我的业务到底缺显存还是缺质量」，而不是「哪个方案听起来更无损」。

**边界**：本表速度列是 A100 带宽理论值（实际受显存带宽、前缀缓存命中、批大小、实现影响），质量列的真实数字必须由部署环境实测填写——**表是模板，不是结论**；不可跳过。

## §8 历史定位：PTQ 与 QAT，以及低位宽的地平线

**是什么**：量化方法论按「需不需要重新训练/校准」分成两条线：

| 路线 | 全称 | 是否需要训练 | 成本带 | 什么时候用 |
|------|------|--------------|--------|-----------|
| **PTQ** | 后训练量化（Post-Training Quantization） | 只要校准集（离线跑一次） | 低（一次性） | **主流**：绝大多数部署 |
| **QAT** | 量化感知训练（Quantization-Aware Training） | 需要把「量化误差」作为损失的一部分重训 | 高 | 少数为极致质量/极致压榨的场景 |

**为什么 PTQ 是主流、QAT 用得少**：PTQ 一个校准集 + 工具链一次跑完，质量损失对 INT8/INT4 够用（上三角表）；QAT 要重训模型、观察 2-3 个 epoch 的成本与调参风险，只有「INT4 还不满足质量红线」或「要压到 INT3/INT2」这种极端才会走。这条「反正 PTQ 够了，QAT 是别人的事」的经验分布，构成了本节的「历史定位」。

**低位宽的边界**：INT3/INT2（<0.5 字节）只出现在极限压缩场景（边缘端内存极限、ANSAF 压缩推理），因为它开始明显牺牲可表示的动态范围、且依赖激活/权重分布恰好可压——能维持质量的窗口很窄。**因此本讲定位在 FP8/INT8/INT4 三根主力档位，INT3 以下仅技术观察**。

## §10 常见坑

| 坑 | 现象 | 正确的做法 |
|----|------|-----------|
| 用 FP16 显存算 70B 是否装得下 | 说装不下就不装，错过 INT8/INT4 | 用 `wt_gib(70, 1)=65.19` 算 80G 单卡，明确成本收益 |
| 只比较显存省了多少 | 选了省最多的但质量掉一大截 | 三角一起比：质量-速度-显存（§7） |
| 对长上下文只量化权重 | KV 占大头，权重省了 KV 还爆 | 权重量化后第二步加 KV 量化（§6） |
| SmoothQuant 当成万能 | 对激活极端脏的场景仍掉点 | W8A8 必须离线校准；校准不完备要回退 |
| 直接用 `QAT` 解决所有 | 成本高、口径全变 | PTQ 先上，质量红线破了才考虑 QAT |
| FP8 当「无损」 | 某些层掉点没觉察 | 每个量化方案跑 §7 三角表 |
