## §1 五把尺的口径表：先分子分母，再说数字

05-09 把服务上线后，问的第一个问题永远是："它到底跑得怎么样？"——答案取决于**你选哪把尺、这把尺的分子分母是什么**。指标不去定义就先去测，等于拿一把没有刻度的尺子量布。先背下面这张口径表：

| 尺 | 口径（分子/分母） | 量的是什么 | 一句直觉 | 锚点 |
|---|---|---|---|---|
| **TTFT** | 首 token 时间（预填充完成到返回第一个 token）/单位=秒 | prefill（05-01 计算密集段）做得多快 | **长 prompt 由 prefill 决定**——prompt 越长 TTFT 越大，几乎是线性 | 06-01：流式 TTFT 0.850s→0.010s（85×）；13-03：TTFT 是 P50/P95 的构成分子 |
| **TPOT / ITL** | 每 token 时间（相邻 token 间隔）/ ITL=inter-token latency，单位=秒或 ms | decode（访存密集段）多快 | **≈200ms 是"流畅感"分界线**（> 300ms 人感知卡顿） | 本仓库约定：TPOT≈200ms 流畅线（§1.2） |
| **吞吐** | 单请求 tokens/s vs 整机输出 tokens/s 与 QPS（每秒请求数） | 整机单位时间吐出多少 token / 接住多少请求 | **看场景选尺**：单用户流应用看单请求，批处理/仪表盘看整机 | 13-03：串行 239.3→连续批 B=8 ≈1914（出厂）；05-06：静态 33 步 vs CB 25 步=1.32× |
| **GPU 利用率** | 计算利用率 / 显存利用率 / 带宽利用率三根 | 卡在干多少活 | **三根分开看**：计算塞满≠显存/带宽塞满 | 05-02：7B FP16≈13.04 GiB；05-04：KV 每 token≈267KB |
| **成本** | $/1M tokens（输入与输出分开计价） | 每百万 token 的账单 | **输入便宜输出贵**；cost 是"吞吐优化后的结果" | 13-08：$0.005/请求；本仓库：输出 token 22% 花 52% 钱（§5） |

### 1.1 为什么每一把尺都要"先分子分母再谈数字"

拿 TTFT 举例，最干净的教训来自 05-01 的推导：**prompt 很长时，TTFT 由 prefill 决定**——因为 prefill 是计算密集段（整段 prompt 一次性算完），decoder 是访存密集段（逐 token 吐）。同样是报"TTFT=2 秒"，**prompt 长度是 100 还是 10,000**，判断完全相反：短 prompt 2 秒=慢到爆；长 prompt 2 秒=相当快。所以：

> **口径自查三连**：① 这数字的分子分母是什么？② 在什么输入上测的（长度分布）？③ 是单次还是分布（P50/P95/P99）？——三个都不答的指标报告，直接扔掉。

同样的道理套到吞吐：**"吞吐 1000 tokens/s"** 要再问一句——是**单请求吐 1000**（流式应用体验好）还是**整机 128 并发一起吐 1000**（批处理吞吐）？前者延迟好，后者吞吐好，**两件事不矛盾，但数字不可比**。

### 1.2 TPOT/ITL 与"流畅线"

**TPOT**（time per output token，也是 ITL）是 decode 的每次吐 token 间隔。它的"流畅"不是绝对值，而是**跟人类可感知的节奏比**：一般认为 **≈200ms/token ≈ 5 tokens/s** 是流畅交流的底线，>300ms 明显拖沓。所以 TPOT 的意义不止在后台调优，它是**交互产品的 SLA**——你的聊天应用该承诺 P95 TPOT ≤ 200ms，而不是均值。

### 1.3 GPU 利用率要拆三根，不能只看"算力利用率"

一张卡"利用率 90%"听起来很满，但要看是**计算利用率**还是**显存/带宽利用率**——05-04 说过 decode 是访存密集，如果显存带宽是瓶颈，"算力利用率 90%"纯属假象（卡在等数据）。所以 query GPU 利用率记住：**三根分开报（compute / memory / bandwidth），报"利用率"必须带前缀**。

## §2 均值君陷阱：为什么"先口径后压测"——报分布不报均值

压测报告里最危险的词是"平均"。**均值是长了腿的统计量**：一个长尾请求就能把均值拉飞，而真实体验的大多数用户落在分布中间。这是 11-08 已经踩过的同一个坑（工程指标章），本篇是**同一口径的推理侧展开**——所以"先口径后压测"的第一条纪律就是：**永不报均值，报 P50/P95/P99**。

用一个具体的数字把"均值君陷阱"钉死（11-08 的延迟实测分布）：

| 统计量 | 数值 | 说明 |
|---|---|---|
| 均值 | 1.16 s | 被长尾拉高的"平均数" |
| **P50** | **0.93 s** | 一半请求比它快、一半比它慢 = 中位用户真实体验 |
| **P95** | **2.66 s** | 长尾里 5% 用户等的真实时间 |
| **P99** | **3.2 × P50** | 最惨 1% 用户 ≈ 三倍多中位体验 |

**为什么必须报分布**：均值 1.16s 看着还行，但你服务的是每个用户——中位用户 0.93s 没事，长尾 5% 用户 2.66s 已经在流失。**P95 ≫ P50 就是长尾信号**（§4 里这是定位故障方向的第一线索）。

> **报分布的口径自检**：报告里必须有 `P50` 和 `P95`（最好 `P99`），并且标注**在什么负载形状下测的**（并发数、输入长度分布的混合）。

## §3 压测方法：vLLM bench / locust / wrk，永远混合长度+混合并发

口径定好后才谈"怎么测"——压测工具三件套 + 一条最高纪律。

### 3.1 工具三件套（按形态对号入座）

| 形态 | 工具 | 用在哪 |
|---|---|---|
| vLLM 部署 | **vLLM 自带 bench**（`benchmark_serving.py`） | 起完 vLLM 就想知道"这配置能扛多少并发 / 快不快"，一条命令测 TTFT/TPOT/吞吐 |
| OpenAI 兼容端点（非 vLLM / 走网关） | **locust / wrk** | vLLM 之上套了网关（05-09 的 6 件套第 1 件），从 HTTP 层按真实用户形态压 |
| 端到端 / 多节点混合 | 网关 + locust 脚本组合 | 模拟真实用户：不同 prompt 长度、不同并发、随机间隔 |

### 3.2 最高纪律：**永远混合长度 + 混合并发，不单测一个 prompt**

这是本仓库压测的第一铁律。单测一个 prompt（比如人人都测的那句 "Hello"）会得到**三个假象**：
1. **TTFT 假象**：短 prompt 的 prefill 秒完，你根本没压到 prefill 的瓶颈（长 prompt 才是 TTFT 重灾区）；
2. **TPOT 假象**：单请求无并发，batch=1 的 decode 速度 != 满并发 batch 的；
3. **吞吐假象**：整机吞吐只有在"多个并发请求混着跑"时才有意义。

所以**压测负载必须是混合的**：输入长度覆盖 短/中/长（比如 32 / 512 / 2k / 8k），并发数从 1 爬到 64+，每个并发档都跑一段足够长的稳态时长（别测 10 秒，至少几十秒到一个分钟级窗口）。

### 3.3 压测矩阵长什么样（一个生产可复用的模板）

| 维度 | 怎么设 | 为什么 |
|---|---|---|
| 输入长度 | 32 / 512 / 2k / 8k 混合（比例按真实场景，如客服 20% / 30% / 40% / 10%） | TTFT 由最长 prompt 决定，测混合才能看真实 TTFT 分布 |
| 输出长度 | 64 / 256 / 1k 混合 | decode 时长决定 TPOT 采样窗口 |
| 并发 | 1 → 2 → 4 → 8 → 16 → 32 → 64 | 找"吞吐拐点"（再上并发吞吐不涨 = 到顶）；记录每档的 TTFT/TPOT/P50/P95 |
| 稳态时长 | 每档 ≥ 30s | 跳过 prefill 冷启动，进稳态 |

> **输出必须是每档的分布**（P50/P95/P99），不是平均。§2 的原因。

## §4 压测解读：症状 → 瓶颈 的四象限

测完拿到一组数，怎么判断机子问题出在哪？**四个症状各自映射一个神经的瓶颈**（这也是探针 `symptom()` 判定的逻辑骨架）：

| 症状 | 指向 | 说明 |
|---|---|---|
| **TTFT ↑** | **prefill 瓶颈** | 长 prompt 算不完 → prefill 太久。对策：分块 prefill（05-06 Chunked Prefill）、前缀缓存（05-04）、换更高算力卡 |
| **TPOT ↑** | **带宽或 batch 过大** | decode 是访存密集（05-01/05-04），带宽顶不住；或并发堆太高，batch 过大 → 每 token 排队变慢。对策：减并发、连续批调度、量化降带宽 |
| **GPU 利用率低** | **调度或搬运问题** | 卡没吃满，说明请求没对齐（05-06 CB 就是解决这个）、或数据搬运太慢（Prefill 与 Decode 抢带宽）。对策：看连续批是否开启、chunked prefill、请求调度 |
| **TTFT/TPOT 都正常但吞吐低** | **并发不足** | 单请求都挺快，但整机没在同时接多个请求。对策：加并发、加副本（05-09 L3 的 HPA 扩缩） |

**长尾信号在前**：先看 `P95 ≫ P50` 的比值，长尾明显说明负载形状或调度不均；长尾消失但中位也差，才轮到"卡不行/配置不行"。

> 一次压测只像一张 X 光片——**单张片不能确诊**。真实排障的套路是"定向复测"：怀疑 prefill 就单独加大输入长度档复测 TTFT；怀疑带宽就在满并发下单独看 TPOT。**先手续后工具**。

## §5 成本口径：推理成本 = 吞吐优化的结果

最后一把尺是钱。成本的口径有两笔，必须先拆开：

1. **输入 / 输出分开计价**：输出 token 计价比输入贵。锚点：**输出 token 只占 22%，却花掉 52% 的账单**——因为输出贵（而且输出长短不可控，是你模型吐的）。
2. **成本 = 吞吐优化的结果**：同样是 10 万请求，整机吞吐越高、每请求分到的 GPU 时间越短、单位成本越低。所以**优化吞吐 = 优化成本**，不是两个目标。13-03 的 $0.005/请求、13-08 的 token 计费都建立在这个口径上。

**成本三率（决策用）**：每请求成本（$/请求）、每百万 token 成本（$/1M tokens 输入/输出分开）、单位吞吐成本（$/k tokens/s）。上线定价和 ROI 决策拿这三率算，别拿"训练多贵"唬自己——推理成本才是长期运营账单。

## §6 与 11-08 打通：端到端延迟的同一把尺

11-08（工程指标章）在评测侧已经立了六把尺（延迟/吞吐/错误率/利用率/成本/QPS）。本篇是**推理侧的同一口径**——唯一需要新记的公式是把两站缝在一起的那条：

> **端到端延迟（用户体感） = TTFT + (N−1) × TPOT**

其中 N 是生成 token 数。这个公式把「评测章的总延迟」拆成「推理章的 TTFT + TPOT」，两站对同一把尺的不同切片：
- 11-08 测的是**整条链**（含网络、网关、前置处理）的 P50/P95 —— 那是用户体感；
- 本篇的 TTFT/TPOT 测的是**纯推理** —— 那是定位"到底哪一段慢"的显微镜。

**断链归因**：端到端 P95 慢了，先拆（TTFT 慢吗？→ prefill 段；TPOT 慢吗？→ decode 段；都不是？→ 网络/网关 13-03/13-08）。这就是"05-10 → 11-08"的钩子，也是后续 12-安全 里"定位慢请求"会反复用到的链条。

## §7 内嵌确定性判定：混合长度合成账 + 症状→瓶颈 5/5

本仓库的确定性探针（纯 stdlib · 零网络 · 零随机）。函数结构：`synth_load()` 按混合长度分布合成 N 个请求，每个请求按其输入长×prefill 每 token 耗时 + 输出长×decode 耗时，算出各自 TTFT/TPOT；从分布里取 P50/P95/P99（演示均值君陷阱：均值被长尾拉高）；`symptom()` 按四个症状判定瓶颈，5 个合成场景全覆盖 → 5/5。

```python
# ---------------- 混合长度合成账 + 症状→瓶颈判定（确定性探针） ----------------
# 纯 stdlib，零网络、零随机、零第三方依赖；三进程 stdout 字节全同。
import time, sys

_wall0 = time.time()

# 请求负载：混合长度分布（输入长度/输出长度 各异，模拟 §3 压测矩阵）
HISTORY = [  # (输入长, 输出长)  — 模拟 短/中/长 混合
    (32, 64), (512, 256), (512, 256), (2048, 1024), (8192, 512),
    (128, 32), (4096, 128), (1024, 2048), (32, 16), (512, 64),
    (2048, 256), (8192, 64), (128, 1024), (4096, 512), (32, 8),
]
PREFILL_PER = 0.00040   # 每输入 token 的 prefill 耗时（秒）— 模拟计算密集段
DECODE_PER  = 0.01000   # 每输出 token 的 decode 耗时（秒）— 模拟访存密集段

def synth_load():
    """按 §3 混合长度分布合成请求，逐请求算 TTFT/TPOT（先分子分母再谈数字）。"""
    rows = []
    for i, (n_in, n_out) in enumerate(HISTORY, 1):
        ttft  = n_in  * PREFILL_PER          # TTFT = 输入长 × prefill 每 token
        tpot  = DECODE_PER * (1 + n_out / 8192)  # TPOT：访存带宽随输出批次摊薄，长输出排队略涨每 token 间隔
        rows.append((i, n_in, n_out, ttft, tpot))
    return rows

def pct(times, p):
    """百分位数（分布口径浮现）。"""
    s = sorted(times)
    k = max(0, min(len(s) - 1, int(len(s) * p)))
    return s[k], s[max(0, len(s) - 1 - int(len(s) * p))]  # P100-p 对照列

rows  = synth_load()
ttfts = sorted(r[3] for r in rows)
tpots = sorted(r[4] for r in rows)
mean_ttft = sum(r[3] for r in rows) / len(rows)
p50_ttft = ttfts[len(ttfts)//2]
p95_ttft = sorted(ttfts)[int(len(ttfts)*0.95)]

A = ["== A · 混合长度合成账（TTFT 分布，均值君陷阱演示） ==",
     "  请求 |  输入/输出长 | TTFT(s) | TPOT(s)"]
for i, n_in, n_out, ttft, tpot in rows:
    A.append(f"  [{i:>2}] {n_in:>5} × {n_out:>5} | {ttft:7.4f} | {tpot:8.4f}")
A.append(f"  ---")
A.append(f"  TTFT 均值 = {mean_ttft:.4f} s      （被长尾拽高的“平均”）")
A.append(f"  TTFT P50  = {p50_ttft:.4f} s      （中位用户真实体感）")
A.append(f"  TTFT P95  = {p95_ttft:.4f} s      （长尾真实） →  P95/P50 = {p95_ttft/p50_ttft:.2f}")
A.append(f"  分布口径：均值君陷阱——报分布（P50/P95）不报均值。")

def symptom(sign):
    """症状 → 瓶颈 判定（§4 四象限）。sign: (ttft_high, tpot_high, gpu_util_low, throughput_low)."""
    ttft_h, tpot_h, gpu_low, thru_low = sign
    if ttft_h and tpot_h:
        return "prefill 与 decode 双瓶颈（输入超长 + 带宽顶不住）"
    if ttft_h:
        return "prefill 瓶颈（长 prompt 算不完 → 分块 prefill / 前缀缓存）"
    if tpot_h:
        return "decode 带宽或 batch 过大（访存密集段顶不住 → 减并发 / 量化降带宽）"
    if gpu_low:
        return "调度或搬运问题（请求没对齐 → 连续批 / chunked prefill）"
    if not thru_low:
```

## §常见坑（指标与压测视角）

1. **单测一个 prompt 就当压测结论**：那句 "Hello" 的 TTFT 和 8k 输入的完全两码事。压测必须混合长度+混合并发（§3.2）。
2. **报均值当成绩**：均值 1.16s 看起来很行，P95 2.66s 才是长尾用户真实体验——这就是均值君陷阱（§2）。
3. **看 TTFT 不看 prompt 长度**：同样的 TTFT，800 输入和 8000 输入意义相反（§1 口径三连）。
4. **GPU 利用率只看"算力"一根**：decode 是访存密集，带宽才是瓶颈时算力利用率是假数据（§1.3）。
5. **吞吐数字不分"单请求 vs 整机"**：流式 App 要单请求 tokens/s，批处理要整机总和——两把尺不可比（§1.1）。
6. **成本只看总账单不拆输入/输出**：输出 token 22% 花 52% 钱，不拆开就没法优化单价（§5）。
