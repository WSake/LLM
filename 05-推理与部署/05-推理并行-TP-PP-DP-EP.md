## §1 并行四式速查（推理侧）

四式是训练课 04-07 就有的，但推理侧每式的"为什么用"不完全同——训练要的是**算得快**，推理要的是**塞得下 + 接得住**。

| 式 | 切什么 | 每卡发生什么通信 | 推理侧用它解决 | 代价 |
|---|---|---|---|---|
| **TP** | 矩阵层内切：权重/激活按列按行分到同一机器内多卡 | 每层前向 **2 次 all-reduce**（每 token 每层），**要求 NVLink 级快互联**（13-02 账A：NVLink 450GB/s vs PCIe 16GB/s = 28.1×） | 单卡装不下大模型权重（70B fp16 130.39 GiB > 单卡 80G）| 通信量大（逐层 160 次阻塞）→ 不能跨机 |
| **PP** | 层切：把 transformer 层切成 N 段，每卡一段 | 只在段边界传一次激活 P2P（70B 每微批约 67 MB，13-02 账C）| 跨机装超大模型（16 卡以上、单机装不下时）| 流水线延迟升（N 段串行，气泡/首 token 慢）|
| **DP** | 副本切：N 个副本各接一批请求，权重各自全量 | 推理无梯度 → **副本间零通信** | 吞吐不够：单副本 64 并发 → 2 副本 128 → 4 副本 256 线性扩 | 显存按副本数翻倍（权重×副本数）|
| **EP** | 专家分卡：MoE 的 FFN 专家拆到多张卡 | 每层 **all-to-all**（top-2 专家路由，30.5 GiB/层/步是训练口径，04-07）| MoE 推理必备：全部专家塞一张卡放不下，且只激活 top-k | all-to-all 是最贵通信点 → 绑定机内/窄集群 |

**一句话速查**：TP 是"把一个大矩阵拆平摊到 8 张卡"，PP 是"把一串层按段分家"，DP 是"整模型复制 N 份各忙各的"，EP 是"把 MoE 的专家当可插拔部件拆出去"。

### 逐式展开

**TP（张量并行）**——把**一个 transformer 层内部**的注意力/FFN 大矩阵，按列/行切成 TP 份，每卡各执一半，前向逐层完成后做一次 all-reduce 把两张图拼回。意味着一句话进网络，**每层都要跨卡交换一次**，所以 TP 严格锁在"机内"（NVLink）：H100 机内 all-reduce 45 例用 450GB/s，得 TP 锁机内 9×；一旦跨机走 PCIe/IB，通信成本直接差一个量级（28.1×，13-02 账A）。**结论：70B 级做 8 卡 TP 是标准姿势（130.39 GiB ÷ 8 = 16.30 GiB/卡），TP 值一般不超机内卡数。**

**PP（流水线并行）**——把 transformer 的 N 层按序号切成 P 段，每卡拿一段完整的前向。段内包着全部权重不拆矩阵，段边界只透传隐藏状态（13-02 账C：`PP_ACT = 8192*4096*1*2 = 67 MB` 每微批）。PP 的价值在**跨机**：16 张卡两台机器时，TP 撑不起（TP16 通信纵穿全网卡），PP 调 2 个段即可。代价是**串行气泡**：同一时刻只有一段在工作，前段等后段，算子吞吐因为你把一批拆成正向/返握而掉。这句话在推理部署里很重要——所以 PP 只在单机装不下的超大模型上出现。

**DP（数据并行）**——最简单也最常用：整模型复制 N 份，每份自己接请求，副本之间**零通信**（推理没有梯度要同步）。这是 serving 吞吐的主引擎：单副本 64 并发 → 2 副本 128 → 4 副本 256，**线性扩展**，且无任何通信开销（账 A 下节验）。唯一代价：权重显存 × N。**结论：几乎每个生产推理服务都至少是 DP=2 ∘ 4，哪怕模型单卡放得下。**（05-06 调度会加"在线 PP × DP"的排队账。）

**EP（专家并行）**——MoE 专用。MoE 的权重主体在几百个 FFN 专家里，一次前向只激活 top-k 个（k=2 很常见）；EP 把专家拆到多卡，每个 token 在每一层都要把激活发去"它的 top-2 专家在的那张卡"，即 **all-to-all**。EP 是 MoE 推理**跑得起来**的前提：671B 级 MoE 的全部专家塞一张 80G 放不下，必须拆。代价是最贵的通信点：all-to-all 是跨卡 scatter-gather，比 TP 的 2 次 all-reduce 还贵 → **EP 也要尽量锁机内**（13-02 把 MoE 列为"机内+窄集群"档）。

> **边界澄清**：DP 和 TP 都会出现"权重切分"，但一个是"整模型复制给多个副本"、一个是"一个副本的权重切成多份"。物理上一卡可以同时是 DP 的一个副本、又拿 TP=2 的一半权重——这就是 §3 的组合。先分清"副本"和"分片"，再谈组合。

## §2 为什么推理并行比训练简单：只有前向，没有梯度通信

训练的反向传播要给每一层算梯度，跨卡同步梯度（all-reduce），这一步是训练并行通信量的主量级（13-02 账B：70B fp32 每步梯度 280GB，N=8 机内 ring all-reduce 1.09s，通信占训练步时间的 62%）。推理**没有反向，就没有梯度**——于是：

| 训练（04-07 账，锚） | 推理（本篇） |
|---|---|
| 每步 forward + backward，反向要跨卡 all-reduce 梯度（70B 280GB/步）| 只有 forward，无梯度可同步 |
| DP 每步必等待梯度同步才能进入下一反摊 | DP 副本间零通信，互不等待 |
| TP 每层 fwd 2 次 + bwd 再次 all-reduce（共 4 次/层）| TP 只需 fwd 的 2 次/层 |
| PP 除 forward 边界外还要反传段间梯度 | PP 只有 forward 段间激活 |

**推论（对部署有实际意义的三件）**：
1. **DP 的"线性扩展"在推理是近乎免费的**——训练 DP 要卡在梯度同步的圆圈上，推理 DP 每副本完全独立，N 副本就是 N 个服务。
2. **同是 TP，推理的通信量只有训练的一半**（fwd 2 次 vs fwd+bwd 4 次），所以 13-02 的 28.1× / 9× / 26× 在推理侧还偏保守——那本是训练账，通信占比在推理会更小。
3. **组合的复杂度也低一档**：训练要协调 PP 气泡+梯度窗口+ZeRO 分片，推理只需考虑"塞不塞得下 + 接不接得住"，决策变量少两个。

> 一句话：**推理并行的复杂度 = 训练并行砍掉反向那一半。** 训练最难的那部分（梯度通信的拓扑与占比）在推理根本不存在。

## §3 组合规则：TP×DP 是 serving 最常见组合

单式不常用，生产里都是组合。serving 场景的组合谱系：

| 组合 | 怎么组合 | 什么时候是它 |
|---|---|---|
| **DP（独）** | 单卡装得下的模型 × N 副本 | 7B 及以下、吞吐不够。最常见起点 |
| **TP×DP** | 机内 TP 摊大模型（70B→TP8）再复制副本接并发 | **70B 级 serving 的默认姿势**：TP8×DP4 = 32 卡，串行 130.39 GiB → 每副本 16.30 GiB，同时吞吐 4× |
| **TP×PP×DP** | 机内 TP + 跨机 PP + 副本 DP | 1T 级稠密、单机装不下必须跨机 |
| **EP×DP（+TP）** | MoE 专家拆卡 + 副本 | MoE 唯一解：671B 级必须 EP，TP/PP 是锦上添花 |

**为什么 serving 不追求 PP？** 因为 PP 的服务端收益几乎为负：它省显存、但引入串行气泡（首 token 时间 = 流水线长度 × 单段延迟），在"服务不是训练"的语境里，你宁可加 DP 副本赚并发，也不想付气泡税。PP 只在**单机物理摆不下** 30 亿卡时出手。

**1T 级才动 TP×PP×EP**：130 GiB（70B）在 8 卡内已解；只有 1T 稠密（权重 ≈ 1.9 TiB，账 B 场景 5）才需要 TP 摊单层 + PP 跨机 + DP 副本三层组合。至于 MoE——**EP 不是可选项是必选项**，其余组合都只能衬它。

> **账 A · 组合并发上限**（内嵌代码 `decide()` + 简化账，锚 05-03/13-02 同式）：TP×DP 到底能接多少并发？见 §6 的确定性代码，5 场景判定 5/5 PASS；这里先给结论数字：**70B 单副本 TP8、每副本有效并发 64 → DP2 = 128、DP4 = 256**（纯线性，忽略调度，见 §6 代码输出）。

## §4 盘式选择：从"装不下"和"不够快"两头排

决策路径（内嵌代码 `decide()` 同逻辑，5 场景见 §6）：

```
模型权重能塞进单卡吗（权重 ×1.1 余量 ≤ 卡显存）？
├─ 是 → 吞吐够吗？
│   ├─ 够 → 单副本，直接上
│   └─ 不够 → DP 副本线性扩（7B 13.04 GiB→40G 卡：DP）
└─ 否 → 是 MoE 吗？
    ├─ 是 → EP（专家分卡）+ TP 锁机内（671B 级）
    └─ 否 → 机内有 NVLink 吗？
        ├─ 否 → 别上 TP：DP 副本 + 离线分片（PCIe 吃 TP 通信，13-02 账A 28.1×）
        └─ 是 → 单机吗？
            ├─ 是 → TP8 锁机内（70B 8×H100，标准姿势）
            └─ 否 → 机内 TP × 跨机 DP（1T 级再叠加 PP）
```

四句口诀：
- **塞不下 → TP**（先想机内）；
- **够用但不够快 → DP**（副本线性扩，最省事的增长）；
- **MoE → EP**（不是优化是必要条件）；
- **超大 + 跨机 → 分层组合**（TP×PP×DP 或 EP×DP）。

## §5 边界与坑：TP 没有好互联会被通信吃掉

| # | 坑 | 实例/数值（锚） | 规则 |
|---|---|---|---|
| 1 | **TP 跨机** | 逐层 all-reduce 通信量在 PCIe 上是 NVLink 的 28.1×（13-02 账A），TP16 跨两台机器，通信占比会从"算完等通信"变成"一直在通信" | TP 值 ≤ 机内卡数；跨机改 PP/DP |
| 2 | **PP 当默认，白付气泡** | PP 每微批 67 MB 边界激活不贵，但流水线首 token 串行延迟长 | 只有单机摆不下大模型才 PP；serving 优先 TP×DP |
| 3 | **EP 的 all-to-all 被低估** | MoE 每层 all-to-all 是最贵点，这不只是训练侧（04-07 账 30.5 GiB/层/步的训练口径）| 尽量锁机内/窄集群部署 |
| 4 | **DP 显存乘以副本数** | 权重 130.39 GiB 的 70B，DP4 就是 521.56 GiB 权重（不含 KV）| 显存预算按副本数核算（§6 账 A 有比例）|
| 5 | **"TP 一定比 DP 好"的迷思** | 单卡放得下的模型，TP 反而增加通信、减不掉显存——属于"没病找病" | 先问"塞得下吗"，塞得下就只考虑 DP 扩并发 |

边界结论一句话：**TP 是"好邻居"——必须住在同一个机箱里；PP 是"唠叨的室友"——省显存、费时间；DP 是"多个家"——最贵但最自由；EP 是"专业库房"——MoE 专用，串在核心链上。**

## §6 关联代码 · 简化账 + 四式选择判定（确定性，可复跑）

> 与 13-02 `train_infra_demo.py` 同公式链、只引不重测；本段代码为 05 章站内简化账，纯 stdlib。三并发进程 stdout 字节全同，且 LF 归一化后与下方 text 块逐字节一致（三进程原始 md5 `073e47d2afe08f4d1fdf173943573254`）。

```python
# -*- coding: utf-8 -*-
"""05-05 推理并行 · 简化账 + 四式判定（纯 stdlib · 零网络 · 零随机）"""

GIB = 2 ** 30

def weights_gib(params_b, bpp=2.0):
    return params_b * bpp / GIB

def tp_per_card(total_gib, tp):
    return total_gib / tp

def kv_per_token_gib(layers, kv_heads, hdim, bpp=2):
    return 2 * layers * kv_heads * hdim * bpp / GIB

def kv_seq_gib(ptok, seq):
    return ptok * seq

def dp_concurrency(per_replica, dp):
    return per_replica * dp

A = []
A.append("== A · 推理并行简化账（与 13-02/05-03 同公式链，只引不重测除本算） ==")
w70 = weights_gib(70e9)
A.append(f"  70B fp16 权重 = {w70:.2f} GiB；TP8 每卡 = {tp_per_card(w70, 8):.2f} GiB"
         f"（H100 80G 可装）；TP4 = {tp_per_card(w70, 4):.2f} GiB")
ptok = kv_per_token_gib(32, 8, 128)
A.append(f"  KV 每 token（32层×8kv头×128维 fp16）= {ptok * GIB:.0f} B；"
         f"32k 序列 = {kv_seq_gib(ptok, 32768):.2f} GiB（对账 05-03：4.0 GiB）")
A.append(f"  DP：单副本 64 并发 × 2 副本 = {dp_concurrency(64, 2)} 总并发；"
         f"× 4 副本 = {dp_concurrency(64, 4)}（吞吐线性上界，忽略调度开销）")

def decide(is_moe, weights_g, per_gpu_g, has_nvlink, machines, throughput_limited):
    """推理侧并行四式盘式选择。
    is_moe: 是否 MoE；weights_g: 权重 GiB；per_gpu_g: 单卡显存 GiB；
    has_nvlink: 机内是否快互联；machines: 机器数；throughput_limited: 是否吞吐不够。
    """
    tp_needed = weights_g * 1.10 > per_gpu_g     # 权重×1.1 余量(KV+激活) 是否超出单卡
    if is_moe:
        return "EP（专家分卡）+ TP 锁机内"
    if not tp_needed:
        return "DP（多副本，吞吐线性扩）" if throughput_limited else "单卡可装：先扩 DP 副本接并发"
    if not has_nvlink:
        return "别上 TP：DP 副本 + 离线分片（PCIe 会吃 TP 通信，13-02 账 A 28.1×）"
    if machines == 1:
        return "TP8 锁机内（8 卡 NVLink）"
    return "机内 TP × 跨机 DP（1T 级再加 PP）"

scenes = [
    ("7B fp16 13.04 GiB 进 40G 单卡，吞吐不够", False, 13.04, 40.0, False, 1, True),
    ("70B fp16 130.38 GiB，单机 8×H100(80G·NVLink)", False, 130.38, 80.0, True, 1, False),
    ("671B MoE 风（激活~37B，专家分卡）", True, 671 * 2 * 1.5 * 2, 80.0, True, 4, False),
    ("4×4090 24G 无 NVLink 跑 70B", False, 130.38, 24.0, False, 1, False),
    ("1T 级稠密·多机 64 卡", False, 1907.35, 80.0, True, 8, False),
]

B = ["== B · 推理并行四式选择判定（5 场景） =="]
exp = [
    "DP（多副本，吞吐线性扩）",
    "TP8 锁机内（8 卡 NVLink）",
    "EP（专家分卡）+ TP 锁机内",
    "别上 TP：DP 副本 + 离线分片（PCIe 会吃 TP 通信，13-02 账 A 28.1×）",
    "机内 TP × 跨机 DP（1T 级再加 PP）",
]
flds = ["is_moe", "weights_g", "per_gpu_g", "has_nvlink", "machines", "throughput_limited"]
ok = 0
for i, (name, *vals) in enumerate(scenes, 1):
    got = decide(**dict(zip(flds, vals)))
    hit = got == exp[i - 1]
    ok += hit
    B.append(f"  [{i}] {name} -> {got} = " + ("PASS" if hit else f"FAIL(期望{exp[i - 1]})"))
B.append(f"  四式判定：{ok}/5 PASS")

print("\n".join(A))
print()
print("\n".join(B))
```

## §常见坑（部署视角）

1. **"先 TP 后 DP"的顺序反了**：先确认塞得下（显存），再看并发（吞吐）；两个都靠后的是 PP。
2. **TP 里用错互联**：70B 放两台机的 8 卡 → 必须拆 TP=4×2，否则 TP8 是跨机（28.1× 通信），这是付费踩坑区。
3. **把训练侧通信账直接套推理**：训练 bwd 是 2 倍通信量（04-07 账），推理 TP 只要 fwd 段——别拿"训练 4 次/层"吓自己。
4. **MoE 只在"卡里放不下"时上 EP**：稠密模型 + EP 毫无收益，全专家单卡放得下就 DP。
5. **DP 不增加单请求延迟、但增加显存**：并发翻倍、钱翻倍（权重复制×副本），预算要按副本数算。
