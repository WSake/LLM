## 1. 两阶段本质：Prefill vs Decode

**是什么**：LLM 的每一次生成都分两段。**Prefill（预填充）** 阶段，模型拿到用户**全部的输入 prompt**，一次性前向传播算完，为每个输入位置产出 key/value；**Decode（解码）** 阶段，模型从最后一个 token 出发，**一次只吐一个新 token**，把它拼进序列再继续——直到遇到停止条件。一次完整的回答 = **1 次 Prefill + N 次 Decode**（N = 输出长度）。

**为什么会出现**：因为自回归天生逐位。LLM 的训练目标就是"根据前面所有字预测下一个字"，这个约束让"读完一整段输入"（可以并行）和"吐出一个个输出"（只能串行）在结构上就是两种形态。要省的东西也完全不同——前者希望算得快，后者希望**读内存快**。

**机制（一句话表，两段三问各答一遍）**：

| 维度 | Prefill（处理输入） | Decode（生成输出） |
|---|---|---|
| 做什么 | 一次性处理全部输入 token | 逐 token 生成 |
| 计算形态 | **计算密集**：一次过完整矩阵乘法，吞吐大 | **访存密集**：每步只算 1 个新 token，但要把权重全读一遍 |
| 主导资源 | 算力（FLOPs） | **显存带宽**（后面 §2 算账） |
| KV Cache | 不需要（每 token 只要这段输入自己） | **专治 decode**：把已算的 k/v 缓存起来，避免全文重算 |
| 优化方向 | 矩阵乘法提速、prefill 分组、chunked prefill | 显存带宽提速、权重量化、batch（吞吐）、投机解码 |

**为什么优化要分开做**：因为"慢在哪"根本不同。Prefill 慢在矩阵算不过来 = 你多堆算力（更大矩阵、多卡）就快；Decode 慢在**内存搬不动** = 你多上算力没用，得降权重大小、提带宽。同一个引擎里这两个阶段要配**不同的优化手段、不同的调度策略、甚至不同形状的 GPU 规格**。§2 把二者各算一笔账，数字会直接告诉你在真正的 GPU 上哪段是真瓶颈。

### 1.1 两段各算一笔账（§5.0"能算"主干）

**Decode 的账（带宽限）**：decode 每吐 1 个 token，都要把模型全部权重从显存读一遍……每一层都要流式读回权重做矩阵乘，而输出只有 1 个 token。权重是**被重复读、而不是被算完的**。所以 decode 的下限是：**一次要读完多少 GB ÷ 每秒能读多少 GB**。

一个 7B FP16 模型权重 ≈ 14 GB（13-01 账 A：13.04 GiB）。设带宽为 `B`（GB/s），decode 最快 ≈ `B ÷ 14GB` token/s。

| 卡 | 显存带宽（TB/s） | 7B decode 理论上限（tok/s） | 计算 |
|---|---|---|---|
| A100 | 2.00 | **143** | 2.0×10⁶MB/s ÷ 14000MB |
| H100 | 3.35 | **239** | 3.35×10⁶ ÷ 14000 |
| H200 | 4.80 | **343** | 4.80×10⁶ ÷ 14000 |
| B200 | 8.00 | **571** | 8.00×10⁶ ÷ 14000 |

（`tokens/s ≈ 带宽×1e12 ÷ (参数量B × 精度字节 × 1e9)`，与 13-01 同式——权重是分母，模型大 10× → 吞吐掉 10×。）

**Prefill 的账（算力限）**：prefill 算的是矩阵乘法，峰值 = 算力（TFLOPS）。7B 每个 token 约 2×7×10⁹ FLOP：

| 项 | 值 |
|---|---|
| H100 FP16 算力 | 989 TFLOPS |
| 7B prefill 算力上限 | ≈ 70.6k token/s（989×10¹² ÷ 14×10⁹） |
| 7B decode 带宽上限 | ≈ 239 token/s（H100 带宽 3.35 TB/s） |
| 算力/带宽 富余 | **295×** |

**结论一句话：单机单卡跑 7B，`算力上限 70.6k tok/s` 远高于 `带宽上限 239 tok/s` → Decode 阶段是被显存带宽卡死的，不是算力卡死的。**（这就是为什么 decode 优化≠加算力，而是省权重、提带宽、加 batch——后面 05-03 量化、05-06 batching 都在打这个）。

**边界（两阶段认知怎么落地）**：两阶段的划分对整个服务层的每一项优化都是"第一前提"——**你优化的那一步，是 in prefill 还是 in decode？**把给 decode 的手段（比如加 batch 提吞吐）用在 prefill 上不生效；把给 prefill 的手段（矩阵切分）用在 decode 上被带宽吃掉。**先判阶段，再判瓶颈，再下手**，是本章所有各篇的读法。

📎 **关联代码**（与 13-01 `code/notebooks/_tools/gpu_account_demo.py` 账 B 共用公式）——两阶段各自算力/带宽上限：

```python
# 复现（只摘主干，与 13-01 同式）
DECODE_BW = [("A100", 2.00), ("H100", 3.35), ("H200", 4.80), ("B200", 8.00)]  # TB/s
def decode_tok_s(bw, n_b=7, bpp=2):
    return bw * 1e12 / (n_b * bpp * 1e9)   # 带宽限 tok/s
def prefill_tok_s(tflops=989, n_b=7):
    return tflops * 1e12 / (2 * n_b * 1e9)  # 算力限 tok/s（每 token ≈ 2×参数量 FLOP）

print({n: round(decode_tok_s(b)) for n, b in DECODE_BW})
# {'A100': 143, 'H100': 239, 'H200': 343, 'B200': 571}
print(round(prefill_tok_s() / decode_tok_s(3.35)))
# 295   ← 算力上限 vs 带宽上限的富余倍数
```
```text
PASS 1.1-1.4 四卡带宽限 143/239/343/571 tok/s 全对（与 13-01 账 B 同式同数）
PASS 1.5-1.6 算力限 70.6k vs 带宽限 239 → 富余 295×（带宽先到瓶颈）
PASS 1.7-1.8 两阶段判定：prefill=计算密集 / decode=访存密集
```
**怎么看**：`PASS 1.1–1.6` 出自 13-01 `gpu_account_demo.py` 的账 B（A100 143 / H100 239 / H200 343 / B200 571，算力富余 295×），本篇**只引不重测**（同一公式同一台机器同一结果）。你换一台真 GPU 压测时，这句是你第一步读卡的口径：**先读带宽，再读算力，先到瓶颈的那个说了算**。

## 2. 三大瓶颈：显存容量、显存带宽、调度效率

**是什么**：地图 §5.0 把"推理为什么贵"归结为三个不同性质的瓶颈——**显存容量**（东西装不装得下）、**显存带宽**（东西读得快不快）、**调度效率**（一堆请求放一起怎么不互相抢）。它们不是三选一，而是三件事；很多项目"看起来很慢"是三个瓶颈叠在一起，要先分开判再各打各的。

### 2.1 瓶颈一：显存容量（装不装得下）

**是什么**：模型能跑起来的第一前提是权重 + KV Cache 放得进显存。

**机制（核心记忆抓手）**：显存容量 = **权重**（固定，模型参数 × 精度字节）+ **KV Cache**（随 seq 和 batch 增长）。KV Cache 的公式与 02-10 完全同式（`2 × 层数 × KV头数 × 头维度 × seq × batch × 字节`）；关键看起来像"增长最快的那头"——**KV Cache 随 seq 线性涨、随 batch 乘着涨**，是长上下文时代显存的第二只猛虎。

**一句话的账**：7B FP16 权重 ≈ 14GB（13-01 账 A 同式，占满一张 A100 80G 的 17%）；KV Cache 在长上下文下可以吃掉可比甚至更大的份额——02-10 探针的实例：**LLaMA-2-7B MHA 32k 的 KV = 16GB，占到（权重+KV）的 53%**；GQA-8 降到 22%，这就把"为什么新模型全上 GQA"这件事从架构侧解释透了。

**边界**：显存容量是"花钱和安排"的问题，不是"性能上限"的问题——装得下之后，瓶颈才轮到带宽和调度。很多人两个瓶颈混着谈，先会算容量账，才能分离出后面的真瓶颈。

### 2.2 瓶颈二：显存带宽（decode 读权重"快不过来"）

**是什么**：装得下 ≠ 读得快。**decode 每吐一个 token 都要把权重全读一遍**，读的速度（带宽）决定生成极限。

**机制（承接 §1 账）**：7B FP16 = 14GB，它在 A100（2TB/s）上 decode 上限 = 14GB / 2TB/s ≈ **143 tok/s**；H100（3.35TB/s）= 239，H200 = 343，B200 = 571。**你看这逐卡翻倍，都是带宽在翻，跟算力没关系**——这正是带宽瓶颈的样子。而 §1 也算过：**算力上限 70.6k tok/s vs 带宽上限 239 tok/s，富余 295×**，在典型 7B 上带宽永远先到瓶颈。所以 decode 阶段优化 = 降权重量（量化）、降访存次数（投机解码、KV 压缩）、或加并发 batch 摊薄每个 token 的带宽成本（05-06）。

**边界**：带宽瓶颈不是绝对的——**模型越小、batch 越大，算力上限与带宽上限的交点会被逼近甚至反超**。7B 单卡 batch=1 是带宽瓶颈；把小模型排满 batch、做成吞吐优先时，算力也会变成决定项。判断口令还是 §1 那两句：**先判阶段，再找先到瓶颈的那个。**

### 2.3 瓶颈三：调度效率（请求一多就抢）

**是什么**：单请求跑多快之外，服务层真正面对的是**一堆请求同时进来**。调度效率 = 同一批算力能同时服务多少个请求、每个请求的延迟/吞吐怎么平衡。co 瓶颈在存量和带宽之外独立存在——**空间与时间都够，排班排不好照样吞吐上不去**。

**机制（三个调度把子）**：现代 serving 引擎做三件事——① **Batching**：多个请求拼成一个大 batch 一起算，把带宽成本摊薄（把"每 token 读一次权重"摊给更多 token，吞吐翻几倍）；② **Continuous Batching / 动态批**：请求随到随进、token 算完即出，而不是"凑满一批才跑"（2022 年的连续批把吞吐提升数倍，是 Serving 的基石）；③ **优先级/配额**：敏感请求（交互）与非敏感（批处理）分队列调度，谁也不饿死。这三件事地图 §5.5 会逐个展开，本篇只建立"调度是一个独立瓶颈"的认知。

**边界**：调度效率的收益上限**被前两个瓶颈锁死**——带宽不动，把 batch 做得再大，吞吐上限也就卡在带宽限制那儿。所以三瓶颈的正确打开方式是**加法题**：容量不够→扩容/量化，带宽不够→量化/换卡/batch，调度不好→调引擎。**先分瓶颈再对症，比盲目上 vLLM 更接近真因**（这也呼应 11-01 先讲口径再讲数字）。

### 2.4 三瓶颈怎么判断（决策三步）

| 症状 | 判瓶颈 | 第一对策 |
|---|---|---|
| OOM / 装不进 | 显存容量 | 量化 / 换大卡 / KV 压缩（05-03/05-04） |
| 单请求 tok/s 上不去 | 显存带宽 | 量化省权重 / 提带宽 / 加 batch（05-03/05-06） |
| 并发一多就排队/超时 | 调度效率 | Continuous Batching / 配额 / 扩副本（05-06/13-03） |

**边界（不是三选一）**：真实系统通常三个症状一起出现，判断的目的是**找先发生的那个**（容量），然后找最贵的那个（带宽），再谈调度。别把 OOM 归到调度头上去了换个 scheduler——那解决不了装不下的问题。

## 3. 一条主链路：7 环全景、各篇逐环展开

**是什么**：地图 §5.0 把"让推理变快变便宜"的全部手段归成一条主线——**权重格式 → 加载/量化 → 显存布局 → 调度 batching → 解码优化 → 多卡并行 → 服务层**。它不只是一张清单，而是一条**流水线**：每一环的产物/约束是下一环的前提，哪一环是限制的，瓶颈就露在哪。

**机制（七环表 + 在 5 章的位置）**：

| 环 | 干什么 | 在哪一篇展开 |
|---|---|---|
| ① 权重格式 | 模型以什么格式存在磁盘/内存（safetensors / GGUF / engine） | 05-02 模型加载与权重格式 |
| ② 加载/量化 | 权重怎么进显存、要不要压精度（FP16→FP8→INT4） | 05-02、05-03 精度与量化 |
| ③ 显存布局 | 权重和 KV 怎么摆，让带宽够、碎片少 | 05-04 KV-Cache 系统级优化 |
| ④ 调度 batching | 请求怎么拼批、怎么动态进出 | 05-06 Serving 核心技术（Continuous Batching） |
| ⑤ 解码优化 | 逐 token 阶段怎么省带宽/少算（投机解码、分页 KV、chunked prefill） | 05-06、05-07 投机解码与 PD 分离 |
| ⑥ 多卡并行 | 一张装不下→TP/DP/EP 分卡跑（怎么通信、怎么平衡吞吐） | 05-05 推理并行 |
| ⑦ 服务层 | 网关 / 配额 / 灰度 / 计费，把模型变成可用服务 | 05-08 框架选型、05-09 部署形态、05-10 指标 |

**为什么是一条"链"**：因为**改前面会连锁改后面**——量化（②）改小权重大小，才让单卡装得下（③）、decode 读得快（带宽账，§2.2）、batch 能开更大（④）……而调度（④）要反过来问：我优化的这一步，是 in prefill 还是 in decode？——又回到 §1 的两阶段认知。所以主干链不是死记七环，而是拿两阶段和三大瓶颈的标尺，沿链核对 你手头的每一步优化到底改善的是哪个环节。

**边界（怎么用这条链，而不是背它）**：主链路是**排障顺序**也是**阅读地图**。遇到性能问题，从链头往链尾逐步排查（权重对不对→显存装不装得下→带宽吃不吃得掉→批处理做没做→解码占不占优→是不是要分卡→服务层挡没挡）。5 章后续 02–10 篇就是沿着这条链逐环铺开——本篇是全景，先有地图，再逐块落地。

## 9. 常见坑（映射大纲点）

| 坑 | 症状 → 原因 → 修法 | 对应大纲点 |
|---|---|---|
| 只说"推理慢"不看阶段 | 两头都慢，无从下手  →  没分清 prefill 还是 decode 是瓶颈  →  先判阶段再判瓶颈（§1） | 1 |
| 把带宽瓶颈归给算力 | 加算力没提速  →  decode 被带宽卡，加算力无用  →  先查 295× 富余那条账（§1/§2.2） | 1,2 |
| 只看显存够不够 | 装得下还慢  →  只算了容量没算带宽  →  三瓶颈分开判（§2） | 2 |
| 一上来就换 vLLM / 加 GPU | 换完还慢  →  没沿主链路找是哪一环  →  沿 7 环逐环节排查（§3） | 3 |
| KV 一直算不对 | 长上下文 OOM 但说"怎么这么吃显存"  →  没沿用 02-10 同公式  →  直接套 `2×层×KV头×头维×seq×batch×字节`（§2.1） | 2 |
