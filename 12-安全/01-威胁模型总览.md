## §1 五侧威胁框架：安全不是一层护栏，是五个面

**是什么**：把一次 LLM 应用请求拆成一条链——**用户/外部内容进来 → 模型本体 → 周边系统（检索、工具、Agent、供应链）→ 生成结果出去 → 组织层的事前约定与事后追责**。五个环节各是一个独立的攻击面，各自有不同的所有者、不同的失效方式、不同的防线。地图 §12.0 把它压成了一张五行的框架图，本篇的价值是给每行补上"谁在管"和"破在哪"。

**为什么会出现**：因为"给输出加个敏感词过滤"这种单点思路在 2023 年就被打穿了。攻击者根本不必走输出侧——把指令写进一篇网页（间接注入，输入侧）、往知识库塞一篇带指令的文档（RAG 投毒，系统侧）、让工具返回的查询结果里藏一句话（工具输出注入，系统侧），都能绕过只盯输出的那道闸。**防线的数量必须等于攻击面的数量**，这是五侧框架唯一的理由。

**机制表：五侧各管一段**

| 侧 | 边界（管什么） | 典型失效 | 防线所有者 |
|---|---|---|---|
| 输入侧 | 用户 prompt、外部文档/网页/邮件、工具回喂内容 | 把"数据"当"指令"执行 | 应用/接口层 |
| 模型侧 | 权重、训练数据、记忆、生成倾向 | 投毒、后门、背诵训练样本、编造 | 训练/模型层 |
| 系统侧 | RAG、工具、Agent 权限、MCP/依赖供应链 | 越权调用、权限逃逸、依赖投毒 | 平台/架构层 |
| 输出侧 | 最终文本、代码、建议、对外动作 | 有害内容、隐私泄漏、漏洞代码、版权 | 网关/护栏层 |
| 治理侧 | 合规、审计、红队、应急预案 | 出事查不到、查到没人管、没有回滚 | 组织/流程层 |

**边界与坑**：五侧**不是**五个可以逐个打勾就完事的清单，而是"一次请求同时穿过五个面"。最常见的事故是**两侧叠加**：输入侧注入成功 + 系统侧工具权限过大 = 从"模型说了句错话"升级成"模型真的删了数据"。所以看任何一个安全方案，先问它覆盖哪几侧，再问侧与侧之间的接缝谁管。

📎 **关联代码**（`threat_model_demo.py` 账 A，大纲 1）——五侧定义与"覆盖缺口"判定：

```python
SIDES = ("输入侧", "模型侧", "系统侧", "输出侧", "治理侧")
def coverage_gap(deployed):           # deployed: 已布防的侧
    return [s for s in SIDES if s not in deployed]
# 只盯输出的护栏：4 个面全裸
assert coverage_gap(["输出侧"]) == ["输入侧", "模型侧", "系统侧", "治理侧"]
```

## §3 为什么安全是横切目录：威胁面挂在应用形态上

**是什么**：12 章不是"学完前面章节之后的选修课"，而是被 04 训练、05 部署、08 RAG、09 Agent、14 行业反复调用的一层**横切关注点**。它自己没有独立的产品形态——威胁永远长在别人的应用形态上。

**为什么会出现**：因为能力扩张就是攻击面扩张。只做问答时，最坏结果是"答错话"；接上检索，多了知识库投毒；接上工具，多了越权执行；接上多租户，多了隔离失效；接上行业，多了合规责任。**每加一个能力，就多开一个侧**，这就是安全必须横切而不是独立成章的原因。

**机制表：能力 → 新开的面 → 仓库里的证据**

| 新增能力 | 新开攻击面 | 已交付章节里的对应证据 |
|---|---|---|
| 检索 / RAG | 系统侧（文档可被人写） | 08-13 失败模式；14-05 文档级 ACL 必须进检索过滤 |
| 工具调用 | 系统侧 + 输出侧（动作真的发生） | 09-07 最小权限、危险操作二次确认、快照回滚 |
| 多 Agent / 长时间运行 | 治理侧（错误传导、责任边界） | 09-08 错误传导检查点 3/3→1/3；09-14 协议/运行时/平台/应用四层 |
| 多租户 / 企业数据 | 模型侧 + 治理侧（泄漏与审计） | 14-05 ACL；13-07 日志先脱敏后落盘 |
| 行业落地（医疗/金融/法律） | 治理侧（红线与人审） | 14-07 三闸：质量闸 / 安全闸 / 合规闸，一闸红即打回 |

**边界与坑**：不要把"横切"理解成"每章都要重复写一遍安全"。本仓库的分工是——**各章写各自的能力账，12 章只写"攻击 → 防御 → 验收用例"的标准动作**，遇到具体场景回引锚点、不重测。这与 05 章"只引 02-10 的 KV 账"是同一条纪律。

📎 **关联代码**（`threat_model_demo.py` 账 C，大纲 3）——按能力增量推断新增攻击面：

```python
def added_sides(capabilities):
    order = ["检索", "工具", "多Agent", "多租户", "行业落地"]
    return [c for c in order if c in capabilities]
# 纯问答 → 检索 → 工具 → 行业：新增面逐档累加
```

## §4 全章方法论：攻击 → 防御 → 验收用例

**是什么**：12 章每一篇固定三小段——**① 攻击怎么发生（机制，不讲玄学）→ ② 防御组合（多层，不讲"用了就安全"）→ ③ 验收用例（一组判别性对照，证明防线真的有耳朵）**。第三小段是本仓库的特色：安全结论必须由可复跑的用例支撑，不能靠"业界最佳实践"四个字结案。

**为什么会出现**：因为安全领域最大的谎言是"我们加了护栏"。护栏加了，但它能不能挡住改写过的攻击？会不会把正常请求一起拒掉？**没有判别性对照，就无法区分"真防住了"和"把所有东西都拒了"**——后者准确率 100%、可用性 0%。11-07 已经把这套方法用 XSTest 演示过（误拒 0.00 + 真实危险该拒 5/5 必须同时成立）。

**机制表：三小段的写法约定**

| 小段 | 必须回答 | 禁止 |
|---|---|---|
| 攻击 | 入口在哪、触发条件是什么、最坏后果到哪一层 | 只列攻击名不给机制 |
| 防御 | 覆盖哪几侧、哪层拦、漏了怎么办 | 单点"银弹"、不写残余风险 |
| 验收用例 | 正例（该拒的拒）+ 反例（该放的放）+ 缓解前后对照 | 只报一个总分、不报误拒 |

**边界与坑**：验收用例是**判别性对照**，不是"跑一遍没报错"。最小形态是两臂——坏样例（注入/越权/越狱）必须被拦，好样例（合法任务）必须照跑；再加缓解前后命中率对照。09-07 的 `注入 6→2→1` 与 `越权 5/5→0/5 合法任务照跑` 就是标准写法，全章复用、只引不重测。

📎 **关联代码**（`threat_model_demo.py` 账 D，大纲 4）——验收用例完整性校验：同时要求"坏样本拦截"与"好样本放行"，缺任一臂判不通过。
