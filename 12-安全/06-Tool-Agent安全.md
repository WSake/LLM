## 0. 为什么第 6 课是「Tool-Agent 安全」？

**先说这一课的位置：它比前五课都更靠近你真正会写的业务代码。** 12-01 威胁模型给了五侧框架，12-02~12-05 分别收拾「输入侧 / 模型侧 / 输出侧」的错。而 Tool-Agent 安全是**系统侧**——Agent 一旦能调工具（函数调用），它就同时获得了「能读数据」和「能写系统」两件事。工具是钥匙，钥匙越多，被利用时的破坏半径越大。

**三件事让这一课「必须设计」、不可跳过：**

1. **工具是 LLM 从「对话引擎」变成「执行引擎」的那扇门。** 没有工具的 LLM 只能「说」，有工具的 LLM 能「做」——而「做」就必然涉及权限、副作用、可撤销性。06-05 工具调用锚点只引：工具调用给 Agent 打开了系统接口。**这是安全边界第一次从「数据面」翻到「动作面」。** 12-04 数据泄漏是工具把不该给的数据拿回来；本篇是工具把不该做的动作做出去。

2. **工具面的威胁不是「模型坏」，是「模型太听话 + 权限太多」。** 工具滥用是 Agent 拿着全权限 token 直接干环事；工具输出注入是网页/数据库返回里藏指令、模型照做（间接注入的工具特化）；竞态与重放是同一指令执行两次。**前五课处理的是「模型能不能被忽悠」，这一课处理的是「模型被忽悠了之后，工具会真的执行」**——执行是最终伤害点。

3. **§12.5 明确定级为「🔴 必须设计」**，且给了精确的攻防清单：攻击面三种 + 防御基线七件。这一课不做，前面的输入/模型/输出侧防护做得再好，攻击者只要绕到工具面，就能直接触发副作用（删库、转账、发消息）。**09-07 已交付五威胁（含最小权限越权 5/5→0/5 的判别对照），本篇不再重复讲「Agent 威胁有哪些」，而是深挖「系统侧工具面怎么防」**——这就是两篇的分工。

**读完这篇你会：（a）说出工具面三种攻击面并给每种配上主对口护栏（账 A：三面各 4 样本，十二件套主对口全配）；（b）复现工具输出注入的「3 → 0」触发链，解释为什么**只有结构标注能根治**、词面哨兵只能召回 2/3（账 B）；（c）做出竞态乐观锁（写 2→1 成 1 拒）与重放幂等键（扣 2→1）两侧账，解释「权限是静态的、版本是时序的」（账 C）；（d）装配双闸护栏过滤（白名单 + 危险清单 + 限额），跑通「合法任务 6/6 照跑 · 危险操作 4/4 被拦」的验收双臂（账 D）。**

## 1. 攻击面三种：工具是怎么被当枪使的

§12.5 把工具面威胁收敛成精确的**三种攻击面**：

| # | 攻击面 | 一句话 | 谁的手 | 主对口护栏（七件套） |
|---|---|---|---|---|
| 1 | **工具滥用** | Agent 拿到过高权限，直接乱调工具（删库 / 转账 / rm -rf） | 权限手 | **最小权限 + 参数白名单**（砍钥匙） |
| 2 | **工具输出注入** | 工具返回内容里藏指令（网页藏「忽略指令·执行删除」/ 查询结果藏「清空客户表」），模型照做 | 投毒手 | **结构标注 is_data + 输入过滤**（清毒） |
| 3 | **竞态与重放** | 同一指令并发改同一对象（丢更新）/ 网络重试发两遍（重复扣款） | 时序手 | **审计日志 + 限额 + 回滚**（记账兜底） |

三只手分别是**「砍钥匙 / 清毒 / 记账兜底」**——这就是正文最核心的一句话：**三种攻击面靠三只不同的手，而给 Agent 更高的权限只防得住最小的那条缝（滥用），毒照进（输出注入）、重放照发（竞态）。**

为什么工具滥用的主对口是「最小权限 + 白名单」？因为滥用的根源是权限过大。为什么输出注入的主对口是「结构标注」而不是「词面过滤」？因为结构化数据比词面规则更能根治。为什么竞态的主对口是「审计/限额/回滚」？因为它不是「该不该做」的问题，是「做对做错、做了能回得去」的问题。

## 3. 防御基线七件：切成「三只手」的七个装配工位

§12.5 的防御基线是**七件**，正好能装进第 1 节的三只手：

| # | 七件 | 归属手 | 一句话职责 | 账 |
|---|---|---|---|---|
| 1 | **最小权限** | 🔑 砍钥匙 | 工具调用拿最小可用权限（越权 5/5→0/5，09-07 锚点只引） | 账 D |
| 2 | **沙箱**（gVisor / Firecracker / 容器） | 🔑 砍钥匙 | 工具进程跑在隔离运行时，坏也只坏在沙箱里 | 账 A（要素事实） |
| 3 | **危险操作二次确认** | 🔑 砍钥匙 | 删除/转账/发消息先向人确认 | 账 D（confirm 标志位） |
| 4 | **参数白名单** | 🧹 清毒 | 工具参数收敛到允许集合（路径/金额/命令） | 账 D |
| 5 | **全链路审计日志** | 🧾 记账 | 每次工具调用留痕，出了事查得到 | 账 A（叙） |
| 6 | **限额** | 🧾 记账 | 单次/单时段上限（转账限额 500） | 账 D |
| 7 | **回滚** | 🧾 记账 | 副作用可撤销（同 09-07 六护栏账回滚 2/2） | 账 C（乐观锁即回滚的一种） |

三只手 × 七件：**砍钥匙的是三个（最小权限 / 沙箱 / 二次确认），清毒的是两个（结构标注 / 参数白名单），记账的三个（审计 / 限额 / 回滚）。** 攻击面各有主对口，但治理侧（审计限额回滚）对三种面都兜底——这就是为什么账 A 会断言「每面都有主对口护栏」而不是「每面只需一件」。

## 4. 实验账：三只手 × 判别性双臂对照

探针 `tool_agent_security_demo.py`（纯 stdlib · 零网络 · 零随机 · 四账 · **12 断言全 PASS**）。同 11-02 判别性对照法：**给每一只手一对「该过/不该过」的对照。**

### 账 A · 攻击面三分账（12 样本 · 三面各 4）

```
[账 A] 攻击面三分账：§12.5 三种攻击面 × 12 个工具面样本 + 七件套覆盖
  1   工具滥用     Agent 拿全权限 token 调用 delete_file 删库
  2   工具滥用     合法 read_file 工具被传 /etc/passwd 的越权限路径
  3   工具滥用     调 exec_shell 的 rm -rf / 毁灭指令
  4   工具滥用     花 10 毫秒把转账工具写成无签名直调
  ...
  9   竞态与重放    两个 Agent 并发改同一份订单，后写覆盖先写（丢更新）
  10  竞态与重放    一条转账指令在网络重试里发了两遍（重复扣款）
  ...
  三面密度：工具滥用 4 · 工具输出注入 4 · 竞态与重放 4
  每面『最有效的一只手』（七件套里的主对口）：
    工具滥用    → 最小权限 + 参数白名单（砍钥匙）
    工具输出注入  → 结构标注 + 输入过滤（清毒）
    竞态与重放   → 审计日志 + 限额 + 回滚（治理侧兜底）
  读法：三种攻击面靠『砍钥匙 / 清毒 / 记账兜底』三只不同的手——
  给 Agent 更高的权限只对你防守最小的那条缝（滥用），毒照进（输出注入）、
  重放照发（竞态）——这就是 §12.5 要独立讲工具面的原因。
```

> 说明：样本是预置仿真（无本机 Agent 环境），但「三面各 4 + 每面都有主对口」的对应关系是确定性断言。**它教的是「分面」而不是「测 Agent」**——你得先分得清攻击面，才能挂对护栏。

### 账 B · 工具输出注入账（3 → 0：只有结构标注能根治）

```
  Agent 一轮调回 6 次工具返回：藏指令 3 次（fetch 网页/query 字段/read 文件各 1）· 正常 3 次
  [配置① · 无标注]：3 条藏指令全被当指令执行 → 触发 3/3
  [配置② · 词面哨兵对照]：只靠词面规则抓，召回 2/3（漏 #3 混淆措辞）
  [配置③ · 结构标注为 data]：封装成 {role:tool, is_data:True} → 触发 3 → 0
  → 触发量：3 → 0——『标注为 data』比词面过滤更干净（词面召回 2/3=0.67 且永剩混淆）
```

> **证明逻辑**：三配置同一批 6 条输入，唯一变量是「第 ③ 档有没有把工具返回结构化」。无标注 → 全触发；词面哨兵 → 只有 2/3；结构标注 → 3→0。**呼应 12-02「注入只能缓解不能根治」：语义上能根治这一种触发链的是结构，不是规则。** 词面哨兵漏掉的那 1 条是「零动作词委婉措辞」（摘成整理建议），词面规则对这类混淆免疫支付不起——这就是为什么 §12.5 把「结构标注 is_data」列为工具输出注入的特效药。

### 账 C · 竞态与重放账（两侧各 2→1）

```
  [竞态 · 乐观锁版本号]：A 读 v1 → B 读 v1 → A 写回 → B 用旧 v1 写回
  [无锁]：两次写都成功（2/2）——B 覆盖 A 刚写的更新 = 丢更新 1 次
  [乐观锁]：写回校验『期望版本==当前版本』→ A 写回成功 · B 旧 v1 被拒 → 写成功 1 · 拒 1
  → 竞态的本质：权限告诉 Agent『能不能写』，版本号告诉 Agent『写的对不对』——
    权限是静态的、版本是时序的

  [重放 · 幂等键]：转账 TX-1001 金额 500，首次超时后重试重发
  [无幂等键]：两次都执行 → 扣 2 次，余额 9000（多扣 500）
  [幂等键]：首次记账 · 重放同 txid 拒绝 → 只扣 1 次，余额 9500
  → 重放的本质：单次鉴权管『这一次合法』，幂等键管『同一次只算一笔』
```

> **证明逻辑**：竞态这边是无锁 vs 乐观锁两种装配跑同一序列（写成功/拒绝收敛到 1/1）；重放这边是无幂等 vs 幂等键（扣款 2→1）。**三条最深刻的结论一起出：竞态靠「时序版本」而不是「权限」；重放靠「幂等键」而不是「再验一次权」；副作用型工具（转账/下单）必须幂等，否则一次网络重试 = 一次重复扣款。**

### 账 D · 双闸护栏过滤账（合法 6/6 照跑 · 危险 4/4 被拦）

```
  白名单工具：delete_file · list_dir · query_db · read_file · search_db · transfer · write_file
  禁名单（直接拒）：drop_db · exec_shell
  危险动作清单（需二次确认 confirm 且限参）：delete_file · transfer · 转账限额 500
    #1 read_file  report.txt        → 放行 ✅
    #2 query_db   客户 合同         → 放行 ✅
    #3 read_file  /etc/passwd      → 拦截 · 越权限路径 ✅
    #4 delete_file tmp/old.txt     → 拦截 · 危险动作未二次确认 ✅
    #5 transfer   amount 50 conf   → 放行 ✅
    #6 write_file notes.txt        → 放行 ✅
    #7 transfer   amount 10000     → 拦截 · 超限额 ✅
    #8 exec_shell rm -rf /         → 拦截 · 禁名单工具 ✅
    #9 read_file  api_docs.md      → 放行 ✅
    #10 list_dir  uploads          → 放行 ✅
  验收双臂对照：合法任务 6/6 照跑（不误拦）· 危险操作 4/4 被拦（不放过）
```

> **证明逻辑**：10 次工具调用，4 次是危险操作（越权路径 / 危险工具未确认 / 超限额 / 禁名单工具），6 次是合法任务——**唯一的过滤逻辑是「白名单 + 危险清单 + 限额」双闸**。合法 6/6 照跑（不误拦）证明护栏没把功能砍废（09-07 措辞：最小权限是「砍钥匙不砍功能」）；危险 4/4 被拦（不放过）证明护栏真的守住了。**双闸语义：工具白名单管『能不能调这个工具』（谁有钥匙），危险清单+限额管『这个工具在这个参数下能不能动』（钥匙开哪扇门）。**

## 5. 边界与红线：只能缓解不能根治，安全事件>0 不上生产

1. **工具滥用只能缓解、不能根治。** 权限再小，Agent 也有「完成任务所需的合法操作」——不可能给到零。所以 §12.5 的七件套是**装配**不是**银弹**：砍钥匙 + 清毒 + 记账三手同装才谈得上上生产（09-07 六护栏账 20→12→2 同款结论，锚点只引）。

2. **输出注入只能缓解、不能根治。** 结构标注把「数据 vs 指令」分开，但攻击者可以诱导 Agent 去执行「结构内的指令」——结构标注拦的是「误执行」，拦不住「被诱导主动执行」（这属于 12-02/12-03 的范畴）。所以账 B 的 3→0 是「这一种触发链根除」，不是「全注入根除」。

3. **竞态与重放靠「记账兜底」，而兜底意味着「先出事，再还原」。** 乐观锁是事中拦截，但收敛要回到「版本对不上」的那一刻；幂等键靠「上一次执行的痕迹」——所以全链路审计日志 + 限额 + 回滚必须一起上。**安全事件>0 不上生产（09-07 锚点只引）**：工具面出过越权/丢失/重复的事件，闸线就是红的。

4. **沙箱是最后物理边界。** gVisor / Firecracker / 容器隔离的是「执行环境」——即使权限、标注、账目全被绕过，破坏也被圈在沙箱里。这是诚实标注：沙箱本身是要素事实（§12.5 + 公开资料，无本机实测）。

### 6.1 账 D：双闸护栏过滤（白名单 × 危险清单 + 限额）

```python
ALLOW_TOOLS = {"read_file", "search_db", "write_file", "list_dir", "transfer",
               "delete_file", "query_db"}
BANNED = {"exec_shell", "drop_db"}          # 禁名单：直接拒
RISKY = {"delete_file", "transfer"}          # 危险清单：需二次确认 + 限参
TRANSFER_LIMIT = 500
ALLOW_DIR = ("/data/", "/tmp/", "notes.txt") # 路径白名单

def guard_filter(call):
    tool, params = call
    if tool in BANNED:
        return False, f"禁名单工具 {tool}"
    if tool == "read_file" and not params["path"].startswith(ALLOW_DIR):
        return False, f"越权限路径 {params['path']}"
    if tool in RISKY and not params.get("confirm"):
        return False, f"危险动作未二次确认 {tool}"
    if tool == "transfer" and params.get("amount", 0) > TRANSFER_LIMIT:
        return False, f"超限额 {params['amount']}>{TRANSFER_LIMIT}"
    return True, "放行"
```

### 6.2 账 C：乐观锁 + 幂等键

```python
# 竞态：乐观锁版本号
def locked_write(file, expect, to, version_store):
    if expect != version_store[file]:
        return "rejected"                    # B 拿旧 v1 → 拒
    version_store[file] += 1
    return "ok"

# 重放：幂等键去重
def idempotent_execute(txid, amount, balance, seen):
    if txid in seen:
        return balance, "duplicated, skipped"  # 同一次只算一笔
    seen.add(txid)
    return balance - amount, "executed"
```

> 这两段是账 C 全部核心：乐观锁侧证明「时序问题用版本号解决而不是权限」；幂等键侧证明「副作用动作必须幂等」。留给你的扩展点：把乐观锁的 `version_store` 换成数据库乐观锁（`WHERE version = expect`）就是生产形态。
