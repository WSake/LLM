## 0. 为什么第 8 课是「工程指标·延迟/吞吐/成本」？

01 篇把评测定成**五层**：能力 / 任务 / 系统 / 安全 / 工程。到本篇为止，安全（07）以下四层都有了专项——**只剩最后一层『工程』还挂在 01 篇的那句"工程[延迟/成本]"上，没有一张自己的桌**。现在把它放大成专项，有三个非讲不可的理由：

1. **工程指标是唯一"不看答案对不对"的评测层。** 前七篇评的全是"模型那头的质量"（benchmark 分数、judge 判分、RAG 答案、Agent 轨迹、内容安不安全）；工程指标评的是"**你这台系统跑得快不快、贵不贵、稳不稳**"——同一个 RAG，答案相关率 0.90，TTFT 3 秒、每 query $0.0042、P99 用户等 30 秒，一样是"被骂死的上线"。**质量之外必须同时测**（§11.7 原句）。
2. **它最容易错的是"口径"，不是"数字"。** TTFT 和 TPOT 分不清、单请求吞吐冒充整机吞吐、均值代替 P95、输入单价当全部成本、思考 token 混进"总 token"……一个模型摆在面前，六把尺的**分子分母先摆对**，数字才有意义——所以 05 章把指标口径章（`05-10`）和本篇定为"**先讲口径再讲数字**"的同一套口径。
3. **工程指标的评测台 = 门禁，不是排行榜。** 换模型、调部署之后跑同一套混合负载，看 P95 和成本预算过不过——预算回归是 05-08 RAG 门禁 / 09-06、11-07 门禁同一个"回归刹车"思想在工程层的兑现；不给工程指标配门禁，线上出问题的不是准确率，是 P95 悄悄翻倍、成本悄悄 ×3。

**读完这篇你会：（a）说出六把工程尺的分子分母与数量关系，能一眼戳穿"TPOT 当 TTFT""单请求吞吐当整机吞吐"这种反例（账 A）；（b）会用均值/P50/P95/P99 四值看延迟分布，知道"均值君"陷阱和"只测一个长度=盲人摸象"（账 B）；（c）会算连续批处理吞吐（批 k → 整机 ×k）与三档价格单 query 账本，知道输出 token 和思考 token 才是钱的大头，Agent 按每任务记账（账 C）；（d）会给工程指标配门禁：指标×任务口径决策翻转 + P95/成本预算回归 + 错误率重试放大 + 慢请求回注（账 D）。（本篇 🔴 必会——联动 01/02/03/06/07/05-RAG 与 §5.8 与知识地图 §11.7；无专属里程碑，与 05-10 同口径。）**

## 1. 先把工程指标拆开：质量之外必须同时测的六把尺——先讲口径再讲数字（§11.7×§5.8）

§11.7 一句话"质量之外必须同时测"，§5.8 把 T 开头的那些名词钉死。两张原文拼成**六把尺的表**：

| 尺 | 量什么 | 分子/分母 | 反例（别这么报） |
|---|---|---|---|
| **① Latency** | 首 token 延迟 / 逐字时间 / 总时间 | 端到端(流式) = TTFT + (N-1)×TPOT | 用 TPOT 报首屏、用均值报延迟 |
| **② Throughput** | 单请求 / 整机 / QPS | 1/TPOT · 批数×1/TPOT · 并发/平均完成 | 单请求吞吐冒充整机吞吐 |
| **③ Token Usage** | 输入/输出/**思考** 分开 | 思考 token 单独一列 | 合报"总 token"藏思考税 |
| **④ Cost** | $/1M 输入/$/1M 输出分开 · 单query · 每任务 | (输入×P_in+输出×P_out)/1e6 | 只看输入单价（输出贵 3-4×） |
| **⑤ GPU 利用率** | 计算/显存/带宽 活跃占比 | 活跃计算秒/墙钟秒 | 只看跑没跑，不看算没算 |
| **⑥ 错误率/重试率** | 失败率 + 重试放大 | 有效调用 =(1-r)×n + r×n×重试 | 错误率 5%≈成本 5%（错） |

**第一张图：延迟的一把尺三段（为什么 T 开头要分开）：** 服务端把一次生成切成两段——**prefill**（读完整 prompt，算出首个 token，决定 **TTFT**）和 **decode**（逐字生 token，决定 **TPOT/ITL**）。所以"流式体感"其实是两把闹钟：**首屏快不快 = TTFT（长 prompt 由 prefill 决定）**；**逐字流不流 = TPOT（约 200ms 是流畅线）**。50 个 token 的输出 = TTFT + 49×TPOT。

**第二张图：吞吐的三把括号（为什么"吞吐很慢"多半是批没上）：** §5.8 说吞吐有**单请求 tokens/s** 与**整机输出 tokens/s** 之分——连续批处理（05-06 那课的算术）把多个请求的 decode 合并成一次矩阵运算：**批 k → 整机输出吞吐 ×k，单请求延迟不变**。先加批，再加机器。

**第三张图：成本的两张价签（为什么"总 token"会骗人）：** $/1M tokens 输入与**输出分开计**，输出单价通常是输入 3-4×；**思考 token（推理模型的 thinking）按输出单价记**——把 350 个思考 token 混进"总输出 570"里报，就看不见"61% 是思考税"。**Agent 任务按"每任务成本"记账**（§11.7 原句、§11.9⑤）。

**最后预告门禁（账 D）：** 工程指标不是报一次数字完事——**每次换模型/调部署跑同一套混合长度+混合并发负载**（§5.8 压测铁律），看 P95 与成本预算过不过；线上慢请求回注压测集（§11.9④ 工程版）。

## 3. 实验 A · 口径账：六把工程尺的分子分母 × 口头禅正反例判定

**口径账的套路 = 「先讲口径再讲数字」（01 篇四件套的工程版）**：六把尺各给出 量什么 → 分子/分母 → 反例，然后拿 10 个确定性算术题把公式焊死。探针里的关键判定（真实输出，10/10 PASS）：

| 判定 | 公式 | 数字 |
|---|---|---|
| Q1 端到端(50 tok) | TTFT + 49×TPOT | 0.85+49×0.12 = 6.73s |
| Q2 单请求输出吞吐 | 1/TPOT | 8.33 tok/s |
| Q3 整机连续批 16 | 16×(1/TPOT) | 133.33 tok/s |
| Q4 QPS | 并发 ÷ 平均完成 | 20÷4.0 = 5.0 |
| Q5 单 query 旗舰档 | (800×2.50+220×10.00)/1e6 | $0.0042 |
| Q6 单 query 思考档 | 思考 token 按输出价记 | $0.01095 |
| Q7 输出 token 的钱 | 220×10.00/1e6 | $0.0022 |
| Q8 GPU 利用率 | 活跃计算秒 49.5 ÷ 墙钟秒 61 | 81.1% |
| Q9 错误率重试放大 | (1-5%×1.5 倍失败重试) | 有效调用 102.5k = ×1.025 |
| Q10 端到端/首屏 | 6.73÷0.85 | 7.9×（体感不是首屏那一下） |

**这 10 题同时是 10 个反例的解药**：Q1↔"TPOT 当 TTFT 报首屏"（错——首屏由 prefill 定）、Q2↔"单请求吞吐冒充整机吞吐"（Q3 才是整机）、Q9↔"错误率 5%≈成本 5%"（账 D3 把它放大到 1.025× 调用量+长尾延迟两个通道）。

## 4. 实验 B · 延迟分布账：均值君陷阱 × 混合长度压测 × 端到端公式

**B1 均值君陷阱（为什么延迟不要只报均值）：** 30 次实测 TTFT（s）：**均值 1.16 · P50 0.93 · P95 2.66 · P99 2.98**。均值比中位数高 0.23s——因为长尾把平均拉高了；**P99 是 P50 的 3.2 倍**。**"均值君"和"P50 君"都看不见你会骂人的那一档用户**：P50 说"九成用户 1 秒内看到首屏"，P95 用户实际等了 2.66s、P99 等了 2.98s——只差 0.32s 就翻倍。**延迟报 (P50, P95, P99) 三值，均值只能当陪跑。**

**B2 记忆铁律（读 11-02 判别性对照那套，在工程层的待遇一样）：** 单测一个 prompt 是看不见这些的——混合长度实测：**短 prompt 均值 0.66s · 中 0.95s · 长 1.87s，长/短 = 2.8×**。§5.8 原句"**压测永远用混合长度+混合并发**"：只测短 prompt = 盲人摸象，上线后长文用户翻 2.8 倍的延迟你完全不知道。

**B3 端到端 = TTFT + (N-1)×TPOT（把"流式体感"钉成三段）：** TTFT 0.85s + TPOT 0.12s（120ms，在 200ms 流畅线内）：

| 输出 token | 端到端 | 首屏占比 | 流水占比 |
|---|---|---|---|
| 10 | 1.93s | 44.0% | 56.0% |
| 100 | 12.73s | 6.7% | 93.3% |
| 1000 | 120.73s | 0.7% | 99.3% |

**"首 token 快≠整体快"是 63× 的那课**：10→1000 token，端到端近线性放大 63×；TTFT 只决定开头 0.85s，后面的时间全是 TPOT×N。**交互任务盯 TTFT，长文任务盯 TPOT×N——这就是账 D1 的结果来源。**

## 5. 实验 C · 吞吐与成本账：连续批处理算术 × 三档价格单 query 账本 × 每任务成本

**C1 连续批处理（吞吐是批数的算术）：** decode 每次仍是一个矩阵，只是这一步喂几个人：

| 批 | 每步 0.12s 产 | 整机输出吞吐 | GPU 利用率 |
|---|---|---|---|
| 1 | 1 token | 8.3 tok/s | 11% |
| 8 | 8 token | 66.7 tok/s | 45% |
| 32 | 32 token | 266.7 tok/s | 87% |

**批 1→32，整机吞吐 ×32，单请求延迟不变**——还嫌慢先加批再加机器（加机器=弹费用的横向扩展）。GPU 利用率从 11%→87% 的那段空闲，就是"批没上满"的实锤（§5.8⑤）。

**C2 思考 token 分开看：** 220 个答案 token + 350 个思考 token = 570 输出——**合报"总 token"会藏 61% 的思考税**；§11.7③ 原句"输入/输出/思考 token 分开看"。**C3 三档价格·单 query 账本**（代表性示例价 $/1M，输入/输出分开）：

| 档 | 价格 | 单 query(800 输入+220 输出) |
|---|---|---|
| 轻量 | $0.30/$0.60 | $0.00037 |
| 旗舰 | $2.50/$10.00 | $0.0042 |
| 思考 | $3.00/$15.00（思考按输出价） | $0.0109（＝轻量的 29.4×） |

**输出 token 只占 22%（220/1020）却花掉 52% 的钱**——单价 4× 输出，长输出答案 = 输出件最贵（账 A 反例"只看输入单价"的算账版）；思考档把 350 思考结进输出价，单 query 直接翻成轻量档 29.4×（模型选型要算的税）。

**C4 每任务成本（§11.7⑤/§11.9⑤）：** Agent 3 步链（每步 800 输入+300 输出）旗舰档 = 3×(800×2.5+300×10)/1e6 = **$0.0150/任务 = 单 query 的 3.5×**。**逐 token 报账看不到"绕路税"（06 账 420/630/840 tok 那课），任务级记账才看得到**——这是 11-06"每任务成本指标"的成本公式版。

## 6. 实验 D · 工程门禁账：指标×任务口径决策翻转 + 预算回归三阅 + 错误率放大 + 遥测回流

**D1 指标×任务口径决策翻转（跟 02 账 C"榜单≠业务"同构）：** 同一张表两张卡——v1（TTFT 0.62s/TPOT 0.11s）与 v2（TTFT 1.10s/TPOT 0.06s）：

| 任务 | v1 | v2 | 谁赢 |
|---|---|---|---|
| 对答 5 tok | 1.06s | 1.34s | **v1（首屏 TTFT 主导）** |
| 长文 500 tok | 55.51s | 31.04s | **v2（流水 TPOT 主导）** |

**工程指标没有"哪一家更好"，挂任务的尺子才有方向**——交互产品考 v1 这类 TTFT 快的，长文档生成考 v2 这类 TPOT 快的。选型别问 "谁快"，问 "**我的任务考哪一行**"。

**D2 预算回归三阅（§11.9③ 工程版，与 05-08 RAG 门禁同构）：** 每次换模型/调部署跑同一套**混合长度+混合并发**负载，两张预算：**P95 ≤ 45s（长文） · 每 query ≤ $0.0040**：

| 版本 | TTFT/TPOT | 长文 E2E | 每 query | 门禁 |
|---|---|---|---|---|
| v1 轻量 | 0.62/0.11 | 55.51s ⛔ | $0.0004 ✅ | **被 P95 拦** |
| v2 旗舰 | 1.10/0.06 | 31.04s ✅ | $0.0042 ⛔ | **被成本预算拦** |
| v3 旗舰+输入缓存半价 | 0.90/0.06 | 30.84s ✅ | $0.0032 ✅ | **全过上线** |

**v1 首屏再快也没用（长文任务先看流水预算）；v2 更好却被成本预算拦下；v3 缓存把输入价砍半（挂靠 06-01 缓存输入半价）后全过。** 预算回归 = 换模型必须重跑的刹车。

**D3 错误率 5% ≠ 成本 5%（§11.7⑥）：** 日 100k 请求错误率 5%（5k 失败）×平均重试 1.5 次 → **有效调用 102.5k = ×1.025（+2.5% 成本）**；失败请求平均 E2E 24s = **3× 正常 8s**。"错误率才 5% 没事"——钱被重试放大 1.025×，泪在长尾延迟：P99 用户被 30s 超时拖着。**D4 遥测回流（§11.9④ 工程版）：** 线上超预算慢请求 8 条回注回归压测集，100+8=108——慢请求也是活样本（09-07 红队回流的思想搬进压测集）。

## 7. 这篇工程指标怎么用（一页带走 + 掌握度检验）

**一页带走——给你的系统按这个次序配工程指标：**

1. **六把尺先各写一段分子分母**（账 A）：TTFT/TPOT/端到端、吞吐（单请求/整机/QPS）、token（输入/输出/思考分开）、成本（输入/输出分开 + 每任务）、GPU、错误率——**10 个口径算术题全部自己手算一遍**。
2. **延迟报分布不报均值**（账 B）：**均值君陷阱**（1.16s vs P50 0.93s）+ 长尾（P99=3.2×P50）+ **混合长度压测**（短长 2.8×）+ 端到端公式分段（首屏 vs 流水）。
3. **吞吐先加批再加机器**、**成本按"输出+思考"记账**（账 C）：批 1→32 整机 ×32；输出 22% 的 token 花 52% 的钱；思考档 29.4×；Agent 按每任务成本。
4. **工程指标 = 门禁不是排行榜**（账 D）：换模型跑同一套混合负载，看 P95/成本预算过不过（v1 被 P95 拦、v2 被成本拦、v3 缓存后全过）——**慢请求回注压测集**。

**掌握度检验（读完自答）：**

1. "我的模型 TTFT 只有 0.5s，流式体验很流畅"——对吗？（只对一半：TTFT 只决定首屏，逐字由 TPOT 决定；长输出看 TPOT×N。账 B3。）
2. "延迟怎么报？"（报 (P50, P95, P99) 三值，均值陪跑——P50 0.93s 但在 30 次实测里 P99 是 3.2 倍。账 B1。）
3. "整机输出吞吐 8 tok/s 太慢，要不要买机器？"（先加批：批 32 整机 ×32 到 266.7 tok/s，单请求延迟不变；加机器是弹费用的横向扩展。账 C1。）
4. "单 query 输入 800 tok 输出 220 tok，多少钱？"（不能只答输入——输出 220 tok 花掉 52% 的钱；思考 token 还按输出价记。账 C3/C4。）
5. "换了个更准的模型，能上吗？"（跑同一套混合负载：P95 和成本预算过不过——v2 更好却被 $0.0040 预算拦下；缓存降本后 v3 才过。账 D2。）

## 8. 常见坑（做工程指标评测的 7 个）

1. **TPOT 当 TTFT 报首屏**：首屏由 prefill 决定（长 prompt 更显）、逐字由 TPOT 决定——俩闹钟，别混一个（账 A Q1）。
2. **单请求吞吐冒充整机吞吐**：整机 = 批数×单请求；批 16 是 133.33 tok/s，不是 8 条 8 tok/s 排队（账 A Q2/Q3、账 C）。
3. **延迟只报均值**：均值 1.16s > P50 0.93s，长尾用户 P99 3.2×——均值君看不见骂人那档（账 B1）。
4. **压测只测一个 prompt**：短 prompt 0.66s 掩住长 prompt 1.87s=2.8×——混合长度+混合并发是铁律（账 B2、§5.8）。
5. **只看输入单价**：输出 220/1020=22% 的 token 花 52% 的钱；思考 token 按输出价记（账 C3）。
6. **逐 token 报 Agent 成本**：3 步链 $0.015/任务=单 query 3.5× 的"绕路税"只有每任务记账看得见（账 C4、§11.7⑤）。
7. **换模型不重跑负载**：v2 更好却被成本预算拦、v1 首屏快却被 P95 拦——工程指标的门禁是"换完必重跑"，不上回归就等着 P95 悄悄翻倍（账 D2）。
