## 0. 为什么第 9 课是「可观测工具链」？

08 篇把「工程指标」做成专项的时候，有一句伏笔：**账 D4 慢请求回注的工程底座**——"线上超预算慢请求 8 条回注回归压测集 100+8=108"。但 08 篇没有回答三个问题：**那 8 条慢请求在线上是怎么被"看见"的？怎么知道它慢在哪一步？慢请求回注之后，评测集又从哪来？** 这就是本篇：**把 08 篇那句"工程自动回注"落成一条真实的观测管线**。三个非讲不可的理由：

1. **先有 trace 再有指标——没 trace 的指标只会告警不会定位。** 两套系统都告诉你"P95 翻倍了"：没有 trace 的那套停在告警，有 trace 的那套往下钻一层就看到"慢在 llm.generate 850ms"。**§11.8 原标题就是规定动作：追踪=一次请求的完整链路（LLM→检索→工具→子 Agent）。** 指标回答"漂没漂"，trace 回答"哪一步在拖"——按这顺序可观测才落地。
2. **LLM 应用的观测必须标准化，否则每接一个模型换一套字段。** OpenTelemetry GenAI 语义约定把 LLM 调用钉成 span 上的六个键（name/span.kind/gen_ai.system/request.model/input_tokens/output_tokens）——**不管底层是哪个模型，观测层看到的都是同一张脸**；Langfuse/Phoenix/LangSmith 都要么按、要么兼容它。这是"一行接入"的前提。
3. **可观测是"评测与运维的桥梁"（§17.9.3），不是选秀。** 线上 trace → 评测集（回流）、线上 judge 分数 → 质量漂移告警、线上慢请求 → 成本/延迟审计——**评测要的样本、运维要的告警，统统从 trace 来**。里程碑 `025（一行接入 Langfuse：可观测三件套）` 就是这桥的第一块板：三件套概念 + 语义约定 + 数据长什么样，本篇给全。

**读完这篇你会：（a）说出三件套（日志/追踪/指标）各管一段、10 个运维问题归对类，知道 OTel GenAI 语义约定把 LLM 调用标准化成哪六个键（账 A）；（b）会把一次 RAG 请求画成一棵 span 树——时间轴自洽、most慢子 span 定位、关键路径、并行支不叠加、LLM 生成是大头（账 B）；（c）会从 120 条 trace 聚合出 P50/P95/P99/错误率/token/成本，配 SLO 门禁，把最慢 trace 回注成回归集（账 C）；（d）会在"上平台 vs 自建最小系统"之间做选择树决策，8 个场景 8/8 命中（账 D）。（本篇 🔴 必装——联动 01/08/02/03/06-Agent/07-Agent 与 §13.7 与知识地图 §11.8；里程碑 `025`。）**

## 1. 先把可观测拆开：先有 trace 再有指标（§11.8×§13.7×§17.9.3）

三张图把可观测钉住：

**第一张图：三件套各管一段（§13.7 原文分工）——** 日志、追踪、指标回答三种不同的问题：

| 采集对象 | 回答的问题 | 重点 | 例 |
|---|---|---|---|
| **日志 Log** | 发生了什么（留痕/审计） | 输入输出（**脱敏**）·模型/版本/温度·工具调用记录 | 被护栏拦下的 prompt 原文、某次输出全文 |
| **追踪 Trace** | 一次请求的调用链（哪一步慢） | 一棵 span 树：LLM→检索→工具→子 Agent | 这条 RAG 请求里的检索→重排→生成 |
| **指标 Metric** | 整体漂没漂 / 告警 | 均值/分位数·错误率·QPS·token·成本 | P95 延迟、错误率、每日成本 |

**一句口诀：日志回答"发生了什么"，trace 回答"一次请求里哪一步在拖"，指标回答"整体漂没漂"。** 三者不是选一个——§13.7 把它们都摆在"🔴 工程必备"里，因为它们回答的是不同问题（账 A 就是考这个分类）。

**第二张图：一次请求不是数据，是一棵树（§11.8 追踪）——** 从"用户提问"到"答案"的所有子调用，是一个**父-子 span 树**：root 是整段请求（SERVER），底下挂 embedding（向量化）、retrieve（检索）、rerank（重排）、llm.generate（生成）、respond（应答）等子 span，每个 span 有自己的 start/duration。**父子时间轴必须自洽（子 span 落在父 span 区间内）= trace 是一棵合法时间树；回答"慢在哪" = 在这棵树上找最长的子 span。** 08 篇教你报 (P50, P95, P99) 三值，本篇给这三值一个来源——**每条 trace 是一行记录，聚合起来就是指标**。

**第三张图：装配（§11.8 原文）——** 平台（LangSmith=LangChain/LangGraph 生态工作台 · Langfuse=开源独立面板，与框架无关国内友好 · Arize Phoenix=OTel 标准 LLM 追踪，本地免费 · Helicone=成本代理）**vs 自建最小系统四级**：日志中间件 → trace → 指标（均值/分位数/告警）→ 评测作业（离线批量）。§17.9.3 一句话="记录每次 LLM 调用的输入输出与成本，支持回放与评测"——**可观测的终点不是面板好看，是评测集与告警都从这里来（§11.9 ④：线上遥测回流成评测集）**。

## 3. 实验 A · 三件套标签账：日志/追踪/指标各管一段 × OpenTelemetry GenAI 语义约定

**账 A 的套路 = 「给问题分类，先知道该问谁」**（01 篇"先讲口径再讲数字"在可观测层的版本：先会归类，再看数字）。10 个真实运维问题，规则机逐一归位（探针实际输出，10/10 PASS）：

| 问题 | 归 | 为什么 |
|---|---|---|
| 这次 RAG 请求『检索→重排→生成』这棵调用树长什么样 | **TRACE** | 一次请求的完整链路=一棵 span 树 |
| 上一条请求的 prompt 全文和模型回复是哪份 | **LOG** | 输入输出留痕=审计与回放来源 |
| 最近一周线上 P95 延迟走势如何 | **METRIC** | 延迟分位数的线上视图 |
| 这条 LLM 调用用了多少输入/输出 token | **TRACE** | gen_ai.usage 挂在 span 上 |
| 某次 call 花了多少钱，归因到哪条请求 | **TRACE** | 成本随 trace 归因 |
| 今天错误率比昨天高吗 | **METRIC** | 错误率是比率型指标 |
| 昨天被护栏拦下的输入原文是哪条 | **LOG** | 红线复盘要原文（09-07 的红线） |
| 这棵树里哪个 span 最慢、慢多少 | **TRACE** | 慢调用定位=看 trace 不猜指标 |
| 告警『p95<2s』现在触发了吗 | **METRIC** | SLO 检测=指标上的告警规则 |
| 线上慢请求有没有进回归评测集 | **TRACE** | 回流对象是 trace 本体（§11.9④） |

**判类口诀**：**一次请求的某一处/某一步（一个 span、一条 token 账、一次归因）→ TRACE；整体的数值 / 告警线 → METRIC；要审的原文留痕 → LOG。** 10/10 —— 先会问对地方，再看面板不迷路。

**OpenTelemetry GenAI 语义约定（§11.8 的标准化核心）：** 把任何 LLM 调用都钉成一个 span，六个必备键，探针实测 6/6 PASS：

| 键 | 值（例） | 含义 |
|---|---|---|
| `name` | `llm.ChatCompletion` | span 名字 |
| `span.kind` | `CLIENT` | LLM 调用是外部客户端请求 |
| `gen_ai.system` | `openai` | 哪个 provider |
| `gen_ai.request.model` | `gpt-4o-mini` | 请求的模型 |
| `gen_ai.usage.input_tokens` | 312 | 输入 token 用量 |
| `gen_ai.usage.output_tokens` | 128 | 输出 token 用量 |

**为什么这六个键是"一行接入"的前提：** Langfuse/Phoenix/LangSmith 都兼容这套语义约定——你的应用埋一次点，换模型、换平台，观测层看到的是同一张脸（input/output/token 用量），成本面板、评测回放都是这张脸的下游。（账 B 的 llm.generate span 就长这样。）

## 4. 实验 B · trace 账：一次请求一棵 span 树 × 最慢 span 定位 × 关键路径 × 归因

**账 B 把一次 RAG 请求画成一棵树。** 探针构建 8 个 span（root + 7 个子调用），时间轴如下（单位 ms）：

| span id | name | kind | start | duration | 起止 |
|---|---|---|---|---|---|
| s0 | query | SERVER | 0 | 1450 | 0–1450（root=整段请求的容器） |
| s1 | authn | CLIENT | 0 | 90 | 并行支（0–90） |
| s2 | embedding | CLIENT | 0 | 120 | embedding 向量化（0–120） |
| s3 | retrieve | CLIENT | 150 | 180 | 检索（150–330） |
| s4 | rerank | CLIENT | 350 | 90 | 重排（350–440） |
| s5 | prompt_build | INTERNAL | 460 | 30 | 拼 prompt（460–490） |
| s6 | llm.generate | CLIENT | 500 | 850 | 生成（500–1350）输入 312/输出 128 tok · $0.0032 |
| s7 | respond | CLIENT | 1360 | 90 | 应答（1360–1450） |

**B1 时间轴合法（自洽时间树）：** 探针逐个校验——**每个子 span 的起止必须落在父 span 区间内**，8 个 span 越界 0。trace 数据能当"证据"的前提是它自洽；采集端混了并行/乱序，定位结论就不可信。

**B2 最慢 span 定位（慢请求 80% 是『一条长 span』）：** 找树的 max：**`llm.generate` 850ms，是次名 `retrieve` 180ms 的 4.7×**。注意一个容易犯的错——root（1450ms）不算"某一步"：它是整段请求的容器 span，排查慢步骤要看它的**子**调用。慢请求只改一个变量：这棵树的慢在**生成段**，不是检索。

**B3 关键路径（为什么总时长不能被"加起来"）：** 串行依赖链 检索(120)→重排(180)→prompt(30)→生成(850)→应答(90) 累计 **1360ms = root 1450ms 的 94%**；而 authn 90ms 与 embedding 120ms 在时间轴上**并行**（都从 0 开始），并行支只算最长、不再叠加——所以 root 只有 1450，不是 1450+90。**trace 里看得见并行：关键路径=依赖链累计，并行支取 max**（08 篇"吞吐是批数的算术"在 trace 上的记账）。

**B4 归因账（trace 给的是一张摊派表，不是一个"慢"字）：** LLM 生成 850/1450 = **58.6%**，检索三件（el+rv+rr）390ms = **26.9%**。**答案不是检索慢，是生成慢**——08 篇工程量尺告诉你"P95 是多少"，trace 告诉你"P95 里谁吃了大头"，这正是"先有 trace 再有指标"的分工。**B5 并行省 90ms**：authn 挪成串行 root ≥1540ms。

## 5. 实验 C · 指标账：trace 聚合出指标 × SLO 门禁 × 遥测回流

**账 C 把账 B 的一棵树放大成 120 棵树——指标就是这些 trace 的聚合一列。** 探针按确定性公式合成 120 条 trace（纯公式无随机；尾部注入长尾峰模拟慢 span/重试），按时延排序：

| 汇总 | 值 |
|---|---|
| 延迟分布 | 均值 1168 · **P50 1108 · P95 2108（1.9×）· P99 2432（2.2×）** |
| 错误率 | 3/120 = **2.5%**（06-10 那课：24h 里必然有失败） |
| token 用量 | 输入 47180 · 输出 8220（08 篇第三把尺：输入/输出分开） |
| 成本 | 旗舰档计价 **$0.2001**（= (47180×$2.5+8220×$10)/1M，**≈$0.0017/query**）|

**C1 三层分位严格递增（08 篇账 B 在 trace 上的兑现）：** P50<2108<P99，P95/P50=1.9×——**报指标永远带三层分位**，均值 1168 反而低于 P50（长尾被拉平的样子：看均值完全看不到 P99 用户）。**C2 错误率 2.5% ∈ (0,5%)**：与 08 篇 D3 同源——错误率是计数指标，慢 trace / 失败 trace 都要被看见。

**C3 SLO 门禁（08 篇『预算回归当刹车』的线上版）：** 闸线 = **P95 ≤ 2200ms**，探针两批对照实测：

| 批次 | P95 | vs 2200ms | 结果 |
|---|---|---|---|
| 正常批 | 2108 | ✅ | **过闸** |
| 流量翻倍批 | **4216** | ⛔ | **被拦（触发告警）** |

**指标+闸线=换流量就报警**：翻倍批 P95 从 2108 跳到 4216，闸线二话不说拦住——08 篇"每次改动跑同一套回归（§11.9③）"在线上指标上就长这样。

**C4 遥测回流（§11.9 ④ 的工程终点）：** 线上最慢的 8 条 trace（2532ms 那一档）导出成回归评测集的活样本——**100 + 8 = 108**。这 8 条 trace 是最该进评测集的样本：**它们在真实负载下慢、可能伴随重试/错误，评测集缺了它们=回归时永远看不见线上那 8 条**（08 篇账 D4 同号、09-07 红队回流 4→54 的思想搬进 trace）。可观测的终点不是面板，是与评测集的回环。

## 6. 实验 D · 装配账：平台 vs 自建最小系统 × 选择树

**账 D 回答"这段观测我自己写，还是上平台"。探针给出四样东西：**

**D1 平台一句话定位（要素事实，非本机实测）：**

| 平台 | 一句话 |
|---|---|
| **LangSmith** | LangChain/LangGraph 生态的 trace+评估工作台 |
| **Langfuse** | 开源可替代：trace/评测/成本面板，**与框架无关**，国内部署友好 |
| **Arize Phoenix** | 开源：OpenInference+OTel 标准，LLM 专门追踪，本地免费 |
| **Helicone** | API 成本代理：请求转发+计费+缓存 |

**D2 自建最小系统四级（§11.8 原文，探针断言 4 级一次给全）：** 日志中间件 → trace（一次请求完整调用链）→ 指标（均值/分位数/告警）→ 评测作业（离线批量）。**可观测是流水线不是插件**：这四级可以全部自己写（个人 demo 一层中间件就够），也可以每一级换成平台（Langfuse 面板 + Prometheus 指标 + 定时回注作业）。

**D3 选择树 8/8（规则机判定，探针实测全 PASS）：**

| 场景 | 判定 |
|---|---|
| 本机个人 demo、零部署预算、想看清楚调用链 | **自建**（一层日志中间件+打点） |
| 生产多团队、要共享 trace 面板+审计回放 | **Langfuse** |
| 已全线 LangChain/LangGraph，想少接一套 | **LangSmith** |
| 合规要求数据不出域、要开源可自托管 | **Phoenix** / Langfuse 自托管 |
| 主要想量化"每次调用多少钱"做成本审计 | **Helicone** |
| 只想要延迟/错误率指标+告警，不需要 trace | **自建指标**（Prometheus 式） |
| 要离线评测作业（dataset/eval） | **评测作业**（Langfuse dataset） |
| 训练实验跟踪/模型注册 | **W&B / MLflow** |

**平台是装配不是信仰**：先自建看清自己，再按"多团队共享→开源面板 / 成本→代理 / 不出域→自托管"换平台——8/8 场景都能查到答案。

## 7. 这篇可观测工具链怎么用（一页带走 + 掌握度检验）

**一页带走——给你的系统按这个次序做可观测：**

1. **先会归类三件套**（账 A）：日志/追踪/指标各管一段，10 个运维问题先归对类；把 LLM 调用按 OTel 语义约定钉成 span（六个键：input/output/token 用量）。
2. **再画一棵 span 树**（账 B）：一次请求=一棵树，时间轴自洽、root 是容器不算一步、慢=看最大子 span、关键路径=依赖链累计、并行支取 max、归因是摊派表。
3. **然后聚合出指标 + 门禁**（账 C）：120 条 trace → P50/P95/P99/错误率/token/成本；SLO 闸线（P95≤2200ms）；最慢 trace 回注成回归集（100+8=108）。
4. **最后装配或自建**（账 D）：平台（LangSmith/Langfuse/Phoenix/Helicone）vs 自建最小系统四级——8 场景选择树给可查答案。

**掌握度检验（读完自答）：**

1. "线上 P95 翻倍了，怎么看慢在哪？"（先看 trace 树上最慢的子 span——不是 root；比如 `llm.generate` 850ms=检索 180ms 的 4.7×。账 B。）
2. "一次请求的观测长什么样？"（一棵 span 树：root=整段容器，子 span=各步骤，时间轴必须自洽；关键路径=依赖链累计，并行支取 max。账 B。）
3. "指标从哪来？"（指标是 trace 的聚合——120 条 trace → P50 1108/P95 2108/P99 2432；没有 trace 的指标只会告警不会定位。账 C。）
4. "慢请求除了告警还能干嘛？"（回注评测集：最慢 8 条 → 100+8=108，评测集最该喂的活样本。账 C4、§11.9④。）
5. "我要不要上 Langfuse？"（个人 demo 先自建一层中间件；生产多团队/共享面板/审计 → Langfuse；不出域 → Phoenix 自托管；只看钱 → Helicone。账 D3 选择树。）

## 8. 常见坑（做可观测的 7 个）

1. **先装指标，没有 trace**：P95 告警响了不知道慢在哪一步——先有 trace 再有指标，时序反了就变"只报警不定位"（账 B）。
2. **把 root 当最慢 span**：root 1450ms 是整段请求的容器，排查慢步骤要看它的子调用（llm.generate 850ms 才对）（账 B2）。
3. **把总时长当各 span 之和**：并行支（authn 90ms）不叠加，关键路径占 94%——用"总和"估耗时是对并行视而不见（账 B3）。
4. **指标只报均值**：均值 1168 反而低于 P50 1108，P99 2432 才是你会骂人的那档——永远带 (P50, P95, P99) 三层分位（账 C1）。
5. **没有闸线**：P95 2108→4216 翻倍的流量没人拦——SLO 门禁=换流量就报警（账 C3）。
6. **线上样本不进评测集**：最慢 8 条 trace 不进回归集=下次上线又清一次线上 P95——遥测回流是评测集最该喂的样本（账 C4、§11.9④）。
7. **平台选择无脑跟风**：个人 demo 上企业面板、要审计的只靠 trace 面板——选择树 8 场景可查表，平台是装配不是信仰（账 D3）。
