## 0. 为什么讲 Gemini 要从"原生多模态"讲起

读 `03-01`–`03-07` 七篇，你得到七句话：**① 目标不变+规模翻页；② 开源投成事实标准；③ 数据与对齐壁垒；④"省"机制级；⑤"省"可卖规格；⑥ 端侧另一本账；⑦ 闭源=只给能力不给权重。** 但有个东西前面七篇谁都没正面碰过：**多模态是"插件"还是"本体"？** ——01-GPT 纯文本、02-Llama 纯文本、03-Qwen 纯文本、04-DeepSeek 纯文本、05-Mistral 纯文本、06-Gemma 纯文本、07-Claude 只有视觉"输入"且闭源不可查。**10-多模态章要等读图/读语音的整套账去补**，而在 `03-模型家族` 这一章里，第一个把"看图"写进家族招牌的，就是 08-Gemini。

知识地图 §3.8 给 Gemini 的八要素速写，前两格是"**架构=原生多模态（不靠 adapter 拼接）** / **训练=多模态语料直训**"。这是它和之前所有"视觉插件"路线最硬的差别，而它正好问出一个**不依赖 Google 权重、任何小模型都能答**的问题：

> **"原生"到底在买什么？把图像 patch 也 token 化、进同一张词表直接训，和"图像先用独立编码器压成一个向量、再注入文本流"的 adapter 拼接，差在哪？**

答案的物理量是**空间寻址**：原生把图的每个 patch 留成序列里一个可被注意力按位置寻址的 token（position-addressable），adapter 把整幅图 mean 成一个向量塞进序列（信息瓶颈，哪个槽是哪个符号被抹平）。本篇 [A] 段用 02-Llama 引擎 + 一个 VQA 玩具直测这条差：**同任务同预算，原生 4-token 把"读第 k 槽是什么"答到 1.000，adapter 1-CLS 只有 0.343**。这就是"原生多模态"四个字的 toy 意义——不是更少的表示维度，是**保留空间结构的 token 流**。

顺带说清本篇在家族谱系上的位置：`03-00` 八要素模板立完，`01-06` 是架构可见的开源家族，`07` 起进"能力可见/权重不可见"的闭源 API 系，本篇是**第二家**。和 06-Gemma 的孪生镜像关系：**同样 Google、同样 8 要素模板，Gemma 卖"open weights + 端侧账本"，Gemini 卖"闭源 API + 原生多模态 + 1M 上下文"**——一个把模型拆给你装手边、一个把能力标价卖给你调用。本篇 = Gemini 侧（原生多模态主菜 + 超长上下文账），06 侧（端侧交替注意力）已由 06-Gemma 篇讲完。

> 一句话（为什么有本篇）：**背"Gemini 是 Google 的多模态大模型"帮不了你判断它的边界；理解"真·原生 = 图像 patch 也是 token，跟文本同一张表一起自回归"，并且亲手跑一个'视觉 token 压缩每到 recall 就塌 0.657 (=1.000→0.343)'的 VQA 对照，才看得清这家卖'统一 token 空间'的公司，招牌下面买的那门技术是什么。**

## 2. 怎么构造：把"原生 vs adapter"玩具成 4 槽符号图 VQA，复用 02-Llama 引擎 + 本期『init_emb』钩子

"原生多模态"抽象成能做实验的问题，需要先回答：**一张图怎么进序列**？真实 Gemini 的做法（公开 tech report 口径，非本机实测）= 图像切成 16×16 patch → 每个 patch 一个 token → 与文本 token 拼在同一条序列里、同一个自回归 Transformer 一起跑。**"同为 token、同表可查、共一个 self-attention"这就是原生。**

toy 化（本篇 `gemini_demo.py`，引擎 = 02-Llama 同款 2-block，`import llama_demo as L`）：

| Gemini 的对应物 | 本篇 VQA 玩具（toy 化） | 02 复习点 |
|---|---|---|
| 图像 patch token | **4 槽符号图**：每个槽位是一个 token id ∈ {0..7}（8 种符号），图的"内容"= 4 个 patch token 组成的子序列 | 02-01 Transformer（token 化思想） |
| 统一 token 空间（视觉与文本同一词表） | **词表 V=40 一张 Wte**：文本 token（问/数词/答案）与视觉符号 token（20..27）都在同一张表里查 embedding——**toy 版"统一 token 空间"**；文本问"符号 s"直接用 20+s 指代、答案直接复用符号 token id | 02-02 词表 / 02-11 Embedding |
| 文本问题 | 两类随机问法：`how many <sym>`（count：数整图里符号 s 出现几次，答案 ∈ 0..4）；`slot k?`（recall：读第 k 槽位是哪个符号，答案 ∈ 0..7） | 02-03 多头注意力（跨模态混合序列的 self-attention） |
| 原生直训 | 逐槽 4 token + 文本 4 token = 一条 9 位序列，监督只打末位答案 token，1200 步×bs64 直训（A1） | 02-12 预训练（next-token + 位置监督） |
| adapter 拼接（反面） | **视觉 mean-pool → 1 个 CLS 向量注入序列首**：`mean(Wve[img_ids]) @ Wproj` 占 1 个位置、文本照常进 Wte（A2） | 02-06 全连接 / 02-02 embedding 对齐（早期融合的信息瓶颈） |
| 跨模态注意力 | 从 cache 里读最后一层"答案 token 的注意力"，量化落图 vs 落文 vs 目标槽（A3） | **02-03 多头注意力（注意力权重直接可读数）** |

引擎只加了一样新东西：**`init_emb` 钩子**（本期给 02-Llama 引擎补的，`None` 走旧路径逐字节向后兼容，llama_demo 自身三遍逐位一致不动）。`fwd(tok, p, init_emb=...)` 允许外部注入"输入 embedding 整块 x"，供 adapter 的 CLS 向量占位用；`bwd` 在注入模式下把最底层梯度存进 `cache['dx0']` 交给外部回收（Wve/Wproj/Wte 文本部分的梯度由 adapter 侧 `adapter_grads` 用 `np.add.at` 同步）。这是下一篇（及 09/10-多模态）可复用的"外部特征注入"口子——和 06-Gemma 给引擎补"逐层掩码"是同级别的家族复用先例。

关键的道具是 A2 的对照构造（信息论上写死结局）：**count 问的是聚合量**（图里有几个 s，mean-pool 仍携带各符号出现次数的分布信息）；**recall 问的是位置量**（第 k 槽是哪个符号，mean 把"哪一槽是哪一个"抹平）——4 张槽位不同但 multiset 相同的图（如 [2,3,4,5] 与 [5,4,3,2]）给出同一个 CLS，recall 在信息论上无解。**原生逐槽 token 流里这些图是不同的序列，query 按槽寻址就能读对；adapter 里它们完全不可区分。** 这就是"原生买的是空间寻址"的最小化构造。

> 一句话（构造选择）：**"原生多模态"不是玄学而是 token 流取舍——把图切成 patch token 进同一词表（原生），recall 能按槽寻址；把图 mean 成一个向量注入（adapter），聚合型问法 count 能答、位置型问法 recall 必塌。02-Llama 引擎一行不动，加一个'init_emb'注入钩子就把两臂摆平。**

## 3. A 段 原生多模态最小闭环：统一 token 空间的 VQA 直训 vs 视觉压缩的丢空间寻址

脚本 [A] 段（`gemini_demo.py`，**本机实测**）：

```text
[A0] 引擎对账：两臂 bwd vs 中心差分（1-block C=16 · 每参数 20 个随机点 · eps=1e-5）
  [A0a·原生] 视觉符号与文本同一张 Wte（统一 token 空间），6 组全参 maxerr≤4.816e-11 ✅
  [A0b·adapter] 视觉 mean-pool→CLS 注入（init_emb 钩子），6 组全参 maxerr≤4.953e-11 ✅

[A1] 原生直训：4 槽符号图 + 文本问题 → 单答案 token（1200 步 × bs64 · seed_tr=1234）
  fresh 正确率：count 0.900 · recall 1.000（全新随机图+问法 n=400）

[A2] token 预算对照：同任务同预算，视觉用 4 token vs 1 token
  原生 4-token ：count 0.900 · recall 1.000
  adapter 1-CLS：count 0.994 · recall 0.343
  → 逐槽保留空间 → 按槽寻址全通；mean 成 1 向量 → count（聚合）仍可答、recall（位置）塌 0.657

[A3] 跨模态注意力读数（最后一层 · 示例 图=[6,3,4,6] 问=slot 0? 答=6）
  答案注意力的落点：落图(4 槽) 2.651 · 落文(4 token) 5.307 · 目标槽0 收到 1.920
  → 图侧占答案注意力 33%，目标槽独占图侧注意力的 72%（按槽寻址的读数）
```

四个读数，逐段解释：

1. **A0：两臂梯度都干净，adapter 是"干净路径"。** 原生臂就是 02-Llama 的 Wte 查表（不加任何钩子），maxerr 4.8e-11；adapter 臂走新加的 `init_emb` 注入 + 外部 `Wve/Wproj/Wte` 回收，maxerr 5.0e-11。**这根钩子没破坏引擎（llama_demo 自身重跑三遍逐位一致）也没破坏 adapter 的反向**——后续所有"外部特征注入"（CLIP 投影、Q-former 的 query token…）都能挂在这根钩子上对账。这是工程可信度门槛，过了才谈实验。

2. **A1：统一 token 空间直训，模型真的学会了"看图"。** 4 个视觉符号 token + 文本问题 = 9 位序列，next-token 直训 1200 步，fresh（全新随机图+问法）就 count 0.900、recall 1.000。**一个 48 维 2-block 小模型，在没给它任何"图像 encoding"结构的情况下，光靠"图也是 token"就学会了跨模态读图**——count 问"几个 s"、recall 问"第 k 槽是啥"都不需要外部断言，self-attention 自己搞定。这就是"多模态语料直训"在 toy 上的意义：**不需要专门的视觉分支，统一 token 空间自己长出读图能力。**

3. **A2：压缩一到，"位置"就没了——这是全文的实锤。** 同任务同预算，把视觉从 4 token 换 1 CLS（每张图先 mean-pool 再线性投影，压成一个向量占据序列首位）：**count 从 0.900 反而升到 0.994**（聚合量靠"平均 embedding"也能带出大致分布，压缩甚至帮它把聚合信号集中）；**recall 从 1.000 塌到 0.343**（= 掉 0.657）。原因在信息论是写死的：4 槽换成 multiset 相同的图（[2,3,4,5] vs [5,4,3,2]）给出**同一个 CLS 向量**，模型物理上分辨不出"第 0 槽 vs 第 1 槽"。**"原生多模态"买的是保留空间结构的 token 流**——视觉信息泄漏成"每个 patch 一个 token"，query 注意力可以**按槽寻址**；adapter 拼接把图压进一个向量，聚合统计仍可答、推进到精确位置的问法立刻露馅。这是 10-多模态章"patch 数 = 空间分辨率"在 toy 上的直演。

4. **A3：跨模态注意力是"位置结构"在读数据上的脚印。** 从训练好的原生模型里抽最后一层、问示例 图=[6,3,4,6]、"slot 0?"：答案位置的注意力落图 2.651 / 落文 5.307 / **目标槽 0 独占图侧 1.920（=图侧的 72%）**。图只有 4 个 token 却拿到 33% 的答案注意力，且**集中在被问的那个槽**——如果不是按槽寻址，图侧注意力会均摊到 4 槽（每个 25%）；实测目标槽 72% 说明"读图"是**注意力在混合序列里精确检索目标位置**，不是 prompt 拼接的假象。03-00 的"跨模态注意力"格在这里第一次给出了可读数。

> 一句话（A 段）：**统一 token 空间最小闭环全部成立：对账双臂 5e-11 干净（init_emb 钩子没破坏引擎）；原生直训 1200 步让 2-block 学会看图（fresh count 0.900·recall 1.000）；把视觉压成 1 个 CLS 后 count 0.994 还能答、recall 塌到 0.343——压缩丢的是空间寻址；再读到答案注意力 33% 落图、目标槽独占图侧 72%——'原生多模态'四个字在量上就是'按槽寻址的 token 流'。**

## 4. B 段 派生账：1M~2M KV 巨账 / 一张图多少 token / 全家谱

[A] 段把"原生意味着什么"（token 流 vs 压缩）讲成了本机实测；[B] 段把 Gemini 另两个招牌按公开配置 × 公式摊成账（`gemini_demo.py` [B] 段，**公开配置 × 公式，非本机实测 · 未在线复核，概数以 Google 官方卡片为准**）：

```text
[B] 派生账（公开配置 × 公式，非本机实测 · 未在线复核，概数以 Google 官方卡片为准）
  ① 超长上下文 1M~2M：KV 驻留账（02-10 母线）
     每 token 每层 KV = 2·H_kv·DH·2B · 取 L=32·H_kv=8·DH=128 一档口径（账算）
     200k 上下文 → KV 驻留 25 GiB（每 token 131,072 B）
     1M 上下文   → KV 驻留 122 GiB
     2M 上下文   → KV 驻留 244 GiB
     → 1M→2M 上下文翻倍，KV 线性翻倍；GQA/MoE 把 H_kv 摊薄（8 头 vs 128 头省 16×）

  ② 原生多模态 tokenizer 经济账：一张图 = 多少 token（16×16 patch，公开 tech report 口径）
     256×256 图 → 16×16 = 256  patch token
     768×768 图 → 48×48 = 2,304 patch token
     1024×1024 图 → 64×64 = 4,096 patch token
     → 一张 1024 图 ≈ 4096 token，比一页纸还多——多模态是『token 预算地图』的另一维

  ③ 全家谱（公开事实，非本机实测）
     Gemini1.0(2023-12 Pro/Ultra/Nano) → 1.5(2024: MoE, 1M~2M, 原生音/视频) →
     2.0/2.5(2025: Agentic, 代码执行/搜索/浏览器, thinking) → 3(2025 末, 大版本迭代)
     八要素速写：原生多模态 / MoE+超长上下文 / 多模态语料直训 / 1M+ 第一梯队 /
     thinking / 与 Google 搜索生态深度绑定 → 与 07-Claude 同属闭源 API 系
```

三本账的读法：

1. **账①：1M 上下文是 KV 巨账，Gemini 的"长"是拿显存堆出来的规格。** 每 token 每层 KV = 2·H_kv·DH·2B（02-10 母线），取 L=32、H_kv=8、DH=128 一档口径：每 token 128 KiB → 200k 上下文 ≈ 25 GiB、**1M ≈ 122 GiB、2M ≈ 244 GiB**。这数字的关键词是**线性**：从 200k 拉到 2M，KV 不是涨一点点，是×10，**2M 的 KV 驻留 244 GiB 已经是一颗大显存卡都放不下的模型级内存**。Gemini1.5 能做到（部分靠 MoE 摊激活、服务端 KV 卸载/PagedAttention 类机制），但这个"1M"名的账单就写在那——这也是为什么"长上下文"在 02-17 是四层墙技术题、在 Gemini 这里是**拿服务端资源换的产品规格**。GQA/MoE 把 H_kv 摊 16×，只是把 244 GiB 往该省的省，方向不变：**上下文再长也要在 KV 账上做减法**（02-18/02-04 复用）。

2. **账②：原生多模态的三重 tokenizer 计价——图是 token 大胃王。** Gemini 用 16×16 patch（公开 tech report 口径）：256² 图 ≈ 256 token、768² ≈ 2304、1024² ≈ 4096。**读一张 1024 图花的上下文预算比一页纸（约 1500-2000 词 ≈ 2000-2800 token）还多**；视频 1 秒若干帧×每帧 patch、音频按 tokenizer 帧长切——全模态输入的本质是**把世界都折算成 token 流，按 token 统一计价**。这与 [A] 的结论同向：**视觉进 token 空间 = 获得可寻址能力，也获得可计价账单**。这也是"为什么多模态模型普遍给视觉 token 打'高倍率'经济账"（预算地图的另一维）。

3. **账③：全家谱一句话。** Gemini1.0（原生多模态首秀）→ 1.5（MoE + 1M~2M + 原生音/视频）→ 2.x/2.5（Agentic + thinking + 搜索生态绑定）→ 3（大版本迭代）。**八要素主值集中在"上下文格（1M~2M 第一梯队）"和"多模态格（原生最强）"两格**——这两格正好是 [A]/[B] ① ②的主题。与 07 的接口旋钮观一致：thinking 也是旋钮（02-20 同账）；Agent 靠 Google 搜索生态（比 07 更"自家闭环"：搜索 = 它的 RAG 后端，非 MCP 那种开放协议）。

> 一句话（B 段）：**Gemini 的"长"和"多模态"都能算成账：1M 上下文 KV 122 GiB、2M 244 GiB（每 token 128 KiB 线性累积，GQA/MoE 摊 16×）；一张 1024 图 ≈ 4096 token（patch 16×16），比一页纸还贵——原生 token 空间 = 可寻址 + 可计价，把世界折算进同一张 token 预算地图。**

## 5. 常见坑

**① 把"原生多模态"当成"有个图像编码器"。**
原生 = 图像 patch 也是 token、同词表同序列可寻址（[A1] 直训即通）；adapter = 图压成向量注入（[A2] 压缩即塌）。**区别落在"能否按空间位置寻址"上，不落在"有没有视觉分支"。** 读 Gemini 的技术叙事，盯"patch token vs 压缩向量"，别盯着"有没有 ViT"。

**② 以为 count 过了（0.994）就等于压缩无害。**
A2 里 adapter 的 count 甚至更高（0.994 > 0.900）——因为 count 是聚合量，压缩把信号集中了。**但 recall 从 1.000 塌到 0.343**。选型错误是把"能数总数"当"能定位"。真实系统同理：早期 fusion 的压缩（BLIP-2/Q-former 少量 query token）在"计数/概括"上可能不输，在"按坐标/按位置检索"上明显吃亏——**token 预算 = 空间分辨率**（10-多模态章的主题在 toy 上已现形）。

**③ 把"1M 上下文"当"模型更强"而不是"KV 更贵"。**
账①：1M 上下文 KV ≈ 122 GiB（每 token 128 KiB 线性累积），2M = 244 GiB。**长上下文的瓶颈是可算的显存账，不是"注意力更聪明"**；Gemini 能卖 1M 靠的是 MoE 摊激活 + 服务端 KV 卸载 + GQA 摊 H_kv（02-10/02-04/02-18 复用），每一把省的都是这个账上的项目。**读"上下文翻倍"先乘一遍 KV 账，再决定要不要追。**

**④ 忘了"一张图 = 多少 token"。**
账②：1024 图 ≈ 4096 token，比一页纸上限还多；视频更狠（帧×patch）。**"给模型贴张图"的下游成本是 token 计价的上下文占用**——在做 Agent/RAG 预算时这一维经常被漏，而 Gemini 这类原生模型恰恰是把图像拉进文本计价带最彻底的（统一 token 空间 = 统一账单）。**多模态预算 = 每模态 token 单价 × 体量，不是"塞一张图免费"。**

**⑤ 把 thinking / 搜索绑定当"功能"而不是"旋钮 + 生态"。**
thinking 模式跟 07 的 extended thinking 是同一颗旋钮（02-20：思考 token 按输出计费）；Google 搜索集成 = 它的 Agent/RAG 后端，跟 MCP 那种开放协议不同（封闭生态 vs 开放协议）。**读 Gemini 的 Agent，看的是"搜索后端回填上下文的成本结构"，不是功能列表。**

**⑥ 忽略"孪生镜像"：Gemini 与 Gemma 是一棵树的两种卖法。**
06-Gemma 给 open weights + 端侧账本（交替注意力、int4 装载）；08-Gemini 给闭源 API + 原生多模态 + 1M 上下文。**同厂同研发线，卖法不同：Gemini 卖能力与账单，Gemma 卖可拆可装的权重**。选型时"要不要自部署"远比"Google 还是 Anthropic"更能区分二者。
