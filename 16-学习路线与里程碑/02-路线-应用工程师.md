## §1 六支应用知识树：向上长，不是向下扎

**是什么**：地图 §18.2 把应用工程师拆成六支——**基础（API + 应用概念）/ 知识工程（核心）/ 框架层 / Agent（核心）/ 工程化 / 业务**。与算法树对照很直白：算法树往模型内部走（原理、训练、评测），应用树往系统外部走（检索、编排、Agent、服务、产品）。

**为什么会出现**：因为应用侧最容易踩的坑是**把框架当能力**——会调 LangGraph 不等于会设计 Agent 的护栏与评测会，会装向量库不等于会判断检索为什么错。六支树把"工具"和"能力"分开：框架层只是其中一支，且不构成壁垒。

**机制表：六支 × 核心内容 × 本仓库落点**

| 支 | 核心内容 | 本仓库落点 |
|---|---|---|
| 基础 | API/流式/重试/成本 · Prompt · Context · Structured Output · Tool Calling | [06-应用开发](../06-应用开发)（6 篇成品） |
| 知识工程 | Embedding / Reranker / 向量库 / Hybrid-BM25 · 文档解析 / Chunking / 元数据 · RAG 进阶 + RAGAS 评测 | [08-RAG体系](../08-RAG体系)（12 篇成品） |
| 框架层 | LangGraph / LlamaIndex / LangChain / DSPy / Haystack · 低代码 Dify/Coze · 观测 Langfuse | [07-应用框架](../07-应用框架)（13 篇成品） |
| Agent | Loop / ReAct / Planning / Memory / MCP · Multi-Agent / Computer Use / Coding Agent · 评测与护栏 | [09-Agent体系](../09-Agent体系)（11 篇成品） |
| 工程化 | Serving（vLLM/SGLang）· TTFT/TPOT · K8s/Ray · 网关 · 可观测 · LLMOps 与数据回流 | [13-工程化与基础设施](../13-工程化与基础设施)（9 篇成品） · [05-推理与部署](../05-推理与部署) |
| 业务 | 企业知识库/客服/流程/代码助手 · HITL / 合规 / 成本 / 体验 | [14-垂直领域](../14-垂直领域)（8 篇成品） |

**边界与坑**：六支**不是流水线**，不需要"学完 06 再学 07 再学 08"。真实项目是倒着驱动的——要做知识库 MVP，会同时用到 06 的 API、08 的分块、11 的评测；树只是查漏补缺的坐标。另一个坑是把"业务"支留到最后：HITL 与合规是产品形态的决定项（14-07 三闸：质量/安全/合规，一闸红即打回），不是上线前的补丁。

📎 **关联代码**（`applied_roadmap_demo.py` 账 A，大纲 1）——六支完整性 + 两支"核心"标记。

## §2 四级路线：每一级换一种产品形态

**是什么**：地图 §18.4 应用路线表——按投入年限分四级，里程碑从"能做出 Demo"逐级升到"能定义团队架构"。本讲在原表右侧补"本仓库对应章节"列。

**为什么会出现**：因为应用侧的能力跃迁体现在**产品形态**上，而不是知识点数量上。知识库 MVP 是单链路，生产级 RAG 多了评测门禁，客服 Agent 多了护栏与回流，数字员工平台多了组织级架构——每一级都要求把上一级的"能跑"升级成"能被管理"。

**机制表：应用路线四级**（级别/年限/里程碑/代表项目 = 地图 §18.4 原文；仓库列 = 本讲整理）

| 级别 | 时间(投入) | 里程碑 | 代表项目 | 本仓库对应章节 |
|---|---|---|---|---|
| 初级 | 0-1 年 | 熟练 API+Prompt+结构化输出；能做简单 RAG；写过工具调用 | 企业知识库 MVP（Dify 或 LlamaIndex） | [06-应用开发/01-Model-API与流式.md](../06-应用开发/01-Model-API与流式.md) · [06-应用开发/05-Function-Tool-Calling.md](../06-应用开发/05-Function-Tool-Calling.md) · [08-RAG体系](../08-RAG体系) |
| 中级 | 1-2.5 年 | RAG 全栈优化（混合检索/重排/评测）；能搭带状态的 Workflow/Agent | 生产级 RAG（含 RAGAS 评测门禁） | [08-RAG体系/03-混合检索与重排.md](../08-RAG体系/03-混合检索与重排.md) · [11-评测与可观测/05-RAG评测.md](../11-评测与可观测/05-RAG评测.md) · [07-应用框架](../07-应用框架) |
| 高级 | 2.5-4 年 | 设计多 Agent 系统并有评测与安全护栏；MCP 服务开发；成本工程 | 客服 Agent（含护栏+评测+回流） | [09-Agent体系/07-Agent安全.md](../09-Agent体系/07-Agent安全.md) · [11-评测与可观测/06-Agent评测.md](../11-评测与可观测/06-Agent评测.md) · [11-评测与可观测/08-工程指标-延迟-吞吐-成本.md](../11-评测与可观测/08-工程指标-延迟-吞吐-成本.md) |
| 专家 | 4+ 年 | 定义团队架构与数据飞轮；AgentOps 平台建设；垂直行业方案 | 行业数字员工平台；Agent 评测基础设施 | [13-工程化与基础设施](../13-工程化与基础设施) · [14-垂直领域](../14-垂直领域) · [11-评测与可观测/10-评测工程最佳实践.md](../11-评测与可观测/10-评测工程最佳实践.md) |

**边界与坑**：与算法线一样，年限是投入刻度不是认证；跳级看里程碑不看年头。应用线特有的坑是**把"用了多少框架"当进度**——中级到高级的分界是"评测与护栏是否成为系统的一部分"，不是"换了个新框架"。

## §3 锚点映射：一个项目要动用哪几章

**是什么**：把 §2 的四个代表项目，逐条拆成"开工前该读哪几章"的清单。**项目是跨章的**——这是应用线和算法线最大的差别：算法项目往往落在 02/04 两章内，应用项目天生横跨 06/08/09/11/13/14。

**为什么会出现**：因为读者拿到"做个客服 Agent"这种任务时，最容易按目录顺序从第 1 篇读起。清单给的是**最小必要集**，让人先跑通再补洞，符合 16-01 的「先项目后论文」。

## §4 交叉地带预告：两条线在哪里汇合

**是什么**：地图 §18.3 列了八项两条线**都必须懂**的共同基础——推理与 Serving、评测体系、数据工程、Context/长上下文、成本模型、安全基础、微调基本盘、MCP/工具协议。一句话收束：**算法向下扎（原理+训练），应用向上长（系统+产品），在「推理成本、评测、数据、安全」四块地带上汇合。**

**为什么会出现**：因为两条路线在中高级会撞到同一批问题。应用侧调不动延迟时，需要懂 KV Cache 与量化（05 章）；算法侧报出模型提升时，需要懂业务指标与成本（11-08）。提前标出汇合点，读者才不会把对方领域当"别人的事"。

**机制表：八项交叉 × 谁更依赖**

| 交叉领域 | 算法侧用途 | 应用侧用途 | 本仓库落点 |
|---|---|---|---|
| 推理与 Serving（KV/量化/vLLM） | 推断成本 | 选型与压测 | [05-推理与部署](../05-推理与部署) |
| 评测体系 | 迭代模型 | 迭代系统 | [11-评测与可观测](../11-评测与可观测) |
| 数据工程 | 训练数据 | 知识库数据 | [04-训练体系](../04-训练体系) · [08-RAG体系](../08-RAG体系) |
| Context / 长上下文 | 窗口训练 | 上下文工程 | [02-核心原理/17-长上下文-四层技术路径.md](../02-核心原理/17-长上下文-四层技术路径.md) · [06-应用开发/03-Context-Engineering.md](../06-应用开发/03-Context-Engineering.md) |
| 成本模型 | 选架构 | 选方案 | [11-评测与可观测/08-工程指标-延迟-吞吐-成本.md](../11-评测与可观测/08-工程指标-延迟-吞吐-成本.md) |
| 安全基础 | 模型责任 | 产品责任 | [12-安全/01-威胁模型总览.md](../12-安全/01-威胁模型总览.md) |
| 微调基本盘 | 主业 | 判断"要不要微调" | [04-训练体系/06-全参微调与PEFT-LoRA-QLoRA.md](../04-训练体系/06-全参微调与PEFT-LoRA-QLoRA.md) |
| MCP / 工具协议 | 评估模型工具能力 | 直接使用 | [07-应用框架](../07-应用框架) |

**边界与坑**：交叉 ≠ 都要深入。对每一项，两条线需要的**深度不同**：例如量化，算法侧要懂 PTQ/QAT 与精度损失，应用侧只要会读显存账和选型表。16-03 会用"问题 → 该由谁答（算法/应用/共同）"的判定把这个差别讲透，本篇只做预告。
